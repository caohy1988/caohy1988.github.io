RFC · end-to-end demo · one live runRFC · Detailed RFC

Write it down. Publish it in BigQuery. Prove the agent’s number.

The problem: an AI agent can find the right metric definition and still report a number nobody can defend: an old formula, unapproved data access, no proof its query was the approved one.

  • Proposed feature · spike code, not a product
  • Synthetic data · one run
  • Real BigQuery, Knowledge Catalog and IAM calls

In 30 seconds

What breaks today

Found is not trusted.

Search finds a likely definition, not the exact version with its rules. Nothing records who let the agent in or whether its query was approved.

Authoring + discovery

Open Knowledge Format + Knowledge Catalog

Finance writes definitions, rules and the approved calculation as Open Knowledge Format files. Knowledge Catalog lets agents find them; each entry names the published version to use. A directory, not the authority.

Serving authority

BigQuery Knowledge Publish

BigQuery stores a fixed, read-only version, reads every row back to check it, marks it ready and switches the “current version” in one step. Agents are served from BigQuery.

What the live run proved

One live run published in BigQuery, then the agent discovered, used, verified, and was revoked — successfully.

Why all three, not one

Each part alone leaves a question unanswered.

The RFC asks three questions of any number an agent reports; only all three parts together answered them.

The path, step by step

Seven steps, one live run.

The RFC’s 118%-versus-96% retention slide is illustrative. This run puts the same checks (definition with its rule, access, receipt) live on Acme, an invented retailer. The agent is asked: What was Acme’s gross margin for January 2026, and can I trust the number?

  1. 1

    Open Knowledge FormatReplayable context

    Author the knowledge

    Finance writes down Gross Margin (full cost, explicitly not the old product-cost-only formula), the policies it cites and the one approved SQL calculation.

    In the run: the pinned files compiled into 44 linked items. ▶ 0:04

  2. 2

    BigQuery Knowledge PublishReplayable context

    Publish it in BigQuery

    BigQuery writes a fixed version, reads every row back, marks it ready, then switches the “current version” pointer in one step; only a ready version can become current.

    In the run: 19 BigQuery jobs; ready after 19 seconds, switched 6 seconds later. ▶ 0:11 ▶ 0:27

  3. 3

    Knowledge CatalogReplayable context

    Discover it in Knowledge Catalog

    Only after the switch is a Catalog entry written, pointing at that exact version. The agent’s tool reads the entry itself, as the agent’s restricted account.

    In the run: denied before access was granted, allowed after. ▶ 0:27

  4. 4

    AgentExplainable access

    Retrieve under the agent’s own access

    The agent pins the named version and retrieves the definition, linked rules and approved calculation from BigQuery, never with the owner’s credentials.

    In the run: all under one restricted account. ▶ 0:40

  5. 5

    ReceiptVerifiable execution

    A receipt checks the number before release

    The approved calculation runs as a BigQuery job; a receipt ties job, query, context and result, and the number is released only if it checks out.

    In the run: $400.00, verified, released. A swapped query, a hidden rule and unreadable output were each refused. ▶ 0:49 ▶ 0:52

  6. 6

    RevokeExplainable access

    Revoke, and the door closes

    Access is removed. A fresh request, a shortcut through the version already pinned, and the receipt already stored must all fail.

    In the run: all three refused; no new calculation launched. ▶ 1:10 ▶ 1:19

  7. 7

    AnswerAll three outcomes

    The agent gets the answer, not the plumbing

    The agent receives the number and verdicts, no IDs, SQL or account names; test tables and entry are deleted.

    In the run: what was served matched what BigQuery published. ▶ 1:24

What we proved · what is still open

Shown once. Not ready.

Shown once, on synthetic data

  • BigQuery acted as the publish authority: a checked, ready version became current in one step.
  • Knowledge Catalog pointed the agent at exactly that version, read under the agent’s own access.
  • The number was released only with a verified receipt.
  • Revocation held against a fresh request, an old pin and a stored receipt.

Still open

  • The same access checks inside BigQuery Graph queries; this run used plain SQL.
  • An independent attester; this run used the SDK’s own checker.
  • Repeated runs, cost, latency and real customer data.
  • Publishing a new revision, and the full sync protocol between BigQuery and Knowledge Catalog.

The decision this supports is on the RFC; the design is in the Detailed RFC.

Technical limits (named, not waived)

  • Graph: retrieval and access ran on relational SQL over the published tables, not BigQuery Graph / GQL; access inside graph queries is still open.
  • Attestation: the SDK example’s own verifier with a requester-held key; no independent attester.
  • Revision: the publication id is content-addressed from the pinned source, so this run deployed the same id the long-lived spike dataset holds into a fresh run-owned dataset: a new deployment, not a new revision of the knowledge.
  • Cross-service protocol (Detailed RFC §05): simplified to one owned dataset with active_publication; no sync_id staging, deployment_heads, *_current views or Catalog lag SLO.
  • Access setup: the harness grants the requester Catalog viewer and dataset reads for the run and removes them to revoke; the denied-intermediate case uses an injected legacy seed on the long-lived _rls copy, not a Catalog discovery.
  • Sample: n = 1, synthetic data, no cost or latency benchmark. Earlier runs stay as recorded: e2e-20260915t070643z-9ddaf35f (consume-only, report) and e2e-20260915t065449z-98e21004 (E2E_BROKEN).
