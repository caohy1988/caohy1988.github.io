BIGQUERY / 3–4 MIN READ

Illustrative scenario · invented company, people & numbers

The board pack says 118%.
Retention is 96%.

8:55 a.m. Maya Chen, VP of Finance at subscription software company Alder, opens the board pack for a $4 million plan to expand sales to existing customers. The meeting starts in five minutes. Her agent calls 118% retention “verified.” An analyst spots new customers in the calculation. Revenue from existing customers fell 4%.

Maya pulls the slide. Three questions go unanswered. The agent found Finance’s definition but missed the accompanying rule: count revenue only from customers there at the start. It reused a total-ARR query; Maya cannot trace the policy allowing this agent to use that asset. And no execution receipt connects the query, the declared retention calculation and the reported result.

Why BigQuery · proposed runtime · early experiments

What BigQuery adds to the story.

Knowledge Catalog (KC) discovers and governs. Open Knowledge Format (OKF) authors the graph.

Especially strong when the facts an agent needs already live in BigQuery on Enterprise or Enterprise Plus capacity, within a latency, freshness, concurrency and cost budget the customer has agreed to. What works today: three recorded experiments, all on invented data. A graph walk finds linked rules. A receipt check ties a query to its result. And on 7 September a chain began at a live catalog read, fed that receipt check from governed retrieval on invented Acme data, and refused a swapped query; nine further chains then tested republishing, stale pins and tampered payloads on an entry we created for the test. Both runs used plain SQL rather than the graph walk and ran under one operator on both legs. What we still need to prove: the same chain inside graph queries, for a second identity and a policy decision, on real cohort data. That is the pilot’s job.

01 Replayable context

Same retention definition, cohort rule and declared computation.

KC + OKF

KC discovers; OKF authors the graph. Similarity ranks candidates; it does not pin linked context. The retriever assembles it.

+ BQ runtime

Host the OKF projection. Pin a publication; use explicit SQL or bounded walks. Fix query, parameters, fact versions, access scope and ordering → same selected context and shape.

Vector search can be deterministic. Replayable context does not promise identical LLM answers. See the recorded graph walk: it behaved correctly in every case we tested. Speed benchmarks and access checks inside graph queries are still to come.

02 Explainable access

Maya can trace why this agent could use the total-ARR asset.

KC + OKF

Custom-entry access uses an EntryGroup boundary today. Per-node policy evaluation is separate.

+ BQ runtime

Join identity ↔ policy ↔ projected assets. Bind the requesting user/agent to the execution identity. Enforce access along the retrieval path; record which nodes were returned to whom under which policy.

Access metadata needs enforcement. Keep source permissions current; metadata access does not grant file access. A separate, deliberately restricted identity passed five access-denial checks on the SQL path. The same checks have not yet run inside graph queries.

03 Verifiable execution

Maya can check whether the board number used the retention calculation.

KC + OKF

Finding the definition and its computation declaration does not prove the calculation ran.

+ BQ runtime

Run retention; validate a job ↔ context ↔ result receipt against the declared computation. A substituted query or missing evidence leaves the number unproven.

A job ID alone is not enough. See the recorded receipt check: one worked example ties the query, its inputs and its result together and withholds the number when they do not match. In the recorded Acme chains, retrieval fed that check instead of a person; they began at a live catalog read, but ran under one operator on both legs and used plain SQL rather than graph queries. The wider demo does not have that check yet.

Later, Maya could ask:

Which definition, cohort rule and calculation did the agent receive? A saved context record would identify the selected versions and links.

Which identity and policy permitted access at the time? A protected access record would explain the check; reading it later still requires permission.

Did the job match Finance’s declared calculation and the displayed number? A checked execution receipt would show the evidence, a mismatch, or why the result remains unproven.

These are goals for the connected pilot. Each answer holds only while that evidence is retained and the reader is permitted to see it now; none explains the model’s private reasoning.

Graph walks need Enterprise or Enterprise Plus capacity. A projected graph can be the first workload there once its inputs are loaded, but the strongest case is a customer whose facts are already in BigQuery. Ordinary SQL and vector retrieval also run on-demand.

Technical designProposed integration · early experiments

This is a proposed integration, not a product. The OKF bundle stays the authored source. BigQuery would host a projection of each publication: its nodes, its edges and its versioned facts. So far we have three recorded experiments, all on invented gross-margin data for a fictional company called Acme. A graph walk retrieves linked rules. A receipt check ties a query to its result. And on 7 September 2026, chains ran from a live catalog read through governed retrieval to that receipt check: retrieval handed over the declared calculation, the receipt check ran it, and the number was released only after it verified. Those chains used plain SQL rather than the graph walk and ran under one operator on both legs, so no second identity or policy decision was involved. The chain section below has the detail.

Retrieve a fixed context

Start at Finance’s retention definition and follow its authored links to the cohort rule and the computation declaration, using plain SQL or a walk with a fixed depth. Everything that shapes the answer is pinned in advance: the publication, the query and its parameters, the fact versions, how far the walk may go, how ties are broken, and the order and shape of what comes back. Nothing time-dependent or unversioned goes in. Those inputs and the returned node IDs are written to a retrieval receipt. The receipt explains which context was chosen. It does not prove retention was computed, and it does not promise the model gives the same answer twice.

We have run this once, in the recorded graph walk, on a measured Enterprise reservation. Starting from a retired definition, the walk followed two links to the sanctioned SQL and produced an impact list that matched a plain relational cross-check. It also coped with placeholder, ambiguous and out-of-scope entries, which we added to a deliberately awkward test bundle because Acme’s own backlog had none. The run used generally available vector search plus graph queries; graph-native semantic search is a separate Preview option we did not test. Two limits. The walk itself only finds the sanctioned SQL and does not run it; the chains below did run it through the receipt check, under one operator, but from plain SQL retrieval rather than from this walk. And this walk’s own starting point was still pinned by hand; it is those chains, not this walk, that resolved their pin from a live catalog read, still on plain SQL and still under one operator. Code and README for the graph walk.

Evaluate current access

The requesting user or agent is authenticated, and that identity is bound to the identity that actually runs the query. Access is then decided by joining three things: who is asking, what the current policy says, and which projected assets the walk wants to touch. Permissions are enforced along the retrieval path, not only at the door, and the record notes which policy version applied and which nodes went back to that requester. Pinning a publication never bypasses current authorization. Seeing metadata about a file does not grant access to the file, and a shared service account on its own cannot tell us it was Maya’s agent asking.

We have tested part of this. On 6 September 2026 we gave a separate, deliberately restricted identity access to the same protected tables and ran five checks on the SQL retrieval path. All five passed. A rule hidden in the middle of the chain stayed hidden. A bundle that identity was not allowed to see came back with no denied node or section identifiers, in either the reply or the error message. With search denied, no output came back, even though that identity could still count rows in the seed store. No request quietly fell back to the owner’s credential. And when we revoked access before replaying a cached request, the replay failed closed. Before running the checks we confirmed the same identity could complete an allowed request, so a pass meant a real denial rather than a broken setup, and afterwards we removed the temporary grants and read back that they were gone (access case records; summary and limits).

What we could not yet do is run those same five checks inside graph queries. That needs an Enterprise capacity window, and this run could not open one. Two other questions are still open: under the operator’s own identity we could not confirm that no hidden identifiers leak, and protection across mixed publications has not been proven on a live run (open items in the graph walk report). These gaps are separate from the receipt check’s own caller-binding and revocation tests, which cover one job’s owner and one dataset grant, not per-node graph authorization. The chains below ran under one operator on both legs and on plain SQL, so they add nothing to these access questions. Work since then on a deliberately restricted requester exists only as offline tests, which is not a live enforcement result.

Validate the calculation

Retention is computed in its own step. The BigQuery job, the exact query and parameters, the input versions, the pinned context and the result are bound together in a computation receipt. That receipt is then checked against the declared retention calculation. Swapping in total ARR, as in Maya’s story, must fail that check. A retrieval receipt or a job ID on its own is not enough. If the evidence is missing, the number stays unproven.

We have run this once too, in the recorded receipt check. The BigQuery job was owned by the caller. The job and its result were read back from BigQuery itself and verified in a fresh process, and a consumer released the result only after the check passed. Wrong-query, wrong-parameter, tampered, replayed and missing-evidence cases all released nothing (case records). The limits: it ran under the requester’s own delegation, with a signing key held locally, on one small invented gross-margin fixture. We have not yet shown an independent verifier, portable signatures or general accounting correctness. A passed check says the evidence for that one example holds up; it is not a product-readiness claim. The wider demo’s computation checks are still placeholders, so its receipts cannot be verified yet.

Discovery, retrieval and calculation as one chain

On 7 September 2026 the chain started where the design says it should: a live read of a catalog entry. It ran on Acme’s invented gross-margin data under one operator holding both legs, so the access step was still not tested against a second identity or a policy decision, and retrieval still used plain SQL on demand rather than the graph walk. The read listed the entry group, matched one entry by name and fetched its runtime aspect. The pin that came back was then checked field by field against configuration we already trust, so a catalog entry can confirm which publication to use but cannot point the chain at a different project or dataset. From there the chain resolved the pin against the stored publication, compiled the pinned source as its trusted copy, retrieved the declared gross-margin calculation and its SQL through governed retrieval, and checked every returned node, edge and governance field against that trusted copy before binding. Only then did it hand the calculation to the receipt check, which ran the job under the caller and verified it in its own process, and the consumer released the number only after that check passed. The approved case released; a substituted query was refused by the verifier; a mismatched declaration was refused before anything ran. Retrieval read Acme’s publication in BigQuery; the receipt ran on the receipt example’s own small fixture dataset; the declaration file’s hash is what joined the two. All 23 jobs that run submitted shared one requester (chain record; how these runs work and their limits).

Nine more chains then ran the same way — same operator, same plain SQL — against an entry and a dataset we created for the test, because the original entry must not be republished or deleted. They moved the published head to a second version while a request was in flight, and the request still served the version it had pinned, exactly. They withdrew a publication the catalog still pointed at, removed a required rule, and pinned a publication and a seed that did not exist; each of those chains stopped at the step that failed, with no calculation and no receipt. A valid pin was then restored and the chain connected again. Two payloads we tampered with ourselves, after BigQuery had returned them and before the guard saw them, were both refused before the receipt check ran; BigQuery did not return a torn publication. Afterwards the test entry and dataset were deleted and their absence read back, the original entry was unchanged, and all 170 jobs those runs submitted were read back one at a time: each had finished, under one identity (what each of the ten cases showed; the job-by-job identity readback).

What these chains do not show. Both legs ran under one operator, so they say nothing new about a second identity, a policy decision or an independent attester. Retrieval used plain SQL on demand, not graph queries, which still need an Enterprise capacity window. The catalog they read is our own, seeded earlier for the experiment, not a customer’s. The number released was Acme’s invented gross margin, not Alder’s retention; the receipt still ran on the receipt example’s own small fixture; and the formula swap was that example’s fixed case, not Maya’s total-ARR query. An earlier chain on 6 September covered the same middle segment from a starting point we chose by hand rather than a catalog read. These runs do not change the assessment above.

Where the evidence stands

All three experiments are merged into their code bases and were reviewed. The receipt check is example code and tests, with no change to the underlying library; the reviewer’s approval note discloses that the same reviewer also wrote the final fix. The graph walk’s speed benchmarks are not finished (0 of 9 cells complete). Its Enterprise reservation was recorded as torn down; that records the reservation, not every pending job or fixture resource. The later access checks used temporary grants on one fixture, removed and read back after the run, which is a narrower cleanup record than the reservation teardown. The catalog runs’ cleanup was rechecked against the cloud afterwards rather than taken from the run’s own report. We keep evidence labels per comparison. No customer has yet agreed an operating budget. The broader case, BigQuery as a general serving layer for the Catalog, is weaker than the scoped case above.

We will call the connected path proven only after one chain runs end to end: catalog discovery, a pinned publication, governed retrieval, a computation delegated by the caller, a receipt bound to the result, and a consumer that enforces it. That chain also needs tests for publication consistency, denied intermediate nodes, revocation before cached replay and unauthorized output. The 7 September chains cover more of that list, from a live catalog read through a pinned publication to an enforcing consumer, and they add the publication-consistency tests, including payloads we tampered with ourselves after BigQuery returned them; they still ran under one operator and on plain SQL in place of graph queries. The separate-identity checks cover the other three tests, each in isolation and outside any chain. Neither clears that bar, and together they do not yet either. Receipt work should not wait for the graph benchmark. We reassess the opportunity at the 19 September 2026 checkpoint. It narrows if budgets or Enterprise cost prove unacceptable, if simpler retrieval meets the need, if semantics, authorization or publication guarantees fail, or if result evidence cannot be bound and enforced. Platform boundaries: BigQuery editions, graph placement.

The proposed BigQuery runtime would turn the OKF graph into replayable context for agents—with explainable access and evidence that the declared computation ran.
