BIGQUERY / 3–4 MIN READ

Illustrative scenario · invented company, people & numbers

The board pack says 118%.
Retention is 96%.

8:55 a.m. The VP of Finance at subscription software company Alder opens the board pack for a $4 million plan to expand sales to existing customers. The meeting starts in five minutes. Her agent calls 118% retention “verified.” An analyst spots new customers in the calculation. Revenue from existing customers fell 4%.

The VP pulls the slide. Three questions go unanswered. The agent found Finance’s definition but missed the accompanying rule: count revenue only from customers there at the start. It reused a total-ARR query, and she cannot trace the policy allowing this agent to use that asset. And no execution receipt connects the query, the declared retention calculation and the reported result.

Why BigQuery · proposed runtime · early experiments

What BigQuery adds to the story.

Knowledge Catalog (KC) discovers and governs. Open Knowledge Format (OKF) authors the graph.

Especially strong when the facts an agent needs already live in BigQuery, on Enterprise or Enterprise Plus capacity, inside a latency, freshness, concurrency and cost budget the customer has agreed.

What we know works. Retrieval can select a definition together with the rules it links to, so an agent gets the cohort rule as well as the headline metric. A receipt can bind a query to its result and withhold the number when the two disagree. And the whole path has run end to end — retrieval into a checked computation into a consumer that releases nothing unless the check passes — including one run whose retrieval went through graph queries on Enterprise capacity — that one under a single identity, from a starting point we chose rather than one discovered through the catalog, and only for the case expected to succeed.

All of it ran on invented data — never a customer’s cohort. And because the graph-query run tried only the case expected to succeed, we have not yet watched a swapped query be refused through graph queries.

What is still open. Catalog discovery, a separate restricted identity and graph queries have never been combined in one run, on a real cohort. Access denials have been demonstrated against a separate restricted identity, but on the ordinary SQL path, not inside graph queries. Speed benchmarks are unfinished, and nobody has yet accepted an operating budget. That is the pilot’s job.

01 Replayable context

Same retention definition, cohort rule and declared computation.

KC + OKF

KC discovers; OKF authors the graph. Similarity ranks candidates; it does not pin linked context. The retriever assembles it.

+ BQ runtime

Host the OKF projection. Pin a publication; use explicit SQL or bounded walks. Fix query, parameters, fact versions, access scope and ordering → same selected context and shape.

Vector search can be deterministic. Replayable context does not promise identical LLM answers. See the recorded graph walk: it behaved correctly in every case we tested. Speed benchmarks and access checks inside graph queries are still to come.

02 Explainable access

Finance can trace why this agent could use the total-ARR asset.

KC + OKF

Custom-entry access uses an EntryGroup boundary today. Per-node policy evaluation is separate.

+ BQ runtime

Join identity ↔ policy ↔ projected assets. Bind the requesting user/agent to the execution identity. Enforce access along the retrieval path; record which nodes were returned to whom under which policy.

Access metadata needs enforcement. Keep source permissions current; metadata access does not grant file access. A separate, deliberately restricted identity was denied where it should be — on the ordinary SQL retrieval path. Those same checks have not run inside graph queries.

03 Verifiable execution

Finance can check whether the board number used the retention calculation.

KC + OKF

Finding the definition and its computation declaration does not prove the calculation ran.

+ BQ runtime

Run retention; validate a job ↔ context ↔ result receipt against the declared computation. A substituted query or missing evidence leaves the number unproven.

A job ID alone is not enough. See the recorded receipt check: one worked example ties the query, its inputs and its result together and withholds the number when they do not match. In our connected runs, retrieval fed that check instead of a person, and the number was released only after it passed. One of those runs retrieved through graph queries — carrying a single identity, from a starting point we chose rather than discovered, and exercising only the case expected to succeed, so a swapped query has not yet been refused through graph queries. The wider demo does not have that check at all yet.

Later, Finance could ask:

Which definition, cohort rule and calculation did the agent receive? A saved context record would identify the selected versions and links.

Which identity and policy permitted access at the time? A protected access record would explain the check; reading it later still requires permission.

Did the job match Finance’s declared calculation and the displayed number? A checked execution receipt would show the evidence, a mismatch, or why the result remains unproven.

These are goals for the connected pilot. Each answer holds only while that evidence is retained and the reader is permitted to see it now; none explains the model’s private reasoning.

Graph walks need Enterprise or Enterprise Plus capacity. A projected graph can be the first workload there once its inputs are loaded, but the strongest case is a customer whose facts are already in BigQuery. Ordinary SQL and vector retrieval also run on-demand.

What the decision turns on, and the numbers it will be judged against. The project owner has not accepted any number below, and no Finance or data owner outside this project has been asked for one. Naming an owner is not agreeing an envelope, so every threshold below is proposed, not agreed.

The task. Proposed. An analyst’s agent answers a question about a defined metric by retrieving the pinned definition, the rules it links to and the declared calculation, and releases a number only when a receipt bound to that calculation checks out. Measured on Acme’s invented gross-margin material. Alder’s retention figures are illustrative and no real cohort data has been used.

The definitions and their versions. Fixed, not proposed. One pinned bundle of Acme’s definitions — seventeen documents and two artifacts, with the question set fixed in advance. Every experiment retrieved from it, and a baseline that changes it is not a comparison. It fixes the definitions and the rules that link them; it identifies no fact data. The exact bundle, publication and source pin are on record.

The fact data and its version. Not yet chosen. The task releases a computed number, so the comparison also needs the version of the rows that number came from, and nobody has picked one. The recorded chains used a small synthetic fixture of their own, tied to the definitions above only by the declared calculation itself. Crucially, nothing pins a snapshot or cut-off for those rows: two runs weeks apart could compute different numbers from the same declaration and both check out. Choosing a fact version is a prerequisite for measuring the full time from question to released number, and Alder’s cohort data has never been selected at all — that is a customer’s to give, not ours to invent.

Concurrency and volume. Proposed. Five requests at once, and ten thousand requests a day. Both are planning defaults that nobody has asked for. One request at a time is the only concurrency any recorded measurement covers, and the ten-thousand-a-day cost model has never been built.

Latency. Proposed. Retrieval within five seconds for ninety-five requests in a hundred, at five at once. Retrieval time and the full time from question to released number are separate measurements and are never swapped for one another; no threshold is proposed for the second, because nothing has sampled it yet. The 5.4 seconds already on record came from twenty-eight of a hundred attempts, one at a time, on graph queries — a partial sample, not an agreement, and not a result at five at once.

Freshness and retention. Proposed. A republished definition visible to new requests within a minute; one publish took 21 seconds, which is a single observation rather than a distribution. A request that has already pinned a publication keeps it, which is deliberate and was tested. Fifteen months of context, access and receipt records, so a number in a board pack can still be explained at the next annual close — a horizon with no measurement behind it, offered to be accepted or replaced.

Success. Proposed. At least ninety-nine requests in a hundred either release a number whose receipt checks out or refuse with a stated reason; no number is ever released without a receipt that checks out; and denied content is never disclosed. The last two are the ones worth arguing about.

Cost. Proposed. At most five cents per answered question at ten thousand a day, counting failed and refused attempts, embeddings, storage, keeping publications current and any reserved capacity. Nothing has been measured against it: none of the graph benchmark’s nine cells is finished, and the ordinary-SQL comparison is a declared plan with no numbers in it yet.

The decision. At the upcoming checkpoint we continue, narrow or stop against whichever of these the owner has accepted by then. If ordinary SQL meets the need, graph queries have to justify what they cost on top. If nobody accepts the envelope, the scoped opportunity narrows: more demonstration evidence is not pilot validation.

Technical designProposed integration · early experiments

A proposed integration, not a product. The OKF bundle stays the authored source; BigQuery would host a projection of each publication. Everything below was exercised on invented gross-margin data for a fictional company, Acme — never on a customer’s cohort.

Retrieve a fixed context

Follow Finance’s retention definition through its authored links to the cohort rule and the declared computation, under fixed inputs and bounded traversal, with a retrieval receipt recording what was pinned and what came back.

Shown

  • On generally available vector search plus graph queries, a walk reached the sanctioned SQL and matched a plain relational cross-check (what the walk showed and where it stops).

Limits

  • The walk finds that SQL but never runs it, from a start pinned by hand, not discovered.
  • Graph-native semantic search is a separate Preview option we did not test.
  • The receipt says which context was chosen, not that retention was computed or that the model answers the same way twice.

Evaluate current access

The requester is bound to the identity that runs the query; access is checked along the retrieval path, not only at the door, and recorded with the policy version and the nodes released.

Shown

  • A restricted identity was denied on the protected tables, stayed denied after revocation, and never fell back to the owner’s credential (the access cases and their limits).
  • Refusals named no denied node or section, though other identifiers can still appear.

Limits

  • Per-node graph authorization is unshown: those denials ran on plain SQL, never inside graph queries.
  • Leakage of hidden identifiers under the operator’s own identity, and protection across mixed publications, remain untested.
  • A pin never bypasses current authorization, metadata about a file is not access to it, and a shared service account cannot by itself tell us who was asking.

Validate the calculation

Retention is computed in its own step, and a receipt binds job, query, inputs, pinned context and result to the declared calculation; the story’s total-ARR swap must fail that check.

Shown

  • Checked independently of the process that produced it, the job under the caller released its number only when query, inputs and result agreed, and withheld it otherwise (what the receipt check showed).

Limits

  • Requester’s own delegation, signing key held locally, one small invented fixture.
  • No independent verifier, no portable signatures; where evidence is missing the number stays unproven.

The three as one path

Joined: a live catalog read picks the publication to pin, governed retrieval supplies the declared calculation, and the receipt check verifies the job before release, each step checked against a copy already trusted.

Shown

  • Catalog-seeded runs went from live read to enforcing consumer, held their pinned version while the head moved, and stopped before any calculation or receipt where validation failed (what those cases showed).
  • A restricted identity held inside the chain: access and revocation were enforced and nothing unauthorized was released (how that run worked and where it stops).
  • One run retrieved through graph queries on Enterprise capacity, releasing only once the declaration matched the publication queried and the receipt check passed (what that run did and did not show).

Limits

  • All three carried a single identity; the catalog-seeded and restricted-identity runs used plain SQL; the restricted-identity and graph-query runs began from a point we chose rather than one discovered.
  • Graph queries covered only the case expected to succeed; a swapped query has never been refused through graph queries.
  • The catalog read is our own, seeded for the experiment; the number was invented gross margin, not Alder’s retention; the receipt ran on a small synthetic fixture and a fixed test case, not the story’s total-ARR swap.
  • No run used an independent attester.

What is still open

The bar. Proven means one run doing all of it at once: catalog discovery, a pinned publication, governed retrieval, a computation delegated by the caller, a receipt bound to the result and a consumer that enforces it, with publication, per-node access, revocation and output checks holding throughout. The three runs above each reach a different part; none has done two, let alone all three.

Also unfinished

  • Speed benchmarks: none of the nine planned cells is complete, and the ordinary-SQL comparison is a declared plan with no numbers in it yet.
  • Merged and reviewed in its own code bases, but on the receipt example the approving reviewer also wrote the final fix; merge is not readiness.
  • No customer has agreed an operating budget, and BigQuery as a general serving layer for the Catalog is a weaker case than the scoped one above.

The checkpoint. Receipt work should not wait for the graph benchmark. The opportunity narrows if cost, simpler retrieval, semantics, authorization or publication guarantees go against it, or if result evidence cannot be bound and enforced. Boundaries: BigQuery editions, graph placement.

The proposed BigQuery runtime would turn the OKF graph into replayable context for agents—with explainable access and evidence that the declared computation ran.
