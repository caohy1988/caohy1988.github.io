# OKF runtime context projection (RFC) versus "Using OKF with Knowledge Catalog to serve context for agents" (Google Cloud blog)

Prepared 2026-09-03. Sources: `/tmp/okf-kc/blog.txt` (text of the Google Cloud blog post, `datePublished` 2026-08-26, canonical `https://cloud.google.com/blog/products/data-analytics/scale-okf-bundles-across-an-organization-with-knowledge-catalog`, authors Firat Elbey and Sam McVeety); `/tmp/okf-kc/rfc.txt` (text of `/Users/haiyuancao/caohy1988.github.io/rfc/index.html`, byte-identical to `/tmp/okf-kc/rfc.html`, footer "Consolidated 2026-08-30"); local `rfc/intent.md`, `rfc/spec.md`, `rfc/plan.md`, `rfc/demo/{README,spec,intent,plan}.md` at HEAD `cc38d7a`; GitHub reads of `GoogleCloudPlatform/knowledge-catalog` (default branch `main`, `pushed_at` 2026-09-03T02:47:08Z) and `GoogleCloudPlatform/open-knowledge-format` (created 2026-08-11T18:29:55Z, `pushed_at` 2026-08-21T20:08:36Z), plus four `docs.cloud.google.com` Dataplex pages. Sibling worktrees `-okf-demo` and `-okf-e2e` differ from `main` only in the two-line Prototype callout of `rfc/index.html`; `-okf-why-demo` is identical; none changes the RFC body, so `main` is treated as canonical.

Labels used below: **[BLOG]** = claim in the post; **[RFC]** = claim in the local RFC; **[GH]** = verified against GitHub or Google docs; **UNVERIFIED** = could not be checked.

`rfc.txt` is an unnumbered text dump, so RFC quotes cite the line number in `rfc/index.html` (`L193` etc.) and the RFC section (`§04` etc.).

## A. Verdict (3 sentences)

The RFC's Knowledge Catalog leg is an independent overlapping design of the same projection the blog ships, not the same work and not yet a clean extension: it was consolidated four days after the post, already names `toolbox/mdcode/demo/okf/push.ts` (L440) but never cites the post, and it proposes a different EntryType (`okf-concept`), a second aspect (`okf-computation`), and two new aspect fields that the shipped `okf-bundle` type and 13-field `okf` AspectType do not have. Everything else in the RFC (BigQuery relational serving authority, the observation/snapshot/publication chain, `deployment_heads` history, the Context Envelope, attested execution with verdicts, and the BQAA `context_ref` seam) has no counterpart in the blog, which stops at push, search, LookupContext and IAM. The correct relationship is therefore "runtime profile layered on the shipped distribution mechanism", and the RFC must be edited to say so, adopt or explicitly reconcile the shipped type names, and correct one factual claim about what `push.ts` does.

## B. Line-level overlap map

### B1. Entry types and aspects: `okf-bundle` + `okf` (shipped) versus `okf-concept` + `okf` + `okf-computation` (RFC)

**[BLOG]** "The setup registers three Knowledge Catalog resources: an EntryGroup to hold the bundle, an EntryType named okf-bundle for its concepts, and an AspectType named okf that carries the OKF signal fields (from the okf-aspect.json schema in the sample code). The push then creates one okf-bundle Entry per concept, each with two Aspects: an overview Aspect for the markdown body, and an okf Aspect for the structured signals." The post's table lists 13 fields, "Every field is annotated with a display name, a description, and a mandatory index."

**[GH]** `toolbox/mdcode/demo/okf/okf-aspect.json` has exactly 13 `recordFields` with `index` 1..13: `okf_type`, `generated{by,at}`, `sources[]{id,resource,title,author,usage_count,last_modified}`, `verified[]{by,at}`, `status`, `stale_after`, `usage_window{from,to}`, `runtime`, `parameters[]{name,type,required}`, `computation`, `executor{resource,receipt[]}`, `attester{resource}`, `extra`. The aspect's own description: "Open Knowledge Format v0.2 signal layer: type, provenance, trust, lifecycle, and computation contract." `setup.ts` creates `entry-types create okf-bundle` with `--display-name=OKF Document` and `aspect-types create okf --metadata-template-file-name=okf-aspect.json`, and comments: "It declares no required aspects: SPEC 8 index files carry no signal layer, so requiring the okf aspect would reject them." `okf.ts` moves the authored `type:` onto the aspect: "`type` and `resource` are carried outside the signal record: `type` as `okf_type`, `resource` as the catalog entry's resource name."

**[RFC]** L451 (§04): "Catalog types: one generic okf-concept entry type in v1, okf aspect preserving the authored type:, okf-computation aspect on §10 concepts; existing entries reused only for physical BigQuery assets." L657 (§06): "One okf-concept entry per concept; okf aspect (authored type, lifecycle, provenance, publication_id, published_snapshot_id); okf-computation aspect on §10 concepts". L733 (Phase 2 outcome): "okf-concept entries, okf / okf-computation aspects ... produced through the kcmd library".

**Resolution.**
- `okf-concept` does not collide with `okf-bundle` by ID; it forks it. The shipped sample types every markdown file, including index files, as `okf-bundle` ("Every file lands as an okf-bundle entry, index files included", `demo/README.md` [GH]). A bundle pushed once by the sample and once by the RFC's `okf-context` would produce two entry populations of different types in the same project, and they cannot be converged in place: "An entry's type is fixed at creation, so a bundle already published under the generic type has to have its entry group deleted and recreated" (`demo/README.md` [GH]). The RFC's "okf aspect preserving the authored type:" is exactly what the shipped `okf_type` field already does, so on that point the RFC is restating shipped behavior without saying so.
- The `okf` AspectType ID is shared and project-scoped, not bundle-scoped: `cleanup.ts` [GH] says "The okf aspect type and the okf-bundle entry type are scoped to the project and location, not to this demo's entry group, so any other OKF bundle in the project is typed by them too." So if the RFC registers its own `okf` AspectType in a project where the sample already ran, it will hit the existing template. There is room to add `publication_id` and `published_snapshot_id`, but only one way: `setup.ts` [GH] states "Dataplex rejects backwards-incompatible template changes, so new fields in okf-aspect.json must be appended with fresh indices; renumbering an existing field breaks this update for everyone who already ran the demo." Appending them as indices 14 and 15 is a change to the shipped sample's template that every bundle in the project then carries. Putting them in the existing `extra` field is wrong by that field's contract ("Producer-defined frontmatter this template does not model ... Keeps the round-trip lossless"), because `pull.ts`/`fromStaging` would write runtime pins back into authored frontmatter. The clean options are an additive template update coordinated with the sample, or a separately named runtime-owned aspect for the pins.
- `okf-computation` duplicates shipped fields 8 to 12 (`runtime`, `parameters`, `computation`, `executor`, `attester`), which the post says are already searchable on `runtime` and `computation`. The RFC never says what `okf-computation` holds beyond those. If it is meant to carry runtime-derived facts (`computation_version_id`, artifact hashes, the attester identity from §06), that is a legitimate second aspect; if it is meant to carry the authored §10 contract, the shipped `okf` aspect already does.

### B2. The freeze claim and where the blog's quickstart actually pushes from

**[RFC]** L193: "Sources: the OKF v0.2 spec now lives in GoogleCloudPlatform/open-knowledge-format; knowledge-catalog/okf/ is a frozen snapshot and nothing here targets it." L439: "Not knowledge-catalog/okf/proposals/ — that tree is frozen".

**[GH] Freeze verified.** `knowledge-catalog/okf/README.md` opens with: "OKF now lives in its own repository: GoogleCloudPlatform/open-knowledge-format ... Stop using the copy under `okf/` in this repository. It is a frozen snapshot, no longer maintained, and anything built against it will drift out of date." That banner landed in commit `62651738` (2026-08-21, "okf: point readers at the dedicated OKF repository (#324)"), which is the last commit touching `okf/`. `open-knowledge-format` has commits from `81f36897` (2026-08-14, "Initial commit") through `ad30107c` (2026-08-21, "Merge pull request #6 ... okf-iso-datetimes"); branches `main`, `full-content`, `okf-iso-datetimes`; no tags. `SPEC.md` is the same blob in both repos (`c06e3eede0c910d0ecf12524c34204156f8795ac`). `bundles/acme_retail` is blob-identical across the two repos except `attesters/sql_equality.py` (`fc110cf979f5` frozen vs `6637e58f074b` new). So as of 2026-09-03 the freeze claim is accurate and the two copies have not yet diverged in content.

**[BLOG] The quickstart targets the frozen copy.** "git clone https://github.com/GoogleCloudPlatform/knowledge-catalog / cd knowledge-catalog/toolbox/mdcode && npm install && npm run build ... cd demo/okf / bun run setup.ts ... bun run push.ts # pushes okf/bundles/acme_retail into the EG setup created". **[GH]** There is no top-level `demo/` in the repo (404); the path is `toolbox/mdcode/demo/okf/` (files: `catalog/`, `cleanup.ts`, `okf-aspect.json`, `okf.ts`, `pull.ts`, `push.ts`, `setup.ts`), which the blog's `cd` chain reaches relatively. `okf.ts` sets `DEFAULT_BUNDLE = 'okf/bundles/acme_retail'` resolved from `REPO_ROOT_FROM_DEMO = '../../../..'`, i.e. the frozen `knowledge-catalog/okf/bundles/acme_retail`. `demo/README.md` still links "Open Knowledge Format" to `knowledge-catalog/tree/main/okf` and calls that bundle "the canonical in-repo bundle". Meanwhile the blog's reader-facing links point at `open-knowledge-format/blob/main/SPEC.md` and `open-knowledge-format/tree/main/bundles/acme_retail`.

**Resolution.** "Frozen snapshot" is right. "Nothing here targets it" is right only for the RFC's own text; the shipped mechanism the RFC now sits on does target it by default, and the RFC should say so rather than imply the frozen tree is unused. Practically the RFC's compiler must accept a bundle from either location and hash it the same way (§06 `source_manifest_hash` "covers every regular file under the bundle root"), and it should note that the two trees differ today only in `attesters/sql_equality.py`.

### B3. Idempotent upsert, deletes, and the two-pushers risk

**[BLOG]** "kcmd push is an idempotent upsert. Re-running is safe (no duplicates, no error), but every push writes every Entry. Concept deletes require an explicit kcmd delete on the Entry, or cleanup.ts to remove the whole EntryGroup at once; cleanup.ts deletes only the EntryGroup and its Entries, so the shared okf AspectType and okf-bundle EntryType stay in place". Also: "One EntryGroup per bundle-owning team is the multi-team pattern".

**[GH]** `toolbox/mdcode/src/libts/sync.ts` `push()`: for each local entry it calls `lookupEntry`, then `createEntry` if absent, else a patch with an `updateMask`; the code carries "TODO: Track what has changed and do minimal update. TODO: Handle creates and deletes, as well as partial updates. TODO: Handle conflicts." No orphan deletion exists on this generic path. `docs/spec.md` §3.8 states the design intent, "Intent to Delete: If an entry type is listed in the publish config, treat missing files compared to state as intent to delete", but the implementation above does not do it. `cleanup.ts` deletes the whole EntryGroup via `gcloud -q dataplex entry-groups delete`. A `kcmd delete` CLI command was not found in `src/tool/commands.ts` or the README command list (UNVERIFIED as a command; `snapshot.ts` has a library-level `deleteEntry`). `push.ts` does not use kcmd as a library for the push: it stages files and then `cp.execFileSync(binary, ['push'])` on `../../dist/kcmd`.

Deletion with ownership exists only on the semantic-model path: `deploy_knowledge_catalog.ts` `reconcileDeletions` [GH]: "Only entries this push OWNS are ever touched: an entry whose id is a pushed model's anchor, or that lives under that anchor's `<model>.entities.` / `<model>.metrics.` namespace. Entries belonging to other models that share the entry group are left alone", plus `--force-remove` "to delete models left in the entry group that the push no longer includes" (README). The semantic-model README also says "An entry group holds exactly one semantic model."

**[RFC]** L440: "Reused via library import, as toolbox/mdcode/demo/okf/push.ts already does: Documents-Layout staging, custom-aspect passthrough, delete-only-what-you-created reconciliation." L658: "ownership is tracked in a BigQuery ledger keyed by deterministic deployment-scoped link and entry IDs, with managed_by_* stamps on aspects where aspects exist. Reconciliation removes or replaces only artifacts this deployment owns ... Coexistence with a kcmd semantic-model push in the same EntryGroup is tested adversarially in Phase 2." L764 (risk table): "Two pushers deleting orphans in one EntryGroup — Ownership ledger + deterministic IDs; no semantic-* reuse in v1 — Phase 2".

**Resolution.**
- The RFC's description of `push.ts` is wrong on two counts: `push.ts` shells out to the kcmd binary (it imports the library only for `ApiContext`), and neither `push.ts` nor generic `kcmd push` performs any delete, let alone "delete-only-what-you-created". That phrase describes the semantic-model deploy path, not the OKF sample.
- The blog neither creates nor resolves the two-pushers risk; it routes around it. Its shipped path never deletes (so it cannot delete someone else's entries) and its multi-team answer is EntryGroup isolation plus whole-EntryGroup cleanup. That makes the RFC's ledger necessary rather than redundant: the RFC's "Deletion is absence from the next snapshot" (§06) has to be carried into Catalog by `okf-context` itself, because kcmd will not do it.
- The blog also adds a concrete second adversary the RFC does not test: a kcmd Documents-Layout push of the same bundle into the same EntryGroup. Both tools derive entry IDs from the file path ("`metrics/revenue.md` → entry `metrics/revenue`" [GH]; RFC `concept_id` "is the bundle-relative path without .md"), so the two pushers would contend for the same entry names with different EntryTypes, which Catalog fixes at creation. The Phase 2 gate currently names only the semantic-model push as the adversary.
- IAM cannot separate two pushers in one EntryGroup. **[GH docs]** `roles/dataplex.catalogEditor` includes `dataplex.entries.*` including delete. A pusher with editor on the EntryGroup can delete anything in it, so the RFC's ledger is a discipline, not a boundary; the blog's one-EntryGroup-per-team is the only IAM-enforceable boundary either document offers.

### B4. LookupContext, searchEntries predicates, and pin-or-fail-stale

**[BLOG]** "LookupContext does not render custom Aspects, so an agent that needs the structured OKF signal fields ... reads them with entries.get and view=ALL alongside the LookupContext call." "Any top-level scalar field in the okf Aspect (okf_type, status, stale_after, runtime, computation, extra) can drive Knowledge Catalog search predicates directly ... Scalar subfields of record fields (generated.by, usage_window.from, executor.resource, attester.resource) also drive predicates. The array fields (sources, verified, parameters) are not server-side searchable on their subfields". "use a bare date (stale_after=2026-12-31) or a range comparison (stale_after>2026-01-01), not the full RFC3339 timestamp." "LookupContext resolves the entry names it is given, up to ten per call, within a single location."

**[GH docs]** `projects.locations.lookupContext` exists: `POST https://dataplex.googleapis.com/v1/{name=projects/*/locations/*}:lookupContext`, `resources[]` "maximum of 10 resources per request", `options` supports `format`, `context_budget`, `all_schema_fields`, response is a single `context` string. The search-syntax page gives custom-aspect predicates as `PROJECT_ID.REGION.ASPECT_TYPE_ID.FIELD_NAME` and says "Only top-level fields of the aspect are searchable", with datetime operators `=, :, <, >, <=, >=`. The docs' "only top-level" statement is narrower than the blog's record-subfield claim; which is right in practice is UNVERIFIED. Whether LookupContext omits custom aspects is UNVERIFIED (the docs page fetched does not say). `okf-aspect.json` marks `search.retrievable: true` only on `okf_type`, `status`, `runtime`; whether that annotation gates predicates is UNVERIFIED.

**[RFC]** L498 (§05): "Every owned Catalog entry carries publication_id and published_snapshot_id. A request launched from Catalog carries that publication_id and either serves that retained publication or fails stale. Agent tools never read Catalog for lifecycle decisions." L734 (Phase 2 gate): "a Catalog-originated request either serves its pinned publication or fails stale, never jumps to the latest head". L376 (system diagram): "HUMAN CATALOG USER ... requests carry publication_id". Phase 3 tools (`search_context`, `expand_context`, `get_evidence`, `explain_context`) run against BigQuery.

**Resolution.**
- Pin-or-fail-stale cannot be enforced through aspect search predicates and the RFC should not imply it can. A predicate such as `aspect:<project>.<location>.okf.publication_id=<id>` can at most filter entries to those stamped with one publication; it cannot compare against `deployment_heads` or refuse a stale one. Enforcement is in the BigQuery runtime (§05 says so), and the Catalog side's only job is to make the pin readable. That works only if `publication_id` is a top-level string scalar in the aspect (a nested `publication{...}` record would fall under "Only top-level fields of the aspect are searchable"), and the RFC should fix that shape.
- The pin is invisible on the blog's primary read path. If LookupContext does not render custom aspects (blog claim), a human or agent that starts from LookupContext never sees `publication_id`, so "requests carry publication_id" requires an `entries.get` with `view=ALL` first. Phase 2 must name that call as the pin-reading step and Phase 3's MCP wrapper must accept the pin as an explicit argument.
- Other Phase 2/3 claims constrained by the post: any Catalog-side filter on `sources[]`, `verified[]`, or `parameters[]` (for example "verified by a human") must be client-side after `entries.get`; `stale_after` predicates must use bare dates or ranges; a Catalog-side "list every entry of this publication" is a `searchEntries` on one scalar and is bounded by search scope, not by EntryGroup listing, unless `entryGroups.entries.list` is used. None of this affects Phase 3's BigQuery path, which is why the RFC's "Agent tools never read Catalog for lifecycle decisions" is the right rule and should be cross-referenced to these limits.

### B5. IAM: EntryGroup cascade versus one security domain per bundle and sub-concept enforcement

**[BLOG]** "Reading agents use roles/dataplex.catalogViewer, which grants the read paths: entries.get, LookupContext, and searchEntries. The identity that runs kcmd push uses roles/dataplex.catalogEditor, which grants the write paths: entries.create and entries.patch. One EntryGroup per bundle-owning team is the multi-team pattern, and IAM on the EntryGroup cascades to its Entries." "Bundle Entries inherit IAM from the EntryGroup".

**[GH docs]** `roles/dataplex.catalogViewer` ("Read access to catalog resources, including entries, entry groups, and glossaries") includes `dataplex.entries.get`, `dataplex.entries.list`, `dataplex.entryGroups.get`, `dataplex.entryLinks.get`. `roles/dataplex.catalogEditor` ("Write access ... Cannot set IAM policies on resources") includes `dataplex.entries.*`, `dataplex.entryGroups.create/delete/update`, `dataplex.entryLinks.create/delete/update`. `entryGroups:setIamPolicy` exists at `projects/*/locations/*/entryGroups/*`. Which permission gates LookupContext and searchEntries, and the cascade from EntryGroup to Entries, are stated by the blog only and are UNVERIFIED against the pages fetched.

**[RFC]** §06 "Policy authority, v1. OKF frontmatter is not an ACL and OKF v0.2 defines no fragment-level policy. V1 supports one security domain per bundle/deployment with caller-delegated BigQuery authorization as the policy source. Mixed-policy bundles fail closed unless an external policy resolver is configured." L585: "The enforcement unit may be a concept, chunk, assertion, evidence record, resource, or computation (#209: concept granularity is not assumed sufficient). Fail closed when access cannot be evaluated." [GH] #209 is an open issue (2026-07-19) titled "Producer report: access is the axis this tracker keeps circling — field notes from a wiki memory that enforces per-fragment read sets".

**Resolution.**
- Compatible at the v1 boundary. "One EntryGroup per bundle-owning team" is the Catalog-side realization of "one security domain per bundle/deployment"; the blog's pattern is what the RFC's v1 assumes.
- The cascade does undercut the RFC's granularity argument, but only for the Catalog projection, and the RFC currently does not say so. On the Catalog side the enforcement unit is the EntryGroup, coarser than the concept, and the `overview` aspect carries the full markdown body ("The overview Aspect holds the full body of revenue.md" [BLOG]). Any sub-concept denial the BigQuery runtime applies (chunk, assertion, evidence) is bypassable by a `catalogViewer` reading the body from Catalog. Therefore the "mixed-policy bundles fail closed" rule must also govern projection: a bundle that needs more than one policy must not be projected into one EntryGroup, or must be projected without bodies. The #209 argument stands for the BigQuery runtime and should be scoped to it.
- The write side reinforces B3: `catalogEditor` grants entry delete across the EntryGroup, so the RFC's "adversarial coexistence in the same EntryGroup" is testable as software behavior but not enforceable by IAM.

### B6. `index.md` and `log.md` as Entries versus RFC concept identity and snapshot membership

**[BLOG]** "The bundle's index.md navigation files and its root log.md are also published as Entries: index files carry only the overview Aspect (no OKF frontmatter), and log.md carries both Aspects with okf_type: Log." "each concept is parented to the index above it, so the bundle's directory structure survives as a browsable hierarchy." "nine leaf concepts across six directories (attesters, tables, metrics, computations, policies, skills), each with its own index.md, plus a bundle root with its own index.md and log.md. That's 17 pushed Entries in total; Dataplex auto-creates one <eg>_entry alongside".

**[GH]** `okf/bundles/acme_retail` holds exactly 17 `.md` files (9 leaves, 6 directory `index.md`, root `index.md`, `log.md`) plus `attesters/sql_equality.py` and `viz.html`; `log.md` frontmatter is `type: Log`. `okf.ts` stages frontmatter-less index files with only the entry type ("SPEC 8 index files carry no frontmatter, so stage the entry type on its own"); `demo/README.md`: "the only native Knowledge Catalog edges are the parent links derived from the directory structure"; "Only .md files are pushed, so bundle attachments such as acme_retail/attesters/sql_equality.py stay local". OKF SPEC §8 "Index files" and §9 "Log files" define both as reserved, optional files. The auto-created `<eg>_entry` is UNVERIFIED.

**[RFC]** L514: "concept_key — bundle_key + "#" + concept_id, where concept_id is the bundle-relative path without .md (OKF v0.2 fallback)." §06: "source_manifest_hash covers every regular file under the bundle root, exhaustively"; "Membership maps logical identities to exact versions per snapshot"; "Resolved bundle-internal Markdown links compile with no extensions, each to a generic explicit edge under a profile-local predicate (context:untyped_link)". The strings `index.md` and `log.md` do not occur anywhere in `rfc/index.html`. `rfc/spec.md` (the demo spec) notes only "frontmatter `type` present on non-reserved `.md`; `log.md` reserved".

**Resolution.** The RFC must address both files; today it is silent and the silence produces three conflicts.
- Concept identity. Under the path rule, `metrics/index` would be a valid `concept_key` and `log` would be a concept with `type: Log`, a `concept_version_id`, and retrieval eligibility. `log.md` changes on almost every bundle edit, so it would mint a new version on nearly every publication, and its body is a history, not knowledge. The RFC should exclude reserved files (§8/§9) from the concept set explicitly.
- Snapshot membership. Both files are already inside `source_manifest_hash` (correct: they are bundle content), so excluding them from the concept set does not change `snapshot_id`; the RFC should say that membership records them as non-concept files so reconstruction still includes them.
- Catalog ownership and parity. The shipped projection has 8 non-concept entries per Acme bundle and a `parentEntry` hierarchy the RFC never models. If `okf-context` owns an EntryGroup previously filled by the sample, its ledger will not know those entries; if it coexists, its concept entries will lack the parent links Catalog users browse by. The Phase 2 gate should state whether index entries are projected (for parity and browsing) and owned, and whether `parentEntry` is set the same way the Documents Layout sets it.
- Edges. Index files are lists of links; if they were concepts, every index would emit `context:untyped_link` edges to all siblings and inflate the assertion ledger with navigation noise. Excluding them also settles that.

## C. What the RFC must change

1. **Cite the post and the sample as the shipped baseline** (§00 Sources L193; §04 Catalog types L451; §06 "Catalog ownership and reconciliation" L657; §09 Phase 2 L733). What: add "Using OKF with Knowledge Catalog to serve context for agents" (Google Cloud blog, 2026-08-26, Firat Elbey and Sam McVeety) and `toolbox/mdcode/demo/okf/` as the reference the Catalog leg builds on. Why: the RFC currently reads as if it were the first Catalog projection; it is not, and a reviewer at either repo will know that.

2. **Correct L440 (§04 Implementation).** What: replace "as toolbox/mdcode/demo/okf/push.ts already does: Documents-Layout staging, custom-aspect passthrough, delete-only-what-you-created reconciliation" with what is verified: `push.ts` stages the bundle into Documents Layout with the signal on a `catalogEntry` passthrough and then executes the `kcmd` binary; generic `kcmd push` creates or patches and does not delete (`sync.ts` "TODO: Handle creates and deletes"); owned-prefix deletion exists only in the semantic-model deploy path. Why: the claim is false and it is the sentence a kcmd maintainer will check first.

3. **Rename or reconcile `okf-concept`** (§03 diagram L318; §04 L451; §06 L657; §09 L705, L733). What: either adopt the shipped `okf-bundle` EntryType (display name "OKF Document") or keep `okf-concept` and state in §04 that it is a deliberate second type, that a sample-pushed EntryGroup cannot be migrated because entry type is fixed at creation, and how `status` reports a bundle that exists under both. Recommendation: adopt `okf-bundle`; the type name is not load-bearing for the RFC and the fork costs more than it buys.

4. **Define the `okf` aspect as the shipped 13-field template plus additive fields** (§06 L657; §05 L498). What: say `publication_id` and `published_snapshot_id` are top-level string fields appended with fresh indices (14, 15) via the template-update path `setup.ts` already uses, or live in a separately named runtime-owned aspect; state they are never written into `extra`. Why: `extra` is round-tripped into authored frontmatter by `pull.ts`; nested placement would not be searchable.

5. **Reconcile `okf-computation` with shipped fields 8 to 12** (§03 L320; §04 L451; §06 L657). What: define `okf-computation` as runtime-derived only (`computation_version_id`, artifact hashes, attester identity, verdict summary) and state that the authored §10 contract stays on the shipped `okf` fields `runtime`, `parameters`, `computation`, `executor`, `attester`; or drop the second aspect. Why: as written it duplicates what is shipped and searchable.

6. **Fix "nothing here targets it"** (L193). What: keep "frozen snapshot", add that the shipped sample and the blog's quickstart push `knowledge-catalog/okf/bundles/acme_retail` by default (`okf.ts` `DEFAULT_BUNDLE`), that the two Acme copies differ today only in `attesters/sql_equality.py`, and that the compiler accepts a bundle root from either repository. Why: accuracy, and because the Phase 0 fixture comparisons will otherwise be run against the wrong tree.

7. **Add index/log handling** (§06 identity L514; §06 membership; §09 Phase 2 gate L734). What: reserved files (`index.md`, `log.md`) are bundle content for `source_manifest_hash` but are not concepts; they get no `concept_key`, no version rows, no edges; Phase 2 states whether index entries are projected and owned for parity with the Documents Layout and whether `parentEntry` is set. Why: see B6.

8. **Reword the Phase 2 gate on pinning** (L734; §05 L498). What: "a Catalog-originated request either serves its pinned publication or fails stale" becomes "a request that reads `publication_id` from the entry via `entries.get` with `view=ALL` (LookupContext does not carry custom aspects, per the post) and presents it to the runtime either serves that retained publication or fails stale; search predicates on `publication_id` filter only and never enforce." Why: B4.

9. **Add the second adversary to the Phase 2 coexistence gate** (L734; risk table L764). ## D. What remains uniquely the RFC's contribution

The post is silent on all of the following; none of it is present in `blog.txt`, `okf-aspect.json`, `okf.ts`, `push.ts`, `setup.ts`, or `cleanup.ts`.

- **BigQuery relational runtime as serving authority.** The post's entire read path is Catalog: `searchEntries`, `LookupContext`, `entries.get`. There is no BigQuery table, view, or dataset anywhere in it. The RFC's "BigQuery relational tables are the authoritative runtime projection ... For agents, BigQuery is the read path; for humans, Catalog is the read path" (§01) is new.
- **Observation, snapshot, publication identity and republish semantics.** The post's only identities are Dataplex `createTime`/`updateTime` on entries and aspects, and it states that "every push writes every Entry". The RFC's `observation_id`, `snapshot_id` with its domain-separated CBOR hash, `publication_id`, and "Retrying an identical publication ... is a no-op ... Publishing a new observation of an unchanged snapshot creates a new publication row ... a provenance event, and therefore not silent" (§06) have no counterpart.
- **`deployment_heads` and `deployment_heads_history`.** The post has no notion of deployment, head, or "what was current for deployment D at time t" (§05). Catalog holds one mutable state per entry.
- **Context Envelope with opaque `envelope_id` and keyed policy-context commitment.** LookupContext returns "a single context field containing a pre-formatted YAML block" with a `context_budget`; it carries no identity, no manifest, no reproducibility, and no cache-equality rule. The RFC's `envelope_id` ("opaque, random, tenant-scoped ... not a public content hash"), `policy_context_commitment`, and `envelope_equality_digest` are new.
- **Attested Computation with an independent attester identity and complete-evidence verdicts.** The post projects the declared contract (`runtime`, `parameters`, `computation`, `executor`, `attester`) and says the computation "appears in the console with its sanctioned SQL, its executor, its attester, its verification history". It never executes anything and has no verdict. The RFC's caller-delegated execution, "The attester runs as an independent, constrained service identity", `ATTESTED` / `UNVERIFIABLE` / `REJECTED`, HMAC parameter-binding commitments, and the stated threat model are new.
- **`context_ref` and the BQAA observer seam.** The post never mentions BigQuery Agent Analytics, telemetry, or any correlation identifier on tool results. The RFC's `context_ref` sub-object and its never-emit list are new, and the local `rfc/demo/` prototype (README: "The handle a Knowledge Catalog entry would expose is `context_ref` `okf:env-observe#674153c572f6`") is the only working demonstration of that seam anywhere in these sources.
- **Unresolved-link losslessness.** The post's sample keeps links as prose ("in-body markdown links between concepts stay markdown; the only native Knowledge Catalog edges are the parent links derived from the directory structure") and has the agent walk `sources[]` by path. The RFC's `target_ref = "resolved:" + concept_key | "unresolved:" + normalized_authored_target` so "two missing targets never collapse into one assertion" is new.
- **Assertion identity distinct from logical edge identity.** The post has no edge model. The RFC's `logical_relationship_key` versus `relationship_assertion_key` with `assertion_mode` preserved is new.
- **Lifecycle-aware retrieval.** The post's `extra` field would carry `supersedes` / `contested_by` as an opaque JSON string; nothing in the post excludes superseded concepts at query time. The RFC's `current` / `historical` / `all` modes and "exclusion follows affirmation" are new.

Honest limits: the RFC's Catalog mapping itself (one entry per concept, an `okf` aspect holding the authored type and signal, `overview` for the body) is not unique; the post shipped it first and more completely, including index/log entries and the parent hierarchy.

## E. Paste-ready positioning paragraph

Google's 2026-08-26 post "Using OKF with Knowledge Catalog to serve context for agents" ships the org-scale distribution mechanism for OKF bundles: the `toolbox/mdcode/demo/okf` sample in `GoogleCloudPlatform/knowledge-catalog` registers an `okf-bundle` EntryType and a 13-field `okf` AspectType, and `kcmd push` publishes every markdown file in a bundle as a Knowledge Catalog Entry that inherits EntryGroup IAM and is reachable through `searchEntries`, `LookupContext`, and `entries.get`. This RFC does not replace that mechanism and does not change OKF v0.2; it is an optional runtime profile layered on it. It adopts the shipped Catalog types as the discovery projection, adds publication pins and an ownership ledger so a Catalog entry can name exactly which compiled state it describes, and puts everything the post leaves out into a BigQuery runtime: immutable observation/snapshot/publication history with per-deployment heads, authorized retrieval that returns a reproducible Context Envelope, attested execution of sanctioned computations with an independent attester and explicit verdicts, and an opaque `context_ref` so BigQuery Agent Analytics can observe use without becoming a source of truth. Where the post says a bundle is discoverable and governed, this profile says which version an agent used, whether the number it returned was attested, and how to reconstruct both.

## F. Strongest objection and honest answer

**Objection.** "kcmd push already puts every concept in Knowledge Catalog with IAM, search, and LookupContext. Why write a second Catalog projection design?"

**Answer.** Because the second design is not the projection; it is what the projection cannot express. Accept the objection on its own terms first: the RFC's Catalog leg should be a small delta on the sample, not a parallel type system, and Section C says so. But three things the post's own text establishes cannot be fixed inside kcmd push. First, identity: "every push writes every Entry" and entries carry only `createTime`/`updateTime`, so nothing in Catalog says which bundle revision an agent read, whether two agents read the same one, or what was current yesterday; the RFC's publication pin on the entry plus `deployment_heads_history` in BigQuery is the smallest addition that answers those questions. Second, lifecycle: the post's read path returns whatever is in the EntryGroup, and generic kcmd push never deletes, so a deprecated or superseded concept is served until someone runs cleanup on the whole group; the RFC's snapshot membership and `current` retrieval mode make retirement a property of the data rather than of an operator remembering. Third, trust: the post displays the attested-computation contract and stops; nothing runs it, nothing issues a verdict, and the number an agent quotes is as trustworthy as the agent that typed the SQL. The RFC's attested execution is the only piece in either document that turns "Backed by an Attested Computation" from a label into a receipt. If those three are not needed, the post is sufficient and the RFC should not be adopted. If they are, kcmd push is the distribution layer and this profile is the runtime that sits on it, which is exactly how the RFC should describe itself.
