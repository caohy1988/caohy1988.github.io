Catalog finds. BigQuery serves. Here is where each one stops.

Four real ADK sessions sit in okf_rfc_demo.agent_events. This page walks a cold reader from those traces through shipped OKF-in-Knowledge-Catalog, the external okf-context sync bridge, the BigQuery serve path, and a two-key attribution query. BigQuery is the runtime of Knowledge Catalog + OKF. Catalog finds and distributes the concept; BigQuery is where retrieval turns deterministic, IAM stays scoped to one deployment, and the OKF chain stays walkable.

  1. Why BigQuery · 1

    Deterministic retrieval from OKF that lives in KC

    Catalog search and LookupContext surface a concept, then stop — lookupContext renders no okf field, takes ten resources a call, and holds no deployment head to pin against. The BigQuery runtime resolves concept → publication → run → receipt in one SQL join, so the next agent reads one pinned answer instead of whatever the EntryGroup happens to hold.

    beat 3 live the okf aspect is absent from lookupContext; eleven resources give back a 400 · beat 6 live 14 attributed, 13 receipt-only · pin-or-fail-stale (FAIL_STALE) stays RFC text only while no head exists

  2. Why BigQuery · 2

    IAM you can scope to a deployment

    In Catalog the enforcement unit is the EntryGroup — IAM cascades, and any catalogViewer on the group reads the whole policy body the overview carries. The BigQuery side of the RFC is one security domain per deployment, with dataset and table grants and caller-delegated authorization, so a deployment rather than a whole group is the blast radius.

    beat 3 live the EntryGroup IAM policy, and the policy body inside lookupContext · the BigQuery side is RFC text only: Phase A service accounts and table-level grants are not built, and this page claims neither

  3. Why BigQuery · 3

    The OKF chain, walked the easy way

    OKF identity is a chain — observation → snapshot → publication, then the edges a snapshot asserts. BigQuery already carries that shape as tables — snapshot_membership, relationship_assertions, context_ref_resolution — and BigQuery Graph is the easy way to walk the OKF-standard chain end to end. Catalog offers no query surface for it at all.

    beat 4 recorded the SDK adapter reproduces observation → snapshot → publication over the checked-in 180-row export · beat 5 seeded three publications rows, with the membership and edge tables created and still empty · the graph projection is RFC text only and optional, relational stays authoritative, and no graph query runs on this page

  4. Proof · the customer story

    Without the runtime, “verified” is just a word

    Consume agent 04fa3d56 read a Catalog-shaped lookup, took its ok flag for an answer, and told the finance team Germany active-customer revenue was “verified”. Nothing computed it. Observe agent f21ee192, carrying a BigQuery verdict field, calls the number unproven in 12 of 12 final answers; one of them in four words: “No. The number is unproven.”

    beat 3 live both system prompts and both answers · beat 5 seeded the verdict field · every receipt on this page is UNVERIFIABLE

Customer value for BigQuery: you already hold the traces. Catalog shelves the concept; only BigQuery retrieves it deterministically, governs who may run it, and joins the run back to a receipt.

Honesty note: normative text here is OKF v0.2 core plus an optional runtime profile, so “OKF 2.0” in a walkthrough is shorthand for that runtime story and not a claim of a published core change. Every card names the beat its evidence sits on, and says RFC text only where the BigQuery side is specified rather than built.

What this demo is asking. Take context an agent already earned the hard way, observe it with BigQuery Agent Analytics, and project it into derived OKF the next agent can discover; then show what the BigQuery runtime adds on top of the Catalog projection Google shipped on 2026-08-26. It is not human-in-the-loop or sentiment promotion, not trusting BQAA as truth, and not a claim that Dataplex or BigQuery syncs anything on their own. Sync is an external CLI you run; Catalog is the discovery projection; BigQuery is the serving authority; every receipt on this page is UNVERIFIABLE.

How this was built / IDs / job ids

Everything on this page is copied from the files in live/; the browser recomputes none of it and calls no Google API. Each BigQuery capture carries the job id it ran as, and live/bq_jobs_identity.json is the INFORMATION_SCHEMA.JOBS_BY_USER row set for those job ids, so the identity that ran every query is on record.

Run it locally / re-run the queries

Check the page against the committed captures with python3 rfc/full-demo/tools/check_full_demo.py.
