Illustrative scenario · invented company, people & numbers

The board meets at 9.
Retention is wrong.

8:55 a.m. Maya Chen, VP of Finance at subscription software company Alder, opens the final board pack. A $4 million customer-expansion plan rests on one claim: existing customers are spending more. Her finance agent reports 118% net revenue retention. “Verified.”

Five minutes to catch it

“Did that include
new customers?”

An analyst spots the problem. The agent reused an old query for total annual recurring revenue (ARR) and labeled its answer retention. It cited Finance’s metric page, but no computation receipt connected that definition to the number.

The opening customer cohort actually shrank. Maya pulls the slide. The board will need a different case for the spending.

What would change · RFC proposal, not built

Give Maya the receipt before the meeting.

Knowledge Catalog would help the agent discover Finance’s approved retention definition in Open Knowledge Format (OKF). BigQuery would be the runtime of that context, beside Alder’s revenue data.

  1. Find the right “retention.”

    The Catalog entry would point to Finance’s OKF definition: start with the opening cohort; exclude new customers. The approved computation would travel with it.

  2. Pin it. Compute the 96%.

    The runtime would hold that context revision fixed and run its declared query for the quarter. A receipt would bind the revision, parameters and BigQuery job to the result. Missing execution evidence would mean “unproven.”

  3. Trace the board-pack answer.

    Maya’s reviewer could trace the answer to the finance agent, its execution identity, the pinned context and the receipt, under explicit access grants. A later definition change would not rewrite that record.

An agent’s boardroom number should come with a BigQuery receipt.

One ask of the BigQuery VP

Sponsor one retention pilot with a Finance owner.

Use one quarter of cohort data. Prove the path from Catalog discovery to an attributable, computed answer—and show that a missing receipt leaves the answer unproven.

Scenario, not customer evidence. No Alder query ran. The runtime above is proposed. Existing demo attesters are stubs; receipts are UNVERIFIABLE. Governed sync and Phase A IAM remain unbuilt.
