OKF runtime context projection
a proposed Knowledge Catalog + BigQuery runtime profile for OKF v0.2

The proposed BigQuery runtime would turn the OKF graph into replayable context for agents—with explainable access and evidence that the declared computation ran.

A proposal, with a reference implementation, for an optional runtime layer. Teams keep authoring knowledge in the Open Knowledge Format (OKF). Each bundle would then be published in two places: Knowledge Catalog, so people and agents can find and govern it, and BigQuery, so an agent’s context can be replayed, its access checked against current policy, and its calculations backed by evidence. OKF itself does not change.

Status: a proposal, with recorded examples on invented data. One example finds linked rules with a graph walk. Another checks a query the caller owns and releases the result only after it verifies. Recorded chains fed that check from governed retrieval instead of by hand, on invented Acme data, starting from a live read of a catalog entry; they ran under a single identity on both legs and used plain SQL rather than the graph walk. A further run retrieved through graph queries on capacity opened for it, and closed cleanly — from a starting point we chose rather than discovered, under a single identity, with only the case expected to succeed attempted. Still to prove: all of it in one path — a live catalog read, a second identity and a policy decision, and graph queries — on real cohort data, with the refusal cases run inside graph queries too. OKF v0.2 is unchanged and works without this runtime.

01 · Summary

Three things a definition lookup cannot establish

An agent can cite the right definition and still give the wrong number. This proposal would connect three things: the knowledge the agent was given, the access that allowed it, and the calculation that produced the answer. The authored OKF bundle stays the source of truth. Knowledge Catalog (KC) and BigQuery each hold a derived copy with a different job.

The bundle owns authored knowledge and the declared calculations. Access policy, deployment state, runtime records and telemetry have separate owners. The table below compares today’s baseline, KC discovery plus authored OKF, with what this runtime proposes to add. It is not a claim about what a custom retriever could never do.

Especially strong when the facts an analytical agent needs already live in BigQuery on Enterprise or Enterprise Plus capacity, within latency, freshness, concurrency and cost budgets the customer has agreed to. No customer has agreed that operating budget yet. A broader Catalog serving layer needs a separate case against simpler retrieval options.

What the examples show: a graph walk can find linked rules; a separate receipt check can tie a query the caller owns to its result; and recorded chains on invented Acme data fed that receipt check from governed retrieval and refused a swapped query. Those chains began at a live read of a catalog entry, but used plain SQL rather than the graph walk and ran under one operator holding both legs; a later run retrieved through graph queries instead, from a starting point we chose rather than discovered, still under a single identity, and with only the case expected to succeed attempted. Still to prove: those parts in one chain — a catalog read, a second identity and policy decision, and graph queries, with the refusal cases inside them — and on a real cohort such as Alder’s retention rather than Acme’s invented gross margin. Each example supports the part it exercised. None establishes the combined product.

02 · Motivation

The board pack says 118%. Retention is 96%.

Illustrative scenario · Alder and Maya are invented

At 8:55 a.m., Maya Chen, VP of Finance at subscription software company Alder, opens the pack for a 9 a.m. board meeting. A $4 million plan to expand sales to existing customers leans on her agent's “verified” 118% retention. An analyst spots the mistake: the query counted new customers. Revenue from the starting customers fell 4%.

All amounts are annual recurring revenue (ARR), measured at the start and end of one quarter:

$9.6m ÷ $10.0mClosing ARR from the same starting customers only96% — retention

Maya pulls the slide. The agent found Finance's definition but missed the accompanying rule: count only customers there at the start. It reused a total-ARR query; she cannot trace the policy allowing this agent to use that asset. No execution receipt connects the query, the retention calculation and the reported result. The access gap is an unexplained decision, not evidence that the agent broke a permission boundary.

Three separate questions are left open after she pulls the slide: which linked rule was missing, which policy allowed the access, and what actually ran. The proposed runtime answers them separately: retrieve the linked definition and cohort rule with the declared computation; explain current access along that path; then validate the actual query and result against the declaration. A good context selection cannot, by itself, validate a different query. Missing evidence leaves the number unproven. The figures do not establish that the expansion proposal itself is bad; they establish that its stated justification was unproven.

03 · System design · proposed

One authored source, three runtime checks

The source bundle is canonical for authored knowledge and computation declarations. The compiler records source observations, resolves the complete artifact closure and produces immutable snapshots and publications. Catalog exposes governed discovery; BigQuery serves the compiled graph and related runtime evidence. Policy and telemetry have separate authorities.

PlanePrimary responsibilityAuthority
Source OKF bundleDefinitions, authored relations, computation declarations and review history (Git in the reference workflow)Canonical authored source; no mandatory BigQuery dependency
Knowledge CatalogDiscovery, ownership, lifecycle and links to assetsDerived discovery projection; identifies the publication it describes
BigQuery runtime projectionPinned retrieval, current-policy enforcement and computation evidenceDerived relational projection; serving authority for this profile
Agent AnalyticsObserve tool use, correlation and evaluationObserver does not decide knowledge truth or runtime authorization

Between source and projections sits the compiler / publication plane: where ingestion records live — source observations, resolved artifact manifests, snapshot membership, sync runs. They are not files in the authored bundle. Corrections flow through the source bundle, never as silent runtime mutation; a future writeback tool may propose source-native changes (a pull request), nothing more.

Three questions, three identities: what was in git (observation), what was compiled (snapshot), what was served when (publication + deployment_heads_history). Citations to humans carry publication + observation; context_ref on tool results carries publication.

01 selects context. 02 controls disclosure. 03 validates execution. The requester is authenticated before context is returned, and current access constrains every candidate and traversal hop — policy is checked before each disclosure, not audited after the return. A retained selection manifest explains the context supplied to the agent. Only the separate computation path can establish that the declared retention calculation produced the reported result. The numbered order is the reader's order; inside the runtime, authorization precedes selection, expansion and disclosure at every step.

04 · Decisions

Six agreements, each answered with one recommendation

These are decided for this RFC and stated as positions, not as a menu, so that maintainers review a recommendation rather than choose among options.

Scope — an optional profile, no OKF core change. The profile compiles unchanged OKF v0.2 input and defines only normalized runtime records and enforcement behavior. It adds no authoring syntax and makes neither BigQuery nor Catalog mandatory for conformance. Demonstrated by the Phase 0 contract fixture: the sample passes a spec-derived OKF §11 inspection unchanged (a named-validator run is still owed — see the closure table in okf-rfc-roadmap.md, an off-site working file not published here), and every key the profile reads is core or a producer-extension key tolerated under §4.1 (keys table in §06). The 2026-08-26 Knowledge Catalog post strengthens this position: it maps unchanged v0.2 bundles onto Catalog with zero new keys, which is the same conformance argument.

Placement — toolbox/okf-context/PROFILE.md, plus a one-page Discussion in open-knowledge-format. The normative document lives beside its implementation, where a maintainer will keep it in sync. The non-normative Discussion, “Runtime profile: consumes v0.2 as-is”, introduces the proposed runtime profile and the conventions it tracks; it does not imply an implemented runtime or change OKF conformance. Not knowledge-catalog/okf/proposals/ — that tree is frozen, and neither repository has a proposals mechanism today. The shipped Catalog sample lives at toolbox/mdcode/demo/okf/, beside the proposed toolbox/okf-context/; whether open-knowledge-format has Discussions enabled is unverified as of 2026-09-03, and the Discussion falls back to an issue if not.

Implementation — a separate package, toolbox/okf-context (name is bikeshed), depending on kcmd as a library. kcmd's core model is pull-then-push reconciliation of catalog metadata inside one EntryGroup; this profile is append-only, push-only, BigQuery-first. Fusing them ties the compiler to a metadata CLI's cadence and invites pull semantics back in. What is reused is what the shipped sample verifiably does: toolbox/mdcode/demo/okf/push.ts stages the bundle into Documents Layout with the OKF signal on a catalogEntry passthrough and then executes the kcmd binary. It does not reconcile deletes: generic kcmd push creates or patches each entry and carries a “TODO: Handle creates and deletes” in sync.ts; owned-prefix deletion exists only in the semantic-model deploy path. The ownership ledger and delete-only-what-you-own reconciliation are therefore this profile's addition, layered on the sample's staging as a delta, not inherited from it. Explicitly not used: toolbox/mdcode/demo/okf/pull.ts and the round-trip connector path. Phase 0 probes the exact kcmd APIs consumed.

Authority — one source, two independent reconcilers. BigQuery's relational deployment head is the runtime-serving authority; Catalog is the governed discovery projection. Both carry the same bundle, observation, snapshot, publication, and deployment IDs. A Catalog failure never rolls back a committed BigQuery publication.

Workflow — source-authoritative, push-only. validate | plan | push | status. No Catalog pull, no source reconstruction, no Catalog-side edits to source-owned fields, no second authoring path. A runtime export, if ever built, is labeled lossy. Catalog-native annotations, if allowed later, live in a separately owned aspect and never enter snapshot identity.

Source conventions — consume adopted syntax only, in this order.

  • First: PR #195 — supersedes / contested_by. The only convention with a PR, shipping producers, and query-time semantics (“exclusion follows affirmation”). The current retrieval mode depends on exactly those semantics. Consumed as-is.
  • Second: the links: carrier from #183 (target, rel, confidence) with #148's rel as predicate; confidence maps onto assertion_mode without inventing anything.
  • Later, not gated on: Discussion #261 — a vocabulary-binding layer over the #183 carrier. Declared vocabulary → namespaced predicate; none → producer:<rel>.
  • Consumed when authored, never inferred: #253 validity. #209's “expiry should down-rank, not hide” corroborates the stale_after-as-warning rule.
  • Identity: path identity until #120. No producer UID extension. A file move is delete-plus-create; a pilot needing continuity may use a profile-local concept_aliases ledger, never presented as OKF syntax.
  • Catalog types: adopt the shipped okf-bundle entry type and okf aspect. These are what the 2026-08-26 post and toolbox/mdcode/demo/okf/setup.ts register (display name “OKF Document”; a 13-field aspect whose okf_type already preserves the authored type:). No fork: entry type is fixed at creation, so a sample-pushed EntryGroup is reused, never migrated. The shipped okf aspect stays the authored-signal layer only; the profile does not append fields to that shared template. Runtime pins and stamps (publication_id, published_snapshot_id, the managed_by_* ownership stamps) live in a separately named, profile-owned okf-context-runtime aspect. The reason is mechanical: generic kcmd push replaces each aspect it stages whole (sync.ts sends updateMask=aspects with aspectKeys limited to the aspects in the staged file and sets no delete-missing flag), so a stock sample repush of the same entry would overwrite pins placed on okf but does not touch an aspect it never stages. Pins never ride in extra, which pull.ts writes back into authored frontmatter. The authored §10 contract stays on shipped fields 8–12 (runtime, parameters, computation, executor, attester); a separate okf-computation aspect carries only runtime-derived facts (computation_version_id, artifact hashes, attester identity, last verdict summary). Existing entries are reused only for physical BigQuery assets. semantic-metric / semantic-entity are not reused in v1: kcmd's semantic-model push deletes orphans under its own <model>.entities. / <model>.metrics. prefixes and the model anchor, --force-remove deletes whole models, and its guide states that an entry group holds exactly one semantic model. Phase 2b may reuse those types only if okf-context entries never sit under a model's owned prefixes and never in an EntryGroup that holds a semantic model.

If accepted, receipt and graph work continue in parallel. Receipt enforcement is the first deliverable to carry forward and must not wait for graph results or benchmark completion. The phases in §09 describe the integrated profile's implementation dependencies; they do not make the independent receipt work wait for optional Graph support.

Shipped baseline and naming — what the 2026-08-26 Catalog sample established, and what this profile adds

On the name. Informally this is still "the OKF Context Graph RFC". Normative text says OKF runtime context projection, because BigQuery Agent Analytics already uses "context graph" for a telemetry-derived graph of agent behavior, and the two must not be confused. Shipped baseline. Google's 2026-08-26 post “Scale OKF bundles across an organization with Knowledge Catalog” (Firat Elbey, Sam McVeety; the body headline reads “Using OKF with Knowledge Catalog to serve context for agents”) ships the org-scale distribution mechanism for OKF bundles: the toolbox/mdcode/demo/okf sample in GoogleCloudPlatform/knowledge-catalog registers an okf-bundle EntryType and a 13-field okf AspectType, and kcmd push publishes every markdown file in a bundle as a Knowledge Catalog Entry that inherits EntryGroup IAM and is reachable through searchEntries, LookupContext, and entries.get. This RFC does not replace that mechanism and does not change OKF v0.2; it is an optional runtime profile layered on it.

What this profile adds. The shipped Catalog sample establishes a distribution and discovery baseline. This profile proposes the additional runtime contracts: an immutable publication that a request can pin, authorized retrieval with a retained selection manifest, and independently validated computation evidence. It reuses the shipped authored-signal types. Publication pins and ownership stamps belong in the separate okf-context-runtime aspect; they never ride in the shared okf aspect or authored frontmatter. Catalog discovery and sample repush behavior do not establish that the runtime has been built.

Package mechanics, retained from the earlier summary. The proposed toolbox/okf-context package compiles the source bundle, publishes immutable runtime state and reconciles a Catalog discovery projection through kcmd; that projection is a delta on the shipped toolbox/mdcode/demo/okf sample (the same okf-bundle type and okf aspect, plus a profile-owned pin aspect and an ownership ledger), not a second one. BigQuery relational state is the serving authority. Each publication pins one source observation to one deterministic semantic snapshot and one deployment, so provenance, compiled state and rollout are never conflated. A Catalog-discovered seed carries the publication it describes: the runtime serves that retained, authorized publication or fails stale. It never silently substitutes the latest head; when the two projections disagree, status says by how many publications. Catalog discovery can start a human or agent request; runtime tools assemble the authorized context; BQAA observes their use through context_ref and owns neither authored definitions, access policy nor attestation verdicts, and nothing here defines a telemetry schema. The reference implementation is specified as push-only, relational-first and subject to the phase gates in §09.

05 · Cross-service consistency · proposed protocol

Explicit states instead of pretended atomicity

This is the proposed publication protocol. BigQuery and Catalog have no shared transaction: immutable rows first stage under an uncommitted sync_id; BQ_COMMITTED means the atomic advance of deployment_heads to a new publication_id, which is when *_current views become visible. Catalog reconciliation follows. A Catalog failure does not roll back a committed publication. The captured demos do not show this commit protocol running. The graph example's publication pointer is narrower than this cross-service protocol and does not demonstrate Catalog pinning.

  • KC_RECONCILING is a legal resting state, but lag is a metric with an owner and an SLO. Persistent KC_RECONCILING is an operational incident, not a steady state. status reports lag in publications. The lag baseline scales with entry count: the post states that every push writes every Entry, and kcmd's spec pushes entries individually, so the SLO is stated per entry count.
  • Publication pinning. Every owned entry is to carry publication_id and published_snapshot_id on the profile-owned okf-context-runtime aspect (§06). Both are top-level scalars of that aspect so they stay searchable. A Catalog-started request obtains those pins through the full-entry read path (entries.get, view=ALL, to be verified by the profile's compatibility gate), then presents them to the runtime. Serve the authorized retained publication or fail stale; a search predicate on publication_id only filters and cannot enforce the pin. Agent tools never read Catalog for lifecycle decisions.
  • Captured API behavior, narrowly scoped. In the September 3 captures, LookupContext returned overview content but omitted the okf fields for the tested shipped metric and computation entries; the corresponding full-entry view=ALL reads exposed those fields. These observations do not establish universal LookupContext behavior or demonstrate the proposed runtime pin aspect. See the metric LookupContext response, computation response, full metric entry and full computation entry.
  • History. deployment_heads answers “what is current now.” deployment_heads_history (deployment_key, publication_id, snapshot_id, committed_at, sync_id) answers “what was current for deployment D at time t.” Both are Phase 1 deliverables.
06 · Proposed model

Design detail, collapsed by intent

Identity: observations, snapshots, publications, versions
  • bundle_key — stable identity of one logical source bundle, independent of revision, deployment, and publication attempt.
  • concept_key — bundle_key + "#" + concept_id, where concept_id is the bundle-relative path without .md (OKF v0.2 fallback). Changes on a file move; see Decision 6.
  • Reserved files are not concepts. index.md (OKF §8) and log.md (OKF §9) are bundle content for source_manifest_hash but receive no concept_key, no version rows, and no edges; an index is navigation and a log re-versions on nearly every edit. The Catalog projection still emits index entries and the root log.md entry for parity with the Documents Layout, owned and pinned as non-concept entries (see Catalog ownership below).
  • concept_version_id — identity-and-content-derived: canonical structured hash of (concept_key, normalized_frontmatter, normalized_body). A version carries an authored locator, not a source revision — one version can appear in many revisions.
  • observation_id — one observation of the source: hash(bundle_key, source_uri, revision). Ingestion state, not bundle content.
  • snapshot_id — deterministic identity of the complete compile-input closure under compiler_semantics_version. It identifies the inputs and their interpretation; a hash alone does not certify compiled output. Many observations may map to one snapshot.
  • publication_id — one observation compiled to one snapshot and committed to one deployment. deployment_heads points to a publication, not only a snapshot.
  • deployment_key — where and under which runtime policy publications land; sync_id — one operational attempt.
  • index_build_id — an embedding/search-index build; envelope_id — one context package delivered; receipt_id — one execution-evidence record, which may carry an unproven or rejected verdict. A receipt's existence implies no verdict.
snapshot_id    = SHA256("okf-context:snapshot:v1\0" || canonical_cbor({
                   bundle_key, source_manifest_hash, canonicalization_manifest_hash,
                   compiler_semantics_version, semantic_config_hash,
                   vocabulary_manifest_hash, resolver_manifest_hash }))

publication_id = SHA256("okf-context:publication:v1\0" || canonical_cbor({
                   deployment_key, observation_id, snapshot_id, profile_contract_version }))

Republish semantics, precisely. Retrying an identical publication (same observation, snapshot, deployment) is a no-op: no rows, no head change. Publishing a new observation of an unchanged snapshot creates a new publication row and advances the head to it, with no new semantic rows — a semantic no-op that is still a provenance event, and therefore not silent.

source_manifest_hash covers every regular file under the bundle root, exhaustively — the bundle root must contain only bundle content, so VCS/CI metadata and validation tooling live outside it and affect validation provenance, not snapshot identity (PROFILE.md §2.8 gives the full membership, path, and symlink-rejection algorithm). All structured identifiers use domain-separated canonical structured encoding, never bare string concatenation; the only raw-byte hashes (per-file, compile-manifest, and artifact bytes) are enumerated in PROFILE.md §2.2.

Configuration is scoped, not lumped

Semantics-affecting config (semantic_config_hash) belongs to the snapshot; chunking/embedding/index parameters (index_config_hash) to the index build; project, dataset, IAM mode, retention, region (deployment_config_hash) to the deployment. Retrieval-selection inputs (query or walk definition, bindings, fact versions, limits, ordering, packing) belong to the retained envelope manifest, never to snapshot identity.

Snapshot membership is the temporal model

Membership maps logical identities to exact versions per snapshot and is logically complete and immutable; any deduplicated physical representation is acceptable provided exact membership for any retained snapshot_id is reconstructible without consulting mutable current state. Deletion is absence from the next snapshot. Reserved files (index.md, log.md) are recorded in membership as non-concept files, so reconstruction includes them without minting concept versions. What this gives is immutable system-time publication history — not bitemporality. Business validity is populated only when explicitly authored.

Artifact closure

computation_version_id = hash(concept_version_id, parameter_schema_hash,
                              computation_artifact_hash, executor_artifact_hash,
                              attester_artifact_hash, runtime_contract_version)

Each snapshot retains an artifact_manifest (authored reference, resolved URI, content hash, media type, role, resolution status, bytes retained). A computation is “reconstructible” only when every load-bearing artifact is retained by content hash or immutably content-addressed. The compiler never merges two documents into one concept on embedding or LLM similarity alone.

Relationships, resource nodes, and unresolved links

Resolved bundle-internal Markdown links compile with no extensions, each to a generic explicit edge under a profile-local predicate (context:untyped_link) — deliberately not an OKF core predicate, since OKF v0.2 links are untyped with meaning carried by prose. External hyperlinks in prose are not materialized as nodes. The compiler never guesses a stronger predicate.

For Alder, selection follows Finance's authored links from the retention definition to the starting-cohort rule and computation declaration. Plain Markdown links remain generic links unless an authored producer extension supplies a stronger predicate. The compiler never invents a cohort relation from semantic similarity.

Assertion identity ≠ logical edge identity

logical_relationship_key   = hash(source_key, canonical_predicate, direction, target_ref)
relationship_assertion_key = hash(logical_relationship_key, assertion_mode, source_kind,
                                  evidence_locator, producer_assertion_id | source_occurrence_id)
target_ref                 = "resolved:" + concept_key
                           | "unresolved:" + normalized_authored_target   # namespaced, never null-collapsed

Equivalent edges from multiple sources are preserved as distinct assertions; presentation may collapse by logical key. assertion_mode (explicit | imported | deterministic-derived | inferred) is always preserved; inferred is always labeled inferred. The complete assertion ledger lives in BigQuery; Catalog receives only the links it can express.

Versioned resource nodes

Edges may target a resource_uri — a real BigQuery table. Resolution is external state, so resource nodes get versions and snapshot membership; resolver outputs are pinned via resolver_manifest_hash so the same source cannot silently compile differently because Catalog or BigQuery state changed.

Unresolved links

OKF requires consumers to tolerate broken links. The relational runtime is lossless: unresolved assertions keep the authored target under a namespaced unresolved: key and resolution_status: unresolved, so two missing targets never collapse into one assertion. The optional Property Graph projection includes resolved edges only.

Runtime schema, current views, and the graph projection

Append-only version tables, snapshot membership, snapshot_observations, publications, deployments, deployment_heads, deployment_heads_history, sync_runs, execution_receipts, and the ownership ledger for Catalog artifacts. Current views resolve through deployment_heads — never a global “latest snapshot.” “Current” is always current for a deployment.

Relational is authoritative. The OKF graph projection consists of versioned concepts, resources and relationship assertions with immutable snapshot membership. Seed lookup, bounded expansion, evidence traversal and path explanation work through relational queries. The relational baseline and receipt delivery do not depend on Property Graph. Enabling the optional Graph implementation requires its own equivalence, authorization and operating-budget checks.

Two kinds of determinism. Compilation fixes the semantic input closure — the same source manifest, canonicalization manifest, compiler semantics version, semantic config, vocabulary manifest and resolver manifest — and reproduces its snapshot_id. Controlled retrieval fixes the publication and selection contract to reproduce selected context. Index builds (index_build_id), ranking, policy evaluation and packing are separate inputs; a deterministic compiler does not make every search or model decision deterministic.

Property Graph is optional. A nodes_current view unions concept and resource nodes (ContextNode, node_kind = concept | resource, namespaced keys). Current BigQuery Graph documentation describes graph inputs from tables or views. This profile still must test its own versioned projections, element-key uniqueness (a definition the compiler validates itself, not an enforced constraint), permissions and relational/GQL equivalence in Phase 5. Graph names are deployment-scoped and must not collide with kcmd's semantic-model graphs in the same project.

Where the evidence stands. The recorded graph example demonstrates a scoped graph projection and retrieval path. It does not implement this RFC's complete identity, publication, access or receipt contracts. Relational serving remains authoritative, and the optional Graph implementation still needs its own equivalence and operating checks.

Product boundaries. GQL queries require Enterprise or Enterprise Plus; creating a graph on-demand is not evidence of on-demand GQL support. GRAPH_EXPAND is not a general substitute for an OKF link graph: its schema relationship graph must be single-root and acyclic, and ambiguous or many-to-many relationships are omitted from that schema graph. Ordinary relational SQL and vector retrieval remain available on-demand. The recorded example used generally available vector search plus GQL; graph-native semantic search is separately marked Preview and was not the tested route. A customer who cannot accept Preview needs a supported generally available route that preserves the required semantics. Google's placement guidance distinguishes analytical work from online neighborhood retrieval, so the broad serving-tier case stays more tentative than the case where the facts already live in BigQuery.

Replayable retrieval, lifecycle modes, and the Context Envelope

Discovery can start with keywords, vector similarity or a model-selected seed. Those techniques find candidates; they do not by themselves bind a definition, its linked rules and its computation into one repeatable selection. The proposed controlled path starts from a fixed selection and uses explicit SQL or bounded relational walks over a pinned publication.

authenticate requester → evaluate current policy
          → seed (explicit selection; lexical / semantic discovery optional)
          → structured filters → bounded relational expansion over the pinned publication
          → dedupe → stable rank + tie-break → token-bounded Context Envelope
          → retain selection manifest → emit context_ref

What must be fixed. Record the publication; seed IDs; query or walk definition and bindings; versioned facts used by selection; traversal depth and result limits; lifecycle evaluation time/mode; ranker and index build if used; stable tie-breaking and ordering; output schema; tokenizer and packing budget. Exclude volatile functions and unversioned external inputs from the controlled guarantee. An explicit order, including tie-breakers, is part of the query contract, not something SQL supplies implicitly.

With those inputs fixed and equivalent effective access, the controlled path selects the same versioned items, paths, ordering and context shape. It need not reproduce request timestamps, opaque envelope IDs or the LLM's final answer. If a model picks a different seed, an index changes or a token budget changes, those are different inputs. Vector retrieval can be deterministic; the comparison is about explicit selection semantics, not an intrinsic defect in embeddings. Graph retrieval implies neither identical model answers nor factual truth.

Current authorization still applies. Authenticate the requester and evaluate current policy before disclosure and throughout the path. A historical publication does not preserve permission to read it. Revocation, quarantine, purge or expired retention may prevent replay; the runtime must not restore historical privileges to manufacture identical output.

Authorization constrains every step — candidates, every expansion hop, edge visibility, evidence retrieval, computation discovery and execution, outputs, and cached envelopes. An authorized seed must not traverse through an unauthorized intermediate node. The enforcement unit may be a concept, chunk, assertion, evidence record, resource, or computation (#209: concept granularity is not assumed sufficient; this holds for the BigQuery runtime, see the Catalog unit below). Fail closed when access cannot be evaluated.

Policy authority, v1. OKF frontmatter is not an ACL, and OKF v0.2 defines no fragment-level policy. The initial profile supports one security domain per bundle/deployment, with caller-delegated BigQuery authorization as its policy source. Mixed-policy bundles fail closed unless an external policy resolver is configured. Per-node enforcement is proposed integration work; placing access relationships in graph metadata does not enforce them.

For this custom-entry Catalog projection, the EntryGroup is the access boundary for published concept bodies: IAM is set on the EntryGroup and, per the post, cascades to its Entries, and the overview aspect carries the full concept body. This is not a claim that all Catalog permissions operate only at EntryGroup scope: source-system metadata permissions and entry/aspect operations have their own checks (Catalog IAM permissions). Anything the runtime denies below concept granularity would be readable in a body projection, so a bundle with mixed body visibility must not be projected into one broadly readable EntryGroup; it fails closed at projection time as well.

Who accessed which asset, under which policy? Bind the authenticated user or agent requester to the execution identity at the trusted runtime boundary. Evaluate policy against the projected asset and, when fetching underlying data, its source permissions. Check intermediate nodes and evidence as well as returned nodes. A shared service account alone cannot identify Maya's agent; a node containing an access label cannot grant access to a file.

Retain the evaluated policy version/context and permitted asset decisions in privileged audit records linked to the request. Keep source permissions current and reevaluate cached or historical reads. User-visible explanations expose only authorized paths; full decisions and denied-asset details stay behind the audit boundary.

Alder consequence: Maya can trace why the agent was permitted to use the total-ARR asset. Permission to read that asset does not make its query the correct retention calculation.

Where the evidence stands. The recorded graph walk does not yet establish these access guarantees inside graph queries. On 2026-09-06, five checks with a separate restricted identity passed on the relational fallback path over the same protected tables (hidden intermediate, denied bundle with no denied node or section identifiers in the reply or error text, output denied while the seed store stayed readable by a row count with search denied, no owner-credential fallback, revocation before cached replay), graded behind an allowed control and with temporary grants removed and read back (access case records). The same cases inside a graph traversal have not run, and protection against hidden-identifier disclosure under the operator's identity and across mixed publications remains unproven live. The receipt example's job-owner and dataset-grant tests cover one job, not per-node graph authorization.

The Context Envelope

envelope_id is an opaque, random, tenant-scoped identifier issued at pack time — not a public content hash, because a deterministic hash is linkable across users and runs. Equality for cache reuse is decided by a privileged keyed digest kept in the manifest, never exposed:

policy_context_commitment = HMAC-SHA256(tenant_scoped_key,
    "okf-context:policy-context:v1" || 0x00 || canonical_cbor(effective_policy_context))
envelope_equality_digest  = HMAC-SHA256(tenant_scoped_key,
    "okf-context:envelope:v1" || 0x00 || canonical_cbor({ publication_id, index_build_id,
    policy_context_commitment, ordered_items, rendered_content_digest, packing }))

A policy context is a handful of group memberships — lower entropy than a date range — so it gets the same keyed treatment as parameter bindings, and its serialization is versioned so that cross-principal cache reuse is collision-safe across authorization-model versions.

The retained manifest lives in the runtime dataset under source-equivalent IAM and records policy and ranker versions, tokenizer version, token budget, ordered version/chunk/assertion IDs, paths, warnings, and the observation for citation. Principal identity never enters the envelope. Possession of an envelope_id grants nothing: reads and replays still pass tenant, deployment, publication, revocation, retention, quarantine, and purge checks.

Retrieval evidence

Retain the selection inputs, returned version IDs and paths, policy/ranker versions, ordering and packing in the governed envelope manifest. Record the authoritative retrieval job/query evidence needed to explain the selection. This is the proposed “retrieval receipt”: a record of context selection, not proof that the business metric ran, and not a new attestation verdict or public identifier. Define its versioned serialization before implementation; do not change public identifiers or context_ref as an incidental documentation edit.

Explainability without side channels: caller-visible explanations return authorized candidates and ranking decisions only — no denied counts (even “1 result filtered” discloses existence), or at most coarse buckets where policy allows. Full access decisions go only to a privileged audit view.

The retained manifest can reconstruct an authorized historical envelope without rerunning discovery; §07 distinguishes that reconstruction from a controlled query rerun.

Verifiable execution: the Attested Computation protocol

Retrieval identifies the declared computation. Execution must separately demonstrate what actually ran. The proposed Attested Computation path binds the context publication and envelope, computation artifact, complete declared parameter bindings, caller-delegated BigQuery job and result path. Validation must also tie the reported result to that execution; matching a query while substituting its displayed answer is insufficient.

Attested Computation is the only execution path whose result may carry this profile's attestation claim for a declared computation. The agent binds declared parameters only (OKF §10); it cannot edit SQL, swap the referenced computation, add parameters, bypass the attester, or run deprecated computations without explicit override. The independent, constrained attester checks authoritative execution evidence under the threat model below. A successful lookup, a self-reported “verified” label or a job ID alone cannot supply that evidence.

Alder consequence: If the job used total-ARR SQL instead of the declared starting-cohort calculation, the mismatch is rejected. If the required artifact, binding, job or output evidence is unavailable, the verdict is UNVERIFIABLE. Either way, 118% cannot be presented as an attested retention result. A retrieval receipt does not turn it into one.

Identity model, decided

Execution is caller-delegated: the computation runs under the caller's BigQuery identity, and BigQuery IAM remains the authorization source of truth. The proposed attester runs as an independent, constrained service identity — not as the caller, because a caller-run attester can be subverted by the caller. Job-metadata access on the executing project (a bigquery.jobs.listAll-class permission such as roles/bigquery.resourceViewer, a Phase 0 probe candidate rather than a proven sufficient grant) can establish which query and parameters ran, but metadata alone cannot bind the reported value to the authoritative result. The full profile therefore also requires a stated, trusted path for result evidence and a consumer that enforces the verdict before release. The exact evidence mechanism and least-privilege grants, including cross-project and cross-region cases, remain design and validation work; broad source-row access remains excluded. Until the required result evidence is available, the verdict is UNVERIFIABLE. Constrained-service-identity execution is out of v1.

Named query parameters, required

Attested SQL executes with BigQuery named query parameters, so the executed query string is the template and bindings appear in job configuration. executed_artifact_hash is computed over the template; the attester compares template text and job parameters literally, with no re-rendering.

Verdicts are exact and fail closed

ATTESTED requires all of: authoritative artifact identity, complete parameter binding, authenticated caller, BigQuery job metadata, result destination, output authorization, authoritative result binding, attester key validity, and evidence digest. Anything less returns UNVERIFIABLE or REJECTED; unavailable evidence never degrades to success. “Parameters where available” cannot support an attested verdict. Missing evidence stays unproven; a demonstrated mismatch is rejected. Separately, a consumer releases a result only after validating a matching successful verdict against the current release conditions; failed or unavailable checks withhold it. A completed release is never a prerequisite for computing the verdict.

Where the evidence stands. These are acceptance requirements of the proposed profile. The wider demo's computation checks remain placeholders. The separate Acme receipt example demonstrates checked result release under the requester's delegation, including verification in a fresh process, with wrong-query, wrong-parameter, substituted-display, tampering, replay and missing-evidence cases withholding the result. It does not establish the independent attester, portable receipt verification or the complete connected profile described here: its verification used the requester's own credentials and a locally held HMAC key, and its example verdict is not this profile's ATTESTED. Neither the Alder illustration nor the recorded probes satisfies this attestation contract.

Two receipt artifacts

(1) The execution receipt presented to the attester may include executed SQL, bound parameters, result, and job metadata — the attester needs authoritative evidence, matching OKF's executor.receipt contract. (2) The persisted receipt projection stores commitments and governed metadata per retention policy.

Authenticated verdicts

The persisted receipt carries receipt and attester identities, verdict, details digest, and an integrity_proof (service signature, runtime MAC, or immutable audit-log reference) with algorithm and key ID. receipt_digest is computed over a versioned canonical serialization; the proof covers at least that digest, the attester artifact hash, and the profile contract version. Verifiers reject a receipt whose canonicalization version they do not understand.

Keyed commitments with domain separation

parameter_binding_commitment = HMAC-SHA256(tenant_scoped_key,
    "okf-context:parameter-binding:v1" || 0x00 || canonical_cbor(parameter_value_map))

Low-entropy parameters make plain hashes dictionary-attackable. Keys remain verifiable for the receipt-retention period or the receipt transitions explicitly to a crypto-erased state. Key custody, rotation, revocation, retained-receipt verification, and crypto-erasure are Phase 4 gates, not prose.

Threat model, stated honestly: attestation protects against an agent substituting an improvised computation, parameters, or displayed result. It assumes the configured executor, BigQuery, the attester runtime, and the receipt-integrity mechanism are trusted. It does not prove correctness against a compromised executor, attester, credential, administrator, or underlying data source. Attestation is evidence of process integrity, not a guarantee of data quality.

Attesters are bundle-authored code (attester.resource), possibly agent-written: sandboxed, restricted identity, subject to the same review as the computations they attest. “Deterministic” is a review property, not enforced.

Seam with BigQuery Agent Analytics

Agent Analytics is observed, not a fifth source of truth. This profile never writes to agent_events, never defines event types, span cardinality, sampling, retention, redaction, evaluation semantics, or health aggregation. It emits identifiers on its tool results. That is the entire seam.

Retrieval and access evidence stay in the governed runtime records. “Retrieval receipt” is explanatory language for the selection record; it does not add principal, policy or graph-path fields to context_ref. BQAA may correlate permitted identifiers, but it neither grants access nor upgrades an unproven execution verdict.

What this profile emits

One versioned sub-object, context_ref, on the response of every profile tool:

context_ref:
  profile_contract_version        # "okf-context/1"
  bundle_key, observation_id, snapshot_id, deployment_key, publication_id
  index_build_id                  # only when an index was used
  envelope_id                     # search / expand / pack results
  computation_version_id, receipt_id, bq_job_id, verdict   # run_attested_computation only
  candidate_bucket                # coarse bucket, never an exact denied/filtered count
  included_count
  warning_codes[]                 # stale, unresolved, contested, draft — codes only

Packed items carry a citation token [okf:<envelope_id>#<n>] so a later “was it cited” analysis can join on envelope_id without item IDs leaving the runtime dataset.

What it never emits into telemetry

concept_version_ids, graph paths, authored locators, principal, policy context (hashed or not), raw query/prompt/answer text, raw bound values. Those live in the envelope manifest and receipts in the runtime dataset and are joined by envelope_id / receipt_id under that dataset's IAM. Telemetry holds opaque IDs only, so it cannot become a path around source authorization.

What BQAA owns

Decided in the companion RFC in the BQAA SDK repository: the event envelope, the TOOL_STARTING / TOOL_COMPLETED / TOOL_ERROR events the profile's tools naturally produce, the attributes key where context_ref lands, content truncation of tool bodies, OTel correlation and the pinned semantic-convention version, principal pseudonyms (keyed and purpose-scoped, not salted hashes), retention, evaluation, citation detection, and Knowledge Health. If Catalog displays a health aspect, it is BQAA-owned, windowed, carries sample_count, and is stored opaquely — never part of KC_APPLIED, publication completion, or snapshot identity.

Catalog ownership and reconciliation

Mapping. The baseline is the shipped sample described in the 2026-08-26 post. One okf-bundle entry per concept; the shipped 13-field okf aspect exactly as the sample writes it (authored type as okf_type, lifecycle, provenance, the §10 contract); a profile-owned okf-context-runtime aspect on every owned entry carrying publication_id, published_snapshot_id, and the managed_by_* stamps; a runtime-derived okf-computation aspect on §10 concepts; index entries with parentEntry set as the Documents Layout sets it, owned but never concepts; the root log.md projected as a non-concept okf-bundle entry exactly as the sample projects it (overview body plus okf with okf_type: Log), owned, pinned with okf-context-runtime, and reconciled like index entries; entry links to existing BigQuery table/column/dataset entries, never duplicates. Catalog has a small set of system link types, so only relationships with matching Catalog semantics are materialized as EntryLinks; the partial projection is documented, and the full ledger stays in BigQuery. No Catalog→source or Catalog→BigQuery import is introduced.

Ownership. The EntryLink API offers no general ownership-stamp surface, so ownership is tracked in a BigQuery ledger keyed by deterministic deployment-scoped link and entry IDs, with managed_by_* stamps carried on the profile-owned okf-context-runtime aspect, never on the shared okf aspect. Reconciliation removes or replaces only artifacts this deployment owns; existing system entries and other bundles' state are referenced, never garbage-collected. The shipped sample never deletes (generic kcmd push is a create-or-patch upsert), so absence-from-snapshot is carried into Catalog by okf-context itself, under the ledger. Coexistence is tested adversarially in Phase 2 against two pushers in the same EntryGroup: a kcmd semantic-model push, and a kcmd Documents-Layout push of the same bundle (the shipped sample, which derives the same path-based entry names). The sample's repush rewrites overview and okf on those shared entries and leaves okf-context-runtime untouched, so ownership and pins survive it; that is the exact assertion the Phase 2 gate makes. IAM does not separate them: roles/dataplex.catalogEditor grants entry delete across the EntryGroup, so the ledger is a discipline, and one EntryGroup per team is the IAM boundary for the custom-entry body projection shared by those publishers.

Non-goals

No mandatory BigQuery/Catalog dependency for OKF; no new OKF authoring syntax or core predicates; no universal ontology or required semantic-web stack; no LLM-guessed typed edges; no universal truth score; no telemetry in the source bundle; no frontmatter-as-access-control; no Catalog→source writeback in v1; no arbitrary agent SQL; no low-latency transactional graph workloads; no telemetry schema in this RFC.

07 · Reproducibility

Replayable context has explicit inputs and limits

These proposed guarantees would hold only while the needed records are retained and the caller is still authorized. A stable identifier does not promise indefinite storage, continuing access or unchanged business data. The levels below are distinctions in the proposed contract, not experimental scores. The recorded examples, including the one connected chain, do not demonstrate them as a whole.

1
What a snapshot and publication identify. A snapshot identifies its complete compile-input closure; a publication identifies the observation/snapshot/deployment binding. Identity alone proves neither output correctness nor a successful recorded deployment.
2
Reconstruct a retained snapshot. Reconstruct complete snapshot membership and immutable versions while they remain retained.
3
Reconstruct a retained context package. Reconstruct what was served from its retained manifest and referenced content, without rerunning discovery. Apply current access, revocation, quarantine and purge checks.
4
Repeat a selection with the same inputs and effective access. Mutable facts or an expired data snapshot can prevent reproducing the number, even when the context is known; BigQuery time travel has a bounded window.

08 · Acceptance

What a “yes” means

Accepting this RFC agrees to a design and its gates. It does not mark those gates complete.

The OKF bundle remains the portable canonical source for authored knowledge and computation declarations; Catalog and BigQuery are independently reconciled projections, with BigQuery relational state as serving authority.
This is an optional profile with zero new required OKF fields and no new authoring syntax; the Phase 0 sample passes §11 conformance unchanged.
Plain bundle-internal links compile with no extensions; typed relationships are preserved as provenance-bearing assertions when present.
Observation, snapshot, publication, and sync attempt are distinct identities; a provenance-only republish is a publication event, not a silent no-op.
Replayable context: a fixed authorized publication and selection contract return the same versioned definition, cohort rule and declared computation, with selection evidence. Catalog pins either resolve as requested or fail stale.
Explainable access: every disclosed path is authorized under current policy. Requester/execution binding and privileged records explain returned assets; denied intermediates and revoked cached access fail closed without leaking asset existence.
Verifiable execution: a substituted query or result fails validation; incomplete authoritative evidence yields UNVERIFIABLE. The receipt binds the actual execution to the declared computation and supplied context. Attested Computation remains the only path carrying this profile's attestation claim — caller-delegated execution, an independent attester identity, complete-evidence verdicts, and a stated threat model. The attester needs a stated, trusted path to authoritative result evidence, because job metadata alone cannot bind the reported value, and the consumer releases the result only after validating a matching successful verdict.
First workload: a projected graph can be the first workload on Enterprise or Enterprise Plus capacity once its authored inputs and the required versioned facts are loaded. That adoption route is separate from the stronger case where the facts already live in BigQuery; ordinary relational SQL and vector retrieval can also run on-demand.
Connected evidence before promotion: the combined delivery claim upgrades only when one chain runs end to end — catalog discovery, pinned publication, governed retrieval, caller-delegated computation, result-bound receipt and consumer-enforced verdict — with publication consistency and negative tests for denied intermediate nodes, revoked access before cached replay, unauthorized output access and a shared service account mislabeled as the requester. BQAA is the observer: this RFC emits context_ref and receipts and specifies nothing else about telemetry.
Placement, package, convention order, Catalog types, and identity are decided as in §04. The recommendations in §04 define the proposed scope; unresolved implementation evidence belongs to the phase gates below. The named-validator run and owner sign-offs remain open.

Receipt check. The recorded receipt check ran a BigQuery job under the caller and verified it independently of the process that produced the result, releasing the number only once query, inputs and result agreed. Where the query, its inputs, the displayed value or the evidence failed validation, the result was withheld, as its recorded cases show. This is example code and tests, with no library change. Verification used the requester's delegation and a local signing mechanism; it does not establish a separate verifier principal, portable signatures or accounting correctness. It did not run Alder's retention calculation.

Connected chain. The chain began at a live read of a catalog entry and ran on Acme’s invented gross-margin data under a single identity holding both legs, so no second identity or policy decision was exercised, and retrieval used plain SQL rather than the graph walk. The catalog confirmed which publication to use and no more: the returned pin was checked field by field against already-trusted configuration, so an entry cannot name a different project or dataset. The chain then compiled the pinned source as its trusted copy, retrieved the declared calculation and its SQL through governed retrieval, checked every returned node, edge and governance field against that copy, and only then handed the calculation to the receipt check, which ran the job under the caller and verified it in its own process. The consumer released the number only after that check passed; a substituted query and a mismatched declaration were both refused, the second before anything ran. Further runs held a pinned version against a republished head, and stopped without a calculation or a receipt wherever the publication or its content failed validation (what those cases showed and their limits). The number released was Acme’s invented gross margin, not Alder’s retention, and the formula swap was the receipt example’s fixed case, not the total-ARR query from the story.

10 · Closing

Give the agent context it can replay—and a number it can account for

OKF supplies the authored definition, relations and computation declaration. Catalog makes that knowledge discoverable and governed. The proposed BigQuery runtime would select a pinned context, explain current access and check execution evidence. BQAA observes use without becoming the authority for any of them.

The proposed BigQuery runtime would turn the OKF graph into replayable context for agents—with explainable access and evidence that the declared computation ran.

One pilot. Sponsor a Finance-owned retention pilot on real cohort data, with an agreed operating budget. Connect catalog discovery, pinned retrieval, current access checks, caller-delegated computation and result-bound consumption in one path. A substituted query or result, revoked access or missing evidence must withhold the claim. Alder's invented 96% is not a target for the pilot's data.

Reassess the opportunity at the 2026-09-19 evidence checkpoint. It narrows if customer budgets or Enterprise cost cannot be met, if simpler retrieval serves the need, if required semantics, authorization or publication guarantees fail, or if result evidence cannot be trusted and enforced. Customers who cannot accept Preview need a supported generally available route. The checkpoint is a decision about the evidence, not a promised production date.
