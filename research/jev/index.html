01 / THE IDEA

An AI function your code can call.

Jev takes evidence and a set of questions, then returns probabilities over answers you define.

TypeSafe calls it a System One model: fast, focused judgment for software. It understands natural-language input but does not write replies, SQL, code, or explanations. Your application decides what to do with the answer. [2]

IMAGINE A CUSTOMER MESSAGE
“I was charged twice for the same order. Please fix it.”
CHOICE

Which team?

Billing 94%
Technical 4%
Other 2%

NOUL

Refund requested?

Probability of yes
0.96

SCORE

How frustrated?

Calm → upset → angry
1.3 out of 2

Invented outputs, shown to explain the three types. Noul is TypeSafe’s name for a yes/no probability. [3]

The evidence is called state. It might contain a conversation, transaction records, and a policy. Each question sees that same material. “State” means the input to this request; it does not promise persistent agent memory. Current inputs are text-based strings, JSON objects, or arrays—not images, audio, or video. [4]

The exact output contract

Choice returns an option, a distribution across all options, and a derived confidence statistic. Noul returns the probability of yes. Score uses an ordered rubric, returns probabilities across its levels, and a probability-weighted score. [3]

For levels 0, 1, and 2 with probabilities 0.1, 0.5, and 0.4, the expected score is 0×0.1 + 1×0.5 + 2×0.4 = 1.3. A score of 1.3 describes position on a rubric. A yes/no probability of 0.5 describes uncertainty, not medium severity.

Offer an “other” or “insufficient information” choice when appropriate. A constrained model can only choose among the possibilities you provide.

02 / THE ARCHITECTURE

Read once. Ask in parallel.

Two expensive habits can be reduced: repeatedly processing the same evidence, and generating a long answer.

A language model first processes its input (prefill), then normally generates output one token at a time (decoding). The scores available at the first output position can already support a decision. OpenJev reads those scores and stops. [7]

EXPLORE SHARED CONTEXT

No prefix reuse200,000state-token processing count
Ideal shared prefix10,000state-token processing count

20 × 10,000 versus 1 × 10,000 state tokens.

An accounting illustration, not a latency or FLOP benchmark. Question processing and attention to the state still cost work. Cache hits are not guaranteed. [5][8]

What the architecture investigation found—and did not prove

Archer Hume probed Jev’s API and reconstructed a plausible architecture. Experiments supported isolation between questions, sensitivity to option order, and interaction among alternatives within a question. These observations constrain possible designs; they do not uniquely identify an attention mask or model family. [1]

The article proposes shared-prefix computation, a causal transformer, and direct readouts. It considers both fixed option-slot scoring and a pointer-like scorer. Sparse mixture-of-experts is the least certain hypothesis. No published weights or full training recipe establish these details. Nothing in the observed behavior requires diffusion. [1]

A mixture-of-experts model stores multiple expert networks and activates only some for each token. That is a possible efficiency mechanism, not an identified Jev component.

Why “causal” does not mean reading input one token at a time

During prefill, every input token is already known. Within a transformer layer, many positions can be processed together while an attention mask prevents a position from seeing forbidden later input. Layers still depend on previous layers. Autoregressive generation adds a different dependency: the next output token does not exist until the previous one is selected.

A KV cache stores attention keys and values from processed tokens. Prefix reuse preserves this intermediate work across requests with common text. It does not remove the cost of reading that context from a new question. SGLang’s RadixAttention is a published approach to automatically reusing shared KV-cache prefixes. [20]

“Parallel” also does not mean one GPU per question or unlimited throughput. It means the branches can be scheduled without waiting for each other’s answers.

Question independence is not probability independence

The API’s contract says each question is evaluated against the shared state. Another answer is not automatically hidden context. If a later question needs newly fetched data or an earlier decision to define its options, make a second request. [3]

Two judgments can nevertheless be correlated. “Is the customer angry?” and “Is the language hostile?” might depend on the same words. Multiplying their probabilities assumes statistical independence, which the serving architecture does not establish.

03 / INSIDE OPENJEV

A working implementation you can inspect.

OpenJev turns an open language model’s next-token scores into a Jev-compatible decision API.

The repository uses Qwen3.6-35B-A3B with SGLang, deployed by default on a B200 GPU. Its jev-latest name is a compatibility alias: requests run on the configured open model, not TypeSafe’s Jev. [5]

  1. 01
    Compile the request

    Render the shared state and independent question suffixes using the model’s chat template. Disable thinking. [6]

  2. 02
    Give every option a one-token label

    Use verified labels such as A, B, and C, preserving the original option names for the response. [6]

  3. 03
    Warm the prefix, then submit branches

    Complete the shared-prefix call first. Submit question calls concurrently, subject to capacity limits. [8]

  4. 04
    Read label scores and format the result

    Request one output position, ignore the sampled token, normalize the allowed labels, and assemble the response. [7][9]

“Prefill-only” has a small implementation nuance.

OpenJev makes N + 1 one-token calls for N questions, including cache warmup. It has no continuing answer generation, but the backend does produce one sampled token per call. [5]

The code-level path, labels, and limits

prompts.py builds a common prefix and one suffix per question. Choice descriptions determine semantic meaning; keys are hidden unless a null description makes the key the fallback. Labels must encode as exactly one distinct token. This avoids comparing only the first token of a multi-token label such as a number. The compiler validates its set of 64 labels at startup. [6]

service.py awaits cache warmup before creating concurrent branch tasks. It validates context and total submitted-token budgets before GPU work and cancels sibling tasks on failure. [8]

backend.py requests max_new_tokens=1, selected-label log probabilities, and no prompt-logprob recomputation. Its parser checks that one output position was returned. [7]

Default limits include 64 questions, 2–64 options per Choice or Score, and 32,768 tokens per branch including output. Caching is opportunistic, not a pinned per-request session; hybrid recurrent state and memory pressure can affect hits. [5]

Why API compatibility does not mean model equivalence

Compatibility can reproduce field names and output types while leaving weights, prompts, calibration, limits, and serving behavior different. OpenJev’s implementation does not supply TypeSafe’s RLCD training recipe. A functioning replica demonstrates feasibility of the interface, not equivalent decision quality.

The repository’s controlled payload comparisons still involve different internal models and prompts. Any quality gap is a comparison of services, not a clean experiment isolating a single training technique. [11]

04 / PROBABILITY & TRUST

A number is not yet a trustworthy probability.

“90% confident,” a 0.90 token score, and a calibrated 90% prediction are three different things.

WORDS

“I’m 90% sure.”

A sentence the model generated.

MODEL SCORES

Label A: 0.90

A numerical preference over allowed labels.

CALIBRATION

About 90 in 100

The observed success rate across similar predictions.

Calibration asks whether predicted probabilities match outcome frequencies across groups. Neural networks can be confidently wrong; direct numerical output alone does not fix that. [16]

CALIBRATION, MADE VISIBLE

100 predictions, each saying “80%.”

A well-calibrated group would have about 80 correct answers.

80 predicted out of 100. 80 actually correct.

CorrectIncorrect

Illustrative population, not measured Jev data.

TypeSafe describes Reinforcement Learning for Calibrated Decisions (RLCD) as post-training for decisions and honest uncertainty. Its public explanation gives an objective, not a complete reproducible algorithm. Calibration describes groups of predictions; it cannot guarantee any one answer. [14]

Normalization: a distribution can sum to 1 and still be misleading

Suppose a model assigns next-token probability 0.12 to A, 0.06 to B, 0.02 to C, and 0.80 to everything else. Keeping only A/B/C and renormalizing yields 0.60, 0.30, and 0.10. These numbers now describe relative preference within the allowed set.

LabelRaw probabilityReturned share
A0.120.60
B0.060.30
C0.020.10
Other tokens0.80Excluded

OpenJev applies stable softmax to the selected label log probabilities. Normalization does not establish that the chosen answer is correct at the stated frequency. That requires an outcome-based evaluation. [9]

Probability versus the API’s separate “confidence” field

TypeSafe says confidence is a statistic derived from the returned distribution. A peaked distribution receives higher confidence; a spread-out one receives lower confidence. Noul has no separate confidence field. [15]

The public TypeSafe LLM adapter computes Choice confidence as (p_max − 1/K) / (1 − 1/K) for K > 1. Three options with a maximum probability of 0.8 give confidence 0.7. This is verified adapter behavior, not proof of the proprietary endpoint’s exact formula. Its Score calculation uses distances from the modal level. [17]

OpenJev instead uses 1 − entropy(p) / log(K). Both are concentration summaries; neither is a new estimate trained against correctness. Do not move confidence thresholds between implementations without validation. [9]

How to evaluate uncertainty in practice

Measure accuracy alongside probability quality. A reliability plot compares predicted probabilities with observed outcomes in bins. Expected calibration error (ECE) averages bin gaps; the result depends on bin definitions and sample size. Brier score and log loss also reflect predictive skill, so they are not pure calibration measures. [10]

Post-hoc temperature scaling is a published calibration technique. It adjusts score concentration; a positive global temperature does not change which score is largest. It cannot repair every wrong decision. [16]

For a real workflow, use held-out examples, inspect high-confidence mistakes, and recheck after the task distribution changes. Choose action thresholds by measured error costs and performance, not by how reassuring “0.95” looks. [15]

All 3,270 labeled development examples were evaluated with the passage as state and a yes/no question. No temperature fitting or other recalibration was applied. ECE used ten equal-width bins; the report includes passage-clustered bootstrap intervals. Models can have different internal prompts despite identical external payloads. [10]

This establishes results on passage-grounded comprehension, not production-domain calibration or unrestricted factual truth. Training overlap with the public benchmark is unknown.

MMLU-Pro protocol, uncertainty, and a second open-model baseline

Jev’s accuracy was 82.9% (95% Wilson interval 80.4–85.1%); updated OpenJev’s was 58.8% (55.7–61.8%). The paired difference was 24.1 points, with a bootstrap interval of 21.0–27.2 points. Both were correct on 554 items, only Jev on 275, only OpenJev on 34, and neither on 137. [11]

The prompt cleanup reused an inspected subset, so this is not an untouched holdout. It is also not the usual full-test, few-shot chain-of-thought evaluation.

A separate hosted Qwen3.8-27B run scored 60.0% on those same 1,000 questions with reasoning disabled and one output token. It used a different prompt wrapper and serving backend; truncated top-20 log probabilities were used for answer selection, not calibration metrics. [12]

Reasoning buys accuracy—but costs time.

A separate OpenJev research experiment allowed Qwen progressively larger reasoning budgets on 128 new questions. The longest budget improved accuracy and substantially increased latency. [13]

Reasoning capAccuracyMedian internal latency
0 tokens53.9%0.11 s
64 tokens51.6%0.61 s
256 tokens53.1%1.89 s
1,024 tokens68.8%7.25 s

Same 128 questions across budgets; different sample and prompt from the 1,000-question comparison. Latency excludes external networking, startup, and client-side queuing. [13]

Why these reasoning results are exploratory

Positive budgets enabled native thinking. The harness stopped at the thinking-end token or cap, closed the reasoning block, and scored one final answer token. Only 14 of 128 traces finished naturally at the 1,024-token cap; none did at the smaller positive caps. Runs used concurrency 16. [13]

One sampled trace per question and budget does not capture repeat-run variability. These results do not imply that more reasoning always helps, or establish Jev’s internal computation. A generated wrong reasoning trace can also distort subsequent confidence.

The repository explored five prompt variants on another 256-question sample. Improvements were modest and exploratory; its research notes also identify an untested KV-cache precision control. The cause of the remaining gap is unresolved. [18]

06 / WHERE IT FITS

Give each part of the system a clear job.

A fast decision model can complement a reasoning agent. It does not need to replace one.

The following is an engineering proposal, not a benchmarked Jev integration. Imagine an analytics assistant classifying requests, detecting missing information, and choosing a route before a generative model writes SQL.

DECISION MODEL

Judge

Classify intent. Flag ambiguity. Score relevance. Select among known routes.

REASONING MODEL

Create

Write SQL. Investigate failures. Explain results. Work through complex dependencies.

DETERMINISTIC CODE

Control

Enforce permissions. Validate schemas. Execute queries. Apply business policy.

EVALUATION

Verify

Measure errors, calibration, latency, and when escalation actually helps.

A concrete agent workflow and its evaluation plan

Supply a user request, relevant schema, and available capabilities as state. Ask independent questions together: “Which capability is required?”, “Is a time range missing?”, and “Does this request ask to modify data?” Combine the results with deterministic checks. Fetch additional evidence before a second decision stage if it is genuinely needed.

For each judgment, build a labeled held-out set. Compare a deterministic baseline, a one-token open-model baseline, Jev, and a reasoning-model fallback. Measure task accuracy, reliability curves, p50/p95 end-to-end latency, cost per successful workflow, and accepted-case error rate at each threshold. Reorder choices to check stability. Keep permissions outside the model.

This is our proposed validation plan. TypeSafe’s documented pattern of focused judgments composed in code motivates the workflow, but does not validate its performance on your data. [2]

07 / WHAT WE CAN CONCLUDE

The useful idea survives the caveats.

Separate the interface, the inference machinery, and the quality of the trained model.

Implemented

Direct decision APIs are practical.

OpenJev provides inspectable code for concurrent questions, shared-prefix reuse, first-position scoring, and typed responses. [6][7][8]

Measured

This replica does not match Jev’s quality.

The published comparisons favor Jev, with a particularly large MMLU-Pro gap. That result does not isolate the contribution of RLCD. [10][11]

Unresolved

The proprietary recipe remains unknown.

Exact architecture, training data, optimization details, and hardware economics cannot be recovered from a compatible API alone. [1][14]

Two claims to read carefully

“Hallucination-free” does not mean error-free. A schema can force the output to be “approve,” “reject,” or “review.” The model can still select the wrong one. TypeSafe’s launch discussion ties its zero-type-error claim to schema guarantees. [19]

A large speedup is workload-dependent. TypeSafe acknowledges that its comparisons depend on prompt shape, reasoning settings, and requiring probability-filled structured responses from baseline models. An apples-to-apples evaluation should match output requirements, quality, hardware, and workload. [19]
