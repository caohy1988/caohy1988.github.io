Durable running agents, explained.

An agent that works for hours will outlive the process running it. What should survive the crash, what runs twice, and who notices?

On 1 October 2026 Earendil released Pi Durable as an experimental package, a library in which “every step of a run is a task that stores a checkpoint before it moves on.”[90][89] The page opens with Pi Durable because it is the recent system that prompted this study. From there it widens to durable running agents in general: how a new process picks up after the old one dies, where that breaks, what it costs, and how 26 systems compare, Pi Durable among them, from durable-execution engines and agent frameworks to vendor agents that run in the background.

The study, in sixteen chapters

Chapter 1

What durability means for an agent.

In short: A durable agent writes its progress to storage as it goes, so that when the process running it dies, a new process can read that record and continue instead of starting over.

An agent works in a loop. The harness, the program wrapped around the model, sends the conversation so far to the model. The model answers or asks for a tool. The harness runs the tool and sends the result back, and the loop repeats. Some agents are meant to live far longer than one request: Cloudflare’s documentation describes agents “that persist for days, weeks, or months”.[62]

Such an agent spends most of its life waiting. The same page lists the waits: user input from seconds to days, human approvals from hours to days, and scheduled wake-ups from minutes to months.[62]

Processes die for ordinary reasons. Earendil’s announcement of its Pi Durable library lists three: “whether the laptop sleeps, the container is redeployed, or the machine runs out of memory”.[89] Whatever the agent held only in memory goes with it: turns not yet saved, an answer the model was halfway through streaming, a tool call in flight, a timer, messages waiting in a queue. Cloudflare puts it in one line: “In-memory variables, timers, open fetches, and local closures do not survive eviction.”[62]

An illustration

An overnight agent is asked to fix a flaky test, open a pull request, and post a note in Slack. Its process dies after GitHub accepted the pull request but before the agent saved that fact. A naive restart opens a second pull request. A durable design has to know the request went out, or at least warn the model that it might have.

An invented scenario used to explain the problem. It is not a reported incident.

Three questions every design answers

  • Where is progress written, and how often? After every step, at chosen points, or only at the end of a run. Chapters 2 and 3.
  • What happens to the step that was running? Run it again, skip it, or ask the model or a person. Chapter 4.
  • What about effects outside the record? A charged card, a half-written file, a browser left on page five. Chapters 4 and 6.

Six terms used throughout

Checkpoint
A saved record of progress that a new process can resume from.
Replay
Running code again after a crash while reusing recorded results for the steps that already finished. Engines that replay, such as Temporal, require the replayed code to be deterministic, so that it “makes the same Workflow API calls in the same sequence, given the same input.”[1]
Stored step result
A saved result for a finished step, so the step is not run again when the program resumes. DBOS, for example, “automatically recovers its execution from the last completed step”.[19]
At-least-once
A step that may run more than once, because a crash can land after the step acted but before its result was saved. DBOS documents the window: after a database write, “but before the checkpoint is saved, the step runs again on recovery”.[20]
Idempotency key
A unique value sent with a request so the receiving service can recognize a retry and return the first result instead of acting twice. Stripe stores the first result for a key “regardless of whether it succeeds or fails.”[138]
Exactly-once
The effect happens once, crashes included. A widely cited essay puts the limit bluntly: “Within the context of a distributed system, you cannot have exactly-once message delivery.” The same essay says the way systems achieve it in practice is “by faking it”, with idempotent messages or deduplication.[139]

Three families of systems

The 26 systems in this study fall into three families. Durable-execution engines such as Temporal, Restate, DBOS, Inngest, Cloudflare Workflows, Vercel Workflow, AWS Lambda durable functions, Azure Durable Functions, and Trigger.dev make long programs survive crashes, and each documents running agents on it.[5][12][22][29][33][41][50][54][61] Agent frameworks and libraries such as LangGraph, the OpenAI and Claude agent SDKs, Google ADK, Mastra, Pydantic AI, Cloudflare’s Agents SDK, and Pi Durable build the agent loop and save it in different ways. Vendor agents such as Claude Managed Agents, the OpenAI Agents API, Codex cloud, Claude Code, GitHub Copilot’s cloud agent, Cursor’s cloud agents, and Devin run the agent for you and keep its state. Chapter 8 places every system on one map and compares them on ten questions, and chapter 9 sets Pi Durable against all the others.

Chapter 2

Checkpoint and resume.

In short: Every durable design saves progress at chosen points and resumes from the last one, and where it saves decides what a crash can lose or repeat.

A checkpoint is only as useful as its timing. Save after every step and a crash loses at most the steps in flight. Save only at the end of a run and a crash loses the run. The systems we read save at different points:

  • Pi Durable saves before every move: “every step of a run is a task that stores a checkpoint before it moves on. If the process dies, a new process opens the same storage, finds the unfinished tasks, and continues each one from its last checkpoint.”[89]
  • LangGraph’s checkpointer saves a snapshot of the graph state at every super-step.[64] A node that was cut off “runs again from the start of its function.”[65]
  • The OpenAI Agents SDK saves a paused run as a RunState that the application stores “in a database or queue” and restores later.[69]
  • Google ADK keeps a conversation’s events in a session service. With the in-memory one, “All conversation data is lost if the application restarts.”[80]
  • The Claude Agent SDK writes the conversation to disk, and “Sessions persist the conversation, not the filesystem.”[75]

Resuming is not the same as recovering on its own. Mastra’s durable agents checkpoint each run’s state to storage, but a crashed run stays “running” with no automatic retry, and the opt-in recovery “can reissue LLM calls (with real cost) and re-execute tool calls.”[84]

Chapter 3

Replay a history, or reuse stored results.

In short: Engines either re-run your code against a recorded history, which requires deterministic code, or keep each finished step’s result and skip that step next time; in both, the step that was running runs again.

Replay a deterministic program against its history

The engine records every step’s result, then on recovery runs the program again from the top, feeding it the recorded results. Temporal, Azure Durable Functions, Vercel Workflow, AWS Lambda durable functions, and Restate work this way.[1][51][37][45][11] The price is determinism. If replayed code takes a different path, Temporal’s runbook says affected executions stop making progress, and “This will not clear up on its own.”[4] Model calls therefore go into Activities, “so they retry durably and are not repeated during Workflow replay.”[5]

Store each step’s result and skip finished steps

The program re-runs too, but the engine only promises that finished steps return their saved results. DBOS “automatically recovers its execution from the last completed step”,[19] and Inngest reuses “results from completed steps whose IDs still match.”[28] The step that was running is retried, so it runs at least once.[20][31]

Snapshot the process or the machine

Trigger.dev freezes a waiting task’s whole process with CRIU, “including memory, CPU registers, and open file descriptors.”[55] On macOS, Devin snapshots a sleeping session’s disk, but “Running processes do not” survive.[134] Claude Managed Agents checkpoints an idle session’s sandbox, “including the filesystem, installed packages, and any files the agent created.”[109] Chapter 6 returns to snapshots.

Changing the code under a running agent

A run that lasts days will meet a deploy. Every durable system has to decide which version of the code a resumed run uses.

  • Pin the run to its version. Temporal can run a pinned workflow “entirely on the Worker Deployment Version where it started.”[6] Restate keeps in-flight invocations on their original deployment, and Vercel pins each run to “the deployment that starts them.”[14][38] The trade-off, in Restate’s words: “When a bug affects in-flight invocations, they remain pinned to the original deployment.”[14]
  • Recover only matching versions. DBOS recovers only “workflows whose version matches the current application version.”[21]
  • Use the new code and match steps by name. Inngest resumes runs on current code; a changed step “can repeat a payment, email, or resource creation.”[28]
  • Store names, not code. Pi Durable resumes conversations with whatever tools the new process installs.[89] Our reading of its scheduler: a stored task version equal to the installed one runs the new code against the old checkpoint without further checks; an older installed version blocks the task, and a newer one needs a migration function.[98]

Chapter 4

Side effects, exactly-once, and idempotency keys.

In short: The step that was running may already have acted, so a design either runs it again, tells the model, or relies on an idempotency key that the receiving service honors; when a request may still be in flight and nothing bounds for how long, checking first cannot rule out a second charge, and the key can.

Most engines run the interrupted step again

Any design that retries an interrupted step runs it at least once and sometimes twice, and the documentation says so plainly:

  • Temporal: an Activity “may be executed multiple times and may even partially complete more than once”.[2]
  • Cloudflare Workflows: “Because a step might be retried multiple times, your steps should (ideally) be idempotent.”[31]
  • AWS Lambda durable functions: “your business logic must be idempotent to handle potential retries”.[46]
  • Inngest: “A step does not make an external action exactly once.”[26]
  • Vercel Workflow warns that a retry can charge a user twice and offers a stable stepId to use as an idempotency key.[39]

Agent frameworks decide per tool

Agent-specific designs differ on the tool call that was cut off:

  • Pi Durable stores a tool call’s intent before running it. On recovery the call runs again only when both the stored and the current declaration say safe, and the default is unsafe; otherwise the model is told the tool “was interrupted and may have partially run”.[92][94]
  • Claude Code takes the conservative path on resume: a cut-off tool “doesn't finish or run again when you resume”, and Claude is told to check whether it took effect.[122]
  • Google ADK’s resume goes the other way and runs tools “at least once”.[79]
  • The OpenAI Agents SDK warns that a resumed snapshot “does not guarantee exactly-once tool side effects.”[70]
  • Pydantic AI says a durable unit “can run more than once” when a worker fails after its side effect.[86]

Model requests get a different rule. Pi Durable sends a cut-off model request again, with no declaration needed, and keeps the partial answer in the transcript, marked as aborted.[89][99] Temporal’s agent integration runs model calls as Activities, which retry.[5]

Evidence: the code behind Pi Durable’s tool rule

In Pi Durable v1.0.0, the tool task records its replay policy with its intent, defaulting to unsafe: replay: tool.replay ?? "unsafe". The recovery path carries the comment “Recovery after intent: rerun only when the stored and the current policy both say safe.” and, when it does not rerun, settles the call with the message Tool ${call.name} was interrupted and may have partially run.[92] The four built-in coding tools, read, write, edit, and bash, declare no replay setting, so after a crash even a read is reported as interrupted instead of being run again.[97]

Keys that the receiving service honors

An idempotency key turns a retry into a no-op only if the service that acts checks it. Stripe stores the first result for a key “regardless of whether it succeeds or fails.”[138] Keys inside the harness are narrower: Pi Durable’s requestId is a “Host-provided deduplication key, scoped to the conversation.”[95] Our reading of the code: it stops a client from submitting the same request twice, and it does not stop a tool from repeating an effect further down.[96]

The research measures the difference. In a simulated benchmark, frontier models instructed to act exactly once duplicated a write in 56% of episodes when the request was still in flight and committed late, and in 74% when the transport delivered it twice. A separate experiment in the same paper, with four models and a tool contract in which every write accepts an idempotency key, cut the late-commit duplicate rate of agents without a guard from 61% to 9%. The same paper proves that “no verification-only policy is exactly-once under late commits without a bound on in-flight time”, and adds that “Waiting works when such a bound is short and known”.[156] A study of five workflow frameworks found LangGraph 1.2.9 “exactly-once across interrupts, at-least-once across crashes”, and when k processes resumed one parked interrupt, the gated effect fired k times.[155]

An outcome nobody knows

The cautious alternative leaves the question open. Pi Durable tells the model a tool “was interrupted and may have partially run”;[92] Claude Code tells Claude to check whether a cut-off call took effect.[122] The model then has to investigate. The Limbo study found that agents reported success in 90% of the episodes in which they had duplicated an effect.[156]

Chapter 5

One owner per run.

In short: Durable designs assume one process advances a run at a time, and when two machines can open the same record, a lease is not enough; the storage has to reject a stale writer.

A single-owner design is only as safe as the lock that enforces it. Pi Durable’s README is direct: “One process owns a storage at a time; there is no cross-process locking.”[91] Keeping a second process out is the host’s job; Earendil’s own demo app takes a file lock and notes that “A lock left by a crashed process goes stale after 10 s”.[103] Mastra says it “doesn't provide a distributed lease or lock yet.”[84] SQLite’s write-ahead log needs every process on one machine: “WAL does not work over a network filesystem.”[141]

A lease alone is not enough when an old owner can wake up late. Fencing tokens fix that, but as Martin Kleppmann wrote, “this requires the storage server to take an active role in checking tokens”.[140] The research shows what happens without it: when k processes resumed one parked LangGraph interrupt, the gated effect fired k times.[155]

The newest commit is the fragile one. For Pi Durable’s SQLite store the README says that “commits survive process crashes; the newest may be lost on power or host failure.”[91] Its JSONL backend’s fsync option “Defaults to false.”[101] Our reading: a recovery rule that relies on a stored intent record assumes that record survived. If a power cut loses it, a tool can run again even though it was never declared safe. We did not test this.

Engines and hosted runtimes enforce one owner in different ways. Temporal assigns each execution to a history shard, and “A History Shard assumes that only one concurrent operation can be within a partition at a time.”[10] Restate offers Virtual Objects and Workflows a “Single-writer guarantee”.[11] Cloudflare’s agents are Durable Objects, “single-threaded compute instances with long-term storage”.[36] LangSmith’s Agent Server queue “enforces that at most 1 run can be executed for a given thread at one time”,[136] and Cursor allows one active run per agent.[131] DBOS tags each workflow with the executor that started it and asks operators to “recover each workflow only once.”[24] The comparison in chapter 8 lists what each system’s documentation says about who may advance a run.

Chapter 6

State outside the transcript.

In short: Saving the conversation does not save the world the agent changed, so files, processes, browsers, and sandboxes need snapshots of their own, or a check before the agent trusts its memory.

The transcript survives; the world it describes may not. “Sessions persist the conversation, not the filesystem”, say Anthropic’s SDK docs.[75] A reclaimed Claude Code cloud VM comes back with the conversation, but “Background work that was still running when the VM was reclaimed, such as subagents and shell commands, isn't restored.”[123] OpenAI’s Agents API: “Reusing the environment ID does not restore files in replacement compute.”[114]

The Crab paper measured the gap: restoring chat history alone recovered 8 to 13% of tasks correctly, against 100% when sandbox state was checkpointed too. By workload, chat-only recovery succeeded on 13% and 8% of shell-intensive Terminal-Bench tasks with the Claude Code and iFlow-cli agents, and on 9% of code-repair SWE-bench tasks.[154]

Some products snapshot the environment. Claude Managed Agents checkpoints an idle session’s sandbox and keeps that state for 30 days from creation.[109] Cursor deletes environment snapshots after 90 days unused.[130] On macOS, Devin keeps a sleeping session’s disk but not its running processes.[134] Libraries usually leave the environment to you: Pi Durable’s execution environment interface covers files and shell commands and has no snapshot or restore operation.[102]

Rewinding has the same boundary. AgentRewind restores an agent’s context and workspace together, and its authors state the limit: “Effects outside the workspace filesystem, such as network requests, external-service calls, and external runtime state, cannot be undone.”[159]

Chapter 7

Compaction and handoff.

In short: Long runs outgrow the model’s context window, so compaction summarizes older turns at the cost of a model call and some detail, and a handoff starts a fresh context from a note.

Compaction is a model call, and it discards. Anthropic’s documentation says compaction “requires an additional sampling step, which contributes to rate limits and billing”, and warns that images, documents, uploads, and fetched URLs in a summarized range “are gone once the block replaces them.”[149][148] OpenAI’s Agents API takes the job on: “OpenAI manages sessions, orchestration, context compaction, and recovery”.[113]

Pi Durable compacts in the background while the conversation keeps going. With its built-in defaults the next request waits for a summary once the context passes the model’s window minus 16,384 tokens, and a background summary starts 32,768 tokens before that.[89][100] When a provider still rejects a request as too long, the code compacts once and tries again.[99] The post adds that “The older messages always stay in storage.”[89]

A handoff is the blunt version: start a new context from a note. In Pi Durable, “reset() goes further: it starts a new context, optionally from a handoff note”, and “Because nothing is deleted, a second tool can still search everything before the handoff.”[89]

Summaries can lose what mattered. Once a compaction block is in place, the summarized messages are removed, and “Claude sees the summary where those messages were.”[148] Anything the summary leaves out, an early instruction included, is no longer in what the model reads. An application can replace the default summarization prompt with its own; Anthropic’s example asks the summarizer to “Preserve every entity and field name agreed so far, and the user's latest open request.”[148] Research is trying to make compaction learned rather than fixed; chapter 13 lists three such papers.[161][162][163]

Event History is capped at 51,200 Events or 50 MB; no time limit is imposed on an execution; closed executions are kept for a Retention Period of at least 1 day.[3][9][10] A warning comes at 10,240 Events or 10 MB; the Retention Period defaults to 3 days when a Namespace is created with the temporal CLI without setting it.
Human waits and timers
Timers are persisted, so a Workflow waiting on one resumes once its Worker and the Temporal Service are back; Workflows can also wait on a Signal or Update for a person's approval.[8][5] A Timer may be as short as one second or as long as several years, and Workers use no extra resources while waiting.
Caveats
  • A non-determinism error after a code change stops affected Executions from making progress, and it does not clear up on its own.[4]
  • Local Activities are not recorded in Event History between Workflow Task heartbeats, so a rescheduled Workflow Task runs them again from the beginning.[4]
  • A long chat-style agent can reach the per-Workflow Event History limit, so the integration uses Continue-As-New to start a fresh Execution that carries the history forward.[5]

Restate

Restate is a durable execution engine: the Restate Server sits in front of your services, journals each step of a handler, and replays the journal after a failure.[11]

Where state is stored
The Restate Server records each step of a handler and its result in a journal, and stores all state and execution history, so the services themselves stay stateless.[11] A single-node server recovers from persistent disk; in a high-availability cluster, other nodes take over without losing execution state.
How a run is recovered
Restate restarts the failed handler and replays its journal: completed steps are replayed without re-execution, and execution resumes from the first incomplete step.[12][11][14] Replayed code must produce the same journal; otherwise the invocation fails with a journal mismatch error.
Exactly-once or idempotency keys
Restate's docs say invocations run exactly once and ctx.run side effects execute exactly once; the SDK's doc comment says an action may re-run if a failure hits between success and persisting its result.[11][12][13] Duplicate incoming requests are deduplicated only when the caller adds an idempotency key to the request headers.
Who may advance a run
Virtual Objects and Workflows have a single-writer guarantee, so only one handler modifies state at a time; a service that cannot send journal entries stops, and the Server retries it on another instance.[11][16] If an exclusive Virtual Object handler sleeps, all other calls to that object are queued; concurrency limits for other invocations are an opt-in flow-control feature.
A tool call cut off by a crash
Tool steps in ctx.run persist their result; an unfinished or failed one is retried with exponential backoff, by default up to 70 attempts before the invocation pauses.[12][11][17] Applies to tool code wrapped in ctx.run; the LangChain middleware does not journal tool calls automatically.
A model request cut off by a crash
Restate's agent docs wrap every LLM call in ctx.run or a durable middleware; each response is persisted and replayed on recovery, and execution resumes at the first incomplete step.[12] Applies when LLM calls are wrapped as the durable agents page shows, with ctx.run or an integration such as durableCalls, DurableRunner, or RestateAgent.
Files, processes, and sandboxes
Services stay stateless: the Restate Server stores all state and execution history and sends it with each request, and if a service crashes or restarts, ongoing executions are retried on new instances.[11] The pages we read do not mention files on a service's disk or a sandbox.
Hosting model
Your services embed the Restate SDK and run on your infrastructure, such as containers, serverless functions, VMs, or Kubernetes; the Restate Server runs as a single node, a cluster, or Restate Cloud.[11]
Run length or retention
Journals of completed invocations and idempotency keys are kept 24 hours by default; the timers page says there is no hard limit on how long a handler can sleep.[17][16][14] Retention is tunable; long sleeps keep an invocation on its original deployment, so the docs advise avoiding handlers that run for days or months.
Human waits and timers
Durable timers survive failures and restarts, and an agent can wait on a durable promise (an awakeable) for human approval, then resume where it left off even if the process restarted.[16][15][11] On FaaS platforms such as AWS Lambda, Restate suspends the handler while it sleeps or waits for external events.
Caveats
  • The TypeScript SDK's doc comment says an action in ctx.run may run again if a failure occurs after it succeeds but before its result is persisted.[13]
  • In-flight invocations stay on the deployment where they started, so long-running handlers require keeping old deployments until they finish.[14]
  • When retry attempts run out, the default is to pause the invocation for a manual resume; configuring it to be killed instead skips compensation logic.[17]

DBOS

DBOS is an open-source library you install into your application; it checkpoints workflows and steps to a database and uses those checkpoints to recover workflows after failures.[18]

Where state is stored
The DBOS library checkpoints workflow inputs and step outputs to a system database: Postgres is recommended for production, and the Python SDK defaults to SQLite.[18][22] In TypeScript, DBOS uses Postgres by default; Conductor does not have access to this database.
How a run is recovered
DBOS calls each interrupted workflow again with its checkpointed inputs; steps with a checkpoint return the saved output instead of running, and execution continues normally from the first step without one.[18][21] Workflow functions must be deterministic, and with versioning DBOS only recovers workflows whose version matches the running application.
Exactly-once or idempotency keys
Steps are tried at least once but never re-executed after completing, so DBOS asks for idempotent steps; an assigned workflow ID acts as an idempotency key, so that workflow executes only once.[19][18][20] Transactions commit exactly once, and Java transactional step factories make database-write steps exactly once by committing output and write together.
Who may advance a run
Each workflow carries the ID of the executor that started it; a restarted executor recovers only its own pending workflows, and Conductor signals another executor to recover an unhealthy executor's workflows.[24][18] Without Conductor in a distributed setup, you assign executor IDs and must recover each workflow only once; enqueued workflows are picked up by processes polling the queue.
A tool call cut off by a crash
A step cut off by a crash has no checkpoint, so it is retried during recovery and may repeat its effect; a step that completed and was checkpointed is never re-executed.[18][20][22] Applies when each tool call is a step, as DBOS's AI quickstart instructs.
A model request cut off by a crash
DBOS's AI quickstart says to make each LLM call a step; a step interrupted by a crash is retried during recovery, and a completed one returns its checkpointed output.[22][18] Applies when LLM calls are annotated as steps, or wrapped by an integration such as Pydantic AI's DBOSAgent.
Files, processes, and sandboxes
Not stated in the sources we read. Looked for in [18][19][20][21][22][23][24][25].
Hosting model
DBOS is an open-source library inside your application with no separate orchestration server; your processes can run on Kubernetes, EC2, or serverless platforms, and Conductor is a recommended control plane off the execution path.[18]
Run length or retention
Conductor can delete completed workflows' history after a time or row threshold and cancel workflows after a global timeout; all three are off by default, and running workflows are never deleted.[25][19] These policies require Conductor; the docs describe durable sleeps lasting days, weeks, or months and very long workflow timeouts.
Human waits and timers
DBOS.sleep stores its wakeup time in the database and still wakes on schedule after restarts; DBOS.recv durably waits for a message, such as a human approval, across server restarts.[19][23] Messages sent with DBOS.send are persisted, so a send that completes is guaranteed to reach the destination workflow.
Caveats
  • A step that writes to a database and crashes before its checkpoint is saved runs again on recovery and can write twice; Java transactional step factories commit the output and the write in one transaction.[20]
  • An uncaught exception ends a workflow with status ERROR, and DBOS does not recover it.[19]
  • With versioning, a workflow only recovers on processes running the application version it started on.[21]
  • On files, the architecture page only advises keeping large ones in blob storage such as S3 and having steps return pointers to them, because the size of each checkpoint write follows the size of a step's output.[18]

Inngest

Inngest runs durable functions: an Inngest server, in Inngest Cloud or self-hosted, schedules runs and records each step's result, while your app serves the function code.[30][27]

Where state is stored
Inngest saves each completed step's result in the run's state, held by the Inngest server's queue and run-state store, whether in Inngest Cloud or on a self-hosted server.[26][29][30] A self-hosted server without external services keeps queue and run state in an embedded Redis-compatible store and persists to SQLite.
How a run is recovered
When a run resumes, Inngest re-enters the function and the SDK returns each completed step's saved result instead of running it again; code outside steps can run again.[29][28][26] Saved results are found by step ID, so step IDs must stay stable across deployments.
Exactly-once or idempotency keys
A step does not make an external action exactly once: if a provider's response is lost, the step can retry the action, so Inngest asks for idempotency keys on writes, payments, and messages.[26]
Who may advance a run
The Inngest server's runner schedules functions and resumes waits, and its executor runs steps, calling the function code your app serves over HTTP or Connect; flow-control rules such as concurrency limit active work.[30][27] On Inngest Cloud, plans include 5 (Free), 100 (Pro), or 500 (Business) concurrent steps, and a custom number on Enterprise.
A tool call cut off by a crash
Each tool call runs in its own step.run, and Inngest retries only the failed step; a tool that changed an external system before its result was saved can repeat that change.[29] Applies when the tool call is wrapped in step.run, as the durable agents page shows.
A model request cut off by a crash
Inngest's durable agents page runs each model call in step.run; Inngest saves completed steps, retries only the step that failed, and resumes after a crash without repeating earlier model calls.[29] Applies when model calls are wrapped in step.run, as the durable agents page shows.
Files, processes, and sandboxes
Inngest Sandboxes, in beta, run model-written code in an isolated Linux VM; each Sandbox call is a durable step, so a retry reuses the same Sandbox, and files and processes persist between tool calls.[29] In beta; the docs say to pause the Sandbox during approval waits, and you destroy it yourself on success and in a failure handler.
Hosting model
Inngest Cloud or a self-hosted Inngest server runs the engine, and your app hosts the function code separately, on your own servers or a serverless host, serving it through HTTP serve() or Connect; self-hosted single-node mode is labeled beta.[27][30][29] The self-hosting guide does not guarantee direct support for self-hosted instances.
Run length or retention
Runs, including sleeps and waits, last at most 30 days on Free, 90 on Pro, 366 on Business, and a custom length on Enterprise; on every plan, run state is capped at 32 MiB and a function at 1,000 steps.[27] These are Inngest Cloud limits; trace and log history is kept 24 hours on Free, 7 days on Pro, 14 days on Business, and up to 365 days on Enterprise.
Human waits and timers
step.sleep, step.sleepUntil, and step.waitForEvent suspend the run without holding a process, worker, or connection, so an agent can wait days for a person's approval event, with a timeout.[26][29][28] A single sleep can last up to 1 year, within the plan's maximum run length.
Caveats
  • Changing a step's ID makes an in-progress run execute it as new work, which can repeat a payment, email, or resource creation.[28]
  • A step can run for at most 2 hours, or less if the function host has a shorter timeout.[26]
  • On a self-hosted server, PostgreSQL rows for events, runs, and traces are not removed automatically.[30]

Cloudflare Workflows

Cloudflare Workflows runs multi-step programs on Cloudflare Workers: a Workflow is a Worker script whose work is split into individually retryable steps that can persist state.[31][32]

Where state is stored
The Workflows engine persists the state each step returns, so an instance can continue from its last finished step after a network or infrastructure failure.[31][62] Only state returned from steps persists; a Workflow may hibernate and lose all in-memory state.
How a run is recovered
After an engine restart, completed steps are not rerun: their saved results are reused, keyed by step name. Logic outside steps may run again, and an interrupted step starts over.[31][33] Steps should be named deterministically so their state is cached.
Exactly-once or idempotency keys
A step might be retried multiple times, so the docs ask that steps be idempotent, for example by checking whether a customer was already charged before charging.[31] The docs call idempotency optional for some uses but recommend always trying to guarantee it.
Who may advance a run
The platform schedules instances: only running instances count toward the account's concurrency limit, beyond which instances queue; when a running instance starts waiting, a queued one is scheduled.[32]
A tool call cut off by a crash
A step cut off by an engine restart starts over from the beginning of that step; the docs' agent guide wraps each tool call in its own retryable step.[31][33] Side effects inside a retried step can repeat, so the docs ask for idempotent steps.
A model request cut off by a crash
Cloudflare's durable agent guide makes each LLM call a step: a failed call is retried automatically, and a finished call's response is persisted, so on resume it is skipped.[33] Stated in the Build a Durable AI Agent guide, which says the same patterns apply to any LLM SDK.
Files, processes, and sandboxes
A Workflow may hibernate and lose all in-memory state, so state must not be kept outside steps; only what steps return carries over.[31]
Hosting model
Cloudflare runs Workflows on its Workers platform: each Workflow is a Worker script and inherits Workers limits, such as per-invocation CPU time.[32] Workflows cannot be deployed to Workers for Platforms namespaces.
Run length or retention
An instance can run forever while each step stays within its CPU limit and the instance stays under the step cap: 1,024 steps on Workers Free; on Workers Paid, 10,000 by default and configurable up to 25,000. step.sleep lasts up to 365 days on both plans.[32] Per-step CPU time is 10 ms on Workers Free, and 30 seconds by default, configurable to 5 minutes, on Workers Paid. Completed instance state and logs are kept 3 days on Workers Free and 30 days on Workers Paid.
Human waits and timers
step.sleep and step.waitForEvent put an instance in a waiting state; the engine can hibernate it and wakes it for the sleep or event. The agent guide uses waitForEvent() for human approval lasting hours or days.[32][31][33]
Caveats
  • Code outside steps may run more than once, so side effects and non-deterministic values belong inside steps.[31]
  • A non-stream step result can persist at most 1 MiB, and a step that returns more fails.[31]

Vercel Workflow

Vercel Workflow (the Workflow SDK) is a programming model for durable functions: every state change is recorded in an event log, and workflow code is replayed against it after suspensions and failures.[42][37]

Where state is stored
An event log: every state change in a run is persisted as an event, and state is derived by replaying it. On Vercel, the Vercel World keeps it in managed persistence.[37][40][44] Other Worlds store it elsewhere: the Local World keeps workflow data in a local directory for development and testing, and community Worlds serve self-hosting.
How a run is recovered
Replay: workflow code re-runs against the event log, which holds each step's result, so the run resumes where it left off instead of starting over.[42][37]
Exactly-once or idempotency keys
Steps retry, and a retried step can repeat a side effect such as a charge; each step has a stable stepId to use as an idempotency key with third-party APIs.[39] Hook tokens can also deduplicate whole runs while a run is active.
Who may advance a run
Concurrent invocations can replay the same run and write to one shared event log; a per-run sequencer gives each write a distinct position, and the first recorded outcome counts.[37] Sealed logs apply to runs at specVersion 7 and above, the default for new runs.
A tool call cut off by a crash
If the function running a step crashes before reporting a result, the step is re-tried under its retry policy, by default up to 3 retry attempts, so side effects can repeat.[43][42] The docs name function timeouts, out-of-memory errors, and network issues as causes.
A model request cut off by a crash
The AI agents guide says Workflow SDK turns LLM calls, tool executions, and other async operations into retryable steps, whose results are persisted for replay.[41][42] Stated for agents built with WorkflowAgent, which runs the agent loop inside a workflow.
Files, processes, and sandboxes
Workflow code runs in a sandboxed environment without full Node.js access and is re-run from the event log each time the run resumes, using no compute while suspended. If the function invocation running a step crashes, the step is retried under your retry policy.[42][43] The pages we read do not mention files kept between invocations.
Hosting model
On Vercel, the Vercel World supplies durable storage and managed queuing, and Workflows invoke Vercel Functions billed at compute rates; through Worlds the same code also runs locally or self-hosted.[44][40] Self-hosting relies on community-maintained Worlds or one you build.
Run length or retention
No limit on run or sleep duration; every run allows 25,000 events, 10,000 steps, and 2 GB of entity storage, and replay is capped at 240 s. Stream storage size is unlimited. Data in Vercel's managed persistence is kept after a run completes for 1 day on Hobby, 7 days on Pro, and 30 days on Enterprise.[40] These are Vercel's limits; runs past 2,000 events or 1 GB of entity storage replay more slowly.
Human waits and timers
sleep() suspends a run, and hooks or webhooks pause it until external data, a user action, or an HTTP request arrives; both are stored as entities, and a waiting run resumes even after a deploy.[42][37][38] A waiting run resumes on the deployment that started it, not on newer code.
Caveats
  • A run's event log is capped and replay reads the whole log, so the docs advise splitting into child workflows past a few thousand events.[37]
  • Runs are pinned to the deployment that starts them, so a fix applies to old runs only if you cancel and rerun them.[38]

Sources for this system: [37][38][39][40][41][42][43][44].

AWS Lambda durable functions

AWS Lambda durable functions are regular Lambda functions that use a durable execution SDK to checkpoint steps and waits and recover by replay, for executions of up to one year.[45]

Where state is stored
Lambda keeps a checkpoint log of every durable operation, including step results and execution state, and saves it when the function pauses or is interrupted.[48]
How a run is recovered
Lambda invokes the function again from the beginning and replays the checkpoint log, using stored results for completed operations instead of re-executing them.[48][45] Code must be deterministic during replay.
Exactly-once or idempotency keys
Steps run at least once by default, so step logic must be idempotent; execution names act as idempotency keys for starting executions, and an at-most-once-per-retry option exists for side effects.[46][49] Neither step semantic guarantees exactly once across the whole workflow.
Who may advance a run
Lambda drives each execution, invoking the function again whenever it resumes; execution names are unique per account and Region, and a duplicate start with the same payload returns the existing execution.[48][46] A duplicate name with a different payload returns DurableExecutionAlreadyStartedException.
A tool call cut off by a crash
By default a step interrupted before it completes runs again on replay; with at-most-once per retry, the SDK instead marks it interrupted and raises a StepInterrupted error.[46][49] To run a step at most once end to end, combine at-most-once with a no-retry strategy.
A model request cut off by a crash
AWS's Pydantic AI integration checkpoints each model request and tool call as a durable step, so an interrupted or retried run resumes from the last completed step.[50] Stated for the pydantic-ai-harness integration; a run started outside the durable agent handler checkpoints nothing.
Files, processes, and sandboxes
Lambda is designed for compute that does not retain state between invocations, and one durable execution can span many invocations; progress carries over through checkpointed results.[47][48]
Hosting model
Durable functions are regular Lambda functions on Lambda's serverless model, with automatic scaling including scale-to-zero and no infrastructure to manage; SDKs cover JavaScript, TypeScript, Python, and Java.[45][48] Each invocation is still limited by the Lambda function timeout of at most 15 minutes.
Run length or retention
The execution timeout defaults to 24 hours, maximum 1 year; an execution allows 3,000 durable operations and 100 MB of written storage; history is kept 1 to 90 days, default 14.[48][47] Retention starts when the execution ends; then Lambda deletes its history and checkpoint data.
Human waits and timers
Waits pause for a time period, an external callback, or a polled condition without compute charges, which AWS suggests for human-in-the-loop workflows; Lambda then re-invokes the function and replays it.[48][45][46] Waits count against the execution timeout but not the Lambda function timeout.
Caveats
  • Event source mappings don't support idempotency at launch, so each invocation, including retries, starts a new durable execution.[46]
  • Code outside steps re-runs on every replay, so random numbers or the current time outside steps can change between replays.[48]

Sources for this system: [45][46][47][48][49][50].

Azure Durable Functions

Azure Durable Functions is an extension of Azure Functions for stateful orchestrations; the same Durable Task model is also offered as portable SDKs backed by the Durable Task Scheduler.[53][52]

Where state is stored
An append-only execution history of each orchestration, saved at every checkpoint to the storage provider you configure, such as Azure Storage, MSSQL, or the Azure-managed Durable Task Scheduler.[52] The Azure Storage provider gives no transactional guarantee between tables and queues and relies on eventual consistency patterns.
How a run is recovered
When an orchestration gets new work, the orchestrator re-executes from the start; activities already in the history replay their recorded results instead of running again, rebuilding local state.[52][51] Orchestrator code must be deterministic for replay to work.
Exactly-once or idempotency keys
Activities run at least once: if a failure occurs after an activity completes but before its result is recorded, it might run again, so the docs ask for idempotent activity logic, such as upserts.[53]
Who may advance a run
Each orchestration instance is single-threaded and identified by an instance ID unique within its task hub; durable-entity locks let orchestrations guard critical sections against each other.[52] Critical sections are available for .NET and JavaScript orchestrations in Durable Functions 2.x.
A tool call cut off by a crash
Tool calls go in activities, which run at least once: an interrupted activity can run again, even one that finished before its result was recorded. Retry policies can also retry failed activities.[54][53][52]
A model request cut off by a crash
Microsoft's agentic patterns put LLM calls in activities, which are checkpointed, so after a crash execution resumes from the last completed step without re-consuming LLM tokens for finished calls.[54] Stated in Microsoft's Agentic application patterns guide for Durable Functions and the Durable Task SDKs.
Files, processes, and sandboxes
Orchestrator local state survives process recycles and VM reboots through checkpoints and replay; static variables in Azure Functions are not guaranteed to persist between executions.[52][51]
Hosting model
Durable Functions runs on Azure Functions with serverless hosting; the portable Durable Task SDKs run on any compute, including Azure Container Apps, Kubernetes, virtual machines, or locally, backed by the Durable Task Scheduler.[54][52] Support for the in-process model ends on November 10, 2026.
Run length or retention
An orchestration's lifespan can be seconds, days, months, or years, or it can be configured never to end, as an eternal orchestration.[52][51]
Human waits and timers
Durable timers and external events pause orchestrations; at a wait the orchestrator is unloaded from memory, and a timer firing or an event arriving wakes and replays it. External events suit human interactions.[52][51] Durable timers do not count toward orchestrator execution time.
Caveats
  • Orchestrators replay many times, so they must not do I/O directly; I/O belongs in activities.[51]
  • An unhandled exception leaves an orchestration Failed, and a failed instance cannot be retried.[52]

Trigger.dev

Trigger.dev runs long-running background tasks for your application on Trigger.dev Cloud or a self-hosted instance, pausing waiting tasks with process checkpoints.[55]

Where state is stored
Trigger.dev keeps a record of each run and its attempts; when a task waits, a CRIU checkpoint of its entire state is compressed and stored on disk, and subtask outputs are cached by idempotency key.[58][55] Checkpoints are taken at waits; a wait.for() or wait.until() shorter than 60 seconds doesn't checkpoint.
How a run is recovered
A run whose worker process crashes is marked Crashed and isn't retried. A task that throws is retried per its retry settings from the beginning, reusing cached subtask results; waits resume from checkpoints.[58][55][60] An out-of-memory failure is retried on a larger machine only if the task sets a retry for out-of-memory errors.
Exactly-once or idempotency keys
An idempotency key makes repeated triggers of a task start only one run, and subtask outputs are cached by key; a retried task still re-runs its own code from the beginning.[58][55]
Who may advance a run
Runs wait in queues and are dequeued to workers that execute them, within concurrency limits allocated per environment.[58][57][55]
A tool call cut off by a crash
A worker-process crash marks the run Crashed with no retry; a thrown error retries the task from the beginning under its retry settings, rerunning the call unless a cached subtask made it.[58][55][60] Out-of-memory failures are retried on a larger machine only when the task opts in.
A model request cut off by a crash
Not stated in the sources we read. Looked for in [55][56][57][58][59][60][61].
Files, processes, and sandboxes
When a task waits, CRIU checkpoints its entire state, including memory, CPU registers, and open file descriptors, then restores it into a new execution environment when the wait ends.[55] Waits shorter than 60 seconds don't checkpoint.
Hosting model
Trigger.dev builds your task code into a Docker image and runs it on Trigger.dev Cloud or your self-hosted instance, in a serverless architecture without timeouts; dev mode runs tasks on your machine.[55]
Run length or retention
maxDuration caps CPU time per attempt (minimum 5 seconds), excludes waits, and can be turned off. On Trigger.dev Cloud, a 14-day maximum TTL limits time spent queued, not running time. Logs are kept 1 day on Free, 7 days on Hobby and 30 days on Pro.[56][57] There is no maximum on delay.
Human waits and timers
wait.for, wait.until, and triggerAndWait pause a task and checkpoint it, releasing its resources, though time waits under 60 seconds don't checkpoint; wait.forToken pauses a run until a token is completed, as for human approvals.[55][59]
Caveats
  • Only subtasks are skipped on retry, so the docs' durable pattern breaks work into subtasks triggered with idempotency keys.[55]
  • A run can also end in System failure, described as an unrecoverable system error.[58]

LangGraph

A low-level orchestration framework and runtime for long-running, stateful agents built as graphs, with durable execution, streaming, and human-in-the-loop support.[68]

Where state is stored
A checkpointer you choose saves a snapshot of graph state at each super-step, keyed by thread ID: in memory, SQLite, Postgres, MongoDB, or Azure Cosmos DB.[64][66] InMemorySaver keeps checkpoints in RAM, and they are lost when the process restarts.
How a run is recovered
After a failure you resume the thread from its last checkpoint; nodes that finished in the failed super-step are not rerun, because their pending writes were stored.[64] It depends on the durability mode: "exit" saves no intermediate state, so a crash mid-run cannot be recovered, and "async" has a small risk of losing a checkpoint.
Exactly-once or idempotency keys
A resumed node runs again from the start, so the docs ask you to make node logic idempotent with idempotency keys, upserts, or read-before-write checks.[65] Completed task results inside a node are restored from the checkpointer rather than run again.
Who may advance a run
Not stated in the sources we read. Looked for in [64][65][66][67][68].
A tool call cut off by a crash
On resume, the node holding the tool call runs again from the start of its function, so code and side effects before the pause run again.[65] Work wrapped in a task that already completed is skipped, because task results are checkpointed.
A model request cut off by a crash
Model calls live in nodes, which run again from the start when a thread resumes; the docs say replay re-executes nodes after the checkpoint, including any LLM calls.[68][65][64]
Files, processes, and sandboxes
Not stated in the sources we read. Looked for in [64][65][66][67][68].
Hosting model
A framework you install and call from your own code with a checkpointer you configure; LangSmith's Agent Server is a separate option that handles persistence for you.[68][66] With LangSmith's Agent Server, checkpointers and stores are handled for you.
Run length or retention
A single execution may run at most 1000 super-steps by default (the recursion limit, since version 1.0.6); checkpoints accumulate until you prune them.[65][66] The recursion limit can be set per run in the config.
Human waits and timers
interrupt() saves graph state through the checkpointer and waits indefinitely until you resume the thread with Command(resume=...); the interrupted node then reruns from its beginning.[67] It survives a restart only with a persistent checkpointer, which the docs recommend for production.
Caveats
  • If a node calls tasks or interrupt(), stricter determinism rules apply on resume.[65]
  • The thread ID is the pointer to saved state: reusing it resumes the same checkpoint.[67]

OpenAI Agents SDK

OpenAI's lightweight package for building agent apps, in which a Runner drives the loop of model calls, tool calls, and handoffs.[73][72]

Where state is stored
A paused run's RunState, which your application serializes and stores, for example in a database or queue; conversation history can live in a session store or on OpenAI's servers.[69][72] The SDK resumes from the RunState of a paused run or of a run stopped after a turn.

Mastra

An agent framework whose durable agents, a beta added in @mastra/core 1.45.0, wrap a regular agent so the agent loop runs inside a workflow.[84]

Where state is stored
Durable agents can checkpoint each run's state as workflow snapshots in the storage configured on Mastra, such as a PostgresStore.[84] By default (recovery.durableAgents: 'off'), only pending, paused, and suspended snapshots are written, not per-step running checkpoints.
How a run is recovered
Recovery re-drives a run left in running status from its last persisted snapshot, automatically on server start with recovery.durableAgents: 'auto' or manually with recoverActiveRuns().[84] With the default 'off' setting and no custom snapshot policy, running checkpoints are not written, so recovery finds nothing after a crash.
Exactly-once or idempotency keys
Recovery can reissue LLM calls and re-execute tool calls, including a whole sub-agent run, so the docs ask for idempotent tools or deduplicated external side effects.[84]
Who may advance a run
No distributed lease or lock yet: with automatic recovery on, every replica races to recover the same runs, so the docs advise your own leader election or a single replica.[84]
A tool call cut off by a crash
When recovery is on, the agent loop re-runs from the last persisted snapshot and can re-execute tool calls; on Inngest, each tool call is a memoized step that Inngest can retry.[84] Without recovery, a crashed run stays in running status with no automatic retry.
A model request cut off by a crash
Recovery re-runs the agent loop from the last persisted snapshot, which can reissue LLM calls, with real cost.[84] Running checkpoints are written by default only when recovery.durableAgents is 'auto'.
Files, processes, and sandboxes
Not stated in the sources we read. Looked for in [84].
Hosting model
A framework you run in your own server: createDurableAgent() runs in one process, createEventedAgent() runs in the background, and createInngestAgent() runs the workflow on the Inngest platform.[84]
Run length or retention
No run-length limit is stated. If you do not call cleanup(), Mastra deletes a run's cached events cleanupTimeoutMs after the run ends; setting it to 0 turns that timer off.[84]
Human waits and timers
When a tool call needs approval, the workflow suspends and waits for resume(); suspended snapshots are always persisted, so human-in-the-loop resume works without configuration.[84] Inngest agents persist only suspended snapshots, because Inngest's own replay provides durability.

Pydantic AI

An agent framework that makes runs durable by attaching an engine such as Temporal, DBOS, Prefect, or Restate, which wraps each model request and tool call as a durable unit.[85]

Where state is stored
The attached durable engine keeps the run's progress, not chat threads; with Temporal, the Temporal Server stores workflow state in its internal database.[85][87] With Temporal, a run is durable only when it executes inside a Temporal workflow.

The engine recovers the run: Temporal replays workflow code against saved inputs and decisions, and completed model requests and tool calls return recorded results instead of running again.[87] With DBOS a recorded step result is replayed on workflow recovery, and with Prefect a task cache hit reuses it.

A model request cut off by a crash

Cloudflare Agents SDK

The Cloudflare Agents SDK is a library whose agents are Durable Objects: addressable, single-threaded instances with SQLite storage that wake on events and hibernate when idle.[36][62]

Where state is stored
Agent state, SQL tables, schedules, and fiber checkpoints live in the Durable Object's built-in SQLite storage and survive hibernation and restarts.[62][36] Class fields not stored through setState() or this.sql are lost on eviction.
How a run is recovered
runFiber() records work in SQLite and stash() saves snapshots; after eviction, onFiberRecovered() receives the last snapshot and your code decides what recovery means. It is not automatic replay.[63][62] AIChatAgent and Think wrap chat turns in fibers automatically; other in-progress work is lost unless it was checkpointed.
Exactly-once or idempotency keys
startFiber() takes an idempotency key so a retried submission joins or returns the existing job instead of starting a duplicate; recovery after eviction is left to your onFiberRecovered() code.[63][62] startFiber() is a durable acceptance API; an interrupted callback is not replayed automatically.
Who may advance a run
Each agent is one Durable Object, a single-threaded instance with a unique ID; every wake source for an agent name, such as requests, WebSockets, alarms, and email, routes to that same instance.[36][62][63] Several fibers can run at once inside one agent, each with its own SQLite row.
A tool call cut off by a crash
In Think, an interrupted tool call becomes an errored tool result before the next model call, so the model does not silently re-run it. Elsewhere, an interrupted fiber is not replayed automatically.[34][63] Applies to Think chat turns; repairInterruptedToolPart can change the repaired shape.
A model request cut off by a crash
AIChatAgent and Think wrap each chat turn in a fiber; after eviction the default persists partial output and continues or retries the turn when safe, with strategies varying by model provider.[62][34] onChatRecovery can return { continue: false } to prevent another model call.
Files, processes, and sandboxes
Agent memory is lost on eviction. An attached sandbox container keeps files only while it runs; when it stops, files are gone unless saved as a snapshot.[62][35] The docs' example keeps the container running 10 minutes after the agent goes inactive so files remain for the next turn.
Hosting model
Cloudflare runs each agent as a Durable Object and handles placement, scaling, and recovery; you manage no servers, and a hibernated agent consumes zero compute.[62][36] The SDK is the agents library; its Agent class extends Durable Objects.
Run length or retention
keepAlive() suits work measured in minutes, not hours; alarm handlers time out at 15 minutes; an interrupted fiber whose recovery keeps failing is discarded after fiberRecoveryMaxAgeMs, 24 hours by default.[62][63] Agents themselves are described as persisting for days, weeks, or months.
Human waits and timers
schedule() stores tasks in SQLite and fires alarms that wake a hibernated agent, while setTimeout timers are lost; human approval inside an agent is built yourself with state and WebSockets, or delegated to a Workflow.[62] For waits of hours or days, the docs persist the job ID in state and hibernate until a callback, poll, or workflow completion wakes the agent.
Caveats
  • keepAlive() only reduces eviction; without runFiber(), work in progress is lost if the agent is evicted anyway.[63]
  • Durable Objects are also evicted by code updates and runtime restarts, which the docs put at 1–2 times per day.[63]
  • The beta PiHarness runs the Pi Durable harness inside an agent's Durable Object and follows Pi's own rules, such as not rerunning an unsafe tool and telling the model.[106]

Pi Durable

An experimental package from Earendil for long-running, durable agents: a harness that runs conversations, model requests, and tool calls as checkpointed tasks over a storage backend.[89]

Where state is stored
Conversations, task checkpoints, and documents are committed to a storage backend you choose: memory, SQLite, JSONL, or your own, such as a key-value store or Postgres.[89][91] Memory storage persists nothing; on SQLite, commits survive process crashes, but the newest may be lost on power or host failure.
How a run is recovered
Every step is a task that stores a checkpoint; after a crash, a new process opens the same storage and continues each unfinished task from its last checkpoint.[89][91][98] Interrupted work stays pending until resume(), a submission, or a wait starts the task scheduler.
Exactly-once or idempotency keys
A requestId deduplicates submissions within one conversation; task phases and hooks can run again after a crash, so the post uses an idempotency key and first-write-wins memos.[89][95][96] The post calls this an exactly-once submission; a repeated requestId in the same conversation returns the stored submission.
Who may advance a run
One process owns a storage at a time and other clients attach to that process; there is no cross-process locking.[89][91][103] The demo coding app takes its own file lock, which goes stale 10 s after the process holding it crashes.
A tool call cut off by a crash
An interrupted tool call reruns only if both its stored and its current replay policy say safe (the default is unsafe); otherwise the model is told it was interrupted and may have partially run.[92][94][89][93] A tool that no longer resolves after the restart is treated as unsafe.
A model request cut off by a crash
An interrupted model request is sent again with no declaration needed; its partial answer stays in the transcript, marked as aborted.[89][99][91] Partial answers are committed at most every 100 ms, so a crash loses at most that window.
Files, processes, and sandboxes
Tools work through an execution environment the application supplies, such as your laptop, a remote VM, or an in-memory sandbox; the env function builds it for every tool call.[89] The post says application state, including the sandbox a conversation runs in, lives in documents committed with the transcript.
Hosting model
A library you embed in a JavaScript process. The post says its SQLite and JSONL storage also run on Bun or inside a Cloudflare Durable Object with a small adapter.[89][106] Cloudflare documents a beta PiHarness that runs it in a Durable Object.
Run length or retention
No limit on run length, total history, or storage is stated. The post describes a harness that supports infinitely long conversations; compaction bounds the active transcript, and older messages always stay in storage. Each tool result is cut to its tool's output limits before it is stored.[89][106][92] Cloudflare's page notes that Pi Durable cannot delete a conversation yet, and that on its PiHarness one model request that streams for more than 15 minutes can be cut off.
Human waits and timers
Tasks get timers that survive restarts and can wait on other tasks with no code running; a sleep waits for an absolute wake-up time, which the built-in retry and poll phases keep in their checkpoints.[89][91][98][99][106] There is no built-in approval step for tool calls; the post's approval example asks from a hook and stores the answer in a memo.
Caveats
  • Pi Durable is experimental, and its API may change between releases.[89][91]
  • The package's own test expects a real bash command cut off by a close and reopen to be reported as interrupted, not rerun.[93]
  • JSONL storage does not flush to disk before each commit unless you pass fsync: true.[101][91]
  • On Cloudflare's beta PiHarness, one model request that streams for more than 15 minutes can be cut off.[106]
What we found reading the v1.0.0 code
Checkpoint unit
The harness runs one task for each model request, one for each tool call, and one for compaction. When a harness opens its storage, tasks that were running are switched back to pending and continue from their last committed state. The unit is a step inside a task, which the code calls a phase. Our reading: anything a phase does before its next commit can happen again after a crash.[89][98]
Built-in tools
The four built-in coding tools, read, write, edit, and bash, declare no replay setting, so after a crash even a read is reported as interrupted instead of being run again.[97]
Compaction
With the built-in defaults the next request waits for a summary once the context passes the model’s window minus 16,384 tokens, and a background summary starts 32,768 tokens before that. When a provider rejects a request as too long, the code compacts once and tries again.[89][100][99]
Spend
Each conversation records token use and cost in a document, and “Failed and aborted attempts count too.” We searched the package source for a turn limit or a budget and found none. Spend is recorded, not capped.[91]

What Pi Durable teaches

  • A model request and a tool call need different rules after a crash. Pi Durable sends a cut-off model request again with no declaration, keeping the partial answer marked as aborted, and reruns a cut-off tool call only if both the stored and the current declaration say safe; the default is unsafe.[89][92][94] Eight of the nine engines in the table retry both as durable steps instead, and Temporal notes that a retried model call is “an independently sampled answer rather than a continuation”.[5] In our reading, the split puts the caution where the risk is: a resent request costs tokens and returns a new sample, while a repeated tool call can repeat an effect.
  • The checkpoint can sit at every message. The harness runs built-in tasks, “one for each model request, one for each tool call, and one for compaction”, each with “a checkpoint after every step”, and it commits partial answers and tool output at most every 100 ms.[89][91] Calls can run at the same time: in the post’s demo, “A subagent runs three searches in parallel, each a durable task.”, and the README’s example sets toolExecution: "parallel".[89][91] In our reading, a crash therefore leaves in doubt each task that was unfinished, from its last checkpoint, and up to 100 ms of its output, however many tasks that is. Engines reach a boundary this fine when each model call and each tool call is its own step, which is what their agent guides ask for.[22][29][33]
  • One owner is an assumption to enforce. Pi Durable’s README is plain: “One process owns a storage at a time; there is no cross-process locking.”[91] Some engines enforce one writer inside their own service: Temporal assigns each execution to a history shard, and Restate offers a “Single-writer guarantee”.[10][11] In our reading, running Pi Durable in more than one process means adding a lease and a fencing check yourself, as chapter 5 describes.[140]
  • Compaction is part of the record. Pi Durable runs compaction as a task of its own and pins the range it will summarize in its checkpoint; a comment in the code reads “The context at tail is immutable, so this is the range select chose.”[105] In our reading of that code, a process that restarts in the middle of a compaction summarizes the same range again, and the cut never separates a tool call from its result. The post adds that “The older messages always stay in storage.”[89] Among the other systems, compaction is built in for some and left to your code by others, and for 16 of the 26 systems the pages we read do not say whether the system compacts its context; Explainer 4 lists which.
  • A library leaves the service work to its host. Pi Durable runs only while a process runs it: work interrupted by a crash “stays pending” until resume(), a submission, or a wait starts the task scheduler.[91] It has no cross-process locking, its execution environment has no snapshot or restore operation, it has no approval or permission step for tool calls yet, and we found no turn limit or budget in its source; it records spend instead.[91][102][106] Engine services such as Temporal, Restate, or Inngest run part of this work for you, scheduling, retrying, and keeping runs, as chapters 3 and 8 describe.
  • Safe by default has a cost. The four built-in coding tools declare no replay setting, so after a crash even a read is reported as interrupted instead of being run again.[97] Cloudflare’s page on Pi suggests marking a tool safe “when running it twice is harmless, such as a read or a whole-file write.”[106] In our reading, unsafe by default is the right failure for writes, and it leaves the host to declare its reads.

Chapter 12

Costs and other hazards.

In short: Long runs pay to re-send their history, and runs that nobody watches need caps on turns and spend, care with what they reload, and credentials that outlast them.

Every model request in an agent loop sends the conversation so far. Server-side conversation state does not avoid this. OpenAI’s docs: even with previous_response_id, “all previous input tokens for responses in the chain are billed as input tokens in the API.”[151] Prompt caching is what makes long runs affordable. On Anthropic’s list prices a cache read costs a tenth of normal input on most models, while writing to the 5-minute cache costs 1.25 times normal input and the 1-hour cache 2 times.[137]

A cache only helps while it is warm and unchanged. Changing tool definitions “invalidates the entire cache”.[147] Resuming a conversation “sends the whole conversation again,” and after a break longer than the cache lifetime “there is no cache left to read”.[150] A crash, a slow human approval, or a redeploy can each make the next request pay to write the whole prefix to the cache again.

Other meters

  • Compaction is a model call. Anthropic: “Compaction requires an additional sampling step, which contributes to rate limits and billing.”[149]
  • Tokenizers differ. Anthropic says its updated tokenizer maps the same input to “roughly 1.0–1.35×” as many tokens as before,[152] and OpenRouter measured “32–34% more native tokens” for production-scale prompts.[153]
  • Harnesses differ. In the Limbo study, “a Codex CLI episode consumed about 153k tokens, against 12k for the minimal scaffold.”[156]
  • Orchestration is metered too. Temporal Cloud starts “at $50 per million actions”;[7] on Inngest “A function run with five steps uses six executions.”[27] Claude Managed Agents adds $0.08 per session-hour, counted only while the session is running.[137]
  • Waiting can be free or not. AWS Lambda durable functions’ waits “suspend execution without incurring compute charges,”[45] and sleeping Cloudflare Workflows instances do not count toward concurrency limits.[32] A user running Pi Durable on Cloudflare Durable Objects reported that a host cannot tell when the harness is only sleeping, so the object stays awake and billed.[104]

Loops that run up a bill

An agent that runs unattended can spend unattended. OWASP lists runaway cost as a security risk, “Denial of Wallet”.[144] Lan Tian’s blog recounts an autonomous agent that tried to scan the DN42 hobby network for about 24 hours before it was shut down; an email from an address claiming to be its operator then asked for donations toward an AWS bill of $6,531.30.[146] Caps help only when set: the Claude Agent SDK’s turn and spend caps are “off when unset”,[77] the OpenAI Agents SDK stops Python runs after 10 turns by default,[71] and a Claude Managed Agents budget “is enforced between model requests, not mid-request.”[111] Pi Durable records spend but does not cap it.[91]

Injected instructions that come back

Persistence also preserves attacks. Anthropic’s engineering team names the state directories of scheduled and long-running agents among the places where “An injection that lands in any of these is reloaded each time the agent starts.”[142] Meta’s “Rule of Two” guidance concedes that “a background process where human-in-the-loop is disruptive or ineffective” is hard to fit into its rule.[143]

Credentials that expire mid-run

A run can outlive its login. Claude Code’s docs warn that a background session that outlives its login “stops making progress once the credential expires”.[145]

Chapter 14

What to do with this.

In short: Durable systems solve the bookkeeping, and the judgment about side effects stays with the people who build the tools.

  • Decide, per tool, whether a rerun is harmless. Default to no. Pi Durable defaults to unsafe;[94] Cloudflare suggests marking a tool safe “when running it twice is harmless, such as a read or a whole-file write.”[106]
  • Give every external write an idempotency key the receiving service honors. A key that only your harness checks does not stop the second charge.[138][156]
  • Plan what happens after “may have partially run”. Give the model a way to read the real state before it tries again, and do not take its report of success as proof.[92][156]
  • Treat the sandbox as state. Snapshot it if the agent depends on files or processes; the transcript will not restore a browser or a half-written file.[154][109][55]
  • Enforce one owner with a lease and a fencing check if more than one machine can open the same storage.[91][140]
  • Pin or migrate code deliberately for runs that will see a deploy.[6][21][98]
  • Cap turns and spend, and alert on them. Some harnesses leave caps off by default or have none.[77][91]
  • Treat persisted context as input you did not write. Anything saved can be replayed into the next session, including an injection.[142]
  • Watch the cache. Keep prefixes stable and expect a full-price request after a crash or long wait.[150][137]

Choosing among the families is mostly about who operates what. Engines such as Temporal or Restate bring replay and versioning, at the cost of running a separate service and, in Temporal’s case, determinism rules.[4][11][14] Libraries such as DBOS or Pi Durable live inside your process with storage you own.[18][89] Vendor agents keep the state for you, under the vendor’s limits.[109][127] Chapter 11 turns these trade-offs into six questions, and chapter 9 sets out how Pi Durable differs.

Chapter 15

Where a data warehouse fits.

In short: In our reading, the recovery store is for resuming one run, and a warehouse copy of run history is for learning from many; the study tested no warehouse in either role.

Chapter 1 calls durability a record that outlives the process: a new process reads it and continues.[89][62] Pi Durable commits that record to storage you choose: memory, SQLite, JSONL, or your own (chapter 9).[89][91] Chapters 2, 5 and 8 describe what particular designs require: Pi Durable checkpoints each step, DBOS stores wake-up times, shared storage has to reject a stale writer, and the OpenAI Agents SDK docs call for an atomic conditional transition there.[89][19][140][70] We evaluated no warehouse, BigQuery included; none of the 26 systems is listed with one as its durable store, and whether a warehouse could meet those requirements is untested.

In our reading, chapter 14’s advice suggests reviewing history across runs: were keys sent, how did the model respond to “may have partially run”, and which runs merit spend alerts? In our reading, those checks need complete enough records of keys, interrupted tool calls, what followed and spend. Chapter 13 reports one calibrated, deterministic simulation: the expected outcome was recovered after all 240 injected crashes, yet 30 traces changed because pre-commit crashes repeated a planner call.[158]

In our reading, that review is the warehouse’s best position, and the recovery store stays where a run resumes. Our example is BigQuery Agent Analytics (BQAA), which Haiyuan works on; we did not run its SDK. The BQAA SDK README calls BigQuery a “Google Cloud analytics data warehouse” and says the SDK is “read-only over that table” of agent events.[166] It describes trace reconstruction, per-event-type views, turn-count and cost metrics, evaluation with an LLM judge, by trajectory and across trials, and regression detection through BigQuery SQL or Python.[166] It also describes Agent Context Graph decision traces, “the requests an agent handled, the options it weighed, and the outcomes it committed”, and long-horizon cross-session memory.[166] It does not say whether those events record idempotency keys or interrupted tool calls.[166] In our reading, that memory puts the warehouse back in the loop, so chapter 14’s rule applies: treat persisted context as input you did not write.[142]
