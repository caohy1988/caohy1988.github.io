An illustrated study, researched 2 October 2026 (Pacific time)

Durable running agents, explained.

An agent that works for hours will outlive the process running it. What should survive the crash, what runs twice, and who notices?

On 1 October 2026 Earendil released Pi Durable, an experimental harness for agents that keep going after their process dies.[1] This study explains the idea, checks Pi Durable’s claims against its source code, maps the alternatives, and collects what research and incident reports say about the hazards and the costs.

Start with the idea

Eleven chapters, three interactive explainers, and 151 numbered sources, each opened and read for this study.

The central finding

Durable harnesses make the agent’s own record survive a crash. What happened outside that record, in files, sandboxes, payment systems, and deploy pipelines, still needs idempotency keys, snapshots, or a person to check.[14][54][140][142]

The study, in eleven chapters

Chapter 1

An agent run that outlives its process.

A durable agent writes its progress to storage as it goes. When the process running it dies, a new process can read that record and continue instead of starting over.

An agent works in a loop. The harness, the program wrapped around the model, sends the conversation so far to the model. The model answers or asks for a tool. The harness runs the tool and sends the result back, and the loop repeats. Long tasks take many turns: one Hacker News commenter described “6-12 hour long individual runs” that touch databases, files, and apps.[42]

Processes die for ordinary reasons. Earendil’s post lists three: “whether the laptop sleeps, the container is redeployed, or the machine runs out of memory”.[1] Whatever the agent held only in memory goes with it: turns not yet saved, an answer the model was halfway through streaming, a tool call in flight, a timer, messages waiting in a queue. Cloudflare’s agent documentation makes the same point in one line: “In-memory variables, timers, open fetches, and local closures do not survive eviction.”[78]

An illustration

An overnight agent is asked to fix a flaky test, open a pull request, and post a note in Slack. Its process dies after GitHub accepted the pull request but before the agent saved that fact. A naive restart opens a second pull request. A durable harness has to know the request went out, or at least warn the model that it might have.

An invented scenario used to explain the problem. It is not a reported incident.

Three questions every design answers

  • Where is progress written, and how often? After every step, at chosen points, or only at the end of a run.
  • What happens to the step that was running? Run it again, skip it, or ask the model or a person.
  • What about effects outside the record? A charged card, a half-written file, a browser left on page five.

Five terms used throughout

Checkpoint
A saved record of progress that a new process can resume from.
Replay
Running code again after a crash while reusing recorded results for the steps that already finished. Engines that replay, such as Temporal, require the replayed code to be deterministic, so that it “makes the same Workflow API calls in the same sequence, given the same input.”[58]
At-least-once
A step that may run more than once, because a crash can land after the step acted but before its result was saved. DBOS documents the window: after a database write, “but before the checkpoint is saved, the step runs again on recovery”.[71]
Idempotency key
A unique value sent with a request so the receiving service can recognize a retry and return the first result instead of acting twice. Stripe stores the first result for a key “regardless of whether it succeeds or fails.”[122]
Exactly-once
The effect happens once, crashes included. A widely cited essay puts the limit bluntly: “Within the context of a distributed system, you cannot have exactly-once message delivery.” The same essay says the way systems achieve it in practice is “by faking it”, with idempotent messages or deduplication.[123]

Chapter 2

What Pi Durable says it does.

Pi Durable is an experimental TypeScript library that Earendil shipped alongside Pi 1.0 on 1 October 2026. It runs agent conversations on storage you choose and promises to pick up where it left off after a crash.[1][2]

Pi is Earendil’s minimal coding-agent harness. The post draws a line between the two products. The coding agent runs in a terminal for one person, and “If the process dies, you look at what happened and tell it to continue.” Pi Durable is a separate package, “built specifically for long-running, durable, and malleable agents that can run anywhere.”[1]

The release timing is easy to reconstruct. The npm registry recorded version 1.0.0 at 19:11 UTC on 1 October, the GitHub release went up at 19:20, and Hacker News user paulsmith submitted the post at 19:24.[18][16][26] The npm record also lists eight earlier versions, the first published on 19 September.[18] Both Pi and Pi Durable are MIT licensed.[2]

Its vocabulary

Harness
“A harness is storage plus the machinery needed to run one or more conversations with large language models in parallel.”
Conversation
“A conversation is an interaction between you and an agent, recorded as a transcript.”
Agent
“The agent is the large language model together with its settings, like the thinking level, and the tools it can call.”
Task
“Everything the harness runs, from calling the model to executing a tool, is a task.”[1]

The promises, in the post’s own words

Checkpoints
“In Pi Durable, every step of a run is a task that stores a checkpoint before it moves on. If the process dies, a new process opens the same storage, finds the unfinished tasks, and continues each one from its last checkpoint.”
Model calls
“A model request that was cut off is sent again; the partial answer stays in the transcript, marked as aborted.”
Tool calls
“A tool call that was cut off reruns if it is safe to; otherwise the model is told it was interrupted.”
Submissions
“A requestId makes a submission exactly-once, so a client that retries after a crash gets the original submission back instead of asking twice.”
Decisions in hooks
“A hook can run again after a crash, so a hook that makes a decision stores it in a memo: a small value stored with the task, where the first write wins.”
Storage
“One process owns a storage at a time, and other clients attach to that process.”
Long conversations
“If the provider still rejects a request as too long, the harness compacts and retries once.” And: “The older messages always stay in storage.”
Changing code
“Conversations store extension and tool names, never code, so after a restart they pick up whatever the new process installs.”
Many clients
“Any client can steer a running conversation or queue a follow-up.”
Status
“Pi Durable is experimental, and the API might still change.”[1]

The post’s examples make the tool rule concrete. A search tool is declared replay: "safe" with the comment “only reads, so a rerun after a crash is fine”. A deploy tool leaves the setting out, with the comment “No replay: a deploy interrupted by a crash is reported to the model, never repeated” (line break removed).[1]

Some pieces are left to the builder. “Pi Durable has no built-in subagents, but they take a few lines of code to build,” and tools reach files and shells through an execution environment, “which can be your laptop, a remote VM, or an in-memory sandbox.”[1] The post describes a library you install from npm. It does not describe a hosted service.

Chapter 3

What the code confirms, and where it is narrower.

We downloaded the v1.0.0 source and read the code behind each promise. The recovery rules work as the post describes. Several promises carry conditions the post does not spell out.

The v1.0.0 tag points at commit a13d35a, made on 1 October.[16] By 22:14 UTC on 2 October the main branch was 25 commits ahead, but inside the durable package only the changelog had changed.[17] We did not run the harness. Everything below comes from reading the source, and statements marked as our reading are inferences from that code, not tested behavior.

Size
We counted the lines ourselves. The 54 source files outside the shipped testing helpers come to 15,483 lines; with the helpers, 60 files and 17,662 lines. The storage backends are 2,926 lines, and there are 32 example files. That fits the post’s “about 15,000 lines” and “3,000 lines” if the testing helpers are left out.[1][16] OpenAI’s open-source o200k_base tokenizer gives 144,423 tokens for the 54 files, close to the post’s “about 150,000 tokens with GPT”.[1][25] The post does not say which tokenizers it used, and we did not count Claude tokens.
Checkpoints
When a harness opens its storage, tasks that were running are switched back to pending and continue from their last committed state.[10] The unit is a step inside a task, which the code calls a phase. Our reading: anything a phase does before its next commit can happen again after a crash.
Model calls
An interrupted partial answer is appended to the transcript with the stop reason aborted, and the request is sent again.[11]
Compaction
The post’s settings are the built-in defaults: the next request waits for a summary once the context passes the model’s window minus 16,384 tokens, and a background summary starts 32,768 tokens before that.[1][12] When a provider rejects a request as too long, the code compacts once and tries again; a comment explains that “An overflow is never retried: only a compaction can make the next request fit.”[11]
Tool calls
The tool’s intent is committed before it executes. On recovery the call runs again only when both the stored and the current declaration say safe, and the default is unsafe.[4][6] Otherwise the model gets an error result holding whatever output was saved, followed by a note that the tool “was interrupted and may have partially run”.[4][5]
Built-in tools
The four built-in coding tools, read, write, edit, and bash, declare no replay setting, so after a crash even a read is reported as interrupted instead of being run again.[9] An issue filed on 2 October said the same; the repository’s bot closed it eight seconds later under its rule of auto-closing issues from new contributors.[21] The four files on the main branch were unchanged on this point when we checked on 2 October.[9]
requestId
The code calls it a “Host-provided deduplication key, scoped to the conversation.”[7] A repeated key returns the submission already stored.[8] Our reading: this stops a client from submitting the same request twice. It does not stop a tool from repeating an effect further down; that depends on each tool.
One owner
The README is direct: “One process owns a storage at a time; there is no cross-process locking.”[3] Keeping a second process out is the host’s job. Earendil’s own demo app takes a file lock and notes that “A lock left by a crashed process goes stale after 10 s”.[15]
Commit durability
For SQLite the README says that “commits survive process crashes; the newest may be lost on power or host failure.”[3] The JSONL backend’s fsync option “Defaults to false.”[13] Our reading: the recovery rules assume the tool’s intent record survived. If a power cut loses that newest commit, a tool can run again even though it was never declared safe. We did not test this.
Timers
sleep() is an in-process timer loop.[10] A wait survives a restart when its wake-up time is stored in the checkpoint, as the built-in retry and poll steps do.[11] A user running Pi on Cloudflare Durable Objects reported on 2 October that closing and reopening in the middle of a sleep works, but that a host cannot tell when the harness is only sleeping, so the object stays awake and billed.[22]
Sandboxes
The execution environment interface covers files and shell commands and has no snapshot or restore operation.[14] The post lets a document record “the sandbox a conversation runs in,” but the files and processes inside that sandbox are outside Pi’s record.[1][14]
Spend
Each conversation records token use and cost in a document, and “Failed and aborted attempts count too.”[3] We searched the package source for a turn limit or a budget and found none. Spend is recorded, not capped.
Prompt cache
The post says that on models supporting mid-conversation changes “only the change is sent, so the prompt cache stays valid.”[1] In the model catalog shipped with pi-ai 1.0.0 we counted 85 of 1,604 entries flagged for mid-conversation system messages and 6 for mid-conversation tool changes.[19] For other models “the replayed system message leads, and every later system message is dropped” (line break removed).[20] We did not measure cache hits.
Cloudflare
The post says the SQLite and JSONL storage runs “on Bun or inside a Cloudflare Durable Object” with a small adapter. The Pi repository at v1.0.0 contains no such adapter; outside the post, the claim appears only in its README.[1][3] Cloudflare’s documentation, last updated on 2 October, describes one: a beta PiHarness that keeps Pi’s tables in the object’s SQLite database and restarts an evicted object from a heartbeat alarm that fires every 30 seconds.[24] Cloudflare lists limits, among them “Pi Durable has no approval or permission step for tool calls yet” and that a single model request streaming for more than 15 minutes “can be cut off.”[24]

Two open issues from the first day show where builders are already pushing. One asks for a configurable commit interval: its author, building a hosted service on pi-durable with a remote Postgres store guarded by a lease, measured about 16 commits for one turn with one tool call.[23] The other is the sleeping problem above.[22]

Chapter 4

Engines, libraries, and hosted agents.

Durable agents come in three shapes: general durable-execution engines that agents run on, agent libraries with persistence of their own, and hosted agents where the vendor keeps the state.

In the Hacker News thread, lukebuehler named “LangChain Deep Agents, Vercel Eve, OpenAI Agents API, Anthropic Managed Agents” as products in this space and gave three reasons for the trend:[29]

1) they are "durable", i.e. easier to make long-running in an unattended way, and easier to implement recovery, monitoring, etc

2) separating the harness from the compute brings safety and scaling benefits

3) easier to make multi-player.

lukebuehler on Hacker News, 1 October 2026[29]

Chapter 5

Four ways to pick up where you left off.

The systems differ less in their storage than in what they do with the step that was running. Four designs cover most of them.

  • Replay a deterministic program against its history

    The engine records every step’s result, then on recovery runs the program again from the top, feeding it the recorded results. Temporal, Azure Durable Functions, Vercel Workflow, AWS Lambda durable functions, and Restate work this way.[58][87][80][84][65] The price is determinism. If replayed code takes a different path, Temporal’s runbook says affected executions stop making progress, and “This will not clear up on its own.”[61] Model calls therefore go into Activities, “so they retry durably and are not repeated during Workflow replay.”[62]

  • Store each step’s result and skip finished steps

    The program re-runs too, but the engine only promises that finished steps return their saved results. DBOS “automatically recovers its execution from the last completed step”,[70] and Inngest reuses “results from completed steps whose IDs still match.”[75] The step that was running is retried, so it runs at least once.[71][76]

  • Snapshot the process or the machine

    Trigger.dev freezes a waiting task’s whole process with CRIU, “including memory, CPU registers, and open file descriptors.”[88] Devin snapshots a sleeping session’s disk, but “Running processes do not” survive.[120] Claude Managed Agents checkpoints an idle session’s sandbox, “including the filesystem, installed packages, and any files the agent created.”[106] Research prototypes such as Crab coordinate sandbox snapshots with the agent’s turns.[140]

  • Checkpoint each task and declare what may run again

    Pi Durable stores a tool call’s intent before running it and leaves the decision about a cut-off call to a declaration: run it again if it is safe, otherwise tell the model.[4] A cut-off model request needs no declaration; it is sent again.[11] Claude Code takes the conservative path on resume: a cut-off tool “doesn't finish or run again”, and Claude is told to check whether it took effect.[114] Google ADK’s resume goes the other way and runs tools “at least once”.[100] Cloudflare’s Agents SDK hands the decision to the application: runFiber() records work in SQLite, lets code checkpoint with stash(), and “calls onFiberRecovered() on the next activation if the agent was evicted mid-task.”[79]

Changing the code under a running agent

A run that lasts days will meet a deploy. Every durable system has to decide which version of the code a resumed run uses.

  • Pin the run to its version. Temporal can run a pinned workflow “entirely on the Worker Deployment Version where it started.”[63] Restate keeps in-flight invocations on their original deployment, and Vercel pins each run to “the deployment that starts them.”[68][81] The trade-off, in Restate’s words: “When a bug affects in-flight invocations, they remain pinned to the original deployment.”[68]
  • Recover only matching versions. DBOS recovers only “workflows whose version matches the current application version.”[72]
  • Use the new code and match steps by name. Inngest resumes runs on current code; a changed step “can repeat a payment, email, or resource creation.”[75]
  • Store names, not code. Pi Durable resumes conversations with whatever tools the new process installs.[1] Our reading of its scheduler: a stored task version equal to the installed one runs the new code against the old checkpoint without further checks; an older installed version blocks the task, and a newer one needs a migration function.[10]

Chapter 7

How long runs go wrong.

Durability fixes one failure, losing the record, and makes others easier to see. These are the hazards the sources document.

The same effect, twice

Any design that retries an interrupted step runs it at least once and sometimes twice. Temporal says an Activity “may be executed multiple times and may even partially complete more than once”.[59] In a simulated benchmark, frontier models instructed to act exactly once duplicated a write in 56% of episodes when the request was still in flight and committed late, and in 74% when the transport delivered it twice. A separate experiment in the same paper, with four models and a tool contract in which every write accepts an idempotency key, cut the late-commit duplicate rate of agents without a guard from 61% to 9%.[142] In Pi Durable, a tool declared safe is simply run again from the start; our reading is that a crash after it acted but before its result was saved repeats the effect.[4]

An outcome nobody knows

The cautious alternative leaves the question open. Pi Durable tells the model a tool “was interrupted and may have partially run”;[4] Claude Code tells Claude to check whether a cut-off call took effect.[114] The model then has to investigate. The Limbo study found that agents reported success in 90% of the episodes in which they had duplicated an effect.[142]

The record and the world drift apart

The transcript survives; the world it describes may not. “Sessions persist the conversation, not the filesystem”, say Anthropic’s SDK docs.[97] A reclaimed Claude Code cloud VM comes back with the conversation, but “Background work that was still running when the VM was reclaimed, such as subagents and shell commands, isn't restored.”[115] OpenAI’s Agents API: “Reusing the environment ID does not restore files in replacement compute.”[111] The Crab paper measured the gap: restoring chat history alone recovered 8 to 13% of tasks correctly, against 100% when sandbox state was checkpointed too. By workload, chat-only recovery succeeded on 13% and 8% of shell-intensive Terminal-Bench tasks with the Claude Code and iFlow-cli agents, and on 9% of code-repair SWE-bench tasks.[140]

Two processes, one record

A single-owner design is only as safe as the lock that enforces it. Pi Durable has no cross-process locking,[3] and Mastra says it “doesn't provide a distributed lease or lock yet.”[102] SQLite’s write-ahead log needs every process on one machine: “WAL does not work over a network filesystem.”[125] A lease alone is not enough when an old owner can wake up late. Fencing tokens fix that, but as Martin Kleppmann wrote, “this requires the storage server to take an active role in checking tokens”.[124]

Instructions lost to compaction

Long runs must shrink their context, and summaries drop details. Anthropic’s docs warn that images, documents, uploads, and fetched URLs in a summarized range “are gone once the block replaces them.”[134] Summer Yue wrote on 23 February 2026 that an OpenClaw agent had been told to suggest what to archive or delete and not to act until instructed, and that “my real inbox was too huge and triggered compaction. During the compaction, it lost my original instruction”.[130] TechCrunch, which reported that the agent then began deleting email, said it “could not independently verify” what happened.[131]

Loops that run up a bill

An agent that runs unattended can spend unattended. OWASP lists runaway cost as a security risk, “Denial of Wallet”.[128] Lan Tian’s blog recounts an autonomous agent that tried to scan the DN42 hobby network for about 24 hours before it was shut down; an email from an address claiming to be its operator then asked for donations toward an AWS bill of $6,531.30.[132] Caps help only when set: the Claude Agent SDK’s turn and spend caps are “off when unset”,[99] the OpenAI Agents SDK stops Python runs after 10 turns by default,[96] and a Claude Managed Agents budget “is enforced between model requests, not mid-request.”[108] Pi Durable records spend but does not cap it.[3]

Injected instructions that come back

Persistence also preserves attacks. Anthropic’s engineering team names the state directories of scheduled and long-running agents among the places where “An injection that lands in any of these is reloaded each time the agent starts.”[126] Meta’s “Rule of Two” guidance concedes that “a background process where human-in-the-loop is disruptive or ineffective” is hard to fit into its rule.[127] On HN, zmmmmm sketched the defense for an email agent that will be “prompt injected constantly”: a low-trust subagent reads the mail, and only cleaned-up output reaches the agent allowed to change a database.[45]

Credentials that expire mid-run

A run can outlive its login. Claude Code’s docs warn that a background session that outlives its login “stops making progress once the credential expires”.[129]

Chapter 8

Long runs pay for their history.

Every model request in an agent loop sends the conversation so far. The longer a run lives, the more each request re-sends, and the more a crash or a long pause can cost.

Server-side conversation state does not avoid this. OpenAI’s docs: even with previous_response_id, “all previous input tokens for responses in the chain are billed as input tokens in the API.”[137] Prompt caching is what makes long runs affordable. On Anthropic’s list prices a cache read costs a tenth of normal input on most models, while writing to the 5-minute cache costs 1.25 times normal input and the 1-hour cache 2 times.[109]

A cache only helps while it is warm and unchanged. Changing tool definitions “invalidates the entire cache”.[133] Resuming a conversation “sends the whole conversation again,” and after a break longer than the cache lifetime “there is no cache left to read”.[136] A crash, a slow human approval, or a redeploy can each make the next request pay to write the whole prefix to the cache again. That is why Pi Durable’s promise to send only changes mid-conversation matters, and why it is worth knowing it applies to the minority of models flagged for it.[19][20]

  • Compaction is a model call. Anthropic: “Compaction requires an additional sampling step, which contributes to rate limits and billing.”[135]

Chapter 10

What to do with this.

Durable harnesses solve the bookkeeping. The judgment about effects stays with the people who build the tools.

  • Decide, per tool, whether a rerun is harmless. Default to no. Pi Durable defaults to unsafe;[6] Cloudflare suggests marking a tool safe “when running it twice is harmless, such as a read or a whole-file write.”[24]
  • Give every external write an idempotency key the receiving service honors. A key that only your harness checks does not stop the second charge.[122][142]
  • Plan what happens after “may have partially run”. Give the model a way to check the real state, such as a status query, before it tries again.[4][53]
  • Treat the sandbox as state. Snapshot it, or keep agents to declarative changes you can re-apply. The transcript will not restore a browser or a half-written file.[140][54][52]
  • Enforce one owner with a lease and a fencing check if more than one machine can open the same storage.[3][124]
  • Pin or migrate code deliberately for runs that will see a deploy.[63][10]
  • Cap turns and spend, and alert on them. Some harnesses leave caps off by default or have none.[99][3]
  • Treat persisted context as input you did not write. Anything saved can be replayed into the next session, including an injection.[126]
  • Watch the cache. Keep prefixes stable and expect a full-price request after a crash or long wait.[136][109]

Choosing among the families is mostly about who operates what. Engines such as Temporal or Restate bring replay and versioning, at the cost of running a separate service and, in Temporal’s case, determinism rules.[61][65][68] Libraries such as Pi Durable or DBOS live inside your process with storage you own.[1][69] Hosted agents keep the state for you, under the vendor’s limits.[106][117] Pi Durable’s contribution is a small, readable design that makes its recovery rules explicit. It is also, by its own description, experimental.[1]
