The theme: the agent's own account of what it did is not enough evidence. A tool can report success and return a truncated payload. An injected string can empty the reasoning trace while the harmful tool call still runs. An agent can claim it finished without anything independent checking. 2. NEW rank: Letta Code v0.33.0: background memory worker, running workflows exposed in the protocol, ambient credential redaction

What shipped (read from the release notes and PR bodies; PyPI letta 0.33.0 is summarized as "Letta Code: stateful agents in your terminal"):

  • #4628 / #4634, background memory worker.
  • Letta Code's memory is a Git repo. When the post-turn sync finds an unfinished merge or rebase, a repair-only worker now fixes it instead of asking the agent to.
  • Each handed-off conflict is recorded (HEAD, the operation's heads and a per-attempt token) so that a duplicate repair becomes a no-op.
  • Routine memory upkeep also moves to the worker.
  • #4652, running workflows in the protocol. Background workflows used to appear in the App Server status snapshot as Bash processes. They now have their own workflow variant with task id, description, start time and status.
  • #4657, redacting ambient credentials (incident LET-10106). A sandbox env-file parse error printed the full LETTA_API_KEY to stderr. The runtime credential is now scrubbed from:
  • streamed stdout/stderr, with a chunk-boundary-safe scrubber (a secret split across chunks is still caught)
  • the final return of every tool, not just shell tools
  • thrown errors and background output
  • PostToolUse / PreToolUse hook feedback
  • The PR itself says this is containment of accidental output, not a credential boundary.
  • #4663: subagents keep effort-suffixed model pins when they spawn.

TL;DR for BQAA: two patterns to copy.

  • Redaction. Secrets can leak through tool errors and stream chunks, not just tool results. Any payload BQAA logs from tool output needs the same chunk-safe scrubbing before the write to BigQuery.
  • Work outside the turn. Background memory upkeep and repair happen outside the turn that caused them. BQAA should log them as separate events tied to the originating turn and attempt token, or memory state will change with no trace attached.

1. NEW rank: arXiv 2609.27542: Control-Token Injection Suppresses Chain-of-Thought and Defeats Reasoning-Based Oversight in Tool-Using Agents

Who / what:

  • Usama, Jung (Braindeck) and Un Nisa (U. Wah); cs.CR; submitted Sep 23; no venue.
  • Code with per-trial logs: https://github.com/Usama1002/deleting-the-trace.

Finding. One fixed string of gpt-oss-20b's own control tokens, placed in untrusted input, drops reasoning from a mean of 52.5 tokens to 0 in 40/40 trials, while the http.post exfiltration still fires 40/40 (Table 1).

  • With malicious framing, rule-based and LLM monitors that read the reasoning go from catching 100% of plain trials to 0% of forged ones. The attack converts 39.6% of refusals into completed exfiltration (Table 3).
  • Planting a fake reasoning line ("Routine request; proceeding.") gets past keyword, empty-trace and LLM-judge monitors, 16/16 (Table 7).
  • Swapping only the tool-call parser gives 24/24 vs 0/24 on identical model outputs (Table 4). So the harness decides whether an emitted call executes.

Caveats:

  • Small n: one main model, and an unnamed sandbox.
  • The 24/0 parser gap partly comes from an integration bug, which the authors disclose.
  • It applies to open-weight models whose chat template the customer controls, not to hosted Gemini.

TL;DR for BQAA: any safety analytics that reads logged thoughts can be blinded by one string. BQAA should log tool arguments and executed side effects next to the reasoning, and support three flags: empty or boilerplate reasoning, control-token patterns in user or tool content, and emitted-but-not-executed divergence.

2. NEW rank: arXiv 2609.27871: Bounded Loops — Pre-Run Spend Bounds, Proved Termination, and Verified Completion for Agent Harnesses

Who / what:

  • V. P. Bhardwaj (Qualixar), G. Singh and A. P. Bhardwaj; cs.SE; 74 pp.
  • The abs page's citation_date is 2026-08-20, although the ID is a September one; I took it as-is.
  • Code (Apache-2.0): https://github.com/qualixar/bounded-loops.

Finding. A step is "done" only when an independent gate the worker cannot write to returns pass / reject / incapacity. The verdict goes into an append-only hash-chained ledger, and the run has a pre-declared budget.

  • Proofs:
  • Runs terminate even when a failure re-runs earlier steps, with at most (R+1)·Σm_v attempts. This needs a single run-wide repair budget; with per-node budgets two nodes could re-run each other forever.
  • "Done" is always backed by a recorded verdict.
  • Adding a model judge next to a deterministic gate (both must pass) cannot add false accepts.
  • Empirical:
  • 47 gate defects in shipped code, 20 of them false accepts.
  • After repair, 0/209 false accepts (α ≤ 1.8%, Wilson 95%). A new mutation family then got 23.3% false accepts, so the zero means the tests were saturated, not that the gates are correct.
  • The declared wall-clock ceiling was only checked between attempts. 65 of 69 loops declared 60 s for 10 attempts; real turns had a median of 48.3 s and a max of 270.6 s (§14.2).

Caveats:

  • The authors wrote the gates, the corpus and the catalogue.
  • Vendor conflict of interest (disclosed).
  • Arithmetic slips: the Table 13 caption and the §12.7 Wilson bound do not match the text.
  • The abstract overstates "47 vacuous": 2 of the 47 are false rejects and 11 are misfiled incapacities.

TL;DR for BQAA: this is the closest paper yet to a spec for an audit log of agent completion: the gate verdict, whether an attempt actually happened, the attempt counter and the declared budget, all checkable by a third party from the log alone. BQAA should record these fields, not enforce them. The unenforced-ceiling finding is a reason to log declared budget next to actual spend for every run.

3. NEW rank: arXiv 2609.26836: Silent Failures in Agent–Tool Interaction — An Audit of ToolUniverse

Who / what:

  • Gopalan, Singh and Narayanan (AI Tech Ethics); cs.AI/SE; submitted Sep 21; no code released.

Finding. Tool calls through MCP often look successful but return incomplete, transformed or unqualified data. The agent then states wrong claims confidently, which the authors call "silent amplification".

  • 91 human-verified failures across 198 test cases in 15 tools.
  • Most originate in the API or wrapper layer, not the agent.
  • Completeness is the top issue dimension (28 of 134 occurrences).
  • 7 of 15 tools failed more than half their test cases.
  • The paper proposes a 7-level failure-locus taxonomy (tool limitation … agent misinterpretation).

Caveats:

  • Tools were chosen because they already had candidate failures, so the rates are not base rates.
  • An LLM generated the candidate failures and adjudicated them; validation of the rest was partial.
  • The 51/25 API-vs-wrapper split is in the abstract but cannot be traced in the body.
  • The agent's model is not named.

TL;DR for BQAA: "tool returned OK" is the wrong success signal. The TOOL_COMPLETED payload needs truncation, row-cap, empty-but-success and missing-field indicators so silent failures can be queried. The L1–L7 taxonomy is a usable starting label set for a detector.

4. NEW rank: arXiv 2609.28197: PASTABench — Proactive Assessment of Sequential Trajectories for Agent Safety

Who / what:

  • Sun, Zhou, Zhu, … Han and Guo (HKUST), with J. Zhou (PKU).
  • EMNLP 2026 per the arXiv comments. The paper says the benchmark is released, but gives no link.

Finding.

  • Setup:
  • 1,139 synthetic trajectories across 13 risk sub-categories and 496 tools.
  • Each trajectory has two labelled turns: the Earliest-Signal turn and the Trigger turn.
  • The monitor reads the history turn by turn and must continue or interrupt, and name the risk.
  • Across 16 LLMs:
  • The best "Perfect" score (interrupts inside the window with the correct category) is 40.74% (GPT-4o); the mean is 28.22%.
  • Failures are dominated by interrupting too early: up to 64.27% of trajectories for Gemini-2.5-Pro, while late interruption is ≤1.32% for every model.
  • With hazard keywords neutralized, many models appear to react to words like "transfer" or "payment" rather than to the risk itself.

Caveats:

  • All data is synthetic (DeepSeek-R1).
  • GPT-4o both annotated the ground truth and ranks first.
  • There are no fully benign control trajectories, so false alarms on safe runs are never measured.

TL;DR for BQAA: PASTABench gives a ready scoring scheme for any LLM monitor replayed turn by turn over logged event sequences: early / in-window / late, plus the right category. Before BQAA ships proactive alerting, false-alarm rates must be measured on benign traces. The paper itself shows this is exactly where judges fail.

5. NEW rank: arXiv 2609.27954: When Accuracy Gaps Fail to Certify — Auditing Cross-Domain Recalibration of LLM Judges

Who / what:

  • Afrin (KIIT) and Shihab (Iowa State); cs.LG; no venue; code "will be" released.

Finding.

  • Setup: 13 judges (1–9B open models plus Claude Sonnet 4.5), 8 domains, 1,176 predeclared transfers.
  • The gap is a weak signal. The source-to-target accuracy gap barely predicts calibration harm: leak-free r = 0.25, CI [−0.09, 0.55]. On the second answer generator it falls to r = 0.09.
  • Target labels beat source fitting. Spending 16 target-domain labels on temperature scaling gives ΔBrier −0.171 with a 9% harm rate. Source-fitted Platt gives −0.052 with 34% harm. EM label-shift makes things worse on average.
  • What does predict harm is only the raw error measured on the target probe, and that replicates on the second generator.
  • The certificate is valid but powerless: it has 0.128 power even at 1,024 labels.

Caveats: small generators, 40 items per domain, verbal-confidence parse failures of up to 20.6%, and one frontier judge.

TL;DR for BQAA: if BQAA stores judge scores for agent evals, an accuracy-parity dashboard does not show that a judge transfers to a new agent or domain. The paper's recommendations:

  • log raw judge scores and parse failures
  • key calibration by domain
  • budget a ~16-item labeled probe for each new agent/task

6. NEW rank: arXiv 2609.27263: Specifying and Maintaining Agentic Workflows — An Empirical Study of GitHub Agentic Workflows

Who / what:

  • Khelifi, Oukhay, Ouni and Sayagh (ÉTS), with Saied (Laval); cs.SE.
  • Data: https://github.com/stilab-ets/ghaw.

Finding.

  • Corpus: 1,248 gh-aw Markdown specs from 276 repos, with 7,446 commits.
  • Specs are substantial: the median body is 556.5 words.
  • Specs keep changing: 78.2% are still edited in month 4. Changes split into 44.8% frontmatter only, 37.8% body only and 17.3% both.
  • Specs are copied: 29.6% of projects reference another repo's spec.
  • What specs declare (from the 42-label taxonomy):
  • Task, Output, Constraint and Process appear in over 93% of specs.
  • Resource Budget: 38.2%. Cross-Run Memory: 18.1%.
  • Prompt-injection defence: 9.4%.
  • An LLM (one-shot Gemini 3.1 Pro) applies the taxonomy at F1 0.818 and κ 0.715.

Caveats:

  • Single-run model rankings.
  • The study does not measure whether instructions change execution outcomes.

TL;DR for BQAA: recurring agents drift because their specs are edited constantly and copied across repos. Stamp an instruction/spec version hash on every run so behaviour can be compared before and after an edit. The taxonomy gives fleet-level tags (declares a budget? declares injection defence?) that can be joined to observed behaviour.
