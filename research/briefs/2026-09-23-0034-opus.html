1. NEW rank: Langfuse v4.42.0: decision-model evaluators (TypeSafe Jev) are released and available to every project, with three gallery templates; trace review and annotation are embedded beside traces; default pricing for Opus 5.5 and GPT-6 Sol/Luna

What shipped (I read the release list and the full bodies of #17733, #17778 and #17797):

  • A new evaluator type, DECISION_MODEL (#17733). One evaluator is one JSON state + N typed questions = N named scores from one Jev call.
  • Question types:
    • choice (2–255 options) becomes a CATEGORICAL score;
    • score (2–10 ordered levels) becomes a NUMERIC expected level;
    • noul (yes/no) becomes a NUMERIC P(true).
  • Certainty never changes the score value. probabilities, confidence, legend, questionId, type and the resolved model go into metadata.typesafe on every score. The comment holds a one-line summary (e.g. ready (p=0.91); confidence 0.82; runner-up needs_revision (0.09)), since Jev returns no rationale.
  • Execution: runs on the LLM-as-judge queue through @ai-sdk/typesafe-ai + experimental_evaluate (so the AI SDK decision-call shape carded at 1834 is now inside Langfuse's worker). It writes one execution trace (GENERATION span) that every score links to.
  • Cost and errors: a default Jev price row ($0.042 per M input tokens, output free) costs these generations at ingestion. Provider 429s are retried, and auth failures pause the evaluator.
  • The feature flag is removed (#17797). Decision-model evaluators are now offered in every project, not only to admins or flagged orgs. Labels still read "(experimental)". TypeSafe connections are kept out of playground and judge model pickers on purpose.
  • Gallery templates (#17778):
  • Assign Input Topic (Choice). It takes the "Recommended" slot from the LLM-judge version.
  • Flag Out-of-Scope Request (Yes/no).
  • Rate Customer Frustration (Score, 4 levels).
  • In the same release:
  • Review and annotation:
    • comments and annotation embedded beside traces and sessions (#17745);
    • unified score editing and review state (#17740);
    • batch-mapping validation for decision models (#17785).
  • Ingestion and IO:
    • OTel event processing extracted in the worker (#17736);
    • the normalized IO parser is GA in the single-trace UI (#17729);
    • the experiment attribute is read from the experiment root span (#17473).
  • Pricing: default pricing for Claude Opus 5.5 and GPT-6 Sol/Luna (#17802).

Why it's a rank:

  • Langfuse is the most widely self-hosted OSS trace and eval store. This release makes Jev-as-judge a default gallery option in self-hosted deployments, not a hosted-vendor feature.
  • It is also the first vendor to state a score storage contract for decision models: the value is fixed by type, and certainty sits in namespaced metadata.
  • Honest caveats:
  • The PR's own verification skipped a live TypeSafe call (no key in CI), so result-panel mapping was tested against fixtures.
  • Decision-model evaluators are hidden from the public API and MCP (they cannot be listed or fetched there). Programmatic export of the evaluator definitions is limited for now, although the scores they produce are ordinary scores.

TL;DR for BQAA:

  1. Langfuse puts probabilities in score metadata, not in the value. That is the pattern BQAA should expect when it ingests or federates third-party eval results. Plan a typed judge_probabilities / judge_confidence / judge_model_resolved projection, not a JSON blob. Academy ranks 2 and 8 explain why those columns matter.
  2. "One call, N scores, one linked execution trace" is a clean join shape. BQAA's evaluation events should carry a judge_call_id shared by all scores from one decision call, so cost and latency are not counted N times.
  3. Langfuse's LLM-as-judge queue now runs a non-generative model. If BQAA or ADK adds a hosted judge step, reserve a distinct evaluator type for decision models rather than overloading the LLM-judge path. That is the same conclusion as the 1834 AI SDK card, now confirmed by a second vendor.

1. NEW rank: arXiv:2609.25938 — Certified Against Which Oracle? Execution Labels Set the Reported Risk of Conformal Abstention for Text-to-SQL (Liu, Qiao, Zhang, Chen — Xinqiao Hospital, Army Medical University; v1, Sep 22 2026; 34 pp)

What it does:

  • Setup: a preregistered 2×2 intervention on Spider-Realistic (508 questions). Four SQL-specialist checkpoints (Kwai-AutoSQL-32B/14B, OmniSQL-32B, XiYanSQL-32B), 50 samples per question (304,800 generations), 3 seeds, 200 splits.
  • The abstainer: consistency across execution-equivalence classes, thresholded by split conformal risk control at α=0.10.
  • What is swapped: where the grouping and the correctness labels come from, either the single shipped DB or the distilled multi-instance test suite.

Findings:

  • Switching the label oracle alone moves the certificate's real risk up by 2.73–10.23 points above what it reports. For example, Kwai-32B reports 0.098 and carries 0.200 under the suite (Table 2).
  • Neither oracle matches experts. On 1,028 blind expert-labelled answers, a certificate nominally at 0.10 carries 20.0 (XiYan) and 17.2 (Kwai) points of risk (Table A11). The strict oracle errs both ways: only 26–35% of its rejections are real semantic errors.
  • About 17.5% [12.2, 22.8] of reference SQL queries are defective (blind expert audit of flagged vs control questions).
  • Scores always look better under their own oracle. Each consistency score looks better under the oracle that built its clusters in 16/16 cases. Under expert labels, the claimed AUROC gain holds for Kwai (+6.96, p=0.004) and not for XiYan (+1.53, p=0.275; suite labels had said +8.3).

Caveats:

  • One benchmark family (SQLite/Spider), Qwen-lineage models only.
  • Expert labels cover 2 models at 1 seed.
  • AI-reviewer census from a single model family.
  • The endpoint was chosen after an earlier registration missed its criterion (disclosed).
  • Code is public (github.com/yahiko-l/text-to-sql-oracle-certificates); the data is not.

TL;DR for BQAA:

  1. This bears directly on BigQuery conversational analytics. Any "the agent abstains when unsure, risk ≤ X%" claim is a claim about a label oracle. Every correctness label BQAA stores for a text-to-SQL eval should carry label_oracle (single DB / multi-instance / expert / LLM judge / user feedback). Without it, a risk number cannot be read.
  2. Don't grade a confidence score with labels from the executions that built it. Keep one independent label source (expert or held-out instances) for calibration checks.
  3. Cheap reference-SQL lint catches a lot: empty result on its own DB, ordering or comparison on a text column, joins with no ON clause, case-sensitive literals. Run it before trusting any golden set.

2. NEW rank: arXiv:2609.26707 — Optimal Sequential Annotations for Off-Policy Evaluation (Chae, Nwankwo, Qin, Zhou — USC, UC Berkeley, UW; v1, Sep 22 2026; 52 pp, stat.ME)

What it does:

  • The problem: a cheap judge labels every step of a multi-step trace, and expert gold labels are bought for a sample. The paper treats this as off-policy evaluation with missing rewards and builds a doubly-robust estimator with stage-wise inverse-probability-weighted corrections.
  • Theory: it is unbiased, with a variance decomposition and asymptotic normality both non-adaptive and batch-adaptive.
  • The key result (Thm 1): the optimal probability of expert-labelling a step is proportional to the conditional standard deviation of that step's contribution. Labelling is forward-monotone: you can only label step 2 if step 1 was labelled.
  • Uncertainty signal: it can be disagreement among several cheap (silver) judges, which costs no gold labels.

Results:

  • Simulation: RMSE falls 37–40% at a 20% budget, and CI coverage is 0.92 vs 0.83 for random sampling.
  • Homelessness-services casenotes (777 clients, 180k notes): RMSE falls 17–68% depending on task and budget.
  • LMArena (21,685 sessions, T=2): 55–62% lower RMSE, but only under the equal-exposure target policy. Under the tilt ×1.5 policy it is only ~11–21% (Table 1). The abstract doesn't make this distinction.

Caveats:

  • The casenote "ground truth" is itself silver labels from a fine-tuned LLM.
  • The simulator figures disagree between sections (33–51% vs 37–60%).
  • The implementation differs from the theory (cross-fitted variances).
  • The LMArena intervals come with no coverage guarantee. Only T=2 is tested.
  • No code released.

TL;DR for BQAA:

  1. This is the statistics behind "Jev on everything, humans on a sample." It only works if each judged row stores annotation_prob, the probability it was selected for human review, next to judge_label, judge_prob and nullable gold_label. Without the selection probability, no debiased estimate is possible afterwards.
  2. Sample human review in proportion to judge uncertainty, using disagreement among cheap judges or Jev's own probability spread, not uniformly. That is a concrete default for a BQAA review-queue feature.
  3. Log the route and its propensity on each span, i.e. which model or route was taken and with what probability. LiteLLM's Jev router (Industry rank 2) now produces exactly those, which makes "what if we routed differently" estimable from logs.

3. NEW rank: arXiv:2609.26779 — CliffCompaction: Cost-Efficient Compaction for Long-Horizon Coding Agents (Nguyen, Cho, Dettmers — Carnegie Mellon; Chen — Bosch Center for AI; v1, Sep 22 2026; 25 pp)

How it works: rule-based compaction with no extra LLM call. When context crosses budget B, it:

  • drops tool results over 500 characters,
  • shrinks tool calls to a 150-character signature,
  • trims thoughts to 300 characters,
  • keeps the system prompt, the task and the last K turns verbatim.

The key rule is "never compact a compaction": the previous compacted block is discarded, not nested. The prompt cache therefore stays valid between compaction events, which gives the context curve its "cliff" shape.

Results:

  • Terminal-Bench 2.0 (Table 2):
  • Kimi K2.6 at 16K scores 61.42% vs 59.16% with full context and 55.45% with native summarization, at $0.19 vs $0.40 per task.
  • GLM 5.1 at 16K: 54.33% vs 49.83%.
  • Inside Claude Code (TB 2.1, GLM 5.3 Flash at about 45K): 76.69% vs 70.97% for Claude Code's own auto-compaction.
  • Test-time scaling: three compacted rollouts plus the authors' SGV selector reach 69.7% for $58, i.e. +10.5 points at 1.9× cost. Uncompacted is +4.8 at 3.0×.
  • KernelBench L3: 3.58× speedup vs 1.30× without compaction. Without it, 98% of runs hit the 256K window at a median of 99 steps.
  • Where the context goes (Table 7): tool results 56.0%, tool calls 28.0%, thoughts 13.6%, system/task 2.4%. Cache reads are 78% of the uncompacted bill and fall 80%.

Caveats:

  • Headline costs assume "perfect caching." Metered costs differ (Table 8): GLM cache-hit rates run 47–91%, and Kimi at 8K on SWE-bench is +1%.
  • The number of seeds is never stated.
  • On SWE-bench it is slightly worse than full context (73.87 → 71.87).
  • The SGV selector is trained on the same 89 Terminal-Bench tasks (the authors argue there is no leakage).
  • Comparisons to frontier models mix sources.
  • Code: github.com/nguyenvuthientrang/cliffcompaction.

TL;DR for BQAA:

  1. Compaction should be a first-class event: tokens before and after, method, and whether it invalidated the cache. The paper itself infers compaction from a drop in prompt length between calls. BQAA can do the same in SQL from per-call prompt_tokens/cached_tokens, today, for any agent.
  2. Split cost into cache-read, uncached prefill and output, and attribute context by component (tool_result / tool_call / thought). Cache reads, at 78% of spend, are the lever that matters, and they are invisible in a single total_tokens column.
  3. Best-of-k selection is possible from event-row features alone: step count, tool-call count, "marked complete", and agreement between rollouts. This is a concrete demo of analytics feeding back into agent quality.

4. NEW rank (qualified): arXiv:2609.25804 — The Tasteful Agent: Measuring and Improving Taste in Long-Horizon Tasks (Pan et al. — City University of Hong Kong + Microsoft; v1, Sep 22 2026; 33 pp)

What it does: Taste-Bench is 502 "decision forks" mined automatically from existing agent traces.

  • Fork types:
  • "Parallel" forks: a passing and a failing attempt at the same task, aligned at the step where they diverge.
  • "Detour" forks: a single run that commits to a direction, hits an observed failure, then recovers.
  • Sources: 2,677 SWE-bench Pro rollouts and 1,132 runs from METR's MALT transcripts. 10.8% of 4,657 candidate forks survive filtering.
  • Human check: 98.8% agreement with the mined label (κ=0.973).

Results:

  • The best model scores 59.7% (GPT-5.6 Sol), where chance is 25% (a question counts only if answered correctly in both orders).
  • Accuracy falls from 62.3% to 21.0% when the deciding evidence arrives later in the run. More reasoning effort doesn't help.
  • A distilled Qwen3.6-27B advisor lifts held-out SWE-bench Pro from 14.6% to 33.7% (oracle advice gives 39.0%).

Caveats:

  • The end-to-end test is n=41, and the averaging behind 33.7% is not stated.
  • The advice is mined from earlier runs on the same tasks.
  • The candidate wording was written by the top-ranked model.
  • Time-horizon labels come from a single judge.
  • Code and data are released (github.com/wbopan/tastebench; HF wenbopan/taste-bench).

TL;DR for BQAA:

  1. Multiple attempts at the same task with pass/fail outcomes can be mined into labelled decision points with no annotation. Keep task_id joinable across run_ids and keep outcomes on runs.
  2. Store the exit code or error on every tool result. Then "commit → wall → recovery" detours can be found with SQL.
  3. Consider a "time-to-evidence" metric: steps between a decision and the observation that confirms or refutes it. Late-evidence decisions are where models are near chance.

5. NEW rank (qualified): arXiv:2609.26760 — Grow the Harness, Not the Context: From Strategy-Free Scaffolds to Reusable Specialist Agents (Li, Li, Zhao, Ye, Li, Gao — SIAT-CAS; Xu — Univ. of Macau; v1, Sep 22 2026; 16 pp)

What it does:

  • Starting point: an empty harness (h0 returns nothing), with the model and tools held fixed. Only the harness code is learned.
  • Tracing: each run records a function-level execution DAG with harness-function, LLM and tool calls, each carrying inputs, outputs, errors, parent and duration.
  • Repair loop: an optimizer fixes a window of K failures together, and may only edit functions that appear in the failure traces. A 50-task held-out gate rolls back any regression.

Results:

  • Best success in 5 of 6 settings on BrowseComp-Plus and WebArena-Verified, with 76–92% fewer LLM calls and 74–99% lower cost than tool-calling. For example, BrowseComp-Plus with gpt-oss-120b: 49.3 vs 40.0, at $0.87 vs $6.70.
  • WebArena success holds at ~45% down to a 4B model, where tool-calling falls to 6.7%.
  • Ablation: removing function-level trace guidance halves success (36.0 → 18.0).

Caveats:

  • 50-task test sets with ±11–13 pp CIs that overlap baselines in several cells.
  • Single-run ablations.
  • Optimizer cost is excluded from the cost figures.
  • Site-specific resolvers raise overfitting risk.
  • No code.

TL;DR for BQAA:

  1. Span trees should include harness-function spans, not only LLM and tool spans. The set of functions touched in a failed trace is what the optimizer edits.
  2. Record harness_version and gate outcomes (accepted or rolled back) per run, for regression detection across versions.
  3. Report cost per successful task, split into online and offline-optimizer cost.

6. NEW rank (qualified): arXiv:2609.25913 — When Does Execution Provenance Help Agent Memory Retrieval? (Wang, Ju, Zhang, Sun et al. — USQ, SUSTech, Nanjing Univ., Norve Labs; v1, Sep 22 2026; 14 pp; header claims WSDM 2027)

What it does:

  • Reframes agent-memory retrieval as "budgeted evidence completion": does all the gold evidence fit under a B-token budget?
  • Provenance units: chunks aligned to tool-argument and tool-output fields.
  • Graph layer: a zero-initialised residual R-GCN over typed provenance edges on top of a frozen dense retriever.

Results:

  • Aligning chunks to tool-call fields beats 512-token windows by +19.07 Full-Support@2048 (53.71 → 72.78). It is still +11.96 over an oracle that picks the best flat chunk size.
  • The graph layer adds +4.55 (CI [2.98, 6.18]), almost all on multi-event questions (+11.83), at +20 ms latency.
  • Where the graph signal comes from: most of it is the lexical feeds edge, i.e. a path, ID or hash from an earlier output reappearing in a later argument. Artifact I/O edges add nothing detectable.

Caveats:

  • Synthetic OS-agent traces (ISETrace, 23k trajectories) with LLM-written queries.
  • The audit checked model judgments rather than re-annotating blind.
  • The end-to-end QA gain is borderline (CI [0.00, 12.10]).
  • Code and data are released.

TL;DR for BQAA:

  1. Store span addresses (event_id + JSON path + offsets) and tool_call → tool_output links as columns.
  2. An exact-match value-reuse edge (IDs, paths or hashes flowing from one output into a later argument) is cheap to compute in SQL and carries most of the graph benefit.
  3. Measure agent-memory quality as "complete evidence within budget," not recall@k.

7. NEW rank (qualified): arXiv:2609.26457 — Recursive self-improvement of AI research agents (AIDE²) (Srikanth, Zhao, Xu, Wu, Jiang — Weco AI; v1, Sep 22 2026; 28 pp)

What it does:

  • Two loops: an outer agent (Opus 4.7) rewrites the code of an inner AI-research agent (Gemini 3 Flash). A rewrite is accepted only if the private held-out grade improves.

Results:

  • The featured run lasted 8 days, generated 100 candidates and accepted 7. The grade rose from 0.703 to 0.778, vs 0.749 for Weco's human-built agent.
  • Held-out benchmarks: ALE-Bench 1790 vs 1511; WeatherBench 2 0.793 vs 0.404.
  • Reward-hacking rate on KernelBench fell from 55% to 32%.
  • About a quarter of rejected rewrites beat the incumbent on the public score but lost on the private one.
  • The main discovered changes: a bandit over drafting strategies, a bounded history summary (prompts ~50× smaller), and failure memory.

Caveats:

  • One featured run; the two repeat runs accepted only 2 and 4 rewrites.
  • Small held-out sets (WeatherBench 2 is one task).
  • Gains are not monotone (AIDE₄₇ beats AIDE₈₅ on two benchmarks).
  • The baseline is the authors' own agent. No code; total run cost not stated.

TL;DR for BQAA:

  1. Self-improving harnesses need a lineage table: candidate, parent, diff, public score, private score, Δ, accepted.
  2. Keep public and held-out scores as separate fields. The gap is a direct reward-hacking signal.
  3. Prompt size per call over a run, bug rate and repeated error signatures predict context-overflow deaths. They are cheap standard metrics.

8. NEW rank (qualified; position paper): arXiv:2609.26489 — Calibration as a First-Class Criterion in LLM Evaluation (Sanz-Guerrero, von der Wense — JGU Mainz, CU Boulder; v1, Sep 22 2026; 8 pp)

What it argues: a short position paper with no experiments.

  • Nobody reports calibration. An informal check of recent model reports (GPT-5.5, Claude Sonnet 4.6, Gemini 3.5 Flash, and open models) finds none reporting it.
  • Miscalibrated judges bias the pipeline: "If the judge is miscalibrated, the resulting rankings, win rates, and reported improvements are biased."
  • Metric choice matters. ECE depends on binning; Brier is a proper scoring rule; AUROC is not a calibration measure (shifting every confidence by the same amount leaves AUROC unchanged).
  • The recipe needs two fields per example: confidence and correctness.

Why rank it at all: it is thin as evidence. It is ranked, qualified, because this week five-plus vendors started shipping probability-emitting judges (tonight: Langfuse metadata.typesafe, LiteLLM routing probabilities), and none of them reports calibration against ground truth. The 1834 JEV-as-a-Judge paper measured judges at 0.90–0.96 confidence while near chance on reference-free prose. This paper names that gap and gives the minimal fix.

TL;DR for BQAA:

  1. Store judge_confidence next to judge_label and any eventual ground-truth label. Then ECE, Brier and a reliability diagram are one SQL aggregate, a natural BQAA feature.
  2. Tag the confidence type (logprob / verbalized / decision-model probability). They are not interchangeable.
  3. Keep per-step confidence on agent spans, so calibration can be computed over whole traces.

9. NEW rank: arXiv:2609.26777 — SWE-Serve: Benchmarking Agentic Engineering For Production Inference Serving (Williams, Farris, Farris — NVIDIA; Jiao — NVIDIA + UC Berkeley; v1, Sep 22 2026; 43 pp)

What it does:

  • Tasks: 53 repository-grounded tasks from merged SGLang changes (12 CPU, 41 single-H100). Qualification: 53/53 reject the unchanged repo and accept the reference.
  • Scoring: hidden fail-to-pass and pass-to-pass tests. 19 tasks also carry 276 model-serving end-to-end tests.
  • Runs: 11 models, 31 model–effort configurations, 3 runs each.

Results:

  • The best configurations reach 75% pass@1 (Opus 5 max at $17.40 per task; GPT-5.6 Sol max at $12.26).
  • Four configurations tie at 64% with a 7.6× cost spread ($0.95–$7.24).
  • The E2E gap is the headline: on 19 tasks / 627 patches, removing E2E tests from scoring lifts the pass rate from 45.9% to 69.4% (+23.4 pp, CI 13.4–34.4). A matched control removing the same number of non-E2E tests adds only half as much.
  • Harness comparison: Codex scored 73.6% and Claude Code 69.8%, vs 75.5% for a bash-only scaffold.
  • Open-book pilot: agents retrieved the upstream solution on up to 32.1% of tasks.

Caveats:

  • One serving system.
  • 3 runs with normal-approximation CIs.
  • The E2E finding rests on 19 tasks.
  • Contamination is only mitigated by a canary string and closed-book runs.
  • Release promised, but no URL in the paper.

TL;DR for BQAA:

  1. Split agent outcomes into fail-to-pass, pass-to-pass (regression) and E2E tiers. One success bit hides about a third of production failures here.
  2. Cost per solved task separates configurations with equal pass rates, a BQAA view that needs only cost + outcome per run.
  3. Auditing trajectories for external fetches (solution retrieval) is a concrete trace-analytics use case.

10. NEW rank (qualified): arXiv:2609.25443 — ZeroGate: Trust-Preserving Fast Paths for Governed AI Agent Runtimes (Wang — Ond Holdings; single author, vendor; v1, Sep 21 2026; 47 pp)

What it does:

  • ActionPass: an issuer signs a short-lived, single-use approval for one exact action. At dispatch, a trusted adapter rebuilds the final action from the bytes actually sent.
  • One transaction: a local gate verifies the binding, then consumes the nonce, updates quota and writes an admission receipt in one SQLite transaction.
  • Four separate records: the paper insists on keeping request, grant, admission receipt and effect evidence distinct. Operator states are prepared / admitted / outcome-pending / effect-verified.

Results:

  • Semantic fixtures: 0/1,360 false allows. Ablations produce 80–1,300 false allows, e.g. 140 without action binding and 240 without freshness checks.
  • Azure cloud study: 4,800/4,800 attempts succeeded. p95 time to permission is ~10 ms vs 25–334 ms synchronous. But the full lifecycle is slower at every concurrency level (e.g. 4.26 s vs 53 ms at C=1). The author says it is "not a net speedup."

Caveats:

  • Single author, vendor-affiliated, not peer-reviewed.
  • All fixture labels written by the author.
  • One deployment; freshness and revocation distribution not implemented; nonce enforcement on a single host.
  • Artifact released (github.com/OndCo/Agent-Action-Boundary-Benchmark plus arXiv ancillary).

TL;DR for BQAA:

  1. Log approval, admission and effect as separate event types, joined by pass hash / action fingerprint. An "approved" or "admitted" row must never read as "completed."
  2. Useful anomaly checks: executed payload hash ≠ approved hash, reused nonce, admission against a stale policy epoch.
  3. Show lifecycle latency next to gate latency. A p95-to-dispatch dashboard alone would hide the 1.5–4.2 s cost measured here.
