1. LangSmith Python SDK v0.12.0 — sampling goes deterministic, anonymization goes fail-closed (Sep 1)

Shipped 07:35 PT this morning, so it technically predates the 0849 brief but wasn't on the changelog page that pass checked (the SDK releases on GitHub, and the changelog page still shows the Aug 24–31 rollup). Three breaking changes: trace sampling is now deterministic ("make trace sampling deterministic"), per-function anonymization now fails closed — if a custom anonymization callable errors, the SDK raises instead of silently shipping unredacted data — and the HTTP layer moved to httpx2 with httpx fallback. Plus replica-write compression and single-frame serialization of identical replicas.

The first two are the story. Deterministic sampling means a sampled trace set is reproducible — you can rerun analytics over "the same 10%" and get the same rows, which is what makes sampled telemetry citable. Fail-closed anonymization is a vendor putting in writing that a redaction failure is worse than a telemetry gap. The wrong belief to kill: sampling and redaction are capture-time conveniences with no analytics contract. Both are now breaking-change-worthy API surface at the biggest LangChain-side vendor. Judgment: peer, and the strongest single release in this pack.

TL;DR for BQAA. This is row 3's argument made by someone else: redaction behavior is a forensics statement, and the producer contract should say what happens on redaction failure (drop the event? drop the field? flag it in telemetry_factors?). Worth one explicit line in the producer contract doc.

2. Phoenix: session-level PII evaluator (Sep 1) + PXI agent workflows (Aug 25) + persistent agent sessions (Aug 11)

Three Phoenix moves the allowlist under-covered. Today: arize-phoenix-evals 3.6.0 adds a session-level pii_detection evaluator — PII checked across a whole session, not per span. Aug 25 (server 20.4.0): PXI, their in-product agent, can now run multi-step workflows across the Phoenix UI with approval gates for GraphQL changes, and a retrieval-relevance evaluator grades the combined result of each retrieval step regardless of source (vector search, tool call, SQL). Aug 11 (server 20.0.0): agent sessions are persistent server-side — browse, restore, rewind, branch, from browser or terminal interchangeably, with REST routes at /v1/agent_sessions and admin idle-deletion controls.

The pattern: session is becoming the unit of evaluation, storage, and management at Arize, not the span. The wrong belief to kill: PII detection is a span-payload scrubbing problem. A session-level evaluator exists because PII risk composes across turns — individually clean spans can leak in aggregate. Judgment: peer, coherent direction.

TL;DR for BQAA. Session-level PII is a SQL problem for us — an example query that aggregates payload fields per session_id and flags exposure would demo in an afternoon and reads well next to the redaction-mode story. Persistent-session management stays vendor territory; BigQuery tables already are the persistence.

3. Braintrust's three-week arc: Harbor (Aug 24) → MCP write tools (Aug 26) → SDK 0.36.0 (Sep 1)

Three connected releases. Harbor is a Python framework for sandboxed agent tasks — each task runs in an isolated Docker container, agents execute, verifiers score, everything lands in a job directory — and its Braintrust plugin syncs jobs into datasets and experiments, with trajectories in ATIF format and the API key held in the host process so agent code can't reach it. The MCP post ships write tools: coding agents can create evaluators and scorers, build datasets, run evals, configure monitors and alerts from the terminal — "move from investigating a problem to acting on what it finds." Today's SDK 0.36.0 closes the loop: Agno eval instrumentation and Harbor standard-verifier-output upload. (The source pack claimed redact_patterns in 0.36.0; the release page shows no such thing — dropped.)

The wrong belief to kill: eval platforms are dashboards humans click through. Braintrust is making the eval platform itself agent-operable — the agent files its own evals. Judgment: peer, and the MCP-write direction is the one to watch; it's where "observability as a tool surface for agents" gets real.

TL;DR for BQAA. BQAA's equivalent already exists structurally — agent_events is queryable by any agent with BigQuery MCP access, no bespoke write tools needed. That's a positioning line worth writing down: our "MCP integration" is BigQuery's, inherited for free.

4. Traccia — OTel control plane with runtime blocking (Product Hunt, ~Aug 27)

New entrant. OTel-native open-source SDK (Python and Node), framework-neutral, and the differentiator is runtime policy enforcement: govern() hard-blocks agents mid-execution — runaway cost, loops, data leaks — with the pitch "the only tool that enforces, not just observes." Also claims cost attribution across 2,500+ models that stays accurate at 10% trace sampling, and PII flagging before export. The wrong belief to kill: observability vendors will stay observers. The market is pulling toward enforcement. Judgment: early-stage, but the third "control layer" claim in this pack alone — it's a wave, not a startup quirk.

TL;DR for BQAA. Runtime guardrails stay do-not-start (observer stance, OBPE) — this validates that the lane exists and that we're deliberately not in it. One line for the positioning doc, nothing to build. Their sampled-cost-accuracy claim is the same problem our coverage/telemetry_factors fields address from the honest side: say what's missing rather than extrapolate.

5. Agnost AI — mine production conversations to discover evals (~Aug 25)

Launch pitch: read every production conversation across chat and voice agents, detect silent failures, drift, hallucinated links, user frustration; group them into recurring patterns tied to users and conversations; turn patterns into evals. Their core line is good: "evals test problems you already know about. You can't write an eval for something you haven't discovered yet." Claims 1M+ messages analyzed daily, integration in three lines or via OTel. The wrong belief to kill: the eval suite is the source of truth for quality. Dashboards show 200 OK while the agent confidently lies; discovery has to run on the raw conversations. Judgment: small but pointed at a real gap — eval discovery, upstream of eval execution.

TL;DR for BQAA. The raw material for this is exactly what agent_events holds. A "find recurring failure shapes you don't have a rubric for" example — even a simple clustering-by-error-text query — is a doc-example candidate, not roadmap.

6. Operata — one journey trace across AI and human agents (Aug 28)

Contact-center observability vendor extends to AI agents: a single customer-journey record spanning AI and human interactions, normalized metrics/traces/logs across voice AI, CCaaS, CRM, and CPaaS stacks, real-time visibility into AI-to-human handoffs, and governance evidence collection aimed at EU AI Act Article 50 (disclosure of AI interaction). The wrong belief to kill: the trace ends where the AI agent stops. In CX, the handoff to a human is part of the same session, and regulators care about exactly that boundary. Judgment: vertical, not a competitor — but the Article 50 framing is the first time this pack ties agent telemetry to a named regulatory article.

TL;DR for BQAA. "Handoff to human" is an event type worth checking against the schema — can a customer represent an AI→human transfer in agent_events today without contortions? If yes, one sentence in the docs; if no, note it for the producer contract.

7. Weave 0.53.6 / 0.53.7 — Claude Agent SDK tracing + PII helpers (Aug 13 / Aug 27)

Two releases the allowlist missed (dates confirmed via GitHub API). 0.53.6: Claude Agent SDK tracing including nested, background, and subagent spans; linking weave ops and evaluations to the agent spans that produced them; cost mapping for OpenAI cache tokens; new intent and failure-signature tables in the schema. 0.53.7: record which agent span invoked a call, PII detection and redaction helpers plus an agent PII policy field, and keeping eval rows that have no scores. The wrong belief to kill: Claude Agent SDK telemetry is a niche integration. W&B built first-class nested/subagent tracing for it, which says where their customers' agents run. Judgment: peer, quietly thorough — their span→eval linkage and failure-signature table rhyme with our fault-edge direction.

TL;DR for BQAA. Second data point (after Langfuse's cached-token columns at 0849) that cache-token cost accounting is table stakes — reinforces the 0849 action to verify what the ADK plugin emits for cached vs uncached tokens. Also: does anything exercise BQAA with Claude Agent SDK-shaped multi-producer traces? Worth knowing before a customer asks.

8. Datadog Patterns — clustering production behavior (Jun 9, still Preview)

Dated catch-up. Patterns clusters production LLM interactions into hierarchical topic groups without predefined categories, then attaches cost, latency, error rate, and evaluation coverage per cluster. The pitch: align quality infrastructure with the interactions users actually have, not synthetic test sets. Same gap as Agnost (item 5), from the incumbent side. The wrong belief to kill: you know your agent's workload taxonomy. Users "develop workflows the application was never designed to support." Judgment: Preview since June, so not urgent — but "eval coverage per behavior cluster" is a metric shape worth remembering.

TL;DR for BQAA. Pairs with item 5; same one-line implication. Per-cluster eval coverage is a view over agent_events joined to eval results — a future doc example, nothing more.

9. Grafana Agent Observability GA (Jul 30)

Dated catch-up: what launched as public preview in April went GA July 30. OTel-compatible, thin SDK, captures generations, conversations, tool usage, token and cost metrics; continuous output evaluation via LLM-as-judge, heuristics, or regex, wired to native alerting. The framing is "treat agents like the rest of your services." The wrong belief to kill: agent observability is a specialist-vendor category. It's now a GA checkbox at a general observability platform. Judgment: commoditization signal — the capture layer is table stakes; differentiation moves to analytics on the stored data, which is our ground.

TL;DR for BQAA. Strengthens the substrate story: when every platform captures, the question becomes where the data can be queried at warehouse scale — one sentence for positioning.

10. GitHub Copilot: per-agent activity in the metrics API (Aug 7) + per-model token breakdown (Aug 11)

Dated catch-up, one theme: GitHub is decomposing the usage black box. The metrics API adds totals_by_3rd_party_agent — per-agent agent_id, interaction counts, session counts — because "agent activity in your usage metrics was effectively a single bucket." The usage report adds per-model input, output, cache read, and cache write tokens beside the credits they consumed. The wrong belief to kill: usage accounting can stay aggregate. Buyers now expect attribution by agent and by model, with cache split out. Judgment: this is the demand side of the same cached-token contract Langfuse and Weave ship on the supply side.

TL;DR for BQAA. Per-producer, per-model, cache-split cost views over agent_events are exactly what enterprise admins are being trained to expect. Confirms the producer-id field earns its place (row 3); no new work beyond what 0849 already queued.

11. AWS Bedrock AgentCore — all agent telemetry in one per-agent log group (Jul 23)

Dated catch-up. AgentCore now lands traces, prompts, structured logs, and stdout in a single per-agent CloudWatch log group (/aws/bedrock-agentcore/runtimes/<agent_id>-<endpoint>), replacing the split between a shared spans group and per-resource event logs. Per-agent IAM and encryption; default for agents created after Jul 20. The wrong belief to kill: unifying telemetry destinations is a small plumbing fix. AWS is making "one queryable place per agent, with agent-granular access control" the default — the same bet BQAA makes with one table and row-level access. Judgment: convergent design from the largest cloud; useful validation, not competition on our analytics layer.

TL;DR for BQAA. One positioning sentence: AWS unified to a log group; BQAA unified to a warehouse table — same instinct, and only one of them takes SQL joins against business data.

12. Snowflake Cortex AI Gateway (Jul 28, public preview "soon")

Dated catch-up, and a naming correction: the press release says Cortex AI Gateway, not "Gateway 2." A centralized control layer: govern agent access to models, data, and 100+ MCP servers; end-to-end activity monitoring; unified consumption tracking with spending limits; quality/cost/latency routing. Supports third-party agents including Claude Code and Cursor, plus identity partnerships (Okta, SailPoint et al.) for task-scoped agent access. The wrong belief to kill: the warehouse rivals will compete on trace analytics. Snowflake is competing on gateway governance — enforcement again, like Traccia at 100× the size. Judgment: the closest strategic neighbor in this pack; watch whether monitoring data lands in queryable Snowflake tables, which would be the direct BQAA analog.

TL;DR for BQAA. No action now — press-release stage. Flag for a closer read when the preview docs exist: specifically whether agent activity is exposed as tables.

13. Microsoft Foundry — ROI for agents (private preview, ~Jul)

Dated catch-up; the techcommunity page wouldn't render, verified via Microsoft's devblogs and search excerpts. Foundry translates agent running cost into business value — task completion, time saved — against customer-defined value models, side by side in portal and API, with drill-down from low-ROI numbers into the underlying traces. Private preview, sign-up gated. The wrong belief to kill: agent analytics stops at cost and quality. Microsoft is building the layer above: cost versus modeled value, per agent version. Judgment: earliest-stage item in the pack, but the trace→ROI drill-down is the shape enterprise buyers will start asking every vendor about.

TL;DR for BQAA. ROI-per-agent is a join between agent_events cost fields and the customer's own business tables — an argument BigQuery wins by default. Keep as a talking point; build nothing.

14. Vercel "Is Agentic" — scoring sites for agent readiness (Aug 23)

Dated catch-up, adjacent rather than core. Free public tool scoring how readily agents can discover, access, use, and pay on a website — 118 checks from Ora across four layers (Discovery 20 pts, Access 30, Usability 40, Payments 10), reverse-engineered from real agent runs rather than authored opinion. The wrong belief to kill: agent failures on the open web are agent bugs. Often the site is the fault side — which is an environment-side fault-attribution claim, the mirror of our fault-edge story. Judgment: lowest direct relevance in the pack; kept because it's the only item scoring the environment instead of the agent.

TL;DR for BQAA. One line for the fault_side design note: the industry is starting to grade the environment's side of the edge, not just the agent's.
