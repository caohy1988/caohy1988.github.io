Progress — Langfuse 4.70.0 connects batch requests to evaluator traces and scores

Target catalog item id: langfuse-v4-61-0-v4-63-0-skills-gateway-keys-experiment-filters.

Primary: v4.70.0, stable release, October 24 12:54:58 UTC / 05:54:58 PT.

On installations with the events table enabled, manual batch evaluations propagate batch_action_id through the queue into evaluator execution metadata and associated scores. The released change covers LLM-as-judge, code and decision-model evaluators. It also makes the existing UI batch path enforce the organization's accessible-data window on the server: requested older observations can be excluded even when the submitted filter includes them. This changes both result attribution and the effective evaluation population. Released implementation and scope, service at the release tag.

The accompanying runBatchEvaluation MCP tool runs saved, observation-scoped evaluators against a filtered selection, with time bounds, sampling and a row limit. It returns an asynchronous batch action ID. The tool requires evaluationRule:CUD, is marked potentially expensive, and is approval-gated in the in-app agent. Both its registration and the service depend on LANGFUSE_MIGRATION_V4_ALLOW_PREVIEW_OPT_IN; the UI retains a separate evaluator-v2 preview check. This is a qualified capability in the released artifact, not a claim of universal hosted enablement. The explicitly unstable Topics endpoints receive no separate admission.

BQAA inference: store requested filters, effective time window, sampling, evaluator/version mapping and batch ID together. Join execution traces and scores to that ID, then reconcile selected, attempted, completed and scored counts. An accepted request is not evidence that every selected row finished. The new queue field is optional for rolling compatibility, so missing IDs on older jobs must remain missing rather than being synthesized. No retrospective backfill or production completeness was verified.

Progress — AI SDK 7.0.153 selects the final JSON answer while retaining response evidence

Target catalog item id: vercel-ai-sdk-7-0-113-tool-approval-replay-gemini-3-8-tts.

Primary: ai@7.0.153, stable, October 24 17:57:31 UTC / 10:57:31 PT; npm 17:57:40.777 UTC. The same release train shipped the OpenAI adapter 4.0.102 and Azure adapter 4.0.110; their npm distributions precede the core package by about a minute. This is one Progress update for the train.

For non-streaming Responses JSON output, commentary or repeated final answers could previously be concatenated into invalid JSON. The provider can now supply a separate structuredOutputText, selecting the last message marked final_answer. The SDK parses that selection while keeping the complete response text, content, annotations, conversation messages and usage available. This is material for failure analysis: an apparent model-output failure can originate in the SDK's answer-selection rule. Released change.

The inspected source and regression cases distinguish three situations: absent selection falls back to concatenated text; an explicitly empty or malformed selection still fails validation rather than borrowing an earlier valid answer; ordinary text output retains all text. These were source inspections, not tests run here. No streaming fix, universal-provider behavior or measured production error reduction is claimed.

BQAA inference: retain the raw response and selected answer as separate fields, alongside message phase, adapter/core versions and parse/validation outcome. A dashboard that reparses concatenated raw text can recreate the old false failure even after the application SDK is fixed. Compare parser-version cohorts before interpreting a success-rate change as improved agent capability.
