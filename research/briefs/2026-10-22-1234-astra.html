NEW — LangChain.js Core 1.3.0 changes the tool-call stream contract

Primary: @langchain/core 1.3.0, October 22, stable. GitHub: 17:57:19 UTC / 10:57:19 PT; npm: 18:04:49 UTC / 11:04:49 PT. Suggested id: langchain-core-1-3-0-tool-call-delta-stream-contract.

Tool arguments now arrive as incremental tool-call-delta slices instead of cumulative block-delta argument snapshots across the listed supported adapters. Google and Ollama retain complete snapshots; Anthropic mcp_tool_use remains a non-standard block using block-delta. Final assembled messages and .toolCalls are unchanged; raw-event consumers must migrate. Identity can arrive at block start or, when delayed, at block finish. Released emitter behavior and exceptions.

Upgrade clients first: the documented minimums are LangGraph SDK 1.12.6, React/Vue/Svelte/Angular clients 1.2.6, and Python langchain-core 1.6.13. Registry checks confirmed all were published October 21. Older clients mishandle the new events; pin JS core below 1.3.0 when postponing migration. Compatibility notice.

BQAA implication: event count is a transport measurement, not a count of completed tool operations. A consumer should retain the stream format and producer version, reconstruct each call, and tolerate late identity. Test mixed snapshot/delta producers and interrupted argument streams before comparing payload sizes or call counts across an upgrade. No measured production savings are claimed here.

Progress — Langfuse 4.68.0 exports score lineage and adds gateway completion evidence

Target catalog item id: langfuse-v4-61-0-v4-63-0-skills-gateway-keys-experiment-filters.

Primary: Langfuse v4.68.0, October 22, stable; 14:30:27 UTC / 07:30:27 PT. This extends the existing platform/gateway card, without repeating 4.65–4.66.

Blob exports gain separate, opt-in score metadata and provenance groups. Provenance includes author, configuration, queue, evaluator, evaluation-rule and execution-trace references. Existing exports retain their old selection; observation metadata does not implicitly enable score metadata. The released change warns that older workers/forms do not safely understand saved new groups, so enable them only after coordinating the relevant components. Correction scores remain outside this export. Export behavior and version-skew limits.

Gateway request logs and server spans now carry connection linkage; connection-close logs record socket-write progress and stalls, while execution logs expose output_complete at info level. Small connections without write problems can be filtered out. This helps distinguish provider truncation from gateway write stalls, but connection-level bytes do not prove that a particular response reached or was consumed by the end user. Released logging semantics.

BQAA implication: exported scores need enough lineage to join back to the judge and its execution. For delivery analysis, preserve separate provider-completion, connection-write and application-outcome signals; retain their different granularities. A further released legacy-ingestion restriction is controlled by an optional organization-creation cutoff. Its actual Cloud activation time was not verified and is not asserted here. Conditional ingestion behavior.

Progress — AI SDK 7.0.149 tightens approval execution and tool-choice enforcement

Target catalog item id: vercel-ai-sdk-7-0-113-tool-approval-replay-gemini-3-8-tts.

Primary: ai 7.0.149, October 22, stable; npm 18:53:25 UTC / 11:53:25 PT. Treat the simultaneous major-line releases as one family.

Only the first approval response for a tool call is processed, preventing repeated or conflicting responses from causing duplicate execution or an execute-and-deny combination. The same fix is in 6.0.313; 5.0.280 does not claim it. Version 7.0.149 also enforces toolChoice: 'none' before local execution and withholds streamed tool parts that could otherwise reach client-side execution. 7.x release.

The release adds an interrupted finish reason and handling that preserves partial output while stopping continuation and tool execution. Provider detection/emission is explicitly separate work. Do not infer automatic truncation detection across current providers. The expanded public type can also break exhaustive TypeScript switches despite the patch version. Compatibility notice.

BQAA implication: record the approval response actually consumed and the resulting execution once, while retaining duplicate/conflicting inputs for diagnosis. Distinguish incomplete output from an ordinary error and from success. A missing error event cannot establish successful completion.

Progress — Opik 2.2.114–117 changes evaluator authoring and repairs large trace writes

Target catalog item id: opik-2-2-99-triggered-alerts-aws-eventbridge-mcp-instructions-deferred-tools-server-breakdown-row.

Primary: 2.2.114, 2.2.115, 2.2.116, 2.2.117, October 22, stable. PyPI first uploads: 07:35:06, 09:04:06, 12:28:29 and 16:16:20 UTC, respectively. All are in-window and unyanked at lookup. Version 2.2.114 was correctly deferred by the prior slot.

The online evaluation editor is a substantive change beyond panel layout: a single prompt with inline variables, task-completion defaults by scope, Boolean templates, a separate decision-model form with yes/no questions, and prompt attachments. Saving an older multi-message judge combines its messages; old rules remain unchanged until saved. Custom Python mappings have an explicit conversion action. Released editor and migration behavior, shipped in 2.2.114.

Version 2.2.116 fixes a trace/span write inconsistency: large payloads accepted by batch creation could fail during later writes because SQL literals exceeded max_query_size. Payload streaming bypasses that parser limit while retaining server-side merge behavior. The implementation reports single-node tests; it does not establish unrestricted payload sizes or multi-replica behavior. Released write-path fix.

BQAA implication: treat a saved judge conversion as a potentially meaningful evaluation-definition change. Preserve the prompt, input mapping, score type and version when comparing old and new evaluations. Also test create, update and update-before-create paths independently: ingest acceptance is insufficient evidence that a large trace remains maintainable. The rest of this train stays supporting maintenance rather than additional cards.

Progress — Agno 3.1.9 makes published MCP tools runnable from an HTTP inspection surface

Target catalog item id: agno-3-1-0-agentos-rbac-audit-log-per-user-filesystem-mcp-tools-opt-in.

Primary: Agno v3.1.9, October 22, stable; GitHub 16:50:03 UTC / 09:50:03 PT; PyPI 16:51:09 UTC. This is separate from the already-covered 3.1.8 checkpoint changes.

The new HTTP runner executes tools published on the AgentOS Server Card, allowing operator testing without an MCP client. It can be disabled. The released implementation pins execution to the published tool version/schema and applies the relevant authentication and per-tool scope gates. Runner contract.

Its result contract is analytically useful: a tool that ran and failed returns HTTP 200 with isError=true; malformed/invalid requests and unpublished tools return 4xx; timeout returns 504 with cancellation handling. A 200 therefore does not establish tool success, and timeout handling should not be generalized into proof that an external side effect was rolled back. Status and cancellation semantics.

BQAA implication: record invocation surface, published tool/schema version, admission outcome, execution outcome and cancellation separately. Include inspection-originated calls in the correct cohort rather than silently counting them as autonomous agent work.

Progress — Letta Code 0.34.21 preserves MCP originator boundaries across queued work

Target catalog item id: letta-code-v0-34-12-13-claude-codex-subagents-connected-computer-live-tool-progress-opencode-backup-wake.

Primary: Letta Code v0.34.21, October 22, stable; npm 18:57:08 UTC / 11:57:08 PT; GitHub 19:02:59 UTC. The release's comparison starts at 0.34.19; only the newly shipped originator work is advanced here.

Queued inputs with incompatible MCP originator authority stay in separate listener turns and approval continuations. Explicitly tokenless inputs cannot borrow a token later stored for the same super run. Recovery sends its existing approval results before resuming queued work separately. Queue/continuation boundary.

A companion change advertises the cooperating client's isolation behavior alongside attributed requests. That marker is compatibility information, not identity proof: the server must verify authority. These client changes do not themselves activate restricted connections or isolate shared conversation history. Request marker and limits.

BQAA implication: track originator scope through enqueue, continuation, recovery and tool execution. Preserve unknown authority as unknown, and keep secrets out of analytical records. The release supports a narrower client-boundary claim; it does not establish end-to-end multi-user isolation.
