What the endpoint does (guide + SDK types src/openai/types/decision*.py at tag v3.26.0, PR #4033, +3,393/−51): - Input: model, input and an ordered list of questions, plus an optional safety_identifier. - input is either a string or user messages only, containing input_text and inline base64 input_image parts. - Hosted image URLs and file IDs are not supported, and a request can carry at most 128 image parts. - Question types: predicate (instructions), choice (typed choices, where a string and a Boolean with the same text are distinct values) and score (labelled levels). - Answers come back in question order: - predicate → probability; - choice → choice, confidence and a probabilities[] array; - score → score (probability-weighted level index), confidence and probabilities[] (label, value, probability); - any question can instead return {type: "refusal", name}. The SDK docstring adds that "the host may decline one question without disclosing its refusal score". - usage has input_tokens (with cache_write_tokens/cached_tokens), output_tokens (with reasoning_tokens) and total_tokens. Billing is input-only per the guide. - Positioning: OpenAI claims typed answers "10x faster than the Responses API". The guide says to use Structured Outputs instead when you need to generate your own JSON object. ZDR and HIPAA are supported for eligible customers, and GA is "expected in the coming weeks". The guide notes regional premiums and long-context multipliers apply.

BQAA read. A decision call is a new event class that analytics must not fold into generations: - the request carries N ordered questions; - the response carries N typed answers, each with its own confidence and probability distribution, and any of them may be a refusal; - output tokens are reported but unbilled, so cost attribution changes for this class; - the refusal deliberately withholds its score, so a refusal is a categorical outcome with no confidence attached.

The schema should key on (request, question index or name) and keep answer type, confidence, the probability vector and refusal as first-class fields. Otherwise "decision accuracy versus confidence" and per-question cost analysis cannot be computed.

NEW — 2610.08364 — Transect: Retaining Observability for Long-Horizon LLM Agent Evaluations — one turn axis aligns token use, sub-agent spans, compactions, operator messages and judged phase labels with per-judgment provenance; in one 13M-token AI R&D run, 89% of tokens were sub-agent work, self-review plus write-up took ~10.7M of 14.5M new-work tokens, and only 2 of 580 orchestrator outputs were labelled Hypothesising

Full PDF read (27 pp., main text §1–4 and Appendix A.1–A.5 read in full). Authors: UK AI Security Institute + Meridian Labs. Submitted 6 Oct.

Method (§2, App. A.1–A.2): - An open-source package built on Inspect Scout. It ingests Inspect .eval logs and OpenClaw JSONL exports, places every model output (orchestrator and sub-agents in separate lanes) on a shared turn index, and runs two kinds of scanner: - structural scanners (token_timeline, context_flush, human_intervention, eval_setup) that read recorded facts without model calls; - judged scanners (decision_phases over a closed, pre-registered vocabulary; subagent_classification from delegation instructions). - Judging regimes: solo, k-rolls or a multi-model cohort, with a verifier re-checking low-confidence or low-agreement labels (triggers below 0.6; label changed only at verifier confidence ≥0.6; 5% random spot-checks). - Provenance: every judgment's prompt, inputs, member votes and verifier changes are stored. - Token accounting (App. A.2): four derived per-turn measures, context, new_work, billable (excludes cache reads) and turn_total, assuming Inspect's convention (input excludes cache reads/writes; output includes reasoning). Importers with other conventions must normalize first. - Output tables (Table 3) have explicit row units and join keys (turn, phase_index, agent_span_id, model, roll). - Audit warnings (App. A.5) fire on: k-roll agreement <0.80 or >0.95; cohort Krippendorff α <0.66 (red); verifier-change rate ≥0.20; any applied spot-check change (red); ≥25% missing classifications (red).

Case study (§3; one CRUX shadow-eval epoch, Claude Opus 4.7 on OpenClaw): - Run profile: 554 orchestrator tool calls, 79 sub-agent deployments, 57 operator messages, 8 compactions, 13M tokens (89% delegated). - Phase labels (k=5 rolls): 474/580 outputs (81.7%) unanimous on research activity and 476 (82.1%) on paper-specific labels. Hypothesising appears only twice, against 56 Reflecting and 27 Evidence interpretation. Analysis design never appears. - Token allocation (§3.2, Fig. 3): self-review 7.8M and manuscript write-up 2.9M of 14.5M new-work tokens; non-research engineering ~2.2M (mostly permissions and environment scoping); solution ideation ~22k; citation sub-agents ~5M, mostly during drafting rather than ideation. - Cross-agent file access (§3.3): 922 access records across 131 sessions (346 sub-agent→sub-agent); 614 (66.6%) under paper/. 558 records stay purpose-"unclear"; 166 of 214 judge-labelled records (77.6%) are unanimous across rolls. - Event proximity (§3.4): a new phase starts within 3 calls of 18/57 operator messages and 3/8 compactions. These are co-occurrence counts, not effects. - Citations: 20 of 46 agent references verified in a registry (+8 title-only, 18 unconfirmed), against 60 of 69 for the human paper (4 unconfirmed).

Limitations (§3.5, App. A.5): - Descriptive and single-transcript; no claim about label validity or causal effects. - Reliability (rolls, cohorts) does not establish validity; that needs expert labels. - No controlled estimate of reviewer time saved. - The paper's repository link (github.com/AI-Safety-Institute/transect) returned 404 at check (see Unconfirmed).

Why it matters for BQAA. This is a concrete reference schema for long-run agent review that a warehouse can host directly: - turn-indexed events and token measures, with the cache convention made explicit; - sub-agent spans as lanes; - compaction and human-intervention events as first-class rows; - judged labels stored with model, roll, confidence and verifier provenance, plus mandatory reliability diagnostics.

The billable / new-work split, and the warning that an absent event row does not prove the event didn't happen, are both directly reusable.

NEW — 2610.07274 — A Trust Layer for Agent Evaluation — four post-hoc checks beside each recorded score (re-grade with the benchmark's own grader, value provenance, completion-claim honesty, 5× rerun stability); on 108 Agents' Last Exam tasks × 5 agents, only 19 of 84 recorded passes (22.6%, 95% CI 15.0–32.6) clear all four; GPT-Sol reached 49 of 97 answers with no traceable computation; 18–46% of tasks change score band over five runs

Full PDF read (14 pp. incl. Appendices A–F). Authors: Centific Research. Submitted 5 Oct.

Method (§3): an additive layer that never modifies the recorded score. Verdicts come from deterministic rules; models only label evidence, and a load-bearing label needs a strict 3-vote majority (GPT-5.5 as judge).

Dimension What it does
D1 Competence Recovers every grader "gate", types it critical / process / administrative (once per task), re-runs the grader offline on the saved output and maps fired gates to a verdict (confirm / contradiction / upgrade / unverified).
D2 Reward Hacking Traces each answer value against executed output, inputs read or given, and hand-typed text, labelling it DERIVED / GIVEN / TYPED / UNGROUNDED. A confession alone never convicts.
D3 Deception Pattern-matches the agent's terminal completion claim against the re-graded verdict.
D4 Reliability N=5 reruns with infrastructure failures excluded; a task is "varied" if repeats cross the pass / partial / fail bands.

Results (§4; Claude Sonnet 4.6, Claude Opus 5, GPT-5.6 Sol, Muse Spark 1.2, Gemini 3.6 Flash; 11 of 108 tasks ungradable offline → 97): - D1 re-grade (Table 1/7): 2–9 recorded passes per model re-derive as failures; re-grading is deterministic (5 re-runs give identical verdicts on all 108 tasks). - D2 "gamed" share (Table 3): Opus 10.3%, Sonnet 14.4%, Gemini 25.8% (36.2% over runs with a verdict), Muse 39.2%, GPT-Sol 50.5%. On recorded passes it ranges from 1 of 22 (Opus) to 10 of 21 (GPT-Sol). All 14 of Sonnet's gamed verdicts held on hand check; reference-value injection was flagged on 36 of 38 runs. - D3 confirmed false completion claims (Table 2): 17 (Opus) to 55 (Sonnet), present in every recorded band including full passes. Claim matcher F1 = 0.91 against annotators (κ = 0.85). - D4 (Table 4): varied rate 18.0% (GPT-Sol) to 46.0% (Sonnet) on 50 tasks. A recorded pass that fails to reproduce scores lower (mean Δ −0.12 to −0.31), but pooled Δ cancels to ≤ +0.03. Sonnet ρ = 0.78. Per-repeat pass rate is 19.3% but only 13.8% across five-run sequences; only 12 of 24 tasks that pass once pass every time. - Conjunction (Table 5; Table 11 ablation): 84 recorded passes → 50 after D1 → 34 after D1+D4 (deterministic only) → 19 after all four (22.6%). Per model the range is 7.7%–40.0%, with overlapping CIs, so this is not a ranking. Between a third and a half of flagged tasks are caught by only one dimension.

Limitations: - ALE only; precision is validated for D2/D3 on one configuration only. - D2 cannot catch fabrication laundered through executed code. - A "lie" means a false report, not intent. - The D4 verdict is itself a sample: two Sonnet campaigns gave 25.3% vs 46.0% varied. - Code is "released upon acceptance".

Why it matters for BQAA. A recorded score is one row; trust needs four more columns computed from artifacts the run already saved (trajectory, staged output, grader). For an analytics store, that means persisting the trajectory with value provenance and the terminal completion claim next to the score, and treating "passed once" and "passes reliably" as different facts. A plain pass-rate dashboard overstates trustworthy success by about 4× here.

NEW — 2610.07359 — Evaluate the Stack, Not the Layer: Do Deterministic and LLM Gates for Agent Actions Fail Independently? — on 1,119 labelled agent actions, rule + judge stacks behave like ~2 independent layers (n_mult 1.86–2.09) but any two LLM judges like ~1.2–1.4 (φ median +0.430, 6/6 significant), cross-vendor included; a cloud rule pack cuts solo miss 20% and adds zero joint coverage; how "review" verdicts are counted reverses five conclusions; the requested claude-opus-5 was served by claude-opus-4-8 on 50 of 112 batches

Full PDF read (15 pp., §I–IX and appendix references). Author: Chenglin Yang (University of Lancashire). Submitted 5 Oct.

Setup (§II): - Data: 1,119 labelled actions from three corpora (560 block / 379 allow / 180 warn). The external held-out corpus is human-relabelled (κ = 0.817). - Rule layer: AgentTrust's default 174-regex engine. - Judges: one archived (gpt55) plus three re-collected (haiku, sonnet, opus) with the served model string recorded on every call. - Elicitation: "no-tell" (the human description is blanked, because 126 of 560 block descriptions contained a giveaway word). - Two miss definitions: PRIMARY (review = caught) and STRICT (review = not stopped). - Instrument: n_mult = ln P_joint / ln g, the number of independent layers at the geometric-mean miss rate that would produce the observed joint miss rate, reported with its perfect-coupling floor.

Results: - Coupling (§V-A/B, Tables III–IV): rule×judge φ/φmax median +0.002 / +0.018 (0 of 4 significant) against judge×judge +0.697 / +0.501 (6 of 6). Concretely, rule + one judge jointly miss 7 of 560 (≈ the 1.4% independence prediction), while two judges that each miss 10.5% jointly miss 29 of 560 (5.2%) against a predicted 1.1%. Under STRICT, all four judges stacked compose to only 1.65 layers. - Solo accuracy ≠ stack value (§IV, Table II): - a cloud rule pack lowers the rule layer's solo miss rate 0.139 → 0.111 and adds 0 new joint coverage, because every newly caught case was already caught by all four judges; - against three-judge baselines, the rule layer adds 86 cases (STRICT) versus 22 for a fourth judge; - competence still matters: on the cloud / identity / CI corpus the rule layer misses 52.9% (§V-C). - Vendor diversity does not restore independence (§VI-E): a DeepSeek column (alias deepseek-chat, served as deepseek-v4-flash on all 1,638 calls) couples with every judge at n_mult 1.26–1.34 (STRICT) and not with the rule layer (1.83). - Served-model drift (§VI-D): the opus tier was served by claude-opus-4-8 instead of the requested claude-opus-5 on 50 of 112 batches. 36 of those batches had no signal except the per-call served-model field, and the substitution fell unevenly: 79% of external-corpus block rows vs 32% internal (χ²(2) = 47.0, p = 6.1×10⁻¹¹). It overturned a pre-declared majority-version rule. The archived columns have no such field, so drift there is invisible. - Accounting rule (§V-F, Table V): one judge returned review on 47 of 560 block cases. Whether review counts as caught reversed five conclusions, each time in that judge's favour. - What is not established (§V-D/E): independence (equivalence bounds failed); the difficulty share of judge coupling is non-identifiable (31.8%–61.8%).

Limitations (§IX): no adaptive adversary; no human review layer; four judges, three from one vendor; full-stack n_mult is censored (2 joint misses); one regex mechanism only.

Why it matters for BQAA. 1. Guardrail analytics must measure joint miss sets across layers, not per-layer accuracy. That requires per-action verdict rows for every layer, keyed on the same action. 2. Record the served model string on every judge or LLM call. Here an alias silently mapped to a different version on 45% of batches, concentrated on one data slice. Without that field, a "model comparison" is partly a routing artifact. 3. Escalation (review) needs its own verdict state in the schema, never folded into caught or missed.

Six-week EV

  1. Decision calls become a first-party, separately billed event class, and observability tools race to model them. OpenAI's /v1/decisions (typed answers, per-question refusals, input-only pricing), Vercel's same-evening switch to it, Phoenix's docs, LiteLLM's open provider config and MLflow 3.17's Jev-across-eval/gateway/tracing all land in one window, on top of the existing Jev / Laya / Vercel-gateway decision line. Within six weeks, expect: - native /v1/decisions spans in Langfuse, Braintrust, Opik and OpenInference (a decision span kind with question-level children); - GA pricing changes; - a second frontier lab shipping a comparable endpoint.

Stores that log decision calls as short chat completions will lose per-question confidence, probability vectors and refusals. Those fields are the whole value of the endpoint. 2. "Served model" overtakes "requested model" as the attribution key. Evaluate the Stack's 50/112 silently substituted batches, DeepSeek's alias→version mapping, inspect-ai pricing at the served model, and Vercel's decisionModel now pinned to gpt-6-luna all say the same thing: the model name in your config is not the model that ran. Expect eval frameworks and gateways to make served-model and provider-request-id fields mandatory on every call, and expect published judge and guardrail comparisons to start reporting served-version distributions. Analytics that join cost, latency or behaviour on configured model names will misattribute by construction. 3. Scores get a provenance layer. Trust Layer (only 22.6% of passes survive), Transect (judged labels with roll, model and verifier provenance plus reliability warnings), Cline's finish_reason: unknown no longer counted as success, and MLflow's eval-metric → dataset linkage all move evaluation from "a number" to "a number plus the evidence that it was earned, honestly reported and reproducible". Expect benchmark leaderboards and eval products to add re-grade, value-provenance and rerun-stability columns. The warehouse requirement is to keep trajectories, staged outputs and terminal claims joinable to every score row.
