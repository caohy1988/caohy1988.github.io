Industry

Braintrust: Patterns, Debugger, Loop runtime, and Loop automations (public preview, Sep 3)

The changelog's September section grew from four entries to roughly fourteen, and the four that matter are new named capabilities, not SDK bumps. Patterns "runs Loop against your project on a schedule, searching for recurring problems and trends that no scorer is already measuring, such as a failure mode affecting one cohort of users or an LLM call whose cost has climbed." Enabling it creates a scheduled Loop automation that runs at 9:00 AM on weekdays, queries the last 30 days by default, and re-inspects the full range every run rather than only new traces. A pattern is recorded only when Loop can attach supporting evidence, and digests can post to Slack. It runs on Braintrust's built-in GPT-5.6 models and draws down the organization's monthly model credits; self-hosted deployments need data plane v2.13 or later.

The Debugger is the per-trace counterpart. From the Logs page you open a trace, pick the Debugger layout, and run it; the report lists findings ordered by severity (critical, high, medium, low), each with a hypothesis, a candidate root cause, an area label such as infrastructure, evaluation, or tool_call, and an Evidence section that names the spans, tool calls, and model outputs behind it. Clicking an evidence item jumps to that span, scrolled to the field it came from, with the supporting phrase highlighted. Loop itself now runs in a Braintrust-managed runtime instead of the browser, so threads persist and it can query logs, experiments, and datasets together, run SQL and code, and take approval-gated write actions (create evaluators, datasets, dashboards, monitors). Loop automations generalize Patterns: a scheduled run (daily, weekly, interval, or cron) with its own instruction, model, write permissions ranging from read-only to creating patterns, scorers, or facets, and Slack or webhook destinations. Everything above is labeled public preview, and the post says pricing will be set before general availability.

TL;DR for BQAA. The shape here is an agent that runs over the trace store on a schedule and writes structured findings back. BQAA is the trace store, and the equivalent is a scheduled investigation over the events table, which needs nothing new in the schema except what the Debugger's evidence links need: a stable event id and a field path on every event so a finding can point at "this tool result, this field." That is the failure-step pointer from the reserve list with a shipped reference. Note Datadog's Patterns docs page no longer shows the Preview label the 0746 brief recorded, but the Jun 9 launch post still says preview and nothing announces GA, so I am not calling that a change.

Epistemic Sybil Resistance: Multiplying AI Agents Without Multiplying Evidence (submitted Sep 1, cs.AI and cs.MA)

Marc Bara, Universitat Oberta de Catalunya, Barcelona, single author.

The claim is that a multi-agent system's own orchestration manufactures corroboration. Branching one retrieval across several agents, passing one agent's output into another's input, or re-prompting a shared base model all produce reports that look independent but descend from the same evidence. The paper defines an additional report as an epistemic Sybil extension when it carries zero conditional information about the latent state given what the aggregator already has, and proves that no rule seeing only report content can be Bayes-correct under both the "copy" and "independent" structures, since identical reports demand different posteriors. At 70% per-report accuracy the unavoidable error is about 0.072 in posterior probability. A Gaussian shared-root model then shows the middle ground: repeated extraction from one source does add information, but toward a ceiling set by the source's own noise, with the effective number of reports equal to m divided by 1 plus rho times (m minus 1), which is exactly the discount factor a recent provenance-aware aggregation paper had used as a heuristic. Correlated extraction errors, the kind agents sharing a base model produce, lower that ceiling further.

The empirical section uses a single Haiku-class model reading synthetic quarterly-revenue memos from fictional companies, chosen so pretraining cannot leak the answer. Holding one evidence root fixed and raising report count from 1 to 32, nominal 95% coverage of the naive independence-assuming aggregator falls from 0.940 to 0.263 and its calibration ratio (RMSE over posterior standard deviation) rises from 0.961 to 5.473, while the provenance-aware aggregator stays between 0.850 and 0.940 coverage. Holding 16 reports fixed and raising the number of independent roots from 1 to 16 closes the gap monotonically; at 16 roots the two aggregators are identical to three decimals (coverage 0.927 vs 0.927). The model's replicate extractions from the same document are correlated (gamma estimated out of sample at 0.719), and an aggregator that accounts for that restores coverage to 0.940 to 0.953. The sharpest result is a 2×2 design that manipulates rationale wording separately from true ancestry: an embedding-plus-cosine deduplication baseline moves its inferred cluster count by 1.425 (95% CI 1.363 to 1.485) in response to wording, and by 0.040 (CI −0.045 to 0.120) in response to a fourfold change in true root count. No similarity threshold gets both false-merge and false-split error below 0.846 on the evaluation set.

Stated limits: one task family, one main model, synthetic documents, heavy-tailed extraction noise the Gaussian aggregators do not model, and a pilot informativeness gate that was missed and disclosed rather than fixed. The correlated-extraction aggregator is flagged as exploratory. The author says the frozen Grid A and Grid B outputs will be released as a standalone benchmark with an aggregator interface, so the tables reproduce without any model calls.

TL;DR for BQAA. This is the third paper this week (after EAL-Bench's memory source references and the MCP-to-A2A field lineage trace) whose method depends on an event carrying a list of the events it derived from. For a multi-agent session, "how many independent tool results actually back this final answer" is only a query if each agent report event names its input events, and the paper's central finding is that no amount of text similarity over the outputs can recover that after the fact. One nullable repeated field, source event ids, serves all three papers.
