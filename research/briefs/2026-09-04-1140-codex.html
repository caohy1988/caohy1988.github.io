1. IBM watsonx Orchestrate gives builders a control-plane dashboard that separates fleet health, adoption, usage, performance, and quality (August 26 and 28)

The watsonx Orchestrate product team's dated August 26 end-month release says builders can now open the control-plane dashboard directly instead of depending on administrators for operational metrics. It describes a redesigned dashboard with purpose-built panels for fleet health, adoption metrics, usage trends, performance indicators, and quality insights. A separate dated August 28 September technical touchpoint calls out an Adoption dashboard and defines its two lenses as reach—how broadly agents are used across people and teams—and engagement—how often and how deeply users return. That distinction matters because a technically healthy deployed agent can still have no organizational uptake, while aggregate activity can hide a small group of heavy repeat users. The posts establish availability and product shape but do not expose exact formulas, unique-user windows, cohort rules, or retention denominators, so those details are not inferred here. The already-carded Trace Inspector, Custom LLM-as-a-Judge, and AgentOps GA content from IBM's September 3 announcement is deliberately excluded.

TL;DR for BQAA. Add a compact example that reports agent reach and repeat engagement separately from reliability and quality, with an explicit time window and distinct-user denominator. This is a vocabulary/query note: do not build a proprietary adoption dashboard until customers ask for one.

2. IBM watsonx Orchestrate can deploy a named stable agent version while development continues on a separate draft (August 26)

The same August 26 product update says teams can save named agent versions before deployment. They can deploy a specific version independently of the current working draft, so continued editing does not silently change production. IBM also says the deployed version can be tested without affecting the live production experience. This is a stronger operational contract than recording whichever mutable agent resource name happened to receive a request: the observable run has a resolved, stable deployment identity even while the authoring object moves forward. Haystack version comparison, Agno immutable published versions, and Gemini Enterprise's contrasting dynamic child-agent reference already support the general version-identity note; IBM adds a clean draft-versus-live deployment model. No claim is made about rollback, traffic splitting, promotion approval, or the underlying version identifier because the dated post does not specify those semantics.

TL;DR for BQAA. Preserve both the configured agent reference and the immutable deployed version resolved for each run; keep draft metadata out of production attribution unless it was actually deployed. For ADK interoperability tests, change the draft after deployment and verify that traces continue to name the stable live version.
