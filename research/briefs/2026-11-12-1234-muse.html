Read this first

Two items clear the bar. First, a controlled architecture study (reserve promotion, full PDF read) holds model, tasks and tools fixed across 13 enterprise SOPs and finds cost — not accuracy — is what separates agent architectures: every coordinated arm spends 1.4–4.7× the tokens and 2.6–5.8× the latency of a plain function-calling single agent, and only one arm significantly beats that baseline, at the highest token cost in the study. For ADK/BQAA the operational rule is: default to a single agent per workflow, and make any orchestrator, swarm or skill layer earn its keep with a measured per-workflow success gain before it ships. Academy

1. Agent Architecture Cost–Success Trade-offs: A Controlled Evaluation across Enterprise-Style SOPs — reserve promotion, full PDF read

Full PDF read: yes — pdftotext of the complete v1 PDF, read in full including abstract, introduction (§1), related work (§2), methodology (§3, Table 1), results (§4, Tables 2–5, Figure 2), conclusion (§5), limitations, ethics, references, and Appendices A–G (Tables 6–9). Amazon + University of Washington authors; cs.AI, submitted 7 Nov 2026 (Nov 11 batch). Not in catalog (grep: 0 hits). Promoted from the reserve queue — first in line per the 0034 brief — because the Thursday batch has still not listed.

What it does: eight arms across four architecture families — function-calling single agent (baseline), skill-augmented Constrained Skill Execution with high-/low-quality skill corpora (CSE-high/low), centralized orchestration in two implementations (Orch-v1 isolated-slice workers; Orch-v2 full-SOP workers with commit-with-basis, one re-dispatch round, output validation), and a triage-guided swarm at three blueprint levels (none/descriptive/full) — run on SOP-Bench's 13 enterprise SOPs (2,124 tasks per arm) with one pinned model (claude-opus-4-8; model name from the paper's methods, §3.1) and deterministic mock tools. SOP is the unit of inference; a 50-point Skill-Definition Quality Rubric (§3.3, Appendix A, Table 6) builds the matched corpora (pooled means 99.8% vs 67.6% — a manipulation check, not a success predictor).

Key numbers (Tables 2–3 unless noted; macro TSR = mean task success rate over the 13 SOPs):

  • SOP dominates architecture (§4.1): per-SOP TSR spans single digits to near-ceiling within every arm (hardest: content_flagging, video_annotation; easiest: referral_abuse, email_intent); between-SOP standard errors are 6.3–7.8 points and overlap across all arms, so no aggregate ranking is asserted.
  • Cost is the robust separator (§4.4, Table 3): every coordinated arm spends 1.4–4.7× baseline tokens and 2.6–5.8× latency (baseline 24.9k tokens / 24.0s per task). The baseline (67.4%) is Pareto-optimal — no arm is both cheaper and more accurate; Orch-v1 and Swarm-none are strictly dominated. CSE-high buys +5.7 points (73.1%) at 3.0× tokens; Swarm-descriptive +3.0 (70.4%) at 1.9×; Swarm-full +3.1 (70.5%) at 2.7× — none significant by per-SOP sign test.
  • Implementation quality beats the single-vs-multi choice (§4.2): Orch-v1 is the worst arm in the study (58.2%; baseline beats it on 9 of 13 SOPs, 6 significant) because slice-isolated workers cannot resolve missing inputs and emit placeholder decisions (patient_intake 13.6%, know_your_business 23.3%). Orch-v2's targeted fix recovers exactly those SOPs (13.6→98.5; 23.3→60.0; email_intent 75.8→96.2) and is the only arm to significantly beat the baseline (75.6% vs 67.4%; paired random-effects odds ratio 1.72, p=0.007, Appendix D) — but at 4.7× tokens / 3.1× latency, the most expensive arm in the study.
  • Skill quality helps narrowly, hurts silently (§4.3): CSE-high beats CSE-low by 13.3 macro points (73.1% vs 59.8%), concentrated in know_your_business (+45.6) and email_intent (+39.2), not significant by sign test (7 wins, 4 losses, 2 ties); degraded skills fall below the no-skill baseline. Appendix G's trace-level case: on referral_abuse_v2 the degraded skill drops the output contract, so correct decisions (≈96% read from the misplaced field) score 2.5% because they are filed under an invented key — sound reasoning, unusable output.
  • Blueprint helps, rigidity doesn't (§4.3): descriptive swarm blueprint lifts macro TSR 65.4→70.4 over none (stage coverage: peers stop handing off before all specialists run); the fully ordered blueprint adds nothing over descriptive (sign test p=1.00) at 42% more tokens and 39% more latency, and its "all stages must run" rule overrides legitimate early-exit gates.
  • Complexity split is directional only (§4.5, Table 4): on simple SOPs architecture is a wash (baseline already 71.8%); on complex SOPs the baseline degrades most (−8.2) while Orch-v2 (72.9%) and CSE-high (71.1%) hold up, but no edge-vs-complexity correlation is significant (n=13 needs |ρ|>0.56). The two-SOP open-tool ablation (Table 5, exploratory): hard tool scoping wins with few tools (KYB, 8 tools: CSE 85.6 vs open 68.9) and loses with many (video_annotation, 26 tools: 37.6 vs 57.6). §4.7 discloses two scoring defects the authors caught and fixed (multi-field output-contract truncation; a trace-denominator bug inflating one cell 93.5→97.9%) — outcome metrics need harness-level scrutiny before architectural conclusions.

Why BQAA/ADK care: (1) This is the controlled evidence for an architecture-selection rule ADK guidance currently states as taste: single agent by default; coordination must show a per-workflow TSR gain exceeding an organization-set cost threshold (the paper's Figure 1 break-even framing, explicitly conceptual, not estimated). (2) For BQAA analytics specifically, cost per task — tokens, latency, LLM calls — belongs on the same dashboard as task success, per workflow/SOP, not pooled: pooled means hide that SOP identity explains more variance than architecture, and more tasks per SOP do not shrink between-SOP error. (3) The silent output-contract failure (Appendix G) is a BQAA-shaped hazard: an analytics agent that computes the right number but emits it under the wrong field/schema must score as a failure in evals and alert as one in production — output-contract validation is a first-class eval dimension, exactly what Orch-v2 added to win.

Limits the authors state themselves (Limitations; §3.1): one benchmark with synthetic deterministic mock tools (no live-service latency/errors/nondeterminism); one model family (baseline macro TSR stable within 2.3 points across three versions in Appendix E/Table 9, but no cross-family claim); one run per task (binomial uncertainty only, no stochastic variance); each architecture is a single implementation and the skill-quality contrast is a bundled degradation, so neither isolates a best instantiation nor a single causal factor; process metrics (procedural fidelity, judge-scored reasoning quality) not reported. Reader's caution, verified in the PDF: the Conclusion (§5) restates the headline as "12 shared SOPs… 74.4% versus 65.6%; odds ratio 1.78, p=0.008" and cost ranges as 1.5–4.8×/2.5–5.9×, which do not match the 13-SOP Tables 2–3 and Appendix D values (75.6/67.4, OR 1.72, p=0.007; 1.4–4.7×/2.6–5.8×) used above — cite the tables, not the conclusion paragraph.
