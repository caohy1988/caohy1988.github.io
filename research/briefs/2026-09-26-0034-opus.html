1. NEW rank: arXiv 2609.22259: Which Part of the Context Layer Does the Work? Separating Semantic Content from Retrieval Scaffolding in Text-to-SQL Agents

Qing Ye (independent researcher). v1 submitted 6 Sep 2026 (cs.CL; cross-listed to cs.AI and cs.DB), listed Tue 22 Sep, 21 pages.

  • The harness, the frozen contract and the result rows are at github.com/flyersworder/agentic-data-contracts.
  • All 6,416 transcripts are released.

Full PDF read: §1–9 and App. A–H (Tables 1–12, Figs. 1–3).

What they did:

  • The question. Context layers, meaning curated documentation an analytics agent fetches at query time, produce large text-to-SQL gains. A with/without comparison can't say which part works: the semantic content, the retrieval scaffolding, or the pre-computed views that usually come along.
  • The instrument: a "data contract".
  • It is two YAML files (60,181 characters), authored only from DABStep's manual, then frozen and content-hashed about 35 commits before the first run.
  • It declares 5 readable tables, 11 forbidden operations, 8 domains and 14 metrics, each metric with a SQL expression.
  • Nine governed tools serve it. sqlglot checks every statement against the allow-list before it reaches the database.
  • Four arms on DABStep, the Adyen / Hugging Face payments benchmark (401 tasks with reconstructed golds, 332 of them hard):
  • schema: three ungoverned tools and no documentation (the floor);
  • hollow: the same nine tools and "look it up" instruction, over a contract whose prose a script emptied ("No documentation is available for this domain");
  • manual: the 24,177-character manual pasted into the system prompt (the practitioner's baseline);
  • contract: the full contract, one lookup away.
  • Four models: GLM-5.3-flash, DeepSeek-v4-flash, Claude Sonnet 5 and GPT-5.6 Sol, each pinned to one endpoint.
  • A ceiling. Compiling the contract's own SQL expressions into two views reproduces the gold answer on all 176 tasks those views cover.

Numbers:

  • Content dominates (Fig. 2, Table 4). Hard-task accuracy, schema → hollow → contract:
  • GLM 13.9 → 19.3 → 55.1%;
  • DeepSeek 22.6 → 22.6 → 56.6%;
  • Sonnet 5 22.9 → 38.0 → 68.4%;
  • GPT-5.6 37.0 → 51.2 → 77.4%.
  • Restoring the prose adds 26.2–35.8 points, while the tools and instruction alone add 0.0–15.1. The content step is 1.8× to 6.6× the scaffolding step, and on DeepSeek it is the whole effect.
  • The contract beats the same knowledge in the prompt on every model, by 13.7–44.6 hard-task points. On Sonnet 5, the pasted manual is indistinguishable from a bare schema (79 against 76 of 332, p = 0.72).
  • Graded by the benchmark itself (App. A). Submitted to the DABStep leaderboard, the GLM contract arm scored 51.9% against manual's 18.8% on 378 hard tasks (paired McNemar p = 4.9×10⁻²⁸). The author's own reconstructed golds run 5.7 points high for contract and 3.0 for manual.
  • Why: the rule is within reach (§6.1, Table 7). Both prompts contained the fee rule. On the 97 tasks that need all six fee clauses, the contract arm's SQL contains all six 39%, 65%, 55% and 98% of the time. The manual arm's does 3%, 9%, 4% and 4% of the time.
  • The derivation gap (§5.3, Table 6).
  • On the 176 tasks the compiled views answer outright, the contract arm recovers 60.8%, 62.7%, 73.9% and 94.9%. The gap to a proven ceiling falls from 39.2 points to 5.1 as capability rises.
  • On the 148 tasks that need reasoning on top of the views, it scores 45.9–60.1%, with no clean ordering by model.
  • Work and cost (Tables 8–9).
  • The contract arm uses the fewest turns and the least reasoning on every model, and it never ran out of output budget.
  • Cost per correct answer is lowest on three models. On Sonnet 5 it was $0.136, against $0.259 for the next arm.
  • On GPT-5.6 the manual arm is cheaper ($0.062 against $0.067). Knowledge fetched by tools is billed at the fresh-input rate, while a static prompt is cached.
  • Empty tools are not free. hollow was the most expensive arm on both frontier models: told nothing, the agent searched harder. On Sonnet 5 it called lookup_metric 1,620 times.
  • Governance (§7, Table 10). Ungoverned arms submitted 166 mutating statements across 26 tasks, and two reached the (disposable) warehouse. Governed arms submitted none, so the validator never had to fire.
  • Reproducibility (§8.3). A near-replicate of the GLM contract run, differing only by a validator fix, at temperature 0 on a pinned endpoint, flipped 94 of 401 task verdicts (23.4%), about equally in each direction. Aggregate accuracy did not differ (60.3% against 57.9%, p = 0.35).

Caveats I'd flag:

  • One benchmark, one domain. 294 of the 332 hard tasks concern fees, and on the non-fee hard tasks the contract shows no advantage (App. E).
  • The contract settles three things the manual leaves open. For example, list-typed fields use an empty list as the wildcard. The author notes this matters for 87 of the 97 payments tasks, and did not run the arm that would strip it (§8.2).
  • Thin replication. Single author; one run per model; lenient reconstructed golds; DeepSeek lost 29% of its rows to rate limits; a validator defect on GLM handicapped both governed arms; no contamination probe.
  • Two frontier points. They disagree on several capability trends, so read the capability story as two data points.

Why it ranks:

  • It is the cleanest decomposition I've seen of what a context layer buys.
  • It hands BQAA a method it can copy: a hollow control plus a compiled ceiling.
  • It adds a governance metric (attempted mutations) and a cost finding (context delivered by tools is billed fresh).
  • It is distinct from the catalog's text-to-SQL cards:

2. NEW rank: arXiv 2609.24161: MCP-GRANITE Benchmark: GRANularity Interface TEsting for MCP-Based LLM Agents

Paschalides, Symeonides, Pallis, Dikaiakos (University of Cyprus). v1 21 Sep 2026 (cs.DC; cross-listed to cs.AI and cs.LG), listed Tue 22 Sep, 8 pages. Author copy of a MASCOTS 2026 paper; code at github.com/dpasch01/mcp-granite.

Full PDF read: §I–VI (Tables I–V, Figs. 1–9).

What they did:

  • Tool granularity is the only variable. The same capability set is exposed through MCP in four ways:
  • L4: 8–10 single-purpose tools;
  • L3: 4 task-class tools;
  • L2: one read tool and one write tool;
  • L1: one monolithic tool.
  • Domain logic, the deterministic mock data and the prompts stay the same, and each level has its own gold call sequence.
  • Scale: 81 scenarios across 9 edge and IoT domains, and 9 local models (268M–20.9B parameters, 3- to 8-bit quantized, served by Ollama on one T4 GPU). Temperature 0, 3 repetitions, 8,748 runs in all.
  • The harness is Google ADK's McpToolset with LiteLLM, discovering tools at runtime through tools/list.
  • Metrics: task completion; tool-selection F1 (over tool names, ignoring order); argument accuracy; the rate of runs with no tool call; errors; latency; GPU power and energy.

Numbers (Table II unless noted):

  • Task completion: L4 0.42, L3 0.49, L2 0.42, L1 0.36.
  • The headline "+16.4%" and "+33.6%" are relative gains of L3 over L4 and over L1, not percentage points.
  • A logistic regression controlling for model size, quantization, domain and difficulty gives L3 1.36× the odds of completion (CI 1.12–1.66, p = 0.002), and L1 22% lower odds (p = 0.009).
  • Argument accuracy roughly doubles from L4 to L3 (0.20 → 0.40); L2 reaches 0.38.
  • Picking the tool is easier than using it. Tool-selection F1 peaks at L2 (0.71), but completion does not. In the paper's words, "argument construction, not tool selection, is the main bottleneck".
  • One monolithic tool breaks agents qualitatively. 28.2% of L1 runs finished without calling any tool (L4: 10.2%). Error rates were 11.4% at L3, 12.9% at L4, 14.1% at L2 and 15.8% at L1 (§V-E).
  • Size predicts latency, not success (§V-C).
  • Parameter count correlates at ρ = 0.285 with completion (p = 0.46) and at 0.946 with latency.
  • A 3.2B model at its best level beat a 20.9B model at a mismatched one.
  • GPT-OSS (20.9B) and xLAM-2 errored on 55.6% and 52.8% of runs, mostly with malformed calls against schemas discovered at runtime (Table I, §V-A).
  • Energy (Table IV). At L3, Llama 3.2 3B used 621 J per successful task and Qwen3 14.8B used 14,544 J (23×), completing 0.61 against 0.79.

Caveats I'd flag:

  • The MCP servers are mocks with fixed responses, so this measures the agent side only.
  • Only small, quantized local models on one GPU; no frontier models.
  • Marginal confidence intervals for completion overlap across levels. The L3 advantage rests on the paired bootstrap and the regression.
  • Quantization differs by model (3- to 8-bit), which confounds the size analysis. Energy is estimated from mean GPU power times time.
  • With a single tool (L1), order-free tool-name F1 mostly measures call counts.

Why it ranks:

  • It makes the tool surface a controlled variable. For small models, it moves completion and argument accuracy about as much as model choice does.
  • The transferable result is diagnostic: tool selection and argument construction fail independently, and "answered without calling a tool" is a distinct failure.
  • It is built on ADK's McpToolset and LiteLLM, so it can be rerun directly on an ADK agent.
  • It is distinct from arxiv-2609-20886-bi-agent-bi-bench-end-to-end-bi, which adds specialized tools rather than regrouping one capability set.

TL;DR for BQAA:

  • Store a tool-surface identity (tool count and schema hash) with every trace. Tool-call success rates are not comparable across agents with different surfaces.
  • Report tool-selection accuracy and argument accuracy separately.
  • Count runs that finish without any tool call as their own failure class.
