What changes in the traces:

  • One fewer LLM call per fallback (#7373).
  • "llm_fallback_adapter and its provider request both report chat, so observability backends can count an extra LLM call."
  • The adapter span keeps its metadata and fallback events but drops gen_ai.operation.name.
  • This is part of LiveKit's adoption of the newer OTel GenAI attributes (AGT-3191).
  • Provider after failover (#7374).
  • "After failover, llm_node could report the fallback model with the primary provider."
  • The node now records its request identity before nested inference starts.
  • Custom span metadata restored (#7428).
  • set_tracer_provider(provider, metadata={...}) was "silently ignored for every span created inside a job". All agent spans are in-job, so user metadata never landed.
  • That broke the documented langfuse.session.id session grouping. The PR traces the regression to #7033, merged Aug 29, so it first shipped in 1.8.0 on Sep 5.
  • Job attributes keep precedence, and provider metadata is kept separate so "simulation and redaction flags cannot cross jobs".
  • Exceptions under redaction (#7376).
  • "With project redaction enabled, uncaught exceptions lose their span event and error status."
  • Both tracer context managers now record the exception and error.type through the redaction-aware helper. Duplicate recording in LLM and TTS attempts is removed.
  • Negative span durations (#7332).
  • user_speaking starts on the STT turn anchor and ends on a backdated VAD anchor. "The two detectors do not share a clock."
  • On short bursts the end landed before the start. OTel keeps durations unsigned, and the reporter's backend read 18446744073500970us.
  • The end is now clamped to the start, and the trace-schema check flags any span that ends before it starts.
  • Close spans that nest (#7322).
  • session_close now covers the whole close. Before, work in the close handlers parented to an already-ended agent_session span.
  • In one export, a 103 ms event_loop_blocked appeared 8 ms after the session ended.
  • Realtime transcription usage (#7303).
  • OpenAI realtime ASR duration and tokens are reported as STT metrics and attributed to each session's current transcription model.
  • input_tokens includes audio and text, and input_audio_tokens is the audio subset.
  • Tool exchanges that stop disappearing (#7330).
  • ChatContext.copy(tools=...) dropped name-less tool outputs and then their orphaned calls, so "a completed tool exchange disappeared from the request".
  • Outputs are now paired by call_id. A realtime call rejected before execution is also now recorded in session.history.
  • Tool events:
  • ToolCallEnded.message no longer carries the ToolResult wrapper's repr (#7377).
  • Tools can return ToolResult(..., reply_required=False) to keep a result in history without prompting a reply (#7340).
  • Also in the release notes (not individually verified):
  • GPTLiveModel.with_azure (#7325) and a GPT Live service tier (#7401).
  • Opus 5.5 on Bedrock falls back to auto tool choice (#7411).
  • Google tool-schema errors are reported instead of ending the session silently (#7371).
  • Silently dropped STT sockets are now detected for several providers (#7357, #7359, #7364, #7369).

  • LLM call counts;
  • provider attribution;
  • session grouping through custom metadata;
  • error status;
  • span durations;
  • per-session ASR usage.

TL;DR for BQAA:

  • Segment LiveKit metrics by livekit-agents version. Before 1.8.3:
  • fallback turns carry an extra chat span (don't count it as an LLM call);
  • llm_node provider may be the primary after failover;

1. NEW rank: arXiv 2609.24928: Trajectory-Aware Benchmark Subset Selection for Cost-Efficient Software Engineering Agent Regression Testing

Ayyad, Wang, Shin, Zou, Adams (Queen's University; Wang at Concordia). v1 21 Sep 2026 (cs.SE), 37 pages, an ACM manuscript. The replication package, with the standardized trajectories, parsing schema and selection code, is at github.com/SAILResearch/swe-agent-subset-selection.

Full PDF read: §1–9 (Tables 1–9, Figs. 1–7).

What they did:

  • The problem. Agent developers rerun a full benchmark after every model, prompt or architecture change. The OpenHands harness subsamples with a fixed-seed random draw.
  • The data. 31,779 public trajectories from 58 runs across five agent frameworks, in three regression scenarios:
  • 45 reruns of one OpenHands setup on SWE-Rebench (3,188 instances);
  • 6 OpenHands runs with different models on SWE-bench Verified (Sonnet 3.5, Sonnet 3.7, Devstral, Sonnet 4, Kimi K2, GPT-5);
  • 7 runs across OpenHands, Moatless, Lingxi, Trae and Refact.
  • The pipeline:
  • Parse every framework's log into one schema (steps, commands, files touched, tests run, errors).
  • Sanitize it. Random identifiers become typed placeholders, and boilerplate is removed. Words that reveal the outcome (like "passed" and "exit code 0") or the repository are flagged by keyness testing and removed after review.
  • Embed each step with Nomic Embed v1.5 (768-d). Pool each trajectory into 3,840 dimensions: the mean, standard deviation, first, middle and last step.
  • The selection. Group instances by how many times they passed in past runs, then pick the instances nearest each group's centroid. This is deterministic, with no random draw.
  • The evaluation:
  • Strict temporal cross-validation: select on past runs, score on later ones.
  • 1,000 synthetic 250-instance test suites across nine difficulty levels for the model and framework scenarios.
  • 500 seeds per random baseline, and 76 configurations in all.

Numbers:

  • Stratifying by past pass counts is the strong baseline (Tables 3–4).
  • It cuts median RMSE against random sampling by 51% (reruns), 31–32% (model changes) and 40–42% (framework changes). Stratifying by repository adds under 2%.
  • But the tail stays wide. At a 5% subset, a typical pass-count-stratified draw's worst single-run error is 14.4 points on model changes and 14.3 on framework changes. The unluckiest seed's is 34.6 and 31.3 points; pure random reaches 47.2 and 47.8. Even at 30%, the worst seed errs by 11.4 and 10.5 points.
  • Trajectory-aware selection (Tables 5–6). At a 10% subset on model changes, median RMSE is 0.0431 against 0.0498 (mean −11.4%, Cliff's δ 0.49, large).
  • Worst single-run error is 8.56 points. That compares with 9.63 for the typical baseline draw and 15.87 for the 95th-percentile draw.
  • On framework changes: −3.1% RMSE (δ 0.22, small), and a worst error of 8.95 against 9.60 and 14.94.
  • At 20–30% the edge persists on model changes but disappears on framework changes.
  • A worked failure (§6.2). One 5% baseline draw picked 12 instances that all passed on Kimi K2. It estimated a resolve rate of 1.00 against the true 0.43. The trajectory-aware subset estimated 0.42.
  • Both parts are needed (Table 7, 10% subset). RMSE rises when you change any one piece:
  • dropping the pass-count grouping: +36.7% (model changes) and +30.5% (framework changes);
  • clustering trajectories instead of grouping by pass count: +15.7% and +9.0%;
  • shortlisting by geometry and then sampling randomly: +20.8% and +25.5%.
  • Determinism alone doesn't explain the gain. The trajectory-aware subset beat the middle 95% of random stratified draws on 20.4% and 30.7% of test suites, and lost on 1.9% and 0.6%.
  • Cost (Tables 8–9):
  • The six OpenHands runs cost 335M–945M tokens each, 3.44B in total, and input is 99.3% of the volume.
  • Per-instance cost varies up to 492×. Sonnet 4 took 2.2× GPT-5's steps (69.7 against 31.2) but cost 2.7× per instance, because context is re-sent every step.
  • The trajectory-aware 10% subset consumed 10.48% of tokens, so it doesn't favor cheap or expensive instances. That is 3.44B → about 345M.
  • Sanitization check (§4.2.4). A TF-IDF classifier still predicts pass/fail at 65.7–80.3% after sanitization, against 68.9–78.3% before. But its top features change from "passed" and repository names to task terms.

Caveats I'd flag:

  • Only code-repair benchmarks (SWE-bench Verified and SWE-Rebench).
  • The model and framework results use synthetic suites drawn from one 500-instance pool, with a mean Jaccard overlap of 0.35. So the p-values are optimistic.
  • The authors rest their conclusions on Cliff's δ, plus a per-difficulty-level sign test. There, core/edge selection beats the baseline on all nine levels at 5% and 10% (p = 0.004).
  • The gains concentrate at 5–10% subsets. A framework change still needs a full run to refresh the embeddings.
  • Sanitization needs a manual calibration pass per dataset, and it removes explicit outcome words, not all correlation with the outcome.
  • Only 6–7 runs in the model and framework scenarios. On average, 21% of instances flip outcome between two model-change runs (§8.3).

Why it ranks:

  • It is the first method I've seen that uses stored agent trajectories as the selection signal for regression evals. Trace data directly lowers eval cost.
  • It separates the two ways an eval subset fails: average error, and one bad estimate that reverts a good release. It shows random subsets hide a long tail: a worst draw of 47 points at 5%.
  • It is distinct from the catalog's eval-cost cards:
  • arxiv-2609-21267-efficient-benchmarking-production-analytics-agent: stratified fixed subsets plus gp-IRT on a production analytics agent, about 38.5% of cost.
  • arxiv-2609-20625-chronicle-cut-point-replay-regression: replay, not instance selection.

TL;DR for BQAA:

  • For each eval instance, keep its pass count across full runs and a trajectory representation. Then a 10% regression subset is one query: stratify by pass count and take the most central trajectories in each stratum.
  • Report worst single-run error for subset evals, not just the mean.
  • Model agent token cost as context re-sent every step (input is 99% of tokens), and expect a two-order-of-magnitude spread per task.
  • Strip outcome words and repository identifiers before embedding trajectories, or the embedding clusters by result.

2. NEW rank: arXiv 2609.22573: Zero-Trust Authorization and Discovery for Enterprise MCP

Huan Li, Yuwei Wang, Srinivasan Manoharan (PayPal). v1 18 Sep 2026 (cs.CR; cross-listed to cs.AI), 12 pages. The artifacts are promised "in a public repository (link to be added at submission/acceptance)".

Full PDF read: §1–7 and App. A (Tables 1–8, Fig. 1).

What they did:

  • A gap analysis of six official MCP SDKs (Python, TypeScript, Go, Rust, C# and Swift, at versions current as of 2026-05-15), in Table 1:
  • none offers pre-authentication tool discovery;
  • only Python with FastMCP offers permission-filtered listings and declarative per-tool permissions;
  • the three older SDKs bind credential extraction to the Authorization header.
  • Four FastMCP extensions, in production on PayPal's enterprise agent platform ("dozens of authenticated MCP servers"):
  • C1: SSO bearer and service-account credentials arrive on different headers and are normalized into one principal.
  • C2: opaque-token verification is cached (SHA-256-keyed, 300 s TTL).
  • C3: an unauthenticated metadata endpoint lets a registry index tools without credentials.
  • C4: one per-tool permission annotation (AND/OR) drives both the filtered list_tools and the invocation check.
  • The attack test. 60 hand-reviewed injection payloads in four classes, 4 models, 3 server configurations and 3 seeds: 2,160 attempts in all.
  • The target is a mock 8-tool Kubernetes server, where a viewer must not call restart_pod.
  • The configurations: every tool listed with checks inside tool bodies; filtered listing only; and filtered listing plus the invocation check.

Numbers:

  • Listing the forbidden tool invites attempts (Table 4).
  • With all tools listed, 152 of 720 runs named restart_pod: 21.1%, Wilson 95% CI 18.3–24.2. None executed, because the in-body check refused them.
  • With the filtered listing, attempts fell to 0/720.
  • Refusal is a vendor property. On identical prompts: claude-sonnet-4-6 0/180, claude-opus-4-7 3/180, gpt-5 59/180 and gemini-2.5-pro 90/180 (50%).
  • Role-play (70/180) and direct injection (56/180) broke models most. Context overflow broke them least (3/180).
  • Hidden is not unknown.
  • With the tool filtered out, models still repeated its name, which the prompts made inferable: claude-opus-4-7 169/180 (94%), claude-sonnet-4-6 142/180 (79%), gemini 44/180 and gpt-5 13/180.
  • A scripted client calling the hidden tool directly succeeds when only the listing is filtered. Only the invocation-time check blocks it (Table 6).
  • Operations (§4.2, Table 2):
  • In a 7-day production trace, the verification cache served 96.1% of requests at 9.9 ms p50, against 296 ms p50 on a miss.
  • The filter and invocation check added about 0 ms at p50 and at most about 0.15 ms at p95.
  • Filtering also removed "the PermissionError/wasted-LLM-cycle class" and trimmed tool schemas from context.

Caveats I'd flag:

  • The authors call the 0/720 result "almost true by definition": a model can't call a tool that isn't in its schema. The empirical content is the baseline attempt distribution and the leak rate.
  • Narrow setup: one forbidden tool, 60 payloads and no-op mock tools. The models are older than today's frontier: Sonnet 4.6, Opus 4.7, GPT-5 and Gemini 2.5 Pro.
  • A weak positive control: it ran on three models, used successor Claude models, and only the GPT-5 control matched the attack run's checkpoint. Gemini had no control.
  • Tools without an annotation default to open. A revoked token stays valid for up to one TTL.
  • Production figures are observational, and the artifacts are not yet public.
  • FastMCP's own auth= already couples listing and invocation. What's added is AND/OR composition and a third consistent surface, the pre-auth metadata.

Why it ranks:

  • It quantifies a boundary an observer can see: attempted, executed, and named-while-hidden are different events.
  • It shows containment by model refusal moves by 50 points across vendors on identical inputs, so it shifts at every model upgrade.
  • It pairs with tonight's crewAI #7779, where an empty allowlist allowed everything. Visibility and invocation are separate controls, and each fails on its own.
  • It is distinct from:
  • arxiv-2609-22076-aport-vault-payment-authorization-benchmark: a deterministic authorization layer for payments;
  • arxiv-2609-24161-mcp-granite-tool-interface-granularity: tool granularity, not permissions.

TL;DR for BQAA:

  • Log, per session, the tool list the agent was shown (count, schema hash and the caller's permission set), separately from each call's authorization result.
  • Count three event classes: forbidden tool attempted, forbidden tool executed, and hidden tool named in model output.
  • Segment attempt rates by model and model version.
  • Treat permission-denied tool calls as wasted cost.
