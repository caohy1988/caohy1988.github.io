NEW A1 — Asking for What Was Never Requested: Horizontal and Vertical Proactivity in Agents (arXiv 2609.37236)

Full PDF read (48 pp. incl. appendices A–O; IBM + Weizmann; code, need graphs and a Qwen3-8B LoRA are released).

What it is.

  • The axis. The paper separates what an agent pursues without being asked from whether or when it acts.
  • Horizontal proactivity pursues an unstated need that the current state already names, like looking up the account from a name and ZIP code.
  • Vertical proactivity pursues a need that only newly found evidence names, like the order that account record points to, and then the size-8 variant.
  • The need graph. Each task gets a graph of the evidence it requires. An edge from A to B means B can only be named once A is found. The graphs are recovered mechanically from the benchmarks' own decompositions (MuSiQue #1 references, StrategyQA, 2Wiki). No person or model wrote a node or edge (§4, Table 4).
  • Metrics, all computed from a finished transcript with no model judge (Table 1, Table 5):
  • required-evidence coverage;
  • breadth;
  • depth-weighted recall;
  • deepest need resolved;
  • out-of-order rate: evidence taken before its prerequisite;
  • promptness;
  • stop-when-done and ask-when-not-done, read at every decision point, not just the last one;
  • cost per need found.
  • Q&D, the training method.
  • A questioner is trained against a frozen drafter. At a fork in a recorded run, 8 candidate questions are sampled and each run is continued to the end.
  • The candidate whose continuation retrieves more required evidence, sooner, is preferred (§3). The training is imitation → DPO on question pairs → DPO plus stop contrasts.

Key numbers:

  • At equal retrieval spend (Table 2, Table 10), trained Qwen3-8B vs the same model prompted:
  • Coverage rises +11.2 pts on MuSiQue (78.3 → 89.5), +7.0 on StrategyQA and +5.0 on 2Wiki.
  • Depth-weighted recall rises +12.5, +5.4 and +5.5.
  • It beats prompted GPT-OSS-120B (15× larger) on MuSiQue (+7.0) and StrategyQA (+4.3) but trails it on 2Wiki (−3.5).
  • Cost and ablations:
  • Tokens per required need found fall 40% on MuSiQue (11,610 vs 19,354; §5).
  • Swapping in random same-benchmark questions costs 34.7 and 63.3 pts of coverage.
  • Letting the prompted model spend as many question tokens still leaves it 14.9 and 4.7 pts behind (App. C).
  • Stopping (§5, App. G): the trained questioner stops 29–33 pts more often once the evidence is complete. Stopping is still the weak part: it clears the stop-when-done floor of 0.85 on neither suite (0.427 / 0.545 on dev; App. G). Answer F1 gains are not detectable (+2.4 on MuSiQue, interval spans zero; Table 10).
  • τ²-bench transfer, with no retraining (§5, App. H Tables 18–20):
  • Retail success goes from 13% / 12% to 34% / 32% across the two prompt variants, better on 10 of 25 tasks and worse on none. Airline success rises +6.9 / +6.4.
  • Against GPT-OSS-120B in retail: +17.0 / +12.7 success, with 1.6 / 1.8 fewer customer follow-up turns (decided).
  • Follow-up turns vs the same model prompted, the declared primary endpoint, are not established. Every pooled interval spans zero (Table 18).
  • Label validity (App. I). Two human raters agree on whether a question reaches an unstated need (κ = 0.76). They agree on which question is the better move only at κ = 0.24. Each agrees with the rule on 65–68% of pairs, against 50% chance.

Limitations the authors state (§7, App. I.4).

  • The retrieval pools are small (10–20 paragraphs), so only 20 of 1,040 prerequisite edges actually gate retrieval. "Vertical" therefore means depth in the benchmark's decomposition, not evidence that was truly unreachable earlier.
  • Every user-facing number comes from a simulated customer.
  • The two reported seeds share one supervised fine-tuning (SFT) checkpoint.
  • "Proactive without harassing the user" is not measured.

Why it matters for BQAA. This is a ready-made trace-level metric family that needs no judge. Given a per-task list of required evidence, the tool-call log alone yields:

  • coverage;
  • out-of-order rate;
  • stop-when-done / ask-when-not-done per decision point;
  • cost per need found.

The per-decision-point reading of stopping is the useful part: a run-level "did it stop" summary gives full credit to an agent that asked six extra questions after it was done. And "user follow-up turns and task success, never one ratio" is the right pairing for customer-facing agent dashboards.

NEW A2 — AutoDataBench: Can Agents Write the Data That Feeds the Self-Improvement Loop? (arXiv 2609.35025)

Full PDF read (21 pp. incl. appendices A–I; HKUST / SLAI / NTU; code and rubrics released).

What it is.

  • An episode. The agent under test gets one original task and six sanitised transcripts of a fixed target model (deepseek-v4-pro) attempting it. It must deliver one new executable task, with its own verifier, for the same suite.
  • Scoring (§2.3, Eq. 2): score = gate × difficulty × quality.
  • Gate. Any of eight defects scores zero, for example a verifier that never checks the answer, a leaked answer, or a surface-swapped clone of the original. The clone check starts from a word-level instruction diff.
  • Difficulty. 1 if the target model's pass rate on the new task, over K = 6 runs, is in [0.125, 0.75], else 0. The task's own verifier decides this, not a judge.
  • Quality. Coverage of a hidden rubric of 3–5 failure modes an analyst wrote from the transcripts. A mode counts only if the judge cites an attempt, a step and a verbatim quote. Coverage is capped with a = 0.6.
  • Setup. 24 original tasks from Terminal-Bench 4.0, Terminal-Bench-Science and AutomationBench. The analyst and judge are claude-opus-5.

Key numbers:

  • Scores (Table 2): no author agent scores above 0.20. kimi-k3 0.184, gpt-5.6-sol 0.177, qwen3.8-max 0.139, glm-5.3 0.130, deepseek-v4-pro 0.097.
  • Difficulty is the bottleneck (Table 2). Only 14.6–25.0% of deliveries land in the pass-rate band. The in-band, ungated ones cover 0.70–0.97 of the rubric.
  • Self-authoring (Table 2). deepseek-v4-pro, writing for itself, has the highest in-band rate but passes the gate on only 41.7% of those tasks. Staying close to the original is the cheapest way into the band, and the clone gate catches it.
  • Domain ranking is unstable (Fig. 4). qwen3.8-max is first on Terminal-Bench and scores zero on AutomationBench.
  • Time budget (§3.3, Fig. 5). At 180 vs 45 minutes, kimi-k3 goes from 0.184 to 0.541.
  • Caveat (App. F): the 180-minute arm also ran at maximum reasoning effort, so budget and effort are confounded.
  • The cost of one usable task barely moves: $11.88 → $12.62, and 244 → 230 minutes (Table 3).
  • Cost of one usable task (Table 3): $4.81 (deepseek-v4-pro) to $27.69 (gpt-5.6-sol), versus $0.50–$5.77 per episode.
  • Failure catalogue (App. H, Table 5). Of 14 cross-agent behaviours, 8 cost the pass rate. Two examples:
  • Extrapolating a pass rate from one sample, then delivering without re-testing (C4).
  • Adding a discriminating condition, then spelling it out in the instruction (C14).

Limitations the authors state. 8 tasks per suite, and a single target model. The analyst and judge are one model family. The budget/effort confound noted above. The paper does not test whether a task that exercises a failure mode actually repairs it after training (§6).

Why it matters for BQAA.

  1. Rubric modes from transcripts. The analyst → hidden-rubric → evidence-cited-judge pipeline turns failure transcripts into reusable, suite-level failure modes. The same pipeline could turn BQAA trace clusters into eval tasks.
  2. Cost per usable output, not per run. Pricing agent work by accepted outputs matters for any customer running data-generation agents: the per-episode cost ordering and the per-usable-task ordering disagree.
  3. Difficulty needs execution. Difficulty calibration only closes by actually running the target model. Authoring agents compress it into the last minutes (C11), and a trace view of calibration loops would expose that directly.

Six-week EV

  1. Judge-free, trace-derived behavior metrics (high EV).
  • 37236 shows that coverage, ordering and stopping can be scored from tool-call logs against a task's required-evidence list. The per-decision-point stop rates are the novel reading.
  • A BQAA "evidence coverage" view needs only one customer-supplied mapping: required records per task → tool-result identifiers. It would sit next to judge-based evals and cost nothing per row.
  1. Telemetry completeness checks at the SDK boundary (high EV).
  • This window adds three silent-loss or zero-value cases: Langfuse Python's 64 MiB batch drop, Opik's $0 quarkus-langchain4j spans, and dropped Nova cache counters. At 0034 there were two more: Cline's double-counted reasoning tokens and Mastra's cache-write pricing.
  • A BQAA ingest check could flag three things: span-count drops across exporter errors, cost = 0 on priced models, and cache counters missing where the provider reports them.
  1. Approval and resume lifecycle (medium-high EV).
  • Several stacks are converging on durable approval and resume flows:
    • qwen-code Hosted approvals (pending release);
    • Mastra durable resumeData;
    • agno's HITL continue fix;
    • Codex authoritative resume history.
  • The failure mode common to all of them: resumed runs that duplicate or drop turns. A trace check for "the same tool_call_id appears twice across a resume" would catch exactly the agno bug class.
  1. Cost per accepted output for generation agents (medium EV). AutoDataBench's cost ordering and quality ordering disagree by 2.3× at near-equal score. Customers running synthesis or labeling agents need an acceptance-joined cost metric, not a cost-per-run metric.
