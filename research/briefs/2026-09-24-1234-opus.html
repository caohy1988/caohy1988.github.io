1. NEW rank: Letta Code v0.33.1: Claude Code and Codex become tracked subagents under a Letta orchestrator

What shipped (release notes + PR bodies read):

  • #4694 Claude Code and Codex workers (+3,548/−178):
  • Agent() can launch the locally installed Claude Code and Codex CLIs as coding workers, with Letta Code as the orchestrator.
  • Codex runs through a managed codex app-server --stdio child, and active messages use turn/steer.
  • Claude Code runs as a managed stream-JSON process. An active message triggers a native interrupt, then the replacement instruction goes into the same session.
  • Letta owns background tasks, cancellation, output transcripts, completion notifications and process cleanup.
  • MCP inheritance passes discovery metadata and parent identity, not credentials.
  • #4704 Wake:
  • A default tool with create/list/cancel resumes the current conversation at a chosen time.
  • It reuses the existing schedule API and adds no scheduler.
  • Calendar times must carry an explicit RFC 3339 offset.
  • #4714 credential redaction:
  • A long-running child keeps the credential it inherited at launch. Redaction now uses that launch-time set, so a credential that rotated mid-run cannot reach the model or an overflow file.
  • Tests rotate the parent credential after the child starts.
  • Also in the release: agent-free turns can call SDK tools, headless runs honor a model override, and model structured-output support is shown and filterable.

Why it's a new rank and not progress on the v0.33.0 card:

  • v0.33.0 was about a background memory worker.
  • v0.33.1 adds a new orchestration surface: another vendor's harness running as a child session, with native IDs passed back. The version bump is a patch, but the capability is new.

Pack correction: Agy 1232 filed this as "Letta 0.33.1 (PyPI)". The PyPI letta project now describes itself as "Letta Code: stateful agents in your terminal", and its source link points to letta-ai/letta-code. The legacy letta-ai/letta server repository has been archived since 2026-08-16 (#3430); its last tag is 0.16.8. The product is Letta Code, released on GitHub, npm and PyPI together.

TL;DR for BQAA:

  • A subagent span should record the harness vendor, the child's native session or thread ID, the parent's session ID, and the steer/interrupt events. Today a Letta → Codex hand-off would show up as one opaque tool call.
  • Log redaction by credential set at launch, not current credential. The same bug is likely in any plugin that scrubs at export time.

1. NEW rank: arXiv 2609.22682: Self-Organizing Agent Teams Learn to Reason Together

Pappu, Suzgun, El, Kwon, Bianchi, Kochenderfer, Cao, Zou (Stanford / Together AI / Emory). Submitted 19 Sep 2026 (v1) and featured on HF Daily Papers on 09-24. Read in full (main text + Appendices A–B + transcript figures).

What they did:

  • A teamwork strategy is a small DSL. Each strategy is an ordered list of conversational phases. Each phase has a participant subset, a round count, and an information-flow mode (local vs summary broadcast), plus a shared team prompt and persistent per-agent roles.
  • Learning runs offline. One designated member (o3-mini for math, Gemini-2.5-Flash for GPQA) reads prior strategies, transcripts, per-member answers and probe results. It proposes up to 3 mutations per round for 6 rounds per training problem.
  • A mutation that solves its source problem is tested on 5 other training problems ("validation probes").
  • A separate audit rejects strategies that encode problem-specific content.
  • A coverage-greedy pass keeps 10 strategies, and the bank is frozen.
  • At test time, every strategy produces a candidate with a checkable "certificate". One judge (the strongest member) audits all the certificates in a single prompt and picks the answer.

Numbers (Tables 1–2, 4):

  • Math and physics (o3-mini + Sonnet 4 + DeepSeek-V3; trained on 15 AIME-2024 problems):
  • The average over 5 benchmarks is 66.7%. For comparison:
    • best member: 48.8%
    • self-consistency K=10: 55.4%
    • Mixture of Agents: 57.3%
    • linearization, where o3-mini runs the same strategies alone at about the same budget: 58.7%
    • homogeneous team of 3× o3-mini: 56.0%
    • routing-oracle coverage: 59.0%
  • On AIME 2026 the team scores 71.2%, 13.4 points above the oracle. On HMMT 2026 it ties linearization at 39.4%.
  • Knowledge and logic (Gemini-2.5-Flash + Llama-4-Maverick + GPT-4.1; trained on 25 GPQA problems): the team averages 72.8%, which is best among the methods but below oracle coverage (79.6%). The team's own candidate pool covers 87.9%, so selection loses ~15 points.
  • Against the seed strategy (debate + majority vote): 54.1 → 66.7 on math and 69.6 → 72.8 on knowledge.
  • Demonstrability: a 10-model panel's rate of picking the correct certificate over a wrong one tracks the team's gain over its best member across 8 benchmarks (Spearman ρ = 0.90, p = 0.005; leave-one-out 0.86–0.96).

Caveats I'd flag:

  • The rosters are older, deliberately weaker models, chosen to leave headroom.
  • Results are means over 3 seeds, and some benchmarks are small (the AIME splits are ~15–30 problems).
  • The paper reports no token or dollar cost beyond "approximately the team's total inference budget" for linearization.
  • The demonstrability result is post hoc and correlational over 8 points. The authors say so themselves.
  • The judge is also a team member.

Why it ranks: it gives agent analytics a concrete, computable baseline that separates selection from collaboration: the routing oracle and coverage vs accuracy. Most multi-agent evals compare only against the best single agent, which cannot tell you whether the interaction created the answer.

TL;DR for BQAA:

  • For multi-agent sessions, log each member's independent answer before interaction as well as the team's final answer. With both, oracle_coverage, team_coverage and team_accuracy can be computed in SQL.
  • Tag phases and roles on spans (phase id, participants, flow mode). A learned strategy is only auditable if the trace says which phase produced which claim.
