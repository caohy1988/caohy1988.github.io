1. NVIDIA opens Parse 3.5 training data and measures DFlash2 document-parsing throughput

Primary: https://huggingface.co/blog/nvidia/building-on-nemotron-35-parse-open-data-fine-tunin (Hugging Face RSS published 2026-11-26T05:05:36Z, in-window).

NVIDIA releases Synthetic Charts V1 (9.98M examples), Synthetic Tables V1 (1M) and OCR Synthetic Multilingual v2 (7.9M), with images, annotations, generation documentation and training format. Parse turns page images into reading-ordered, located and typed records for RAG and agents. The post also explains the two-stage supervised fine-tuning and GRPO verifiable-reward recipe, and releases a DFlash2 speculative-decoding path that proposes up to 32 tokens ahead.

In the matched development-checkpoint comparison, loop-flagged outputs fall from 126 to 29 pages, outputs reaching the 9,000-token limit fall from 185 to 35, and overall score rises from 66.24 to 71.38 (Figure 3). Those checkpoints are explicitly separate from the final released model. In the native single-pass benchmark on one H200 in BF16, DFlash2 improves throughput 7.62× at concurrency 1 and 1.52× at concurrency 512 over Parse 3.5 with speculation disabled. At concurrency 512, Parse 3.5 reaches 13.48 pages/s without and 20.44 with DFlash2, against 2.98 for Parse 2.0 (Figure 4). Parse 3.5 uses three-trial medians; Parse 2.0 uses one trial per point.

Why it ranks. This is a material training-data, recipe and inference release for document agents, with measured extraction and serving results rather than a model-name bump. BQAA should trace parse model/version, page count, pass count, structured-output validity, loops/token-limit failures, latency and cost per successfully parsed page. Multi-pass refinement can improve difficult regions while changing the cost denominator; no cross-hardware or independent quality replication is supplied. 1. Spec-Test Coverage Gap: Detecting Overspecified Tests in SWE-Bench-Style Benchmarks — https://arxiv.org/abs/2611.31839

Full PDF read: yes — entire 16-page PDF read via pdftotext, including the judge/relaxer protocols, execution controls, limitations, references and Appendices A–J. arXiv v1 is dated 2026-11-24 and was carried from the Wednesday screen; it is absent from the live catalog.

Problem and method. STCG asks whether every reasonable correct fix would pass the evaluation tests. Two judges see the task specification and test patch, but not the repository or reference fix; a task is flagged only when both score it 3–4 (§3). On a held-out 206-task split, the panel reaches 89% recall on known-overspecified tasks and a 4% false-flag rate on known-fine Verified tasks (§4, Table 4). The panel then runs over all 500 Verified and 731 public Pro tasks.

Results to reuse. It flags 117/500 Verified (23%) and 258/731 Pro tasks (35%; §5, Table 5). On Verified, the top 30 submissions resolve flagged tasks 31% of the time versus 88% for unflagged tasks (§5.1). For executable confirmation, the authors relax flagged tests and regrade 2,186 failed patches that fail evaluation but not regression tests: 61% flip to passing, versus 29% under a forced unflagged control (§7, Table 7). With the same no-findings prompt, the comparison is 49% versus 0%. Counting every flip would add 33–60 resolved tasks per top-30 submission, but the authors explicitly call those score changes an upper bound, not corrected scores (§7.2, §8).

Qualifications. Pro has no known-fine validation set or executable confirmation. Validation uses clear cases, flipped patches receive only sampled manual inspection, the relaxer is one of the judges and can over-loosen tests, and repository conventions are hidden from the judge (§8). BQAA should audit spec/test gaps alongside pass rates and preserve relaxation provenance plus positive and negative controls; never convert the 61% flip rate directly into agent credit.

2. How Much Do Coding Agents Over-Edit, and Why? An Empirical Study of Unneeded Edits in Repository-Level Agent Patches — https://arxiv.org/abs/2611.34875

Full PDF read: yes — entire 30-page PDF read via pdftotext, including methods, all results, limitations, references and Appendices A–I. arXiv v1 is dated 2026-11-25 and is absent from the live catalog.

Problem and method. Delta Residue Attribution (DRA) replays trajectories, attributes every final-patch unit to its introducing step, reverts each unit and reruns task tests (§3, Algorithm 1). The study covers 7,660 resolved GitHub Copilot CLI trajectories from 18 models: 6,728 on SWE-bench Verified and 932 on DeepSWE (§4.1). Developer patches are graded with the same oracle, test edits are separated from code, and behavioral probes test whether removing test-unneeded code changes behavior.

Results to reuse. Under the task-test oracle, mean code necessity is 0.887 for agents versus 0.864 for developers on Verified; 11 of 18 models leave less unneeded code, four show no significant difference and three leave more (§5.1, Figure 2). About 11% of agent code units are test-unneeded, and 89% of 3,559 probed units change behavior when reverted (§5.2; Appendix C.1, Table 7). On Verified, 61% of extra edits are tests and 13% documentation; debug steps write only 154 of 3,987 unneeded code units (§5.2–5.3, Figure 3). With the agent's and repository's tests, pruning reaches 67.3% recall at 46.3% precision and 89.1% still-resolving patches on 2,495 eligible patches; self-audit reaches 35.5% recall at 65.7% precision (§5.5, Table 1).

Qualifications. The oracle matters decisively: strengthening it with developer-equivalent behavioral probes raises developer necessity from 0.864 to 0.970 and agent necessity from 0.887 to 0.925, flipping the agent–developer gap from +2.3 to −4.5 points (Appendix C.1). Results cover resolved patches, primarily one harness, LLM-written probes, single-unit reversions and no completed human validation (§6; Appendices A–B). BQAA should report oracle identity, code/test necessity and behavioral change next to resolve rate, not equate large patches with bad patches or test-passing pruning with safe cleanup.

3. Attack Policy Selection can Mislead Monitor Evaluators — https://arxiv.org/abs/2611.34934

Full PDF read: yes — entire 24-page PDF read via pdftotext, including the case-study setup, all attack methods, proxy/legitimacy analysis, limitations, references and Appendices A–I. arXiv v1 is dated 2026-11-25 and is absent from the live catalog.

Problem and method. The paper varies attack generation while holding the deployment scenario, monitor and control tasks fixed. Attacks are developed only against proxy monitors; the reported false-negative rates (FNRs) measure transfer to a held-out GPT-5.4 monitor (§§1–2). The four methods are basic prompting, optimized prompting, reinforcement learning and transcript editing, with primary FNR conditioned on side-task success.

Results to reuse. On IaC, basic and async-control prompting produce 0.2% and 0.5% FNR. Optimized prompting reaches 6.4%, RL rises from 0.5% to 20.8%, and transcript editing rises from 0.3% to 23.0% (§2, Figures 2–5; Appendix B, Table 1). A narrow evaluation using only basic methods therefore makes the monitor look much stronger than the broad one (Figure 1). Transfer is environment-dependent: on LinuxArena, optimized prompting and the best RL results fall to 0.2% and 0.7%, while directly optimized transcript editing reaches 16.2% (Appendix F, Figure 6). Counting flagged failed side tasks under a stricter metric lowers optimized prompting to 5.4% and final RL to 17.5% (Appendix G, Table 4).

Qualifications. Attack transcripts are off-policy proxies, edited tool calls are not re-executed, the target agent is less capable than the monitor, and direct optimization against the held-out monitor is untested (§§3–4). The paper's central requirement is a legitimacy argument for why a proxy distribution is informative or conservative; no FNR here is a deployment-risk estimate. BQAA should record attack method, optimization budget, proxy/target monitor, environment, success conditioning and transfer results with every monitor evaluation.
