Industry

BigQuery release notes, Aug 31 entry — identity columns (Preview) + pipelines in Git (Aug 31, appeared ~noon PT)

Three features in one entry. First: identity columns, Preview — you can declare an auto-incrementing column on a table, and "when you insert a row into a table that has an identity column, BigQuery generates a unique integer value for that column" (verbatim from the note). It's pitched as primary-key maintenance, and it's the first time BigQuery generates a row key for you instead of making the producer bring one. Second and third: pipelines can now be created, stored, and managed in Git folders (Preview), and folder-based pipeline management is GA — pipelines-as-code with version control, on the same platform that holds the trace table. The one contract that matters for BQAA: agent_events currently has no table-generated key; dedup and ordering ride entirely on producer-supplied fields (timestamps, trace_id, span identifiers). An identity column would be a free, BigQuery-native tiebreaker — if it populates under Storage Write API appends, which is BQAA's write path and which this release note does not mention. The wrong belief to kill: "identity columns solve event ordering for agent_events." Unverified against the Write API, Preview, and a generated integer is an arrival-order artifact, not a semantic sequence — it can supplement sequence-style ordering, not replace it. Judgment: calendar — home-platform feature, worth one test, threatens nothing.

TL;DR for BQAA. Run the ten-minute test: add an identity column to a scratch agent_events clone and append through the Storage Write API. If it populates, that's a free dedup/tiebreaker key and one new doc line; if it doesn't, that's a caveat worth writing before a customer files it. The Git-pipelines item is a substrate-story footnote — the "PR" end of the trace→cluster→PR loop is drifting into BigQuery itself — note it, start nothing.
