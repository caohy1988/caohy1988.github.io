1. NEW rank: Mastra @mastra/core@1.69.0 reaches npm latest: typed Classifier primitive, ClassifierProcessor (fails closed by default) and classifier workflow steps are now stable; tracingOptions.rootSpanName gives each run its own root span name

What shipped. I read the ## 1.69.0 section of packages/core/CHANGELOG.md on main; the npm tarball ships no CHANGELOG. The release was published to npm at 09:36:31Z (02:36 PT), the promotion predicted by the 0034 six-week EV at ~85%.

  • Classifier stack (minor changes):
  • a typed Classifier primitive for fixed-option evaluation with AI SDK evaluation models (#24458);
  • registration on the Mastra instance (#24738);
  • classifiers as typed workflow steps (#24747). These expose "complete typed answers and token usage" to branch and conditional control flow, in both fluent and dynamic graphs;
  • ClassifierProcessor (#24768), which applies typed classifier policies to agent input, output and streaming content.
  • ClassifierProcessor fails closed by default (#24793). If the classifier call fails, the request is aborted. Setting errorStrategy: 'warn' restores fail-open. Contrast LiteLLM's Jev compaction guardrail (0034 card), which fails open.
  • Observability contract changes:
  • tracingOptions.rootSpanName (#24564) replaces the default agent run: '<id>' / workflow run: '<id>' name on the root span only. It is accepted on the agent and workflow HTTP routes and in client types. It works for the Inngest engine too, because the name is applied before any durable snapshot is taken.
  • The trace-query group option is deprecated in favour of the queryThreads thread-query contract (#23790).
  • Internal spans now keep their internal status through rebuildSpan()/exportSpan() (#24742), so they stay out of exporters by default.
  • runEvals no longer saves mastra__authToken or unstorable values into score rows. Nested request-context objects become dotted keys (#24753).
  • Also in this release:
  • context.background.adopt() for background tasks (#24418);
  • validateSkillContent() / validateSkillMetadata() for SKILL.md (#24766);
  • tool calls with a function-valued approval policy now run in parallel when the policy returns false;
  • a fix for an event-loop hang after a persisted idle signal.

Why it's a rank. The 1834 and 0034 briefs tracked this as an alpha. This is the stable release, and it makes Mastra the first agent framework on a latest tag that has a typed, probability-bearing classifier as a first-class primitive, used as a workflow step (routing) and as a processor (guardrail). Tonight's product pattern: the same decision call is showing up as judge, router and gate, and each role has a different failure policy.

TL;DR for BQAA:

  • Log a classifier decision as its own event type, separate from LLM calls and eval scores. It needs role ∈ {route, gate, judge}, options, chosen, probabilities, error_strategy (fail_closed/fail_open), aborted (bool) and token usage. The same model call means different things in each role.
  • rootSpanName breaks "group by span name = group by workflow". Customers who set it will emit arbitrary root names. BQAA should key workflow identity on a stable workflow_id/agent_id attribute, never on the root span name.
  • Fail-closed aborts are a new outcome class. A request aborted by a classifier outage looks like a user-facing failure with no model error. Dashboards should separate "blocked by policy," "blocked because the classifier failed," and "model error."

Boundaries. The GitHub release page still returns 404, so npm is the authoritative artifact. Mastra #24566 (trusted tenant scope across trace queries, merged 09:44Z) and #24813 (Inngest resumed agents no longer replay suspended runs) merged after 1.69.0 was published and are not in it. 1. NEW rank: arXiv:2609.26758 — Type-Safe Is Not Error-Free: A Constrained Decision Head Follows the Option Name, Not the Rubric Bound to It (Sun — NUS; Xu — Fudan; equal contribution; v1, Sep 22 2026; 9 pp, read to App. E)

What it is:

  • A controlled test of Jev-style constrained decision heads, the "one state + typed options → probabilities" call that Langfuse, LiteLLM, Mastra and the AI SDK adopted this week.
  • The question, state and rubric text stay byte-identical. Only which option name each rubric is bound to is swapped.
  • Models tested: two open encoder heads (ModernBERT with a marker read-out, DeBERTa with a span-mean read-out) and the vendor's hosted model.

Results (n = 1,200 over 4 predicates; one predicate is agent-trace triage):

  • Swapping rubrics behind no/yes flips 76.92% of answers, against 6.50% for neutral 0/1 names. That is a difference-in-differences of +70.42 pts [67.58, 73.08].
  • The failure is confident inversion, not noise: AUROC .9376 → .2315.
  • Hosted model: 32.50% flips against a 1.33% test-retest floor; AUROC .8146 → .5806.
  • The span-mean read-out flips 4.1× less than the marker read-out. Random-string option names bring flips back to the neutral level.
  • Type-error rate: 0% in every condition.

Caveats:

  • Two authors; one checkpoint per architecture; English only.
  • The proposed mitigations are not evaluated.
  • A code release is claimed, but no URL is given.
  • The abstract is partly garbled, and it names "Jev" while the body says "vendor".
  • The claim that the effect grows with more options rests on a multi-way arm the paper itself calls directional.

TL;DR for BQAA:

  • Schema validity is not correctness. Every decision-model score row should carry the option names and the rubric binding (or a hash of them). Without that, a template edit that renames options silently changes what the scores mean.
  • Offer a label-free "name-invariance flip rate": re-run a sample with neutral or permuted option names, and track it next to accuracy and calibration. It costs two extra passes per sampled item and needs no human labels.
  • Langfuse's "Flag Out-of-Scope Request" (yes/no) template is exactly the shape that flipped worst here.

2. NEW rank (qualified): arXiv:2609.26529 — From Approval to Execution: Reconstruction-Aware Repair Analysis for LLM-Agent Software (Zhu, Liu, Fan, Chen, He; no affiliation given; v1, Sep 22 2026; 18 pp, read to the Data Availability statement and references)

What it is:

  • In agent frameworks, the action a human approves can be reconstructed before it executes: on workflow reload, transcript projection, argument rebinding or a durable-state lookup.
  • The executed action can then differ while the approval ID stays the same.
  • The paper formalizes "reconstruction-stable authorization". Its analyzer, APAS-Finder, decides whether a proposed fix is sufficient and where a bypass remains.

Results:

  • Frozen predictions match 28/28 controlled outcomes; baselines get 20/28 and 16/28.
  • A checked-fields-only rule separates 0/4 matched pairs; the method separates 4/4.
  • Two analysts agree on 19/20 sink dependencies.
  • In released packages, five fixes block 60/60 out-of-scope effects. On the AI SDK path, signed replay still passes (5/5) even with HMAC.

Caveats:

  • Small, purposive sample: the 28 cases are a 4-graph × 7-fix factorial.
  • Graphs are built by hand, at a median of 63 minutes each. Automated extraction recovers only 45/233 (AST) or 104/233 (CodeQL) facts.
  • The artifact is anonymous; the fixes are not confirmed by maintainers; ChatGPT/Codex use is disclosed.

TL;DR for BQAA:

  • For ADK tool-confirmation (HITL) events, log approved_action_hash over the security-relevant fields at approval time, executed_action_hash at dispatch, plus grant_id, nonce/epoch and sink.
  • "Approved ≠ executed" then becomes a one-line BigQuery anomaly query. Replay shows up as a reused nonce.
  • This pairs with ZeroGate (0034 #10): both argue approval and execution are two events, not one.

3. NEW rank (qualified): arXiv:2609.25502 — Spend Classification Without Leakage: An Evaluation Harness and What It Changed in a Deployed System (Gupta — SpendSide / Cognistone; single author; v1, Sep 21 2026; 16 pp, read to App. D Table 17)

What it is: an evaluation harness for spend classification with four split protocols, run over 1.26M public procurement lines (California and Washington). It measures how much item text repeats between train and test. It also derives a text-only ceiling from identical texts that carry conflicting labels.

Results:

  • Under a random split, 60.7% / 61.2% of test rows repeat training text. Naive Bayes scores 56.0% on repeats vs 31.9% on new text.
  • The text-only ceiling is 79.4% (CA) vs 98.4% (WA).
  • On WA, the leaky split makes 1-NN and DistilBERT look equal (87.5 vs 87.1). Leak-free splits put DistilBERT +2.3–3.6 pts ahead.
  • Deployment: reviewers accepted 351/1,084 = 32.4% of suggestions (CI 29.7–35.2). This is self-reported and labelled "corroboration, not validation."

Caveats: single author with a disclosed conflict of interest; one run per cell; the pilot data is proprietary; LLM-assisted prose. Code is released.

TL;DR for BQAA:

  • When customers build eval sets from their own traces, dedupe or split by normalized input (hash the normalized user turn). Around 60% repeated inputs silently inflate scores and can flip model rankings.
  • Keep the original suggestion and the human accept/reject as separate immutable rows; the paper's external check depended on having both.
  • Compute a per-dataset "conflicting-label ceiling" before comparing accuracies across datasets.

4. NEW rank (qualified): arXiv:2609.26781 — Agensh: Scaling Organizational Intelligence to 1,024 Agents (Zhan, Song, Dong, Huang, Lian, Xia, Wei — Microsoft Research; v1, Sep 22 2026; 13 pp, read to App. C)

What it is:

  • A multi-agent harness with no central orchestrator. Workers loop: gather context → claim → act → verify → merge.
  • They coordinate through three channels:
  • a Gitea workspace;
  • Mattermost messages;
  • an append-only shared-context board with typed entries (OBSERVED, FACT, FAIL, CLAIM, PATCH_SUMMARY) inside an event envelope (event_id, source, kind, observed_at).
  • Model: GPT-5.6-sol (high), 6h budget.

Results:

  • On the 5 hardest ProgramBench tasks, the mean final pass rate goes 19.31% → 20.68 / 26.52 / 28.78% at 1 / 8 / 32 / 128 agents.
  • On pandoc: 33.89% (1) → 50.94% (128) → 55.06% (1,024).
  • On pandoc, 128 agents pass 30% by minute 30, versus minute 90 for 8 agents.
  • Code: the paper links github.com/microsoft/Agensh, but it still returns 404 on my probe at ~15:00Z (STALE-bench, by contrast, returns 200).

Caveats:

  • One run per configuration; no variance.
  • No token or dollar cost reported, which is striking at 1,024 agents.
  • The 1,024-agent point is pandoc only.
  • The "emergent roles" are anecdotal. Vendor-authored.

TL;DR for BQAA:

  • At swarm scale, the unit of analysis is the organization, not the span. Claims, conflicts, merges and handoffs need to be first-class event rows keyed by worker.
  • The paper's own omission (cost per agent-hour, contribution per worker) is exactly the join BQAA can compute when those events land beside LLM usage.
  • Codex's new "message board instead of direct messages" option (Industry, alpha) is the same pattern arriving in a product.

5. NEW rank (qualified): arXiv:2609.25173 — Attack Success Rate Is Not a Number: On Measurement Validity in Agentic AI Security Evaluation (Pathade, Pawar, Patil — independent; v1, Sep 21 2026; 7 pp, read to the Reproducibility statement)

What it is: it defines six axes of how attack success rate (ASR) is measured: unit, oracle, trials, attacker adaptivity, defense knowledge, and the partial-success rule. It meta-analyzes 259 arXiv papers with regex detectors checked against hand coding, then adds an analytical power study.

Results:

  • 58.0% (Wilson CI 44.2–70.6, hand-coded n=50) report neither variance nor repeated runs; the automated rate is 65.3%.
  • 29.7% of judge-using papers validate the judge against human labels.
  • 10.8% state an attack budget; 2.3% state a partial-success rule.
  • On a 100-instance benchmark the minimum detectable difference is 18.2 pts. A true 5-pt gap is ranked backwards about 21% of the time (Monte Carlo .237).

Caveats: one human coder; detectors tuned on the sample used to validate them; the inversion results are analytical, not empirical; the checklist is unvalidated; no artifact.

TL;DR for BQAA:

  • An eval or red-team row needs unit_of_analysis, oracle_type, judge model and prompt version, judge-human agreement, run_index, seed and temperature, and a benign-utility pairing. Otherwise two ASRs or pass rates are not comparable.
  • On benchmarks of ~100 items, show the minimum detectable difference next to any A/B delta.

6. NEW rank (qualified): arXiv:2609.26086 — CoVeR: Coverage-Based Routing of Verifier Calls in Agentic Retrieval (Roh — independent; Han — KAIST; v1 dated Sep 3 2026, first listed Sep 22; 32 pp, read to App. J)

What it is:

  • Before each stop-verifier call in an agentic retrieval loop, CoVeR computes a cheap coverage margin from frozen E5 embeddings.
  • If the margin exceeds τ = 0.16, the verifier call is skipped. The gate can never stop the loop on its own.
  • Setup: Self-Ask with Qwen2.5-3B/7B on HotpotQA, 2Wiki and MuSiQue.

Results:

  • Verifier calls cut by 62.2% / 67.8% / 93.0% (MuSiQue is saturated), with EM within ±0.3 pp. Verifier input tokens drop 72 / 73 / 97%.
  • The margin cannot replace the verifier: AUROC with generated claims is 0.686 / 0.680 / 0.760, versus 0.89 / 0.90 / 0.83 with oracle claims.
  • It also cannot veto verifier errors (AUROC 0.39).
  • The analysis is unusually careful: pre-registered bars, paired bootstrap, TOST.

Caveats:

  • The verifier is the authors' own HALT, whose weights are not released; code is promised "on publication".
  • Single seed and scaffold; low absolute EM (0.08–0.31).
  • The HotpotQA CI does not exclude a 1 pp loss.

TL;DR for BQAA:

  • Most judge calls inside agent loops are predictable "keep going" calls. Log verifier_called, skipped_by_gate, gate margin, verdict and verifier tokens per step. Customers can then see how much judge spend was skippable.
  • This is the in-loop counterpart to Mastra's classifier-as-workflow-step.

7. NEW rank (qualified): arXiv:2609.26204 — WatchPoint: Executable User Feedback for Real-World Agentic Web Development (Yang, Liu — Stevens; Yang — UT Dallas; v1 dated Aug 10 2026, first listed Sep 22; 24 pp, read to App. K.2)

What it is:

  • After a failed attempt, two single-shot agents write Playwright and bash diagnostic scripts. These emit raw {n, v} "CHECK" facts, which are fed into the warm-start retry.
  • By design, no LLM ever interprets the output. An earlier version that let an LLM interpret it hallucinated, and Pass@1 fell from 11/20 to 4/20.
  • Tested on Web-Bench (50 projects, 1,000 tasks) with OpenHands.

Results:

  • Recovery 38/66 = 57.6%, against 45.1% for the baseline on the same categories.
  • Overall P@2 26.6% → 28.1% (GLM-5 diagnoser) / 27.9% (GPT-5.4).
  • For the stronger coder GLM-5, adding diagnostics lowered P@2 from 44.5% to 37.7%.
  • Diagnostics add under 2% to cost.

Caveats:

  • Single run per configuration. The authors' own variance analysis shows 11.5% of tasks flip between runs (about ±6 pp on P@2), which is on the order of the headline gain.
  • The "comparable to humans" claim compares 28 projects against 5 easy projects done by 2 students.
  • Log release is claimed, but no URL is given.

TL;DR for BQAA:

  • Store raw executable observations (key/value checks with feedback_source = test / browser / terminal / human and attempt_idx) separately from LLM-written summaries. Only the former are evidence.
  • Report run-to-run flip rate as the noise floor for any retry or feedback A/B.
  • Feedback helps weak agents and can hurt strong ones, so slice by model.

8. NEW rank (qualified): arXiv:2609.25396 — Passes Alone, Fails Together: Benchmarking Semantic Coordination in Parallel LLM-Agent Development (Xia, Park — UIUC; Wu — Columbia; v1, Sep 21 2026; 6 pp, EXPRESS '26 workshop; read to App. C)

What it is: STALE, a benchmark that runs the same tests on each parallel agent's patch alone and on the merged result. It counts only failures that appear after the merge. There are three tiers: synthetic, mined real PR pairs, and constructed Django tasks.

Results:

  • Mined: only 1 of 834 runs over 417 Django pairs interfered, once a grading bug the authors disclose was fixed.
  • Constructed: GPT-5.5 interfered in 105/108 (97%). A message describing the other agent's finished change recovered 89/108.
  • Synthetic: a ~130-token message cut interference from 2.50 to 0.04.

Caveats: short workshop paper; nearly all Django; the "message" condition is an ideal, complete description; only GPT-5-class models. Code is public (github.com/illinoisdata/STALE-bench).

TL;DR for BQAA:

  • The authors explicitly ask for execution records of parallel agents. The fields are a shared base commit, each agent's patch, and per-patch plus post-merge test outcomes against one suite.
  • With those, "fails only after merge" is a BigQuery query. It is the correctness companion to Agensh's scaling curve.

9. NEW rank (qualified): arXiv:2609.25645 — Efficient Cost-Aware LLM Evaluation via Bayesian Bandit Gittins Indices (Xie — Cornell/Columbia; He — NYU; Cao — NYU/SUFE; v1, Sep 22 2026; 42 pp, read to App. E.3; ICML 2026 DEMO workshop spotlight)

What it is: it treats choosing an LLM configuration as a cost-aware Bayesian bandit. Gittins indices, precomputed offline with an FFT, decide which configuration to evaluate on which example next, and when to stop. An "LCB-style" rule (posterior mean minus one SD) makes the final recommendation.

Results:

  • Offline replay over existing score tables: GSM8K 122×1000, PIQA 103×1000, AlpacaEval 152×805, MMLU 1,500 configurations × 57 subjects.
  • Stopping triggers at 1–10% of full-evaluation cost.
  • At 2% of cost, the LCB rule cuts regret from 0.0780 to 0.0080 on GSM8K and from 0.0828 to 0.0018 on MMLU Hard-Large.

Caveats:

  • The "1–2% cost" headline is read off plots only.
  • The LCB rule that drives the gains sits outside the optimality proof.
  • The cost weight and batch sizes were tuned on the same data.
  • Costs are API-price proxies; the models are old; AI helped draft the proofs. Code is released.

TL;DR for BQAA:

  • Adaptive eval needs per-(config, example) score rows with cost, tokens, batch ID and timestamp, which a trace store already has.
  • Also store the recommendation rule used; switching it moved regret about 10×.
  • A natural "stop evaluating early" feature on top of BQAA eval tables.
