Read this first

  1. NOMOS (2610.11030) compiles a written policy into a deterministic tool-call gate. It then tests the gate by replaying it over stored traces before deployment. On τ²-bench, the share of state-changing calls that violate the policy falls from 66.3% to 2.6% (airline) and from 30.8% to 6.9% (retail). Without the static checks, 8 of the 14 airline rules the compiler emits cannot function. Two findings bear directly on BQAA. First, the replay preflight is a query over recorded runs, and it caught a rule that refused 95.9% of legitimate calls. Second, the deterministic checker and a frontier LLM judge agreed on only 50% of calls (κ ≈ 0). → NEW Academy.
  2. AgentHorizon (2610.11050, ServiceNow/Mila): the same judge model scores differently depending on the harness it runs in. Judges also rarely catch side effects. Qwen 3.6 27B scores 71.6% balanced accuracy in Codex and 51.2% in OpenHands. No judge recalls more than 24.1% of "bad side effect" failures. With only the final screenshot, judging is a coin flip (49.1%). → NEW Academy.
  3. Harness Evolution Hits a Ceiling (2610.11655) labels each failed run by the first signal that fires. The labels are evidence, harness friction, loop/budget and poor content. A self-evolving harness removes loop failures but never reduces content failures. Some accepted edits never actually executed (one in the 4B line, three on WebArena-Lite). The paper also gives a concrete noise floor: 0.035 between two 4-rollout means, and up to 0.05 drift for the same configuration across nights. → NEW Academy.
  4. OpenInference for the Vercel AI SDK (3.3.0, Oct 9) now emits DECISION spans for experimental_decide. After mapping, it strips the gen_ai.* model and usage attributes from those spans. Cost rollups that read only gen_ai.usage.* will silently miss decision-model tokens. → Progress on the Phoenix DECISION-span card.
  5. crewAI 1.15.27 (Oct 9) logs why each evaluation stopped before a verdict, using a closed list of reasons. It also fixes the crewai eval --models table, which had printed totals summed over runs under per-setup columns. → Progress on the crewAI eval card.

OpenInference-Vercel 3.3.0: decision-model calls become DECISION spans and stop looking like LLM spans

Parent: arize-phoenix-20-19-0-openinference-decision-span-kind-experimental Source: https://github.com/Arize-ai/openinference/releases/tag/%40arizeai%2Fopeninference-vercel%403.3.0 (GitHub 2026-10-09T23:18:45Z; npm @arizeai/openinference-vercel@3.3.0 23:20:51Z, latest)

  • What changed: Vercel AI SDK v7 experimental_decide calls are now DECISION spans with decision.* model, provider, system and token-count attributes. The parent card noted that Phoenix 20.19.0 shipped the span kind with "no decision-specific attributes yet", so this release fills that gap for one producer.
  • Outer operation: a new enrichSpanWithOpenInference callback, passed as the OTel enrichSpan option, classifies the outer decide operation as CHAIN. That keeps model identity and usage from being counted twice. It requires ai ≥ 7.0.128 and @ai-sdk/otel ≥ 1.0.128.
  • The analytics catch: after mapping, gen_ai.provider.name, gen_ai.request.model, gen_ai.response.model and gen_ai.usage.* are removed from decision spans, so GenAI converters do not re-label them as LLM calls. Meanwhile, the still-open vercel/ai#22539 ("record gen_ai.response.model on decision model spans") moves the producer the other way. Depending on the exporter path, the same decision call can carry gen_ai.* or not.
  • Why it matters for BQAA: a cost or model rollup keyed only on gen_ai.usage.* / gen_ai.request.model drops decision tokens for OpenInference-instrumented AI SDK apps. Normalize on span kind first, then read decision.* or gen_ai.* as appropriate.

crewAI 1.15.27: every evaluation stop now has a reason, and eval --models prints per-run cost

Parent: crewai-1-15-23-crewai-eval-grades-last-traced-run-declared-vs-produced-output-spans Source: https://github.com/crewAIInc/crewAI/releases/tag/1.15.27 (GitHub 2026-10-09T22:33:44Z; PyPI crewai 1.15.27 22:34:28Z)

  • Stop reasons (#7963): each evaluation that stops before a verdict is now counted once as cli_usage:eval_stopped:<reason>. The reasons come from a closed list: untraced, declined, no_project, login_unreadable, network_error, amp_401/403/404/4xx/5xx, invalid_response, evaluation_failed, unexpected. The reason is never the error message, which could carry a path or server text. The PR states that about four in five presses of Evaluate never became an evaluation, and that telemetry previously could not say why (author's claim; see Unconfirmed).
  • Units fix (#7965): the crewai eval --models table had summed cost and time over all runs of a setup. For example, it printed $0.0061 and 46.4s for three runs, while the report said $0.0020 and 15s per run. It now prints cost / run and time / run, falls back to labelled totals only when the service sends no per-run figure, and never mixes the two units in one column.
  • Why it matters for BQAA: this is an eval-funnel pattern worth copying: count every abandoned evaluation under a closed reason enum, without the message text. The units bug is also a warning for any comparison table. Store cost per run and run count separately, and never let a column switch units.

NEW — NOMOS: Compiling Written Policies into Statically Verified Tool-Call Gates for LLM Agents — https://arxiv.org/abs/2610.11030

Yu, Kim, Choi (Corners Co.), cs.CR, submitted Oct 8. Full PDF read.

  • What it is: a four-pass compiler that turns a natural-language policy into rules over a closed predicate vocabulary. Only one pass, extraction, calls an LLM; it samples 5 times and keeps majority votes. A deterministic gate then checks each tool call in ~3 µs with no LLM call. The gate's facts come only from tool results and user turns, never from the agent's own claims (§3.1).
  • Static checks matter more than extractor size. Schema-only checks (self-blocking, write scope, argument consistency, satisfiability, wildcard scope) repair or reject 29 of 79 airline candidates and 7 of 53 retail candidates (Table 3). With no checks, airline ships 14 rules of which 8 cannot function, and retail ships 5 of which 3 cannot function. One of the retail rules deadlocks every conversation, because it blocks the very lookup tools that authenticate the user (Table 8). A frontier-model compilation produced defects in two of the same classes (§5.4).
  • Safety result: violations of the reference-encoded clauses among state-changing calls fall from 66.3% to 2.6% (airline, 234/353 → 3/116) and from 30.8% to 6.9% (retail) (Table 5). Under a looser "one confirmation covers the batch" reading, the falls are 36.8% → 2.6% and 13.6% → 5.3%. On airline, pass^2–4 improves significantly and pass^5/pass^1 rises from 0.51 to 0.67 (Table 6). Retail task success does not change significantly.
  • The BQAA-shaped part is the behavioral preflight (§3.4, Tables 4 and 9). Before deployment, the compiled rules are replayed over recorded transcripts of the undefended agent, and refusals are counted per (rule, tool) pair inside runs that passed. A development rule that passed every static check refused 47 of 49 legitimate payment-request calls (95.9%) and was flagged. The same predicate on another tool refused 0 of 44 and was kept. The unit of repair is the binding, not the rule.
  • Measurement honesty (§4): the deterministic checker and a frontier LLM judge given the same calls agreed on 50.0% of 160 calls (κ = −0.01). The judge was wrong on facts the transcript settles in 30 of 77 disagreements.
  • Injection results: on AgentDojo banking, ASR falls from 46.5% to 0.0%, and all 183 attempted attacker calls were refused (Table 11). The cost is real and depends on the domain. Benign utility falls 8.3 points on banking and 76 points on Slack (90.5% → 14.3%), where legitimate tasks act on targets the agent discovered by reading (Table 16).
  • Limits (stated by the authors):
    • The implementation (compiler, predicate evaluators, preflight) is proprietary; only rules, policies and a checker are on Zenodo.
    • The authors wrote the AgentDojo policies themselves.
    • Rules that admit history-derived targets can be poisoned through structured fields, and the benchmarks do not test this.
    • Most runs use a single 26B agent model (Llama-3.3-70B reproduces the main effect).
    • Residual violations under the gate are coverage gaps in the compiled clauses.
  • For BQAA: three columns would make this analysis possible on our tables: a block-log row per refused call (rule id, clause, tool), fact provenance per fact (tool result, user turn or agent claim), and confirmation consumption. The preflight is a query of the form "replay candidate rule × stored runs, group by (rule, tool), filter passed runs" — a natural BigQuery job.

NEW — AgentHorizon: Evaluating Agentic Judges for Long-Horizon Computer-Use Tasks — https://arxiv.org/abs/2610.11050

Lù et al. (ServiceNow Research, McGill, Mila), cs.AI, submitted Oct 8. Full PDF read.

  • Design: 1,373 human-recorded desktop trajectories (166 hours, 112 apps, median 121 steps). Annotators recorded two runs for two closely related instructions. Swapping the instructions gives negatives that look complete but do the wrong thing: 523 positives and 850 negatives (§3.2, Table 4). Each negative is typed as Critical Mistake, Bad Side Effect or Misunderstanding.
  • Headline: the best judge, GPT-5.5 inside Codex, reaches 80.9% balanced accuracy on the hard split. Gemini 3.1 Pro in Gemini CLI reaches 77.7%, and Claude Opus 4.7 in Claude Code 76.0% (Table 2). Judges differ sharply in which errors they make. For example, Qwen 3.6 27B as a direct judge accepts 93.8% of valid runs but rejects only 61.5% of invalid ones.
  • The judge's harness changes the score. With the same model, prompt and items, Qwen 3.6 27B scores 71.6% in Codex, 70.4% in OpenCode and 51.2% in OpenHands. GPT-5.5 loses 3.7 points moving from Codex to OpenCode (Table 8). Tool use does not help consistently: Qwen 3.6 27B does better as a direct judge (77.6%) than in OpenCode (70.4%).
  • Side effects are the blind spot. Exact recall for Bad Side Effect ranges from 0.0% to 24.1% across judges, against 47.6–77.7% for Critical Mistake (Table 7). In the worked example (Fig. 2), a published post includes content the user never asked for, and the judge accepts it because the run is internally consistent.
  • Inputs matter: with only the final screenshot (plus the instruction), balanced accuracy is 49.1%; without the instruction, ~49% (Table 9). Frontier agentic judging costs $0.40–$0.66 per trajectory, using 0.5–1.4M input tokens (Table 6).
  • Limits:
    • The benchmark tests subtle near-miss errors only, not loops, crashes or drift.
    • No independent inter-annotator agreement was collected.
    • The hard split is defined by three specific models.
    • It is English-only, and evidence is screenshots plus action logs, not application state.
  • For BQAA: a judge verdict row needs the judge harness as well as the judge model, or score comparisons across judges mean nothing. Side-effect checks need the full log of external writes (which channel, which recipient), not the final state.

NEW — Harness Evolution Hits a Ceiling: When Weight Training Should Begin — https://arxiv.org/abs/2610.11655

Tian, Hu et al. (independent, UC Berkeley, Purdue, Stanford), cs.AI, submitted Oct 8. Full PDF read.

  • Failure labels by first signal (§3.1). A deterministic checker labels each failed run by the first of four signals that fires. F1 (evidence): ≥ 50% of the plan's claims are unbacked by anything retrieved. F2 (harness friction): a harness intervention blocked the agent. F3 (execution control): the same call was repeated ≥ 3 times, ≥ 90% of the step budget was used, or the harness terminated the run. F4 (planning capacity): a plan was delivered but is poor. The labels need only process signals and the scorer, with no LLM annotator.
  • Result: a propose-and-verify self-evolving harness on DeepPlanning lifts held-out scores from 0.164 to 0.297 (Qwen3.5-4B) and from 0.323 to 0.442 (9B) (Table 5). For 4B, loop failures (F3) fall from 64.1% to 37.0% of runs, but F4 is never reduced (9.9% → 28.1% for 4B; 27.1% → 25.0% for 9B, Table 6). LoRA trained on evolved-harness runs adds about +0.13 held-out. A placebo adapter trained on shuffled outputs scores 0.227 below base (Table 10).
  • What carried the gain: components that give the agent capability (state ledger, lessons file, invented tools). Removing enforcement components (exit gate, checkpoint, hard blocks) leaves scores within noise, except the 4B exit gate on held-out (Tables 11–12).
  • Measurement findings worth keeping (App. A, G):
    • The noise floor is a per-rollout SD of 0.023, so two 4-rollout means must differ by > 0.035 to count.
    • The same configuration drifts by up to 0.05 across nights, so comparisons should be same-night.
    • Picking the best of K candidates inflates the reading: retained candidates read 0.316/0.327/0.323 where fresh anchors measured 0.282/0.288/0.305.
    • "Inert accepts" occurred: an edit that never executed passed the judge (one in the 4B line, three on WebArena-Lite). The authors now require evidence that an edit's code path fired before judging it.
  • Why the loop stops (§6.2): the proposer's evidence package led with gate and checkpoint metrics and never aggregated the scorer's failure composition. The loop optimized what it could see.
  • Also: the benchmark's plan-to-JSON LLM converter silently picks one draft and inflates scores by ~0.025 (App. I).
  • Limits:
    • Mostly one benchmark plus WebArena-Lite, on small open models.
    • There is no matched-budget search baseline.
    • Some 4B ablation cells use 2 rollouts.
    • The frontier-model rows (App. J) have no per-run data attached.
  • For BQAA: the F1–F4 rule is a CASE expression over trace process signals (repeat count, budget used, harness blocks, delivery), which fits BQAA's failure tables. Two practices also translate directly. Record whether each harness or config change actually executed in the run, and keep a fresh baseline after every accepted change rather than reusing the winning candidate's own score.

Six-week EV

  • Replay-before-deploy becomes the norm for agent controls. NOMOS screens new policy rules by replaying stored runs. The harness-evolution paper shows that edits can "pass" without ever executing. Both need a store of past runs that can be replayed with per-call facts and outcomes. That is BQAA's table, provided it keeps fact provenance, refusals and the "did this path fire" flag.
  • Decision spans split from LLM spans. OpenInference strips gen_ai.* from DECISION spans while vercel/ai#22539 adds gen_ai.response.model to them. Expect a few weeks of mixed shapes. BQAA rollups should branch on span kind and carry an "attribute source" flag.
  • Judge identity widens to judge harness. AgentHorizon's 20-point swing for one model across harnesses means "judge = model" is not a stable dimension. Eval tables need judge harness and version alongside judge model.
  • Deterministic failure labels gain ground over LLM labels. Both NOMOS (checker vs judge κ ≈ 0) and Harness Evolution (first-signal labels from process signals) prefer checkable labels. BQAA can offer a standard F1–F4-style CASE view over its trace tables.
  • Eval funnels get instrumented. crewAI's closed stop-reason list is a small but copyable pattern. Expect other eval CLIs to count abandoned evaluations, and BQAA to be asked for "why didn't it evaluate" breakdowns.
