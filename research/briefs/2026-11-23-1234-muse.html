Audit the grader contract, split the verdict, and instrument recovery outcomes — in that order.

1. Benchmarks' Last Exam: prompt/environment/grader agreement audit — https://arxiv.org/abs/2611.27622

Full PDF read (15 pages; fetched via curl, converted with pdftotext, read in full including methods, results, discussion and limitations). The paper synthesizes task-level quality reviews of 749 tasks across eight frontier benchmarks and 767 public model evaluations under one rubric (§1, Table 1). A task is a three-part contract — prompt, environment, grader — rated Accepted (no substantive defect), Doubtful (specific unverified concern) or Refused (confirmed defect), with five primary failure classes: C1 grader/reference logic, C2 unstated scoring rule, C3 missed critical error, C4 bypass/leak, C5 harness conflict (§2.1). Cohort totals are 346 Accepted (46.2%), 67 Doubtful (8.9%) and 336 Refused (44.9%) (Table 1).

Validity stratifies by grading architecture, not by difficulty. Revised closed-form Q&A reaches 92.5% verified Accepted (AA-Omniscience v1.1 98.0%, HLE-Diamond 87.0%) versus 30.0% for document rubrics and 28.9% for agentic execution (29.3% pooled multi-step; Fisher P = 1.3×10⁻⁵⁸, §2.2, Fig. 2). The six multi-step suites still contribute 161 verified complex tasks, so the finding is “repair and keep,” not “discard.” Failure modes differ by architecture (§2.3, Fig. 3): 94.9% of rubric defects are C1+C2 (wrong reference criteria, unstated expectations; 0% C4 because solvers never run code in the grader), while agentic suites place 48.1% of defects in C3–C5 (incomplete state assertions, leaks, grading-time collisions). Worked cases include a rubric miscoding a 100-basis-point move as 1,000 (GDP.pdf gdp-060), a checklist requiring a Slack emoji absent from the solver attachment (Harvey LAB), a sign-reversed ledger passing all eight state checks (AutomationBench), and hidden Go tests colliding with agent-written tests (DeepSWE, Fig. 6).

The directional result matters most for BQAA: 71.7% of the 336 confirmed defects penalize valid work (C1+C2+C5, 241 tasks) versus 28.3% permitting shortcuts (C3+C4, 95 tasks) (§2.4, Fig. 4). False-negative graders hit every valid trajectory down a path; shortcuts only fire when a trajectory finds the unguarded branch — so raw ceilings on unverified multi-step suites “understate what frontier models can already accomplish.” Isolation helps the shortcut direction: confirmed C4 rates run 14.7% in shared containers, 9.0% with mutable mock APIs, 2.7% with a fresh git-diff verifier container (5.5× drop, P = 8.4×10⁻⁴), and 0% read-only/static (§2.5, Fig. 5). Repairs are mapped class-by-class (Table 2): blind-solve each task from the prompt alone (C1/C2, 67.9% of defects), ship plausible broken outputs the grader must reject (C3), grade only declared outputs/diffs in a fresh container (C4), and reserve hidden-test namespaces (C5); fixing primary C1/C2 then C3–C5 defects lifts coverage 46.2% → 76.6% → 91.1% before Doubtful review (Fig. 5a).

Read the limits before citing the headline. A Refused label proves a defect exists, not how much it moved any model's aggregate — rank changes “await re-running model cohorts on patched harnesses” (§3.2). Isolation and curation contrasts compare different benchmarks (confounded by domain and authoring workflow), each task counts only its primary defect, and four suites are 100-task stratified samples with Clopper-Pearson intervals (§4.1–§4.3). Note the figure arithmetic: Refused-only counts are C1 111, C2 117, C3 63, C4 32, C5 13 (§4.2); Fig. 3a's larger numbers add Doubtful tasks (e.g. C1 124 = 111+13). For BQAA/ADK: never report an agent-eval delta without a contract audit split by defect direction — most “model failures” in this cohort are grader failures, and training against them teaches models to guess undocumented conventions (§3.1).

2. Who Grades the Agent? SplitBench privilege-separated grading — https://arxiv.org/abs/2611.27860

Full PDF read (18 pages including appendices; read in full). SplitBench treats coding-agent benchmarking as adversarial measurement: the agent's code runs during grading and has already forged reports, edited tests, read answers and interfered across cases in the wild (§1–§2.1, Table 2). The design, split verification, separates working, running and judging (Fig. 2, §4.1). The agent works in an Agent environment; only scoped changed files cross as a bounded candidate (§4.2). A trusted Oracle holds hidden data (expected answers, held-out inputs, run seed), releases only the current challenge inputs, and judges returned values outside both untrusted environments; adapters run code and report values but “contain no expected answers and make no decision” (§4.3). Each case runs in a fresh Evaluation environment from a setup snapshot, destroying cross-case state (§4.4), and network egress is limited to a provider relay plus a per-task domain allowlist (§4.5). Four goals organize the guarantee: mutual isolation, verdict integrity, test-case isolation, access control (§3.3, Table 3). Only hidden data and the seed must stay secret; grading logic may be public.

Adoption is tested by agent-driven conversion of Terminal-Bench 2.0 and DeepSWE v1.1 (§5.1, Table 4): 180 of 202 tasks convert (68/89 Terminal-Bench, 112/113 DeepSWE) at a median of “just under two hours” and “about $10 per task” at public API prices (~$3,000 total, 4.8B tokens, 92% cached). Non-converters mostly need a running service, privileges/system paths, or a speed target. During qualification, 429 tailored attacks were run: native graders accepted 230, SplitBench accepted none. Fidelity holds (Table 5): on 1,374 same-files comparisons the graders agree on 98.7% (Sonnet 99.4%, GPT 97.9%), pass counts barely move, and median attempt time is essentially unchanged (Sonnet 157s vs. 152s; GPT 280s vs. 279s). Of 18 disagreements, 5 are native-grader errors (crashed tests counted as passed), 12 reflect agents editing test files (SplitBench grades with upstream tests), and 1 is timing-dependent; 26 comparisons are excluded (including 7 symlink rejections from one conversion error), so 98.7% is agreement conditional on both grading.

The adversarial campaign is the load-bearing result (Table 6, §5.3). With full knowledge (adapter, evaluation files and Oracle code, never hidden data), SplitBench rejected 126 of 168 completed attempts (75%); with limited knowledge, 117 of 139 (84%); zero passes came through a flaw in SplitBench. Of 64 passes without solving, 47 exploit weak upstream tests across 34 tasks (native regrade passes 40 of them; Appendix E lists them), 12 rest only on public answers (out of scope), 2 are conversion errors (an ungraded server; an expected answer left in an Oracle comment), and 3 are faked implementations where candidate code running inside the adapter produces expected values without the requested implementation. A smaller native-grader campaign (96 completed, 264 stopped by safeguards) is explicitly too small for a general claim; SplitBench rejected 55 of its 71 native passes on regrade.

Limits are stated plainly (§3.4, §6.2): isolation-mechanism escapes, misuse inside an allowed service, already-published answers and weak acceptance conditions are out of scope; the Oracle “judges what the candidate does, never how” it computed it; 87 of 112 DeepSWE conversions still trust upstream-runner outcomes for regression tests (feature tests are judged by value, so forgery alone cannot pass); running-service, privileged, timing and multi-run tasks are unsupported. Evidence is empirical for two benchmarks, two fidelity agents and bounded attack budgets — not equivalence or universal resistance. For BQAA/ADK: any grader that executes candidate code in agent-controlled state and trusts its report should be migrated to value-judging outside that state, with fresh per-case environments and a secret seed; keep acceptance-strengthening (the 34 weak-test tasks) as a separate workstream, because privilege separation deliberately inherits weak tests.

3. Exercised, Rarely Recovered: recovery field evidence across 50 harnesses — https://arxiv.org/abs/2611.27090

Full PDF read (5 pages; read in full including threats to validity). Under a protocol frozen before data collection, the study grades 12 persistent runtimes, 26 coding-agent harnesses and 12 research runtimes on eight recovery mechanisms (M1 checkpoint/resume, M2 retry/timeout, M3 rollback/undo, M4 compensation of committed external effects, M5 validation gates, M6 human approval, M7 sandboxing, M8 trace logs), from L0 not found through L4 exercised (operator-attributable real-run use with recovered/partial/failed/unclear outcome), plus a production-evidence ladder E0–E5 (§II). Two blind LLM coding passes (mechanism-level κ = 0.80, weakest M5 κ = 0.51; E-level κ = 0.68), blind adjudication of 131 disagreements, re-verification of every L4/E3+/large disagreement (10 labels changed), and author checking of every final label produce a hash-locked dataset; a missing label means “not found,” not “not used.”

Recovery is exercised almost everywhere in practice — 11/12 runtimes and 25/26 harnesses have at least one L4 report — yet of 128 L4 reports only 19 fully recover, 54 are partial, 45 fail and 10 are unclear (Fig. 1, §III-B). State-restoring mechanisms fare worst: checkpoint/resume recovered 1/27 (13 failed, 13 partial), typically needing manual lock deletion or resuming without settings; rollback recovered 1/15, with failures that discarded user work or missed subagent edits. Trace logs fare best (7/25 recovered, 0 outright failures) because a persisted transcript “was what let the operator diagnose and repair the run.” Human approval splits (7 recovered, 9 failed): interrupts that stopped runaway loops sit beside bypassed or always-allowed approvals. Production evidence separates practice from research (Table I): 27 systems reach E3+, 7 reach E4, none E5, while 11/12 research runtimes stop at E1 (benchmarks) with no public operation report. The guarantee gap is sharpest at compensation (Table II, §III-C): 3 research runtimes evaluate M4 and 6 document it, but among 38 practice systems only 2 show anything at M4 — both framework clean-up, not semantic inverse actions — and “no harness or runtime exposes … saga-style compensation.”

Do not read 19/128 as a failure rate: 98/128 L4 labels rest on GitHub issues alone and “issues are filed when things break”; successful recoveries are under-reported (§III-B, §V). Further bounds: “operator” includes any attributable GitHub user (a named-organization view would be stricter; 6/7 E4 labels rest on one operator), both coders are LLM agents so κ is model–model agreement with no independent human second coder, search is bounded with two research systems coded from abstracts, the author co-authored one included research runtime (coded from public sources, private repo excluded), and labels hold at the 2026-11-09 cutoff. For BQAA/ADK the actionable read is narrower and stronger: resume and rollback are the mechanisms users rely on and publicly report failing, trace logs are the recovery substrate that works, and almost no harness measures its own recovery (L3 is “nearly empty” in practice) — so recovery outcomes belong in trace analytics as first-class measured events, not as feature-presence checkboxes.

Six-week EV

  • Grader-contract audit before any eval delta (high EV, 2–4 weeks). For every BQAA/ADK eval suite that gates a decision, sample tasks and label each Accepted/Doubtful/Refused under the prompt/environment/grader contract with C1–C5 primary classes and defect direction. Require a blind-solve from the prompt alone and 2–3 plausible broken outputs per task before freeze. Report verified-accepted rate beside every score, and quarantine penalizing defects (C1/C2/C5) from training/reward pools first — the filed prior is that ~72% of defects punish valid work, so “headroom” claims without this split are not decision-grade.
  • Split-verdict grading for code-executing evals (high EV, 3–6 weeks). Move expected values and the pass/fail decision out of any environment candidate code can touch: scoped candidate capture, fresh per-case evaluation from a setup snapshot, adapters that return bounded values only, a trusted judge holding hidden data plus a secret seed, and stored evidence for recomputation. Qualify each converted task with reference-pass, no-change-fail, mutant-agreement and tamper-attack candidates under both graders, and track the residual weak-test rate separately — isolation removes forgery, not loose acceptance conditions.
  • Recovery-outcome telemetry in BQAA traces (high EV, 2–5 weeks). Emit structured recovery events for resume, rollback, retry, approval and compensation attempts with outcome (recovered/partial/failed), state restored vs. external effect committed, and whether trace replay enabled the repair. Dashboard resume/rollback success on real runs (not feature presence), alert on partial-recovery patterns (resumed without settings, undo that discards user work, subagent edits missed), and use the field prior — full recovery is rare in public reports, trace logs are the substrate that works — until BQAA traffic replaces it.
