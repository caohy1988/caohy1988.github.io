NEW rank (boundary absorb): Vercel AI SDK ai@7.0.111 + @ai-sdk/otel@1.0.111 — experimental_evaluate gets OpenTelemetry spans, tracing-channel events and four lifecycle callbacks, giving decision-model ("Jev-shaped") calls their own trace shape; Mastra builds a typed Classifier on the same interface (@mastra/core@1.69.0-alpha.2, alpha)

What shipped (#21162, commit 31d24ce; I read the full commit message and the diffs of the telemetry docs and the event types):

  • Two CLIENT spans per call:
  • an evaluate {modelId} root span for the whole operation;
  • an evaluate {modelId} child span for the logical model call, including provider retries.
  • Both carry standard gen_ai.* provider/model attributes with gen_ai.operation.name: "evaluate". Token usage goes on the child span.
  • Opt-in content attributes: ai.evaluation.state, ai.evaluation.questions and ai.evaluation.answers. When enabled, answers are written to both spans.
  • Deliberate semconv choice: the PR explains why it does not use OTel's gen_ai.evaluation.result. That event "describes a score/label on an existing model response," whereas AI SDK evaluation is "a model operation over arbitrary state deciding between multiple questions." evaluate is therefore an AI SDK-defined custom operation name.
  • Callbacks: experimental_onEvaluateStart, experimental_onEvaluationModelCallStart, experimental_onEvaluationModelCallEnd and experimental_onEvaluateEnd. They are kept out of the stable onStart/onEnd unions.
  • The end event carries: callId, operationId: 'ai.evaluate', provider, modelId, state, questions, maxRetries, exactly one typed answer per question ID, usage, warnings, provider-declared rounding (decimal precision of probabilities/scores), providerMetadata and response (resolved model ID + timestamp).
  • Tested end-to-end against "TypeSafe AI jev-latest" (per the PR).
  • Background, pre-window and not previously carded: the evaluation-model interface itself (Experimental_EvaluationModelV4 in @ai-sdk/provider, registry support, gateway and Google evaluation models) merged Sep 16 (#20863/#20875/#20885). #20892, embedding-backed evaluation models, is still open.

Mastra, folded in (alpha only):

  • #24458 adds Classifier (@mastra/core/classifier) on AI SDK EvaluationModelV4. It asks named Choice / Score / Boolean questions about a shared state and returns calibrated answers with probabilities. The PR pitches it "for routing, guardrails, tool selection, or evaluation judgments."
  • #24738 makes classifiers first-class Mastra registrations, with typed add/remove/list/get by key or ID.
  • Status: in 1.69.0-alpha.2 only; latest is still 1.68.0 (carded at 0634). Promote to its own progress line when 1.69.0 reaches latest.

Why it's a rank and not a NOTE: the 1234 brief carded the Jev-as-judge wave from the eval-vendor side. This is the framework and SDK side of the same wave: a TypeScript SDK with very wide adoption now defines what a decision-model call looks like as a span. Mastra is already building a framework primitive on it that is explicitly meant for in-agent routing and guardrails, not just offline eval. The patch version number understates it.

Why it's a boundary absorb: npm published at 18:11:20Z Sep 22, before the 1234 as-of (~20:04Z), but no pack surfaced it and the catalog has zero hits. This is the same absorb rule the 1234 brief applied to LiteLLM v1.102.0.

Honest caveats:

  • Everything is experimental_-prefixed. The PR says the prefixes stay on "unstable public extension points," while emitted span names and attributes are meant to be semantic and stable.
  • This is not an OTel semconv change. gen_ai.operation.name: "evaluate" is vendor-defined, so other SDKs may pick different names.
  • Content capture is off by default, so answers and probabilities are only on the span if the app opts in.

TL;DR for BQAA:

  1. Decision-model calls are becoming their own event class. They are neither LLM_REQUEST nor a judge score on a prior response. BQAA's plugin and schema should decide now whether to map gen_ai.operation.name = "evaluate" spans to a distinct event type. The alternative is letting them look like chat completions with odd payloads.
  2. The fields worth keeping as typed columns (not JSON blobs):
  • per-question typed answers (choice label / score / boolean);
  • the probability vector;
  • provider-declared rounding;
  • resolved model ID;
  • retry-inclusive latency.

Academy rank 1 below shows why: q, probabilities and judge version per row are what make escalation and calibration analysis possible. 3. ADK parity question: ADK has no equivalent "typed decision call" span today. If Jev-style gates spread into agents (Mastra Classifier; REFLEX, Academy rank 4), ADK callbacks and BQAA will need a shape for them. The AI SDK's is the first concrete reference.

1. NEW rank: arXiv:2609.26550 — JEV-as-a-Judge: Accept When Confident, Escalate When Unsure (Li, Miao, Krishnan, Padman — Carnegie Mellon; v1, Sep 22 2026; 31 pp)

What it is: an independent evaluation of TypeSafe jev-1.13.0 as a decision-only judge. The judge receives a state, instructions and a typed label set, and returns a verdict plus label probabilities. Confidence is q = max label probability (Spearman 0.95–0.999 with Jev's native confidence).

  • Judges compared: Jev and 16 others: 12 hosted, from GPT-4.1 mini to GPT-6 Astra, Claude Sonnet 5 and Gemini 3.1 Pro; 2 local Qwen models; PairRM; Skywork-Reward-V2. All of them run under the same "verdict + probabilities, no rationale" contract.
  • Cascade: accept Jev when q ≥ τ, else escalate. Pairwise items are judged in both orders and the probabilities averaged.
  • Protocol:
  • thresholds are fit on a 96-pair pilot and tested on 510 disjoint pairs;
  • 642 + 670 frozen items (RewardBench, JudgeBench, HaluEval, labelled replies), plus RewardBench 2, RM-Bench and reference-free prose add-ons;
  • blind human adjudication of 183 Jev-vs-GPT-6 disagreements.
  • Funding and conflicts: NIST-funded; no TypeSafe authors and no TypeSafe conflict declared.

Evidence (Tables 1–2, 3, 11–16, 19; Fig. 2, 5):

Accuracy by benchmark:

Benchmark Jev GPT-6 Jev − GPT-6
RewardBench 92.2 93.5 −1.3 [−3.8, 1.5]
HaluEval 87.5 86.7 +0.8
JudgeBench 78.6 93.1 −14.6 [−18.9, −10.3]
RM-Bench, hard style pairs 74.8 94.6 −19.8
  • JudgeBench by domain: reasoning 68.4 vs 95.9, coding 76.2 vs 97.6.
  • Reference-free prose (Table 19): every judge is near chance (Jev 52.5%, GPT-5.4 55.0%) while reporting mean max-probability 0.90–0.96. Jev's error-detection AUROC there is 0.518.
  • Human adjudication (Table 16):
  • on JudgeBench, humans sided with GPT-6 57 times and with Jev once;
  • the RewardBench gap under adjudication is −3.0 [−5.3, −0.8];
  • 24 of 26 HaluEval "both wrong" items were label noise.
  • Cost (Fig. 2, 120-item panel): Jev $0.044 per 1k judgments at 0.152 s median, vs GPT-6 $12.18 per 1k at 1.885 s, about 277×.
  • Confidence tracks errors: pooled accuracy is 47.7% at q < 0.6 and 99.1% at q = 1. On items accepted at q ≥ 0.9, Jev ≈ GPT-6 (95.8 vs 96.5).
  • Pre-specified cascade Jev → GPT-6 at τ = 0.9 (Tables 3, 11):
  • accepts 53.7% of items;
  • 92.5% vs 93.1% accuracy (Δ −0.6 [−1.8, 0.6]);
  • 0.568 of GPT-6's fee.
  • It failed its 2-point tolerance with the GPT-5.6 fallback (−2.4).
  • Calibration does not transfer (Table 12): fitted temperatures are 0.65 / 2.15 / 4.45 across tasks, and NLL worsens out of sample on 2 of 3.
  • Order sensitivity (Table 14): swapping candidate order flips 3.2% (RewardBench) and 11.1% (JudgeBench) of Jev decisions, vs 1.5% / 0.9% for GPT-6.

Honest caveats:

  • Abstract vs body:
  • "Within three points" holds on benchmark labels; under adjudication RewardBench is exactly −3.0, with a CI reaching −5.3.
  • The abstract's "99% at lower cost" is the post-hoc single-order cascade. The pre-specified result is 99.4% at 57% of the fee on preference only.
  • "0.36% of fee" comes from a 120-item panel.
  • Exploratory additions: the cross-family comparison was expanded after the first results, and the RM-Bench and prose studies were designed afterwards.
  • Adjudication quality: one human adjudicator from the team; the second pass was by Claude (a protocol deviation); RewardBench human–LLM κ = 0.29.
  • Other limits: one Jev version; fees are estimates; cascade latency was not measured live.
  • No agent traces. Everything is single-turn preference, factuality or final-answer judging.

TL;DR for BQAA: this paper sets the evidence bar for every Jev-as-judge integration carded at 0034/0634/1234.

  1. Use Jev where it holds: reference-grounded checks (preference, evidence faithfulness, answer vs reference) at ~1/277 of the cost. Don't use it alone for code or derivation correctness or style-adversarial pairs, and don't trust any judge on reference-free agent final responses. That last case is common in agent traces.
  2. Per judgment row, store: verdict, full label probabilities, q, judge model and version, and presentation order. Default pairwise evals to both orders.
  3. Fit escalation τ and calibration per workload or segment, re-validated on held-out data, never globally.
  4. Low-q or escalated rows are the natural stratum for stronger-judge or human sampling. That is exactly the probability-sample design PP-S (2609.20758, carded at 1234) needs for per-segment intervals.

2. NEW rank (qualified): arXiv:2609.26693 — Measuring the Serving Stack Instead of the Model: Hidden Confounds in Local Tool-Use Evaluation (Tang, Zheng — Northeastern University Seattle; v1, Sep 22 2026; 9 pp; REALM @ EMNLP 2026)

What it is: a measurement study of tool-call "protocol fidelity" for small local models in a ReAct coding harness (extending LOCA-bench).

  • Per-turn label: valid / hallucinated tool / unparseable / no-call prose / non-response.
  • Conditions: native tools=, native+hint, and text-tools.
  • Models: Qwen2.5-Coder 0.5–14B, Llama-3.2-3B, Phi-3-mini and Gemma-3, on Ollama 0.30.8 Q4_K_M; 8 seeds.
  • Cross-stack probe: the same request on Ollama, llama.cpp, vLLM and SGLang.
  • Code: https://github.com/LijuanTang94/serving-confound-repo

Core finding: Ollama rejects tools= for Phi-3 and Gemma-3 with HTTP 400 before inference. The harness writes the error string as an assistant turn, so naive analysis reports a 0% model. Table 2 shows the same GGUF weights return 200 on llama.cpp. vLLM returns 400 until launched with --enable-auto-tool-choice and a parser. SGLang returns the call as text.

Evidence:

  • Table 1:
  • Qwen native 0/38/23/59/60 → native+hint 35/58/82/89/80 per-seed.
  • The largest per-seed vs turn-pooled gap is Qwen-3B native, 23 vs 79 (one looping episode dominates the pool).
  • Constrained decoding: 8/8 single-step valid calls, but weak models then loop 600–900 turns.
  • Table 3: gating replicates on a dependency-chain task.

Honest caveats:

  • Small n: 8 and 4 seeds; some denominators are 4–5 turns; HumanEval n = 6.
  • T = 1.0 with no RNG control.
  • Partly a harness artifact: the authors note BFCL and SWE-agent keep structured errors.
  • Narrow coverage: one Ollama release; vLLM and SGLang probed on two models only; no significance tests.

TL;DR for BQAA: this is a direct schema lesson.

  1. Never let a serving-layer rejection, retry exhaustion or empty response land as an ordinary LLM response row. Keep a structured status / error_type / HTTP code on LLM and tool events.
  2. Record serving provenance: backend, version, tool-call parser and template.
  3. Default dashboards to per-session rates with intervals next to event-pooled rates, and flag looping sessions that dominate pooled SQL aggregates.
  4. Productize the paper's checklist. Its three-step "diagnose a 0% tool-call rate" checklist is close to a shippable diagnostic query.

3. NEW rank (qualified): arXiv:2609.25806 — When Are Aggregate Agent Traces Diagnosable? Traffic-Governed Interpretation and Calibrated Abstention (Zhu, Chang — Blossom AI; v1, Sep 22 2026; 9 pp)

What it is: a rule for when a fault claim is allowed. Before claiming a fault from aggregated traces, a unit must pass two gates:

  • a reference-map gate: enough clean support per partition;
  • a matched runtime gate: baseline and current windows both have support ≥12 in the same partitions, in ≥14 of 15 partitions.

Otherwise the unit abstains (states: REFERENCE_ABSTAIN / RUNTIME_ABSTAIN / SIGNAL_ELIGIBLE / DETECTED / NOT_DETECTED).

  • "Affected clean traffic" (τ): the share of real visits falling in changed cells, proposed as the predictor of detectability instead of the count of changed cells.
  • Drift: a split-conformal detector triggers a baseline refresh, not a fault verdict.

Evidence:

  • Table 1: 55/72 units admitted; stable false admission 0/20 (one-sided 95% upper bound 0.139 against a pre-set ≤0.20).
  • Table 2: detection rises with traffic target (uniform masks 0/54 → 17 → 37 → 52 → 54/54), and all 44 zero-exposure cases abstained.
  • Table 3: traffic beats cell count by 0.126 nats/row in NLL (cluster-bootstrap CI [0.059, 0.192]), a 29% reduction.

Honest caveats:

  • The "agent traces" come from a tabular hotel-pricing simulator, not an LLM agent. There are no tool calls and no production traces.
  • n = 20 clusters, and the safety bound is 0.20, not 0.05; a single false admission would have failed it.
  • Thresholds are hand-set.
  • "Pre-registered" is claimed without a registry link, and no code is given.

TL;DR for BQAA: carded for the design rule, not the evidence.

  1. "No regression" is not the same as "not enough traffic to tell." Before any slice-level regression, judge diff or tool-degradation claim, require joint support in the same partitions in both windows, and return an explicit ABSTAIN / INSUFFICIENT_EVIDENCE state.
  2. Weight exposure by real traffic share, not by the number of affected categories.
  3. Drift alarms should recompute the baseline, not raise incidents.

4. NEW rank (qualified): arXiv:2609.26532 — REFLEX with Jev for Efficient Selective Control in LLM Agents (Wu, Lim — NTU Singapore; v1, Sep 22 2026; 19 pp)

What it is: Jev as an in-agent control layer, not a judge.

  • Gate: at each step Jev picks the bounded choice (tool, continue, retrieve, clarify, complete) with confidence c. If c ≥ τ and the action is executable, it runs directly; otherwise the step escalates to a strong LLM. A cheap executor fills in arguments.
  • Metrics:
  • GMR (the reduction in strong-model calls);
  • risk vs coverage and AURC;
  • cost per successful episode;
  • an error split into control / argument / termination / policy.
  • Benchmarks: REFLEX-Sim (the authors' own, 100 held-out tasks), the RF-5C factorial (1,440 decisions), BFCL, and τ²-bench (60 tasks × 5 arms).

Evidence:

  • REFLEX-Sim (Table 1): success 0.95 vs strong-only 0.88, with strong calls per task 1.12 vs 4.10. McNemar p = 0.039 on 9 discordant tasks.
  • Cross-family: GMR 0.66–0.72 with three strong fallbacks.
  • Table S9: 192 of 208 errors are on control decisions. Risk/authorization decisions are 0.512 accurate (≈ chance) while tool selection is 1.000.
  • BFCL: which function to call 0.984; whether to call 0.520, with wrong calls at mean confidence 0.778.
  • Read-vs-write intervention: irreversible-commit errors are 10.0% with a write competitor vs 1.7% with a read competitor (p = 0.0014).
  • τ²-bench: REFLEX 0.850 at $0.057 per episode vs strong-only 0.900 at $0.211. The cheap Flash→Max cascade beat it (0.917 at $0.041).
  • Table S13: run-to-run drift of strong-only at T = 0 is ±3 points, as large as the cross-family effects.

Honest caveats:

  • The headline benchmark is self-built, and τ = 0.5 was selected on the test tasks.
  • The abstract's non-inferiority claim fails the formal lower-bound test for Kimi (Table S12).
  • Samples are single-run with small n.
  • The paper retires 4 of its own 12 claims, including "beats the cheap cascade."

TL;DR for BQAA:

  1. Log gate decisions per step. If agents route steps through typed decision gates (REFLEX here, and Mastra Classifier in Industry rank 1), traces need decision type, gate confidence, τ, an escalated-or-autonomous flag, and whether the action is reversible (read vs write).
  2. Then eval can report irreversible-commit rate and risk vs coverage by decision type.
  3. Tool-selection accuracy is saturated. Eval templates should target "should the agent have acted or asked," where both Jev papers find confident errors.
  4. Show cost per success and repeated-run intervals. Single-run deltas under ~3 points are noise.

5. NEW rank (qualified): arXiv:2609.25960 — CausalLoss-Fin: Attributing Financial-Agent Loss to Decisions and Infrastructure Faults (Sharma — independent; v1, Sep 22 2026; 8 pp)

What it is: exact interventional attribution on a deterministic structural causal model of a financial-operations environment (FinalityBench).

  • Faults: each episode's delivery schedule is diffed against a fault-free one, giving named message-level faults (delay / duplicate / loss / reorder / half-commit / stale read across four systems).
  • Exact split: loss = infrastructure effect + policy differential + reference residual, with nothing left unattributed. The terms are signed, and some can be negative.
  • Shapley: splits the infrastructure term across individual messages.
  • Seven blame methods compared.
  • Code: https://github.com/abhisheksharma2411/causalloss-fin (Zenodo-archived).

Evidence (545 planted episodes):

  • The agent-only baseline (a CAR-shaped stand-in): scores 0% top-1 on all infrastructure groups (structural) and charges $114,383 to the agent (Table II).
  • Repairing what it blames recovers 0.0% of the loss, vs 100% for the minimal sufficient set at 2.3 replays per episode, against 280 for Shapley (Table III).
  • 27.8% of infra-loss episodes are non-additive (CI 23.3–32.3), and in 5.6% every single-message repair scores zero.

Honest caveats:

  • No LLM agent was run. All policies are deterministic programs, which is what makes replay exact.
  • The headline 0% is by construction.
  • Dollar figures don't reconcile ($114k charged vs $82k recoverable, unexplained), and the abstract says 3 policies where the tables show 4.
  • Single author, own benchmark, weak stand-in baseline.

TL;DR for BQAA:

  1. Agent-only attribution will blame the agent for infrastructure faults. Any "which step failed" or LLM-judge blame built only from agent spans has no other variable to point to.
  2. Log infrastructure and delivery facts as their own event types: tool-response retries, duplicates, stale reads, missing callbacks, latency.
  3. Report blame as a signed agent / infra / irreducible split, and where replay exists, as a minimal fix set rather than a single blamed step.

6. NEW rank (qualified): arXiv:2609.26048 — FIRE: Failure-Informed Runtime Engineering for Reliable Language-Model Agents (Agarwal, Jain — Failproof AI; v1, Sep 22 2026; 17 pp)

What it is: hand-written runtime policies hooked into Codex CLI v0.146.0 on UserPromptSubmit / PreToolUse / Stop.

  • Policy structure: a lexical eligibility check, a runtime trigger over action history, an action (insert an instruction or deny a tool call), and a release condition plus nudge limit.
  • Target: "procedural losses," where the agent solved the task but lost the result in delivery (e.g. a server dying with the shell).
  • Main test: a randomized five-arm panel with a timing-matched sham that separates what the instruction says from the effect of just interrupting.
  • Also: the full Terminal-Bench 2.1 suite across three GPT-5.6 tiers.
  • Artifacts: https://huggingface.co/datasets/failproofai/fire-runtime-policy-reliability

Evidence:

  • Panel (Table 3): on 14 eligible tasks, real policy 17/28 vs sham 10/28. Real minus sham +25.0 points [7.1, 46.4], p = 0.061. On silent tasks the policy never fired and success was unchanged.
  • Funnel (Table 4, deterministic log extractors, not an LLM judge):
  • risky state appeared in 24–26/28 attempts in every arm;
  • the registered corrective behavior followed in 22/24 real-policy attempts vs 11–14 in the other arms;
  • only 12 of those 22 passed.
  • Full suite (Table 5): pass@1 gains are not significant in any tier; Sol cost rises +47.7%.
  • Terra+policy vs Sol: 20/28 vs 18/28 at half the cost, p = 0.82.

Honest caveats:

  • Vendor-authored (the authors co-founded the runtime's maker; declared).
  • The abstract omits the null CIs.
  • Policies were derived from the development distribution, and Appendix H's regexes match task-specific paths despite the "no task names" claim.
  • 14 tasks with 2 attempts each.

TL;DR for BQAA: carded for the measurement shape, not the gains.

  1. Log the four-stage funnel. Risky state observed → policy fired → registered behavior → verifier pass is the cleanest observability shape for harness policies. BQAA should be able to emit and query it from ADK before_tool / after_agent callback events (policy_id, hook, decision allow/instruct/deny, nudge_count).
  2. Add a pass∧k (repeated-success) metric next to pass@k.
  3. Support a sham arm in eval A/B.
  4. Make firing breadth and cost-per-policy first-class dimensions.

7. NEW rank (qualified): arXiv:2609.26761 — A2M: Trace-Optimized Agent Hijacking in the MCP Ecosystem (Li, Wang, Zhao et al. — SIAT-CAS, NTU, SUSTech, Univ. of Macau; v1, Sep 22 2026; 19 pp)

What it is: a black-box attack on MCP agents via a malicious registered tool, in two phases:

  • Attraction: persuasive tool names and descriptions, ranked by how often they get selected.
  • Manipulation: return payloads aimed at token-burn loops, .env key exfiltration, MCP-config tampering, or reasoning derailment.

The analytics-relevant twist: an Analyzer LLM reads the victim's full execution trace to diagnose failed attempts, and an Optimizer rewrites the tool over 10 iterations. The execution trace is the optimization signal.

  • Setup: LangChain ReAct on LiveMCPBench (95 tasks, 527 tools).
  • Code: https://github.com/Lilaizhen/A2M

Evidence:

  • GLM-4.6 (Table 1): malicious-tool invocation 93.6% mean, attack success 74.4% mean, token-burn 32.4×.
  • Transfer to Qwen3-Max / DeepSeek-V3.1 / Kimi-K2 / GPT-5: invocation 63.6%, success 24.5%, cost 2.7×. GPT-5 exfiltration and config tampering: 0%.
  • Defenses: perplexity filtering and a small-model auditor fail (Table 9). FIDES-style information-flow control cuts success to 11–23% while invocation stays above 80% (Table 11).

Honest caveats:

  • Headline numbers are in-sample (optimized and evaluated on the same queries); held-out generalization is shown only for invocation.
  • Denominators imply ~40 tasks per cell, not the stated 95, and the split is unexplained.
  • Single runs, no CIs.
  • Attack success comes from an unvalidated DeepSeek-V3 judge.
  • "Outperforms all baselines" holds only on GLM. AMA beats A2M on transfer invocation in several cells.

TL;DR for BQAA: static metadata screening fails. The attack is visible only as sequence and flow patterns in trace rows, which is BQAA's lane. Candidate SQL detectors and judge rubrics:

  • per-tool self-call loop depth plus an input-token spike tied to one tool;
  • imperative "call again / blocking_condition / *_REQUIRED" language in tool-return payloads;
  • a secret-shaped value read by a file tool flowing into a third-party tool's arguments;
  • writes to MCP config paths;
  • sudden invocation share for a newly seen tool.

Always report "invoked" separately from "achieved." And keep raw tool-return content, access-controlled: the attacker's optimizer is itself a trace analyzer, and forensics without payloads is impossible.
