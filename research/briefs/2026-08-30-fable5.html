6. Databricks unified trace table (Beta)

What it actually is. Gateway-side capture: "every request and response across all Unity AI Gateway services into one Unity Catalog table in OpenTelemetry format" — "Each row in the unified trace table is one OpenTelemetry span." Producers are the gateway's model services and MCP services, not agent code. Beta per the August product notes entry dated 2026-08-21; docs page last updated 2026-08-28. (docs, Aug 2026 notes)

How it works. Account admin enables "Enhanced Unity AI Gateway beta features"; metastore admin creates the table once (<catalog>.<schema>.unity_gateway_otel_spans), after which logging applies across services with no per-endpoint opt-in; "By default, only the metastore admin who creates the trace table can read it." Schema (reference page, also 2026-08-28): record_id, time, date, service_name, service_id, trace_id, span_id, trace_state, parent_span_id, flags, name, kind (SPAN_KIND_SERVER root / SPAN_KIND_CLIENT), start/end_time_unix_nano, attributes VARIANT, dropped_attributes_count, events (primary event policy_evaluated), links, status, resource, instrumentation_scope, *_schema_url; clustered by time. Attribute keys include gen_ai.request.model, gen_ai.usage.input_tokens/output_tokens, enduser.id, mlflow.spanInputs/spanOutputs, and for MCP mcp.method.name, gen_ai.tool.name, gen_ai.tool.call.arguments, gen_ai.tool.call.result, databricks.tool.connection_type; "MLflow-compatible OTel schema". Limits: "The maximum attribute size that is logged is 3 MiB … truncated … marked with databricks.trace.payload_truncated"; "Trace log delivery is best-effort. Most traces will arrive within seconds, however for new tables, traces may take up to an hour"; "not guaranteed for 401, 403, 429, or 500 errors"; "shared trace IDs to reconstruct a full multi-hop trace are coming soon"; "Databricks does not manage the lifecycle of the trace table; without a retention policy, it grows indefinitely" — enable Auto-TTL. No pricing or region statement on the page.

Confirming the question in the brief: last night's §6 covered the MLflow / Zerobus path (SDK-emitted spans landing in _otel_spans tables, docs of Aug 19). This is a different object — gateway interception with no SDK — and was not in last night's catalog.

What people get wrong. Calling it an agent trace table. Without shared trace IDs across hops, a multi-step agent run is N unrelated root spans; the page says so. It is an LLM/MCP gateway log in OTel clothing: the analog on GCP is a Vertex/Model Armor request log, not agent_events. It also inherits the gen_ai.* naming directly into attributes VARIANT keys — a convention rename is a query rewrite for every customer. What it does better than BQAA: coverage by construction (everything through the gateway is logged, no instrumentation, no plugin drop queue) and policy evaluation on the row (policy_evaluated event).

Judgment. Peer on substrate, on a different layer. The "closest warehouse peer" label from the pack is right for the table and wrong for the content.

TL;DR for BQAA. One positioning sentence and one feature. The sentence: gateway logs give you every call; agent events give you why the call was made — TelemetrySuffBench (§10) is the citation, and mlflow.spanInputs on a gateway row is the D factor only for the single hop. The feature: policy_evaluated as a first-class event is the GUARDRAIL_DECISION event §12 asks for; BQAA has no equivalent row and should — ADK 2.0's TOOL_PAUSED with pause_kind=hitl_confirmation is the nearest thing and it is a human gate, not a policy gate. Do not chase "no instrumentation"; the plugin's best-effort queue is the cost of owning the schema, and get_drop_stats() (§4) is the honest counterpart to Databricks' "best-effort delivery" line.

8. Opik 2.2.35 — ADK span-conversion failures no longer silent

What it actually is. A Comet Opik SDK release, published 2026-08-20T17:45:42Z, whose ADK line is: "[OPIK-7972] [SDK] fix(adk): report silent span-conversion failures, and pin the fix to the deferred-class case" (PR #7900). (release)

How it works. Opik's ADK integration converts ADK callback events into Opik spans; when conversion of a deferred-class object failed, the span was dropped without a signal. The fix surfaces the failure. Releases 2.2.36 (Aug 21) through 2.2.44 (Aug 28) carry no further ADK lines; the only earlier ADK fix in the 2.2 series is 2.2.8 (2026-07-28): "recover ADK LLM spans when ContextCacheConfig detaches the async context."

What people get wrong. That this is a competitor feature. It is a competitor reliability bug of the same class BQAA's plugin already reports through get_drop_stats() — the difference is that BQAA counts drops per reason and Opik, until Aug 20, did not count them at all. The two ADK fixes in a month (context-cache detachment, deferred-class conversion) are also a map of where ADK's event model is hard to project onto a span model: async-context detachment and lazily-materialised content.

Judgment. Peer; low threat. Progress line, not a section, going forward.

TL;DR for BQAA. Cite it once in the plugin's reliability docs as external evidence that silent loss is the default failure mode for ADK exporters, then move on. The actionable part is internal: make sure arrow_prep_failed (the BQAA analog of a span-conversion failure) is tested against the same deferred-class ADK objects Opik tripped on.

9. Snowflake Cortex Agent evaluations — TSA / TEA (Public Preview)

What it actually is. Warehouse-native evaluation of Cortex Agents on Snowflake's Goal-Plan-Action framing with four system metrics: tool_selection_accuracy (Public Preview), tool_execution_accuracy (Public Preview), answer_correctness, logical_consistency (reference-free). The word "trajectory" does not appear on the page. No last-updated stamp; GPA metrics went GA 2026-03-13 per the release note; the Preview ship date of TSA/TEA is not on the page. (docs)

How it works. TSA is deterministic: matched tools / max(expected entries, actual calls), order-insensitive, "penalizes every failure mode: too few calls, too many calls, or the wrong tools." TEA is an LLM judge over tool input/output quality against ground-truth invocations; an expected tool never invoked scores 0.0; extra tools do not penalize TEA. Judge families are versioned (v1 claude-4-sonnet; v2 claude-sonnet-4-5 / gpt-5.2; v3 claude-sonnet-4-6 / gpt-5.4). Runs are started with EXECUTE_AI_EVALUATION('START', …, '@stage/config.yaml') and read back through table functions (GET_AI_EVALUATION_DATA, GET_AI_RECORD_TRACE, GET_AI_OBSERVABILITY_LOGS); results carry METRIC_CALLS with per-call criteria, explanation and token counts. Limitations: no MCP tools during eval; TSA/TEA skip code-execution and skill invocations.

What people get wrong. Reading "GPA" as a process-reward story. TSA is a set-overlap ratio and TEA is a judge; neither scores order, loops, or intermediate state. It is Snowflake's version of BQAA's trajectory matching + rubrics, inside one product, with a versioned judge family — the versioning is the part that is ahead.

Judgment. Peer; included because it beats nothing on EV but confirms the shape of the warehouse-native consensus: deterministic set metric + versioned judge + results table with per-call explanations. Does not displace Databricks or LangSmith in the catalog.

TL;DR for BQAA. Copy two small things. (1) The TSA formula as a deterministic metric in the SDK's trajectory matcher — matched / max(expected, actual) is order-free, penalizes over-calling, and needs no model; today match_golden_qa is answer-side only. (2) A judge_version column on every rubric result — Snowflake's v1/v2/v3 families are the same concept as #435's evaluation_run_id binding "judge endpoint/model/execution mode", and putting it on the row now costs nothing.

10. TelemetrySuffBench — Zhu & Pu, East China Normal University, arXiv 2608.07899

What it actually is. A controlled benchmark that holds the execution and the gold fault origin fixed and varies only what the diagnoser is allowed to see. It is the first paper to measure telemetry sufficiency as a variable, separate from model capability. Submitted 8 Aug 2026 (the pack's "~Aug 11" is the aggregator date, not the arXiv date). (abs)

How it works. 312 traces (96 clean controls + 216 fault traces in 108 matched two-origin groups, 24 origins at each of nine components: agent, planning, reasoning, retrieval, memory, tool call, guardrail, delegation, LLM call), three domains, four topologies, plus a frozen 216-trace blind holdout. Six views per trace: Full, Content-redacted, Metadata, Structural, OpenTelemetry-compatible, OpenInference-compatible. Seven factor masks: I identity/event semantics, D decision and latent-reference content, P registry/provenance mappings, R propagation/handoff relations, S tool inputs and state transitions, V observation/verifier evidence, T terminal status. Five models: GPT-5.5, GPT-5.6 Sol, DeepSeek-V4-Pro, Claude Opus 5, Qwen 3.7 Max. Results, verbatim from the abstract: "With full telemetry, origin-step Top-1 accuracy ranges from 33.8% to 97.2% across models. Metadata, OpenTelemetry-compatible, and OpenInference-compatible views retain 99.5% to 100% detection F1 while limiting origin-step accuracy to at most 0.5%." Removing D "reduces origin-step accuracy to zero for every model" (component accuracy falls to 11.1%); removing P costs 19.4–79.9 points depending on model; the subset I+D+P+V reaches 86.1–100% step accuracy while D+P+V alone reaches only 5.6–61.8%. On the OTel view, 99.0% of origin predictions "land on the downstream symptom". A stress test on 218 public TraceElephant traces: Full view yields 9.6–24.3% decisive-event Top-1; content-redacted yields zero. Reproduction cost ≈ US$2,400.

What people get wrong. Three things. First, the pack's framing "OTel vs OpenInference" as two shapes: the paper says "the two compatibility renderers use the same conservative generic field set", so they are one projection, not a contrast. Second, reading "≤0.5%" as "LLMs cannot localize". With the Full view the best model localizes 97.2% of synthetic origins; the ceiling is the telemetry, not the judge. Third — and this is the one that matters for the thesis — assuming this contradicts LongRCA's 24.1%. It does not. TelemetrySuffBench says content-plus-provenance is necessary (drop D → 0%); LongRCA says on natural long traces even full content is not sufficient (24.1% exact step, 39.5% human agreement). The TraceElephant appendix is the bridge: on real traces the Full view drops from 97% to 9.6–24.3% — the same band as LongRCA.

Judgment. Highest-EV paper of the week. Peer to the #435 decision model; it does not threaten anything BQAA ships, it tells you which columns make attribution jobs possible at all.

TL;DR for BQAA. Map the seven factors to agent_events and you get the real answer to "does the warehouse support forensics": I ✔ (event_type, agent, invocation_id); D ✔ only if content is retained — LLM_RESPONSE text is the decision content, and every redaction mode (payload_column_denylist, Amplitude-style metadata_only) deletes exactly the factor that carries 100% of localization; P ◐ — tool provenance (LOCAL/MCP/SUB_AGENT/A2A) exists, a registry mapping "which tool definition was bound at this call" does not; R ◐ — AGENT_TRANSFER in ADK 2.0, parent-span link via attributes.otel only when enable_otel_correlation is on; S ✔ tool args/results; V ✗ — no verifier-evidence column; T ✔ status. So BQAA is closer to the I+D+P+S view (86–100% synthetic ceiling) than to the OTel view (0.5%) — provided content is kept. Two shipping consequences: (1) the retention/redaction docs must say explicitly that redacting LLM text turns the warehouse into a detection store; (2) the #435 MVP should record, per session, which factors were present (telemetry_factors bitmask) so a localization number is never reported over a denominator that mixes redacted and full sessions. Do not cite the 97.2% as a BQAA capability; cite the TraceElephant 9.6–24.3% next to LongRCA's 24.1% as the honest band.

11. Agent-Native Telemetry / ATP — He & Yu, OpenKedge.io, arXiv 2608.16178

What it actually is. A proposal that operational telemetry for agent consumers should be a signed, hash-chained ledger of typed state deltas (Transitions, Observations, Relations, State Checkpoints) under content-addressed schemas, with free text isolated as digest-verified blobs; plus a "verified negative" theorem — a query can prove an event did not happen if coverage is complete. Submitted 17 Aug 2026. cs.DC, not cs.DB. (abs)

How it works. Records are binary tuples schema_ref | entity_ref | time_delta | presence_bitmap | positional_values. Producers Merkle-root and sign each batch, chain it to the previous root, and a collector verifies signature/schema/continuity before atomic append; independent checkpoints defeat suffix deletion; read-time range verification emits a coverage receipt {complete, truncated, tampered, gap}. Two read paths: a stateless positional decoder and a stateful graph gateway serving "bounded graph capsules". Numbers, all confirmed on the page: vs OTel JSON at 512.4±54.2 B/record, ATP is 18.4±3.8 B/record — "reduces raw wire payload and modeled cloud query scan costs by 96.4%"; the same table gives OTLP Protobuf 148.6±16.8 B/record (−71.0%), CLP −91.8%, LogCrisp −93.9%. Token reduction: 34,180 tokens per incident triage with Claude-3.5-Sonnet on OTel JSON → 11,460 with the stateless decoder (−66.5%) → 3,820 with the semantic gateway (−88.8%); query operations 7.1 → 2.4 (−66.2%). 500/500 storage mutations detected; 0/50 prompt injections per ATP config vs 39/50 on raw text and 31/50 on OTel logs. 60/60 verified negatives correct vs a 26.7% false-suspect rate under baselines. Benchmarks: AIOpsLab HotelReservation (18 Go microservices) and OTel Astronomy Shop (14 services), 120 injected incidents.

What people get wrong. Reading −96.4% as a warehouse number. It is bytes-per-record of JSON text versus a positional binary encoding, and "modeled" scan cost is derived from that byte count. BigQuery does not scan JSON text; it scans compressed columns, and agent_events already promotes hot fields to typed columns with attributes as JSON only for the tail. Against ATP's own OTLP-protobuf row the gap is ≈−87.6% (18.4/148.6), and against a columnar store the honest comparison is unknown because the paper does not run one. The token number is real but it is a read-path result (a graph gateway that returns capsules instead of raw rows) and it was measured with Claude-3.5-Sonnet, a 2024 model, on microservice incidents — not agent traces. The verified-negative theorem is the genuinely new idea and it is about coverage receipts, not encoding.

Judgment. Distractor on encoding; peer on one idea (coverage receipt). Not a competing warehouse — there is no query engine, no join, no retention story.

TL;DR for BQAA. Ignore the encoding claim; do not benchmark against it. Copy the coverage receipt: get_drop_stats() already exists on the plugin (see §4), which is exactly the input a verified-negative needs. Persist it — a plugin_drop_stats row per invocation (or a session-level coverage column: complete | truncated | gap) turns "no TOOL_ERROR rows for this session" from an absence into a certified negative. That is a one-column change and it is the difference between a dashboard and evidence. It also answers TelemetrySuffBench's abstention result from the other side: a judge should abstain when coverage ≠ complete.

12. AgentChaosBench — Zhang, Li, Tian, Bachras, Jacobsen, University of Toronto, arXiv 2608.14680

What it actually is. A fault-injection benchmark over production-shaped traces: five A2A+MCP applications, ten operational faults injected at tool/model/guardrail/inter-agent boundaries, traces recorded by Langfuse and sanitized. Submitted 4 Aug 2026. (abs)

How it works. 5 apps × 11 conditions × 5 = 275 traces (250 faulty, 25 clean), each faulty trace paired with the clean run of the same input. Faults: Tool Failure, A2A Timeout (availability); Tool Latency, A2A Latency ~15 s (performance); Infinite Loop (≥3 identical calls), Tool Misroute, Agent Misroute (control/routing); Context Overflow (>1.3× clean), Output Corruption, Guardrail Bypass — "the guardrail records pass for a policy-violating request" (data/policy). Span kinds in the Langfuse trace: AGENT, LLM_CALL, TOOL_CALL, MEMORY, A2A delegation, guardrail. Agents themselves run on Qwen3.5-9B. Zero-shot diagnosis on a one-line-per-span view: local ≤14B models 13.6–19.2% top-1 fault type; DeepSeek-v4-pro 24.8% (34.0% top-3); type+location 22% for DeepSeek, 8–16% local; random 9%. Guardrail Bypass "is usually predicted as No Fault", and a paired clean reference makes it "unmoved or slightly worse (−5 to 0 points)".

What people get wrong. Treating 24.8% as a judge-quality number. Half the taxonomy is deterministic from telemetry: Infinite Loop is COUNT(*) ≥ 3 over identical calls; Tool Latency / A2A Latency are a duration threshold; Tool Failure is status='ERROR'; Context Overflow is a length ratio against the paired clean run. An LLM scoring 25% on a task where SQL scores near 100% on four of ten classes is a statement about the baseline design, not the ceiling. The real result is the other half: Guardrail Bypass is invisible in a single trace and in a paired trace, because a forged pass looks like a real pass. That is a policy-ground-truth problem, not a telemetry problem — no column fixes it.

Judgment. Peer; the fault list is a free spec for deterministic views.

TL;DR for BQAA. This is the specification for v_tool_repeat and its siblings. Ship four deterministic session-level flags straight from the taxonomy: loop (≥3 identical tool+args), latency_outlier (span duration vs per-tool p95), misroute (tool called by an agent that has no binding for it — needs the P factor from §10), overflow (output length ratio vs session median). Those four plus status='ERROR' cover six of ten AgentChaosBench classes with no model call. For the remaining four, the honest label is unknown. Guardrail Bypass is the argument for an explicit GUARDRAIL_DECISION event with the policy version attached — without policy ground truth in the row, no consumer can ever catch a forged pass, and BQAA should say so rather than promise it.

13. llmmas-otel — Seyedghorban, Klimov, van Deursen, Panichella, Kulahcioglu Ozkan, TU Delft / JetBrains Research, ICST 2026, arXiv 2608.24271

What it actually is. A framework-agnostic wrapper that emits OTel spans for session / segment / agent-step / A2A send-receive / tool call / LLM call, and injects faults at the same boundaries so baseline and faulty runs share a span skeleton. Published at ICST 2026 (DOI 10.1109/ICST69053.2026.00037 in the full text; the abs page does not name the venue); arXiv v1 25 Aug 2026. (abs)

How it works. Attribute table (confirmed): session.id; segment.name/order/origin; agent.id, step.index; A2A: source_agent.id, target_agent.id, edge.id, message.id, channel, message.preview, message.sha256; tool: operation.name, tool.name, tool.type, tool.call.id, tool.args.preview, tool.args.sha256; LLM: provider.name, request.model, request.id, llm.input.preview, llm.input.sha256; fault: fault.injected, fault.type, fault.spec_id, fault.decision. Faults: A2A delay/drop/truncate; tool delay/not_installed/timeout/malformed; LLM delay/rate_limit/timeout/network_error/malformed. Validation on ChatDev × 30 ProgramDev tasks × 5 repeats with 1,000 ms injections: a single LLM delay amplifies to mean 48.1× (median 13.9×); an A2A delay to mean 59.2× (median 6.6×); the two-agent demo stays ≈1.05×.

What people get wrong. Quoting 59.2× as the effect. The median is 6.6×; the mean is a tail statistic from runs where one delayed message triggered retries or re-planning. The interesting engineering fact is the shape, not the magnitude: latency in an A2A hop is amplified by control-flow, so per-span latency dashboards understate session impact by an order of magnitude on the tail.

Judgment. Peer; schema donor.

TL;DR for BQAA. Two columns to steal, both cheap: *.sha256 content digests next to every *.preview (lets you join identical messages/args across sessions without storing or comparing text — this is also how v_tool_repeat should key its "identical args" test instead of hashing at query time), and a nullable fault.* group so that chaos runs land in the same agent_events table as production and are comparable by segment.order. The A2A edge attributes (source_agent.id, target_agent.id, edge.id) are the interaction-edge key that §16 (Model or Harness) needs; ADK's AGENT_TRANSFER event carries the endpoints but not an edge.id.

14. AgentTrails — Wu, Castelo, Liu, Silva, Freire, NYU, VLDB 2026 DASHSys workshop, arXiv 2607.18816

What it actually is. Post-hoc provenance: convert a chronological tool-call log into a bipartite provenance graph (activities = tool calls; entities = inputs/outputs/artifacts), recover usedBy edges from identifiers, paths, URLs and value reuse with a constrained LLM patch step only on remaining candidates, then align many traces into a joined quotient graph by clustering "activity capsules". Submitted 21 Jul 2026; 4-page short paper accepted at DASHSys 2026, co-located with VLDB 2026. (abs)

How it works. Deterministic skeleton first: entity e_j → activity a_i when recovered keys of e_j intersect the argument refs of call c_i with j<i (acyclic by construction); weaker semantic matches (shared values, query terms, columns) become candidates; LLM refinement returns graph patch ops accepted only if they preserve node validity, temporal order and schema. Capsules = (tool identity, I/O structure, local graph context, upstream root lineage); similarity is a weighted sum of Jaccard/cosine terms; each cluster becomes a joined node carrying supporting traces, support counts and per-trace multiplicity. Evaluation: "we hand-annotated 10 traces with 234 gold dependency edges; preliminary results are promising and a full staged evaluation is underway." No precision/recall figure anywhere on the page.

What people get wrong. Citing it as a result. It is a design and a demo (SciAgentGym physics task 27, Discovera gene-set task). What it does establish is the correct order of operations for provenance recovery over a warehouse: deterministic key-intersection first, LLM only on residual candidates, and hard constraints on what the LLM may write.

Judgment. Peer; the closest data-systems-venue statement of BQAA's context-graph direction.

TL;DR for BQAA. The deterministic skeleton is a SQL job over agent_events: for each TOOL_STARTING, intersect JSON_EXTRACT_STRING_ARRAY-style key sets from its args with the ids/paths/URLs found in earlier TOOL_COMPLETED results in the same invocation → usedBy edge table. That is the context-graph edge set with zero model calls; run it before any LLM patch. The quotient join is the cross-session view the #435 P-tax study needs (which workflows are shared, which branches are low-support) and it is a GROUP BY over capsule hashes once tool.args.sha256 (§13) exists. Do not adopt the LLM patch step until the authors publish the 234-edge precision.

15. AgentDebugX — Zhu et al., UIUC / Toronto / Google / Stanford, arXiv 2607.18754

What it actually is. An open-source Detect → Attribute → Recover → Rerun loop over a portable AgentTrajectory of AgentEvents, with a multi-turn diagnoser (DeepDebug: global read, structure-guided investigation, cross-examination, adjudication), a 19-mode seed taxonomy, and OTel GenAI span export. Submitted 21 Jul 2026. (abs)

How it works. Who&When (n=184; 126 algorithm-generated, 58 hand-crafted) with qwen3.5-9b: agent / step-exact / agent+step-exact — rule heuristic 14.1 / 1.6 / 1.6; all-at-once 47.8 / 22.3 / 21.7; DeepDebug 56.0 / 28.8 / 28.8; ±1-step tolerance lifts DeepDebug to 32.1. On qwen3.6-27b the strict gain shrinks to 38.0 vs 36.4. Appendix C: on hosted backbones (gpt-5.4-mini, gemini-3.5-flash) "a single global reading is already stronger". GAIA validation (165 tasks), policy = qwen3.5-9b Open-Deep-Research: DeepDebug repairs 13/73 failed tasks in one rerun vs CRITIC 4, AutoManual 5, Reflexion 6; overall 55.8% → 63.6%, with the gain at L1 (77.4 → 81.1) and L2 (48.8 → 61.6) and none at L3. Recover is suggest-only behind a human/policy gate; Rerun scores the branch beside the original.

What people get wrong. "The named loop exists; BQAA should copy it." The loop is named, and the shape is right (attribute → propose → rerun → score beside original, never in place). But the attribution number is 28.8% on a 9B model, 38.0% on a 27B, and the paper's own appendix says the multi-turn machinery stops helping on frontier backbones. So the loop's value is Recover/Rerun on an injected benchmark (GAIA L1/L2), not Attribute — which is the same LongRCA / TelemetrySuffBench lesson from a third direction: the diagnoser is not the bottleneck; the evidence is.

Judgment. Peer on loop shape; distractor on attribution accuracy.

TL;DR for BQAA. Take the four verbs and the gate, leave the model. The BQAA loop last night's brief named — cluster → dataset → re-score — maps to Detect → (no Attribute) → Rerun → score, which is the half of AgentDebugX that actually moved GAIA. Concretely: issues table (deterministic clusters from §12's flags + failure_attribution rubric at the role level only) → match_golden_qa seeds → GraderPipeline re-score of the rerun stored as a new evaluation_run_id, never overwriting the original. AgentDebugX's AgentTrajectory is also a reasonable interchange shape for a bq-agent-sdk export agentdebugx — low priority, but it is the second external consumer format after LangSmith re-export.

16. Model or Harness? — Raj, Gupta, Mahmoud, Dumitru, Yi, Sabharwal, He, Scale AI, arXiv 2607.28802

What it actually is. An interaction-centric failure taxonomy: 41 failure modes, each assigned to an edge between two components (model, owner, grader, third parties, context, memory, tool, local/external environment; grouped into User / Harness / Environment families; multi-agent as model—model with role peer|subagent) and a fault side naming which end owns the repair. Attribution rule: "the earliest failure from which execution does not recover". Submitted 30 Jul 2026. (abs)

How it works. Notation comp1 — comp2 · fault: side, e.g. tool — model · fault: model. 36 of 41 modes are model-side, 5 on surrounding components. Grounded in 40 worked examples (E1–E40) from public benchmarks, system cards, reports and logged trajectories — "illustrative rather than exhaustive". Judge reproducibility on those 40: GPT-5.5 κ=0.76 vs human category labels (category acc/F1 0.80/0.69; failure-mode acc/F1 0.72/0.64); Claude Opus 4.6/4.7/4.8 κ=0.71/0.71/0.70; best pairwise κ=0.84 (Opus 4.6 vs 4.8).

What people get wrong. Reading κ=0.76 as a validated taxonomy. It is 40 hand-picked examples, and the failure-mode-level (not category-level) agreement is 0.64 F1. What the paper gets right is structural: the unit of attribution is an edge plus a side, and the side is what makes a label actionable (post-train vs scaffold vs environment vs grader). Who&When Pro's 18 modes and MAST's 14 are lists of what went wrong; this is the first taxonomy whose primary key is where the fix goes.

Judgment. Peer; directly changes the #435 column design.

TL;DR for BQAA. Yes — #435 needs fault_edge and fault_side more than a 19th mode. The three session-level columns last night's brief ranked (loop/thrash, failure_mode, responsible_role + confidence) should be re-cut so that responsible_role becomes fault_edge STRUCT<src STRING, dst STRING> + fault_side STRING ∈ {model, harness, environment, grader, user}, with failure_mode as a secondary enum under the edge. That is cheaper, not dearer: the edge set for an ADK agent is enumerable from the event stream (model—tool from TOOL_STARTING, model—model from AGENT_TRANSFER, model—context from EVENT_COMPACTION, model—owner from TOOL_PAUSED/HITL), so the judge chooses among a handful of observed edges instead of 41 modes. Keep the 40-example caveat in the docs; do not cite κ=0.76 as a target for the #435 κ≥0.6 gate — different task, different n.

17. Safety Does Not Compose / LoopHarness — Wu et al., arXiv 2608.27141

What it actually is. A separation result: against an attack whose evidence is fragmented across s ≥ 2 iterations of an autonomous loop (each fragment distributed exactly like benign traffic; the capability appears only when all fragments coexist in persistent state), every trajectory-scoped monitor has TPR = FPR regardless of capacity, while a monitor that reads cross-iteration state gets TPR 1 at FPR 0. A geometrically decaying risk score does not fix it: the cooling-off wait k* = ⌊log(ρ/θ)/log(1/γ)⌋+1 is a constant independent of horizon N. Submitted 27 Aug 2026, cs.CR. (abs)

How it works. LoopHarness: five never-reset components — intake/provenance monitor; cross-iteration risk cumulant Ξ_i = max(r_i, γ_i Ξ_{i−1}) with γ latching to 1 once a loop-structural flag fires; a memory-integrity guard (HMAC hash-chained append-only log + checkpoints); a stopping arbiter; a compounding-risk governor with budget B. Bound on unauthorized irreversible actions E[U] ≤ B + m − 1 + m/δ_M, constant in N; the B+m−1 term is model-free and survives a colluding verifier. Evaluation on Agent-SafetyBench: Track B (attacks with no lexical tells; 200 episodes per family) — trajectory-only baselines B0–B3 at 88.4–97.6% ASR; full LoopHarness B4 at 0.1% ASR with 96.9% clean goal completion; removing the latch alone restores 97.0% ASR. Track A: baseline cASR grows 2.9% → 6.2% from N=5 to N=10; B4 stays 0%.

What people get wrong. Reading this as a runtime-safety paper with no analytics content. The theorem is a statement about which table the monitor reads. Any evaluator that is scoped to one invocation_id — every per-invocation rubric BQAA ships, every LangSmith thread evaluator, every Langfuse Monitor over an observation window — is a trajectory-scoped monitor in the paper's sense, and the theorem says it cannot see an s-fragmented pattern by construction, not by weakness. The fix is not a better judge; it is a non-decaying, session-or-loop-scoped state column that the judge reads.

Judgment. Peer; reframes v_tool_repeat as necessary-not-sufficient.

TL;DR for BQAA. agent_events is per-event and per-invocation; the persistent object that spans iterations is session_id (and, for ADK 2.0, AGENT_STATE_CHECKPOINT). Ship a non-resetting session-level risk latch as a view first (v_session_risk: MAX() over per-invocation flags, monotone, never windowed), and note in the docs that windowed or decayed aggregations of v_tool_repeat are exactly the construction the paper proves blind. Longer term, the memory-integrity guard is the same object as ATP's coverage receipt (§11): a hash-chained AGENT_STATE_CHECKPOINT stream would make "state was not tampered between iterations" a certifiable query. That is a plugin change, not an SDK change, and it is the one place this brief recommends touching the write path.

18. Intent-as-a-Tool — Zhang et al., Tsinghua et al., arXiv 2608.27348

What it actually is. Add a zero-parameter "intent tool" D_b per target behaviour b to the action space, instruct the model to call it once it has decided to do b and before executing; the next-token probability of the tool name at each reasoning prefix is then a judge-free, dense intent score. Submitted 27 Aug 2026. (abs)

How it works. Scenarios from Anthropic's Agentic Misalignment suite (blackmail, leaking, murder), 234 cases × 3 rollouts = 702 per model-scenario; five open models (Gemma-4-31B-IT, Qwen3.5-27B, Qwen3-235B-A22B, Qwen3-32B, Qwen3-8B). Score = p(D_b | prefix) at sentence boundaries with max_tokens=1. Online intervention: when the intent tool has the highest tool preference, append a first-person reflection and resume. Qwen3-32B: 100.0 / 96.5 / 98.9% of risky cases intervened successfully vs 80.0 / 78.9 / 63.4% for prompting; Gemma-4-31B is the reverse (31.2 / 18.6 / 57.8 vs 99.2 / 55.0 / 89.0). Requires logprobs; closed models out of scope.

What people get wrong. Logging the intent tool as a tool. If D_b is emitted as TOOL_STARTING/TOOL_COMPLETED, every downstream view (v_tool_repeat, tool error rate, cost per tool) is polluted by a call that has no side effect, and the one thing that makes it valuable — the probability at each prefix — is lost because BQAA records calls, not logits.

Judgment. Distractor for the SDK; a one-line spec for the plugin.

TL;DR for BQAA. Reserve an event type INTENT_DECLARED (or tool_origin = INTENT) with attributes.intent = {behavior, score, prefix_index}, excluded from all tool views by default. It costs nothing now and prevents the pollution later. Do not build the scoring; ADK does not expose logprobs and Gemini-hosted models are out of the paper's scope.

Academic thesis for BQAA

Last night: academia is ahead on what to measure, industry on the write path. This morning the papers say what the row must contain for measurement to be possible at all, and they agree with each other.

  • Sufficiency (TelemetrySuffBench). Detection is free (99.5–100% F1 on any view). Localization needs decision content (drop it → 0%) and provenance (drop it → −19 to −80 points). The OTel/OpenInference projection is a detection store. agent_events is not an OTel projection — unless redacted into one.
  • Length (LongRCA, unchanged; TraceElephant appendix of §10). Even with full content, natural long traces give 9.6–24.3% (TelemetrySuffBench on TraceElephant) and 24.1% (LongRCA). Both papers land in the same band from opposite directions; that band is the honest number for any span-level claim.
  • Diagnoser (AgentDebugX, AgentChaosBench). Better diagnosis loops move attribution by single digits on small models and stop helping on frontier ones (§15 App. C); zero-shot on production-shaped traces is 24.8% type / 22% type+location (§12). Half of AgentChaosBench's classes are SQL. The model is not the bottleneck.
  • Unit of attribution (Model or Harness). Edge + fault side, not mode. 41 modes on 40 examples with κ=0.76 is a schema proposal, not a validated taxonomy; the schema is right.
  • Scope of the monitor (LoopHarness). Any per-invocation evaluator has TPR = FPR against evidence fragmented across iterations. Session-level, non-decaying state is a theorem, not a preference.
  • Coverage (ATP, Traccia, LoopHarness). Three papers in six weeks want a hash-chained, coverage-certified trace. BQAA has the input (get_drop_stats()) and does not persist it.

This gates #435 exactly as last night, with one addition: the MVP's denominator must carry which telemetry factors were present per session (redaction mode, enable_otel_correlation, producer) or every localization number will be computed over a mixed population and be unreportable. The factor bitmask is the next column on the manifest.
