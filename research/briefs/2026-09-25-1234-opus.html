Theme 1: evaluation data that was quietly wrong, now fixed in shipped releases.

  • Opik 2.2.81:
  • An online evaluation rule stored its duration filter in seconds, exactly as typed, but the backend compared it against milliseconds. So Duration > 5 matched "every trace slower than 5ms — effectively all of them", and an LLM-judge rule meant for the slow tail judged every trace (#8544).
  • Models from 19 providers, including OpenRouter, Azure AI and Vercel AI Gateway, "silently cost zero", because their price rows were dropped (#8548).
  • Weave 0.53.11: when two sibling spans started at the same instant, the one that ended last was listed first. A transcript then showed "Script ran, done." ahead of the Shell call it described. A judge reading such transcripts "reported a false success claim on 12 of 31 checked Cursor traces" (#7952).
  • mem0 2.2.1: when the vector store rejected records, add() still returned them as ADD events and wrote ADD history rows for memories that were never stored (#7066).
  • LangSmith SDK 0.14.1: the OTel export of LangChain runs carried no gen_ai.tool.call.id on tool spans and no gen_ai.tool.definitions on model spans (#3584).
  • Letta Code 0.33.2 (no pack reported it): a workflow step that returned the wrong JSON shape "quietly produc[ed] an empty list" (#4707).

Theme 2: one dependency release broke a tracing SDK on fresh installs. OpenTelemetry Python 1.45.0 (noted at 0634) moved its OTLP/HTTP exporter onto a new transport and removed two private attributes. Weave read both. Every fresh pip install of weave 0.53.8–0.53.10 then failed in weave.init(). Weave's CI did not catch it, because it installs from a lockfile pinned to OTel 1.42.1. Weave 0.53.11 caps the exporter below 1.45. Logfire had already capped below 1.45. I found no other watched SDK that reads the removed attributes.

Theme 3: what an evaluation must log to be checkable.

  • 2609.29454 measures skill use from session traces. Skills changed results only in the configuration that loaded them: Codex/GPT-5.5 loaded skills in 40 of 40 audits and gained +22.8% in detection. Claude Code/Opus-4.8 loaded none in 40. With a weaker backend model, every harness did worse with skills available.
  • 2609.30074 audits its own eight-model evaluation:
  • Only the bottom of the ranking survives resampling.
  • One undocumented merge rule moves the headline by 7.1 points.
  • A hard 60-second client timeout produced a finding that two model families were "inaccessible". The author withdrew that finding.
  • Four of the eight model endpoints were retired within ten weeks, so the study can no longer be rerun.

What this means for BQAA (as the observer, not the source of truth):

  • Check evaluation data on ingestion:
  • Store durations with their units.
  • Flag model calls that have tokens but zero cost.
  • When rebuilding a transcript from spans, break equal start times by end time or by an explicit sequence number.
  • Join evaluator scores on evaluator ID, not score name.
  • Treat a memory ADD as confirmed only when the store acknowledged it.
  • Log skills as events. Record when the skill list was shown to the model, when a skill was loaded (name and version), and when its resources were read. Compute skill effects only over sessions that actually loaded the skill.
  • For evaluation runs, record per call:
  • finish reason, client timeout, token cap, model and endpoint ID;
  • the raw output;
  • the run date and campaign.

Report how stable a ranking is under resampling next to the ranking itself.

1. NEW rank: arXiv 2609.29454: Demystifying Agent Skills for Smart Contract Auditing: Design, Effectiveness, Behavioral Impact

Gao, Zhong, Chen, Wang, Wu (Lingnan University, PolyU, Zhejiang University, HKUST). Submitted 24 Sep 2026 (v1, cs.SE), 12 pages. The authors say they release the skill corpus and artifacts.

Full PDF read: §I–IX, Tables I–IX and Figs. 1–11.

What they did:

  • Corpus: 155 candidate audit skills from six skill marketplaces, two GitHub collections and SkillsBench, as of 21 Apr 2026. After deduplication, 83 remain (Table I).
  • Benchmark: EVMBench (40 real audits, 120 known vulnerabilities).
  • Seven agent–model configurations (CLIs as of 28 May 2026):
  • Each harness with its flagship model: Claude Code/Opus-4.8, Codex/GPT-5.5, Antigravity/Gemini-3.5-Flash and OpenCode/GLM-5.1.
  • Claude Code, Codex and OpenCode, each on the same weaker model, DeepSeek-V4-Pro.
  • Setup:
  • Skills are installed globally, and the agent is never told to use them. Only each skill's name and description sit in context until the agent loads the full SKILL.md.
  • Activation is counted from session traces: a skill counts as used only when its SKILL.md is read (§VI-B).
  • Behavior measures:
  • Trajectories are compared in two views: text embeddings, and a 10-way share of action types (reason, skill, read, list, grep, edit, bash, plan, search, other).
  • The test is a paired Hotelling T² with a sign-flip permutation (B = 5000).

Numbers:

  • What skills look like (Table II, §IV):
  • The median SKILL.md is 120 lines and 1,281 tokens; the median package is 3 files and 25 KB.
  • 88% of skills call tools, but only 23% depend on vulnerability-analysis tools (Slither in 18).
  • Effect on detection (Table VI):
  • Codex/GPT-5.5: 79 → 97 of 120 (65.8% → 80.8%, +22.8% relative). Precision rose from 28.8% to 33.1%, and the dollar value of bugs found rose +43.2%.
  • Claude Code/Opus-4.8: 62 → 64 (+3.2%).
  • Antigravity/Gemini-3.5-Flash: 47 → 50 (+6.4%).
  • OpenCode/GLM-5.1: 36 → 41 (+13.9%), but the value of bugs found fell −25.6%.
  • On DeepSeek-V4-Pro, all three harnesses got worse (−5.9% to −9.4%).

  • Cost (Fig. 8):
  • Codex/GPT-5.5 was cheaper (−5.24%) and faster (−3.64%) with skills.
  • Antigravity was both more expensive (+11.90%) and slower (+24.09%).
  • Claude Code/Opus used +11.88% more tokens but ran −28.73% shorter.
  • How skills are used (Fig. 11):
  • Every configuration follows the same six stages: read instructions, explore, read README, read code, grep/trace/test, report.
  • Some load skills early and some late. Some use one skill throughout. Others chain them by code region, for example blockchain-auditor → bridges → erc20 → precision-math → proxies.
  • Repeat runs (Table IX), for Codex/GPT-5.5 only: detection gains of +22.8%, +20.3% and +28.2%. Precision moved +14.8%, +2.5% and −10.6%.
  • My inference from the paper's own tables:
  • Six of seven configurations shifted significantly in at least one view, and the only exception was Claude Code/DeepSeek.
  • So Claude Code/Opus-4.8 and Codex/DeepSeek changed behavior even though they never loaded a skill. Listing 83 skills in the context appears to be a treatment by itself.
  • The paper does not discuss this. With 14 tests and no multiplicity correction, treat it as a lead.

Caveats I'd flag:

  • Results are mostly single runs; only Codex/GPT-5.5 was repeated, three times.
  • The study uses one benchmark, which the authors say may be leaked, and one domain. The skill corpus is an April snapshot.
  • The paper does not report a check that each harness actually listed the 83 global skills at startup. Claude Code's 0 of 40 could partly reflect discovery rather than the model.
  • There is no per-skill causal attribution. OpenCode/GLM gained +13.9% while loading skills in only 3 audits, with overlapping confidence intervals, which shows how noisy single-run deltas are.
  • The design analysis was coded by GPT-5.4, reviewed by Claude Opus 4.6, with manual adjudication.

Why it ranks:

  • It measures skill use in shipping harness–model pairs from traces: whether a skill loaded, when, how often, and in what chain. Those are the events a skill-telemetry schema needs.
  • It is timely. Today Langfuse built versioned skills with an MCP loadSkill tool (still internal), and ADK 2.10 added a skill lifecycle and discovery modes (first-party). The catalog also carries the OTel gen_ai.skill.* proposal (otel-genai-skills-proposal).
  • It is distinct from the catalog's skill cards:
  • arxiv-2609-26863-skillapt-when-to-activate-agent-skills learns a policy for when to load a skill, on a benchmark.
  • arxiv-2609-12742-skill-issue-repository-skill-optimization-noise-floor finds SKILL.md optimization gains within noise.

TL;DR for BQAA:

  • Log three skill events: the list shown to the model, a skill loaded (name and version), and a resource read.
  • Report the load rate per model and harness, and measure a skill's effect only over sessions that loaded it.
  • Treat "skills available" as its own condition, because the list alone may change behavior.

2. NEW rank: arXiv 2609.30074: How Reproducible Are Evaluation Conclusions? A Self-Audit of LLM-Inferred Prompt Structure

Sarkar (Skelf Research). Submitted 24 Sep 2026 (v1, cs.CL; cross-listed to cs.AI and cs.LG), 13 pages. Previously submitted to the TAE workshop at NeurIPS 2026. The author says the corpus, the 293 raw outputs and all scripts are released.

Full PDF read: §1–10 and App. A–F (Tables 1–3 and the appendix tables).

What they did:

  • Eight open model variants from five families (8B to 675B), served by one commercial endpoint, were asked to recover the structure of prompts as a typed list of nodes.
  • Each identical call was repeated 2–5 times with caching off, and all 293 raw outputs were kept.
  • The author then audited seven of the study's own claims (Table 2).

Numbers:

  • The measurement itself is unstable (Table 1, §4.1–4.3).
  • Across models, agreement between repeated identical calls (node-set Jaccard) ranges from 0.39 to 0.96. Only 35 of 127 prompt–model cells (28%) were perfect.
  • Within one family, the larger model was less reproducible: gpt-oss:120b scored 0.386 against gpt-oss:20b's 0.766 on 18 shared prompts (Wilcoxon p = 0.0046).
  • On unannotated real SKILL.md files (11 models × 19 files × 3 runs), mean agreement is 0.22, and 15% of cells share no node ID across runs.
  • The ranking does not survive resampling (§5.2). Under a joint cluster bootstrap over prompts (9,583 usable replicates), only the bottom holds: last place in 99% and seventh in 86%. The middle four keep their place in 27–48% of replicates, and the top two in 68% each.
  • Analysis choices move the headline (§5.2, App. C, E, F).
  • Two defensible rules for merging repeated campaigns change four of eight rows, and the share of perfect cells moves from 27.6% to 20.5% (7.1 points).
  • A tolerance documented as relative but coded as absolute changes how many cells "stabilize" from 80 to 50 of 98.
  • Reproducible is not correct (§6). Recall of annotated nodes is 0.86. About one in five nodes that a model said it had copied matches no annotation (explicit precision 0.82).
  • The instrument manufactured a finding (§7, App. D).
  • A hard 60,000 ms client timeout logged slow reasoning models as connection failures, which produced a "DeepSeek and Zhipu are inaccessible" finding. The author withdraws it.
  • Under a 1,500-token cap, 8 of 11 models stop at length with invalid JSON; with 8,000 tokens, all 11 return valid JSON.
  • The endpoints disappeared (§7, App. A). Four of the eight ranked models were retired on 2026-07-15 with HTTP 410. Of 15 models named in the study, 10 were gone by the 17 Aug audit, in two waves. "Had we kept only summary CSVs, half this paper would be unfalsifiable."

Caveats I'd flag:

  • A single author, and one narrow task (recovering prompt structure), with no agent evaluation.
  • An unbalanced panel; two rows rest on 3 and 6 prompts.
  • One endpoint and one time window, and the author cannot verify which weights actually answered.

Why it ranks:

  • It is an end-to-end audit that names the pipeline facts an evaluation must record to stay checkable: raw outputs, finish reasons, client timeout and token cap, campaign and merge provenance, dates and endpoint status. BQAA can store and surface every one of them.
  • It is distinct from the catalog's evaluation-reliability cards (arxiv-2609-26489-calibration-first-class-criterion-llm-eval, arxiv-2609-29769-jev-vs-llm-rubric-judges-correlated-errors). Those are about the judge; this is about the pipeline around it.

TL;DR for BQAA:

  • For every evaluated call, store the finish reason, client timeout, max_tokens, model and endpoint ID and the endpoint's status.
  • Classify each failure as the instrument's (timeout, token cap), the model's, or the endpoint's (410).
  • Keep raw outputs, date every run and record which campaign each result came from.
  • Report ranking stability next to any leaderboard.
