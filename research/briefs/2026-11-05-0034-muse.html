Academy

NEW 1 — Trace2Eval: benchmarks reconstructed from real-world coding-agent traces — arXiv:2611.06506

Full-PDF-read statement: main text §§1–6 read in full; Appendices A.1–A.6 read for methods, tables and case detail (taxonomy Table 18 and long system listings skimmed). Key numbers cite section/table below.

Trace2Eval turns anonymized real user traces into executable evaluation instances instead of curating static tasks. From 20,000 collected online traces (June–July 2026), 14,603 are code-related; distribution-aligned selection plus admission voting yields a 129-task benchmark (§3.1, Fig. 2). For each retained trace, recovery agents reconstruct the pre-interaction workspace and a containerized environment; acceptance is by trajectory equivalence — replay the original tool calls in the recovered context and score per-call agreement with recorded outputs (§3.2, Eqs. 2–3). Recovery reaches an 82.6% workspace acceptance rate at mean replay score 0.9175 (§4.2). Artifacts are then scored on 11 human-grounded rubric dimensions (accuracy / code quality / user experience, weighted 50/35/15) by judge agents using source plus runtime evidence; overall usability agreement is 93.0% vs 92.9% human (§4.3). Rubric feedback is actionable: across 19 model–harness configurations, revision gains average +10.05pp, max +19.28pp (Table 1), and an unguided-revision ablation (§4.4, Fig. 5) shows smaller gains without the diagnosis. Limits are stated plainly (§5): judge agreement still has headroom, and recovery occasionally emits packages missing core files even after human verification.

BQAA read: this is the strongest argument yet that a trace store must preserve enough context to replay, not just to report. If BQAA cannot reconstruct initial workspace/environment state (or at least tool inputs/outputs in order), customers cannot build refreshable evals from production traffic — they can only dashboard it. The replay score itself is a warehouse-native metric worth copying: per-call agreement, averaged per trace, stored beside the trace rather than collapsed into pass/fail.

NEW 2 — Task-efficient agent evaluation from cached traces (trubric) — arXiv:2611.06803

Full-PDF-read statement: full PDF read — main text §§1–5 including Limitations (§5.1), plus Appendices A–C (probe Table 2, prompts, system/task panels Tables 3–4 skimmed as listings). Key numbers cite Table 1 / §4.1.

Standard efficient benchmarking predicts a new system's full score from binary correctness on a few tasks. This paper instead embeds the trace: an LLM extracts a task-specific structured rubric summary (trubric — understanding, localization, reproduction, editing, verification, final state), each field is embedded, and systems are placed in a geometry built from cached reference traces (§3). Raw-trace embeddings mostly encode system identity, model family and harness; trubric suppresses those while keeping task/correctness signal across seven encoders (Fig. 1, Table 2 — e.g. system-identity probe accuracy falls from 0.89 raw to 0.20 trubric for one encoder, correctness held at ~0.84). Combined with an item-response model, a single random executed task predicts full SWE-bench Verified score at MAE 0.08 vs 0.13 for IRT alone, and Terminal-Bench 2.0 at 0.12 vs 0.14 (abstract; Table 1); at five tasks the combination reaches 0.063 / 0.090 respectively, and decides 88% of head-to-head pairs from one task per system on SWE-bench (§4.1, Fig. 5). Limits (§5.1): only paired, fully-covered reference panels tested; single summarizer model; rubric fields unoptimized; a candid warning that bulk trace summarization triggered a provider account ban as suspected distillation.

BQAA read: cached traces have resale value as an evaluation asset only if the warehouse can serve comparable representations across systems and harnesses. Raw log text will cluster by harness fingerprint, not by behavior. A BQAA-native trace_summary table (fixed rubric fields per task type, versioned summarizer) is the difference between "we store logs" and "we can estimate your next benchmark from one run."

NEW 3 — GH-AWTrace: a large-scale dataset of agentic-workflow execution logs — arXiv:2611.06866

Full-PDF-read statement: full PDF read (5-page dataset paper, §§I–V, Fig. 1–3, Table I, schema Fig. 2, Data Availability).

GH-AWTrace links 25,014 verified GitHub Agentic Workflows across 5,051 repositories to 4,112,526 run records and 562,877 nonempty execution-log archives (56.1 GB of ZIPs; §II, Fig. 1), explicitly because the platform deletes public workflow logs after at most 90 days and run records after 400 days. The schema (Fig. 2) is deliberately warehouse-shaped: Repository → Workflow → Run → Attempt-log, joined on stable ids with SHA-256 receipts per archive. Coverage caveats are quantified, not hidden: 13,618 workflows have no recorded runs; 821,672 in-window runs have no downloadable archive; 1,070,338 downloaded ZIPs are empty (early audit: mostly skipped jobs); logs are partial observations, not complete trajectories (§§II–III, V). Even so, 178,151 nonempty archives (31.7%) attach to failure-conclusion runs, and case excerpts (§IV) show what run conclusions alone hide: tool denials with mid-run strategy changes, provider auth failures with internal retries, and within-run multi-reviewer delegation. Dataset is public (Hugging Face link in Data Availability).

BQAA read: this is the retention parable with numbers. Any BQAA pitch that starts at query time loses to the customer's own 90-day deletion clock. The join keys here — workflow, run, attempt — map directly onto session / run / retry modeling, and the empty-archive audit is a reminder to model absence (skipped, deleted, inaccessible) as a first-class state, not as zero activity.

Six-week EV

Highest expected value in the next six weeks is a replay-and-summarize spike over data BQAA already lands: (1) pick one coding-agent workload, store ordered tool inputs/outputs with attempt ids, and compute a Trace2Eval-style replay-agreement score on reconstructed contexts for a small sample — success criterion is a per-trace score distribution, not a demo dashboard; (2) emit a versioned six-field trace summary per run (trubric shape) into its own table and test whether summaries cluster by behavior rather than by harness on internal traces; (3) adopt GH-AWTrace's absence modeling (skipped / expired / inaccessible / empty) in retention docs before the next customer discovers their source logs aged out. Each step is reversible, warehouse-native, and directly citable to a paper above if leadership asks why now.
