I1 (NEW). Claude Code v2.1.287: Claude Mods, a built-in "You should know" watcher agent, and an OTel prompt_text field; Agent SDK v0.3.287 adds latency fields and an MCP result cap

What shipped (both released 2026-10-01 at 18:00Z, prerelease: false):

Claude Code v2.1.287 (from the release notes):

  • Claude Mods: "plugins may now modify deeper behavior." This is a new extension tier above hooks, skills and MCP.
  • "You should know": a built-in mod in which "a side agent watches your back and flags things you or Claude might miss." It is turned on with /plugin enable cc-plugin-you-should-know@builtin and is available only for first-party sessions with telemetry on.
  • OTel: prompt_text is added to the user_prompt event as a copy of prompt, for backends that nest dotted keys. The notes say to drop or mask it wherever you drop or mask prompt (anthropics/claude-code#70763).
  • MCP: URL prompts (for example sign-in) now work from servers on the 2025-11-25 protocol. bareElicitationCapability is an escape hatch.
  • Reliability and safety fixes:
  • Tool heartbeats now reach SDK hosts while the model stream is stalled.
  • A dangerous rm no longer loses its always-ask safeguard when it is combined with a ~/wildcard redirect.
  • Org per-tool permission ceilings are no longer dropped for an MCP tool named __proto__.
  • --include-partial-messages no longer sends message_stop late or never.

Agent SDK v0.3.287 (from the release notes; parity with Claude Code 2.1.287):

  • The success result message gains optional remote-session latency fields: first_text_post_queue_wait_ms and first_text_post_queued_behind.
  • MCP tool_use_result: structuredContent over 1,048,576 JSON characters is left off and structuredContentOmitted: true is set. SDK-server and MCP Apps tools are exempt.
  • A WebFetch or WebSearch call that steps aside for a priority message now returns { detachedToolCall: true }. Its result arrives in a later turn.
  • commands_changed no longer arrives before init or twice.

Why it's a NEW card and not Progress on claude-code-2-1-283-…: 2.1.284–2.1.286 were fix-and-telemetry trains. 2.1.287 adds a new extension tier (Mods) and ships a first-party second agent that runs alongside the main one. That is a product-level change.

BQAA read:

  1. "You should know" puts a second agent in every opted-in session. Its flags are agent output that is not a reply to the user. A trace schema that assumes one agent per session will either merge the watcher's spans into the main agent or drop them. BQAA should give watcher and advisor agents their own agent id or role inside one session, rather than treating them as subagents of the main agent.
  2. prompt_text is a second copy of the raw prompt. Any BQAA redaction rule keyed on prompt must also cover prompt_text. Anthropic's notes say this directly.
  3. structuredContentOmitted: true and detachedToolCall: true both mean "the result is not here". An analytics pipeline should count these as known omissions, not as empty or failed tool results.

Academy

A1 (NEW). ActionGuard: authorizing each tool call against the trusted user request, without letting the reviewer see the poisoned skill (arXiv 2609.39450)

Full PDF read (14 pp. incl. appendix; Han, Jang, Kwak, Han, Korea University; cs.CR, submitted 2026-09-30). The 0634 brief scouted it at abstract level only.

Method (§4):

  • ActionGuard sits at OpenClaw's before_tool_call hook. The target agent still plans from the raw SKILL.md, but the Reviewer never receives the raw skill.
  • The Reviewer sees four inputs:
  • the trusted user request, captured at session start;
  • a "balanced skill profile" (ordinary workflow + suspicious signals), built once from the raw skill by a separate model and cached in a profile DB;
  • the current and recent tool calls, in normalized and raw form;
  • "Inspected Files": the pre-execution contents of any local script the call would run.
  • It returns ALLOW/DENY plus a reason code (Table 1). The policy is fail-closed: an unparseable reply or a failed reviewer call is a DENY. Every decision goes to an audit log.

Results: 319 SKILL-INJECT pairs (139 contextual, 180 obvious), 5 reviewer models, 3 runs each; target agent and judge are both gpt-5.5.

  • Overall attack success rate (ASR) / task success rate (TSR) (Table 4):
ASR TSR
No safeguard 29.05% 93.46%
Dynamic Guardian 16.05% 92.08%
SkillGuard 13.42% 88.55%
ActionGuard 8.65% 90.38%
  • Contextual injections (attacks dressed up as "backup" or "validation"): ActionGuard's ASR is 8.20% vs SkillGuard's 19.81% (§6.2).
  • On obvious injections SkillGuard is slightly better: 8.48% vs 9.00%.
  • ASR stays within 7.73–9.30% across reviewer models from a 4-bit Gemma 4 to Claude Haiku 4.5 (§6.3). The defense does not need a strong reviewer.

Limitations (§7.2, §8):

  • A compound call that bundles a benign and an unauthorized action is blocked whole. In INST-10, git add && commit && push --force was blocked and the agent never retried a safe push, so the task failed.
  • One framework, one target model, one benchmark.
  • Attack and task outcomes are adjudicated by an LLM judge. The authors list hybrid deterministic adjudication as future work.

BQAA read:

  • Authorization belongs at the call boundary, with the trusted request as the reference, and the reviewer should not read the untrusted instruction text.
  • The paper's audit log has exactly the rows BQAA would want: three outcome classes ("no attack action generated" / "generated but blocked" / "allowed but did not execute") plus a per-call reason code.
  • A DENY-then-no-replan is a distinct utility-loss signature worth detecting.
  • This is the research counterpart to the open Inspect AI #5654 ("remote MCP tools running without approval").

A2 (NEW). JuryFlow: re-judging only the claims a judge panel disagrees on beats majority vote by 6.6 points on LLMBar (arXiv 2609.40103)

Full PDF read (9 pp. incl. appendix; Yang, Yu, Ding; Tsukuba, Tokyo, Hiroshima; HAI '26, cs.CL, submitted 2026-09-30).

Method (§3):

  1. Five heterogeneous judges decompose a response into atomic claims, give each claim a verdict (accept / reject / uncertain) and add dimension tags.
  2. A disagreement graph scores each claim node by verdict entropy. Edges mix tag Jaccard and embedding cosine (α = 0.4).
  3. The top-m high-entropy claims are re-judged against the evidence.
  4. Each correction propagates along edges with w > β and to similar historical claims through a FAISS index.
  5. The correction is distilled into a rubric entry that every judge inherits.

Results (3 seeds; MT-Bench 300 pairwise instances, LLMBar 419):

  • Accuracy and Cohen's κ (Table 2):
MT-Bench acc. MT-Bench κ LLMBar acc. LLMBar κ
Best single judge 0.804 0.59 0.679 0.36
Majority-vote panel 0.828 0.64 0.718 0.44
JuryFlow 0.857 0.71 0.784 0.57
  • Where the gain comes from on LLMBar (Table 3): focal re-judging alone gives +3.0 points; propagation +2.8; rubric induction +1.2. Total cost is 3.6 re-evaluation calls per instance.
  • Propagation threshold β (Table 4): too-loose propagation hurts. At β = 0 it costs 8.7 calls and accuracy falls to 0.761.
  • Panel diversity (Table 5): a single model with varied personas reaches only 0.726, barely above majority vote. The gain needs genuinely different model families.

Limitations (§7):

  • The "human-in-the-loop" mode is not validated. Every number uses automatic entropy selection.
  • Confident but wrong consensus has zero entropy and is never flagged.
  • The rubric can grow and drift without bound.
  • The panel uses 2024-era models (GPT-4o, Claude 3.5 Sonnet, Gemini 1.5 Pro, Llama-3.1-70B, Qwen2.5-72B), and the gold sets are public.

BQAA read:

  • Store judge verdicts per claim, not one score per response. Disagreement entropy is then a cheap, queryable signal for where to spend re-evaluation.
  • The persona-panel result argues against "one model, five prompts" juries.
  • Keep the rubric-entry history versioned so drift can be audited.
