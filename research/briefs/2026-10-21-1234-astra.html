The practical thread is preserving the meaning of telemetry as systems change. Braintrust introduces log records that can share a span ID without being additional spans. Claude's API migration distinguishes organization-wide keys from Default Workspace keys and changes analytics response fields. Mastra extends its query contracts to span aggregates and time to first chunk. These are ingestion and aggregation changes worth testing before comparing dashboards across versions.

The second thread is keeping evaluation and recovery evidence honest. Opik now finishes certain suites when the judge cannot run, but those assertions are represented as failures with a not-evaluated reason. Agno makes checkpoint retention finite by default. The full-read paper shows why a working-looking judge and an available rollback button are insufficient evidence of reliable automated repair.

Recalled lessons applied: missing or unmeasured evidence is not zero; a full PDF extraction is not a full read; the completion marker must be inside the brief file. Only one paper receives a full-read claim. Release notes establish shipped scope, not observed performance in a customer deployment.

Industry

NEW 1 — Braintrust adds application logs alongside traces, with explicit log-record identity

Stable, in-window: Braintrust JavaScript 3.39.0, GitHub 09:03 PT / 16:03Z; npm publication 09:08 PT / 16:08Z, Oct 21. The admission is for a new telemetry surface, not the version increment or a repeat of the existing span-export-hook card.

The SDK adds severity-based application logging and wrapConsole() capture. The released change's API description makes an important distinction: messages inside an active Braintrust or compatible OpenTelemetry span inherit its trace and span IDs while retaining their own log row IDs. They do not create child spans or alter the active span. Outside an active span, messages share the logger's baseline trace ID. Template-aware logging also preserves message templates and typed parameters for grouping.

This means ordinary application events can be correlated with agent execution without pretending each log message is a timed operation. The same stable release adds AI SDK batch and code-mode tracing, LiveKit cascade instrumentation, and corrections to cache-token and streamed-tool-call capture. Those additions are one release-family item, not separate cards.

BQAA implication: preserve record kind and record ID in addition to trace/span IDs. A join on span ID alone can multiply log rows and inflate operation counts. Test console capture, unscoped logs and explicit logger calls as separate paths; capture is opt-in and the SDK evidence does not establish lossless collection, redaction guarantees or measured ingestion overhead.

NEW 2 — Claude API 2026-10-21 changes the tenant and credential attribution contract

Stable, in-window: the official Oct 21 API release notes announce API version 2026-10-21. Python SDK 2.0.0 defaults to it and was uploaded to PyPI at 08:51 PT / 15:51Z; TypeScript SDK 1.0.0 reached npm at 09:00 PT / 16:00Z. These are one coordinated API/SDK migration.

The migration guide replaces an API key's ambiguous workspace_id with an explicit scope. Previously, a null value could mean either Default Workspace or an all-workspaces key. Now a workspace-bound key carries the actual workspace ID, including Default Workspace, while an organization-wide key has scope.type = organization. Enterprise analytics also changes actor.email to actor.email_address and activity-summary summaries to data. The new API version removes the old response names.

The SDK credential path changes too: API keys normally move from X-Api-Key to Authorization: Bearer, and the ordinary client selects one credential. Gateways and instrumentation that read only the old header need compatible handling. Platform clients have documented exceptions; for example, the Python Foundry client still uses x-api-key.

Why rank it: the released API contract can now distinguish key scopes that the old nullable field conflated, while changing the fields consumed by governance and usage analytics. BQAA implication: version tenant mapping, response parsers and credential-redaction rules together; validate Default Workspace and organization-wide fixtures independently. This is not a model-quality or cost-saving claim. The separately documented end-customer enforcement fields are held under Unconfirmed, rather than assumed to be typed in these SDK releases.

Progress — Mastra extends trace analytics to a capability-gated span-aggregation contract

Target catalog item: mastra-core-1-72-0-trace-aggregate-plans-lease-fenced-background-tasks-cyber-refusal-retry.

Mastra core 1.79.0 and its coordinated package train shipped Oct 21: npm 04:41 PT / 11:41Z, GitHub 05:28 PT / 12:28Z. The meaningful extension is aggregateSpans() behind the span-aggregate storage capability. It supports questions such as tool-latency percentiles and token/cost totals grouped by a span's own, parent or root entity. Token and cost measures count usage on the span that recorded it; model/provider grouping is not yet supported. An adapter without the capability rejects the operation. A released contract is not evidence that every adapter already implements it.

The release also adds timeToFirstChunkMs to trace/span queries, returning null when no chunk was streamed, with capability signaling for stores. This is time to first chunk, not automatically model time to first token. Root-entity filtering and batch experiment-ID metric queries improve attribution. Meanwhile, the querySpans() response/filter contract changes, including removal of model/provider filters and its returned cost field; consumers need migration checks rather than assuming old row schemas remain valid.

BQAA implication: expose the population, entity level, usage ownership and measurement coverage behind an aggregate. Compare returned spans with aggregate counts on the same filter. Treat experimental MCP Events in the same train as NOTE-only; the monorepo release is not a card per package.

Progress — Agno adds shared PostgreSQL checkpoints and limits the default restore horizon

Target catalog item: agno-v3-1-4-sandboxed-harness-agents-durable-queue.

Agno 3.1.8 shipped Oct 21 at 05:15 PT / 12:15Z, with PyPI upload at 05:16 PT / 12:16Z. Its opt-in PostgresCheckpointStore stores sandbox checkpoints in PostgreSQL for multi-replica restore without shared local filesystems or S3. The notes describe chunked transactional writes, SHA-256 deduplication and verification on read.

The consequential behavior change is retention: only the three newest sandbox checkpoints per session are retained by default. retain_checkpoints=None preserves unlimited retention. Opening an older checkpoint can therefore fail. Durable-queue sandbox configurations using the host-local default store now fail at startup; a committed checkpoint missing from storage terminates with a non-retryable error and releases the session instead of leaving it blocked in retries.

BQAA implication: retain checkpoint ID, storage status, retention policy and restore outcome alongside run lineage. A historical run record does not establish that its execution state remains restorable. This materially advances the existing sandbox/durable-queue card and connects directly to the Academy distinction between restoring a saved version and generating a replacement.

Progress — Opik terminates unjudgeable suites; preserve the reason behind the failure

Target catalog item: opik-2-2-99-triggered-alerts-aws-eventbridge-mcp-instructions-deferred-tools-server-breakdown-row.

The stable 2.2.111, 2.2.112 and 2.2.113 releases are all in-window: PyPI uploads at 04:21, 06:18 and 07:57 PT respectively. Version 2.2.110 uploaded at 00:21 PT, before the cutoff, and is not admitted here.

The material evaluation change in 2.2.112 prevents a suite from remaining running indefinitely after assertion judging fails. The released change description distinguishes permanent provider rejection from transient errors: supported permanent rejections can try the next configured judge candidate, while 429/5xx failures retain normal retries. When a suite-assertion message is finally retired, a best-effort hook records a failed assertion with the evaluation error and decrements the counter so the experiment can finish. Ordinary online-scoring rules do not acquire that suite-specific retirement behavior.

Do not turn this into a quality verdict: a failed assertion carrying a not-evaluated reason is not evidence that the agent's answer was wrong. Preserve scoring availability, failure reason, selected/fallback judge and final score separately. Version 2.2.111 also routes OTLP traces by opik.project_name; 2.2.113 blocks empty-dataset/test-suite runs and corrects authored feedback-score reads in the existing deprecated workspace metrics endpoints. No new-dashboard launch or performance gain is inferred from those repairs.

Academy

NEW 1 — Recoverability and Verifier Strength: Two Measured Preconditions for Unattended Agent Self-Improvement — arXiv:2610.27465

Pre-window carry-forward: v1 Oct 20, announced in the Tuesday-evening batch consumed by the 0034 window, scouted there but never ranked. This is newly admitted evidence, not a new Wednesday-morning paper. Full PDF read: all 11 pages, including definitions, platform design, experiments, limitations, references and Appendices A–E. Full PDF.

The paper separates verifier strength from recoverability. Strength is Matthews correlation against a fixed reference verifier, so a constant-answer gate scores zero instead of looking accurate on an imbalanced population. Recoverability distinguishes writing back a retained version from regenerating an undo, and measures restored behavior and the reach of changes while deployed (§§2–3). The proposed autonomy rule requires both a retained rollback path and measured verifier strength; its threshold is application-specific.

The useful measurements, with their limits:

  • Silent gate collapse: the platform's diversity judge returned the same score across all tested imbalance levels in 9 of 37 configurations (§5.1, Appendix A). The deployed small judge accounted for 33 of those 37 configurations, so the count alone is not a model-vendor comparison. Matched-input tests and removal of the purported signal provide stronger evidence that a functioning API can conceal an ineffective judge.
  • Verifier uncertainty: on airline trajectories, the LLM judge has MCC 0.70, but a task-resampled interval of [0.36, 1.00] because errors cluster by task (§5.2, Table 1). There are 80 test trajectories but only 20 distinct tasks. Appendix E explains why counting repeated runs as independent evidence understates false-admit uncertainty.
  • Restoring a saved prompt: behavior returns to the null-change noise floor, with restoration difference 0.000, 95% CI [−0.038, 0.038]; the equivalence test uses a prespecified ±0.05 margin (§5.2, Appendix C). Three regenerated undos instead differ from baseline by −0.16, CI [−0.27, −0.07] relative to their noise floor. Those undo experiments use 30 training tasks, not the saved-copy comparison's 20 test tasks, and the gate rejected all three; they are not three deployed recovery successes.
  • Reach is not harm rate: three deployed prompt changes alter task outcomes by 0.17 above the null-change floor, CI [0.08, 0.27], over 50 probe tasks (§5.2, Table 3, Appendix C). Outcomes flip in both directions—18 improvements and 20 regressions—so this does not mean 17% of users were harmed or that a rollback repairs already-issued effects.

What the paper does not establish: the central experiment relating lower verifier strength to worse selected changes is not statistically resolved: slope −0.065, CI [−0.234, 0.120], one-sided p=0.23; retail shows no trend (§5.2, Table 2, Appendix D). Candidate quality spread and the small task set limit power. The rule was applied after the fact on one platform; only prompt edits were tested end to end. Tool, skill and weight-update policies follow from the design, not separate experimental validation.

BQAA implication: model a repair attempt as evidence → proposed change → verifier configuration → admit/reject/refuse → deployed version → rollback/remaining effects. Keep “refused because evidence is missing” distinct from “rejected because the candidate is worse.” Store verifier model/settings, reference-label version, distinct task count, false-admit/false-reject rates and confidence intervals. Appendix D also reports infrastructure failures leaving empty, unscored transcripts without a runner error: a useful reason to validate run completeness before aggregating scores, alongside Opik's now-explicit unjudgeable outcomes.

TL;DRs for BQAA

  • Braintrust: log records may share a span ID; count operations and messages separately.
  • Claude API: migrate tenant scope, analytics field names and credential-header handling as one versioned contract.
  • Mastra: span aggregation requires explicit adapter capability, usage ownership and measurement coverage.
  • Agno: a retained trace is not proof of a retained checkpoint; expose the restore horizon.
  • Opik: a completed suite with unjudgeable assertions is not a fully evaluated suite.
  • Recoverability study: measure the verifier and rollback behavior, preserve task-level uncertainty, and do not treat the proposed autonomy rule as experimentally proven.
