4. Agent Mesh — Shaikh, Bombarde, Pathak, arXiv 2608.26225 (submitted 26 Aug)

What it actually is. A failure study of one production agentic software-delivery platform (66,185 lines, 59 modules, deterministic-DAG orchestration) — 147 numbered incidents across 81 runs with measured cost — asking why service-mesh reliability primitives (retry, timeout, error-rate circuit breaking) fail when the callee is a non-idempotent agent. Affiliations are not on the abs page; the data is the platform's own durable records ("persisted attempts, recovery leases, budget documents, structured failure envelopes" and the event stream), not OTel. (abs, html)

How it works. Two incidents carry the argument. An independent-verifier agent issued the same tool call with one distinct payload 54 times in 11 minutes; every call returned success, so "no error-rate breaker could see" it. Separately, an event log outside the transactional workspace accumulated 21 events across six invocations of one delegation over four hours; each invocation correctly published exactly three, but the ledger kept the previous invocations' effects, so a correct, idempotent component became "unwinnable". The paper names two adequacy conditions — identity adequacy (five subsystems failed because an identity did not discriminate: progress fingerprints over constant identifiers, commit keys on transactions instead of content, and so on) and evidence adequacy (a reliability decision needs evidence that "is capable of moving", "attributable to what it measures", and "deterministic under identical conditions") — and seven delegation-level primitives. The two that matter here: P1 progress-based breaking, where progress is content-keyed ("a read returns the file's digest with its content, so re-reading a file whose bytes changed is grounding while an identical re-read is not") and identifiers the strategy re-emits unchanged are discarded by construction; and P3 an effect ledger of "canonicalized tool calls, argument digests, external mutation identifiers" observed "at tool and sandbox boundaries" with no agent cooperation, keyed on content rather than invocation (that part is proposed, not built). Measured costs on the page: 107 agent turns with zero accepted writes (costliest enforcement-layer incident); a 943-tool-turn, 71-minute repair window; one traced run of 4 h 55 min with 12 terminal component failures and 23 stall verdicts. On tracing, verbatim: "a span in both records that a call happened; the checkpoint ladder records whether an effect was committed, which is what a routing decision needs and what a call-level span cannot supply."

What people get wrong. Reading it as an orchestration paper. Its analytics content is a correction to how loop detection is usually specified: status = 'ERROR' sees nothing, and "identical tool + args ≥ 3" (yesterday's #1 move) is necessary but wrong-keyed — the 54 calls had one distinct payload, and the thing that made them a loop is that the result never changed. A second correction: effects accumulate across invocations of a delegation, so any per-invocation view is blind to the 21-event case for the same structural reason LoopHarness gave yesterday. This is the industrial twin of LoopHarness's theorem, from a team that paid for it.

Judgment. Peer; highest-EV of the new batch. Single platform, no author affiliations, no baseline comparison — cite the mechanism, not the counts.

TL;DR for BQAA. Re-key the top move. v_tool_repeat should flag (tool, args_sha256, result_sha256) repeats, and latency_outlier/loop must not require status='ERROR'; that needs a result_sha256 (or content_parts digest) on TOOL_COMPLETED, which is the *.sha256 column yesterday's llmmas-otel item already asked for — now with a second reason. The session latch (v_session_risk, monotone MAX across invocations) is also the effect-ledger idea at read time: group by session_id, not invocation_id. Put the tracing sentence in the SDK docs as the one-line reason agent_events records TOOL_COMPLETED with content rather than a span with status.

5. Approved Too Late: Verdict Staleness — Shraga (Cambridge), Eshel, Gorelik (Open Univ. of Israel), arXiv 2608.26306 (submitted 26 Aug; IEEE ACSOS 2026)

What it actually is. A time-of-check/time-of-use result for LLM guardrails: an approval that is correct when checked can be stale when the action executes. The paper states a freshness contract — "every approval must be correct at check time and remain valid at use time" — and a Freshness-Bounded Shield (FBS) that bounds how long an approval may be used. (abs, html)

How it works. Five self-adaptive-system environments (DeltaIoT, SimTune, mRUBiS, Switch, SimDex), each with a gate feature and threshold. At K=8 simulator steps between check and use, the all-candidate verdict-change rate runs from 5.3% (SimDex) to 48.4% (DeltaIoT) — the paper calls it "a roughly ninefold spread" driven by plant dynamics. Approval-expiry rates fall from 3.4–24.7% (open baseline) to 0–1.8% with FBS. Four LLM judges on DeltaIoT show nonzero use-time invalidity: qwen2.5:0.5b 11.5%, gpt-4o-mini 36.8%, the other two in between (check-time error and temporal expiry combined). FBS needs no plant model: horizon δ = min(δmax, margin / volatility), where margin is the signed distance to the admissibility boundary and volatility is an EMA (α=0.1) of feature changes; the gate passes only with upstream approval, positive margin, and K ≤ ⌊δ⌋, else a declared fallback. The deployment recommendation is specific: each approval should record its "checked context and action, grounding time, expiry or revalidation rule, and a fallback justified for the deployment," and operators should monitor grounding-age, margin, volatility, and fallback frequency.

What people get wrong. Filing this under control systems. Every HITL approval in ADK is the same object: TOOL_PAUSED records the check, the resumed tool call is the use, and since Friday's adk-python change (nested HITL resume is multi-turn) the two can sit in different invocations minutes apart. The wrong belief is "an approved tool call is a safe tool call." It is a tool call approved against a context that may no longer hold. Judgment: peer; a spec, not a threat. Five simulators, not agents — the percentages do not transfer, the contract does.

TL;DR for BQAA. Two things. Today, a view: v_approval_age — for each resumed tool execution, milliseconds since its TOOL_PAUSED, plus whether any LLM_RESPONSE/TOOL_COMPLETED intervened in the session between check and use (a proxy for "context changed"). Reserve, for the GUARDRAIL_DECISION event yesterday's brief asked for: checked_context_sha256, grounding_ts, expiry_rule, fallback — the four fields the paper names. That makes the guardrail row a freshness statement rather than a boolean. Do not build FBS; it is a runtime component, not an analytics one.

6. CTF-ABACUS: Trace-Level Provenance — Milner, Shao, Rani et al., NYU Tandon / NYU Abu Dhabi / CISPA / IIIT Hyderabad / IIT Tirupati, arXiv 2608.26237 (submitted 26 Aug)

What it actually is. An audit framework for offensive-security agents that replaces "did the flag get recovered" with an evidence-grounded solve profile reconstructed from the trace, and reports how many "successes" are actually backed by an observed exploit. (abs, html)

How it works. Each run becomes P(T) = ((eᵢ, zᵢ)ⁿ, ξ, f, σ, s): action/observation steps labelled with a pentest phase and technique, plus three pivotal events — the exploitation act ξ, the flag's first appearance f and its source σ, and the submitted flag s. A solve is trace-verified when the flag appears in the target after an observed exploitation reaching the Vulnerability Analysis phase or deeper; otherwise it is a shortcut (direct exposure, external lookup, reasoning-only, guessing). Multi-agent D-CIPHER runs are flattened into a single time-ordered step sequence with executor actions spliced at delegation points. Scale: 1,435 attempts, 240 challenges, six models (Claude Opus 4.8, GPT 5.5, Gemini 3.1 Pro, GLM 5.2, DeepSeek V4 Pro, Qwen 3.7 Max), 2,870 solve profiles. Trace-verified share of recovered flags: CTFTiny 86%, HTB 81%, InterCode 64%, Cybench 62% — "62–87%" in the abstract. Shortcut trajectories are shallower: 42% reach the Exploitation phase versus 89% for genuine solves.

What people get wrong. Treating it as a security paper. It is the clearest example yet of TelemetrySuffBench's V factor (verifier evidence) — the one factor agent_events does not carry: an outcome check says the answer matched, a trace check says the required work was observed. The wrong belief is "golden match ≥ 0.92 means the agent did the task." It means the output resembled the reference; on these benchmarks 13–38% of matching outputs got there without the work. Judgment: peer; adjacent domain, transferable definition.

TL;DR for BQAA. Add a trajectory_verified boolean beside match_golden_qa: true only when the answer matches and a required tool (or tool class) appears in the session's TOOL_COMPLETED rows with status='OK' before the final response. The TSA-style set match yesterday's Snowflake item proposed is the mechanism; the golden record needs one extra field, required_tools. Do not import PTES phases or technique labels; a tool set is the BQAA-shaped version of "phase reached".

7. Same Model, Different Harness — Lewis, arXiv 2608.26218 (submitted 26 Aug)

What it actually is. Holding model and task fixed and varying only the harness: baseline shows full chronological history; the treatment "keeps the same record but mechanically shortens older tool results" as context fills. Three benchmarks, two harness configurations. (abs)

How it works. On SWE-bench Verified (169 tasks) with a 20,480-token window, mean per-task fail-to-pass goes 28% → 49% and complete solutions 43 → 72; the effect held across three more models without retuning; at wider context windows the two harnesses are comparable. Conclusion in the abstract: "coding-agent evaluations should treat the model and harness together as the tested solver." Single author, no affiliation on the page.

What people get wrong. Reading it as a context-compaction trick. The result is that a harness decision moved outcomes by ~21 points with the model untouched — which is exactly the case yesterday's Model-or-Harness item wanted a column for (fault_side = harness) and which no per-model eval leaderboard can see. The wrong belief: "our eval run compares models." It compares model×harness pairs, and if the harness version is not on the run manifest, a regression from a compaction change will be filed against the model. Judgment: peer; small study, clean design.

TL;DR for BQAA. Put the harness on the eval manifest. evaluation_run_id metadata should record ADK version, the compaction/context policy, and the plugin config alongside the model; ADK 2.0's EVENT_COMPACTION rows are the observable — COUNT(*) per session belongs in the same manifest, so two runs with different compaction counts are never compared as if only the model changed. That is one JSON field, and it is what makes fault_side = harness populatable later.
