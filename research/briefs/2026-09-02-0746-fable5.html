Read this first. Three things are true at product level this morning. First, "evaluate, then alert" is now a shipped loop in three eval platforms: Langfuse turned evaluator scores into alerts today, LangSmith Engine now files Slack alerts and Linear tickets from trace-detected issues, and Braintrust exposes alerts and monitors as MCP write tools. Second, "evaluate any agent from its OTel spans" is a hyperscaler feature, not a spec draft: AWS AgentCore Evaluations reads OTel GenAI or OpenInference spans from CloudWatch and scores agents from six named frameworks, Google ADK included, plus a generic path for anything that follows the conventions. Third, Google Cloud itself shipped three agent-telemetry features in August that sit next to BQAA: data-agent conversation monitoring in BigQuery (Preview), ADK gen_ai metrics from Agent Runtime into Cloud Monitoring, and larger per-span limits and OTLP log ingestion GA in Cloud Observability. The midnight brief spent its weight on an unmerged OTel PR about content references and three instrumentation merges; those are inputs to a future release, not news a TL should act on. The papers that earned cards yesterday still hold, and two more from the same batch belong: OpenAgentFlow, which normalizes every agent action into one event stream with audit records, and a clinical "morbidity and mortality" framework for reconstructing single AI failures from preserved evidence. Judgment: the market is converging on a single shape, an event stream in a warehouse-like store, evaluators that read it, and alerts that fire on the scores. No re-rank. Do not start the #435 clock.

Industry

1. Langfuse: evaluator alerts (Sep 2) on top of a stable evaluator API (Aug 27)

Today's changelog entry, "Create alerts for evaluators," lets you create an alert from inside the evaluator workflow with the metric and filters prefilled. Triggers: an evaluator's average numeric or Boolean score drops below a target, categorical score counts change "in topics, failures, or policy outcomes," or an LLM-as-a-judge cost threshold is crossed, for one evaluator or all combined. You pick how the team is notified.

The Aug 27 entry is the foundation: stable, ID-based endpoints under /api/public/v2 for evaluators and evaluation rules, with create, read, update, delete and version history. Names no longer act as identifiers, rules always use the latest version of their evaluator, and the stated goal is to "keep evaluation setup in version control" and reuse it across projects from CI. Old unstable endpoints must be migrated by November 16, 2026, the same day Langfuse Cloud goes v4-only.

TL;DR for BQAA. The eval loop customers now expect is score → threshold → alert, with the evaluator definition itself versioned as code. BQAA's eval results should carry a stable evaluator id and version so the same loop can be built with Cloud Monitoring or a scheduled query; that is a schema statement, not a feature.

2. LangSmith Engine: self-hosted, wired to Slack and Linear, cheaper to run (Aug 25)

Engine is LangSmith's in-platform agent that reads production traces, finds issues, proposes fixes and watches for regressions. The Aug 25 post says it is now ">2x better on internal benchmarks" at finding issues and "25% better on industry-standard benchmarks" at fixing them, has scanned over 60 million traces and surfaced more than 20,000 issues, runs self-hosted inside a customer VPC, posts detected issues to Slack, opens Linear tickets, closes stale issues automatically, and has a Reduced Analysis mode that scans fewer traces to save cost. Plus and Enterprise plans. The Aug 24–31 changelog adds that Engine usage now costs 40% fewer usage credits and that ABAC policies can scope access to matching project traces.

The Aug 18 Tuned Evaluators post (Perceived Error, a post-trained model that flags conversations where the agent "made a mistake, misunderstood a request, or took the interaction in the wrong direction") is already catalogued and unchanged.

TL;DR for BQAA. The trace store is being read by an agent, not a dashboard, and the output is a ticket. BQAA's answer to "who reads the table" should name the loop explicitly: the same event rows feed an issue-finding agent, and the issue it files points back at session and event ids.

3. AWS AgentCore Evaluations: any OTel or OpenInference agent, Google ADK included (Jul–Aug; walkthrough blog Aug 26)

AgentCore Evaluations has been GA since March 2026. The July release notes added evaluation of agents built with OpenAI Agents, LlamaIndex, Google ADK and Claude Agent SDK, alongside Strands and LangGraph, plus "generic framework support": emit spans in the OpenTelemetry GenAI or OpenInference conventions and the service "classifies your spans and extracts the values that evaluators need." The supported-frameworks doc keys everything on the span's scope.name; Google ADK is supported through the OpenInference ADK instrumentation, Python only. The Aug 26 blog is a walkthrough of this: invoke-agent, inference and execute-tool spans reconstructed from CloudWatch, then scored by built-in evaluators such as GoalSuccessRate, Correctness and Helpfulness.

August added two more things. Skill evaluators (Builtin.SkillSelectionAccuracy, Builtin.SkillInstructionFollowing) run per skill invocation and anchor each result "to the tool call span that loaded the skill." Third-party evaluators from DeepEval and AutoEval can be run managed or derived into custom evaluators, and all of them are discoverable through one ListEvaluators API.

TL;DR for BQAA. A hyperscaler now treats "spans that follow the GenAI conventions" as the producer contract and evaluates ADK agents through someone else's instrumentation. BQAA's coverage matrix should state, per framework, which instrumentation produces rows and which attribute names the evaluators may rely on. Skill-anchored eval results are a reminder that eval rows need a target span id, not just a session id.

4. Google Cloud, next door to BQAA: data-agent monitoring, ADK metrics in Cloud Monitoring, bigger spans (Aug 13–31)

Three platform release notes, none of them the BQAA product page.

  • BigQuery (Aug 24, Preview). "Monitor the performance, adoption, latency, and costs of your data agents and their conversations by using Google Cloud Observability in BigQuery." The doc lists agents used in conversations, users who asked questions, conversations created, top-answering agents, most-used knowledge sources, token usage projections and hourly answer latency. It requires the Cloud Trace, Cloud Monitoring and Cloud Logging APIs.
  • Gemini Enterprise Agent Platform (Aug 13). Agents on Agent Runtime built with ADK 2.6.0 or later "can emit gen_ai application metrics that follow OpenTelemetry's generative AI semantic conventions" to Cloud Monitoring as user-defined metrics, alongside traces and logs, behind one environment variable. On Aug 15 the semantic governance policy engine got built-in metrics in Preview: throughput, evaluation counts, latency, ALLOW versus DENY verdict distribution and token consumption, queryable with PromQL and usable in alerting.
  • Cloud Observability (Aug 12–31). Cloud Trace limits rose to 1,024 attributes and 256 events per span (Aug 17). The Telemetry API for OTLP logs went GA (Aug 14). Remote MCP servers now emit a span per tools/call (Aug 12, Aug 27). Trace sinks can no longer be created or edited as of Aug 31, and the stated migration path is Observability Analytics with SQL. Custom dashboards can show trace exemplars linked from SQL results (Preview).

TL;DR for BQAA. Google now has two first-party ways to see agent conversations in Cloud Observability that are not BQAA, and a SQL-over-traces path that is not BigQuery. The positioning line has to be precise: BQAA is the durable, joinable, per-event record for analytics and forensics, and it should ingest or link to the same gen_ai metrics and trace ids rather than compete with them.

5. ADK Python 2.8.0: opt-in agent and workflow metrics (Aug 26, still current)

Already covered in earlier briefs and unchanged since. With ADK_EXPERIMENTAL_TELEMETRY=true ADK emits per-invocation token spend on invoke_agent, per-workflow inference and tool-call counts, per-workflow token spend, MCP HTTP exchanges as OTel log records, and context cache state on the LLM call span. The Aug 27 v1.39.1 patch back-ported credential and inline-data exclusions from logs and spans to the v1 line. ADK Java's newest release, v1.9.0, has no observability item.

TL;DR for BQAA. These are the numbers a BQAA session summary should reproduce from rows, so that the metric and the table never disagree. Nothing new to do this week.

6. Braintrust: conversation-scoped online scoring and coding-agent traces (Aug)

Beyond the already-catalogued MCP write tools (Aug 26) and Harbor sandboxed evals (Aug 24), the August changelog lists two product features not yet in the catalog: group scope for online scoring, which evaluates "multi-turn conversations as single units," and coding-agent plugins that trace Claude Code, Codex, OpenCode and pi sessions through the bt CLI. Monitor views became dashboards with a project-scoped list.

TL;DR for BQAA. Session-scoped online scoring is now the default grain at a third vendor after Phoenix and LangSmith. Coding-agent sessions are an ingestion source peers take seriously; a BQAA example that loads a coding-agent transcript would be cheap and timely.

7. LangWatch Agent Testing v2 (Aug 30, v3.17.0)

Replaces Simulations. A run can hold up to four targets, each with its own parameters, and results render as a side-by-side matrix; scenarios and results are two tabs on one page, and test suites are folders of scenarios. The workbench gained "Optimize this prompt," which scores a baseline, generates candidates, evaluates them and returns a closing report.

TL;DR for BQAA. Multi-target comparison is the query shape: same scenario, N agent versions, one matrix. A BQAA example query that pivots eval scores by agent version and scenario covers it.

Academy

arXiv cs.AI's newest announcement day is still Wednesday, Sep 2. The cards below from that batch stand; two more from the same batch are added because they speak to the event-record and forensics rows.

9. Parsing the Stream: A Live Trace Model for Long-Horizon Agents and Their Observers (2609.01466)

Pakhomov and Nijkamp, Salesforce AI Research, code released. Thesis: a long-horizon trace outgrows both the human observer and the agent's own context, so keep an append-only event ledger, fold it deterministically into typed run state, and compile per-consumer views. Their observer-side result was roughly 14x fewer input tokens and 0.85–0.87 accuracy against 0.48 for reading the raw trace, with the caveat that only the token reduction transfers, "conditional on schema coverage."

TL;DR for BQAA. Outside evidence for typed state derived from an event table rather than model summaries of raw traces. Read the eleven folding requirements against the state and loop columns.

10. EDGE: Error Dependency Graph-Guided Multi-Error Attribution (2609.01360)

Hou, Pitre, Fang, Wang, EMNLP 2026. Failures contain several related errors; EDGE builds an error dependency graph, validates a causal subset by counterfactual rollout, and guides a two-stage judge. Evaluated on TRAIL and MAST.

TL;DR for BQAA. An error row needs a parent-error pointer, or every attribution tool will rebuild the graph from timestamps.

11. Cheap Verifiers, Large Blind Spots (2609.01345)

Rajput. In a cheap-answer, strong-verify cascade, every dashboard metric computed through the verifier "reads a flat 3% error while true delivered error swings up to 32%."

TL;DR for BQAA. Record which model produced each verdict so quality dashboards can exclude in-loop judges.

12. New: OpenAgentFlow: System-Wide Safety Boundaries for Heterogeneous AI Agent Fleets (2609.00015)

Chen, Zhao, Yao, Wei. A control-plane and action-plane architecture that "normalizes pending GUI actions, API calls, tool calls, and LLM-generated invocations into a unified AgentEvent stream," routes each through a shared pre-execution policy enforcement point, and "maintains provenance, session state, audit records, and updatable policies in the control plane." New rules take effect without changing agents, prompts or models. Evaluated on Android: 94.0% accuracy and a 95.3% block rate on a 300-case action-event benchmark, and a 92.9% trace-adjusted pass rate across 98 traced emulator cases.

TL;DR for BQAA. Enforcement stays out of scope, but the paper's event stream is the same normalized action record BQAA stores, and its audit records are what a forensics query reads. The producer contract should make a policy decision (allow, deny, rule id) a first-class event so an enforcement point can write into the same table.

13. New: AI Morbidity and Mortality: A Framework for Clinical AI Failure Review (2609.00076)

Mui, Sittig, Labkoff, Basu. Argues that aggregate model monitoring and incident reporting both miss how a single AI-related failure emerged, and proposes a blameless case-review framework built on "evidence preservation and investigator-level reconstruction, tool-in-loop attribution, and corrective-action tracking," with each case classified on four axes: Trigger, Mechanism, Clinical Pathway, Corrective Action. Five illustrative cases, two reviewers, full agreement on all 20 axis-level classifications.

TL;DR for BQAA. Forensics is a per-case workflow, not a metric. The test for the redaction and retention design is whether an investigator can reconstruct one session months later; that is the sentence to put in the redaction-as-forensics statement.

Six-week EV only

No re-rank. The ten rows and their order from 1434 hold. Evidence weight moves on three rows:

  • Named loop and eval schema. Three products shipped score-to-alert this fortnight (Langfuse alerts, LangSmith Engine to Slack and Linear, Braintrust alerts via MCP). The eval results table needs a stable evaluator id and version, a target span id (AgentCore anchors skill evals to the tool-call span), and the judge model id (Cheap Verifiers). A scheduled-query-to-alert example belongs in docs, not roadmap.
  • Coverage and producer contract. AgentCore's generic framework support and Google Agent Runtime's gen_ai metrics both define "conforming spans" as the contract. The coverage matrix should say, per framework, which instrumentation produces BQAA rows and which attribute names are guaranteed.
  • Forensics and redaction. OpenAgentFlow's audit records and the AI M&M reconstruction standard replace the unmerged OTel content-reference proposal as the outside citation for redaction as a forensics statement: what an investigator can rebuild from a session months later, and what a pointer to offloaded content is worth if the upload failed.

Positioning note, writing not engineering: Google Cloud now has first-party agent conversation monitoring in Cloud Observability and SQL over traces in Observability Analytics. BQAA's one-line difference is the joinable per-event record, and the docs should link to the gen_ai metrics rather than restate them. Reserve and do-not-start unchanged. Do not start the #435 clock.
