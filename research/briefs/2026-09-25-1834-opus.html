Theme 1: attribution keys are moving into the request itself.

  • Claude Code 2.1.283 adds x-claude-code-prompt-id to the gateway hint headers it can send (opt in with CLAUDE_CODE_GATEWAY_HINT_HEADERS=1).
  • I compared the 2.1.283 binary with 2.1.282, and this is the only new x-claude-code-* header name.
  • Names already present include session ID, agent ID, parent agent ID, agent type, request class and two compaction markers.
  • Codex 0.159.0-alpha.2 (its release object appeared this window) appends a fresh UUID to every exec-server process ID (#48168). Before this, threads sharing an executor, and sandbox retries, could reuse one process handle.
  • Vercel's harness packages changed two identities:
  • The ACP adapter now identifies tools by the protocol's tool.name field instead of display titles.
  • Harness sandboxes now live in their own sessions, which outlive the agent session.

Theme 2: voice agents change what a turn costs and how it is judged.

  • PydanticAI's GPT-Live meters audio seconds and backend tokens separately, at two prices. Its context-window ratio is a snapshot, "never summed". Two gaps are documented rather than fixed: a barge-in is recorded as a complete reply, and closing a session mid-reply loses that reply's usage.
  • Pipecat's judge now classifies and reports a confidence. On Pipecat's own replay, the Jev classifier matched 300 of 300 recorded verdicts, though 2 flipped between runs. Its median was 0.22 s per reply, against 6.2 s for the LLM judge.
  • 2609.29431: on task success in human–AI voice calls, no tested judge beat "the shorter call succeeded".

Theme 3: judges are instruments, and instruments drift.

  • 2609.28478: one judge-model upgrade moved a pass rate from 97% to 11% overnight, and 94% of 140,000 flagged failures did not survive a second judge. The team made three changes: repeated-judge panels that fail a case only when every run fails, a judge model chosen per evaluator, and softer rubrics. Precision per flag rose from 0.6% to 48.9%.
  • 2609.29431: a two-parameter transform, fit on a 32-conversation anchor set, puts different judges on one scale. It aligns scales; it does not make any judge more accurate.

Theme 4 (NOTE, unreleased): numbers that were quietly wrong, fixed on main.

  • Tokens:
  • Cline counted reasoning tokens twice in output tokens, including in the counts it reports to the Harbor eval harness (#14426).
  • Mastra's speed meter showed 4,840 tokens/s for a step that spent 60 s thinking and then wrote 40 tokens in 1 s (#25196).
  • Cost and privacy (LiteLLM):
  • Provider budgets ignored all Responses and Messages spend (#38172).
  • turn_off_message_logging left the prompt in raw_request (#43219).
  • 422 errors copied the submitted body, passwords included, onto OTel spans (#43231).
  • Traces: Phoenix merged two mappings of one span into messages that never existed (#16092).
  • Success that wasn't:
  • LiteLLM streams that ended silently now fail explicitly (four PRs).
  • A killed Docker command no longer reads as a clean exit in Mastra.
  • A jailbreak found mid-conversation no longer turns into a pass in Promptfoo.

What this means for BQAA (as the observer, not the source of truth):

  • Add a prompt-level key between session and request. Capture x-claude-code-prompt-id wherever a gateway logs headers. It is opt-in, so treat it as optional.
  • Meter voice sessions in two currencies.
  • Store audio seconds and backend tokens separately, each priced at its own model.
  • Store context-window ratios as the latest snapshot; never sum them.
  • Flag replies cut off by barge-in, a dropped connection or a close. They can be recorded as complete, or have no usage.
  • Register every judge as a versioned instrument.
  • Store the judge model and version, rubric version, panel size, each run's verdict, and the confidence with its source.
  • Track each evaluator's activation rate and its capture rate on a fixed set of severe cases. Expect step changes when a judge model is upgraded.
  • Calibrate on a shared anchor set before comparing judges.
  • Normalize reasoning tokens at ingestion. Vendors disagree on whether output tokens include reasoning. Store the provider's total, the reasoning count, and the convention used.

2. NEW rank: PydanticAI v2.51.0: OpenAI GPT-Live voice agents, metered twice, with context use reported as a snapshot

  • Clocks: tag 22:46:37Z, GitHub 23:19:04Z, PyPI 23:32:17Z (pydantic-ai and -slim).
  • The previous card on this line is pydantic-ai-v2-50-0-decision-model-decide-spans-route-threshold (0034).
  • The 1234 brief NOTEd #8390 and #8755 as unreleased. Both ship here.
  • What GPT-Live is (#8390, +25,061/−78).
  • It is "a separate protocol from the Realtime API". The Live model "runs the spoken conversation and delegates the work to a Responses backend".
  • PydanticAI gives that backend the agent's instructions and tools, so its calls arrive as ordinary tool calls.
  • Which model is the backend:
    1. An explicit option.
    2. A + in the model name (openai:gpt-live-1+gpt-6-luna).
    3. The agent's own OpenAI model, if it sits at the same base URL.
    4. Otherwise auto, which means gpt-6-sol.
  • How it is metered, which is the analytics part:
  • "Two usage meters."
    • Live's own audio is a cumulative duration. It is recorded as increments in RunUsage.audio_seconds and priced against the Live model.
    • Backend tokens "land on the ModelResponse that spent them and are priced against the backend's model".
  • Requests are counted differently. A new responses_are_requests flag makes usage.requests and request_limit count the backend's responses, not the spoken replies inferred from the audio.
  • One change reaches outside realtime. Spans and cost metrics now report response.usage.cost when the response carries it, instead of re-pricing it from response.model_name.
    • Without this, "a delegated Live turn is priced as gpt-live-1 using the backend's tokens".
    • The PR says no other model's span output changes.
  • Context use is a snapshot (#8803). context_window_used is "a provider-reported fraction (a snapshot, never summed)".
    • Where response tokens don't measure the whole context, the derived ratio is turned off. xAI Grok Voice reports incremental input tokens: verified live over five turns, they were 908, then 10, 5, 5 and 10.
    • GPT-Live's 128,000-token window is inferred from its reported ratios; OpenAI does not state it.
    • The value can drop after a server-side compaction or truncation "which no provider announces".
  • Recorded wrong, documented rather than fixed:
  • "Barge-in isn't recorded as an interruption: Live cuts its own reply off but says nothing on the wire, so the reply is recorded as complete."
  • "Closing mid-response loses that response's usage" (#8762), because OpenAI reports usage only in response.done.
  • The turn boundary is inferred. There is no end-of-turn frame, so the connection synthesizes ResponseDone after openai_live_turn_silence_ms of quiet, and a synthesizes_turn_boundary profile flag says so.
  • Fixed in this release:
  • #8762: tool-call responses on OpenAI Realtime had provider_details=None, and a reply cut off by a dropped socket or close() had no provider_response_id.
  • #8755: a forcing tool_choice on realtime now raises. As the 1234 NOTE reported, gpt-realtime-mini had looped on the tool until request_limit=6 ended the session.
  • #8761: Gemini Live close codes now raise RealtimeError.
  • On main after the release (NOTE): #8764 records user turns in speaking order. Before it:
  • a push-to-talk transcript could be filed after its own answer ("Peru?" recorded after "Lima.");
  • a barge-in turn could be filed before the reply it cut off;
  • with transcription off, one live test recorded "5 turns for 2 utterances".
  • Caveats: Pydantic's gateway cannot route Live yet. Live has no automatic reconnection. Final audio seconds after you close a session are an open issue (#8371).
  • TL;DR for BQAA:
  • For voice sessions, keep two meters, audio seconds and backend tokens, each priced at its own model.
  • Store context-window ratios as the latest snapshot; never sum them.
  • Flag inferred turn boundaries, and replies cut off by barge-in or close.
  • Don't read turn order in stored history as speaking order until #8764 ships.

3. NEW rank: Pipecat v1.12.0: typed classifiers for voice agents, an eval judge that classifies and reports a confidence, and a bridge that doubled every word

  • Clocks: GitHub 01:58:06Z; PyPI pipecat-ai 01:57:50Z. The previous release, 1.11.0, came on Sep 18.
  • First mention: no catalog item or brief has mentioned Pipecat before (grep: 0 and 0). Only DSH 1732, which landed during this run, reported it.
  • Pipecat Classifiers (#5863).
  • A classifier "answers typed questions about some state": yes/no, a choice among options, or a score on a scale. Each result comes with probabilities.
  • JevClassifier answers through TypeSafe's Jev, with a limit of 255 options per choice. LLMClassifier asks any Pipecat LLM service everything in one JSON call, with a 10 s default timeout.
  • Classifiers report metrics through on_metrics: processing time, and for JevClassifier the tokens used, as LLMUsageMetricsData.
  • The voicemail detector and the UI worker now decide with a classifier.
  • The eval judge now classifies (#5857).
  • EvalJudge decides every verdict with a classifier. An "explainer" LLM gives the reason for each no and each unsure verdict. "The classifier's verdict always stands."
  • JudgeVerdict has a confidence from 0 to 1: "With Jev the number is calibrated. With an LLM it is the LLM's own guess."
  • LLM judges behave differently too. They now get structured state instead of a prose prompt, so "A borderline reply can get a different verdict than before".
    • Simulations are now judged one bot turn per call, so they cost more calls. With the LLM judge, a simulation now takes about 13 s, up from about 1.9 s.
  • The PR's own replay:
    • Of 300 recorded turn-completion replies, Jev matched 300/300 of the recorded verdicts ("2 flip between runs, as Jev's borderline calls do"). The LLM judge (gemma4:12b) matched 297/300.
    • Median time per reply was 0.22 s for Jev and 6.2 s for the LLM judge.
    • An earlier sweep of 1,395 replies had Jev agreeing with the LLM judge on 1,394.
  • Running the release evals as shipped needs the jev extra and TYPESAFE_API_KEY.
  • Observability fixes that changed eval results:
  • Doubled words. "Fixed a bridged PipelineWorker reporting every frame from its LLM twice over RTVI ... which doubled every word of a bridged worker's reply in the client's LLM text and in the evals." enable_rtvi is now off by default for bridged workers.
  • Wrong reply judged. "Fixed the eval harness treating the bot's earlier speech as its reply when a scenario interrupts the bot" (#5846).
  • Duplicated or dropped turns and messages:
    • Inworld's realtime service resent a transcript after a fast tool result, which "duplicated user turns and responses" (#5116).
    • The Telnyx serializer silently dropped RTVI messages (#5841).
    • NVIDIA STT kept transcribing with its old settings while reporting the new ones (#5632).
  • Observer memory. Observers kept every frame ID they saw for the life of the session (#5908). Observers set to observe_every_push=False now see a frame once, and FramePushed.first_push marks the first push.
  • Also:
  • Every frame now has an interruptible flag (#5835).
  • User turns that end with no transcript get configurable handling (#5907).
  • The mcp extra now requires MCP SDK 2 (mcp[cli]>=2.1.1,<3).
  • Caveats:
  • The agreement numbers are Pipecat's own replay against its old judge's recorded verdicts, not against human labels.
  • Jev's borderline calls can flip between runs.
  • TL;DR for BQAA:
  • Store a judge's confidence together with its source, calibrated classifier or LLM self-report, and never average the two kinds.
  • Record which judge implementation produced each verdict, because a judge swap alone can flip borderline verdicts.
  • Dedupe voice-agent text by frame or turn identity; a bridge reported every word twice.

1. NEW rank: arXiv 2609.28478: When Evaluators Cry Wolf: Lessons from Production LLM-as-Judge Evaluation in Educational AI

Rohlfs, Vergara Bosse, Hopper, O'Keefe, Russell (MagicSchool AI). v1 dated 1 Aug 2026 (cs.CY), 16 pages.

  • It was listed at Thu 1834 as "backfill, not new work" and was never read or ranked.
  • It sits in cs.CY, which no scan since then covered.

Full PDF read: §1–7, Limitations, Ethical Considerations, App. A–E (Tables 1–3, Figs. 1–5).

What they did:

  • The setting. MagicSchool's offline evaluation layer, EvalEye, runs 21 deployed evaluators, each targeting one failure mode, across four severity groups (Table 1).
  • The product suite is used by "millions of teachers", with "millions of teacher and student messages each month".
  • A flag routes a case to analyst review. It is not a real-time block.
  • The trigger (§1):
  • "a vendor upgrade to an evaluator's judge model lowered pass rates on Factual accuracy from 97% to 11% in a single day". The drop was caused by the measurement, not by the product.
  • A second LLM judge re-examined every failure from 2.5 million evaluations over six months, and "In 94% of the 140,000 failures, the second model failed to corroborate the issue."
  • Three levers (§4):
  • Unanimous-fail panels. A panel is k repeated runs of one judge model on one rubric, capped at 5. It fails a case only if every run fails, and it stops at the first pass. Split cases go to a lower-priority "minority report".
  • A judge model chosen per evaluator: Sonnet 4.5, GPT-5.4 or Haiku 4.5.
  • Softer rubrics: fail only when the violation is unambiguous, fail only when it dominates the response, and judge the response as a whole instead of letting any single checklist item trip it.
  • Two measuring sticks:
  • A 2,482-case synthetic benchmark measures how often each evaluator fires, its "activation rate". The authors don't call it a false-positive rate, because the pool is unlabeled.
  • A 570-case synthetic set of egregious failures checks that the worst cases are still caught.

Numbers:

  • Activation (§5, Table 2). The median after calibration was 0.04%: 16 of 21 evaluators at or below 0.2%, and 8 at 0.00%. The single-judge baseline had a mean of 7.7% and a median of 1.9%.
  • Benchmark cases flagged in any non-trivial category fell from 2,086 to 72 (Fig. 2).
  • The biggest change was "Shallow", from 54.71% to 0.12%, still catching 29 of 29 egregious cases.
  • Precision per flag, audited by hand (Limitations). It rose from 0.6% (24 true positives among 4,002 flags) to 48.9% (43 among 88). True-positive flags rose from 24 to 43.
  • Severe-case capture. All 21 evaluators caught 100% of their egregious set afterwards. Before, the median was 100%, with a range of 73.3–100% (Fig. 3).
  • What drove the gain (App. E).
  • Going from 1 judge to 3 under the unanimous rule cut activation by about 40% on average, across three critical evaluators.
  • Five evaluators run a single judge, so their whole gain came from the rubric and the judge model. Readability went from 11.28% to 0.00%.
  • By the authors' reading, rubric changes were the main driver.
  • What failed (Table 3). Five instruction-following evaluators never reached deployable rates; their best configurations still fired on 2.23–20.72% of cases. The authors now plan narrow evaluators for the instructions that matter most.
  • Cost (App. E). Because the panel stops at the first pass, the average cost stays close to one judge call on traffic that passes anyway. Input context moved cost more than the panel size did.

Caveats I'd flag:

  • In-sample. The configurations were tuned on the same benchmark whose rates are reported, with no held-out split (Limitations).
  • Different audits. The before and after precision audits used different protocols: fixed rules plus human review, versus fully manual review.
  • Synthetic data. Both pools are synthetic, and the severe-set denominators are small, 12 to 79. At n = 12, the 95% lower bound on a 12-of-12 capture is 73.5%.
  • No isolation of levers. There is no factorial ablation, so no single lever's contribution is isolated.
  • Closed judges, and a known asymmetry the authors accept: one lenient judge run can pass a case, which they say would be wrong for front-line moderation.

Why it ranks:

  • It is production evidence that a judge is an instrument whose readings change when its vendor ships an upgrade. It gives the two health metrics a trace-analytics product can compute for every evaluator: activation rate, and capture rate on a fixed severe set.
  • It is distinct from the catalog's judge cards:
  • llm-judge-instrument-snapshot-identity-ladder: identical requests disagree about one time in five.
  • arxiv-2609-12191-gauge-judge-trust-boundaries: judge-satisfied transcripts that fail the task.
  • arxiv-2609-30074-eval-conclusions-reproducibility-self-audit: the pipeline around the judge.
  • None of them is a production program with a measured recipe and before/after precision.

TL;DR for BQAA:

  • Keep an evaluator registry: judge model and version, rubric version, panel size, each run's verdict and the stop point.
  • Chart each evaluator's activation rate over time, and alert on step changes after a judge-model upgrade.
  • Keep a fixed set of severe cases, and require 100% capture on it before any evaluator change ships.

2. NEW rank: arXiv 2609.29431: Calibrating LLM Judges for Human and AI Conversations

Züfle, Schmidtová (equal contribution), Zouhar, Bokkahalli Satish, Cooper, Banga, Nalawade, Kaur, Niehues, Müller, Klejch (KIT, Charles University, ETH Zurich, KTH, NICT, Voice Arena, Edinburgh). Submitted 24 Sep 2026 (v1, cs.HC), 5 pages. The authors release code and the VA dataset.

Full PDF read: §1–6, Tables 1–4, Fig. 1.

What they did:

  • Judges on human–human conversations. They scored four open judges on CANDOR: 1,636 recorded conversations between strangers, each at least 25 minutes, with participants' own success ratings.
  • The judges were Qwen2.5-Omni-7B, Phi-4-Multimodal and Qwen3-Omni-30B, given audio or transcript, and Qwen3.5-27B, given the transcript only.
  • Each judge scored conversations one at a time and also compared them in pairs.
  • A calibration method. They fit a monotone affine transform per judge on a small anchor set that has human scores, so that different judges land on one scale.
  • A new voice dataset. They built the Voice Arena Goal Dataset (VA): 200 task-oriented voice calls, 17.75 hours in total.
  • A human caller booked or changed flights with four AI systems (Gemini, Grok, OpenAI, Inworld) and a human agent.
  • Raters made 1,606 pairwise judgments across 397 pairs, on task capability and humanness.
  • A transfer test. They checked whether a calibration fit on CANDOR transfers to VA.

Numbers:

  • Judges agree weakly with people (Table 1). The best correlations with participants' own ratings were ρ = 0.32 (Phi-4, audio) and 0.28 (Qwen3.5-27B, text).
  • Separating clearly good from clearly bad conversations is easy: 93.6% and 90.3%, against 83.2% for a "longer transcript wins" baseline.
  • On general pairs, every judge scored below 70%, against 61.3% for that baseline.
  • Pairwise judging has position bias. Phi-4 and Qwen2.5 picked the first-presented conversation about 90% of the time.
  • Calibration (Table 2). Fitting a Wasserstein-affine transform on 32 anchors cut the distance between judge and human score distributions from 0.69 to 0.41 (optimized anchors).
  • Mean/SD matching was best with only 8 anchors.
  • Recommendation: a fixed, optimized 32-conversation anchor set, calibrated by closed-form mean/SD matching.
  • Transfer to human–AI voice calls (Table 4). The mean pairwise distance between judges' score distributions on VA fell 3–10×:
  • overall, from 1.44 to 0.29 (mean/SD) or 0.19 (Wasserstein);
  • humanness, from 3.08 to 0.61 or 0.30;
  • task capability, from 2.31 to 0.84 or 0.30.
  • On task success, no judge beats call length (Table 3).
  • "Shorter call wins" scored 65.0% on task and 60.4% on humanness. Humans reached 84.2% and 86.7%.
  • The best judge on task reached 64.7% (transcript). On humanness, the best reached 67.2% (audio), about 7 points above the baseline.
  • Overall, "Most score at or below the duration baseline", and only three variants beat chance significantly.

Caveats I'd flag:

  • Only small open judges (7–30B) were tested; there are no frontier or proprietary judges.
  • A monotone affine transform aligns scales but by design cannot change rankings, so it does not make a judge more accurate. This agrees with the catalog's arxiv-2609-27954-accuracy-gaps-fail-to-certify-llm-judge-recalibration.
  • The anchor set is made of human–human conversations. VA is small, with one to six raters per task instance.
  • The paper is short and has no limitations section.

Why it ranks:

  • It gives two results BQAA can act on:
  • A 32-item human-labeled anchor set plus a two-parameter transform makes scores from different judge models comparable, and the fit carries over to a new domain.
  • For voice-agent task success, call duration is a baseline that today's open judges do not beat.
  • It lands in the same window as GPT-Live support (PydanticAI) and Pipecat's classifier judge.

TL;DR for BQAA:

  • Store every judge score with its judge ID, and keep a small anchor set with human labels.
  • Fit and version a calibration transform per judge before comparing scores across judges or over time.
  • For voice-agent success metrics, always log call duration and report it as the baseline a judge must beat.
