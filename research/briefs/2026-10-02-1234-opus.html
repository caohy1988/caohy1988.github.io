I1 (NEW). MCP TypeScript SDK 1.32.0 and v2.3.0: same-origin redirects, tool-argument limits, token-audience binding, one server per request

What shipped:

  • Release clocks: GitHub 1.32.0 at 17:28:24Z Oct 2, with npm @modelcontextprotocol/sdk@1.32.0 at 17:32:51Z (latest). GitHub v2.3.0 at 17:55:03Z, with npm @modelcontextprotocol/server@2.3.0 at 17:48:29Z (latest), plus client / core / server-legacy / codemod 2.3.0, node 2.1.1, express / hono 2.0.2 and fastify 2.0.1.
  • Redirects stay on the same origin (v1 #2902, v2 #2901). The HTTP client transports follow a redirect only if scheme, host and port are unchanged; http to https on the same host is allowed. To redirect to another host, you must set redirectPolicy: 'follow' or configure the final URL. In browsers, a cross-origin redirect now fails unless that option is set.
  • Two new opt-in server limits:
  • maxToolInputElements on McpServer caps the array elements and object members in a tool call's arguments (#2927 / #2926).
  • expectedResource on requireBearerAuth (v2 also on verifyBearerToken) accepts only tokens whose audience is this server (#2930 / #2929).
  • v2 only:
  • One server per request: Server.connect() rejects an instance that is already connected, and a stateless Streamable HTTP transport serves one request (#2918). Creating a server is now cheap because tool schemas are no longer converted up front (#2889).
  • Large SSE messages are fast: with eventsource-parser ≥3.0.8 the client handles a large single-event message quickly. A 100 MB tool result went from about a minute and 1.7 GB of peak memory to under a second and about 0.5 GB, and a 50 MB result from about 13 s to under 1 s (#2846).
  • The Tasks extension's tasks/get and tasks/cancel work on 2026-07-28 connections (#2599).
  • allowedOrigins accepts <scheme>://* entries for browser-extension clients (#2907).
  • SSEClientTransport refreshes once after a 401 instead of retrying without limit (#2905, #2934).
  • v1 also: the in-memory task store keeps tasks within the session that created them (#2925).
  • Context: the repo's most recent published advisory is GHSA-6qxp-vccf-f47h (Sep 30, high: an OAuth client could send credentials to an authorization server chosen by the MCP server). This release continues that hardening, but it cites no new advisory.

Why NEW: there is no MCP SDK card in the catalog. This is the reference implementation most agent frameworks embed, and it changes default network behavior for every TypeScript MCP client.

BQAA read:

  1. A new class of connection failures. MCP endpoints behind cross-host redirects (load balancers, auth proxies) will start failing after upgrade. In agent telemetry this shows up as MCP connect errors, not tool errors. Keep mcp.connect failure reasons as their own dimension, so a jump after an SDK bump can be attributed.
  2. Audience binding is a security attribute worth logging. Whether a server enforces expectedResource decides whether a token issued for one MCP server can be replayed against another. Capture the setting with MCP server inventory when it is available.
  3. Large SSE payloads were slow on the client side. If BQAA ever saw multi-second tool latency on large results from TypeScript MCP clients, part of it was this client-side parsing cost. Recheck baselines after clients upgrade.

Native workflows can be hosted over Foundry Responses and Invocations (#8947, #8966).

  • Also in this release:
  • native computer use in Responses clients (#8751);
  • DuckDB and SQL Server vector stores and a TypeSafe AI connector (#8675, #8686, #8592);
  • Bedrock forwards Converse guardrail options and streams through ConverseStream (#8680, #8683, #8685).

Why NEW: there is no Microsoft Agent Framework card in the catalog. A major vendor's agent framework switching approvals to fail-closed is a product-level change, as is a durable-run model for its hosted agents.

BQAA read:

  1. "Blocked because approval could not be bound" is a new outcome. It differs from "user denied" and from "policy denied". An approval-outcome dimension should carry at least approved, denied_by_user, denied_by_policy and blocked_unresolvable. Otherwise fail-closed blocks look like user denials.
  2. Tool inventory now changes during a session, under policy. Labels applied at discovery time mean a tool's security label can appear partway through a session. Join tool calls to the tool-label state at call time, not at connect time.
  3. RUN_STARTED before execution helps run-level joins. AG-UI clients now get a run ID before any tool fires. Durable disconnected runs mean one run can span client sessions, so key runs by run ID, not by connection.

A1 (NEW). Continuous Process-Level Evaluation for Evolving Enterprise AI Agent Skills (arXiv 2610.01833)

Vo, Doshi, Sheinin (IBM Research / Georgia Tech). NeurIPS 2026 workshop, Continual Learning for Enterprise AI Agents. Full PDF read (13 pp., including Appendices A–B).

What they did:

  • They evaluated two revenue and productivity apportionment skills in an IBM resiliency system.
  • The skills run as Claude Code or Codex sessions over two MCP servers: 23 stateless tools over Instana, Kubecost and ServiceNow, and 18 tools over a SQLite state store (§4).
  • The evaluator has five stages (§5, Fig. 1):
  1. parse the harness tool-call trace (tool, arguments, return value, turn index);
  2. compute ground truth by calling the same live APIs independently of the agent;
  3. expand template test cases whose placeholders resolve at evaluation time from that ground truth;
  4. check tool selection, arguments, ordering by turn index (fetch → stage → readback → allocate → write), scope coverage and database integrity;
  5. collapse failures to root causes through an authored dependency graph.
  • The design: 2 skills × 2 specification variants × 2 harnesses × 3 models (GPT-5.6-Sol, Opus 4.8, Sonnet 4.6) × 10 trials = 240 runs (§6).

Key results:

  • Final numbers miss process failures (§7.1): 175 of 240 runs passed every final numerical check, and 162 of those 175 (92.6%; Wilson CI 87.7–95.6%) had another evaluator-detected deviation.
  • With a broader seven-check final-state baseline, 151 of 164 passing runs (92.1%) still violated a trajectory check: 109/109 for Revenue and 42/55 for Productivity.
  • All 120 Revenue runs got the revenue right, and all 120 had a deviation.
  • Removing the allowlist check, which is arguably normative, leaves the 162 unchanged.
  • Root families among the 162 (not exclusive, §7.1): data or numerical consistency 106, missing phase or required tool 66, allowlist 55, redundancy or call count 43, scope or filter 13.
  • The leading Revenue roots are wrong staged-utilization arguments (75/120), an off-allowlist tool (42/120) and a missing database readback (24/120).
  • Root-cause compression: a mean of 6.34 failed checks per run (median 4) collapses to 2.65 roots (median 2), cutting initial triage by 58% (§7.1).
  • Harness × specification interaction (Table 1): the same specification revision costs GPT-5.6-Sol −1.2 pp on Claude Code but +12.9 pp on Codex (Revenue). Bootstrap interaction intervals exclude zero for all three Revenue model comparisons.
  • Cost and reliability:
  • Unrecovered errors cluster in Codex (38 vs 5; App. A, Table 2).
  • Recorded cost was $859.34 across 240 runs: Claude Code averaged $1.04 per run against Codex's $6.12. Cache reads are 90.7–92.9% of Claude Code tokens for Claude models and 0% under Codex (App. B, Tables 3–4).

Limitations (App. A):

  • one system, one portfolio and one date window per skill, at 10 trials per cell;
  • the specification variants differ in content, not just format;
  • the evaluator encodes workflow policy (the "irrelevant tool" check is the root failure in 71/240 runs);
  • the judge (Sonnet 4.6) is also an evaluated model, and the 57/60 judge audit was done by the authors;
  • live-API ground truth can drift;
  • persistence under real API evolution is untested.

BQAA read: this is the clearest published case for SQL assertions over agent_events.

  • Tool presence, arguments, turn-ordered phases, per-scope call coverage and "readback before write" are each a query over the tool-call table.
  • Template tests with runtime placeholders map to parameterized checks whose expected values come from a reference query.
  • A dependency graph over checks gives "root failures per run", a better triage metric than a raw failure count.

A2 (NEW). Right Answers, Wrong States: Hidden Information Failures in Multi-Agent Collaboration (arXiv 2610.01244)

Wan, Wu, Luo, Ma, Li, Chen, Kan (Xi'an Jiaotong, NUS, Yunnan, A\STAR). Full PDF read (44 pp., including Appendices A–E). Code and data: github.com/whr000001/OffQuery.*

What they did:

  • The benchmark (OffQuery):
  • It builds 723 + 587 healthcare cases (from MediQ) and 93 disaster-response cases (from CrisisFacts).
  • A reliable global state is split into shared context and private observations across 5–7 agents.
  • One agent gets a fabricated, refutable claim, and the shared context gets misleading additions (§3.2, Table 4).
  • Three scores (§3.1):
  • T1 asks whether the team can identify the misleading source;
  • T2 asks whether it can rebuild the shared state, scored on atomic facts (keep reliable facts, drop injected ones);
  • T3 asks whether it answers the current multiple-choice question.
  • ReGround, their fix (§4), works in three steps:
  1. resolve conflicts between agents into a candidate pool;
  2. verify the shared context fact by fact against trusted sources;
  3. rebuild the state and reason only over it.

Key results:

  • The gap: averaged over 21 model–setting combinations, standard collaboration reaches T3 64.7% but T1 14.3% and T2 43.1% (§1, Table 1). GPT-5 on Healthcare-S scores T3 86.2% against T1 10.9% and T2 33.2% (Table 1).
  • Distribution alone hurts the state more than the answer (Table 2): with all information reliable, splitting it across agents drops T2 by 34.2 and 34.3%, but T3 by only 6.9 and 12.4%.
  • The mechanism is selective use (§6, App. E.1): unreliable facts appear in 60.9 and 71.7% of explanations for wrong decisions, but only 13.9 and 19.2% of explanations for correct ones.
  • Latent errors surface on reuse (§6, App. E.2): in 100 healthcare cases where T3 was correct but the state still held misleading facts, 43% of broader clinical plans were inconsistent with plans built from the reliable state.
  • ReGround improves all three scores in every setting, with average relative gains of +309.0% (T1), +82.9% (T2) and +17.6% (T3). It uses fewer tokens than standard discussion: 19.4K vs 52.1K with GPT-4o on Healthcare-S (Table 11).
  • Given the misleading source directly, T2 goes from .728 to .813 and T3 from .661 to .837 (Table 10). Source attribution is the bottleneck.

Limitations (App. A, D.2):

  • the benchmark and all corruptions are GPT-4o-generated;
  • the main setting has exactly one misleading agent (multi-source stress tests are in App. E.4);
  • T2 relies on an LLM judge;
  • Claude models were not evaluated, because of API limits;
  • episodes are bounded, with no persistent memory.
  • Inconsistency in the paper: §3.3 reports human–GPT-4o agreement of 0.86 with Cohen's κ 0.84, but Table 7 gives human–GPT-4o κ of 0.76 and 0.68. 0.84 is the human–human κ. I use the Table 7 figures.

BQAA read: task success does not certify what a multi-agent system carries forward.

  • For agents with shared memory or blackboards (ADK session state, A2A handoffs), log state writes as facts with their source agent. Then "facts in state that no trusted source supports" becomes a metric next to answer accuracy.
  • A correct trace today can be the cause of a wrong answer tomorrow.

A3 (NEW). Agents Are Systems, Not Models: Rethinking Agentic Evaluation (arXiv 2610.01618)

Wiedmann, Girrbach, Schmid, Akata (TU Munich / MCML / Helmholtz Munich / Inria). Full PDF read (main text plus Appendices A.1–A.18). 18,240 trajectories released.

What they did:

  • The tasks: four science tasks where a coding agent must find and operate a published specialist model. Three tasks reward using the specialist (redshift from galaxy images, promoter prediction with fine-tuning, RNA folding). One rewards declining a weaker specialist (MMLU-astronomy).
  • The configuration axes:
  • Information: none, identity, interface or protocol;
  • Reasoning: act-only, think-act or ReAct;
  • Verification prompt: none, asked, reported or binding;
  • Budget: 5, 10 or 20 minutes;
  • Model: Qwen3.5 35B, 122B or 397B.
  • The grid: 432 cells × 5 repeats × 4 tasks = 8,640 main runs, plus Step-3.7-Flash, Claude Sonnet 5 and oracle-tool ablations (§3, §4.1, Table 4).
  • The metric: the share of the backbone-to-specialist gap the agent closes. A hurdle separates genuine attempts from trivial ones.

Key results:

  • Noise: among genuine attempts, about 54% of score variance is within-configuration repeat noise (ICC 46.1%; 39.4% over all completed runs; §4.2, Table 8). 19.3% of runs ran out of budget (A.4).
  • Information dominates. Effect sizes are 1.93, 1.45 and 1.50, against Model at 0.70, 0.17 and 1.25 (Table 3). Information ranks first in ≥99% of bootstrap draws (A.9). More information also lowers cost and runtime and improves calibration.
  • Interactions: more budget lowers the score for the small model and raises it for the large one (Table 19). On redshift with no task information, more time makes the result worse (Table 9).
  • Verification is a system property, not a prompt property (§4.3, §5, Fig. 4):
  • Moving the prompt from none to binding raises reference-based verification only from 19% to 22%.
  • An oracle-check tool roughly triples it, raises Qwen-122B pooled G from 0.822 to 0.923, and cuts calibration error from 0.093 to 0.002 (Table 12).
  • Only 4.4% of oracle runs hill-climb (A.12).
  • Authority bias: 99.8% of MMLU-astronomy runs used the weaker specialist. Accuracy was 0.685, against 0.967 for the backbone alone (A.13).
  • Closed vs open model (Table 17): Claude Sonnet 5 uses fewer tool calls (14.2 vs 31.4) and makes fewer errors (0.5 vs 2.6), and is better calibrated. But its pooled G is lower (0.828 vs 0.870), and for it Budget, not Information, ranks first (Table 16).

Limitations (§6):

  • four tasks in two domains;
  • memory and multi-agent setups excluded;
  • the "system beats prompt" finding is shown on one behavior (verification);
  • open models are FP8-quantized.

BQAA read:

  1. Log configuration as dimensions. Outcome analytics are noisy without them: information level, budget, model and whether a verification tool exists.
  2. Report variance and repeat counts. With half the variance being noise, a single-run success rate in a dashboard is misleading. Show confidence intervals per configuration, and keep completion separate from genuine-attempt success.
  3. Tool calls beat prompts as evidence. If verification behavior is wanted, it should show up as tool calls in the trace, not be inferred from the prompt.

Six-week EV

  1. MCP transport defaults keep tightening. The TypeScript SDK now limits redirects to the same origin and offers audience binding. goose added an SSRF guard on MCP redirects. Expect the Python MCP SDK to match the redirect and audience behavior, and at least one major client to make audience checks the default, by mid-November. MCP connect-failure analytics will need a "policy refused" reason. Value: medium-high.
  2. Process checks over traces become the eval product pitch. IBM shows 93% of right-answer runs broke the required process. Phoenix is hardening online evals, and Mastra and LiteLLM are building trace-aggregate queries. Expect at least one observability vendor to ship "trajectory assertions" (ordering, scope, required-step checks) as a first-class feature within six weeks. BQAA can offer the same as SQL over agent_events. Value: high for BQAA.
  3. Vendor-hosted agents emit lifecycle events as well as traces. OpenAI now has session webhooks to go with OTLP traces. An ingester needs failed and action_required events to know when to pull. Expect at least one more hosted-agent platform to pair traces with status webhooks. Value: medium.
  4. Fail-closed approval spreads. Microsoft Agent Framework now blocks unresolvable approvals; Pydantic blocks when unsure (prior slot). Analytics that can't tell a policy block from a user denial will misreport human-in-the-loop friction. Value: medium-high.
