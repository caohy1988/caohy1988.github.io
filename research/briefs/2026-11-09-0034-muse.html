Two papers clear the bar, both about costs that outcome-only measurement hides. First, a controlled study of 732 coding-agent trajectories shows that one stale line in a repository instruction file makes agents run checks that test nothing and pay extra tool calls on every later run, while task success never moves. Academy

NEW 1 — When Instruction Files Go Stale: Documentation Debt and Hidden Cost in Coding Agents — https://arxiv.org/abs/2611.09802

Full PDF read (pdftotext, every part including methods, results Tables I–III, discussion and threats to validity).

The authors take three real stale lines from active open-source repositories — a moved test command, a moved code location, and a moved add-a-component procedure — and run the same 22 maintenance tasks under three versions of each line (stale, corrected, removed) with code and task held fixed: 732 runs, two models from one vendor in one harness, analyzed tool call by tool call (Section III, Table I). Agents took the stale path in 78/80 runs for the test command, 55/80 for the procedure, and 0/84 for the code location no task needed (Table II). Task success did not move in any condition. The measurable cost is narrow but real: on the stale test command the stronger model used 7.8 tool calls vs 5.8 corrected (about two extra per run, a third more), and in 19 of its 40 stale runs the first check of its own fix ran zero tests because the documented command pointed at a deleted folder and the piped output still reported success (Section IV, RQ2). Agents recovered in 130/133 encounters, mostly by search, but only 21/133 final reports named the mismatch and 0/732 runs edited the instruction file (Table III). Correcting the line removed all stale-path work; deleting it removed most but agents still guessed the old folder in 20/80 procedure runs.

Why it matters for BQAA: this is a clean existence proof that success-only evals and even patch inspection miss recurring trajectory waste — in four tasks all 15 runs across conditions produced byte-identical patches, so only the path differed. A trajectory metric that counts "a test call happened" would score the zero-test run as verified. Limits: three cases where instruction type, repo and tasks vary together; the effort effect is exploratory and resolves for one model on one case only; seeded small bugs (Section VI). Read it as a mechanism with a measurement recipe (stale-path operations, zero-test verification rate), not as a general rate.

NEW 2 — AutoRefine: Auto-Calibrating Code Judges from Workflow Outcomes — https://arxiv.org/abs/2611.09291

Full PDF read (pdftotext, every part including method, results Tables I–II, threats and conclusion).

A team at a large platform company describes a loop that rewrites a deployable code judge's prompt to reproduce labels the workflow already emits (tests pass/fail; diffs land or are abandoned). An informed teacher sees the judge's view plus the outcome, explains each label it keeps, and abstains (drops the sample) when the outcome cannot be explained from that view (Section II). Under trustworthy execution-oracle labels, calibration raised a rubric judge's chance-corrected agreement (Scott's π) from 0.36 to 0.60 on an 85-task held-out test, beyond threshold tuning (Table I). With 25% of labels flipped at random, the teacher set aside flipped FAIL labels at more than twice the rate of genuine ones, cutting noise from 24.9% to 20.4% (Section IV-A). Recalibrating a deployed performance-optimization agent's judge raised π on 17 independent held-out diffs from 0.16 to 0.51 and landed-diff recall from 6/8 to 8/8; on 16 older diffs the previous judge stayed ahead, which is the paper's point about recalibrating as the judged system evolves (Table II). Abstention doubles as an input-quality signal: without a reference patch the teacher abstained on 12/13 hidden-test failures and 0/72 passes (Section III-C).

Why it matters for BQAA: it is a production pattern for keeping LLM-as-judge honest without hand labels — outcome joins plus an abstention rate that says "fix the judge's inputs, not its prompt." Limits are material: one company, one deployed agent, small held-out slices (n=17), judge and teacher from the same model family, and an asymmetric teacher that keeps most failing diffs mislabeled PASS (Section VI). Card it as a method to pilot with independent audit, not as validated effect sizes.

Six-week EV

  • Stale-instruction waste (2611.09802): High EV as a BQAA product check, low build cost. Flag instruction-file paths that no longer exist at session load, and add two trajectory metrics to any agent analytics surface: operations on nonexistent paths and verification calls that executed zero tests. Both are computable from stored spans today.
  • Outcome-calibrated judges (2611.09291): Medium-high EV as an operating pattern wherever BQAA-adjacent evals gate agent output. Join judge verdicts to downstream outcomes (landed/abandoned, passed/failed), track chance-corrected agreement over time, and treat a rising "outcome not explainable from judge inputs" rate as a schema bug. Pilot needs an independent human audit slice; do not copy the small-n effect sizes.
  • Per-query token forecasting (2611.09028, unranked): Medium EV as background for cost analytics. Median-per-model pricing materially misprices reasoning workloads; per-request length distributions belong in cost dashboards even without building a router.
