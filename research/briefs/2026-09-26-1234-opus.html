Theme 1: the route to a model is part of the measurement.

  • Inspect 0.3.269 (Sep 25) and 0.3.270 (today) show how much a gateway can change an eval:
  • #5559 (0.3.269). Before Inspect had a LiteLLM-specific provider, evals through a LiteLLM proxy had no context window or cost for the model. Claude replies were cut at LiteLLM's 4,096-token default for models it didn't know, and one deployment "recorded 0 cache reads over 715M input tokens".

How I checked:

  • The tag compare 0.3.269...0.3.270: 10 commits touching 29 files.
  • I read the PR bodies for #5575, #5577, #5579, #5519, #5551 and #5532, plus #5559 from 0.3.269.
  • I downloaded the published wheel and confirmed three changes in the built code:
  • scorer/_classification.py builds Counter word counts for _f1;
  • _eval/task/run.py (lines 3631–3672) reuses a prior log when the dataset grew as a strict superset;
  • model/_providers/litellm_proxy.py defaults GPT-5+, o-series and Codex models to the Responses API when responses_api isn't passed.

What changes in the logs and scores:

  • Proxied OpenAI reasoning models keep their reasoning (#5575).
  • Before, every request through the provider used Chat Completions, "where OpenAI returns no reasoning, so a GPT-5 tool loop through the proxy starts each turn without its earlier reasoning".
  • Now GPT-5 and later, o-series and Codex models use the Responses API, streamed, with encrypted reasoning replayed each turn (store=false).
  • This applies only when every deployment of the alias uses LiteLLM's openai route with no other api_base. Azure and OpenAI-compatible servers are not covered. -M responses_api=false opts out.
  • Key and team aliases now resolve to their target model through /key/info and /team/info. Before, an alias failed to construct for lack of model info, even though it routed fine.
  • In the PR's live check through LiteLLM 1.104:
    • cost includes cached input at the cache-read rate;
    • on gpt-5-mini, effort none is dropped, and xhigh and max are lowered to high with one warning each.
  • Claude reasoning reaches the log through older LiteLLM (#5579).
  • On LiteLLM 1.96, Claude 4.7+ returned thinking "with empty text (only a signature)".
    • A live before/after with Opus 5.5 at high: 0 characters plus a 1,396-character signature became a 249-character summary.
    • The stream also carried no bytes while the model thought. A thinking phase longer than the 600 s request timeout "fails and is retried from scratch", on "about 1–1.5% of calls" on one deployment.
  • Now Claude 4.6+ requests with an effort send thinking: {type: adaptive, display: summarized}. -M thinking_display=omitted opts out.
  • Known limit: on LiteLLM 1.104, a Claude 4.6 codename configured with base_model but without the model_info flags silently gets a 2,048-token thinking budget instead of the effort's 4,096.
  • eval_set tops up grown datasets (#5577).
  • When a dataset grew as a strict superset with stable sample ids, prior samples are reused by (id, epoch) and only the new ones run. The successor log holds all of them.
  • A shrunk dataset, growth without stable ids, or an unknown prior count still re-runs everything.
  • The PR notes that reuse "never inspects sample content". At equal count it already reused samples by id regardless of content.
  • f1() counts repeated tokens (#5519).
  • It scored token overlap as a set, so "Paris Paris Paris Paris Paris" against "Paris" scored 1.0.
  • It now uses multiset overlap, matching SQuAD F1. Only answers or targets with repeated tokens move; the PR's test case drops from 1.0 to 0.67.
  • Live readers stop mixing attempts (#5551).
  • In shared log directories, a retried or requeued sample inherited the previous attempt's buffered events.
  • The viewer, filestore recovery and inspect ctl sample events --log-dir saw both attempts as one sample. A model event could resolve its input to the previous attempt's messages.
  • It affected readers of the synced sample buffer; the changelog describes it as happening while the sample runs.
  • Checkpoint resume (#5532).
  • After a resume, hooks (on_sample_event), the live viewer and ACP clients received attachment:// references instead of the restored text and images. They now get the content.
  • Raw model API calls stay condensed until the sample completes. "The final eval log is unaffected."
  • Context from 0.3.269 (#5559, Sep 25).
  • Before the litellm-proxy provider existed, evals through a LiteLLM proxy used the generic openai-api provider:
    • there was no context window or cost for the alias;
    • no max_tokens was sent, so LiteLLM's 4,096-token default cut replies from Claude models it didn't know;
    • one deployment "recorded 0 cache reads over 715M input tokens".
  • The authors filed six LiteLLM bugs upstream.
  • The 0.3.269 changelog also records reason="no_response" for empty completions, with score values unchanged. Samples cut off by a cancellation Inspect didn't issue now count as errors instead of completed. Both are changelog only.

Caveats:

  • It is a point release in a fast train: 0.3.265 through 0.3.270 shipped in nine days.
  • The Responses default covers only OpenAI-routed aliases. Azure, OpenAI-compatible servers and model_info=false stay on Chat Completions.
  • The 715M-token and 1–1.5% figures each come from a single deployment described in a PR body.

Why it ranks:

  • It changes four things an eval store derives from Inspect logs:
  • model behavior for gateway-routed OpenAI reasoning models (API family and reasoning replay);
  • what reasoning text the log holds for Claude through LiteLLM;
  • the definition of the F1 metric;
  • sample provenance in topped-up eval sets.
  • Its PRs show, with numbers, that the same model scored through a gateway and directly was not the same experiment.
  • It is the first Inspect card. The nearest catalog cards are other eval vendors' releases: promptfoo-0-123-1-openai-agents-api-portable-mcp-schemas and deepeval-4-2-4-to-4-2-5-jev-system-one-classifiers-jeveval.

TL;DR for BQAA:

  • Tag every eval sample with its route (direct provider or litellm-proxy) and API family.
  • Before 0.3.270, proxied GPT-5-class runs had no reasoning replay.
  • Before 0.3.269, proxied runs of Claude models LiteLLM didn't know could be capped at 4,096 output tokens with no prompt caching.
  • Segment F1 scores by Inspect version at 0.3.270.
  • For topped-up eval sets, keep a per-sample reused-or-new flag and per-sample timestamps. A log's creation time no longer dates all of its samples.
  • Expect Claude reasoning text in LiteLLM-routed logs from 0.3.270. Don't read its earlier absence as no reasoning.

1. NEW rank: arXiv 2609.24130: Self-Healing Harness for Runtime Oversight of Agent Self-Modification

Tayebati, Kumar, Darabi, Krishnan, Trivedi (University of Illinois Chicago; Krishnan at AI Labs, Capital One). v1 21 Sep 2026 (cs.AI), 16 pages.

  • The paper states that Capital One does not use the method.
  • There is no code or artifact link. Tracing and evaluation run on the first author's PandaProbe.

Full PDF read: the main text (RQ1–RQ5, Limitations, Conclusion) and the Technical Appendix (Tables 1–14, Algorithms 1–3).

What they did:

  • The question. An agent that can rewrite its own operating instructions needs a rule for which self-edits persist. Improving the failure that prompted an edit is not enough, because the same edit can break something that worked.
  • The harness wraps an unmodified agent with fixed weights and runs a Detect, Notice, Heal, Validate loop:
  • Detect. Each turn's trace is scored, and a gate fires on the shape of each metric's series, not on a single low score.
    • It fires on a stall (10 traces without a 0.02 gain while the peak is below 0.5) or a regression (a drop of more than 0.15 below the running peak).
    • Cheap metrics (task completion, coherence) run every turn. Tool-call and argument correctness run on the latest trace only after a flag.
    • Only a finding corroborated by a step-level or outcome failure becomes a replayable case.
  • Notice. The finding goes to a mailbox in an external workspace, not into the conversation.
  • Heal. The agent pulls the notice and writes a candidate rule, which is in force provisionally.
  • Validate. The runtime replays up to three matching failure cases and two previously passing "protected" cases under the candidate.
    • It promotes the rule only if the target metric improves by at least 0.05 on one failure case and no metric on any replayed case drops by 0.05 or more. Otherwise it retires the rule.
    • When replay isn't possible, a weaker forward trial compares the flagged rate over the next three sessions.
    • A corpus guard re-tests the whole active rule set.
    • Each promotion records the case, metric and improvement that justified it.
  • The evaluation. Paired Baseline and Harness runs:
  • benchmarks: AppWorld test_normal (168 tasks), Terminal-Bench sample@2.0 (10), and τ²-bench airline (50) and retail (114);
  • models: gpt-5.6-terra, gpt-5.6-luna, claude-haiku-4.5 and claude-sonnet-5;
  • k = 4 trials per task and seed 1, giving 16 pairs.

Numbers:

  • Most rejected edits were locally right and globally harmful (Table 2).
  • Agents proposed 2,306 rules. 1,244 were promoted and 1,062 retired (Table 10).
  • Of the 383 retirements decided by replay, 211 (55%) improved the failure that motivated them but regressed a protected case. The other 172 improved nothing.
  • Observed regressions include a 0.60 drop in task completion and a 0.25 drop in outcome correctness.
  • "A retention policy keyed only to improvement of the triggering failure would have accepted every one of them."
  • End-to-end gains are modest (Table 1). Task-completion score rose in all 16 pairs, but only two intervals exclude zero:
  • AppWorld with gpt-terra: 0.701 → 0.723 (+0.022, 95% CI [+0.006, +0.040], p = 0.010), with pass@1 from 0.018 to 0.054;
  • τ² retail with claude-sonnet-5: 0.669 → 0.701 (+0.032, [+0.003, +0.061], p = 0.03).
  • Success on all four trials was higher in 12 pairs and tied in 4.
  • Rules admitted one at a time still drifted as a set (Table 4).
  • On AppWorld with gpt-luna, the paired advantage fell from +0.017 in the first quarter of tasks to −0.016 in the last (p = 0.022).
  • Over that span the active set grew from 13 to 70 rules, and input tokens per turn from 1.50× to 2.52× Baseline.
  • "Every rule passed the gate individually, so the harm is a property of the corpus."
  • The corpus guard could not see it, for three reasons:
    • it replays only captured failure cases;
    • it flags only per-case drops of 0.05 or more;
    • it cannot reproduce live retrieval dilution.
  • The judge was biased against the harness's own tools (Table 12).
  • Trace judges penalized calls to the harness's read-only meta-tools: 14% of sampled rationales blamed them, and 31 scores were spurious zeros.
  • Neutrality guidance in the judge prompt cut this to 0.17% and 1 zero across 4,800 sampled rationales. Both arms use the corrected prompts.
  • Replay was not always possible (Table 3).
  • Replay settled 58–92% of validations, except on Terminal-Bench. There it settled 0%, because validating would mean rebuilding the environment, so no rule was ever retired there.
  • On τ² airline, a budget counted in turns but spent in message hops truncated many replays.
  • Cost (Tables 13–14):
  • context averaged 1.25× Baseline, and agent turns rose by 0.0 to 1.8 per trial;
  • task spend went from $177.06 to $211.46, plus $92.90 of repair (1.72× overall);
  • wall-clock time rose 1.7–7×, mostly from synchronous trace evaluation. AppWorld went from 17–20 s to 109–120 s per trial.

Caveats I'd flag:

  • The authors did not run the arm that would isolate the gate's benefit: the same agent admitting its rules immediately. So the end-to-end gains don't show that gating, rather than the healing loop, is what helped.
  • Only 2 of 16 intervals exclude zero, and all runs use one seed.
  • Each decision replays at most five sessions and at most two unranked protected cases. The 211 are detected conflicts, not an incidence rate.
  • The forward-trial path has no protected-case test and a lenient default baseline (p0 = 1).
  • The agent is assumed non-adversarial, the guarantees cover only measured metrics, and no code is released.

Why it ranks:

  • It measures, on the agent's own proposals, how often "fixes the failing case" coincides with "breaks a passing one": in 55% of the replay rejections. That supports replaying protected cases before any skill, prompt or rule persists.
  • It also shows a second failure scale: every per-candidate check passes while the accumulated set degrades, with context growth as a visible covariate.
  • It is distinct from two replay cards in the catalog:
  • arxiv-2609-20625-chronicle-cut-point-replay-regression replays to regression-test an agent build;
  • arxiv-2609-14858-dream-rsi-discovery-history-replay-simulator replays search histories to re-score orchestration policies.
  • Here, replay is the runtime admission test for agent-authored changes.

TL;DR for BQAA:

  • Store per-turn metric series, and captured failure and protected cases with their baseline scores. Both the trigger and the admission test depend on them.
  • Log each self-authored change's lifecycle (proposed, promoted, retired) with its case, metric and delta.
  • Track outcome by execution order against active-rule count and input tokens per turn, to catch drift no per-case check sees.
  • Audit judge rationales for bias against specific tools whenever the harness adds tools.

2. NEW rank: arXiv 2609.27607: Can Jev Judge Radiology Reports? Evaluating a System One Model for Clinical Factuality

Huang, Yang, Ma, Liang, Cai, Ma, Chen, Sun, Tan (Macao Polytechnic University; Liang at the Netherlands Cancer Institute and Radboud UMC). v1 23 Sep 2026 (cs.CL, cross-listed to cs.AI), 19 pages. The analysis scripts are "not yet publicly available".

Full PDF read: §1–7 and App. A–G (Tables 1–3 and A1–A12; Figs. 1–4, A1 and A2).

What they did:

  • The judge. TypeSafe's Jev (jev-1.13.0) answers typed questions with probabilities.
  • A local Qwen3.5-9B splits each report into atomic findings.
  • Each finding goes to Jev with the full opposite report and one Choice question: is it supported, contradicted or not addressed? This is "OneQ".
  • A report's error score sums contradiction and non-coverage for the generated report's findings, plus non-coverage for the reference's findings.
  • "Full" adds six questions: negation and hedging booleans, the error type, and clinical significance.
  • The tests:
  • Kendall τb against radiologists' error counts, on RadEvalX (100 pairs) and RadEvalExpert (624 pairs from 208 studies);
  • 19,513 controlled-error sentences from ReXErr;
  • comparisons with an open DeBERTa NLI judge under the same decomposition, a finding-count baseline, GREEN, RadCliQ, and local RadFact and RadMatch (Qwen3.8-27B);
  • five-run repeatability;
  • token cost at the listed $0.042 per million input tokens (output tokens are free).

Numbers:

  • Agreement with experts (Table 1):
  • OneQ reaches τb = 0.573 [0.470, 0.661] on RadEvalX and 0.398 [0.339, 0.455] on RadEvalExpert (total errors).
  • The NLI judge, with the same decomposition and aggregation, reaches 0.337 and 0.323. Counting findings alone reaches 0.288 and 0.261.
  • Local RadMatch ties on RadEvalX total errors (0.580) but leads on clinically significant errors (0.491 vs 0.346).
  • On a shared 200-pair RadEvalExpert subset RadMatch leads on both: 0.453 vs 0.322 (total) and 0.485 vs 0.259 (significant).
  • One question is enough (§5.3, Table A8):
  • OneQ vs Full changes τb by −0.009 [−0.026, 0.008] and +0.001 [−0.002, 0.004].
  • It uses 44.56% and 43.03% fewer input tokens: 9,695 → 5,375 and 10,797 → 6,151 per pair.
  • That is $0.000226–$0.000258 per pair, about 2.3–2.6 cents per 100 report pairs, excluding local decomposition.
  • In a three-finding demo (§5.4, App. E.1), Jev cost $0.00005044 against $0.00018520 for GPT-5.6 Luna with reasoning off (about 3.7×). Median time was 1.13 s against 3.57 s, and all 30 calls gave the same labels.
  • What it catches (§5.2, Table A9):
  • Sentence-level AUROC is 0.977 for false negation (91.9% recall at 0.5), 0.984 for a changed location, 0.975 for severity and 0.989 for an added device.
  • Typos score 0.562, and recall on repetition is 0.003.
  • So NLI wins when meaning-preserving edits count as errors (0.8969 vs 0.8896 overall), and Jev wins on factual errors only (0.9680 vs 0.9614).
  • Scores vary run to run; rankings don't (Table 3):
  • Across five uncached runs, no pair got an identical score, yet median between-run rank agreement was 0.990 for OneQ. The SD of its expert correlation was 0.0038.
  • GREEN with greedy decoding repeated exactly.
  • RadMatch at its default temperature of 1.0 repeated exactly for 10% of pairs, with rank agreement 0.662. At temperature 0 that rose to 82% and 0.965.
  • Calibrate before thresholding (§5.6, App. G, Table A10):
  • Raw sentence-level expected calibration error (ECE) is 0.1192, against 0.1045 for NLI.
  • In Jev's lowest-probability bin, 16.7% of sentences carried an injected error, although the mean predicted error probability there was 0.37%.
  • Much of that bin is plausibly the typo and repetition class, which Jev treats as meaning-preserving. That is my inference from Table A9, not a number the paper reports.
  • Isotonic calibration fit on held-out studies cut ECE from 0.1235 to 0.0077, with AUROC unchanged.
  • At report level, Full's top score bin averages 8.53 against 5.30 expert errors.
  • Aggregation carries report size (§5.5). On the 200-pair subset, the same Full judgments give τb 0.320 as a count and 0.111 as soft F1.

Caveats I'd flag:

  • Scope:
  • Agreement is measured against the reference text, not the image.
  • Only one Jev version is tested, and the expert sets are small.
  • RadEvalX has one generator and RadCliQ-stratified sampling.
  • Method:
  • Sentence-level detection and calibration use Full, not OneQ.
  • The baselines ran on a local 27B backend rather than their original judges.
  • The weight setting that reaches τb 0.635 was chosen on the evaluation labels, which the authors flag.
  • Report-level error categories are unreliable. The "false finding" share dominates even for location and severity errors (App. F).
  • The scripts are unreleased, and the price is the paper's listed rate.

Why it ranks:

  • It adds the operating numbers the catalog's Jev-as-judge cards lack:
  • how many questions you need (one);
  • what a judgment costs;
  • that raw probabilities are miscalibrated until fit on your data;
  • that scores never repeat exactly while rankings do.
  • It qualifies the confidence-threshold rules in earlier cards: arxiv-2609-26550-jev-as-a-judge-accept-escalate (CMU; accept when q ≥ 0.9) and arxiv-2609-29769-jev-vs-llm-rubric-judges-correlated-errors (Penn; 29–325× cheaper). A raw-probability threshold needs task calibration first.
  • It shows that count-based scores partly measure output size: the finding-count baseline alone reaches τb 0.26–0.29.

TL;DR for BQAA:

  • Store every judge call as a probability vector with the judge name, version and question id, not just the top label. Then re-aggregation, calibration and thresholds become queries.
  • Fit calibration per task and judge version before any accept-or-escalate threshold, and keep a small labeled holdout.
  • For regression detection, compare judge rankings across reruns rather than raw scores.
  • Report a size baseline (findings, claims or steps) next to any count-based judge score.
