I1 (NEW). Agno v3.1.0: AgentOS role-based access control with an audit log, a per-user filesystem, and MCP tools that are opt-in

Primary: https://github.com/agno-agi/agno/releases/tag/v3.1.0 (published 2026-10-01T09:29:15Z, not a prerelease) · PyPI agno 3.1.0 (uploaded 2026-10-01T09:30:24Z) · release PR https://github.com/agno-agi/agno/pull/10702 · v3.1 feature PR https://github.com/agno-agi/agno/pull/10530 · MCP opt-in PR https://github.com/agno-agi/agno/pull/10285

What shipped (from the release notes):

  • User management and authorization (RBAC). A new agno.os.authz package adds a role store, a scope policy, an audit log, a user directory and an admin router to AgentOS. Authorization runs through pluggable engines: a native engine, or a fine-grained fga engine. Scopes and auth middleware were extended to enforce it.
  • AgentOS filesystem. agno.fs adds DbFileSystem, with /filesystem routes backed by an agno_fs table.
  • Breaking: the filesystem table is keyed by (namespace, user_id, path). A table created by an earlier release is refused with SchemaOutdatedError until the user runs a migration script for Postgres or SQLite. The release notes say the re-key never runs automatically.
  • Breaking: MCP default and lifecycle tools are now opt-in. MCPConfig(tools=[...]) publishes exactly the listed tools. Before this release it also published the built-in defaults and the lifecycle tools continue_run and cancel_run.
  • Fixes:
  • A paused HITL run continued with background + stream no longer duplicates itself in its own history.
  • A failed async DB delete is no longer reported as "run not found".
  • Python tool results now distinguish a None value from a missing variable.

Why it matters for BQAA.

  • Authorization rows. The audit log is the new source of authorization events. If BQAA ingests them, the useful join is audit row → tool call, keyed on user, agent, session and scope. That is the join the approval-laundering paper at 0034 needed and could not get from tool-call logs alone. I did not inspect the audit-log schema (see Unconfirmed).
  • MCP tool inventory. After the upgrade, an AgentOS MCP server that used to expose continue_run/cancel_run stops exposing them unless they are listed. Tool-inventory dashboards will show those tools disappearing at the version boundary. That is a configuration change, not a usage drop.
  • HITL duplicate runs. Before 3.1.0, a run continued with background + stream could appear twice in its own history. Run counts from those versions may be inflated.

Parent context: agno-3-0-agentos-published-versions-per-user-metrics-runs-table (Agno 3.0). I card this as NEW rather than Progress because the authorization layer and audit log are a new product surface, not a follow-up fix.

A1 (NEW). BACKDROP: the world around an agent costs it 38 points, and overclaim doubles (arXiv 2609.38469)

Full PDF read (30 pp.). Lia & Roy Dipta, submitted 2026-09-29, under review at ICLR 2027. Code: github.com/NusRAT-LiA/BackDrop.

What it does. The paper turns each of 618 AppWorld tasks into a family of worlds that share one instruction and one correct end state. The families have:

  • a twin with no hazard;
  • one ablation per hazard;
  • a compound with all four hazards.

The four hazards are:

  • authority: another person's message contradicts the user;
  • injection: planted text in a record the agent reads;
  • boundary: a request to write in an app the agent was not given;
  • fault: the agent's own write returns a 500 that does not say whether it committed.

That gives 3,678 variants and 202,290 runs across 16 models (§5). AppWorld's own evaluator decides pass or fail. Separately, a programmatic grader (no model judge) reads the end-state databases, the API call log and the agent's final message, and flags seven failure modes (Table 8).

Key numbers

  • Mean pass rate is 69.5% on twins and 31.3% on compounds, a 38.2-point gap [95% CI 36.4–40.1] (Table 3, Table 15). The paper's "Claude Fable 5.1" falls from 96.6% to 56.0%.
  • Hazard cost, meaning the share of twin passes removed (Table 15):
Hazard Cost
authority 42.2%
fault 21.8%
boundary 19.3%
injection 9.7%

Authority costs more than injection for 16 of 16 models.

  • Among runs where the cue actually reached the agent (Table 4), agents followed another person's message 46.4% of the time and injected text 20.3%.
  • Overclaim (reports success on an unfinished task) fires in 29.4% of twin runs and 62.4% of compound runs. Collateral, meaning an irreversible effect outside the task's scope, rises from 9.0% to 23.9% (Table 5).
  • Fault-mishandled (re-sending a write without first checking whether it landed) fires in 47.9% of fault-ablation runs (Table 5). Per model on compounds, it ranges from 10.7% to 76.0% (Table 16).
  • For 12 of 13 models, the best of four attempts on the compound is still below one attempt on the twin (sign test p = 0.0034).

Limitations (§7, App. O)

  • One benchmark, AppWorld.
  • The authors built the hazards themselves, and placement matters: injection costs 3.6% in an email body against 24.3% in a text message (Table 14).
  • Fault-mishandled and interaction rates are upper bounds.
  • Three models ran only once.
  • Detector validation used 21 scripted control runs (precision/recall 1.00). That bounds error on behavior the authors wrote; it does not estimate an error rate on real runs (App. K). Two log-reader bugs surfaced only on real traces.

Why it matters for BQAA. Most of BACKDROP's failure modes can be computed from data BQAA already stores:

  • Fault-mishandled is a call-log pattern: a write returns an error and is re-sent without an intervening read of the same resource. It can be expressed as a SQL detector over tool-call rows.
  • Boundary-write needs a per-session "granted tools" set joined against the write calls.
  • Overclaim needs the agent's final message joined to the end state or tool results.

This also bears on Mastra's new default retry (P1), which retries transient errors automatically. The paper's App. C shows that read-back-then-decide is the only policy that is correct whether or not the write landed.

A2 (NEW). Can terminal agents trust their own verification? A "no error" check is right only 51.5% of the time (arXiv 2609.38812)

Full PDF read (22 pp.). Luo et al. (Northeastern / Ant Group Inclusion AI / UMD), submitted 2026-09-30. 0034 scouted this at abstract level and flagged it as a next-slot candidate.

What it does.

  • LLM judges mark the first complete candidate solution in each trajectory and classify the agent's subsequent self-check as error, no-error or unresolved.
  • The trajectory is replayed in a fresh environment up to that point, and the official evaluator grades the candidate state. This gives ground truth for whether the candidate was actually correct.
  • The study covers 10 agents × 89 TerminalBench2.1 tasks × 3 runs, using the Terminus-2 scaffold (§2, App. B).

Key numbers (macro average, Table 5 / Fig. 2):

Metric Meaning Value
Verification trigger rate Agent attempts verification after forming a candidate 99.53%
Error-signal precision An "error" signal is right 92.65%
Error detection rate Incorrect candidates that get caught 61.43% (48.92–71.52%)
Verification pass reliability Candidate is correct when the agent's check says "no error" 51.52%
Repair success rate Detected errors that get fixed 49.36% (23.65–75.68%)
  • Repair success correlates with final accuracy at Pearson r = 0.98 (Fig. 2c).
  • Accuracy rises 25.4 points on average from the first candidate to the final answer.
  • The proposed method, SCVD (the teacher demonstrates verification from the student's own candidate state), lifts Qwen3.5 Pass@1 by 9.74–16.85 points. Unlike full-trajectory distillation, it does not lose performance on SWE-bench Verified (Table 2).

Limitations

  • The annotation uses LLM judges. Three-way exact agreement is 74.29% on the candidate boundary and 85.16% on verification semantics. Calibration used only 20 human-checked trajectories, with judge joint accuracy of 76.7–86.7% (App. B.1).
  • 2% of replays failed (Table 4).
  • The ~99.5% verification rate depends on the Terminus-2 scaffold (App. B.3).

Why it matters for BQAA. This quantifies the vault's "code decides done" rule: an agent's own passing check is roughly a coin flip on correctness. The paper's recipe has a concrete telemetry shape:

  • a candidate-boundary marker (step id plus tool-call index within the step);
  • the self-verification outcome;
  • a replay grade.

Without a replay or external grade, a BQAA "agent said it verified" flag should not be shown as a quality signal.

A3 (NEW). Risk-aware adaptive evaluation: replaying recorded trials finds 3.5× more high-impact failures at 6% of the budget (arXiv 2609.38914)

Full PDF read (22 pp. including the NeurIPS checklist). Maji & Ghose Chowdhury (Georgia Tech), submitted 2026-09-30. Code and the 824-trial corpus: github.com/priyanathmaji/risk-aware-eval.

What it does.

  • The paper treats agent evaluation as a budgeted bandit: which scenarios to run, and how many times to rerun each.
  • Each scenario gets a fixed, rule-based impact score before it is run: 5 = irreversible, 4 = mutation plus payment or confirmation, 3 = mutation, 1 = read-only (Eq. 2).
  • Each scenario also has a 17-feature context vector. A contextual Thompson Sampling policy uses both to pick the next trial (Eq. 3–4).
  • All policies are evaluated by offline replay over 824 recorded τ-bench airline trials across 70 scenarios. There are 30 shared-seed replicates and paired Holm-corrected tests (§3.4–3.5).

Key numbers

  • At a budget of 50 trials (6% of the corpus) (Table 1):
Policy Share of oracle impact-weighted discovery Impact-weighted failures found
Contextual Thompson Sampling 86.1% 215.4
Uniform allocation 24.9% 62.2
  • Discovery per dollar is 5.0× higher (3207 vs. 636 Y/$, Table 3), and total spend is lower.
  • The share of budget spent on scenarios that never fail falls from 34.2% to 2.8% (Table 5, App. B).
  • Scenario context helps only in the cold start (B ≤ 100, p_Holm < 0.005). Posterior-based exploration helps at B = 300–500 (Table 2). By B = 700, every adaptive policy reaches about 99.7–99.9% of the oracle.

Limitations (§5, App. E–F)

  • One domain and one agent/user model (GPT-4o).
  • 20 of the 70 scenarios are custom additions to τ-bench's 50 (App. F).
  • Cost covers only the simulated user's spend, not the agent's (Table 3 caption).
  • The impact score is a fixed rule.
  • Scenarios are treated as independent arms.
  • The objective is discovery, not reliability estimation. A scenario sampled rarely is "unexamined", not "safe" (§6).

Why it matters for BQAA. Replay over recorded trials needs only a per-trial table with scenario id, failure flag, resource use and cost, which BQAA's evaluation tables could hold. A static impact tier (read-only / mutation / payment / irreversible) derived from tool metadata is enough to beat uniform reruns by about 3× at small budgets. The caveat for any regression dashboard built on this: an adaptive schedule cannot be used as an unbiased estimate of the pass rate.
