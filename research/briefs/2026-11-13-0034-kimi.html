Read this first

Four items clear the bar. The tau2-bench evaluator study is the most direct BQAA result: a repeatable LLM verdict is not a valid substitute for an outcome oracle, and a deterministic check of expected versus observed writes catches forbidden commits that every gpt-4.1-tier judge configuration largely passes. The history/world study is the ADK counterpart: rewriting an error into a completed action without repairing the world reduces recovery, while exactly the same success receipt helps or hurts depending on whether its effect exists. Evaluate compaction and handoff against restored world state, not just readable transcripts. SynthCorp then supplies an enterprise data-agent benchmark pattern: event-driven relational/document/catalog estates, hidden causal logs, and executable gold programs; its results also show that structured search tools deliver agentic accuracy at much lower token cost than raw file/CLI access, and that output-format mismatches must be separated from reasoning failures. Industry has one material stable runtime release: Mastra 1.83.0 adds reconnectable run streams, replay, observation and ownership-checked abort across readers and servers. It is useful run-control machinery, not crash recovery for a plain agent process.

1. Mastra 1.83.0 — resumable streams and run observation become core runtime behavior

Stable on npm at 2026-11-12T21:27:47Z, inside the window. The exact same-version GitHub Release lookup returned 404 at verification time, so this is npm ahead of GitHub; capabilities were verified against the repository packages/core/CHANGELOG.md, not inferred from the version number. No existing 1.83.0 catalog item was found.

The material change is that resumable streams now apply to every Agent, not only durable agents. An agent registered on Mastra publishes each run to its stream topic and keeps a replay cache. A client can reconnect through agent.observe(runId), follow the run through tool-approval suspensions, and abort through the observation API or run routes. Shared PubSub/cache deployments can observe and abort runs started on another server. Ownership records make unknown or expired runs return 404, reject duplicate run-id claims with 409, and confirm abort with the executing process. The behavior change operators must understand: closing an HTTP stream no longer stops a plain server-side run; it continues until completion or explicit abort. A plain-agent process crash still stops the run — reconnect is not crash recovery.

The same stable train adds configurable built-in MCP serving and OAuth discovery/audience checks, observability/observability_analytics toolsets, model/provider/duration span ordering, feedback replacement and optional review-status methods. Those are supporting runtime and observability improvements, not separate items; 1.84.0-alpha.0 and branch snapshots are NOTE-only. For ADK/BQAA, the useful pattern is an explicit run-ownership and reconnect contract: readers can detach without cancelling work, while resume, duplicate-claim and abort semantics stay deterministic.

1. When Evaluators of AI Agents Disagree: An Empirical Study of Native Scoring, LLM Judges, and Commit-Boundary Checks on tau2-bench — full PDF read

Full PDF read: yes — complete 38-page v1 PDF, including §§1–9, Tables 1–7, Figures 1–3, Declarations, Appendices A–B (Tables A1–A3, B1), and references. cs.SE; submitted 10 Nov 2026. Not in catalog (grep: 0 hits).

What it does: 90 airline/retail tasks × two agent models × four cumulative gate conditions × three repetitions produce 2,160 episodes. Every episode is scored by native gold-state scoring, an LLM judge, the judge with the policy, and a deterministic boundary evaluator that compares whether a write was expected with whether one committed. Two annotators independently label 120 episodes for task correctness (A1), policy compliance (A2) and commitment correctness (A3), with adjudication and sampling weights (§§4.4–4.6).

Key findings:

  • Reliability is not validity (Table 4, §5.1). The main judge repeats itself on 98.2% of episodes but agrees with native scoring on only 56.2%. Native scoring fails 1,007 episodes; the judge passes 929 of them (92.3%). The disagreement is systematic, not sampling jitter.
  • Forbidden commits expose the oracle gap (Tables 5–6, §§5.2–5.3). Humans confirm 11 premature commitments. The main judge and policy-aware judge pass all 11; with untruncated input the main judge passes 10 and the policy judge still passes 11. The stronger no-policy judge passes 6. The deterministic boundary check catches all 11, and no tested judge significantly exceeds it on A1/A3. Giving the strongest judge the policy catches all 11 but also fails 40 of 55 fully correct episodes — sensitivity is not discrimination.
  • The boundary check is necessary but incomplete (§5.2). It catches 24 of 53 human A3 failures, versus 40 for native scoring. It cannot see a write that was expected and occurred but had wrong content or timing, and it still needs one item of gold information: whether this request type should write. On policy compliance, no automatic evaluator beats the always-“compliant” baseline (0.688); human agreement is weakest there too.
  • Gates need their own evaluation (Tables 7, Figure 3, §6). Without gates, 60/540 episodes (11.1%) commit prematurely: 58/300 airline (19.3%) versus 2/240 retail (0.8%). Verification, correction and safe-termination gates show no significant reduction after Holm correction. Trace analysis finds the implemented verifier's digest dropping order status or customer authentication through an 800-character cut or a shrunken message window, causing valid requests to be rejected. This is evidence for measuring gate evidence quality, not proof that gates as a class cannot work.

Why BQAA/ADK care: store a commit event for every state-changing tool call and annotate request types with expected_write; compute correct_action, missed_action, premature_commitment, and correct_refusal beside any LLM score. Keep task success, policy compliance and commitment correctness as separate constructs. Do not use a judge alone as a release gate, and include the gate's own evidence digest in trace review.

Limits (§8 and appendices): two customer-service domains, two agent models from one family and judges from one vendor; the boundary evaluator cannot judge write content and needs its partial oracle; one annotator is the author and the other a colleague; gate results include the identified implementation defect. Frequencies should not be exported directly to other workloads.

2. Cleaning an Agent's History Hurts When the World Still Holds the Error — full PDF read

Full PDF read: yes — complete 23-page v1 PDF, including §§1–7, Tables 1 and B–F results, Figures 1–4/S1–S2, limitations, references, and Appendices A–K. Salesforce AI Research; cs.AI; submitted 10 Nov 2026. Not in catalog (grep: 0 hits).

What it does: two controlled continuation experiments separate the agent's record from the executable world. On AgentCE-Bench, 319 frozen states where a wrong value is already committed are restored under four record arms, with two receivers and 2,552 continuations. On AppWorld, receipt success/failure is crossed independently with the database effect being absent/present: 65 task families, 1,040 primary continuations, then an eight-receiver expansion. Restoration and endpoint replay checks are described in §4 and Appendices C–H.

Key findings:

  • The same correct value has opposite effects by record form (§5.1, Figure 2, Appendix B). With the world still wrong, a truthful note beside the preserved error raises recovery from 50.57% under a matched neutral note to 65.78% (+15.20 pp [12.46, 18.00]). Rewriting the agent's own call into a completed correct action lowers recovery from 50.13% under the unedited record to 43.70% (−6.43 pp [−8.88, −3.97]). The prespecified difference of contrasts is +21.63 pp [18.21, 25.08], positive in both receivers. Merely exposing the answer cannot explain the reversal.
  • The same success receipt flips sign with world state (§5.4, Figure 3, Appendix C). When the write's effect is absent, whole-task success is 28.46% with a success receipt versus 45.38% with a failure receipt (−16.92 pp). When the effect is present, it is 48.85% versus 38.46% (+10.38 pp). Their interaction is +27.31 pp [14.23, 41.54] at 97.5%, positive in six of eight receivers at 97.5% and seven at 95% (§5.5, Appendix D).
  • Process evidence supports the world-account reading (§5.4, Appendix C.3). Under a success receipt, re-issuing the focal request falls from 52.69% when the effect is absent to 10.38% when present. A false failure receipt also produces duplicate inserted rows in some receivers. The compatible explanation is that the record acts as a map of remaining work, although truth, channel and implied work are not fully separated.

Why BQAA/ADK care: a trace is not the world. Compaction, repair and handoff should preserve unresolved errors and their external effects rather than manufacture a clean-looking success narrative. Evaluate those policies from frozen (record, world) checkpoints and score the final world; BQAA should retain enough causal provenance to distinguish “receipt says success,” “effect exists,” and “remaining work.”

Limits (§6 and Appendix H): the truthful note and falsified action differ in role, position, visibility and implied remaining work as well as truth; AppWorld receipts differ in content; step budgets bind unevenly; only two receivers carry the AgentCE primary; closed-model versions and author-selected edits limit prevalence claims. The sealed AppWorld analysis and preregistered targeted-control estimator never ran; independent reimplementations and replay checks are disclosed instead, and the targeted control is incomplete. These are controlled interventions, not an evaluation of a production compaction policy.

3. SynthCorp: A Platform for Creating Benchmarks for Data Agents — full PDF read

Full PDF read: yes — complete 32-page v1 PDF, including §§1–7, Tables 1–8, Figures 1–2, limitations/future work, references, and Appendices A–D (Tables 9–12). Google authors; cs.AI/cs.DB; submitted 10 Nov 2026. Not in catalog (grep: 0 hits).

What it does: a scenario and requested complexities become routine/disruption event types, compiled into programs over 12 simulation primitives and scheduled on a virtual calendar. Execution materializes relational databases, documents and an incomplete catalog while recording a hidden causal simulation log. The generator uses that log to make answerable tasks, derive executable gold programs, audit table lineage/business rules, and compose multi-event tasks. Seven estates yield 256 tasks across retail, music, banking, logistics and insurance, with Retail-1000 reaching 1K operational tables (Table 4).

Key findings:

  • Provenance makes hard answers auditable (§§3.5, 4.4, 5.5). Atomic gold fragments are checked against logged writes, authoritative-table lineage, generation rules and independence from frozen copies; composite tasks are ablated to ensure every complexity matters. In one Retail-1000 case, the log disproves the plausible current-tier gold answer: the point-in-time historical join gives 826 Bronze members versus 880 in the current table, and all 12 Opus and all 12 DeepSeek runs choose the latter. On 11 multi-rule Retail-1000 composites, S3 accuracy is 91%/76%/33% for Opus/DeepSeek/Gemma.
  • The generated contexts separate models and interfaces (Table 7). Overall execution accuracy for Gemma is 33.3% schema-only, 42.3% with one document, 54.6% with structured agent search and 47.1% with files/CLI; DeepSeek is 41.9/56.2/76.6/77.7; Opus is 54.6/71.2/86.6/88.8. One retrieved document is the cheapest gain; structured search and raw-file access reach similar accuracy for the stronger models.
  • Raw files cost much more per correct answer (§5.5, cost analysis). S3 uses 102K input tokens per correct answer for Opus and 360K for DeepSeek; S4 rises to 226K and 934K — 2.2× and 2.6× the S3 cost. Paged, purpose-built search tools are therefore not merely an accuracy choice.
  • Grading must separate format from reasoning (§5.5). Format differences account for 56% of Opus and 61% of DeepSeek failed S4 runs; format-tolerant review lifts accuracy to 94% and 90%. Treating those as reasoning failures would overstate the benchmark's difficulty, while treating every format mismatch as success would erase the output contract; report both explicitly.
  • Correctness claims need the error breakdown (Tables 5, 10). The six smaller estates pass all nine deterministic checks, and Retail-1000 passes static program/calendar checks but has 33/15.7K runtime database failures (0.2%). Semantic compilation errors remain: cross-column/row dependency violations affect 12.7% of specified dependencies overall, and operator-contract violations 3.6% on the smaller estates and 7.1% on Retail-1000. “Near-zero” applies to specific deterministic/runtime checks, not every semantic property.

Why BQAA cares: this is a concrete way to build fresh enterprise analytics evals without manual gold annotation: simulate business events, keep the causal log hidden from the agent, and require executable, provenance-audited answers. It also supplies two immediate evaluation rules — compare structured retrieval against CLI on cost per correct answer, and split output-shape mismatches from retrieval/reasoning failures.

Limits (§6–7 and appendices): complexity is primarily metadata-level; row distributions are not ground truth for operational business decisions and differ from real references on several stylized facts. Three development and four held-out scenarios is still a small domain set; many generated tasks are easy for frontier models; and log-verified synthetic correctness is not production correctness.

Six-week EV

  • Commit-boundary evaluator (high EV, days). Add expected-write annotations for common BQAA request types and compute the four boundary labels from stored traces. Seed forbidden/missed writes in evals and route label changes to human review; do not replace native outcome scoring or validated judges, and do not claim content correctness from the boundary bit.
  • World-aware compaction/handoff replay (high EV, 2–3 weeks). Build several frozen (trace, actual state) checkpoints, then compare unedited history, truthful annotation and cleaned-history arms on final-world success. Ship no compaction policy that underperforms the unedited control; preserve unresolved error/effect provenance in ADK handoffs.
  • Event-sourced data-agent eval (high EV, 4–6 weeks for a narrow prototype). Generate one small analytics estate with schema drift, stale snapshots and policy documents, then derive executable answers from its hidden event log. Compare structured search with file/CLI on cost per correct answer and report format-only failures separately. Kill it if gold answers cannot be independently audited against the log.
  • Run reconnect/ownership contract (medium EV, one-week design spike). Prototype detach/reconnect, duplicate-run rejection and explicit abort semantics against ADK's existing run model. Treat plain-process crash recovery as a separate durability problem; Mastra is evidence of a useful contract, not a drop-in BQAA dependency.
