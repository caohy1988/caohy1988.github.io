Industry

BigQuery Aug 31 entry, the part Monday missed: Graph GA + TabFM (Aug 31)

Monday's 12:34 brief covered identity columns and Git pipelines from the Aug 31 release-notes entry; today's fetch of the same entry shows two more items our passes didn't record. First, BigQuery Graph is GA, with a CALL statement and three path-inspection functions (IS_ACYCLIC, IS_SIMPLE, IS_TRAIL). Agent traces are graphs — invocation trees, agent-to-agent edges, tool-call fan-out — and until now querying them meant recursive SQL over trace_id/span parentage. GQL over an edge view derived from agent_events is now a supported, GA pattern on the same platform that holds the table. Second, TabFM, Google's tabular foundation model, is exposed through AI.PREDICT and AI.EVALUATE (Preview): zero-shot regression and classification over tables by in-context learning, no training run. That is a plausible zero-setup session-labeling primitive — but it's Preview, and nothing on the page says anything about token cost or row limits, so treat it as untested. The wrong belief to kill: "Graph GA means we should rebuild analytics views as graphs." It's an option for path questions (which agent's edge does a failure cross?), not a replacement for the SQL views customers already have. Judgment: calendar, home-platform — but Graph GA is the most BQAA-adjacent platform GA since the launch.

TL;DR for BQAA. Two cheap experiments, one owner each: (1) a graph view over agent_events edges (span parent → child, agent → sub-agent) and one GQL example query in the docs — this directly serves the future fault_edge story; (2) point AI.PREDICT at a session-summary view and see if zero-shot session classification is usable. Neither is roadmap; both are doc-example material if they work.

Langfuse v4.27.0 (Sep 1)

Third release in roughly 48 hours (4.25.0 and 4.26.0 both landed Aug 31). The substance: evaluators now accept multimodal inputs, the trace table now shows cached input tokens and cost as first-class columns, a normalized input/output parser went in behind a feature flag, and there's a new evaluator-testing tool for their MCP integration. The cadence is the signal — Langfuse is iterating on the evaluator + trace-table surface daily while their Cloud v4-only cutover (Nov 16) approaches. The one contract that matters: cached-token accounting is becoming a standard column in trace UIs, because prompt caching now dominates real cost math for long-running agents. The wrong belief to kill: "token_count is enough." A cost column computed without cache-hit breakdown overstates spend on exactly the workloads BQAA targets. Judgment: peer, moving fast on the consume layer.

TL;DR for BQAA. Check what the ADK plugin actually emits for cached vs uncached input tokens in agent_events, and make sure the example cost views don't conflate them. If cached counts are already in the payload, one documented view; if they're not, that's a capture-layer gap worth a line in the producer contract.

Phoenix client 7.7.0 — trace lifecycle as API surface (Sep 1)

Arize shipped phoenix-client@7.7.0 with setProjectRetentionPolicy (per-project trace retention) and transferTraces (move traces between projects). The wrong belief to kill: "BQAA needs SDK parity here." AgentLogs: GitHub's Copilot cloud-agent logs, released (2608.29204, submitted Aug 29)

Richards et al. release a dataset of 307,416 agent tasks, 549,239 sessions, and 64,255,174 session log entries from GitHub's Copilot cloud agent operating across 35,810 popular public repositories — prompts, intermediate reasoning, tool calls (file edits, git operations, GitHub interactions), and token usage. The pitch is "opening the black box": studying agent behavior, efficiency and cost, failure modes, and human-agent collaboration from the logs rather than from the resulting PRs. This is, structurally, a public dump of an agent_events-shaped table at production scale — the first one. The wrong belief to kill: that real-agent-log research is blocked on data access; as of this week it isn't, and every attribution/detection paper for the next year will benchmark on this. Judgment: neither threat nor peer — raw material, and the highest-leverage item in this brief.

TL;DR for BQAA. Load AgentLogs into BigQuery mapped onto the agent_events schema and make it the public demo dataset: every EvalBench rubric, drop-stat query, and future session flag can be demonstrated on 549k real sessions instead of toy traces. Also the honest test of whether our schema survives contact with someone else's agent. One engineer-week, high EV — this is the strongest new candidate for the six-week list since it was written.

Detect Before You Attribute — DUOTRACE (2608.29646, submitted Aug 30)

Zhang et al. argue that failure attribution improves if you first run anomaly detection over the trajectory and only then hand the focused evidence to the attributor. Mechanism: VAE-based anomaly detection over dual semantic-structural node representations, Tree-LSTM trajectory encoding, and data augmentation to cope with scarce failure labels. Gains: +8.7% agent-level and +7.0% step-level attribution accuracy over attribute-directly baselines, which they show degrade on long trajectories. This is direct outside evidence for the ordering our loop name already encodes: cheap deterministic detection first, expensive attribution only on flagged sessions. The wrong belief to kill: that attribution models should eat whole raw traces; narrowing the evidence window is itself most of the win. Judgment: supports the thesis; the specific model stack is not something to copy.

TL;DR for BQAA. Evidence for six-week rows 1 and 2: deterministic session flags are not just a triage convenience, they measurably improve whatever attribution runs downstream. Cite it when writing the Detect→Rerun doc; build nothing from the paper.

Minimal Repair Families via counterfactual replay — GCJR (2608.29228, submitted Aug 29)

Li et al. reframe attribution: instead of "which step failed," recover all inclusion-minimal sets of events whose counterfactual repair restores task success. Their Graph-Constrained Joint Replay walks the execution dependency graph, proposes graph-feasible singleton and pair candidates, and validates them by replay against clean counterparts — 1.000 family exact match on 90 controlled cases while cutting replay calls 55% (56.3 → 25.3). The important claim for us: pointwise attribution structurally misses jointly-necessary repairs — some failures have no single culprit step, only culprit sets. The wrong belief to kill: that a single fault_step column can be made accurate; sometimes the ground truth is a set of edges. Caveat: the method needs replay capability and clean paired runs — BQAA has the dependency data but is an observer, not a replayer. Judgment: calendar; strengthens the schema argument for fault_edge over fault_step.

TL;DR for BQAA. When fault_edge/fault_side lands (six-week row 7), make the field repeated, not scalar — the academy is converging on failure-as-set. Replay itself stays out of scope (observer stance).

APIFlow-Bench: agents die at delivery, not at the task (2608.29128, submitted Aug 29)

Wan et al. release 44,362 execution transcripts of REST-API workflows with dependency chains up to 20 subtasks, graded deterministically with provenance, across 19 models. Three numbers worth keeping: success falls 93% → 61% from single tasks to 20-subtask chains; the spread between models is 44 points on reliability but only 7 points on capability; and 77% of failing chains reach the correct final state and fail only at delivery (expired credentials, malformed payloads, missed handoff). That last number is the one to quote — most long-workflow "failures" are last-mile telemetry-visible mechanical faults, not reasoning faults, and end-to-end pass/fail hides them. The wrong belief to kill: that session success is one boolean. Judgment: peer benchmark, and the best external justification yet for deterministic session flags.

TL;DR for BQAA. The session-flag design (row 1) should distinguish final_state_correct from delivered — two deterministic booleans computable from events, no judge. If 77% of production failures look like this, that single split is most of the triage value.

ATLAS: production diagnostics at two horizons (2608.30685, submitted Aug 31)

Chen et al. (Meituan) describe the evaluation stack running on Xiaotuan production traffic. Two horizons: request horizon — trajectory-level signals that tie each deficiency to the execution location where it occurred — and interaction horizon — user-level signals measuring whether service stays consistent across continued exchanges. LLM judges are calibrated against real business logs, then distilled into cheap diagnostic models for scale; validated by offline experiments and online A/B with engagement and business-outcome gains. No headline accuracy number, but the architecture is the message: a production evaluator locates deficiencies within trajectories and across sessions, not just at the end. The wrong belief to kill: that per-request rubric scores are the finished product. Judgment: peer (industrial), corroborates the trajectory-location thesis from the attribution literature.

TL;DR for BQAA. EvalBench's 8 rubrics are request-horizon. The interaction-horizon counterpart — per-user consistency across sessions — is a SQL view over agent_events, not a new judge. Worth a named example view; not a six-week row yet.

Without self-check tools ~1 in 7 builds fails to launch; a single boot probe eliminates nearly all launch failures at ~35% of a full shell's token cost (full shell: 2.35× cost). Claim: "a verification tool improves the artifact only where its reach covers the way the application actually fails" — the cost/coverage framing rhymes with TelemetrySuffBench's sufficiency argument, applied to verification instead of telemetry. Calendar.

Relevant only as a reminder that token-usage fields undercount what mattered. Distractor for us.
