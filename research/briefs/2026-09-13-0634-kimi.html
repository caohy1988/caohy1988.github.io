MCP Registry random draw — NEW rank: the production tool failure distribution is not in the benchmarks

What a Random Draw from the MCP Registry Contains, and What Tool-Use Benchmarks Contain Instead, Haseeb Mohammed Afsar. Full text read including threats-to-validity. (PDF)

The first probability-sample measurement of the MCP ecosystem: a seeded, hash-pinned draw of 400 npm/stdio servers from a 24,135-server registry census, each probed once over the wire with an outcome recorded for every draw. Only 48.8% complete an initialize handshake (vs 66.7% on a hand-curated frame), and the dominant failure is not credentials (13.3%) but servers that never start at all (37.5%). Among the 195 that run, hard schema conformance is total — zero fatal JSON Schema violations across 2,766 advertised tools — but optional safety annotations are omitted at 58.8%, 17.3 points worse than curation suggests. The second half holds one TF-IDF cosine method constant across real and benchmark tools: real MCP shows 2.8% near-duplication, all within single servers (0.0% cross-author), while BFCL v4 shows 16.7% near-duplication — mostly between independently presented tasks — and 68.8% of raw BFCL rows are exact name+description repeats (UltraTool: 85.6%). All figures regenerate from released scripts, a committed seed, and a hash-pinned frame (GitHub + Zenodo DOI 10.5281/zenodo.21347997).

Mandatory qualifications: npm/stdio is a shrinking 30.7% of the registry; remote/PyPI/OCI servers are out of frame. 48.8% is a lower bound — single probe, no retry, no credentials. The curated contrast rests on n=24 servers. UltraTool is cleaner than real tools on near-dup (0.3%), so "synthetic = duplicated" is specific to BFCL's raw release, not a class claim (the author says so). The cross-task duplication comparison is not power-matched (BFCL averages 1.8 tools/row vs 14.2/server), and 7 of 20 BFCL files expose no function list and are excluded. Similarity is lexical, not semantic. Single-author preprint; the author discloses one unreleased earlier run that disagrees with the current sample.

BQAA/ADK application — editorial proposal: any ADK/BQAA tool-reliability number computed over a curated tool set should be re-run over a seeded probability draw from the real registry, and reported with the startup-failure rate as a first-class metric. An agent eval that never sees a server fail to start is measuring a world that does not exist.

BenchShield — NEW rank: reward integrity as an infrastructure property, with a self-adjudication caveat

BenchShield: Formal Model-Backed Instrumentation for Reward Integrity in LLM-Agent Evaluation Infrastructure, Shenghan Zheng, Zonglin Di, …, Dawn Song, Christophe Hauser (Dartmouth / UC Berkeley / UC Davis / Ohio State / Amazon / BenchFlow et al., 22 authors). Full text read. (PDF)

Treats reward hacking in executable agent benchmarks as an integrity property of the whole source-to-score lifecycle: a finite TLA+ lifecycle model with seven integrity dimensions (six TLC-checked), a static phase-aware taint analysis over a task-activated capability graph that finds exposed reward paths before any run, and a runtime lane that attributes infrastructure-side events and issues evidence-backed verdicts (Checked / VectorExposed / AgentViolation / Inconclusive). From 31,000+ public runs across Terminal-Bench 3, SkillsBench, and ClawsBench the authors build a 456-trajectory human-adjudicated corpus (3 annotators per record) and find 69% of adjudicated trajectories contain at least one exploit episode, typically emerging mid-run after legitimate work. Against BenchJack on identical stripped packages, static analysis raises full-chain recall from 23–94% to 77–100%; runtime attribution from infrastructure evidence reaches 96% accuracy among covered cells vs 36% for a transcript-only LLM detector. A counterfactual shows a separate verifier environment removes 82–95% of packages exposed on the structural dimensions — but nothing touches fail-open handling or semantic adequacy.

Mandatory qualifications — read before quoting: ground truth is self-adjudicated by the authors' own team with no held-out external label set; the taxonomy was derived from the same failure literature that populates the corpus. The 69% figure is not a population rate — the corpus deliberately includes elicited exploits. ClawsBench contributes only 12 tasks from one environment family (recall there is "trivially high" by the authors' own admission); the runtime study covers 60 tasks / 144 runnable cells, with 36 of 180 planned cells unlaunchable. All evaluation calls use a single model (Claude Opus 5). Conflict of interest: two authors are affiliated with BenchFlow, the infrastructure BenchShield is instantiated on, and two of three run sources are BenchFlow-run benchmarks (disclosed). Tables 2–4 render as images in the HTML; headline numbers are corroborated in prose but the exact "up to 65%" per-task cost reduction and the annotator-agreement statistic could not be re-derived from extracted text — verify against the PDF before printing either.

BQAA/ADK application — editorial proposal: the durable lesson is that prompt-level guardrails cannot see reward hacking; the detection surface that works is infrastructure-side evidence (filesystem, process, network events) attributed through a lifecycle model. For BQAA evaluation jobs, define the reward-relevant event lifecycle first, then decide which events the agent's sandbox may legitimately touch — and publish any detector's accuracy against independently labeled trajectories, which BenchShield itself does not do.

VP-CONTROL — NEW rank: evidence diversity beats model diversity, and only atomic guards survive races

Engineering Reliable Commit Gates for Agentic AI: Cost-Aware Verification Portfolios under Common-Mode Data Failures, Zihao Zheng, Baichuan Li, Junyi Yao, Jiayu Long (WashU St. Louis / Southern Methodist). Full text read. (PDF)

A commit-gate study for agents that propose state-changing writes. Across a deterministic 2,880-scenario benchmark (48 templates × 10 worlds × 6 fault regimes), a 2×2 factorial separates the two things "more verifiers" usually confounds: cross-model voting over shared evidence approves 62.9% of unsafe proposals, while sourcing independent evidence is the dominant lever — paired effects of −40.9pp (source) vs −11.3pp (model diversity). The 22.9% figure the pack quotes is specifically the cross-model plus independent-source cell; same-model + independent-source is 33.3% (baseline 74.2%). A preregistered live HTTP/SQLite arm (216 episodes) shows verifier-only gates all commit the same 12 unsafe effects under after-check races; only clauses re-checked inside the write transaction survive, with a full atomic guard at 0/216 unsafe (cluster-adjusted 95% upper bound 1.4%) and idempotent request IDs eliminating duplicate side effects on 96 retried requests. Unusually self-critical: preregistration, Holm-corrected comparisons, leakage audits, and a negative FinQA external check where the source effect reverses with weak verifiers.

Mandatory qualifications: fully synthetic templates — the authors support only the ordering of mechanisms, not absolute numbers. Tiny quantized local models (4–10B) on one laptop; actors never abstain. The FinQA external check fails to reproduce the main effect (17% unsafe from corrupted shared source vs 20% from correct independent source — a reversal). Calibration is an approximate design-effect-adjusted bound, explicitly "not a finite-sample safety certificate"; unseen fault families yield 16–26% risk at a nominal 5% target. The live arm is loopback, single-writer, with barrier-synchronized forced races; several preregistered live comparisons are not significant after Holm correction. The full atomic guard dominates everything when the predicate is expressible — the portfolio is a fallback for partial-guard settings, not the headline.

BQAA/ADK application — editorial proposal: three concrete rules for BQAA commit/mutation gates: (1) report verifier evidence-lineage independence, not verifier count; (2) idempotency keys on every agent-issued mutation request; (3) any check that can be expressed as a database predicate belongs inside the write transaction, not in a pre-check the world can race. When a guard can only be partial, a cost-aware portfolio over independently sourced evidence is the studied fallback.

ChurnBench — NEW rank: cache age is the wrong staleness variable

ChurnBench: A Drift-Aware Benchmark Demonstrating That Refresh Scheduling, Not Cache Age, Governs Staleness in Agentic AI, Vivek Kumar Singh, Preeti Priyam (independent researchers). Full text read from PDF (no HTML version exists). (PDF)

A drift-aware enterprise benchmark: a four-source data fabric (PostgreSQL warehouse, MongoDB operational store, mock REST SaaS with realistic latency/rate limits, synthetic contract documents) generated as a continuous timeline from an append-only change ledger (56,370 events), so gold answers are resolved at both retrieval time and answer time — cleanly separating freshness errors (correct when read, stale when answered) from reasoning errors. The headline is a negative result: under scheduled tiered refresh, cache age never reaches the retrieval layer, so freshness errors stay flat (7, 4, 4 across 1/14/28-day windows); disabling tiered refresh surges errors 4 → 45 at 28 days (identical 7 at 1 day). Attribution shows staleness exposure proportional to tier width × entity mutation rate — 14 of 15 residual errors came from one fast-mutating entity class on a 7-day tier.

Mandatory qualifications: single model, single framework (LangGraph), single domain (software asset management), fully synthetic data with practitioner-judgment mutation rates. No baseline architecture comparison under the final design — the paper claims an instrument, not a winning architecture. Tiny error counts under tiering (4–7 per 180-task run; the flat sweep rests on differences ≤3 — lean on the 4-vs-45 ablation instead). The 1/14/28-day sweep is not configuration-matched (reasoning mode changed mid-study). Four runs, including the headline ablation, hit interface instability requiring isolated re-runs. 109 of 180 tasks hit unregistered measures, so reported accuracy mostly reflects registry coverage gaps.

BQAA/ADK application — editorial proposal: for BigQuery-backed agent caches, stop reporting "cache age" as a freshness proxy. Track per-entity TTL alignment against measured mutation rate, and label agent answers with freshness-error potential (was the underlying row within its tier's refresh bound at answer time?). ChurnBench's ledger-resolved gold is the right pattern for any BQAA staleness evaluation: truth from the change log, never from the live store.

Tail-aware turn release — NEW rank: readiness is not permission to release

Decoupling Readiness from Release for Tail-Aware Scheduling of Agentic LLM Workflows, Bochao Feng, Jianjiang Li, Haojie Wang, Lin Qiao, Yinghui Li, Yukun Yan, Jidong Zhai (USTB / Qiyuan Laboratory / Tsinghua — pack's "Tsinghua University" attribution is only the corresponding author). Full text read. (PDF)

Identifies that agent runtimes implicitly equate "turn ready" with "turn submitted": under congestion, eager release irrevocably commits work and destroys the workflow scheduler's ability to reorder. The fix decouples the two — a priority index derived from a mean-CVaR objective over workflow flow time (holding-cost rate per unit of estimated turn work), paired with a congestion-adaptive budget on released-but-unfinished work. Evaluated on real GPU serving (vLLM, 1/2/4× A100-80GB; Qwen3-8B/32B, Llama-3.3-70B) with closed-loop replay of mini-swe-agent traces from SWE-bench and SWE-Gym: low-load parity (0.99–1.00×) and up to 3.50× P95 flow-time speedup under load (best case: 1,986s → 568s). Ablations attribute most of the gain to tail-aware ordering (59.5–63.5% P95 reduction) with the adaptive budget adding 10.7–11.6%.

Mandatory qualifications: the only external baseline is eager release — no head-to-head with any published scheduler (FastServe, Parrot, VTC are related work, not comparisons). One Poisson arrival seed, one paired run per reported point, no confidence intervals; speedup is not monotone in arrival rate. 100 workflows per trace means empirical P95 rests on ~5 workflows (authors' own words). SWE-agent workloads only; single-engine, non-preemptive; hyperparameters fixed but never sensitivity-tested.

BQAA/ADK application — editorial proposal: the readiness/release distinction generalizes beyond GPU queues: any BQAA orchestrator that fires downstream work the moment an upstream turn completes loses the ability to reorder under contention. A committed-work budget with a tail-aware priority index is a concrete, implementable policy — but validate it against a real scheduler baseline before claiming the 3.5× class of gain.
