NEW — 2610.07256 — Efficient Auditing of Adversarial AI Agent Behavior from Agent Traces — a deterministic gate (single-event and trace-sequence rules) picks which pending actions an LLM auditor sees; on OpenAgentSafety, audits per run fall 8.15 → 2.33 and tokens 47.8k → 14.6k, with TPR 72.8% vs 81.5% and FPR 5.9% vs 11.8% against auditing every action; 14 of the tuned gate's 59 detections exist only because the provider refused the audit

Authors: Zhang, Yang, Xu (Purdue). cs.CR, submitted Oct 5, 2026. Full PDF read (pdftotext, all sections including discussion and limitations).

Method (§4):

  • Logging: agents log on AgentTrace's three surfaces (operational: methods and outcomes; cognitive: reasoning and plans; contextual: data exchanged with external resources). Logs are append-only, in an environment agents cannot read.
  • Gate rules:
    • A single-event rule matches the pending action's type or argument regexes.
    • A sequence rule needs the pending action and earlier records to match, for example "sensitive data entering context followed by egress".
    • An optimizer LLM refines the rules and the audit prompt together, starting from a single seed rule. It maximises J = TPR − FPR − λ·C/C₀, where C is audit tokens per run and λ = 0.1.
  • Audit: the auditor (Claude Sonnet 5.5) sees the last K records across all three surfaces plus the rules that fired. It returns BENIGN, SUSPICIOUS or MALICIOUS with cited records. A run is flagged on one MALICIOUS verdict or three SUSPICIOUS ones.

Key numbers:

  • Table 1 (test split; 149 runs across 72 unseen tasks):
ConfigurationTPRFPRAudits/runTokens/run
Audit every action81.5%11.8%8.1547.8k
Gated, untuned37.0%13.2%6.6434.0k
Gated, tuned72.8%5.9%2.3314.6k
  • Table 2: the tuned gate cuts all three token categories; cache-read tokens fall 21.1k → 6.1k.
  • Table 3: on the training subset, tuning takes TPR 47.5% → 95.0%. On validation, FPR doubles, 12.1% → 24.2%.
  • Table 4 (two simulated multi-agent attacks, 10 attack + 10 benign runs each): both configurations catch 10/10 attacks with 0/10 false positives. Gated tokens are 82% lower in S1 and 86% lower in S2.
  • §6.1, the ten unsafe runs only full auditing caught:
    • in five, the gate skipped the decisive action (a dependency upgrade, a Python API call outside its keyword list, an unruled final report, two browser clicks that the benchmark logs as element numbers instead of link text);
    • in the other five, the action was audited but the verdicts were too mild.

Limitations that matter (§7, Table 5):

  • Refusals counted as detections. The provider refused 15 of 347 gated audits (4.3%) and 16 of 1,215 full audits (1.3%), and the paper counts a refusal as a detection. 14 of 59 tuned detections rest only on a refusal; ignoring refusals, TPR is ≥55.6%.
  • The suspicion-accumulation rule adds 8 detections and 1 false positive on test, but 2 detections and 5 false positives on validation.
  • Trace tampering is out of scope.
  • Scale: the simulations are small, and the audit model differs from the agent models.

BQAA relevance: this is a cost and coverage model for trace auditing that a warehouse can run.

  • The gate is plain SQL-shaped logic over event rows (event type, argument patterns, ordered sequences within a trace).
  • The expensive LLM pass then sees only gated rows.
  • Provider refusal is a first-class verdict. It should be logged as its own state, not folded into "detected" or "error".
  • Detections are only as good as the logged action detail. Clicks recorded as element numbers made the decisive actions invisible to the gate.

NEW — 2610.07675 — EIO-Agents: The Missing Semantic Layer for AI Agent Evaluation — evidence is typed and an executable witness rule decides whether it can show what the agent did (11 of 110 evidence×source pairs witness, 3 more only with the paired tool call); claims carry seven states (unknown is never a pass; evaluator faults are not charged to the agent); a content-addressed Portable Evaluation Record re-derives byte-identically; across three reference evaluations, 77 jury decisions are EVIDENCE_INVALID (70 cite a juror quote found in no source) and none of 47 jury findings is Proven

Author: Bousetouane (ProofAgent.ai; University of Chicago). cs.AI, submitted Oct 6, 2026. Full PDF read (body, Appendix A worked examples and the conflict-of-interest statement). Apache-2.0 code: https://github.com/ProofAgent-ai/eio-agents (repo created Oct 2; PyPI eio-agents 0.8.5).

What it specifies (§3–5):

  • Chain: Evidence → Predicate → Claim → Proof → Decision, built on four separations: Observation ≠ Evidence, Evidence ≠ Proof, Judgment ≠ Proof, Score ≠ Decision.
  • Witness rule (Eq. 1–2, Fig. 4):
    • A ref witnesses only if its evidence type can prove behaviour, its source may witness, the two are compatible and, for a TOOL_RESULT, the agent's tool call is also cited.
    • It must also be anchored exactly, by casefold, by receipt or by computation. Turn-level and document-level refs only locate.
    • User input, retrievals, policy spans and JUROR_INFERENCE (a juror's quote found in no source) never witness.
  • Claim states (§4.5): seven, namely APPLICABLE_PASS, APPLICABLE_FAIL, NOT_APPLICABLE, UNRESOLVED, EVIDENCE_INVALID, EVIDENCE_INCOMPLETE and EVALUATOR_ERROR. The last three mark the evaluation as failed, not the agent. Metrics use scored claims only, so N/A, unresolved and evaluator faults leave every denominator.
  • Proof (Eq. 4): a claim is Proven only if it was decided by code or a human, cites a witnessing anchored ref, and is exact or a proxy that reproduced in every re-test (CONFIRMED). Semantic (jury) claims are never Proven, so on their own they can reach REVIEW but never BLOCK (Eq. 6–7).
  • Record (PER):
    • 14 required blocks, sealed by a SHA-256 over RFC 8785 canonical JSON;
    • "why" text is rendered from 36 registered templates, never model prose;
    • a coverage block names why each unmet obligation stayed silent (UNREACHABLE, NOT_IMPLEMENTED, NEVER_SELECTED, …), so a predicate that produced no claim never renders as clean;
    • the verifier self-test injects 31 defects.

Key numbers (Appendix A, Table 5):

  • FIN_3 (credit underwriting, 40 turns): 243 claims (59 deterministic, 184 jury) give 12 findings, readiness 49 (capped from a raw 65.3) and BLOCK.
    • 49 claims are EVIDENCE_INVALID: 43 rest only on a juror quote found in no source of the turn, and 6 only on the user's own message.
    • Only one finding is Proven: a deterministic tool-receipt claim at turn 5 that reproduced 5/5.
  • EXAM_B: the same cap and readiness 49, but the proxy reproduced 0/5, so the result is REVIEW, not BLOCK (Score ≠ Decision).
  • MED_1: all 30 jury findings are Unproven, so REVIEW.
  • Across the three records: 47 jury findings, 0 Proven, 77 jury decisions EVIDENCE_INVALID (70 phantom juror quotes, 7 citing only user input).
  • Tamper check: editing BLOCK → PASS by hand fails three independent checks (schema S1, release invariant R2, re-projection D3).

Limitations:

  • Single author, vendor spec. ProofAgent maintains both EIO-Agents and the harness that produced the reference archives, and the re-run data come from an unreleased harness version.
  • No external validation. There is no inter-evaluator agreement study and no independent implementation.
  • Provisional mappings. All 165 compliance controls are marked provisional and need legal review.
  • What "Proven" means. Under the paper's own rules it means "proven under EIO rules", not ground truth.

BQAA relevance: this is the closest published schema to an evaluation "semantic layer" over trace rows.

  • Evidence typing: whether a row can witness agent behaviour or only provide context.
  • Separate claim states for evaluator faults, so they never count against the agent.
  • Coverage-silence causes.
  • A jury-citation validity check. It is cheap to compute in a warehouse: does the quoted span exist in any source row for that turn? In these records, about 23% of jury decisions in FIN_3 (43 of 184) failed it.
