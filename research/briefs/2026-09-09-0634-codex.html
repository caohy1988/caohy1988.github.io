SQLMorph: Query Mutation and Fine-Grained Metrics for Text-to-SQL Evaluation — arXiv:2609.08950

NEW Academy rank, limited to offline diagnostic methodology. Mohammadhossein Malekpour, Mohamed Riahi, Maxime Lamothe and Amine Mhedhbi. The primary history is September 8 v1, 16:08:43 UTC; the metadata also cites ICDE 2026. This is qualification of the previous brief’s PDF queue, not a claim that the research first appeared overnight. The entire 13-page PDF, including references, was read. Full PDF.

What survives review. SQLMorph combines join expansion, naming perturbations and execution precision/recall. Its metrics complement exact execution accuracy. Matching can retain duplicate-row multiplicities; semantic column alignment and partial-cell credit introduce additional evaluator choices.

Evidence and limits from the PDF:

  • JQE generates 6,873 candidates, retaining 58 expansions from 30 seeds. Human checking finds 43 aligned, eight underspecified and seven misaligned NL–SQL pairs. Executability does not guarantee faithful questions.
  • CHESS execution accuracy is 63.33% on seeds versus 44.83% on expansions; the unequal cohorts preclude treating this as a simple paired effect. TQA evaluates each system’s initially correct subset. The abstract’s “17%” headline is not reconciled with Table VII’s larger reported declines.
  • Table IX reverses the strictness descriptions for < versus <=. Table XI’s semantic-column/partial-cell F1 puts DIN-SQL above CHESS, contrary to the prose’s unchanged-order claim. These prevent adopting its tables as unchecked reference labels.

Artifact check adds a separate caution. The metrics documentation exposes configurable matching, an extra-column penalty and a SQLite example. The recovered execution-accuracy source snapshot compares sets of returned tuples. Set equality discards duplicate counts and row order. A local Python sanity check confirms that both [(1,), (1,)] versus [(1,)] and reversed two-row sequences compare equal under that expression. This was not execution of the repository. The raw response is an unpinned, older cached main snapshot; its relationship to the paper’s evaluated revision is unresolved. No current-release defect or successful reproduction is claimed.

Why admit a narrow rank: the framework suggests a concrete, falsifiable improvement to failure diagnosis. Its artifact and explicit metric choices make that question reviewable. The evidence does not justify importing its evaluator unchanged, weakening correctness gates, or using its score as a production training reward. NULL handling, empty outputs, required ordering and aggregate-value errors need an independently specified contract before local adoption.

BQAA TL;DR — proposed application: extend the existing feedback-correction fixture with a small set of known SQL failures. Include one extra-row result, one omitted-row result, duplicate multiplicity, wrong ordering when order is requested, a NULL/empty case and a wrong aggregate. Retain exact correctness as the acceptance outcome. Add diagnostic precision/recall only if blinded reviewers locate and repair errors more reliably within the same review budget.

Pin the schema/data snapshot, seed intent, mutation, expected result and scorer version. Have someone check the rewritten question before using it as gold. Separate the costs of generating cases, executing SQL, matching results and human review. This proposed experiment measures BQAA utility; no BQAA gain is established by the paper.
