PUBLISH with 6 new Industry ranks (one of them a paired LangChain release), 0 Academy ranks, and 5 progress or watch notes.

The theme: the rest of the agent run is becoming structured data too. Mid-run tool changes, individual jury votes, the failed tool call inside a trace, a typed decision call, and the span record itself are all getting explicit fields.

  1. LangChain langchain-openai 1.6.5 + langchain-anthropic 1.7.4 (one rank). An agent's tool list can now change partway through a conversation, carried on a SystemMessage. Previously the payload was silently dropped or failed with an opaque 400. Both packages also add Opus 5.5 and GPT-6-sol/luna model profiles.
  2. Opik 2.2.78. LLMJuriesJudge was silently dropping votes: two judges that emit the same score name collapsed into one entry, while the reason text still said "averaged 2 judge scores". It now reports every vote. Separately, experiment reads are 33× faster: 100k items went from 221 s to ~16 s.
  3. Arize Phoenix 20.16.0. When a server tool raises during a PXI agent turn, the root span now ends in ERROR and the failed tool span appears in the trace list. Before this fix, a turn that failed on a tool left no complete trace. The release also adds cost-table and playground entries for gpt-6-sol/luna and claude-opus-5-5.
  4. Goose v1.52.0 (repo is now aaif-goose/goose). Adds a decisions provider crate with OpenRouter and Jev implementations, separate from the chat providers. It exists because Jev's typed evaluation API does not fit a chat-completion interface. This is the fourth runtime this week to treat the typed decision call as its own kind of call.
  5. Braintrust JS 3.35.0. Adds span export hooks (onSpanExport) that can add, modify, delete or replace fields on a span record before export, once per record rather than once per transport retry. Also adds multimodal instrumentation for OpenAI and Google GenAI, and fixes dataset snapshots that silently included deleted rows.
  6. Mem0 v2.2.0 / ts-v3.3.0. Adds User Profiles: a JSON-Schema-shaped summary of one user, synthesized by an LLM from that user's memories in asynchronous jobs that carry an Idempotency-Key.

What this means for BQAA: three of these ranks (LangChain, Phoenix, Opik) are about what a flat span log loses: the tool list changing mid-run, a tool failure that orphans the turn, and repeated votes collapsing into one. Each is a column or event type that agent_events should be able to hold.

1. NEW rank: LangChain langchain-openai 1.6.5 + langchain-anthropic 1.7.4: mid-conversation tool changes on SystemMessage, plus Opus 5.5 / GPT-6 model profiles

This is one rank: both packages ship the same two PRs, 2 h 24 m apart (OpenAI 15:31:52Z, Anthropic 17:56:03Z).

What shipped.

  • #40758, mid-conversation tool changes. Both providers let the tool set change partway through a conversation, but until now LangChain could not put that on the wire: users got a silent drop or an opaque 400. It is now carried on SystemMessage via non_standard content blocks.
  • Anthropic:
    • tool_addition / tool_removal blocks survive on a mid-conversation system turn.
    • The mid-conversation-tool-changes-2026-07-01 beta header is appended automatically when such a block is actually sent.
    • A tool-change block on the leading SystemMessage raises an error.
    • On unsupported models the block is stripped with a warning and the text is kept.
    • Behavior change: unrecognized blocks on a SystemMessage are now dropped with a warning instead of forwarded verbatim.
  • OpenAI:
    • additional_tools is hoisted to a top-level Responses input item.
    • On Chat Completions it raises, naming use_responses_api=True.
  • #40785: Opus 5.5 and GPT-6 model-profile augmentations.

TL;DR for BQAA: the tool list is no longer fixed for a whole run. Any analysis that treats "tools available" as a session-level attribute will be wrong for LangChain agents on both providers. BQAA should record tool-set changes as events with a position in the conversation, and ADK should decide whether it wants the same primitive.

2. NEW rank: Opik 2.2.78: the jury judge reports every vote; experiment reads are 33× faster; ClickHouse cold tier ships

What shipped (compare 2.2.77…2.2.78; 2.2.76 and 2.2.77 were notes only):

  • #8394, every jury vote in judge_scores.
  • The bug: metadata["judge_scores"] was a dict keyed by score name. Judges share a score name whenever one class is used twice (GEval defaults to "g_eval_metric"), so a multi-criteria or two-model jury, the setup a jury exists for, silently lost votes. Meanwhile reason still said "Averaged 2 judge scores".
  • The fix: repeated names get #2, #3. Keys are byte-identical wherever names were already unique.
  • #8491, experiment-read performance.
  • Page size goes from 100 to 2,000, pages are fetched concurrently, and pages are no longer parsed into pydantic models.
  • Measured on 100k items: 221.1 s → 28.3 s at page size 1,000, ~16 s projected at 2,000.
  • The PR finds that round trips, not payload size, were the cost.
  • #8501: Contains / LevenshteinRatio / RegexMatch now validate string output.
  • #8427: explicit empty rule sets are honored in PromptInjection / Tone.
  • #8363: streamed Mistral tool calls no longer merge when the stream omits index.
  • Infrastructure:
  • ClickHouse cold-tier migration job (#7767);
  • minmax skip index on trace_threads.created_at (#8452);
  • cluster-wide merge/reclaim settings (#8487);
  • Helm PDB fix (#8490);
  • alerts UI rework (#8099).

TL;DR for BQAA: the jury bug is the useful lesson. An LLM-as-judge output keyed by metric name instead of vote identity loses data silently. BQAA's judge/eval rows should key on (judge instance, vote index), not on the score name. The 33× read result is a reminder that experiment reads are limited by round trips.

5. NEW rank: Braintrust JS SDK braintrust@3.35.0: span export hooks; multimodal instrumentation; deleted rows no longer leak into dataset snapshots

What shipped (last card: 3.29.0):

  • #2489, span export hooks. Synchronous onSpanExport customizers can add, modify, delete or replace fields on instrumentation span records before export. They are applied once per record, not once per transport retry.
  • Instrumentation:
  • OpenAI multimodal APIs (#2434);
  • Google GenAI multimodal APIs (#2484);
  • Groq audio APIs (#2473).
  • #2497: token metrics are now correct with AI SDK middleware.
  • #2507: provider-managed tool calls are captured, and the right provider is attributed when going through the Vercel AI Gateway.
  • #2499: Pi Coding Agent tool spans stay current, so nested spans attach under them.
  • #2512: dataset snapshots no longer silently include deleted rows.

TL;DR for BQAA: an export-time redaction/enrichment hook that runs once per record is the right shape for PII masking before rows reach BigQuery. Worth comparing with the BQAA plugin's own content-masking path. Also note #2507: when a request goes through a gateway, the provider actually used has to be recorded separately from the one requested.

6. NEW rank: Mem0 v2.2.0 + ts-v3.3.0: User Profiles are schema-shaped, generated from memories by LLM, as async idempotent jobs

What shipped (#7340):

  • User Profiles on the hosted MemoryClient / AsyncMemoryClient (Python) and MemoryClient (TS). A profile is a structured JSON summary of one user, shaped by a per-project JSON Schema and filled by an LLM from that user's memories.
  • Methods: get_profile, generate_profile, sample_profiles, get_profile_job, get_profile_settings, update_profile_settings.
  • Jobs:
  • Generation is asynchronous.
  • Every job POST carries an Idempotency-Key; callers can supply their own so a retry reuses the running job instead of paying for a second LLM run.
  • #6993: the Valkey vector store no longer crashes on None timestamps.
  • Companion releases: opencode-v0.4.1, openclaw-v1.2.1, pi-agent-v0.3.2.

TL;DR for BQAA: this is memory-derived state produced by an LLM job, outside any agent turn. To answer "why did the agent believe X about this user", the lineage has to cover memory → profile job → profile version → the turn that read it. The idempotency key is a natural join key for that lineage.
