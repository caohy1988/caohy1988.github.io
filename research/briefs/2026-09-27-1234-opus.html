A public door for LangWatchQL (LWQL, SQL over LangWatch's trace datasets).

  • REST. #7611 adds POST /api/v1/query and GET /api/v1/query/schema, and removes the old routes.
  • At the tag, the route file checks only an API key with analytics:view, and I found no feature-flag check in it.
  • An organization or personal key spans every project it can read.
  • Reference, CLI and MCP. #8198 adds:
  • GET /api/v1/query/reference, which describes both query languages in one payload;
  • a langwatch query CLI;
  • an MCP run_query tool that renders up to 50 rows;
  • a filter string on POST /api/traces/search.
  • It also deletes the MCP server's "hand-copied list of 24 filter field names", which had drifted from the real ones.
  • Workbench flag. The release_lwql_workbench flag (default false at the tag) gates the workbench UI and the tRPC endpoints.

LLM judges as SQL functions ("Instant Evals").

  • The functions (#8201). eval(text, instructions) returns a probability. eval_criteria, eval_passed, eval_score, eval_category and eval_category_probs are its siblings.
  • They are ClickHouse projection UDFs, and a call may wrap one extraction function such as conversation_bounded(...).
  • All questions about one text go into one classifier request. Rows are never packed together: per the PR's bench, agreement was 98% on single conversations and 87% with eight packed in.
  • The judge. It is TypeSafe Jev (JEV_BASE_URL defaults to https://api.typesafe.ai; jev-latest resolves to jev-1.13.0 per the PR), called "with LangWatch's own key, never a customer's".
  • Jobs (#8208). An Instant Eval run judges every row an LWQL statement matches:
  • 10,000 rows by default on every plan, up to 100,000 where the plan lifts the cap;
  • POST /api/v1/instant-evals/estimate prices a run before it starts;
  • verdicts go to ClickHouse instant_eval_judgments, exposed as a judgments dataset that joins back to traces. "The judged text is not stored."
  • Spend (#8220). Each run or synchronous judged query writes one row on the gateway spend ledger (RequestType = "instant_eval", Model = "jev").
  • Project and organization gateway budgets apply to it, and it has its own Stripe meter.
  • Organizations without a paid plan get a $1.00 free budget.
  • The PR's pricing doc says $0.0546 per million input tokens.
  • CLI and shorthand (#8216). langwatch instant-eval run|estimate|status|list|results|sample|cancel, plus shorthand targets (traces, threads, llm_spans) that expand into an LWQL statement the caller gets back.
  • Gate (checked in code at the tag). release_instant_evals has defaultValue: false: "Off by default; enable per project or organization via a targeting rule."
  • .env.example says that without JEV_API_KEY "the eval functions are published as unavailable and every judgement is skipped".
  • So on a self-hosted 3.18.0 install the judge functions are dark until both the flag and the key are set.

Cost and usage attribution fixes in the same release:

  • #8080: the metered-spend lane read $0.
  • The governance cost screen's metered lane "has shown zero for every real organization since it shipped". The gateway wrote its daily totals under the trace project, while the screen read under a hidden bookkeeping project.
  • A nightly drift check "compared empty against empty and passed every night".
  • The lane now reads the per-request gateway ledger. Days where nothing was priced read null with a count, not $0.
  • #7757 and #8169: coding-agent cost now splits by declared context.
  • A background agent that runs claude --resume for weeks, across branches, used to charge its "hundreds of millions of tokens" to one pull request.
  • In #8169's case, one reviewer-bot Codex session "with 382 million tokens and $212.61" landed on one pull request.
  • Usage is now split by the repository and branch declared at call time. Codex, which reports tokens only on session_task.turn spans, is covered through a per-context usage record.
  • Sessions folded before the change are not re-split.
  • #7921: zero readings were dropped. A metric value of exactly 0 was accepted with HTTP 200 and dropped by a truthiness check. That includes a neutral thumbs vote, a count of 0 and a latency of 0.
  • #8192: evaluator spans became orphan traces when the target trace had no usable parent link.
  • #8111: the nightly cost-rollup comparison is now event-driven and checks only days that changed.

Why it ranks:

  • LangWatch was already carded for SQL over traces (langwatch-governed-sql-workbench-coding-agent-capture, Aug 16).
  • 3.18.0 goes further in two ways: it opens that SQL to API keys, a CLI and MCP; and it makes an LLM judge a column in the same language, with persisted, joinable verdicts and metered spend. That is BQAA's design space: BigQuery SQL plus AI functions over agent_events.
  • Its cost fixes also show two failure modes a BQAA drift check would miss: empty-vs-empty passing, and whole-session attribution.

For BQAA:

  • Judge columns need three things LangWatch built:
  • one judge request per text for all questions;
  • verdicts persisted with keys (trace, span, question, judge version);
  • judge spend written to the same ledger as agent spend, with an estimate before large runs.
  • Treat a drift check with no rows on either side as a failure, not a pass.
  • For long-lived agent sessions, store usage per declared working context (repository and branch), not per session.
  • Keep 0 and null distinct in every metric column.

2. NEW rank (Industry): Agenta v0.121.4: agent-trace cost and token accounting rebuilt

What shipped:

  • Artifacts:
  • GitHub release v0.121.4 (16:12:22Z, stable);
  • PyPI agenta 0.121.4 (16:13:27Z; the SDK, which carries #7175).
  • Contents: 16 PRs merged into release/v0.121.4. The eleven I read merged between 11:54Z and 14:50Z.
  • Previous coverage: v0.121.3 was NOTE'd at Sat 1834 as a patch. Agenta has no catalog card.

The roll-up and pricing fixes (API):

  • #7179: agent spans had no cumulative cost.
  • The roll-up built trees only from parentless spans. So the agent runner's batch, which hangs under a workflow span from another batch, never got a cumulative cost: "measured: 0 of 48,005 spans".
  • Workflow spans that repeat their children's usage were double-counted: "26 tokens over a 13-token call, and twice the cost".
  • A measured $0 now rolls up as $0, and the walk is iterative. A 3,000-span chain used to risk RecursionError.
  • #7181: traces split across OTLP requests are re-totaled.
  • An agent trace often arrives in several OTLP requests: the SDK sends the workflow span, and the runner sends the model spans. The root's totals missed the other requests' spans.
  • After each batch, every trace the batch touched is now recomputed from all its stored spans, under a per-trace advisory lock. Traces over 10,000 spans are skipped.
  • #7178: unpriced spans are marked, not silently $0.
  • Spans that cannot be priced now carry ag.meta.pricing (unknown_model, missing_model, missing_token_split, pricing_failed or custom_connection) instead of a silent or wrong cost.
  • Cache writes are priced, OpenLLMetry spans get costs, and llm spans are priced.
  • With the runner's 1-hour cache-write marker, one Claude Sonnet turn on a reloaded session was priced $0.4786 instead of $0.3087.
  • #7176: dashboard figures.
  • The failure count used the sum of exception events, so a trace failing three levels deep counted three times. The rate was also multiplied by 100 twice.
  • Charts bucketed traces by storage time (created_at), not run time (start_time).
  • The Cost card now shows "Without cost: N".

The harness fixes (runner):

  • #7177: Claude and Codex usage is booked per turn.
  • Claude Code's total_cost_usd is a session running total, so every message carried the whole conversation's cost. Each turn now reports its own share.
  • Codex runs counted only a turn's last model call and dropped cached tokens. A patch to codex-acp now reports the turn's share of tokenUsage.total, not tokenUsage.last.
  • Without a token split, the runner had reported the context-window size as the token total.
  • Claude's 1-hour cache writes had been priced at the 5-minute rate, "about 35% low on a reloaded-session turn".
  • #7183: usage is kept across an approval pause, and spans served by a custom model connection are marked so they are not priced from the public list.
  • #7185: Pi chat spans carry OpenRouter's billed cost, marked agenta.usage.cost_source = "provider", instead of pi-ai's estimate.
  • #7197: the API downloads LiteLLM's latest price map at startup again. The bundled 1.101.0 map lacked gpt-6-sol.
  • #7203: a late Claude cost reading no longer overwrites a turn's usage.

Caveats:

  • The measured numbers are the PR authors' own.
  • Several PRs list QA still to do. #7181: "The full UPDATE has not run against a real spans table here." #7176's demo was "Not captured".
  • #7181 recomputes only traces that a new batch touches, and none of the PRs describes a backfill of stored traces.
  • Codex turns are still priced as one request over summed tokens, which the PR says can cross a long-context tier.

Why it ranks: it is a release-level change to how agent cost and tokens are recorded. It names the failure modes an observer can inherit from harness telemetry, such as running totals read as per-event costs and last-call-only token counts.

For BQAA:

  • When ingesting Claude Code telemetry, treat total_cost_usd as a running total and take per-turn deltas.
  • When ingesting Codex telemetry, check whether token usage is per call or last call.
  • Store cost_source and a pricing_status enum per span (provider-billed, computed with a price-map version, harness-reported, unpriced with a reason).
  • Recompute root totals from all spans after late batches.
  • Report the count of traces without cost next to any cost total.

1. NEW rank: arXiv 2609.21133: The Stochastic Shift: A New Evaluation Paradigm for Text-to-SQL with AI Operators

Authors: Tarfah Alrashed, Fatma Özcan, Per Jacobsson, Tal Neiman and Xianshun Chen, all Google. v1 17 Sep 2026 (cs.DB), 6 pages.

  • The PDF still carries ACM template placeholders ("Conference acronym 'XX"), so no venue is stated.
  • First-party check: this is Google-authored research on BigQuery's AI operators, not a BigQuery Agent Analytics doc or blog. I rank it under the same reading as arxiv-2609-24972 (Google Cloud AI Research). If Haiyuan reads the first-party rule to cover it, drop this card; the rest of the brief stands.

Full PDF read: §1–8 and the references, Table 1, Fig. 1.

What they did:

  • The problem (§3). SQL with AI operators is not deterministic. A gold query filters reviews with AI.IF('Determine if the following movie review is positive:', …) and counts 9. An equivalent phrasing ("Is this review positive?") counts 11, including all 9, and Execution Accuracy (EX) scores it 0.
  • The framework (§4, Fig. 1).
  • An LLM-based SQL Splitter separates the relational skeleton (the AI predicate replaced by WHERE TRUE) from the AI part.
  • Full and split queries are executed on the real engine.
  • An autorater scores overall, relational and AI similarity on a 1–5 scale (>3 is correct), and names the primary error source.
  • Setup (§5.1).
  • The data is SemBench (55 queries across five scenarios over text, image and audio).
  • A few-shot generator (gemini-3.1-pro-preview, temperature 1.0, no seed) wrote BigQuery (AI.IF, AI.SCORE, AI.SEARCH) and ThalamusDB (NLfilter, NLjoin) queries.
  • The authors verified the outputs by hand: 70% correct on BigQuery and 80% on ThalamusDB.
  • The same model runs the splitter and the autorater.
  • Baselines: EX, and LLM-SQL-Solver's "Miniature & Mull" and "Explain & Compare" prompts, each also run with execution results added.

Key numbers (Table 1; Table 1's rates imply 25 correct / 11 flawed queries on BigQuery and 12 / 3 on ThalamusDB):

  • EX:
  • true-positive rate 36.0% on BigQuery and 25.0% on ThalamusDB;
  • accuracy 52.8% and 26.7%.
  • It accepted a query missing a required DISTINCT because the database had no duplicates (§5.2).
  • LLM-SQL-Solver, Miniature & Mull:
  • true-negative rate 100% on both, but it falsely rejected about 32% of correct queries (true-positive rate 68.0% and 66.7%);
  • adding execution results made it worse (56.0% and 58.3%).
  • Explain & Compare with execution results:
  • 84.0% / 81.8% (true-positive / true-negative rate) on BigQuery, and 91.7% / 66.7% on ThalamusDB;
  • it accepted UNION DISTINCT in place of the required UNION ALL because the results coincided.
  • The split framework:
  • BigQuery: true-positive rate 100.0%, true-negative rate 90.9%, accuracy 97.2%;
  • ThalamusDB: 91.7%, 100.0% and 93.3%.
  • Open problems (§6):
  • choosing between a structured column and an AI operator: "three bedrooms" mapped to number_of_rooms = 3;
  • choosing the data source or modality;
  • queries that mix database columns with world knowledge;
  • generating costly AI queries for questions that should be refused.

Caveats:

  • Tiny n: 36 judged queries on BigQuery and 15 on ThalamusDB. ThalamusDB has only 3 flawed queries, so its true-negative rate moves in 33-point steps.
  • One model family does everything: it generates, splits and rates, at temperature 1.0 with no seed, and no repeat runs or variance are reported.
  • Labels are the authors' manual verification. The authors call SemBench's queries relatively simple.
  • Cost: no framework cost or latency is reported.
  • Artifacts: code and prompts are on figshare. I did not run them.

Why it ranks: it is the evaluation problem for the query shape BQAA users write over agent traces: SQL whose WHERE or SELECT calls a model. It gives a concrete, testable split. It is also the academic side of this window's LangWatch release, which puts judge functions inside a trace query language.

For BQAA:

  • Do not grade AI-augmented SQL by result-set equality. Two correct AI predicates can return 9 and 11 rows.
  • Store AI-operator calls as separate lineage: operator, prompt text, model and connection, per query. That makes the relational skeleton regression-testable deterministically and the AI predicate testable semantically.
  • For natural-language-to-SQL features over agent_events:
  • report whether a query calls an AI operator;
  • evaluate those queries with a split judge, not whole-query EX or a single whole-query LLM judge.

2. NEW rank: arXiv 2609.25237: Trains but Doesn't Learn: A Post-Training Delivery Benchmark for LLM Agents as Forward-Deployed Engineers

Authors: Weihang Ding (UC Berkeley IEOR) and Junfei Zhan (Imperial College London, corresponding). v1 21 Sep 2026 (cs.LG; also cs.AI and cs.CL), 12 pages. The arXiv comment says "Accepted to EMNLP 2026 Industry Track".

  • Queue history: scouted at Sat 1234; read in full and held for the cap at Sat 1834, Sun 0034 and Sun 0634. 0634 asked this slot to rank it or drop it. I read it in full again and rank it.

Full PDF read: §1–6, the Ethics and Reproducibility statements, Appendices A–F, Tables 1–8, Figs. 1–3.

What they did:

  • The plane. An LLM agent in the forward-deployed-engineer seat drives ten governed stages of a post-training delivery: intake, plan, config, schedule, train, eval, register, deploy, cost review and handoff.
  • Each stage is scored by discrete predicates "from platform-recorded facts, consuming none of the agent's own claims" (§1–2).
  • The oracle never reads the trained model.
  • Appendix D gives every predicate, and Table 7 maps stage failures to labels: intake-misread, silent non-learning, cost-irresponsibility, irreproducibility and premature-rollout.
  • The central failure is "trains but does not learn" (TBDL). The train stage passes but the held-out eval does not (Eq. 1): a one-sided exact McNemar test plus a pre-registered margin of 0.06–0.08.
  • Hardware and models: real metered GPUs (L40S, A100, H200) and four open bases (Qwen3-8B/32B, Gemma-2-9B-it, Llama-3.3-70B).

Key numbers:

  • Calibration (§3.1, Table 1).
  • Correct deliveries learn on every base (Δ ≈ +0.48, 12/12).
  • A relabeling trap induces TBDL 12/12 across 8B–70B.
  • An anytime-valid detector (an empirical-Bernstein e-process on a clean-probe loss gap, App. E) flags it 11/12 at a median step 250 of 300, with 0/36 false alarms.
  • It misses the subtle dirty-data trap 0/11.
  • Pressure (§3.3, Table 3). Across the cheaper tier, gate-staging compliance fell from 1.00 (neutral) to 0.96 (deadline), 0.73 (authority) and 0.47 (sunk-cost).
  • Under sunk-cost framing, Claude-Sonnet-4.6 scored 0.30 and Gemini-3.5-Flash 0.10.
  • Claude Opus 5, GPT-5.6-luna and Gemini 3.7 Flash staged 360/360 deliverable tickets and refused 60/60 infeasible ones. This was a call-level probe.
  • Delivery (§3.4, Table 4). Four frontier agents ran 38 certified episodes.
  • 38/38 passed the acceptance metric, with 0 TBDL deliveries, 0 gate bypasses and 12/12 infeasible tickets refused.
  • Yet 31/38 metric-passing deliveries were rejected by the documented contract: schema-checked model cards 30/38, reconciled cost reports 29/38 and registry CI 19/38.
  • Per arm: Opus 5 10/10, GPT-5.6-luna 10/10, DeepSeek V4-Pro 8/8 and Gemini 3.7 Flash 3/10 rejected.
  • Reports reconciled when written in the documented flat shape. "The arms that restructure the schema fail on shape, not on arithmetic."
  • Handing agents the oracle-correct configuration: 24/24 pass acceptance, and 22/24 are still rejected.
  • The worst excluded-contract episode retrained 15 times, for 5.63 GPU-hours and $10.98, "every signal green", and delivered a model no better than base.
  • Humans (§3.5, Table 5). Judgment residuals: GPT-5.6-luna 0.40, Claude Opus 5 0.35, DeepSeek V4-Pro 0.25 and Gemini 3.7 Flash 0.10. Two engineer-plus-assistant arms scored 0.06 and 0.09. No arm reaches zero.

Caveats (§6):

  • The work is post-training only and single-node, with six task groups (cluster df = 5).
  • The human comparison is cross-grid.
  • The flagship pressure result is call-level.
  • The oracle's judgment labels are single-annotator, with no agreement statistics yet.
  • The EMNLP acceptance comes from the arXiv comment only.

Why it ranks now: this window shipped real cases of cost and usage numbers that were wrong while every signal looked healthy (Agenta, LangWatch, LiteLLM). 25237 is the controlled version: an oracle built only from platform-recorded facts, and evidence that agent-written artifacts fail on schema rather than arithmetic.

For BQAA:

  • Keep platform-recorded facts (metered cost, job ledger, registry state) in columns separate from agent-reported claims, and reconcile the two.
  • Validate the schema of agent-emitted artifacts (cost reports, model cards, manifests) as its own check. 22/24 still failed with the right configuration.
  • Use Table 7's stage-failure labels as a starting taxonomy for delivery-agent sessions.
  • Treat "loss falls, every signal green" as a known false-healthy state, and require a held-out check before a session is scored as successful.
