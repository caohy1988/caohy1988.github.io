Theme 2: log the decision, not just the outcome.

  • 2609.22819. A tool-routing change can be evaluated offline only if each logged decision carries:
  • the exact post-permission sampling probability (not a model confidence);
  • the candidate set and the authorization snapshot;
  • a tool-catalog hash.

What this means for BQAA (as the observer, not the source of truth):

  • Key identity by an origin-bound id.
  • For agents, tools and skills: the enrolled endpoint, registry record or workload identity, or the qualified plugin:capability.
  • Store the display name as a separate column.
  • "One display name, two or more origins, one routing domain" becomes a query.
  • Record routing decisions as events:
  • the candidate set;
  • the chosen action;
  • the exact sampling probability;
  • the cause;
  • the policy or version.
  • Without the probability, an offline estimate of a routing change is not identified.
  • Stamp the provenance of every derived number:
  • the price-table version for cost;
  • counted or estimated for tokens;
  • emitted versus delivered counts for each log sink.
  • Treat eval-log config fields as possibly secret-bearing. From Inspect 0.3.271, a gateway token passed as an extra header is written into the log header.

1. Inspect AI 0.3.271: eval-level headers from the CLI (recorded verbatim in the log), and Gemini token counts that fall back to an estimate. Parent: inspect-ai-0-3-270-litellm-proxy-responses-default-eval-set-top-up-f1-multiset.

  • Clocks:
  • PyPI wheel uploaded 2026-09-26 22:07:28Z.
  • Tag 0.3.271 at 22:06:45Z (commit c2b63a0b, "update changelog for release").
  • Compare 0.3.270...0.3.271: 3 commits touching 7 files. The changelog dates the release 26 September.
  • How I checked:
  • Both PR bodies, #5582's diff, and the changelog.
  • The published 0.3.271 wheel, searched for how headers reach the log.
  • The 0.3.270 wheel, to see what already existed.
  • What changed:
  • #5582 (22:06:05Z; its PR body is an empty template):
    • inspect eval and inspect eval-set get --extra-headers and --extra-body, also settable through INSPECT_EVAL_EXTRA_HEADERS and INSPECT_EVAL_EXTRA_BODY.
    • Each takes an inline JSON or YAML mapping, and header values must be strings. The docs example is '{"X-Trace-Id": "abc"}'.
    • Error messages never quote the value, because "--extra-headers can carry a token".
  • Where the headers end up (code reading of the 0.3.271 wheel):
    • CLI keyword arguments become the model's GenerateConfig (_eval/eval.py:2031–2032).
    • The task log writes model_generate_config=model.config (_eval/task/log.py:299) into eval.model_generate_config (log/_log.py:1076).
    • Inspect's own dataframe API exposes that as a column (analysis/_dataframe/evals/columns.py:97).
    • model_args_for_log() strips only api_key and aws_* model args.
    • A new comment in _cli/util.py:287–290 says it plainly: "model_args_for_log() redacts api keys from model args before a log records them; extra_headers is recorded verbatim."
  • What is new versus 0.3.270: extra_headers was already a GenerateConfig field and reachable through --model-spec. What 0.3.271 adds is first-class flags and environment variables that make shell-level headers the easy path.
  • #5581 (21:40:23Z): Gemini's countTokens endpoint returns 404 in some Google configurations, and that "failed the sample" for anything that counts tokens (compaction, context-window checks). Now:
    • 404: the endpoint is marked unavailable for that model instance and not called again, with one warning.
    • Other non-retryable errors (400, 403): that call falls back to the local estimate (o200k_base tiktoken plus 10%), warning once per distinct message.
    • 401, 429 and 5xx: still propagate.
  • For BQAA:
  • The new flags make per-run attribution headers easy: a trace id, or a gateway's tag or metadata header. That supports joining eval samples to gateway spend logs.
  • Scan or redact model_generate_config.extra_headers before ingesting Inspect logs. A bearer token passed there is persisted.
  • Carry a token_count_source (counted or estimated) where Inspect or a gateway reports token counts. Gemini counts behind a 404 are now a heuristic.

1. NEW rank: arXiv 2609.27624: Agent Name Collision Attacks in Multi-Agent Systems

Adithyan Arun Kumar (independent security researcher). v1 23 Sep 2026 (cs.CR), 15 pages.

  • The artifacts repository adithyan-ak/agent-name-collision-attacks was created 22 Sep; I did not run it.
  • Codex-assisted drafting is disclosed.

Full PDF read: §1–11 and Appendix A (Tables 1–5, Figs. 1–2).

What they did:

  • The question. A2A's AgentCard.name is required but defined as a human-readable name. The card carries no stable agent identifier, and the spec has no duplicate-name semantics (§4.1). An open A2A issue, #1014, asks for a persistent id.
  • The failure the paper studies starts when a host uses that display name as a local routing key: a sub-agent name, a generated tool name, a client-map key or a broker topic.
  • Threat model (§2.2). Five conditions must all hold: a shared routing domain, the attacker controls peer B's card name, B wins the collision, the ambiguous name is later used for dispatch, and A and B have different trust. The attacker is already inside the admission boundary.
  • Method (§3).
  • Registration-to-dispatch traces and focused tests at pinned revisions of seven implementations from six organizations.
  • Recording clients or loopback HTTP peers are used, and no third-party endpoint was contacted.
  • The first-party sample test runs no model.
  • Stronger consequences (credential transfer, tool transfer, privileged action, and a later model decision) are tested separately.

Numbers:

  • Wrong-peer dispatch (Table 1, §4.2).
  • Six client-style integrations selected B's client or endpoint for a request addressed to A:
    • Google ADK Python 2.8.0: the Agent Registry helper derives the name; resolution warns, then takes the first match, and B's A2A client is called.
    • Google ADK TypeScript 2.0.0: a normalized name, first match, and B's sendMessage is called.
    • UiPath LangChain 0.17.3 and BeeAI 0.1.83.
    • Mozilla Any-Agent 1.18.0, using the OpenAI Agents SDK 0.20.0 warn policy, which keeps the last colliding tool.
    • AutoDev 2.4.1.
  • Solace Agent Mesh 1.28.8 collapsed A and B onto one name-derived broker route. Whether that means interception or denial depends on queue configuration.
  • Four constructions reach the same failure (§4.3):
  • agent-tree ambiguity (ADK);
  • tool-identity collapse (UiPath, BeeAI, Any-Agent);
  • client-map replacement (AutoDev and the first-party A2A samples);
  • broker identity collapse (Solace).
  • What does not follow (§5, Table 2):
  • Credentials and tools: zero A-specific credentials reached B in the tested bindings, and no A-owned tool object transferred.
  • Delegated context: one conditional case. Solace forwards the caller's a2aUserConfig, which may hold delegated tokens if a deployment populated it.
  • Later decisions: two second-stage dataflows (UiPath, BeeAI) where B's output reached a model that also had a host-only tool. These used scripted models, so they show a path, not a success rate.
  • Propagation (§6.1). The first-party A2A samples had at least six paths that store connections under card.name. A bounded code search found the pattern in 100 files across 83 public repositories. The paper counts that as propagation, not prevalence.
  • Negative controls (Table 3), seven paths that do not misroute:
  • Semantic Kernel .NET (duplicate functions fail closed);
  • Microsoft Agent Framework Python (duplicate executor ids are rejected);
  • Google ADK Java and Go (explicit local names, and duplicates rejected);
  • Strands TypeScript (exact and normalized duplicates rejected);
  • python-a2a (suffixed aliases);
  • Agno (routes by an operator-controlled id).
  • ADK boundary (§4.4, §9).
  • The ADK tests supplied duplicate names by hand. The Agent Registry helpers are the source path from card content to name.
  • The author did not show that a low-privilege agent can create or refresh the needed record in a Google Cloud project.
  • Hence the paper's phrasing: "a vulnerable routing primitive with conditional attacker reachability, not an end-to-end remotely exploitable zero-day".

Caveats I'd flag:

  • Single author, and a purposive seven-target corpus.
  • Results are for pinned revisions, "rather than present-tense vulnerability status" (§9). PyPI google-adk is now 2.10.0 against the tested 2.8.0, and I did not check current code.
  • Solace delivery was not exercised on a real broker.
  • The attacker must already be admitted to the routing domain.

Why it ranks:

  • It is cross-implementation evidence that a display name used as a key sends agent traffic to the wrong principal, silently and deterministically, with no model involved.
  • Analytics keyed on agent or tool display names inherit the same ambiguity: two peers sharing a name are one row.
  • It bears directly on ADK: two ADK languages resolve duplicates first-match and two reject them.
  • It is distinct from the catalog's A2A and MCP cards:
  • otel-genai-195-a2a-protocol-semconv covers A2A span naming;
  • arxiv-2609-18217-implicit-trust-mcp-tool-calling-channel-fragmentation covers payload trust across channels;
  • langsmith-sdk-v0-14-0-agent-identity-otel-finish-reasons covers SDK-level agent ids.
  • None covers name-to-route binding.

TL;DR for BQAA:

  • Record agent and tool identity as an origin-bound id (endpoint, registry record or workload identity) plus a separate display-name column. Never group, join or attribute on display name alone.
  • Add a standing check: the same display name with two or more distinct origins in one app or routing domain. That is the paper's precondition, and it is cheap to query.
  • For ADK: the paper recommends routing by enrolled id, rejecting normalization-equivalent duplicates, and attaching credentials only after identity resolution (§8). ADK Java and Go already reject duplicates.

2. NEW rank: arXiv 2609.22819: Counterfactual Tool Ranking under Utility, Cost, and Privilege Constraints

Jiapeng Li (Microsoft). arXiv v1 19 Sep 2026, labeled "working paper, version 2 … not peer reviewed", 18 pages.

  • Code and artifacts are at jaxblack/counterfactual-tool-ranking (created 18 Sep; I did not run it).
  • GitHub Copilot assistance is disclosed.

Full PDF read: §1–11 (Tables 1–8, the §8.4 proposition, and the reproducibility section).

What they did:

  • The setting. An agent chooses among complete tool calls: the tool, its resources and any amount.
  • A deterministic ACL filters candidates before ranking and again at execution, and abstaining is always allowed.
  • Eleven executable tools cover three synthetic enterprise domains (documents, tickets, customer discounts), with success checked against database state.
  • Logging (§4.3).
  • An epsilon-greedy logger records the full post-permission probability vector and the selected action's exact probability ("not a language-model confidence or a fitted propensity").
  • Each record also holds the candidate and authorization snapshot, policy snapshots, a tool-catalog hash and the outcome.
  • Readers reject records whose candidates, tool catalog or probabilities don't match.
  • Evaluation.
  • Direct, IPS, self-normalized IPS and doubly robust (DR) estimators are compared against each frozen policy's value re-executed in reset environments.
  • Version 1 is a 45-run matrix (387,000 logged selections). Version 2 adds 30 full-return control runs and 15 runs on 1,930 BFCL-derived function-selection tasks with function-name-disjoint splits.
  • Two local Qwen2.5 models (0.5B and 1.5B) are run on 200 held-out tasks.

Numbers:

  • DR's advantage depends on the baseline (Tables 2 and 4).
  • Version 1: DR had the lowest error in every condition. For example, shifted 0.0772 (direct) vs 0.0187 (DR), and linear 0.1039 vs 0.0193.
  • Adding a direct regressor on the full realized return reverses the linear result: 0.0139 (direct) vs 0.0272 (DR).
  • Under shift DR still wins: 0.0948 vs 0.0227.
  • The author: "the benefit of correction depends on the quality of the complete nuisance model; it is not an intrinsic superiority of DR."
  • Learning a ranker (Table 1). DR ranking does not beat direct prediction. In the noisy setting the utility is 0.5027 for DR vs 0.5118 for direct; with small data, 0.4212 vs 0.4616.
  • Public tasks (Tables 5 and 5b).
  • On BFCL-derived tasks the direct selector reaches 81.85% balanced accuracy, against 79.83% for DR and 69.23% for TF-IDF, with about 28% coverage.
  • A post-hoc audit found that all 508 single-candidate rows were should-abstain tasks, a shortcut. On tasks with at least two candidates, direct falls to 76.80% against 64.89% for TF-IDF.
  • Local LLMs never abstained (Table 6). Both Qwen2.5 models answered 0 of 128 should-abstain questions correctly, while getting 46/72 and 59/72 should-call questions right.
  • Missing support (§3.3, §7.4, Table 8).
  • A tool that is authorized but was never explored makes the full value "not identified". The evaluator reports that rather than imputing.
  • Changes can still be identified: if two policies agree on every unsupported action, their difference is point-identified. A disagreement-preserving fallback achieved this in 5 of 5 support-gap runs (width 0, against 0.1315 for DR and 0.2111 for blanket abstain).
  • Conservative bounds never certified an improvement in any of the 15 public runs.
  • Real MCP transport (§7.4).
  • 2,542 tool calls went through an MCP stdio server (protocol 2026-07-28), with a median round trip of 0.755 ms.
  • Replaying the 600 logged training calls over MCP gave zero semantic mismatches.
  • Abstention costs utility (Table 3, noisy setting). The conservative variants fall to about 43% coverage and 0.34 utility, against 0.51 for direct.

Caveats I'd flag:

  • Scale and data:
  • A single-author working paper.
  • Synthetic tools and fees.
  • Semi-synthetic bandit logs on BFCL (one revealed outcome per decision, drawn from full-feedback labels).
  • Five seeds, and BFCL test splits of only 57–132 tasks.
  • Scope: a single decision per task, not multi-step credit assignment.
  • The conservative heuristic is "inadequate as a safety mechanism", in the author's words.

Why it ranks:

  • It turns "evaluate a tool-routing change offline" into a concrete logging contract:
  • the exact propensity;
  • the post-permission candidate set;
  • the authorization snapshot;
  • a catalog hash;
  • the realized full return.
  • Without those fields a change cannot be evaluated. With them, even a partly unsupported change can be.
  • It is honest about the limits: the reversal against a strong direct baseline is the paper's own finding.
  • It is distinct from two catalog cards:
  • arxiv-2609-26707-optimal-sequential-annotations-ope (which label to buy for off-policy evaluation);
  • arxiv-2609-05820-limited-feedback-bandit-llm-expert-routing (bandit prompt routing).
  • Here the unit is a complete, permission-filtered tool call over MCP.

TL;DR for BQAA:

  • For any router or tool selector the fleet or a customer runs, log per decision:
  • the candidate set;
  • the permission-filtered set;
  • the chosen action;
  • its exact sampling probability (0 when deterministic);
  • the policy version and a tool-catalog hash;
  • the realized full return: success, cost, latency and a risk flag.
  • Then IPS and DR are a SQL aggregate over that table. Report "not identified" for actions with zero logged probability instead of imputing.
  • Measure abstention separately: should-act vs should-abstain recall, as balanced accuracy. The small models' 0/128 shows why.
