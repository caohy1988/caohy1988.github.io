1. Does the Judge See What the Evaluation Requires? Input Assurance for LLM Agent Evaluation — https://arxiv.org/abs/2611.02676

Full PDF read (pdftotext of the complete paper; all parts read including §I–§VII, Tables I–III, Fig. 1, and references; key numbers cite sections/tables as printed. Supplementary material is referenced by the paper but not part of the PDF and was not read.)

What it is. An input-assurance case study of one trajectory→judge pipeline (30 trajectories from BFCL and τ²-bench subsets of AgentProcessBench, 60 target steps, 240 packets, five judge configurations J0–J4; §II). A renderer turns structured trajectory records into text packets for a step-level LLM judge; two separately written checkers validate records and packets. The paper asks what evidence shows a packet is what the evaluation requires, and proposes four obligations: (1) required content survives rendering, (2) checkers cover their requirements, (3) a failed check stops later use, (4) the judge reads the bytes last checked (Abstract, §I, Table I).

Results that matter (with receipts). The renderer kept message text but omitted the structured tool_calls field entirely, so a step whose action lived only in that field appeared blank: 53 of 60 judged steps were blank in the original packets (26 of 30 error targets, 27 of 30 comparison targets) even though every packet matched its recorded hash (§II-A). The pipeline's research contrast — how much later context raises error flags — was G = 13 for judge J0 on the blank packets (full minus prefix: +15 on error steps, +2 on correct steps) and fell to G = 2 with calls restored, a reduction of 11 (0.37 per trajectory, 95% cluster-bootstrap interval 0.17 to 0.53; §V). J0 abstained on all 26 blank error-prefix steps, but J1–J4 flagged 20, 20, 7 and 19 of the same 26 blank error steps and 13, 22, 7 and 17 of the 27 blank correct steps — a flag on a blank step reveals nothing about whether the action was present (§V). Both checkers verified every call had a result but neither checked every result had a call, so both accepted an injected unmatched tool result — the only one of 34 shared mutation cases both missed (§III-A); the disk checker's hash comparison compared a hash against itself and could never fail (§III-B). In integration tests a failed build's packet was staged and read, a packet changed after staging was read (time-of-check-to-time-of-use gap), and a CRLF line-ending change passed staging's text-normalized hash (§IV-A). Three cumulative controls (stop-on-failure, exact-byte hashes checked before use, reverse call↔result matching) stopped 18 of 19 constructed fault cases before a recording stub read any packet; the nineteenth (a stale script) never ran (Table II, §IV-B). Honest limits (§VI Scope): one pipeline selected after the omission was found, 30 trajectories / 22 user requests, controls developed on the same cohort and fault cases written with knowledge of the code; transfer evaluation on independent pipelines is planned, not done.

Why BQAA cares. BQAA's core operation — render stored trace rows into judge inputs — is exactly this boundary. The transferable standard is the four obligations with their direct tests (§VI Tests 1–4): render an action held only in a structured field and check name/arguments/position against the source; violate each requirement in both directions (call without result, result without call); continue-after-failure must not reach the judge; change checked bytes and require refusal. Two operational corollaries for any trace warehouse: a matching hash proves bytes unchanged, not content complete; and two checkers written from the same plan share blind spots, so independent implementations do not substitute for requirement-level mutation tests.

2. SpBench: An Agent-Native Framework for Cross-Engine Lakehouse Benchmarking — https://arxiv.org/abs/2611.00449

Full PDF read (pdftotext of the complete paper; all parts read including §I–§VI, Figs. 1–4 as extracted, acknowledgments, and references; authored by the vendor operating the system, as printed on the title page.)

What it is. A production system paper for cross-engine lakehouse benchmarking (TPCx-BB, TPC-DI, and custom benchmarks distilled from production patterns), built so LLM agents are first-class consumers. Three mechanisms (§I): strictly typed benchmark definitions, a structured-telemetry contract, and an agent-native harness of three composable skills. Cross-engine fairness is framed as a triple-equivalence problem — data, query semantics, compute tier — with equivalence promoted from "by convention" to "by construction" (§II).

Results that matter (with receipts). One typed BenchmarkDefinition (→ QueryGroup → Query → QueryStep, Fig. 2) compiles via templated code generation into per-engine artifacts executed by pluggable runners (§III, Fig. 1). Every run emits a star-schema telemetry record to object storage — a fact_runs row, one fact_queries row per query with timing and structured error fields, content-addressed (hash-keyed) dim_* records for deployment, compute tier and environment, plus a per-step timing table that localizes latency (data loading vs compilation vs execution) — exposed as external tables so deterministic SQL powers both dashboards and agent queries (§III). The agent layer (§IV) exposes run monitoring, SQL access and artifact retrieval as typed MCP tools, and splits work into Distill (production telemetry → sanitized spec with no customer query content, table values, or user-identifying information), Build (spec → runnable per-engine artifacts), and Analyze (queries the telemetry tables → pass/fail, latency deltas, outliers). Two governed loops (operational: reproduce/localize/classify a telemetry-detected regression; development: request → spec → code → summary) are gated by staged acceptance contracts, and Build decomposes into four narrow sub-agent delegations (static codegen, per-query code review, SF1 validation, full-scale run) after a monolithic single-agent design "breaks down" from context overload (§IV, Fig. 4). Outcomes (§V): more than 400 benchmark queries run continuously to guide the roadmap and catch regressions (leading to production improvements, e.g. in file-to-table transforms and UDF optimizations); the authoring cycle is reported as reduced from weeks or months to one AI development loop. Limits (§VI): single-organization deployment across a fixed engine set; the paper reports no cost, latency, or accuracy measurements for the agent layer itself, and head-to-head evaluation breadth is stated as ongoing work.

Why BQAA cares. This is the warehouse-native pattern BQAA already argues for, documented end to end for evaluation telemetry: runs as facts, configuration as content-addressed dimensions, per-step timing as its own table, and agents constrained to typed/SQL reads over those tables rather than shell access to logs. The Distill governance rule — a spec derived from production telemetry carries patterns and statistics but no customer content — is a directly reusable constraint for distilling benchmark/eval sets from stored traces, and the staged acceptance-contract gate mirrors Rank 1's input-assurance obligations at the workflow level. Read as an existence proof and schema reference, not as a comparative evaluation of engines or agents.

3. Impossible Code, Barely Changed Score: A Replay Study of Judge-Based Evaluation — https://arxiv.org/abs/2611.01572

Full PDF read (pdftotext of the complete paper; all parts read including §1–§5, Tables 1–2, Fig. 1, references, and Appendices A–O with Tables 3–13; key numbers cite tables/appendices as printed.)

What it is. A replay/replication study of an earlier GRPO code-generation evaluation: three checkpoints of a 7B code model (base, execution-rewarded "CE-trained", judge-rewarded "SLJ-trained") on 421 HumanEval+MBPP problems, scored by a strong LLM judge that reads code without running it, by execution tests, and by a cheap Python syntax check (§2). The question is sensitivity: does a judge-based score reveal a substantial change in the answers it scores?

Results that matter (with receipts). On replay, the base model's invalid-syntax rate is unchanged (0.39%→0.40%) but the two trained checkpoints' jumps to 63.04% and 66.90% (Table 1; mostly one surplus closing bracket — 35,562 of 36,051 SLJ invalid samples, §3.1/App. B), while the strong judge's Pass@32 falls only ~3 points (CE 95.72%→92.70%; SLJ 96.67%→93.95%; Table 10). The judge approves 60.56% of SLJ-trained samples that fail the syntax check, so 59.49% of all its approvals are code that cannot run (Table 4, App. D). On identical second-run outputs, more attempts erase the signal: the judge's base-minus-damaged gap shrinks from 16.01 points at k = 1 to 0.71 at k = 128 (95% interval includes zero), while execution keeps 15.91 points (Tables 7–8); judge Pass@128 is 96.44% vs 28.27% under execution (Table 2). A syntax gate (judge approval ∧ parses) drops Pass@1 by 0.19 points on the healthy checkpoint but 37.40/40.51 points on the damaged ones (Table 11), and a controlled dose-response confirms the mechanism: corrupting up to ~60% of healthy answers moves judge Pass@32 by ≤0.24 points while the parse rate falls to 39.93% (Table 12, App. L). Honest limits (§4, App. H/N): one incident in one pipeline (both checkpoints share a release path; cause unknown — checkpoint corruption, loading/template drift not excluded; no checksums or serving records survive); code only; both judges from one model family (the weaker judge is less insensitive, App. M); MBPP prompt naming depresses absolute execution scores (App. I, Table 13). The paper's recommendation: report the share of answers passing a cheap validity check alongside every judge-based score, and retain generated answers, judge inputs/verdicts, generation settings and artifact checksums per run (§4–§5).

Why BQAA cares. The generalizable claim is about instrumentation, not code: a headline judge metric without a companion validity denominator can stay flat while the underlying outputs collapse, and best-of-k aggregation makes it worse. The warehouse equivalent is a per-run executable-validity rate stored beside every judge score — tool-call JSON parse rate, argument/schema conformance, call↔result match rate (the same quantities Rank 1's checkers failed to enforce) — trended across runs so output damage is visible even when judge scores don't move. The retention recommendation (answers + judge inputs + verdicts + settings + checksums) is a concrete schema requirement for any evaluation built on stored traces.
