Read this first

The strongest BQAA thread is evidence that remains interpretable after execution. This batch supplies three complementary research views: reconstruct a particular action from runtime events; audit the detector that turns those events into a label; and check required actions alongside final state. The practical opportunity is an evidence record that keeps observations, evaluator interpretation and missing information distinguishable. The Academy cards below give the measurements and their boundaries; none is a production validation of BQAA.

NEW — AWS Continuum GA attaches execution evidence to remediation

Primary: AWS Continuum for code vulnerabilities GA, October 22, stable/GA. The AWS announcement feed timestamps it at 21:00 UTC / 14:00 PT. Suggested id: aws-continuum-code-vulnerabilities-ga-evidence-remediation.

AWS describes a workflow that combines application topology, identity relationships and network reachability with vulnerability findings, tests exploitability in an isolated sandbox, and supplies remediation PRs with exploitability proof and a blast-radius assessment. It starts with proposed fixes in Learn mode; the operator can switch to Enforce mode with configured guardrails. This is a product launch, not a repository PR announcement. GA scope.

BQAA implication — inference: retain the evidence and authorization transition connecting a finding, validation attempt, proposed patch and action. A useful analysis should distinguish proposed, approved, executed and independently verified remediation. The announcement supplies no measured precision, false-positive rate or threshold for changing modes; none is inferred here.

Progress — Pydantic AI 2.60.0 records retry causes and mid-run tool additions

Target catalog item id: pydantic-ai-v2-57-0-approval-reviewer-mcp-apps-service-tier-pricing.

Primary: Pydantic AI v2.60.0, stable; GitHub October 23 01:44:06 UTC / October 22 18:44:06 PT; PyPI 02:01:51 UTC, unyanked at lookup. This advances 2.59.0 rather than repeating its missing-usage accounting.

Tool retries become ToolReturnPart(outcome='retried'); feedback without a corresponding call becomes RetryFeedbackPart. Retry metadata can carry cause, attempt and retry budget, including unknown/unavailable-tool rejection. New history therefore requires updated type matching. Tool spans expose pydantic_ai.tool.retry.*; counters can be absent when a retry is not charged. Legacy histories remain loadable. Limits matter: the final rejection when retries are exhausted can still lack a history part, and the Vercel live stream lacks an outcome carrier that preserves this distinction on echoed turns. Released retry representation and remaining gaps.

The release also records newly appearing mid-run tools through ToolAvailabilityDeltaPart, with provider-specific addition channels rather than simply extending the initial tool list. Consumers inspecting only tools[] can miss newly introduced tools. AG-UI client-held history can lose activity messages on its return trip; Temporal cannot recreate an add_function() mutation performed inside an activity it does not re-execute. The documented alternatives are retained server history/returned activity records and workflow-side tool configuration. Released tool-history contract.

BQAA implication — inference: reconstruct the tool set available at each decision and distinguish a rejected call from an executed tool that requested a retry. Keep history/event gaps explicit. This is one framework update; its sandbox, compaction and realtime changes do not become separate cards.

Progress — Weave 0.53.13 traces decision calls and changes emitted usage names

The Python release includes instrumentation for TypeSafe system_one: one model span per call, carrying model, questions, answers, usage and an available request ID. It uses the current turn or a documented fallback; it does not create a Weave Call or make a surrounding @weave.op its parent. Content capture is configurable, and image content is represented by references. The implementation also covers TypeScript, but this brief's release clock establishes the Python distribution only. Instrumentation semantics.

The release emits gen_ai.usage.cache_write.input_tokens and gen_ai.usage.reasoning.output_tokens, replacing older keys, and moves finish reasons to the span-level field in the described integrations. The compatibility notice requires corresponding server changes first: older servers can lose cache-write counts and finish-reason information. A released SDK is not a receipt for the deployed server version. Attribute migration and deployment ordering.

BQAA implication — inference: version semantic-convention mappings and test producer/server combinations. Avoid interpreting a missing count after an upgrade as zero, and do not invent an operation-parent relationship merely because an SDK wrapper surrounds the call.

NEW — AgentTriage: Replayable Security Diagnosis Across Heterogeneous Agent Runtimes — arXiv:2610.30738

Full PDF read — 17 pages. Five runtime overlays normalize invocation/result evidence for deterministic, policy-relative diagnosis. On 120 adjudicated cases, grounded joint diagnosis is 0.858, versus 0.683 for the strongest same-schema baseline; paired gain 0.175, 95% CI [0.092, 0.258] (Tables 5 and 7). Unsupported claims remain 0.036 (Table 5).

The useful design is explicit lifecycle identity, claim-to-event links and abstention when required evidence is missing. Replayability does not establish observational completeness. Two overlays synthesize call IDs, parent evidence varies (Table 2), and selection diagnoses one terminal lifecycle rather than every action (§3.5). Synthetic, pinned configurations limit transfer (§7). Provider token overhead is unavailable, not zero (Appendix C/Table 14).

BQAA inference: prototype replayable outcome queries with recorded evidence classes; test missing results, reordered completions and multiple effects before expanding attribution.

NEW — What the Trace Shows and What the Label Says — arXiv:2610.30491

Full PDF read — 13 pages. A fault-injected calculator audit uses six models and 30 arithmetic tasks per model. Human review covers 90 traces; verification agrees on 67/81 applicable comparisons, while correctness agrees on 67/67 (Table 6). A quiet correction, a repeated expression and a stuck loop can defeat a simple re-check detector's interpretation (§4.4).

These are reviewed-case rates, not population accuracy. One primary reviewer helped expose gaps; detectors were revised and the same reviewed cases rechecked (§§4.3, 5.1). Tool-call frequency changes fault exposure, and execution budgets censor runs (Table 5). The study does not establish reliability in open-ended workflows.

BQAA inference: retain automatic labels, evidence, applicability, cutoff reason and human corrections separately. Validate a detector on held-out traces before treating its label as a behavioral fact.

NEW — TauIndianBankBench: Procedure-Aware, Action-Oriented Evaluation — arXiv:2610.30161

Full PDF read — 15 pages. Across six models on 1,000 synthetic banking tasks, final-state-only grading raises pass rates by 6.5–12.0 percentage points over the combined action/state criterion (Table 2, §5.2). The action check requires specified calls, including reads, and rejects unrequested writes even if later reversed (§3.2).

The scorer is order-insensitive, and one matching call can satisfy a repeated reference call. Task dependencies and the simulated customer supply ordering pressure; this is not direct proof of temporal compliance. Communication assertions do not affect the released score (Appendix F/Table 8). English-only synthetic tasks and an unmeasured customer-simulator error rate limit deployment conclusions (Limitations).

BQAA inference: compare outcome checks with required-event and collateral-action checks, then test temporal constraints separately. Its September 30 submission date is retained; its new October 23 listing is the freshness basis.
