Progress — Inspect 0.3.284 preserves the evidence used to explain evaluation outcomes

Target catalog item id: inspect-ai-0-3-280-agent-bridge-attribution-response-headers-sandbox-mounts.

Primary: 0.3.284 release, stable, October 25 01:19:11 UTC / October 24 18:19:11 PT. PyPI confirms an unyanked distribution at 01:20:42.549926 UTC. This extends the existing evidence/attribution card; 0.3.283 is not re-admitted.

Three changes are material for agent analytics:

  • Historical model messages retain their earlier values. Inputs and output choice messages are snapshotted so a later in-place edit does not rewrite earlier model events. The tagged implementation reuses unchanged snapshots, but explicitly falls back to the live message when serialization or deep copying fails. It is not a universal immutable-log guarantee. Released implementation, change.
  • Unexpected background failures reach sample-level error handling. The background agent's future is marked errored and the exception is propagated, allowing the normal fail_on_error and retry_on_error policies to apply. Recoverable tool errors and subagent-local limits retain their separate handling. This closes a path where the parent sample could finish successfully despite an unexpected child failure. Released change and scope.
  • Crash recovery reconstructs fuller evidence. Both database and filestore recovery prefer the initial sample event and final scorer events over shortened summary fields, preserving input, target, choices and score details where those events exist. A companion fix restores output and message text from attachment references. Missing events still fall back to summaries; already-recovered logs are not automatically repaired. Sample recovery, output recovery, tagged reconstruction.

BQAA inference: preserve runner version, recovery provenance and child-error classification beside scores. Use fixed cases to compare ordinary, recovered and background-failure runs. A post-upgrade change in error rate or score metadata may reflect newly visible evidence. Old records with shortened fields or mutable-message exposure should retain that qualification; this release cannot recreate evidence that is no longer available.

Progress — Letta Code 0.34.24 counts completed local steps and separates run ownership

Target catalog item id: letta-code-v0-34-12-13-claude-codex-subagents-connected-computer-live-tool-progress-opencode-backup-wake.

Primary: v0.34.24 release, stable, October 25 05:39:26 UTC / October 24 22:39:26 PT. npm records distribution at 05:12:04.427 UTC, with no deprecation flag. This is one Progress update for the release, not separate cards for its fixes.

The local backend now emits step_count: 1 for each completed provider step, including when token usage is absent. Previously, its usage accumulator could stay at zero because the emitted chunk omitted the step count. Emission is guarded at the provider stream's completion event; failed attempts that leave through the error path do not become completed steps. Missing token values remain missing, so this counter does not measure all attempts or reconstruct spend. Change, tagged provider executor.

Local active-run ownership now distinguishes different agents' default conversations. Cleanup removes an ownership entry only if it still belongs to that run, preventing stale cleanup from clearing a newer run's entry. The concrete failure modes were false active-run conflicts and cancellation crossing between agents. This is local-backend behavior, not a claim of universal cross-service isolation. Change, tagged backend.

The listener also applies max_turns at an approval stop: at the cap, it ends with max_steps and queues denials for pending tool calls. The source discussion explicitly limits this guarantee: denial queuing is in memory, and a resumed turn starts with a fresh step count after restart. Treat it as a per-process turn limit, not a durable lifetime budget. Change and restart qualification, tagged cap check.

BQAA inference: store agent, conversation, run and process/restart identity alongside completed-step increments. Keep attempts, token usage, approval waits and terminal reasons separately queryable. A missing old counter is not proof of zero work, and a new process should not silently reset an analytics-level budget. These are proposed measurement checks; no production effectiveness or runtime replication is claimed.
