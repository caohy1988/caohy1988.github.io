Academy

NEW A1 — CARGO: Context-Aware Retrieval-Gated Evaluation of Agentic AI in Production (arXiv 2609.30471, Dell Technologies, cs.CL, v1 24 Sep 2026)

Full PDF read: main text §1–10 and Appendices A–H.

  • Problem: reference–instance divergence (RID). In a production support agent, the golden answer closest to a live question almost always answers the same question about a different case, asset or work order. §2.3 shows that a literal reference-based judge can't separate "wrong procedure" from "correctly different entity values".
  • Method:
  • The retrieved reference is reframed as a procedural exemplar.
  • Each claim is scored supported/contradicted/unverifiable against the live trace's observed context, and only contradictions are penalized.
  • Evaluation is gated on retrieval confidence (fixed τ = 0.80, margin-aware, or calibrated), so the evaluator abstains when it has no valid reference (§3.1).
  • It also logs trace-level diagnostics: planner verdict, replanner, response type and latency (§3.4).
  • Key numbers (Table 1; CARGO-Bench, 246 items, 10 seeds, gpt-oss-120b × 3 seeds and gpt-oss-20b × 1, 7,872 judgments):
  • DIRECT, the standard reference-based judge, penalizes 100% of correct entity-transplanted answers, so DI = .00. In 150/150 rationales it cites the value mismatch, and in 149/150 it calls the live value "hallucinated" (§6.1).
  • Adding the live facts without reframing (DIRECT+CTX) changes nothing: DI .00 / −.01.
  • CARGO: 0/50 false penalties on transplants; contradiction recall 50/50 (120b) and 49/50 (20b); DI .58 [.48, .68].
  • The rubric swap (Table 3) shows the context-grounded dimension definitions do most of the work. DIRECT with CARGO's definitions alone reaches DI .49.
  • Limitation the authors own: CARGO catches only 10/50 procedural corruptions (120b): 10/26 step deletions, 0/10 negations, 0/14 policy swaps (§6.1).
  • A post-hoc "authority split" prompt fix doesn't help (ΔDI −.007 [−.038, .023]).
  • An LLM-annotator study with explicit guidelines recovered only 3/10 (App. D).
  • The production-traffic studies are preregistered but not reported: H1 expert agreement and H4 gate calibration (§5, §10).
  • The P4 rate moved from 10% to 20% between the 150- and 246-item releases.
  • The golden set has 30 items, 23 of them entity-free.

TL;DR for BQAA: if we score live agent traces against a golden set, entity-bearing questions make a literal judge report pure noise. Judge against the trace's own observed context, log abstentions as coverage gaps, and add a separate procedure check, because context-grounding alone misses 80% of procedural errors.

NEW A2 — Beyond Approved Actions: Runtime Validation of Persistent Outcomes in Agent Workflows (EffectMatch) (arXiv 2609.31301, Harbin Institute of Technology, cs.SE, v1 25 Sep 2026; submitted to IEEE TSE)

Full PDF read: main text §I–VI and Supplementary S1–S4.

  • Problem. A tool call can be approved and return success while leaving persistent changes nobody approved. Examples: a DB trigger inserts a notification, a value is altered, or a remote payment's response is lost and the retry duplicates it. Downstream work then treats that call as successful.
  • Method: an Effect Commit Contract (§II–III).
  • Before execution, the application states the approved outcome A as a multiset of persistent changes.
  • The runtime binds A to its source, the current task-state revision, the plan revision and one execution occurrence.
  • It certifies that every reachable persistence or dispatch outlet is either observed or denied.
  • It stages the operation (e.g., a held PostgreSQL transaction with write-recording triggers), collects the actual changes E, and classifies the result EXACT/DIVERGED/INDETERMINATE.
  • The decision goes to a durable journal that later workers must read before continuing.
  • Key numbers:
  • Table III(a), PostgreSQL, 3 independently approved MCPMark tasks: Direct and AgentSpec commit 9/9 hidden-trigger writes, missing rows and altered values; EffectMatch commits 0/9 of each and keeps 9/9 clean runs.
  • Table III(b), STATE-Bench, 12 tasks: all 117 mismatches rejected across 39 task×fault cases; error-reject accepts all of them.
  • Table III(c)/S4, 206 tasks with clean references (618 runs per cell): Direct commits 354 omission and 138 duplication faults, error-reject 138 and 138, EffectMatch 0 and 0. EffectMatch keeps all 618 clean outcomes; error-reject withholds 21 correct ones whose trajectories recovered from an intermediate tool error.
  • Table IV/S6 ablations: removing any one mechanism (result comparison, complete observation, approval-source check, one-use binding, durable hazard record, candidate binding, fresh boundary check) re-admits its failure in 20/20 runs.
  • Table VI, recovery: 540 producer processes and 1,080 fresh-reader checks, with no release without a valid terminal.
  • Live agents (Table V): DeepSeek API, a DSH harness and Codex CLI 0.154.0, 108 episodes, all correct. The API config needed a host-finalization fix for 3/18.
  • Overhead (Fig. 6): median +1.08 ms per task (4.35× on sub-ms baselines). Outlet certification adds +15.16 ms median.
  • Limitations:
  • The approved outcomes in the independent subset are hand-authored (S1).
  • The 206-task comparison uses saved clean replays as targets.
  • Faults are injected, not produced by agents. The live-agent batch only shows integration works (S4.D).
  • GitHub readback can't attribute remote changes to a specific request.
  • OPAQUE backends get no rollback: divergence only blocks continuation (Table I).

TL;DR for BQAA: "the tool returned success" and "the system ended in the approved state" are different facts, and only a diff of persistent changes before and after the run shows the second. For an observer, that means logging observed effects next to tool results, and treating a missing terminal decision as "blocked" rather than "succeeded".

Six-week EV

  • Harness-native OTLP is becoming default plumbing. Codex 0.158 ships final-response, Guardian and spawn telemetry. Letta journals each decision's cost and calibration. The 6-week bet is that ingestion from harness-emitted OTLP logs, not just spans, becomes table stakes. Expected: high. Cost to track: low.
  • Judge validity is splitting from judge bias. CARGO (RID) joins 1834's 2609.30290 production SQL-judge audit (kappa .04). The failure is now "the reference is the wrong target", not position or verbosity bias. An abstention/coverage column for evaluators is a cheap, defensible schema addition.
  • "Approved ≠ realized" moves into runtimes. EffectMatch, Letta's "Run must be terminal" check on resumed workers, and Mastra's empty-trajectory fix all separate a reported success from the real end state. Expect more harnesses to emit an outcome-classification field; tracking it is worth it.
