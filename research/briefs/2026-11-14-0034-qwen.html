Read this first

Three items this slot, and they line up into one argument about where agent measurement goes wrong.

  1. AWS gave agent latency a denominator. Amazon Bedrock AgentCore runtime platformVersion="V2" snapshots your container once and restores it per session, and — the part that matters for BQAA — publishes two CloudWatch metrics in the AWS/Bedrock-AgentCore namespace: Latency (time to first byte) and OverheadLatency (the platform's share: starting the microVM, restoring the snapshot). Your code's time is the difference, Latency − OverheadLatency. A managed agent runtime is now reporting its own contribution to end-to-end latency as a first-class metric, alongside explicit guidance to report P90/P99 or a trimmed mean TM90 rather than a plain average, and a warning that OverheadLatency's distribution is confounded by your new-session mix so you must compare runs with a similar mix. That is an attribution-boundary story arriving from the vendor side.
  2. The gateway layer silently rewrites the conversation you think you're tracing. isloss (arXiv 2611.15543) is a deterministic oracle for conversation-information preservation across LLM API translation. Across 685 completed translations from six configurations of five translator codebases (including LiteLLM and Vercel AI SDK v5/v7), 127 (18.5%) pass static target checks while silently introducing at least one avoidable change to prompt, role or tool information. Dropping a tool-error is_error flag collapses compliance from 30/30 to 0/30 on both tested Gemini models. Among the deployment findings: mid-stream errors closed with HTTP 200 and billed as completed requests. If BQAA ingests traces from behind a translator, this is a correctness floor on everything downstream.
  3. A metric that ignores when a monitor fires cannot tell an alarm from an autopsy. PREWARN (arXiv 2611.16803) shows response-level AUROC rating a rule that reads only the response length at 0.9988–0.9995 — near-perfect — while that same rule's early-warning rate is exactly 0.000, because its single flag lands on the last token after the budget is already spent. Two scorers with identical AUROC can range from Warn256 0.000 to 0.627. Selecting a monitor by validation AUROC picks one whose test warning coverage is 3.4× lower than the alternative.

1. Amazon Bedrock AgentCore runtime V2 — snapshot/restore session start, build hooks, and a platform-owned split of agent latency into Latency vs OverheadLatency

AWS ML blog, 2026-11-13 (RSS pubDate 2026-11-13T22:02:39Z; on-page "13 NOV 2026") — in-window. https://aws.amazon.com/blogs/machine-learning/architecture-patterns-for-fast-session-startup-on-amazon-bedrock-agentcore-runtime/

AgentCore runtime with platformVersion set to "V2" changes how sessions start: instead of initialising your container per session, it starts the container once in a fresh microVM, waits for the first healthy GET /ping (within 120 seconds), clears the OS file cache, freezes the microVM and stores memory+disk as a snapshot. Each new session restores that snapshot, so the process resumes with its imports, objects and clients already in place. Consequence AWS states explicitly: every create or update now takes a few minutes while the snapshot is built, and init work moves off the request path entirely — "on V2, do the opposite" of the usual lazy-import cold-start advice, because work deferred to the handler is paid by every new session.

The analytics-relevant part is the measurement contract. AgentCore publishes both halves of request latency as CloudWatch metrics in the AWS/Bedrock-AgentCore namespace:

What you wantHow to get it
TTFB (time to first byte)Latency
Platform overhead (microVM start + snapshot restore)OverheadLatency
Your code's timeLatency − OverheadLatency

Init time is deliberately not in either metric on V2 — it runs once at snapshot build, so it adds to how long a create/update takes to reach READY, not to request latency; you log it yourself before app.run().

AWS also ships interpretation guidance that reads like an analytics spec: report P90/P99 or a trimmed mean such as TM90 (average of the fastest 90%, dropping the slow tail) because "a plain average hides the slow requests"; OverheadLatency covers requests to already-running sessions as well as new ones, so its distribution depends on your new-session mix and you must "compare runs with a similar mix"; and test at the production rate of new sessions, not a handful after a deploy. Diagnostic split: high OverheadLatency on new sessions ⇒ time is in session start; your code's time much higher on the first request than the second in the same session ⇒ work that belongs in init is running in the handler (use custom spans in AgentCore Observability around tool setup, file loads and late imports to find it).

New capability enabling this: build hooks, configured via hooksConfiguration on create/update. AgentCore POSTs to an HTTP endpoint in your container twice per build — once before the snapshot (load into memory, becomes part of every session) and once after a test restore (read the files sessions will need, shaping what restored sessions fetch first). The X-Amzn-Bedrock-AgentCore-Runtime-Warmup-Type header distinguishes them (memory vs disk); the two calls share one 120-second budget, and a non-2xx, failed connection or timeout fails the create/update with no retry. Hooks are V2-only. Port must be 8000–12000 and unreserved; path must not collide with POST /invocations or GET /ping. UpdateAgentRuntime replaces the whole hook config, so it must be re-sent on every update.

Stated trade-off: moving work into init shortens the handler but anything held in memory makes the snapshot larger, and you pay for that held memory in every session — so measure end-to-end session start before and after, "so you know you've reduced latency and not only moved it from the handler to the restore." Reference card in the post: hold large first-request files (model weights, CLI, browser binary) in memory or prime them with a build hook; mount S3 Files/EFS through an access point for selectively-read reference data (requires VPC mode); copy toolchains like tsc to /dev/shm or a ramfs mount during init; ship compiled bytecode (UV_COMPILE_BYTECODE=1 or pip install --compile) because uv pip install does not compile by default.

Four patterns are given, escalating: switch to V2 and do all init before app.run() (~2s session start acceptable); add a build hook for large files/CLI/browser; pre-warm by starting the session in the background on user engagement for sub-second chat/voice; the post notes "for chat and voice experiences even 2 seconds is too slow."

Why it ranks: a material product capability on a GA managed agent runtime — a new session-start architecture, a new hooks API surface, and a platform-owned latency-attribution metric pair with published interpretation rules. No existing catalog card covers AgentCore runtime session start, platformVersion, cold start or build hooks (grep: 0 hits each; the two AgentCore cards are agentcore-evaluations-any-framework and bedrock-agentcore-unified, both about telemetry/evals, not runtime startup). Directly load-bearing for BQAA: platform-vs-code latency attribution is exactly the split an agent-analytics product has to make, and here the platform is publishing its own side of it.

1. isloss — a deterministic oracle proving the translation layer silently rewrites conversations: 127/685 (18.5%) of completed translations pass static target checks while losing avoidable prompt/role/tool information (arXiv:2611.15543)

Testing Conversation Preservation Across LLM APIs: A Rule-Based Oracle for Detecting Silent Information Loss — Xin Liu, Xu Han, Yuxin Wang, Haoran Song, Mingjian Zhao, Lei Wang (Griffith University + independent). cs.SE. Submitted 11 Nov 2026. Full PDF read — 55 pages / 3,247 lines of pdftotext -layout output, read in chunks covering §1–§9 (intro, background + extended case, the ConvIR/rules method, checker validation, study design, empirical results §6.1–6.5, discussion, threats to validity §7.2, related work, conclusion, Broader Impact) plus appendices A.1–A.3 (rule catalogue, spec-gap table, batch numbering), B.1–B.6 (subjects/provenance, sensitivity, replies, persistence, gateways/two-hop/first-party) and C (evaluation protocol + audit record, Tables 27–30).

Method. isloss maps source and translated payloads into a shared intermediate representation, ConvIR — an ordered event list (speaker, content type, payload, flags such as is_error) plus explicitly-set generation controls (tool_choice, declared tool names, sampling params, token limits) — then applies 27 deterministic preservation rules: 13 T1 rules (S01–S13, potential defects), 6 T2 records (D01–D06, separately-reported degradations and informational notes), 8 T3 rules (R01–R08, benign representation changes). No model call and no reference translation. It distinguishes avoidable loss (target API documents a native field that could have preserved it) from target-limited degradation, and records separately whether the translator warned the caller. A finding is silent when no warning is emitted, and a primary finding requires all of: passes static target contract, ≥1 silent T1 finding, and a finding that is both avoidable and touches prompt/role/tool information.

Headline result (Table 2 funnel, §4.1, §6.1). 714 translation attempts across 51 statically-valid source shapes × 14 source-to-target paths; 29 explicit rejections leave 685 completed translations. Funnel: 489 cells with ≥1 potential information-changing difference → 485 after excluding four known permitted-change classes → 467 (68.18%) with ≥1 T1 finding → 333 (48.61%) passing the static target contract → 206 with an avoidable finding → 127 (18.54%) primary. Cluster-bootstrap 95% CI 15.01–22.06%. Subjects (Table 14, pinned): LiteLLM 1.103.1/1.103.2 (drop_params=False), Vercel AI SDK v5 (5.0.271) and v7 (7.0.126), LLM-Rosetta 0.13.0, @musistudio/llms 1.0.53, claude-code-proxy (7ea4177) — 6 configurations, 5 codebases.

Checker accuracy (Table 3, Table 12). Primary held-out evaluation, six blind specification-based batches authored after the rules were frozen: 95/125 activated faults detected (76.0%, Wilson 67.8–82.6%), 2/100 allowed changes falsely flagged (2.0%, CI 0.6–7.0%), J = 0.740. Extended held-out (10 batches): 160/220 (72.7%), 5/170 (2.9%). Program mutants: 81.6–84.3% of activated mutants killed. Public bugs: 45/57 reproduced (78.9%), including 10/14 encodable bugs opened in the 50 hours after the rules froze (prospective). Rule coverage of 125 publicly-reported issues from 12 trackers: 99 (79.2%). Reproducibility: 4,998 test executions, fresh checkout reproduces byte-for-byte in 11 seconds. Reference-free, isloss has the highest observed J among tested judges (Gemini judges J = 0.516 and 0.704; open-weight judges near 0). Given a reference translation, normalised diff (J = 0.842) and two Gemini judges (0.804, 0.840) beat it — the paper states this plainly; obtaining a reference is precisely the hard part for unseen translators.

Human validation (§4.3, Table 12). 54 request-side candidates from 18 mechanisms, four raters: 31 confirmed defects, 11 accepted representation changes, 12 disputed. Among the 28 avoidable candidates: 23 confirmed, 1 accepted, 4 disputed — 23/24 (95.8%, CI 79.8–99.3%) among agreed classifications, 23/28 (82.1%) retaining disputes. Among unavoidable candidates only 6/16 (37.5%) confirmed. A 48-item bridging sample scored by all four raters shows a 37.50-percentage-point rater-pair gap on unavoidable-loss items versus 6.25 points on avoidable items — the paper's own justification for reporting avoidable findings separately rather than treating every loss as an equally clear defect.

Behavioural consequence (§6.2, Fig. 6). 10 of 18 catalogued mechanisms tested live across six models (two Gemini, claude-sonnet-4-6, claude-haiku-5-5, Llama-3.1-8B, Qwen2.5-7B): nine of ten change at least one measured outcome, covering 116 of the 127 primary cells (91.3% mechanism coverage — mechanism-level, not per-cell validation). Sharpest numbers: dropping the tool-result is_error flag takes compliance 30/30 → 0/30 on both Gemini models; dropping functionResponse.id takes parallel tool-call attribution 30/30 → 0/30 (p_Holm = 0.0039); a translator-induced max_tokens rise 100 → 1,124 takes compliance with the caller's own 100-token limit 30/30 → 0/30 on both Claude models; dropping top_p: 0.05 raises mean distinct outputs per scenario 3.8 → 4.8 (p = 0.0156). Honest negative control: a 100-item GSM8K run (700 calls) on gemini-3.5-flash-lite shows no statistically detectable accuracy drop (p ≥ 0.2500) — the paper states the effects are task-dependent and not every translation change degrades every task. Two predictions missed and are disclosed as such: removing thinking blocks produced no predicted effect, and the claude-sonnet-4-6 dropped-prohibition probe fell short (refusals 10/30 → 0/30 against a pre-specified threshold).

Reverse direction and SDKs (§6.3, Fig. 7). Across 1,115 judged reply cells from seven translators, 391 (35.1%) meaning changes, 278 avoidable. Across 558 translated reply streams, 203 (36.4%) raise an uncaught exception or silently corrupt the assembled message in at least one official OpenAI SDK (Python 170/558 = 30.5%, Node 182/558 = 32.6%, overlapping not additive); 199 of the 203 (98.0%) are avoidable.

Persistence and upstream (§6.4, Table 24). Across 50 consecutive LiteLLM releases, every release changes the meaning of at least 31 of the 51 shapes when translating to OpenAI. In a ten-translator / 170-shape census, 2,630 of 2,745 flagged cells (95.8%) remain flagged in later (11 October) source snapshots. 26 issues filed across 12 repositories: 7 fixed and independently re-verified, 1 partly fixed, 1 closed without reply, 17 open as of 15 October 2026.

Gateways, first-party compatibility, real agent traffic (§6.5, Tables 25–26). Bifrost and new-api produce T1 changes in 187/204 judged cells (91.7%) on the 51-shape suite and 978/1,020 (95.9%) on the 170-shape corpus; Portkey 1.15.2 refuses every tested Anthropic→OpenAI/Gemini cell (HTTP 500), i.e. fails closed. Two-hop library chains (16-chain subset without AI SDK, statically-valid shapes): 660/689 (95.79%) end-to-end T1, of which 287/689 (41.65%) are two-hop-only — errors compound through chained translators. Operational probes found Bifrost routing bare model names to a different provider after upstream 400/429/529 while returning HTTP 200, forwarding client authentication headers during cross-provider fallback, and closing mid-stream upstream errors with HTTP 200. Google's hosted OpenAI-compatible Gemini endpoint passes 10/11 behavioural probes, retaining only the last of multiple top-level system messages; unnamed reasoning tokens consume 98.0% of output tokens across 45 calls and count against max_tokens; 5/5 tool round-trips are refused without thought signatures; streamed tool calls emit finish_reason:"stop" rather than "tool_calls". Recorded CLI coding-agent traffic (Claude Code, Codex, gemini-cli, Crush, Aider; 14 shapes, 7 statically valid): 4/98 primary cells (4.1%), 13/196 (6.6%) across all shapes, 23/98 (23.5%) counting all avoidable meaning changes; 9 of 12 closed-loop sessions contain at least one meaning change. CLIProxyAPI strips gemini-cli's system prompt in 4/4 cases and disables Gemini safety filters without logging.

The separate mid-conversation system-instruction case (§2.1, Fig. 2 — explicitly not part of the 18.5%). A harness inserts "run_cmd is DISABLED from now on; refuse any further shell use." across 2 insertion positions × 11 paraphrases (22 requests, all passing static source checks); 1,139/1,530 cells (74.4%) change meaning. Six translator configurations split into four outcomes: AI SDK v5 and LLM-Rosetta preserve position and role; @musistudio/llms silently deletes; LiteLLM retains the text but demotes system → user and adds an operator note; AI SDK v7 and claude-code-proxy reject with explicit errors (fail closed). Deletion takes refusals 11/11 → 0/11 on gemini-3.5-flash-lite at both positions, same pattern on gemini-3.8-flash and Qwen2.5. Demotion is model- and placement-dependent: refusals survive in 5 of 6 tested model–placement pairs but gemini-3.8-flash stops refusing when the instruction is placed last. Note the conservative counting choice: system→user demotion is recorded as T2, excluded from the primary count even where the target could have preserved the system role — including it raises the headline to 134/685 (19.6%).

Stated limitations (§7.2 — read these before quoting numbers). isloss checks only properties represented in ConvIR and cannot establish semantic or behavioural equivalence. The 18.5% is a rate within a deliberately constructed synthetic suite, explicitly "not an estimate of the prevalence of information loss in real-world traffic" — sensitivity analysis spans 12.9–19.6% under alternative validity rules and 16.5–25.7% under alternative counting conventions, and changing LiteLLM's capture point from the pre-serialisation dictionary to the serialised HTTP body moves 127/685 to 132/685 (19.3%). Findings are specific to the chosen capture points; provider-side rewriting downstream is invisible. 277/685 OpenAI-bound cells were never sent to a live endpoint and no GPT model appears in the live experiments. Only 13 of 51 statically-valid shapes are accepted live by claude-sonnet-4-6 (and 8 by claude-opus-4-8), so strata 1/2a/2b/2c/3 answer different questions and are not successive filters of one population. Commercial hosted gateways and the Anthropic/OpenAI compatibility layers were not inspected. isloss is evaluated as an offline research checker; CI integration is future work. §7.1 also states the paper has not measured the effect on published benchmark scores or leaderboard rankings.

Why it ranks: this is a measurement-integrity result at the exact boundary BQAA ingests through. The paper's own framing for evaluation is the transferable claim: "model and agent evaluations should verify the payloads actually delivered to models, rather than relying solely on schema validation or successful API responses," and translation is named as "a potential confounding factor in model evaluation" for any benchmark or agent framework routing through a shared translator (τ-bench and BFCL are named). Three findings land directly on agent analytics: (a) an HTTP 200 is not evidence the conversation survived, nor that the request completed — mid-stream errors closed 200 and billed as completed is a cost-attribution defect, not just a correctness one; (b) cross-provider fallback that is visible only in response headers means your per-model cost/quality aggregation can be attributed to the wrong model; (c) Latency-style platform metrics and trace spans collected behind a translator describe a conversation the model never received.

  • PREWARN — Detection Is Not Early Warning: Evaluating Token-Level Alarms on Language Model Failures (arXiv:2611.16803) — Marco De Negri, Luca Sartori, Lorenzo Baggi, Moritz Reihs, Eduard Frank Ďurech, Mennatallah El-Assady, Valentina Pyatkin, Anna Hedström (ETH Zurich, ETH AI Center, Solaris Research). cs.LG. Submitted 12 Nov 2026; NeurIPS 2026 Workshop: Interpretability as a Science. Full PDF read — 30 pages / 1,774 lines, read in chunks covering §1–§6 (intro, preliminaries, the protocol, experiments Q1–Q4, conclusion, limitations) plus appendices A.4–A.8 (training-strategy table, same-AUROC transforms, baseline definitions and selection grids, judge-labelled vs human-verified splits, β = 1%/10%). Reserve promotion.
    Why I read it fully but am not ranking it as a second Academy card: the contribution is a rigorous, well-instrumented evaluation protocol plus a single case study on one failure mode (repetitive degeneration) in three open-weight models — the authors themselves scope it that way ("it applies to any failure with an onset, such as harmful content or hallucinated entities, which we leave to future work"), and their §6 limitations concede the lead times depend on the onset convention, that on Apertus and Llama the onset usually arrives after a healthy response would have ended so the probes may partly read response length, and that the training strategy and selection rule were tuned on degeneration alone. It is a measurement-methodology correction rather than a product-level or agent-analytics capability, so it belongs beside the catalog's existing eval-methodology thread rather than as a headline rank.
    The substance, since it is directly useful to BQAA's alerting story: PREWARN separates three tasks a token-level monitor can serve — response classification (one verdict on the finished response), failure detection (alarm once the failure is under way, t ≥ o(r)), and early warning (alarm in the window o(r) − W ≤ t < o(r), W = 256) — and notes only the third leaves time to stop, steer or resample. Three steps: calibrate threshold τ on validation to a chosen error budget β, run the monitor, score alarms against the annotated onset. Metrics: Warn256 (warning-window coverage), Early (share of alarming responses whose first alarm precedes onset), Lead (median first-alarm-minus-onset, negative = warning), Post, Detection, FA, Pre, plus a random-alarms chance reference calibrated to the same budget.
    The damning table (Table 1, β = 5%, human-verified in-domain test split): a token-cap rule that reads only the response length reaches AUROC 0.9990 (Apertus), 0.9988 (Llama), 0.9995 (Mistral) — the highest AUROC on two of three models — with Detection 1.00, but Warn256 0.000, Early 0.000 and Lead +3276 / +2958 / +3688 tokens, because its only flag is the last token of a capped response, after the budget is spent. Every scorer except random alarms and Llama's repeated-n-gram rule clears AUROC 0.95; AUROC stays above 0.96 at every layer and best accuracy varies under 3%, while Warn256 is 7× higher at the best layer than the worst (Fig. 2d). Table 4 constructs two transforms of a real probe that preserve its AUROC exactly while moving Warn256 from 0.000 (argmax-only) to 0.627–0.671 (shuffled) and Early from 0.01–0.02 to 0.95–0.96 — a response-level metric therefore cannot distinguish a monitor that never warns from one that warns before almost every failure. Table 5: ranking 27 probe strategies by validation AUROC reproduces itself on test (Kendall's τ = 0.79) but predicts test Warn256 only weakly (τ = 0.33; best accuracy 0.36), whereas validation Warn256 predicts it at τ = 0.94 — so selecting by AUROC picks a probe whose test warning coverage is 3.4× lower.
    Findings: frozen linear probes on activations (no extra forward pass) warn before onset on most loops of Apertus (Early 0.658, Lead −172 tokens) and Llama (0.594, −137) but not Mistral (0.262, +108) where detection is still 0.99 — "on M ISTRAL the probes are useful for failure detection but not for early warning." Rank-16 LoRA adapters below the probe more than double Warn256 on every model (Apertus 0.186 → 0.577; Llama 0.087 → 0.488) but barely raise Early (0.658 → 0.716; 0.594 → 0.655), because Early counts a response once at its first alarm — and much of the added coverage lands long before the window (Pre rises 0.063 → 0.399), which on Llama may partly track response length. No untrained baseline warns much more often than random alarms (chance Early 0.246 / 0.340 / 0.167); windowed seq-rep-n and rep/ℓ cover more of the window but select 1,024–4,096-token windows, flag much of the pre-window text too, and fire well after onset. On held-out sources the frozen probes degrade hard (Llama Early → 0.201, Mistral → 0.115, median alarm after onset) while adapted probes hold up better. Data: 3,630 prompts × 10 responses, seven sources, temperature 0.7 / top-p 0.9 / Tmax 4096; labels from an LLM judge that quotes where the loop begins, with every capped response in both test splits hand-reviewed — reviewers confirm 97–99% of the judge's degenerate labels and keep its onset for only 74–92% of confirmed responses. Probes released with thresholds calibrated at 1%, 5% and 10%.
    Take-away for the catalog's eval thread: an alerting metric that is not aligned to the onset cannot distinguish prevention from post-mortem, and the standard response-level metric actively mis-ranks candidates. Six-week EV
