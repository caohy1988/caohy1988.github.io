What changes when Jev is on:

  • FaithfulnessMetric and other QAG metrics: the LLM still extracts claims; Jev decides one Noul (P(yes)) per claim.
  • GEval: Noul in strict mode, Score when a rubric is provided.
  • DAGMetric: Noul for binary nodes, Choice for non-binary nodes.
  • Classifiers: Choice over a closed label set.
  • Score math is unchanged; faithfulness is still truthful claims / total claims.
  • Vendor-stated economics (not verified): $0.042 per million input tokens with no output charge; ~100 ms per query; a metric's independent questions batched into one request.
  • Opt-in and experimental: deepeval set-mode experimental plus typesafe-sdk plus TYPESAFE_API_KEY. In experimental mode a missing SDK or key fails loudly instead of falling back to the LLM.

The same cut, via #3332, adds categorical LLM-as-a-judge classifiers that return one label from a closed set. Shipped files include abstention, clarification, data_leakage, escalation, forbidden_commitments and the release-note example RefusalClassifier → refused.

According to the shipped docs, you define bounded questions (typed Noul / Score / Choice), Jev answers each with calibrated probabilities, and a fixed equation produces the score: "No LLM judges the conversation"; an LLM only optionally writes the reason.

TL;DR for BQAA: four independent eval platforms now share the same separation: generate with an LLM, decide with a typed model. LangSmith and Phoenix JS at 0034, Opik at 0634, and now DeepEval. DeepEval's version is the most explicit about where the boundary falls: claim extraction stays with the LLM, the per-claim verdict goes to Jev.

For a trace warehouse this means eval results increasingly arrive as typed decisions with probabilities (Noul P(yes), Choice distributions, Score) rather than free-text judge output plus a parsed number. The eval-result schema should keep the probability vector and the question text, not just the thresholded label.

"Fails loudly, never falls back" is also the right provenance rule: a result row should record which decider produced it.

1. NEW rank: arXiv:2609.20758 — Prediction-Powered Smoothing and Validation for Disaggregated AI Evaluation (Kawano, Li, Parker — UC Santa Cruz Statistics; v1, Sep 17 2026; 30 pp)

What it is: evaluation treated as finite-population survey sampling. It estimates quality per segment (conversation type × model, or task type) from LLM-judge scores on everything plus a small human-graded probability sample, with calibrated intervals.

  • It reframes PPI as the survey difference estimator and PPI++ as GREG.
  • PP-S adds a Bayesian Fay–Herriot small-area model over per-segment GREG estimates, borrowing strength via segment-level auxiliary means such as the mean judge score.
  • PP-TS also borrows along a nested taxonomy.
  • DB-CV is a debiased design-based cross-validation score for choosing between direct and smoothed estimators.

Evidence:

  • Open LLM Leaderboard slice (9,324 questions, 34 task types, grading phi-4; Table 2, 10% sample): PP-TS is best under all three auxiliaries, with RMSE 0.082 → 0.059 against the Horvitz–Thompson (HT) estimator using historical difficulty. Figure 3 shows most of the gain comes from the segment-level covariate; shrinkage alone gives only 0.082 → 0.080.
  • PRISM (68,371 responses rated by 1,500 participants, 63 segments = 21 LLMs × 3 conversation types; judge gpt-5-nano, costing about $6 to score everything; Table 3): PP-S with judge plus content covariates gets RMSE 1.527 versus HT 2.505. Interval width in the sparsest quartile falls from ~15 to ~7 points (Figure 4).
  • Coverage: 0.93–0.96 throughout.
  • DB-CV (Table 4) estimates true error at 1.07× versus 2.59–4.00× for alternatives.
  • Code: https://github.com/sho-kawano/disagg-ai-eval

Honest caveats (from the full read):

  • The abstract's "deployed agent traffic" is the public PRISM dataset treated as traffic: user-rated chat, no tools, no multi-step agents. It is untested on real agent traces.
  • With the judge alone as auxiliary, gains are modest (RMSE 2.418–2.253 vs 2.505). The large win needs content covariates.
  • The "perfect oracle ordering" is one replicate; over 100 repeats τ = 0.89.
  • No effective-sample-size figure is reported. My rough conversion from the RMSE ratios is about 1.9× (benchmark) to 2.7× (PRISM).
  • The method requires a probability sample. Sec 2 shows that flagged or complaint-driven samples bias the estimates, and PPI does not fix that.

TL;DR for BQAA: this is close to the statistical backbone BQAA's LLM-as-judge-over-traces story is missing: judge every trace, have humans grade a known-design stratified sample, and report per-segment (agent × tool × intent) quality with defensible intervals. Three design rules follow directly:

  1. Sample for human review by design, never from flagged traces, and record inclusion probabilities in the table.
  2. Use segment-level judge means as covariates, not only per-row judge scores.
  3. Use the agent/tool/intent hierarchy as the smoothing taxonomy.

Pairs naturally with the Jev wave (Industry rank 2): typed judge probabilities make better auxiliaries than parsed free-text scores.

2. NEW rank (qualified): arXiv:2609.24115 — EDGEGEN: Improving Tool-Calling Agents Beyond Happy Paths with Synthetic Edge Case Generation (Abichandani et al. — SAP; v1, Sep 21 2026; 23 pp)

What it is: a five-stage pipeline that generates rule-violating, database-grounded tasks for tool-calling agents:

  1. an LLM extracts atomic compliance rules from the policy document (top 5, so ≤32 rule subsets);
  2. tool-graph workflows are sampled (single / chain / DAG);
  3. rule subsets to violate are enumerated, with contradictions filtered out;
  4. a SQL agent finds the database rows that make each scenario real;
  5. the task is written with natural-language assertions and checked for existence and feasibility.

The outputs drive LoRA fine-tuning (successful gpt-5.4 demonstrations) and Meta-Harness-style harness optimization. Evaluation uses τ²-bench airline and retail (10 test tasks each) and ToolSandbox (15), with gpt-4.1 as user simulator and judge.

Evidence (full read):

  • Headline fine-tuning gain: "+2% to +42%" is relative mean-progress gain over the untuned base model on airline (Table 1): Qwen2.5-3b 0.258 → 0.366; ~flat for Qwen3.5-35b. ToolSandbox: +10.9% to +23.4%.
  • Headline harness gain: "+10% / +30%" comes from one model (Gemma-4-e4b, airline; Table 2): 0.561 versus a human-curated harness at 0.508 and a base harness at 0.430, using fewer tokens (85k vs 121k).
  • The optimized harness converges on a discover → verify → confirm → write protocol rather than a hard-coded checklist (App A.5).

Honest caveats: why this is qualified.

  • Test sets are n = 10–15. There are no significance tests.
  • With gpt-5.4 the EdgeGen harness loses to the human-curated one (0.798 vs 0.831). On ToolSandbox with gpt-4o-mini it also trails (0.923 vs 0.931).
  • In the scaling study (Table 14) harness gains mostly vanish (n = 30/60 falls below base).
  • More violations do not mean more gain (Table 3).
  • "Fully automated" still depends on gpt-5.4 demonstrations and a non-public database generator. Code and data are claimed (Apache 2.0) but no URL is given.
  • The paper's own human audit (Table 5) found only 6/10 airline and 4/10 ToolSandbox judge-"successful" runs actually correct.

TL;DR for BQAA: carded for the method pattern and the audit number, not the headline gains.

  1. Policy document plus live database → rule-violation test cases is a reusable recipe for generating eval sets from an agent's own spec. It is the edge-case complement to judging happy-path traces.
  2. The 40–60% false-success rate of the LLM judge in the paper's own audit is the strongest datum in the paper. It is independent evidence for pairing judge labels with a designed human sample, which is exactly Academy rank 1's method.
