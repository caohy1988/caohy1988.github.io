Industry

1. OTel GenAI #490: external content references get a receipt, not just a pointer (Sep 1, 10:44 PM PT)

The PR was opened by dev404ai at 10:44 PM PT, roughly an hour after the 2134 sweep. It is that account's first PR in any OpenTelemetry repo. It is not a draft. 27 files, about 1,400 lines added, and it links "Fixes #45."

The history matters. Issue #45 was filed in September 2025 by aabmass, a Google maintainer on the Python side, after upstream semantic-conventions #2179 recommended uploading captured content to external storage but "is not normative about where to put the references." The same maintainer opened upstream #2750 the same week with the three _ref attributes. In late September 2025 a spec maintainer converted it to draft with "would like to have some end-to-end impl to proceed." It went stale in November and was auto-closed on May 5, 2026 because the gen-ai area no longer had an active SIG in that repo. The gap has been open for a year with the shape agreed and nobody shipping the proof.

What #490 adds, read from the model diff:

  • Three string attributes, gen_ai.system_instructions_ref, gen_ai.input.messages_ref, gen_ai.output.messages_ref, opt-in on the same span content group as the inline values. Each note says the reference "does not indicate whether storing the content succeeded or whether the content remains available," with a warning about sensitive storage paths and high cardinality. Example value is an s3:// path.
  • A new opt-in event, gen_ai.content.storage.result. Exactly one _ref MUST be set. A required gen_ai.content.storage.status enum with three members: stored ("the uploader reports that storing the content completed successfully"), failed ("attempted to store the content and failed"), and dropped ("did not attempt to store the content"). error.type is conditionally required when failed. The event "MUST NOT contain the referenced content." Severity INFO for stored, WARN for failed or dropped.
  • A reference scenario under reference/scenarios/opentelemetry-util-genai/ that uses the library's real UploadCompletionHook, producing all three references and all three statuses with trace correlation.

The motivation section is the part worth quoting: "Current asynchronous implementations create that reference before the upload finishes. A full queue or background write failure can therefore leave a successful operation pointing to content that was never stored." The stated user journey is "incident investigation and evaluation evidence retrieval." Service logs were rejected because "they are not a portable contract that consumers can correlate with a trace." Synchronous upload was rejected for latency and failure coupling.

Two things to weigh. First, no maintainer has touched it; the only reviews are two Copilot passes, one of which flags that the scenario wraps the upload hook in a span labelled as an inference call with no model call behind it, and that the same util library's hook also uploads tool definitions, which the PR leaves without a _ref. Second, the July comment on #45 from the TraceLake author, who ingests OTLP GenAI telemetry into Iceberg tables and offloads large content to object storage next to the table, asked for a structured reference with uri, content_hash, media_type, and size. #490 ships a bare string. The hash and size fields are what an analytics backend would actually want, and they are not here.

The wrong belief to kill: a reference on the span is a receipt. This PR's whole design is that locator creation and delivery outcome are separate signals, because the async uploader can lose the content after the span has already claimed it.

TL;DR for BQAA. Redaction as a forensics statement now has an outside shape to cite: a row says where the content went, and a separate terminal event says whether it arrived, with dropped distinct from failed. If the event table carries offloaded or redacted content, it should carry a ref column plus a three-valued status rather than a null, and the schema should leave room for hash and size, which the warehouse-native commenter on #45 wanted and #490 omits. Watch for the first maintainer comment; a spec maintainer killed the 2025 version for lacking exactly the end-to-end proof this one brings.
