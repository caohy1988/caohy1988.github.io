NEW I1 — crewAI 1.15.23: crewai eval grades the last traced run; task spans record declared vs produced output; agent spans carry prompt and answer with truncation markers

Timestamps.

  • GitHub release 2026-09-28T21:14:32Z (tag created 21:14:28Z); PyPI crewai 1.15.23 at 21:15:33Z.
  • Both fall inside this brief's window, which starts Mon 19:34Z.
  • The "clock trap" DSH 2332 flagged applies to its own narrower window. The only upload in that window was the nightly 1.15.23.dev20260929 (06:18Z), which is not a release.
  • This is the first crewAI card: the catalog has 0 items for crewAI.

What the release adds (compare 1.15.22...1.15.23, 26 commits; PR bodies):

  • crewai eval (#7649, #7648, #7701, #7707).
  • It evaluates the project's last traced run, or --run EXECUTION_ID, through AMP (POST /crewai_plus/api/v1/tracing/evaluations).
  • It prints the report URL, waits, then prints "the goal gate and the four grades". The #7765 sample shows goal 5/5 tasks 5/5 agents 3/5 tools 5/5.
  • Where the run id comes from. After a traced run, crewAI now writes .crewai/last_run.json with the execution id, start/end times, tier and AMP URL.
    • It does so only when every span export succeeded. Partial or truncated exports are not recorded.
    • The write is atomic and never fails the run.
  • The command lives in a new experimental CLI package, so its output and flags "may change between releases without the deprecation cycle".
  • The PR says AMP owns the grading and access rules.
  • Richer spans (#7597):
  • execute task spans:
    • crewai.task.output_format (json/pydantic/raw).
    • On completion, crewai.task.output_pydantic_produced and crewai.task.output_json_produced. So "a declared-pydantic task that fell back to raw text is told apart from one that parsed".
  • execute agent spans carry gen_ai.input.messages (the task prompt) and gen_ai.output.messages (the answer).
    • These are capped by CREWAI_OTEL_MAX_ATTR_BYTES (default 32 KiB).
    • Over the cap, <attr>.truncated and <attr>.original_size_bytes are set, "so a cut is never mistaken for a short text".
    • There is no content-capture switch; redaction is left to the caller.
  • call tool spans carry crewai.tool.from_cache.
  • Consent and TUI (#7765, merged Sep 28 18:28Z):
  • Turning tracing on (CREWAI_TRACING_ENABLED or tracing=True) now counts as permission to upload. Anonymous runs where nobody can answer (CI, containers) are still not uploaded.
  • An Evaluate button in the run TUI runs the evaluation in place.
  • A freshly finished run waits up to two minutes for its spans. One end-to-end attempt was refused as "No spans recorded" and read fine minutes later.
  • Also in the release: it retries throttled provider calls (#7677) and adds native Gemini 3.8 Flash.

Caveats that ship with 1.15.23 (verified on GitHub at 07:50Z):

  • from_cache misreports on the default executor. #7776 is still open.
  • Per its body, both native tool paths of the default AgentExecutor compute the flag and then leave it out of the event.
  • On a cache hit the span therefore says crewai.tool.from_cache=False.
  • The Mon 0634 brief flagged this. Nothing in 1.15.23 fixes it.
  • The exit code doesn't reflect the gate. In 1.15.23, crewai eval exits 1 only when the evaluation itself fails (#7649), so a FAILED gate exits 0.
  • #7806 makes it exit 1 unless the gate PASSED. It merged 06:17Z Sep 29 and is on main only.
  • Main is 3 commits ahead of the tag, and the fix is only in the .dev20260929 nightly.
  • crewAI's own adoption metric went dark. #7810 (main, 07:40Z) says the tracing:*_sent usage events "are never emitted" since 1.15.22.
  • The PR puts it as: "Telemetry shows 3–4% of projects reporting tracing on 1.15.18–1.15.21 and 0% on 1.15.22."
  • The zero was a gated-off emitter, not a real drop.

TL;DR for BQAA:

  • Silent structured-output fallback becomes a GROUP BY. For crewAI, compare declared vs produced output per task.
  • Truncation. Store *.truncated and *.original_size_bytes next to any captured text, so short answers and cut answers aren't conflated.
  • Cache hits. Don't compute crewAI cache-hit rates from crewai.tool.from_cache on 1.15.23 (default executor).
  • Eval gates. Store the verdict, not the process exit code.
  • Last-run pointers. Only complete exports get recorded, which is a good rule for any "evaluate the last run" pointer.

  • Manual spans, datasets, feedback and separate OTel exporters are out of scope.
  • Usage capture:
  • #800 captures Anthropic usage and refusal metadata.

NEW A1 — TraceDance: An Automated System for Building Agent Behavior Benchmarks from Real-World Agent Deployment Traces (arXiv 2609.33295, ByteDance with UIC, cs.AI, v1 27 Sep 2026)

Full PDF read: §1–6 and Appendices A–F, 34 pages. Code at ZhishanQ/TraceDance. The traces are not released.

What it does (§3, Fig. 1, App. A). A developer names an undesirable behavior in natural language. TraceDance builds a benchmark of recorded contexts cut just before a deployed agent did that thing.

  • Three frames:
  • action cuts before the action;
  • failure keeps the observed failure but not the response;
  • claim keeps the work but not the claim.
  • Grading. An evaluated LLM writes only the next turn. A 3-judge panel (GPT-5.6-Sol, Gemini-3.5-Flash, Claude Opus 4.8) grades it against a behavior-specific 0–5 rubric; a mean of 4 or more passes.
  • No replay needed. There is no reference answer and no environment replay, so traces from private repos and MCP servers stay usable.
  • Cut rules:
  • Source-model reasoning blocks are removed.
  • Cuts at harness-forced turns, such as compaction-summary requests, are excluded.
  • Anchor-and-Confirm.
  • Programmable anchors scan structured traces on CPUs, using tool errors, call arguments, event order and keywords.
  • A Flash LLM (DeepSeek-V4-Flash) only confirms the retrieved candidates.
  • Per successful query, that is 128,297 session scans → 706 candidates → 40.4 instances, costing 552 LLM calls and 25.1M tokens on average (Fig. 3b, Table 23).

Data (§4.1, Table 1, App. B.1).

  • Sessions. 252,557 sessions over six weeks: 75,076 from Claude Code and 177,481 from OpenClaw, mostly driven by Doubao Seed 2.0 models.
  • Held-out split. 10,000 sessions per harness were reserved for behavior discovery.
  • Input source vs role. In the traces, "messages with the user role are not necessarily written by users".
  • Only 74.8% of Claude Code input turns and 30.8% of OpenClaw input turns were user-written.
  • The rest are harness-injected reminders, skills and heartbeats.

Construction results (§5.2–5.3, Table 21).

  • Queries. It built benchmarks for 102 of 107 build-target queries (95.3%) and correctly rejected all 32 rejection-target queries. That produced 107 benchmarks with 4,125 instances.
  • Instance validity. Both annotators confirm the requested behavior in 84 of 100 sampled instances. Rubrics were rated 4/5 or better in 90% of them.
  • Judge vs humans (App. C.2, Table 14):
  • Pass/fail agreement is 81.0%. But humans passed only 16.7% of responses, so an always-fail labeler would agree 83.3% of the time.
  • The chance-corrected κ is 0.40, against 0.31 between the two annotators.
  • The panel is lenient (mean score 2.46 vs 1.68 for humans), with 44.7% precision and 60.7% recall on human passes.
  • GPT-5.6-Sol shows a +0.22 self-preference (Table 15).

What the benchmarks show (§5.4, Table 2, Figs. 4–5, Tables 9 and 26).

  • Overall. Nine LLMs pass 26.7% on average. Claude Opus 4.8 is highest at 33.5% (ranked first in 99.9% of resamples); Qwen3.7-Max is lowest at 22.9%.
  • By what the rubric requires:
  • Valid call: 67.9%.
  • Handle failure: 33.5%.
  • Honest claim: 28.9%.
  • Check first: 8.1%.
  • Worst families:
  • Failure-log inspection 0.6% (read the failed job's log before retrying).
  • Commit hygiene 0.9%.
  • Delivery recovery 2.4%.
  • Secret protection 6.9%.
  • Planning-first responses. Responses that start with TodoWrite pass 4.6%, vs 30.8% for other first actions on the same instances. This holds for all nine models, and 91% of those responses contain no other tool call. The authors call this an association.
  • Rankings hide behaviors. Kimi-K3 beats Opus on error-guided correction (57.8% vs 27.8%), and GPT-5.6-Sol leads 8 of 28 families while ranking fifth overall.

Limits (App. F, §C.4).

  • Only the next turn is graded. A plan-first response may act well later, and a passing response may fail when executed.
  • Pass rates are measured at points where the behavior already happened, so they are not deployment frequencies.
  • The traces can't be released, so the benchmarks can't be rebuilt.
  • The source traces come mostly from one model family. The authors test for a same-family penalty and rule out one larger than about 3 points.

TL;DR for BQAA: BQAA holds exactly the input this needs. Three schema requirements follow:

  1. Store the full request per LLM call, including the system prompt and tool definitions, so any decision point can be cut and replayed as a continuation input.
  2. Record each input turn's source (user-written vs harness-injected) separately from its role.
  3. Flag harness-forced turns, such as compaction requests, so they're never chosen as decision points.

Then SQL anchors do the scan, and a model only confirms the candidates. Report judge–human agreement as κ, never as raw percent.

NEW A2 — Frozen Judges, Moving Agents: Version-Dependent LLM-Judge Error and the Limits of Judge-Assisted Agent Evaluation (arXiv 2609.34198, Jiapeng Li, cs.LG, v1 28 Sep 2026)

Full PDF read: §1–9 and Appendices A–E, 40 pages. This was my own sweep find; it is in no pack.

Design (§3–4, App. B).

  • Question. Can a fixed LLM judge decide whether agent version N+1 beats version N?
  • Primary data. 35 public mini-SWE-agent SWE-bench Verified submissions on 250 held-out issues, with 20 prespecified successive-version pairs: model upgrades, effort changes and scaffold changes.
  • The reference is test-based resolution.
  • Replications: τ-bench (2 agents, 155 tasks, database-state reward) and AgentRewardBench (1,106 expert-labeled trajectories, 15 released evaluators).
  • Judges. GPT-5 mini, GPT-6 Sol, Gemini 3.5 Flash and Claude Opus 5.5.
  • An upstream Opus 5.5 outage after 7,653 of 8,750 cells left three judges on 8,743 aligned cells for the primary analysis. Opus is reported on its matched subset only.
  • Preregistration. The plan was frozen in a private repo on 2026-09-23 with a logged deviation table (§4.6).

Results (§5.2, Table 1; §5.3; §5.4).

  • Error depends on the agent. All three judges reject task-conditioned non-differential error (p = 0.0001 each).
  • Median false-positive rates on failed patches: 65.7% (Gemini 3.5 Flash), 66.0% (GPT-5 mini), 40.0% (GPT-6 Sol).
  • Median false-negative rates: 9.6%, 13.1%, 22.2%.
  • Stronger agents' failures get accepted more. The task-conditioned false-acceptance contrast rises with the agent's resolve rate (mean Spearman 0.819, p = 0.0001). The top half of agents sits 21–26 points above the bottom half.
  • Release decisions. The judges rank the 35 agents well (Kendall 0.71–0.79), yet the differential error component is nonzero in 32 of 60 judge-by-pair units, against about 1.1% under a simulated null.
  • 8 judge-only intervals declare an upgrade the execution-based interval can't establish; 3 miss a real one.
  • Example: Claude Sonnet 4.5 → a high-effort successor scores −0.4 points by tests [−5.2, +4.4]. GPT-5 mini judges it +8.0 [+2.0, +14.4] and GPT-6 Sol +9.6 [+3.2, +16.0].
  • Transported calibration makes it worse. Correcting the new version with the old version's sensitivity and specificity raises mean absolute comparison error from 3.8 to 19.5 points.
  • It is worse in 59 of 60 units, clipped to [0, 1] in 35%, and undefined in 24.6% of bootstrap draws.
  • Prop. 2 explains why: transport divides the differential error by the old version's Youden index, which here is only 0.19–0.38.
  • A confident wrong pick on τ-bench retail.
  • By reward, GPT-4o is 9.0 points worse [−16.0, −2.5]. GPT-6 Sol calls it 17.8 points better [11.8, 24.1].
  • The mechanism: the policy forbids a tool call and a user message in the same turn, and the reward ignores that. Claude's successful retail conversations average 7.4 such turns vs 0.5 for GPT-4o.
  • 31.7% of GPT-6 Sol's rejections of Claude's successes cite the rule; none of its rejections of GPT-4o's do.
  • Audits. Paired PPI++ audits keep coverage (about 94% at 80+ tasks), where judge-only intervals cover the reference in 80.0% of cases.
  • But the judge buys little: about 5% narrower than a classical audit at 80 tasks on SWE-bench (13% on AgentRewardBench).
  • Self-report is a null. Showing the judge the agent's own final message did not raise false acceptance (Holm-adjusted p = 1.0 for all three judges; §5.4).

Limits (§7).

  • Test labels are imperfect. A blinded adjudicator disputes 23.4% of judge-accepted test failures and 49.1% of judge-rejected test successes.
  • All SWE-bench agents share one scaffold family.
  • The code and data are in a private repo, so it can't be reproduced independently yet.
  • There is a single author, and the design and analysis were substantially model-assisted (disclosed).

TL;DR for BQAA: evaluator results need an agent-version column and per-version audits.

  • Store class-conditional judge false-positive and false-negative rates per agent version, from a random reference-labeled sample.
  • Compute version deltas as paired estimates over shared tasks.
  • Never apply one version's calibration to the next.
  • Treat judge-only deltas as "which comparison to audit", not as a ship decision.
  • Log the rubric's success definition next to the reference's. The τ-bench reversal was a construct mismatch.

NEW A3 — TokenCast: Forecasting Token Consumption During LLM Agent Execution (arXiv 2609.35760, Sun Yat-sen, RPI, Southeast, HKUST, cs.LG/cs.AI/cs.SE, v1 28 Sep 2026)

Full PDF read: §1–5 and Appendices A–F, 39 pages. Code at DEFENSE-SEU/TokenCast, created Sep 29.

Method (§3, Eq. 1, App. B).

  • The segment triple. Each run of calls is summarized as (n = calls, g = net input-length change, b = cost minus the starting-input baseline).
  • Composition. Adjacent segments compose exactly: b(A∘B) = b_A + b_B + n_B·g_A. The cross-term is the cost of every later call re-reading the context an earlier segment added.
  • Models. LightGBM models predict prefix, boundary and suffix, and a correction model blends direct and compositional forecasts.
  • Updates and intervals. Forecasts refresh after each call without any LLM call, and calibrated 90% intervals come from quantile models.

Data (§4.1, Table 2, App. C.1).

  • 11,712 traces on 240 tasks: SWE-bench Verified, Search-R1, MMLU-Pro and LongBench-v2.
  • Six agent LLMs, two harnesses: DeepSeek Harness 0.1.1-rc.2 and OpenHands 1.18.0.
  • In both harnesses, context compaction, result pruning and subagents were switched off.
  • For GPT-5.4 on SWE-bench Verified, input is 99% of tokens.

Results (§4.2, Tables 1, 3, 20, 21; App. D).

  • Error. Mean absolute error drops 14.5% on average against the best comparator across 96 benchmark–model–point combinations. The gains are all mid-run:
  • 30.4% at In-call Update and 27.8% at Task Update.
  • −2.2% (worse) at Task Start and 1.9% at Call Start. It trails in 24 combinations, all at those two early points.
  • Example: SWE-bench with GPT-5.4 at Task Update, 80k vs 115k tokens.
  • Intervals. 90% intervals cover 82.0% at Task Start and 89.8–92.8% later.
  • The Self-Prediction baseline's intervals are its native, uncalibrated ones (52.7% at Task Start), so that comparison flatters TokenCast.
  • Budget replay. On 288 GPT-5.4 runs, TokenCast uses 21.3% fewer tokens than a fixed budget at matched trace completion. Savings run from 34.6% at the tightest budget to 7.8% at the loosest.
  • Trace completion means reaching the recorded terminal state, not task resolution (App. D.7).
  • The replay is offline, not live control.
  • Cost of forecasting. 32.8 ms of prediction per run for 19.7 forecasts, under 0.03% of a 129 s median run.
  • What drives the Task Update forecast. Last-call input tokens (0.28), remaining plan items (0.25) and calls without progress (0.23) (Fig. 5).

Limits (from the paper and my read).

  • Zero-shot transfer to an unseen task domain is worse than asking the agent to self-estimate (1.31× at Call Start, 1.47× at Task Update). About 20 target tasks bring it to 0.82–0.85×.
  • Moving from DeepSeek Harness to OpenHands is 1.04× the naive history median at Task Start (Table 12).
  • The paper never models prompt caching or prices. "cach" has 0 matches in the full text, and the target is raw provider-accounted tokens.
  • There is no Limitations section.
  • The Muse 2232 pack described TokenCast as "pre-execution" forecasting. Pre-execution is where it is weakest.

TL;DR for BQAA: a remaining-cost forecast per running session is cheap if every LLM-call row carries input, output and reasoning tokens plus the input-length delta. The (n, g, b) triple is window-function SQL, and "calls without progress" is a strong feature.

  • Forecast dollars, not tokens: with 99% input, cache-read vs uncached pricing dominates the answer.
  • Mark compaction events, which break the "context keeps growing" assumption the method relies on.
