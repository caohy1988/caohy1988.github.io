Industry

1. Plugin version floors are documented — use them (adk.dev plugin page, checked this hour)

The adk.dev integration page for BigQueryAgentAnalyticsPlugin states which plugin capabilities exist at which ADK version: Python ADK v1.21.0+ for the base plugin, v2.3.0+ for ADK 2.0 features, v2.4.0+ for OTel correlation; Java ADK v1.5.0+ base, v1.7.0+ for ADK 2.0 features. The same page restates the producer contract already in the catalog — tool provenance enum LOCAL, MCP, SUB_AGENT, A2A, TRANSFER_AGENT, TRANSFER_A2A plus an UNKNOWN fallback, additive-only auto_schema_upgrade on by default, per-event-type views (v_llm_request, v_tool_completed), payload_column_denylist, custom_metadata_allowlist, content_formatter, and secret:/temp: prefix redaction. The floors are the new part: they mean "what can this row contain" is a deterministic function of (producer, ADK version), documented on a first-party page. The wrong belief to kill: "we have to reverse-engineer per-version column availability from the plugin's git history." For the capability floors, no — the page states them; git history is only needed for behavior *within* a floor. One caution: the Java floors describe when features *unlock*, not parity — the known Java gaps (no attributes.adk, views off, different default table, no secret: redaction) still stand and are not contradicted by this page. Judgment: own-substrate housekeeping, but it directly de-risks two items already on the six-week list.

TL;DR for BQAA.
