Industry

1. IBM watsonx Orchestrate: Trace Inspector, Custom LLM-as-a-Judge, AgentOps Agent and cross-platform agent discovery GA (announced Sep 3; GAs Aug 17 and Aug 31)

IBM's Sep 3 announcement dates four GAs. Trace Inspector (Aug 17) "shows you the full execution path of an agent run," with tool calls and the point where behavior diverged. Custom LLM-as-a-Judge (Aug 31) "lets you define your own evaluation criteria at build time" in natural language rather than generic quality scores. AgentOps Agent (Aug 31) is the loop: it discusses observability data, creates test cases, runs user-simulation evaluations, performs root-cause analysis and optimizes a native Orchestrate agent's instructions or rules with GEPA and ACE, verifying improvement before promotion. AI Gateway cross-platform discovery (Aug 31) scans connected platforms to "discover the agents running on them all at once," today for Amazon Bedrock agents, with inventory, policy application and duplicate detection. Boundaries, stated on the page: Azure AI Foundry and Vertex AI discovery arrive "end of September," and AgentOps for external LangGraph agents is a September expansion. Those are roadmap and are not carded.

TL;DR for BQAA. This is the second hyperscaler-class vendor after AWS AgentCore to ship "evaluate, diagnose, rewrite, verify, promote" as one agent, and the first to make the optimization step (GEPA/ACE over instructions) a product feature rather than a docs example. BQAA is the observer, not the optimizer, so the relevant question is what the optimizer needs from the event record: a test-case row linked to the production session it was derived from, an eval row that names the agent version it scored, and a promotion event that cites the eval run. The first two exist in the schema notes already; the third (a deployment or version-change event that references the evaluation that justified it) is new and belongs with the recommendation-versus-commitment note from 1934. Watch the September LangGraph extension for whether IBM keys external agents on OTel scope names the way AWS does.

2. Salesforce Agentforce Observability: context-based session scoring and multi-agent traces GA, observability unmetered, August trace views (Jul 21 blog; August rollouts; Health Monitoring alerts)

Verified from Salesforce's Jul 21 blog: context-based session scoring and multi-agent traces are GA; session outcome metrics moved "from signal-based to context-based evaluation"; a consolidated dashboard carries Trust, RAG, health and quality metrics; there is a dedicated voice-agent surface and bulk session download; and "Agentforce Observability is now unmetered for every customer across all Agentforce SKUs," with custom dashboards and external ingestion still metered. Stated as rolling out in August: inline citations with highlighted source chunks in the session view, a waterfall trace for multi-agent workflows, and a graph view with trust and RAG metrics at the interaction level. Agent Health Monitoring (error rate, interaction latency, escalation rate in five-minute buckets, custom thresholds, email alerts with 30-minute cooldowns, drill into session traces) was closed beta on Dec 18, 2025; a Tableau new-features snippet says alerts are now GA with Tableau Next, but the page returned 403 tonight.

Verification boundary. The Codex pack additionally reports, from Salesforce Help release notes I could not render (CSS error on every load): streamed Session Trace ingestion replacing 15 to 20 minute batches with roughly 30 seconds to 2 minutes (week of Aug 17), alert evaluation every 10 minutes, and an August Sessions & Intents expansion (TTFT/TTLT p50/p90/p95/p99, connected-agent latency and errors, billable-usage correlation, knowledge-source visibility, scorer management, customizable semantic models), plus a Jul 6 GA that made custom scorers programmable by API. These are plausible and consistent with the Jul 21 post, but they are pack-reported, not verified here. Whole-conversation Testing Center evaluation is labeled Beta by the pack and is not part of the card.

TL;DR for BQAA. Two things transfer regardless of the unverified lines. First, Salesforce writes every turn, LLM call, action and guardrail check as structured trace data into its own warehouse (Data Cloud) and then builds scoring, alerting and BI on that one table; that is BQAA's architecture with BigQuery in the Data Cloud seat, and Salesforce just made the observability side free to drive adoption. Second, if the streamed-ingestion claim holds, "how fresh is the session row when the alert fires" becomes a number competitors publish. BQAA should state ingestion-to-queryable and ingestion-to-alert latency as first-class SLOs in the docs, whatever the current values are. Re-fetch the five help pages from a browser-rendered path before promoting the streaming line to a progress note.

3. ServiceNow Now Assist Suite Aug 7 release: AI Analytics 5.2.5 evaluation KPIs and AI Admin Center 5.1.9 thresholds and business value

The Aug 7 suite release notes list AI Analytics 5.2.5 as new: "detailed evaluation KPIs for deployed AI assets," an "Auto Evaluation dashboard with KPI cards and asset type filtering," asset consumption metrics with benchmarked trendlines, and "granular feedback indicators for conversation interactions, negative feedback reasons, and free-text comment usage." AI Admin Center 5.1.9 adds cross-repository analytics in the Monitor tab (Overview, Performance Explorer and Business Value widgets), a notification configuration that filters by type and shows metrics with change indicators, and a public script include that exposes automation-opportunity data. The pack also lists threshold rules that notify in-console or by email on assist-consumption or execution-count risk; the page confirms the notification surface, and I am carrying the threshold wording as pack-reported detail.

TL;DR for BQAA. ServiceNow's unit of analysis is the deployed AI asset (agent, skill, assistant), and every KPI, feedback reason, consumption figure and business-value widget hangs off that identity. BQAA's equivalent is the agent or app id on the session row; the gap is that BQAA has no asset-registry join, so "evaluation score by deployed asset version" is a customer-built view. No feature; one docs example (asset-level eval KPI query keyed on agent id and version) and a reminder that "negative feedback reason" as a categorical column is now an enterprise expectation, not a nice-to-have.

4. Mastra: feedback analytics (Aug 4), default trace redaction (Aug 10), multi-turn evals (Aug 24), token cost control from the observability store (Aug 27)

Four dated Mastra posts, all "you can now," all verified. Feedback and Feedback Analytics: records carry thumbs, ratings, comments or corrections; are tagged user, SME or qa; and "every feedback record can be anchored to a threadId, traceId, or spanId," queryable by agent, source and time, with user-versus-QA rating comparison and one-click trace opening in Studio; records live in the observability store next to spans and forward to PostHog, Braintrust and Arize (core 1.18.0). Sensitive Data Redaction: SensitiveDataFilter is enabled by default and "recursively walks each span's attributes, metadata, input, output, and errorInfo — including nested objects, arrays, and JSON-encoded strings," with partial or full styles and field-name normalization (api-key, api_key, ApiKey match). Multi-turn evals: runEvals takes gates (deterministic assertions such as tool-called) and scorers (LLM-as-judge over the conversation), per-turn and conversation-level together (core 1.61.0). Token Cost Control: a processor "that reads cumulative costs from observability data" before each model call, scoped to run, thread, user, organization, session or resource, with rolling windows from 1h to 365d, a hard maxCost that blocks and a soft warnAtPercent. Token Limiting (Aug 28) and Trace Intelligence (Jul 27, beta with signup) are pack-reported; the second is a non-card.

TL;DR for BQAA. Two schema notes. The feedback record is the cleanest public statement of what a human-signal row should look like: value, kind, source role, and exactly one of thread, trace or span as anchor. BQAA's feedback event should carry a source-role column (end user, expert, QA) and a typed anchor, because "does QA agree with users on this agent" is the first query anyone runs. The cost-control design is the more interesting one for a warehouse: Mastra reads spend out of the same store it writes traces to, which means the observability table is the enforcement input, and its scopes (thread, user, org, session, resource) are exactly the grouping keys a BQAA cost view needs. That is a docs example (rolling-window spend by scope), not a feature; enforcement stays in the runtime. Redaction on by default is a reminder that the BQAA plugin's redaction posture should be stated in one sentence at the top of the docs.

5. deepset Haystack Enterprise Platform: production Traces with replay in Builder and version comparison (Jul 30)

"Traces is live in Haystack Enterprise Platform. Deploy a new pipeline or redeploy an existing pipeline and it starts generating traces automatically." Each run records a span tree with per-component timing and type, token usage "normalized across providers and attributed per model" (prompt, completion, reasoning, cache), inputs and outputs per component, structured logs, and failures with the root-cause component flagged. Three operations sit on top: "Run in Builder" opens the failing component in the pipeline draft "pre-filled with the exact input from the trace"; compare two pipeline versions for latency, token and answer deltas; and "point a coding agent at your traces through the Haystack Enterprise Platform MCP server." JSON export, workspace RBAC and encryption apply.

TL;DR for BQAA. Third vendor this fortnight (after Phoenix's datagen replay and Braintrust's Debugger) to ship replay-from-trace as a product, and the first to make "compare two versions of the same pipeline on the same inputs" a first-class view. The BQAA shape is a pipeline-version or agent-version column on the session and step rows plus an example query that diffs latency, tokens and outcome by version. The MCP read path over traces is the same pattern as Phoenix's SQL-over-MCP card; count it as a second citation for "agents read the trace store through MCP."

7. MLflow 3.14.0 to 3.15.2: Review Queues and pytest regression gates (Jun 17), MCP Registry and multimodal judges (Jul 31), immutable dataset versions and scorer ensembles (Aug 25)

The hourly beat has watched MLflow tags but never carded its GenAI capabilities. From the releases page: 3.14.0 (Jun 17) adds Review Queues, "a structured, in-UI workflow" where teammates review traces against custom assessment questions and the answers are written back as assessments; the @mlflow.test decorator runs scorers as pytest regression tests in CI; and an LLM Playground. 3.15.0 (Jul 31) adds an MCP Registry, "a centralized catalog to register, version, and share MCP servers across your team," multimodal judges that fetch images from trace spans via a get_span_image tool, and shareable saved table views. 3.15.2 (Aug 25) adds immutable evaluation dataset versions and a scorer_ensemble primitive for combining scorer results. 3.13.0 (May 29, outside the window) added RBAC, policy-driven trace archival from SQL to object storage, and one-click Claude Code, Codex and Gemini CLI onboarding through the AI Gateway.

TL;DR for BQAA. Two notes. Review Queues are human assessments written onto the trace as rows, with the question they answered; that is the eval-events table with a human evaluator id, and it argues for BQAA's eval row to carry an evaluator_kind (judge, heuristic, human) and a question or rubric id, which is the rubric-id column note from 1934 again. Trace archival from SQL to object storage after a retention window is the reverse of BQAA's model (BigQuery is the cold store) and is a good one-paragraph docs contrast. scorer_ensemble is a reminder that an eval row may be a composite; the aggregation definition column from the judge-instrument note covers it.

8. Opik: per-evaluation USD budget caps with a budget_exceeded trace tag (Jul 13) and thread-level RAG context for multi-turn judges (Aug 24)

Jul 13: online LLM-as-judge scoring rules take a spend limit; "once an evaluation's cumulative spend crosses the limit, the agentic scoring loop stops starting new tool-calling turns," and "the monitoring trace for a capped run is tagged budget_exceeded" so a truncated verdict is distinguishable from a complete one; the field is hidden for span-scope rules "since a single LLM call has no loop to cap." Aug 24 (releases 2.2.30 to 2.2.36): evaluate_threads gains trace_context_transform, which "receives the whole trace object and attaches the extracted context to that trace's message," so metrics that declare uses_message_context can judge retrieved documents at thread level, and ConversationalCoherenceMetric now emits a conversational_groundedness_score when context is present. The pack's Aug 10 and Aug 17 entries (metric failures surfaced, experiment traces as a Logs tab) were not opened.

TL;DR for BQAA. The budget_exceeded tag is the smallest good idea in either pack: an eval row must say whether the judge finished or was cut off, or every score-drop alert will fire on budget changes. Column note for the eval-events table: judge termination reason (complete, budget, timeout, error) alongside the score. Mastra's cost-control tripwire "records the tripwire details in production traces" for the same reason. The thread-level context transform is Opik catching up to the session-level evaluation shape BQAA already has; the detail to copy is that retrieved context is attached to the message it grounded, not to the thread as a blob.

Standards

12. OpenTelemetry Collector Contrib gen_ai_normalizer processor: OpenInference and OpenLLMetry span attributes rewritten to GenAI semconv (v0.153.0, May 26, 2026; alpha)

GitHub API confirms v0.153.0 was published 2026-05-26; the release notes list "processor/gen_ai_normalizer: Add a processor that normalizes GenAI telemetry attributes from OpenInference and OpenLLMetry to the official OTel GenAI Semantic Conventions." Stability is alpha for traces. Built-in OpenInference mappings cover token counts, model and provider, messages, tools, agent and session ids and operation type; OpenLLMetry mappings cover usage, request and response parameters, function definitions and entity data; users can define further sources. Stated limits: only span attributes are touched (resource, scope, event and link attributes pass through); OpenInference's indexed multimodal content is not reconstructed, only the flat message.content string; blob, file, uri, reasoning, server-tool-call and compaction parts cannot be emitted; per-message finish reason is always emitted as an empty string. Outside the Jul to Sep window but never carded, and the collector is the layer BQAA's OTLP path sits behind.

TL;DR for BQAA. BQAA's ingestion already accepts OTel GenAI and OpenInference-shaped spans; a collector-side normalizer means customers may arrive with attributes that were rewritten upstream, lossy in the ways the README lists (empty finish reasons, flattened multimodal content). Design note: keep the raw source attributes beside the normalized BQAA columns when the producer scope is not native GenAI semconv, and record which normalizer (if any) touched the span, because "finish_reason is empty" will otherwise be indistinguishable from "the model returned nothing." Also a second citation, after AgentCore's scope-name table, for classifying producers by instrumentation scope rather than attribute shape.
