Industry

Langfuse v4.26.0 — the judge gets a trace; drops get a tag (Aug 31, second release of the day)

Tagged 17:53 UTC, roughly seven hours after v4.25.0 — two releases in one Monday, both in the eval-and-substrate lane. The headline feature is verbatim "link evaluator execution traces": an evaluator execution (the LLM-as-judge run itself) now produces a trace that's linked, so when a score looks wrong you open the judge's own trajectory instead of guessing. Pair that with a fix in the same release — "avoid reasoning collisions in structured output" in evaluations — and the shape is clear: their judges are reasoning models whose structured outputs need guarding, and they've decided the fix for judge opacity is tracing the judge. Below the fold, ingestion monitoring now tags metadata_dropped when OTel metadata doesn't survive ingestion, and another fix parses OTel prompt-version attributes as integers — small, but both are "record the loss, type the contract" moves. The wrong belief to kill: "evaluator quality is a prompt-engineering problem you tune offline." Langfuse just made it an observability problem you debug from the trace table — which is a much better fit for what BQAA already owns. Judgment: peer, and now the third first-party fact in one day (after 4.25.0's MCP evaluator definitions) that eval contracts and eval observability are converging on the trace substrate.

TL;DR for BQAA. Two direct steals. First: EvalBench judge runs should land in agent_events like any other agent's — a judge trace joined to the score it produced closes the loop that judge_version + rubric hash (EV #7) starts; the row gains "and the judge run is queryable" for free because the substrate already exists. Second: metadata_dropped is peer confirmation that drop facts belong in the data, not in a log — one more citation for the coverage + telemetry_factors row (EV #3). No new row; two rows get harder to argue against.
