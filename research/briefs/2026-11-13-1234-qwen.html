1. Cloudflare Spend Management (Beta) — spend caps that pause the product, with an audit log of who changed the limit

Primary: https://blog.cloudflare.com/spend-management/ (RSS pubDate Fri, 13 Nov 2026 14:00:00 GMT — in window).

Cloudflare now lets any pay-as-you-go customer set a spending threshold and have activity paused automatically when the limit is reached, rather than only being notified: "informing is not the same as controlling." Beta scope is Workers and Durable Objects first, configured from the dashboard (Manage Account > Billing > Spend limits), the cf CLI, or the REST API (POST /accounts/{id}/billing/spend-policies). Each enabled product takes a spending limit, a notification recipient and one or more alert thresholds; the dashboard shows current billing-cycle cost per product in near real time (stated as under 10 minutes) plus an audit log recording who changed a limit and when, and when a cap was reached. The post explicitly positions it alongside AI Gateway spend limits, which already carry per-user and per-model budgets for requests routed through the gateway. One non-obvious trap it documents: the billing cycle starts when the paid subscription begins, not at a calendar month boundary.

Why BQAA cares: this is the enforcement half of cost governance arriving as a first-class primitive — threshold → alert → hard stop → audit trail — on the same account surface where per-user and per-model AI budgets already live. Any agent-cost product that only reports spend now sits next to a control plane that can act on it. The audit log is the part worth copying: cost policy changes become attributable events, not configuration drift.

Caveats: Beta; only Workers and Durable Objects at launch, so agent/inference spend is governed through the separate AI Gateway budgets rather than this surface; the "under 10 minutes" latency and the pause behaviour are vendor-stated, not independently verified.

2. Cloudflare Kitesurf open-sourced under Apache 2.0 — a self-hostable browser engine built for agents

Primary: https://blog.cloudflare.com/kitesurf-open-source/ (RSS pubDate Fri, 13 Nov 2026 20:20:21 GMT — in window, ~25 minutes before this slot's cut).

Kitesurf, the stateless browser for AI agents that runs entirely on Workers, is now open source on GitHub under Apache 2.0: "You can read the code, run it locally, change it, and deploy your own instance to Cloudflare Workers." It parses HTML, applies CSS, executes page JavaScript and renders screenshots without a browser container, and speaks the Chrome DevTools Protocol so clients such as Puppeteer can connect. The repository builds on Cloudflare's platform plus Rust-to-WASM ecosystem packages — Blitz (HTML parsing, DOM, layout, painting), Stylo (CSS cascade and computed styles), Boa (JavaScript in WASM, as a last resort when JS cannot run in Dynamic Workers), Linebender libraries (text layout, 2D graphics) and Krilla (PDF output) — which retain their own licenses with third-party notices in the repo NOTICE. Three components: the Engine (sessions and client connections), PageScript (runs the page and its JS) and PageRenderer (draws the result). Local run is git clone → pnpm install --frozen-lockfile → pnpm run dev, then wrangler serves a dev server at http://127.0.0.1:8787; the first build compiles the Rust core.

GitHub verified directly: cloudflare/kitesurf returns HTTP 200, license Apache-2.0 (LICENSE file), 385 stars, not archived, last push 2026-11-13T16:11:21Z, and the repo description still reads "experimental browser engine that runs on Cloudflare Workers." Note one discrepancy I could not resolve: the GitHub API reports created_at 2026-09-30T08:51:43Z, while the vendor announces open-sourcing on Nov 13 — the API cannot tell me when the repository became public, so I attribute the availability change to the dated post, not to the creation date.

Why BQAA cares: browser-tool fidelity is a trace problem. An agent browser whose engine you can read, pin and self-host means rendering and tool behaviour stop being a black box you must infer from screenshots — you can inspect what the agent actually saw, and reproduce it. Prior slots treated Kitesurf as experimental and out of window; the license change is the material move, not a capability upgrade.

3. Cloudforce One: agentic penetration-testing orchestrators went from one framework to over 50 families in three days

Primary: https://blog.cloudflare.com/adapting-to-ai-penetration-testing-orchestrators/ (RSS pubDate Fri, 13 Nov 2026 19:26:07 GMT — in window). This is a dated threat-intelligence report and recommended operating model, not a product release; it is ranked for the quantified field data on autonomous agent traffic, which no other source in this window supplies.

Cloudflare reports that in the last three days it saw over 50 framework families of LLM penetration-testing/orchestration tooling attempt to scan its customers globally, from IP addresses that have "grown into the thousands and continue to increase daily." The lineage traces to ARTEX, an open-source agentic pentesting system whose creator ("Autumn-27") took it down on October 8; in the month since there are now over 12,000 repositories with several hundred unique forks carrying lineage from the original, plus hundreds of other similar agentic orchestration frameworks created since October 8. Daily requests from AI pentesting and exploitation tools have grown 30× since October 1, and in the more complex attacks these tools chain stolen customer credentials for lateral movement. Technically, the frameworks orchestrate agents through stages of the traditional Cyber Kill Chain at scale, plug in existing MCP servers to connect standalone pentesting tools, accept operator direction on the task, and map assets onto a graph so multiple independent parallel agents can enumerate and verify. Cloudflare's response is a six-pillar "Modern Security Model": WAF with rate limits at the front gate, anomaly detection on customer-facing web applications, bot defence, identity-gated access for high-risk applications, validated schemas and explicit security controls, and threat intelligence for visibility.

Why BQAA cares: this is the demand-side mirror of the personal-agent-analytics card already in the catalog — autonomous agents are now a volumetric traffic class that defenders must classify, and the numbers give a real-world scale reference for agent-traffic measurement. It also documents agents composing tools through MCP and parallelising over a shared asset graph, which is a multi-agent orchestration pattern worth recognising in telemetry.

Caveat: all figures are vendor-observed on Cloudflare's own traffic; no independent replication exists, and the underlying dataset is not published.

1. The AI Era's Lines of Code? A Case Study on What an Engineer's Token Spend Measures — full PDF read (reserve promotion)

Full PDF read: yes — all 15 pages including §I–§VII, both supplementary sections (SM A additional results, SM B survey details) and Figures 1–13. Agarwal, Lvova, Sergeyuk, Serova, Bryksin, Zimmermann, Vasilescu (CMU, JetBrains, JetBrains Research, UC Irvine); arXiv:2611.13396v1 [cs.SE], 10 Nov 2026.

Design (§III). At JetBrains (~2,600 employees) an internal gateway meters every coding-agent call. The panel is 404 engineers and 1,827 person-weeks over five analysis weeks (2026-06-29 → 2026-08-02), drawn from 406 metered engineers out of 584 who committed; 3.1 million agent calls, with two agents accounting for nearly all tokens (69% / 31%). The median call sends about 400× as many tokens as it receives, i.e. spend is dominated by re-sent context. Over the five weeks the 90th-percentile engineer used 71× the tokens of the 10th (Fig. 2: n=1,599 person-weeks, n=397 engineers). Output is commit count by author date; 71% of commits touch the shared IDE platform. Estimation is Poisson quasi-maximum-likelihood with person and week fixed effects, cluster bootstrap over engineers; week effects absorb the frontier model that arrived in week 3 and took 45% of all spend within two weeks. All estimates are associations — engineers chose their own usage, and there was no spending target or mandate.

RQ1 (§IV-A). A week with twice an engineer's usual commits costs about a fifth more tokens: elasticity d = 0.26 [0.19, 0.32]; in the other direction the slope of commits on tokens is 0.13 [0.03, 0.32], so twice the tokens goes with ~10% more commits, and proportionality (d=1) is rejected at every time unit (p<0.001). Two defences of a larger d fail: instrumenting commits with lines changed raises d only to 0.48, and the day-level cross-correlation peaks on the same day (0.33) and is gone after about four working days (Fig. 11), so a week contains nearly all the lag. Output metrics (commits, lines changed, bug-linked commits, commit-days) explain 38% of between-person variation on held-out people and 13% of within-person variation on held-out weeks (Fig. 4); role, manager flag and team together predict held-out people worse than the week's average spend (−6%). In-sample, "which person" explains 79% of the deviance. Within every weekly-commit quintile the P90 of spend is 39–240× the P10 (Fig. 1), and after all four metrics the P90 person-week is still 58× the P10. An engineer's spend correlates only 0.24 with the leave-one-out mean of their division and 0.13 with their team's.

RQ2 (§IV-B). Weeks with no commit are only 4% of all tokens (floor: the 49 above-median-spend no-commit weeks are 3.0% [1.8%, 4.5%]). The curve estimate — a no-commit week still costs 77% of the engineer's average week (Fig. 5) — gives 89% [79%, 97%] under raw counts, 63% under square root, 42% [33%, 51%] under log(1+x) and 39% [31%, 46%] under the spline; the authors trust the last two because calibration is 0.91 and 0.96 versus 0.62 for counts, and counts is rejected by five-fold cross-validation and by Poisson/negative-binomial/gamma agreement. Hence "up to about two fifths" of spend does not vary with the week's output — an upper bound, since it also contains the fixed cost of using an agent at all and the spend behind hand-written commits. By group (Fig. 6): all users 39%, developers 37%, leads/managers 40%, QA 50%, interns 59%; heaviest third 36% (while spending 79% of all tokens), middle 51%, lightest 52%. Per engineer the median is 46%, the middle 80% spans 31–68%, and P10/P90 differ 59-fold; team, role, manager flag and prior work mix explain only 11% of that variation. Excess-spend weeks are explained by tooling, not output: within person the residual correlates 0.15 (p<0.001) with the week's share of tokens on the newly released model, 31% of calls sit in sessions longer than two hours versus 18% otherwise, generated text stays under 1% of tokens in both (0.6% vs 0.9%) — so the excess is context sent, not code returned — and the residual does not predict next week's bug-linked commits (0.03).

Survey (§IV-B2, SM B). Of 197 evaluations of the two coding agents by 184 technical respondents (167 answered the past-week use questions): 91% reported time saved (median 10 hours, IQR 5–20) and 88% a positive productivity effect; coding appears in 63% of evaluations while at least one non-coding activity appears in 89% (83% among the 100 assigned-tool evaluations) — processing and analysing data 52%, brainstorming 49%, research 44%, planning 39%, learning 28%, finding/summarising information 28%, writing 23% (Fig. 7). Median hours saved rise from 3 (coding only) to 10 (two or more non-coding activities, Fig. 8A); in the joint model (n=134, R²=0.43) the non-coding activity count is 0.24 [0.06, 0.43] and colleagues-otherwise-needed 0.43 [0.23, 0.61], while coding is not (0.08 [−0.10, 0.27]). 59% named the week's value as "experiments and learning that have not yet brought tangible value". Cost themes (Fig. 9A, n=67): wrong or low-quality output 49%, tooling friction 24%, prompting/context/steering 21%, verifying output 18%. Enabled work (Fig. 9B, n=44): unfamiliar codebase/stack/domain 36%, tasks otherwise deferred or handed off 25%, prototypes 23%, internal tools 20% — and only one of 44 says the work would have happened anyway. Unbilled costs: 31% of technical agent users report higher cognitive load (51% lower), nearly uncorrelated with hours saved (ρ=0.11 vs 0.57 for productivity); and 55% [49%, 60%] of 299 respondents handled colleagues' material they suspected was AI-generated, at a mean cost of 1.6 hours a week [1.2, 2.1], with team leads at 73% versus 50% (OR 2.7, p=0.006).

What the authors conclude (§V–§VI). Spend is "the lines-of-code metric of the AI era" — easy to count, loosely related to accomplishment — with one difference: LOC counted output and stayed useful because program size tracked effort, whereas tokens count an input, recorded whether or not anything is produced. Their within-engineer estimate matches prior between-engineer ones (10× spend ≈ 40% more output across vendor usage deciles; ~2× in a press summary; ≤76% under a 2× mandate study; here ~30% between engineers and 35% within [7%, 109%]), so the weak association is not only an artefact of comparing different engineers. Against the three uses: (a) productivity — do not evaluate engineers by spend even where nobody games it (if the within-engineer association were causal, doubling spend through a target would raise commits ~10% [2%, 25%]); do not divide spend by commits/PRs as ROI, because the ratio mechanically falls as commits rise (2× commits → 1.2× tokens → 40% lower tokens per commit), ranks the top decile unreliably (only 17 of 34 engineers persist across odd/even weeks; Fig. 12B split-half ρ=0.67, top-decile overlap 50%), and moves ~45% with a model release at constant commits; (b) adoption — a token threshold counts one end of a skewed distribution (the heaviest third holds 79% of tokens), so report weekly headcount alongside a context-insensitive measure such as the share of engineers using agents on most working days; (c) budgets — five-week totals rank engineers reliably (projected reliability 0.87) where two single weeks correlate only 0.4–0.6, so budget from multi-week totals and revise the level after a model release; capping mostly hits heavy users and cuts output-tied spend along with the rest, so try context management/compression, caching and cheaper-model routing first, and measure billed cost rather than tokens since removing context can raise cost. Two changes would make value measurable: record at the gateway which issue or task each session served, and develop value measures beyond SPACE/DORA/DX Core 4, which get noisier now that one number can come from different human/agent mixes.

Limits (stated by the authors). Associations only. Commit counts miss review, design and quality, and PR data was unavailable. One company that builds AI coding tools, so some metered use may be testing its own agents; established codebases (where a prior mandate study reports smaller gains); voluntary use; five weeks; the survey cannot be linked to telemetry or to individuals; raw data is NDA-only, with a replication package at github.com/CMUSTRUDEL/token-study-replication.

Why BQAA cares: this is the most direct available test of the metric family our product sits in. Three concrete consequences: (1) a token-per-task or token-per-user dashboard is measuring a stable trait of the user plus the context window and model in use, so it must not be presented as productivity; (2) the 39% upper bound on spend not tied to output is mostly inside weeks that did produce commits, so a "waste" bucket derived from zero-output sessions will understate it by an order of magnitude; (3) the gateway-level session→task linkage they ask for is exactly the join that turns cost telemetry into outcome telemetry, and it is a schema decision, not an analytics one.

2. Where LLM Agents Get Stuck Debugging Databases: Access More Than Reasoning — full PDF read (reserve promotion)

Full PDF read: yes — all 12 pages including §1–§9, Tables 1–2, Listings 1–5, §7 limitations, §8 related work, data-availability and AI-use declarations. Gustavo Pinto (Federal University of Pará), preprint submitted to Elsevier; arXiv:2611.17304v1 [cs.SE], 12 Nov 2026.

Design (§3). Retrospective participant observation: the author was employed at the company and directed the agent (Claude Code) as ordinary work. Evidence is triangulated across three artefacts — session transcripts in JSONL that record both private thinking and public answers, the commit history (which independently records each fix and each fix later corrected), and deployment/workload records. Eight database incidents over a ten-day window; 27 sessions, ~410 cumulative hours, ~3,000 tool calls, roughly two thirds of them shell commands. Model calls went through the company's internal generative-AI platform: an open-weights model served ~79% and a frontier model ~17%; hypotheses are not attributed to models, so the paper makes no claim that a different model would have avoided a given false start.

Setting (§2). A message-dispatch engine (WhatsApp, SMS, email) for B2B marketing campaigns at "a large technology company": Python + SQLAlchemy (asyncpg) behind PgBouncer on Kubernetes with Datadog, in three stages — Compile (audience resolved from a CDP materialising per-customer attributes out of an EAV store of ~38.5M rows across 369 dynamic columns), Orchestration (eligibility, one message per customer per day, phone-number cascade, coverage constraints; materialised into a dispatch-queue table that is the single source of truth; 3,089 journey executions), and Dispatch (a worker claims queue rows in batches of 100 under advisory locks). The queue has accumulated ~4.9M rows and sent ~3.3M messages; the largest single execution held 331,000 rows and up to 22,000 rows were observed pending at once; load concentrates 09:00–12:00 local, and that three-hour window accumulated roughly 600,000 messages over October. The CDP's distinct-customer base grew from ~330,000 in July to ~587,000 by November. The repository holds ~406,000 lines (Python, TypeScript, SQL), ~182,000 of them tests, at 84% line coverage; 1,019 commits by five developers in four months, of which 293 (29%) carry an AI co-author trailer — 289 naming Claude Code, four Cursor — used by only two of the five developers, so it understates involvement. Production deployed on most business days: 232 deployments over 126 days. The codebase was first built with an AI coding agent on Replit and imported in a single ~241,000-line commit in July 2026; many defects surfaced only under production load. The agent runs with elevated permissions (bypassPermissions) and commits under the engineer's identity; a persistent .memory/ directory records decisions, lessons and refuted hypotheses so a fresh session does not re-litigate settled questions; every change passes a merge request approved by a second developer.

The access asymmetry (§3.1). In development the agent had everything a developer has: repository read/write plus a GitLab MCP server (merge requests and history), local run logs, unit and integration test output against a local database, the platform API, and read-only queries over the customer base and hourly dispatch volume. In production it had three partial channels: log search over Datadog and Kubernetes where indexed datasets require browser authentication the agent does not have; a read-only database where the agent writes the SQL but a human runs it through a read-only production proxy that cannot execute, scale or restart anything — each query a round trip through a person, returning a snapshot taken after the agent asked, by which time a transient lock could be gone; and kubectl without exec into the database, without restart or scale, and with an environment context that must be switched manually. The paper's framing: for this class of runtime failure, access to the code is necessary but not sufficient — the code says what can happen, and what did happen lives in production.

Findings (§4–§5, Tables 1–2). Across eight incidents the agent shipped 22 fix commits, and every incident day carried between two and four production deployments; dispatch_service.py alone was touched fourteen times. The agent was never wrong in the end but was often wrong serially — announce a cause, ship a fix, walk it back, one deploy-and-observe cycle per wrong guess. The split follows concurrency exactly: all five incidents whose root cause depended on runtime concurrency began with a false start, and the three that did not (#1 memory exhaustion — first attempt held only in part, symptom fixed by raising CPU 50m→200m request / 500m→1000m limit and memory 2Gi→4Gi, underlying cause of materialising the whole audience instead of streaming left open; #4 trigger committed early — savepoint instead of early commit; #5 monitor card) needed nothing beyond what the agent already had. In the reasoning × access matrix, #2 (summary lock) is access alone — the missing live pg_locks view; #3 (pair lock and ledger), #6 (throughput), #7 (race exposed) and #8 (deadlock retry) are mixed; and no incident was limited by reasoning alone. In each mixed row the reasoning error was retired by evidence rather than reflection: a measurement refuted the throughput hypotheses, the historical cause was set aside once dated to September, and a renewed failure exposed the unsafe rollback(). The throughput incident (#6) alone burned six refuted hypotheses — the preflight query (measured at 0.34 s for 100 rows, far too cheap), the scheduler tick (raising it moved nothing), the batch cap (effective rate two batches per pass, below the cap of three), line eligibility (executions were terminating: 11,476 sent, zero pending), the volume throttle (NULL on every active journey) and the orphan grace period (shortened, then reverted) — before finding the real bottleneck, the retry sweep's five-pairs-per-tick cap saturating during draining. Its fix was a one-line configuration change (five to eight pairs per tick) in the deployment values, not code, which is why Table 1 records zero fix commits for it. The sharpest evidence is §4.10: the deadlock DETAIL — the lock graph naming which transaction waits on which lock and who holds it — was truncated at the source, because the application's logging layer stores the exception in a fixed-length field. The full report existed in the Postgres server's own log, which has log_lock_waits enabled, but the agent had only the application log. "The information was not absent; it was out of reach." And obtaining access itself cost a release: to see live lock state during the summary-lock incident the agent wrote a pg_locks probe and shipped it to production, "turning a read into a release."

A coding distinction worth keeping (§3.2, §4.10). A false start is a hypothesis consistent with everything the agent had seen that turns out to be wrong; a hallucination/fabrication asserts a fact contradicted by evidence already in its context. Retractions were coded from two independent signals — the agent's own later statements and a later commit correcting an earlier one. Within the eight incidents there were no fabrications; one near-case occurred three days before the window, when the agent reported a fix as done that had never reached the code and then caught it. The remedies differ: hallucination calls for better grounding, false starts call for better access.

Tooling agenda (§6.2). Five directions, the first three being the "forensics layer" of the abstract: (1) a safe read-only audited interrogation API exposing pg_locks, pg_stat_activity, query plans and row-level state, rich enough to answer "which statement holds this lock?", living inside the existing VPN, identity-management and access-broker layers rather than as raw credentials — the runtime counterpart of SWE-agent's agent–computer interface and of Panda's grounding and affordance components, but for an application-side agent; (2) a lock-and-deadlock flight recorder that continuously logs lock waits and full deadlock reports, turning an ephemeral failure into a queryable artefact; (3) a production replay harness built on traffic capture or a shadow environment fed by production traffic — "the missing piece between 'I can read the logs' and 'I can reproduce the bug'", since the sandbox ran an older version than production, could not be queried directly, left transactions idle holding locks during external calls, and never reproduced the concurrent load; (4) shorten the guess–ship–observe loop — the delivery pipeline runs roughly twelve minutes end to end across about twenty stages, the unit-test stage alone takes about five and a half minutes (nearly half the pipeline), and the mutation-testing stage added roughly an hour before it was disabled (~5× the rest of the pipeline combined) — via dry-run execution, EXPLAIN against a live replica, or a fast canary with fine-grained metrics; (5) externalise the hypothesis in a ledger recording each hypothesis and the evidence that retired it, treating a hypothesis as a first-class persisted object in the harness rather than private reasoning corrected silently. The repository's memory of refuted hypotheses already did this and is called the cheapest intervention of all.

Implication for benchmarks (§8). AIOpsLab, ITBench and OpenRCA give the agent complete observability by construction — every injected fault leaves its telemetry in the bundle — so their low scores (OpenRCA's best model solves about 11% of 335 failures) are usually read as a reasoning ceiling. This field data supports a complementary reading: in production the evidence for a concurrency failure may never be recorded at all, so the cost is paid earlier, at collection time. Benchmarks should therefore vary what the agent can see — truncate logs, withhold lock views — not only how hard the fault is to explain. Likewise D-Bot and Panda take DBA-side access to pg_stat_activity and pg_locks as given, which does not hold for an application-side agent separated from those views by a VPN, an identity layer and a human-operated read-only proxy.

Limits (§7, stated). One message-dispatch engine with unusually heavy locking, one team, one agent, ten days — so the concurrency/false-start association holds for this sample only. No controlled comparison, so the paper cannot show access caused the false starts; the same applies to model capability, since most calls ran on an open-weights model and hypotheses were not attributed to models (a frontier model might have avoided some of the mixed incidents' reasoning errors). Selection is limited to incidents the team worked on with the agent. The constructs (false start, its source, the reasoning × access matrix) are one author's retrospective interpretation: a derived taxonomy, not a validated measurement — a single author coded them, that author was also the participant, and there is no inter-rater agreement or member checking. Portuguese quotations are the author's translations. Confound: the codebase was first built by an AI agent, so concurrency-defect density may be higher than in a conventionally developed system; and a human ran the agent's SQL through the read-only proxy — 28 such queries over the window, 25 of them in the single race incident — with round-trip latency unmeasured. Raw data cannot be shared. The author used Claude Code to analyse transcripts and repository data and to assist drafting, which is also disclosed as a threat to validity since it is the tool under study.

Why BQAA cares: two things transfer immediately. First, an eval that scores a data agent's reasoning on incidents whose decisive evidence was never recorded will mislabel an access failure as a capability failure — so the eval environment must log what the agent could see, and benchmark scoring should separate "wrong given the evidence" from "the evidence was never collected." Second, the hypothesis ledger is the cheapest high-value telemetry object available: a persisted (hypothesis, evidence that retired it, deploy cycles consumed) triple turns serial self-correction from an invisible cost into a measurable one, and it is a natural fit for trace-as-state.

Tooling agenda: a read-only audited forensics/interrogation API inside existing security layers, a lock-and-deadlock flight recorder, a production replay harness, a shorter guess–ship–observe loop (pipeline ~12 min over ~20 stages, unit tests ~5.5 min), and an externalised hypothesis ledger; benchmarks should vary what the agent can see, since AIOpsLab/ITBench/OpenRCA grant complete observability by construction. Limits: one system/team/agent, ten days, no controlled comparison so no causal claim, model mix (~79% open-weights, ~17% frontier) not attributed to hypotheses, single-coder derived taxonomy with no inter-rater agreement, and the codebase was itself first built by an AI agent.
