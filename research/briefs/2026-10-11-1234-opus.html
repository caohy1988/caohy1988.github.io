Read this first

  1. LiteLLM 1.105.0 (stable, PyPI latest, Oct 11) turns the gateway into an agent-trace store with an analysis tool on top. The proxy now accepts OTLP exports at POST /v1/traces and stores spans in ClickHouse. It adds an Agent Traces view and Lens (Beta): an admin describes the expected behavior, selects runs by agent, team, metadata and time, and samples them. A separate worker model then reviews those runs and returns findings linked to the original trace evidence, within a budget (default: 24h window, 100% sample, $100/month). This competes directly with BQAA's "ask questions of your agent runs" use case, at the gateway layer. → NEW Industry.
  2. SSCBench (2610.11514): whether an agent "ignored contradicting evidence" depends on when the evidence reached it in that particular run, not on the test case. In one fault type, 101 of 141 runs adopted the fault. Only 17 of those runs had seen the contradicting record before first using the bad value; 27 saw it afterward, and 57 never saw it. Removing one read-back cue cut pre-use evidence from 54/115 runs to 0/115. Generic trace diagnostics found "something wrong" but rarely the exact step of first faulty reliance. → NEW Academy.
  3. TestJack (2610.10619, Columbia/Berkeley/GMU): 34.4% of frontier coding-agent "passes" on five benchmarks violate the task's stated requirements. Each refutation is backed by a test that passes on the reference solution. The combined resolution rate drops from 50.6% to 33.2%. Carefully written verifiers do not fix this: DeepSWE loses 43.5% of its passes. → NEW Academy.
  4. Opera (2609.33987, Salesforce): a coding-agent critic that tracks each correction until it is resolved, separately from whether the agent merely complied. With Qwen3.8-27B as the policy, it lifts resolve rates by 4.0–8.9 points. Removing the audit that filters feedback before delivery cuts the gain by up to two thirds. Stronger policies are rescued more often but also regress more often. → NEW Academy.
  5. Mastra 1.76.0 / @mastra/observability 1.19.0 (Oct 11):
    • every token and cost metric row from one model call shares a usageId;
    • cost estimates now include reasoning tokens;
    • an LLM judge run can be nested under the run it scores (nestUnderParent);
    • interrupted model requests get their own span.
      → Progress on the Mastra trace-aggregate card.

LiteLLM 1.105.0 (stable): OTLP agent-trace ingestion into ClickHouse, an Agent Traces view, and Lens (Beta) investigations over sampled runs

Source: https://github.com/BerriAI/litellm/releases/tag/v1.105.0 (GitHub 2026-10-11T09:53:26Z; PyPI litellm 1.105.0 09:47:54Z, now latest)

  • Why this is a new card: the parent card litellm-1-104-0-… covers 1.104.0. Its only progress note (Oct 4) records the 1.105.0-rc.1 trace query endpoint. The Lens and trace-store batch was merged Sep 30 – Oct 2 and carried as WATCH in earlier briefs ("WATCH the v1.105.0 tag for the Lens batch"). It now ships in a stable release.
  • Trace ingestion (#43819, #43915, #43928): the proxy accepts authenticated OTLP exports at POST /v1/traces. It returns OTLP success after ClickHouse accepts the spans and 503 if the write fails. It stores one trace summary per API key with configured retention. Spend is now written to ClickHouse automatically. This requires the compiled Rust extension and a ClickHouse reader URL (#43915 caveats).
  • Agent Traces view (#43891, #43972, #44068): shows a runs table with a zoomable timeline and a span tree of LLM calls, tools and subagents. It includes an OTel setup guide, with a prompt for Claude Code / Codex. Tracing then moved into Lens's Traces tab.
  • Lens (Beta) (#43889, #43942, #43989, #44089):
    • Who can use it: proxy admins configure it; admin viewers can read.
    • Setting up an investigation: an admin writes the expected behavior and individual checks, selects activity (source, team, agent, metadata, time range), then previews matching runs. Sampling can be a percentage, an optional cap, or specific runs.
    • The worker: a separate worker runs on the proxy host or another server. It holds a revocable Lens credential and has no provider keys or database credentials. It reviews runs concurrently and reads long traces in bounded pages.
    • Findings: grouping verifies the cited evidence. Counterexamples stay visible but do not raise recurrence counts or reopen resolved findings. Each batch keeps its own settings, findings, selected runs and cost. Feedback applies to later scans.
    • Defaults: 24-hour window, 100% sampling, no count cap, $100 monthly limit, no schedule. The worker's spend is tracked through virtual keys.
  • Also in 1.105.0:
    • POST /v1/traces/query (team-scoped SQL over traces and spend; carded at rc.1);
    • a Databricks Zerobus trace logging callback;
    • a SigNoz OTel preset;
    • cache and reasoning tokens in Langfuse usage_details;
    • an in-gateway ROI calculator that compares gateway spend with merged PRs.
  • Not in 1.105.0: the later Lens train, including #44711 (rebuilding coding-agent conversations as trace views), #44738 (pricing agent traces through a gen_ai.response.id join to spend logs) and #44786 (run-report-first investigations). I checked both the 1.105.0 and the 1.106.0-rc.1 notes, and neither includes them.
  • Why it matters for BQAA: the analytics path BQAA offers (agent spans → warehouse → questions answered by a model over sampled runs, with evidence links) now ships inside a widely deployed gateway, at no extra charge. Lens's design choices are a useful checklist for BQAA:
    • findings cite the original trace;
    • the run selection is frozen per scan;
    • counterexamples are kept but not counted;
    • the analysis worker's own spend is metered.

Mastra 1.76.0 + @mastra/observability 1.19.0: usage rows tied to one model call, reasoning tokens priced, judges nested under the run they score

Parent: mastra-core-1-72-0-trace-aggregate-plans-lease-fenced-background-tasks-cyber-refusal-retry Source: https://github.com/mastra-ai/mastra/blob/main/observability/mastra/CHANGELOG.md (npm @mastra/observability 1.19.0 2026-10-11T17:09:50Z; @mastra/core 1.76.0 17:11:38Z, both latest)

  • usageId (#26461): every token and cost metric row from the same model call now shares a usageId. Usage rolled up from hidden model calls onto a visible span gets a separate usageId per call. Storage can therefore group or dedupe one call's rows without relying on the span.
  • Reasoning tokens priced (#26521): cost estimates previously left out reasoning tokens. When a model has no separate reasoning price, they are now billed at the output price, so estimated costs for reasoning models go up.
  • Judges nested under runs (#25691): with tracingOptions.nestUnderParent (helper nestUnderRun()), a judge run attaches as a child of the run it scores, in the same trace. Its spans export with nestedUnderParent: true, and the trace keeps the scored run's name, input, output and tags.
  • Smaller observability fixes:
    • Interrupted requests (#25861): a model request cancelled by a queued signal gets its own MODEL_INFERENCE span with finish reason interrupted.
    • Time to first token (#25878): each request now records its own first-token time.
    • Durable agents (#26184): they run the model call inside the model step span.
    • Trace queries (#25111): advanced trace queries gain matches / notMatches text operators.
    • Leaked keys (#26243): internal keys such as channel bot tokens no longer leak into traces and score records.
  • Why it matters for BQAA: two of these change how rows should be counted. A cost rollup has to group by usageId, not just by span. Judge runs now sit inside the scored trace, so "count runs per trace" needs to exclude nestedUnderParent spans. Mastra's own cost history also steps up for reasoning models from this version, which is an artifact of the change, not a change in usage.

NEW — SSCBench: Evaluating the Evidential Validity of Fault-Injection Tests for Tool-Using LLM Agents — https://arxiv.org/abs/2610.11514

He, Dong, Guo, Liu, Xu (Jiangnan, Nanjing, Zhejiang, Wuxi), cs.SE, submitted Oct 8. Full PDF read.

  • The question: when an injected fault propagates, did the agent rely on it despite contradicting evidence, or before that evidence was visible? The paper defines per-run event times (§III):
    • fault delivered (T_F);
    • valid counterevidence fully visible to the model (T_E);
    • first dependent use of the affected fact (T_S);
    • first faulty reliance (T_U).
      Each run is then labelled pre, late or absent arrival. Counterevidence must meet five conditions: equal authority, same entity, same scope, independence from the fault, and sufficiency using only what the agent can see. Evaluator-only state never counts.
  • Setup: two τ-bench domains (retail, airline) and four fault operators: ReturnDate, PaySource, ItemOption, and WriteEffect (a suppressed write that still returns status: success). There are 120 admitted seeds, each with a recorded witness showing the evidence could arrive before use. Five model configurations produce 1,191 faulted runs (Table I).
  • Arrival varies by run, not by case. For WriteEffect, one model saw the evidence before use in 29/29 runs, another never saw it (30/30 absent), and a third saw it late in 20/25 (Table IV). Of 89 seed–configuration groups, 11 changed arrival condition across repeated runs. Removing the read-back cue cut read-backs from 61/115 to 18/115, cut pre-use arrival from 54/115 to 0/115, and raised adoption from 76/115 to 115/115 (§VI-B).
  • Aggregate adoption hides a thin claim. 101 of 141 WriteEffect runs adopted the fault. Of these, 44 eventually saw counterevidence: 17 before first use and 27 after. The other 57 never saw it (§VI-C, Fig. 4).
  • Stopping endorsement is not the same as preventing the error. In 14 of 17 WriteEffect runs, the agent saw the evidence before its first error and still endorsed the fault at the end. In 26 of 27 late-arrival runs, it stopped endorsing it. Neither shows that the external write was repaired.
  • Automated trace diagnostics (Table V):
    • An LLM trajectory judge reaches adoption F1 of .64. Adding the fault contract raises it to .82, and exact first-reliance step to 49% (from 34%).
    • AgentRx reaches F1 .82 but exact step in only 51% of runs. Its recall is 93% / 90% / 9% across pre / late / absent runs.
    • A mined-invariant checker returned a step in 74 of 88 runs but never the exact one (51% within ±1). It flagged 29 of 32 faulted runs that never adopted the fault.
    • Human labels agreed strongly (κ = .972 adoption, .985 arrival).
  • Limits:
    • Two τ-bench domains, four operators and five configurations.
    • Arrival-conditioned comparisons are descriptive, not causal.
    • Case admission and event labels depend on semantic judgments under frozen rules.
  • For BQAA: the measurement needs one thing BQAA can provide: an ordered ledger of what the model actually saw, kept separate from evaluator-only state. With per-step "observation entered context" and "fact used" events, T_E < T_S becomes a query rather than a manual review. The paper's four recommendations translate directly into reporting rules:
    • measure arrival per run;
    • report each claim with its own denominator;
    • report prevention, revision and repair separately;
    • validate any automated oracle on the step it localizes, not just its verdict.

NEW — TestJack: Should you trust the results in coding benchmarks? Agentic Coding Benchmarks Auditing via Evaluator Evolution — https://arxiv.org/abs/2610.10619

Yao, Wang, Sen, Chen, Ray, Song (Columbia, UC Berkeley, George Mason), cs.SE, submitted Oct 7. Full PDF read.

  • Method (§3): for each benchmark-passing trial, an audit agent (GPT-5.5 in Codex) builds three copies of the repository: with the trial's patch, with the reference patch, and with no patch. It then:
    • breaks the prompt into a checklist of requirements;
    • looks for code paths the official tests never execute, hard-coded or special-cased reward hacks, and defects surfaced by mutation testing;
    • writes tests that must fail on the trial and pass on the reference solution.
      A separate reviewer agent keeps only tests that the prompt itself justifies. A trial is refuted only by a surviving "witness" test.
  • Headline (Table 2): 1,545 of 4,487 passing trials (34.4%) are refuted, and the resolution rate over all 8,862 trials falls from 50.6% to 33.2%. The failure models are Claude Opus 4.6–4.8, GPT-5.5/5.6 and Gemini 3.1 Pro.
BenchmarkPasses refuted
DeepSWE43.5%
SWE-Marathon53.6%
SWE-bench Pro29.2%
SWE-bench Verified7.6%
SkillsBench18.2%

The benchmarks with verifiers written from scratch score worst.

  • Cheaper variant (Table 3): analyse the task once, audit 3 randomly sampled trials per task, and replay their witness tests on every other trial. This recovers 72.4% of the per-trial refutations at 84.6% lower cost ($4,037), with 49.2% precision against the per-trial audit. Static augmentation (SWE-ABS) recovers only 9.9% (Table 4).
  • Underspecified prompts (App. A.2, B.2): a requirement counts as "ambiguous" if the prompt does not state it and most models skip it. Trials are not refuted on ambiguous requirements; the prompt is reported instead. 29 of 113 DeepSWE tasks have such prompts.
  • Worked examples (App. C):
    • One SWE-bench Pro task grades a single 531-byte test that misses five of six required behaviors. The passing trial never creates the database column it needs.
    • On another, the trial returns a literal failed_deletes = 1 and passes a single-conflict fixture.
  • Limits:
    • It needs a reference solution and well-formed tasks.
    • Its auditors are LLMs.
    • Recall and precision are measured against the per-trial audit, not human labels.
    • It excludes GPU-bound and ultra-long-horizon tasks.
  • For BQAA: a pass/fail verdict needs the evaluator version and evidence stored with it, so scores can be recomputed when the evaluator changes. TestJack's witness tests are exactly such a change: replaying new checks over stored runs moves historical pass rates by 17 points. An eval table keyed by (run, evaluator_version, witness_id) supports that replay. A table that stores only a boolean does not.

NEW — Opera: A Verbal Critic Framework for Long-horizon Coding Agents — https://arxiv.org/abs/2609.33987

Mei, Hu, Dai et al. (Salesforce AI Research, Rutgers, Lehigh), cs.CL, v1 Sep 27, v2 Oct 8. Full PDF read.

  • How the critic works (§3):
    • It reviews every k turns, and also immediately on five events: idle, repeated action, error, claimed completion, and final patch submission.
    • Each review either lets the agent continue or opens one note. A note names one of nine typed operators (for example state_transition_review or submission_readiness_review), cites evidence, and fixes a resolution criterion.
    • An admission audit must accept the note before it is delivered. A release audit closes it only when the criterion is met on visible evidence.
    • Adherence (did the agent try the fix? checked by rules) is tracked separately from resolution (is the problem gone?).
  • Results: with Qwen3.8-27B as the policy and GPT-5.6-Sol as the critic, Opera beats four critic baselines on all three benchmarks (Table 1):
BenchmarkNo criticOpera
Terminal-Bench 2.165.973.8
SWE-Bench Pro (100-task subset)75.379.3
DeepSWE32.441.3

The margins over the best baseline are small: 0.6–1.9 points. Weaker policies gain up to 12.4–15.0 points (Fig. 4).

  • The audit carries much of the gain (Table 5): without both audits, the gains drop to +2.6 / +3.0 / +4.5 points.
  • Critics have a cost (Fig. 6b): stronger policies are rescued more often but also regress more often (Qwen3.8-27B: 21.3% rescue vs 11.5% regression; DeepSeek-V4-Flash: 28.3% vs 11.8%). Immediate adherence is a poor proxy for resolution (Fig. 9, App. C.1).
  • Training data (Table 3): fine-tuning Qwen3.5-9B on critic-guided runs of its own policy matches fine-tuning on a stronger teacher's runs on held-out SWE-Bench Pro (38.9 vs 39.5). Unlike teacher runs, which drop Terminal-Bench from 23.6 to 7.9, it keeps Terminal-Bench performance (25.8).
  • Deployment (App. A): Opera sits as a proxy in front of the model endpoint and never blocks the agent. It logs every review with its trigger, decision, filter and audit verdicts, and delivery outcome.
  • Limits:
    • SFT is tested on one model with one out-of-domain benchmark.
    • The SWE-Bench Pro set is a 100-task subset.
    • Self-critique compute is not matched.
    • Baselines were re-implemented on Opera's schedule.
  • For BQAA: treat critic or guardrail interventions as first-class rows: note id, operator, trigger, audit verdict, adherence turn and resolution turn. That makes the rescue-vs-regression split a standard report. It also exposes when "the agent followed the advice" is being mistaken for "the problem was fixed".

Six-week EV

  • Gateways become agent-analytics products. LiteLLM Lens (stable) and Mastra's querySpans / aggregateTraces place trace storage and model-run investigations next to the traffic. BQAA's advantage has to come from the warehouse: joins to business data, long retention, and replaying new checks over history. Expect "OTLP in, findings out" to become the default expectation for buyers.
  • Verdicts need evidence and a version. TestJack (17-point drop in pass rate when the evaluator evolves) and SSCBench (adoption claims depend on per-run evidence timing) both say a stored boolean is not enough. Eval tables need the evaluator version, a pointer to the evidence (witness test or counterevidence step), and the denominator each claim uses.
  • Judges live inside the traces they score. Mastra nestUnderParent and Opera's proxy critic both put evaluation spans inside the agent run. Run counts, latency and cost rollups need to separate judge or critic spans from agent work.
  • Usage dedupe moves to a per-call id. Mastra's usageId, OpenInference's decision.* split (last brief) and LiteLLM's ClickHouse spend writes all change where token counts live. Expect a few weeks of double-counting bugs in cost dashboards that key on spans.
  • Typed decision guardrails go stable. LiteLLM 1.104.3 backports the decision-model guardrail to its stable line. BQAA should record fail-open and fail-closed decisions separately for these, as the carded option-channel paper recommends.

  • 2610.10619 TestJack: 34.4% of coding-benchmark passes violate the task. Store the evaluator version and witness evidence with every verdict so history can be re-scored.
  • 2609.33987 Opera: an audited, persistent-note critic adds 4–9 points but causes regressions on stronger policies. Log adherence and resolution separately.

    • title: TestJack: 34.4% of frontier coding-agent benchmark passes violate the task, shown by tests that pass on the reference solution
    • arxiv: https://arxiv.org/abs/2610.10619
    • card text: Prompt-grounded witness tests, each checked against the reference solution and re-judged by a second agent, refute 1,545 of 4,487 passing trials across five benchmarks. A sampled audit with witness replay recovers 72.4% of refutations at 84.6% lower cost, against 9.9% for static augmentation (Tables 3–4).

    • arxiv: https://arxiv.org/abs/2609.33987
    • card text: Event- and interval-triggered reviews open one typed, audited note at a time and close it only when its fixed criterion is met on visible evidence.
