Case: the 2026-10-15 exec wedge — a Mac that answered but could not launch

Context

The fleet’s long jobs run on one Mac through grok-tmux-run: a tmux session, a streaming log, and a ~540-second stale watchdog (§8 launch standards). Scheduled work depends on spawning processes all day — hourly collect packs at :32, the 12-hour Field Brief at :34, evening reviews. The health signal in use was connection-level: the machine answers ListMachines, and a shell responds. No routine checked whether the Mac could still start a program.

Failure

2026-10-15, ~18:43 PT. Mac e327005d reported connected — ListMachines OK, shell OK — but newly started programs hung before running and never came back. From the on-shift collector’s episode note (vault Hunt/agent-analytics/2026-10-15-1832-agy-episode.md):

  • tmux ls hung over 10 minutes (pid 74629; another agent’s tmux list-sessions, pid 74707, hung the same way). The tmux server sat idle in select() — the hang was in the client exec, not the server.
  • sample showed the hung clients stuck at _dyld_start — they never got past the loader. codesign -dv tmux hung too; syspolicyd was not running per pgrep (amfid was).
  • Hung: tmux -V/ls, agy --version, grok-tmux-run, one gh api rate_limit call, the PATH python3, otool. Still fine: /usr/bin/python3, ls, md5, perl, jq, rg, gh --version.
  • Three exec probes at 18:50 / 18:52 / 18:54 PT (10–12 s alarms) all returned rc=142 — timed out.

The 18:32 Agy collect filed SKIP (MAC_EXEC_HANG) and staged nothing — no prompt, no session, no pack. The day’s consolidation (vault Wiki/Daily/2026-10-15-agent-analytics.md, vault commit 2d03f7b) records the blast radius: Muse 1632 left only an .incomplete skeleton, DSH 1732 never ran, Agy 1832 hit the wedge, and the 19:32 Muse collect recovered at ~20:39 PT covering the 4.5-hour gap. The same evening a review run’s tmux server hung at ~19:55 PT; it was relaunched at 22:46, one minute after a “Mac healthy” signal at 22:45 (~/work/perm-1015/RESUME.md, per the main page’s Mac run lessons). Haiyuan reports that a restart cleared the wedge — and that the two obvious bare checks, python3 -c 'print(1)' and tmux -V, had themselves hung during it.

Diagnosis

The wedge sat in process launch: clients stuck at _dyld_start, code-signing validation unresponsive, while the machine, the shell, and already-running processes stayed healthy. Every existing health signal answered “is the Mac there?”, and the true answer was useless: the Mac was there and could not run anything new. Two gaps followed. First, no skill defined a spawn-ok check, so nothing distinguished “unreachable” from “reachable but cannot exec” — collectors filed MISS_MAC-style gaps or, worse, launched into the wedge. Second, the standard probe wrapper was itself unsafe: timeout hung during the wedge, so a naive health check would hang beside everything else.

Control added

Approved by Haiyuan 2026-10-18 11:46 PT (proposal 4 of the harness update; lock Maps/Decisions/2026-10-18-harness-update-approved-1-2-4-5-6.md, vault commit d6983a6): after any Mac trouble — a disconnect, an app restart, a hang the watchdog cannot explain — check spawn-ok before any launch, relaunch or resume. Spawn-ok means both timed probes exit 0:

/usr/bin/perl -e 'alarm 10; exec @ARGV or exit 127' python3 -c 'print(1)'
/usr/bin/perl -e 'alarm 10; exec @ARGV or exit 127' tmux -V

Exit 142 means the program hung; 127 means it could not start; a probe that does not return within about 15 seconds counts as hung. Never probe with timeout — it hung in the 10-15 wedge. On any failure: kill only your own hung probes, launch or resume nothing, record gap: mac-exec-hang as a skip receipt, and ask Haiyuan for a restart. The round-3 review amendment added that the probe must also fail on a missing program or failed exec — not only on a hang.

Where it landed: the box Mac-launch-heartbeats skill (exec-wedge row) and the tmux-backed-launches skill; the vault field-brief-source-collect and harness-lab-source-collect skills; the routine prompts for the daily CLI update, the nightly audit, and the Lab collect kick; and the main page as #spawn-ok. The same lock approved the sibling fix for the evening’s other failure (the Agy idle collect): resume-first with the recorded conversation id, parking when the old process is not confirmed gone.

Measured result after

  • Probe test on this Mac, 2026-10-18 10:44 and 11:55 PDT (recorded in the lock): healthy machine → both probes exit 0; a planted hang (alarm 2 on /bin/sleep 5) → exit 142; a missing program, or a PATH without python3 → exit 127. And the decisive negative test: without the or exit 127 clause, those last two cases exited 0 — a false pass, caught by Astra in triage review round 3 and fixed before approval. The check was seen to fail before it was trusted, per the check-can-fail rule.
  • First live use, 2026-10-20 ~09:03–09:05 PT (vault Hunt/agent-manage/2026-10-20-0900-dsh-harness-lab-MISS_MAC-gap.md): after two ListMachines connected=false results, the DSH Lab collect kick ran both spawn-ok probes; they failed to spawn (“temporarily unreachable” / “local machine isn’t connected”). The kick launched nothing, recorded gap: MISS_MAC, and — correctly — did not file a restart ask, because the probes never reached the Mac: a disconnect is not an exec hang. The control’s first real invocation discriminated between the two failure classes exactly as specified.

What it costs to operate

Two probes, each seconds (worst case the ~15 s hang window), run by hand before any launch, relaunch or resume after Mac trouble — plus one skip receipt line when they fail. The controls inventory rates it report-only: it is not wired into the launcher, so discipline, not code, keeps it in the path. The review cost is already paid (three triage rounds on the wording, including the false-pass catch). The resume-first recovery path it gates still waits on one manual verification run before kicks may use it.

What remains unproven

  • The wedge’s root cause was never established beyond “exec/code-signing validation stuck, syspolicyd absent”; a restart cleared it, so recurrence is possible and unpredictable.
  • The probes were tested against a planted hang and a missing program — not against a recurrence of the real wedge. The 10-20 live use exercised the disconnect branch, not mac-exec-hang.
  • Nothing enforces the probe: a launch after Mac trouble with no probe record would surface only in review, not be blocked.
  • The related failover rows (stop, confirm the old process exited, fail over to the next Lab seat) stayed held until the freshness check runs clean — so a wedged or disconnected Mac still means missed slots, filed as skip, not automatic seat failover.
