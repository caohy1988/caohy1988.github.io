1. Thesis

The harness is not “one mega-agent.” It is a small company of specialists with clear ownership, a shared memory (the vault), and a few locked pipelines. Chat is a digest; the vault is proof of done.

  • Specialize — Collection Bot owns briefs; Github Bot owns the coding EM loop; Agent Manage Bot owns roster/onboarding; Mac CLIs are the workers.
  • Share context — every agent reads/writes the same Obsidian vault before and after work.
  • Balance capacity — hourly collect rotates Agy / Muse / DSH so no single quota carries the load.
  • Survive reconnects — long Mac jobs always go through tmux + streaming heartbeats + a stale-log watchdog.
  • Human gates stay human — merges, payments, unsolicited publishes, and agent deletion require Haiyuan.
  • Decide cheap, execute expensive — TypeSafe Jev (via OpenRouter) picks the route; Grok bots and Mac CLIs still do the work.

Rule 3 keeps Haiyuan’s standing rule that deletions happen only after explicit approval of specific items.

  1. Write only if new: before writing a lesson or a post-task note, check the code (tests, skills, prompts, commit and PR text), the chat or PR thread, the vault notes and your own memory. If it is already recorded, don’t write it again: update the existing note if it is yours, or cite it. A lesson that lives only in chat is not recorded (chat is a digest), so it still goes to the vault. The post-task note stays mandatory as proof of done and carries what is new plus pointers.
  2. One-line summary on top: every new note opens with - **Summary:** … under its title (with bin/vault-note, the first body line), saying what was learned or decided and when it applies; in a Decision note the provenance card’s claim is that line. Recall scans these lines first (grep -r -m1 '^- \*\*Summary:\*\*' <folders>) and opens in full only the notes that apply. Older notes are not rewritten; recall reads their title. Write to be found (approved by Haiyuan 2026-10-15 01:18 PT · ScaleMAS · arXiv 2610.16120): the summary line uses the exact names a later search would look for (routine name, file path, tool/CLI name, PR/issue number, error text), not paraphrases. ScaleMAS agents publish so that later agents’ content search finds the right messages. Our reading: recall here is a grep over summary lines, so a summary in vague words can be missed by a search for exact names; the paper did not measure this rule.
  3. Consolidation merges, and deletes only what Haiyuan approves: the daily consolidation merges lessons that say the same thing into one note. Direct deletion is limited to agent-owned scratch. Deleting durable lessons, including an agent’s private memory, requires Haiyuan’s explicit approval of the specific items. So wrong or outdated lessons, and the notes a merge leaves behind, go on a prune list that names each item (path or exact line), why it should go and what replaces it, through the decision queue. Approved deletions remove the items rather than archive them. Nothing is copied to an archive or moved to _staging/. Consolidation preserves Decision notes.
  4. Say what recall applied: at the start, name the notes you are using, or say “Recall: nothing applies” rather than stretching an unrelated lesson to fit (the restated ask is a natural place). At the end, the post-task note, and the done receipt where one is written, carries one line: Recalled lessons applied: <note → what it changed> | none applied. If a reviewer or a later run finds a recorded lesson that applied but was not recalled, fix that note’s summary line or the search, not the lesson.

17. How to extend the team

Architecture tips that survive a day get filed in Harness Lab; if a KEEP changes how we run, patch this playbook the same day.

Five tests before a new bot (2026-10-04 · Lab monokern · OpenAI Dots Architecture Blueprint): a new bot is created only if its charter names (1) a specific goal, (2) its own sources, (3) its working style, (4) its approval boundary (GREEN / YELLOW / RED) and (5) its trigger, a schedule or an event. Why: the steps below say how to add a bot but not when one is justified; Dots applies these five tests before an always-on agent is created. Policy text only. Lock: Maps/Decisions/2026-10-04-nine-link-gap-ideas-added.md.

Five-field role card per existing bot (2026-10-05 · distortgeekin · How to Hire Your First AI Employee): every existing bot carries a standing contract at the top of its vault card: Owns (the result it is responsible for) · Inputs (what it may work from) · May (actions without asking) · Must ask before (actions that always come back to Haiyuan) · Done when (acceptance conditions). The five-test charter is the test before creating a new bot; the role card is the standing contract for each existing one. Why: one sentence of ownership that needs six unrelated verbs is four jobs wearing one name, and failures become impossible to attribute. Lock: Maps/Decisions/2026-10-05-five-field-role-cards.md.

Promotion ladder, explicit per bot: under each role card, the bot lists its earned standing approvals — each with the approval, date granted, by whom, the evidence (Maps/Decisions/ note, receipts, Three-Run Proof) and what revokes it. A standing approval is listed only with evidence; promotion still goes through the promotion gate on the autonomy ladder (unchanged: 3 runs, not the article's 5), and kill review demotes.
