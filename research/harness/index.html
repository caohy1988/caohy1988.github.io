1. Thesis

The harness is not “one mega-agent.” It is a small company of specialists with clear ownership, a shared memory (the vault), and a few locked pipelines. Chat is a digest; the vault is proof of done.

  • Specialize — Collection Bot owns briefs; Github Bot owns the coding EM loop; Agent Manage Bot owns roster/onboarding; Mac CLIs are the workers.
  • Share context — every agent reads/writes the same Obsidian vault before and after work.
  • Balance capacity — hourly collect rotates Agy / Muse / DSH so no single quota carries the load.
  • Survive reconnects — long Mac jobs always go through tmux + streaming heartbeats + a stale-log watchdog.
  • Human gates stay human — merges, payments, unsolicited publishes, and agent deletion require Haiyuan.

5. EM task loop (intent → plan → PR)

Github Bot CHY1988 acts as engineering manager for the coding team. Code is not the bottleneck — plan, review, and merge still need a loop. Each stage commits an artifact the next stage can read. Humans sit at the gates. The agent that wrote the code cannot approve it.

Roles

RoleWhoJob
Product ownerHaiyuanAccepts intent.md / spec.md; only merge & production gate
EMGithub BotCommits artifacts, fires the next play, triages review, starts the next independent slice; 5‑min heartbeat babysitter
ImplementerClaude / Fable (default)Implements from accepted plan.md; opens PR; cannot LGTM itself
ReviewersCodex / Astra + KimiReview the GitHub PR after it exists; dual LGTM = agent-complete, not shipped
Research originatorhuman or scout botWrites Stage‑1 intent.md (problem, why, constraints) — not a coding task

Artifact chain

intent.md → spec.md → plan.md → PR + tests → dual review → human merge → pipeline ↑ │ └──────── incident / broken demo / failed control band ──────────────┘
  • An accepted intent.md triggers design.
  • An accepted spec.md triggers plan mode.
  • An accepted plan.md triggers Claude implementation.
  • A PR URL existing triggers Codex + Kimi (never before).
  • Dual LGTM + product-owner merge triggers ship. Dual LGTM alone is not merged.

Artifacts live next to the code (intent/, repo-root spec.md / plan.md, or the repo’s existing docs path — e.g. board-pack intent.md + plan.md). Git history is the audit trail.

What each markdown is for

intent.md Problem, why now, constraints, non-goals, success signal. Written by research/product — not by the implementer inventing scope mid-build.
spec.md Observable behavior / acceptance criteria the reviewers will check against. Product owner accepts before plan mode.
plan.md Ordered slices, claim map, files to touch, test plan, and “done” definition. Implementer works from this file; reviewers check the PR against it. Review fix passes append a short record (what changed, which finding) instead of rewriting history silently.

Play-by-play (one slice)

  1. Read vault — EM + implementer pull AGENTS.md, Decisions, prior Ship notes for this area.
  2. Commit intent → spec → plan if missing (any slice bigger than a one-line fix).
  3. Haiyuan accepts intent/spec when the change is consequential.
  4. EM launches implementer via grok-tmux-run + stream-json + watchdog; prompt points at the committed plan.md.
  5. Implementer builds, runs the repo’s one-command tests, commits, pushes, opens the PR — does not wait for reviewers.
  6. EM requests Codex + Kimi on the PR URL. Local CLI review is optional extra, never a gate.
  7. EM triages — P0/P1 block dual LGTM; P2s get a fix pass on the same branch/session id. Recurring findings go into CLAUDE.md / a skill, not another one-off FIX prompt.
  8. Dual LGTM → ping product owner. Merge only if Haiyuan asked (or a standing order for that repo).
  9. File vault — Ship/builds or Ship/rfc note with PR URL, session ids, follow-ups.
  10. Next independent slice starts without waiting on org APPROVE of the previous one.

Clay plays (always on)

  • CLAUDE.md at repo root — build/test/lint, conventions, “things Claude gets wrong” (< 1 page).
  • REVIEW.md — identical reviewer passes every PR; check against spec.md + plan.md.
  • Skills for advisory policy; hooks for must-hold rules (no secrets in diff, no push to main, no weakening tests during a fix).

What the EM does not do

  • Start Codex/Kimi before there is a PR URL.
  • Treat dual LGTM as merged.
  • Stall the next independent slice on org APPROVE.
  • Cold-start Claude/Codex/Kimi when a session id for that PR/slice already exists.
  • Put Haiyuan back on the critical path of mid-build approval prompts.

EM also runs a 5‑minute heartbeat across live agent tasks (babysitter layer). It does not replace Mac grok-tmux-watchdog (~540s) — both apply.

7. Coding loop (SDLC)

Github Bot runs an AI-native Plan → Design → Build → Test → Deploy → Maintain loop. The detailed EM playbook is in §5 (intent.md → spec.md → plan.md → PR → dual review → human merge).

  • Implementer (default): Claude Code / Fable
  • Reviewers: Codex/Astra + Kimi (dual LGTM on the critical path)
  • Optional parallel: Muse Spark or DSH when Haiyuan asks — not required for dual-LGTM
  • Merge: Haiyuan only
  • Context: every stage also files Obsidian notes so the next agent inherits state (§4)

No-exit-while-waiting: Mac agents must not end a turn waiting on background CI/live jobs with a dirty tree. Foreground to a durable exit, or hermetic-first push then a second pass.

8. Mac launch standards

Standing order for every long Mac CLI run (Claude, Codex, Kimi, Agy, Muse, DSH):

  1. Launch via ~/bin/grok-tmux-run <session> -- <cmd> (logs under ~/Library/Logs/grok-tmux/). Never bare nohup from Grok Shell.
  2. Streaming required — Claude stream-json, Muse --json, DSH collect tee stdout/stderr; no long buffered text-only launches.
  3. Attach grok-tmux-watchdog (~540s stale) with --on-stale resume of the same session.
  4. Reuse each tool’s session id per PR/slice; don’t cold-start follow-ups.

Collect launch snippets

# Muse (odd hours in the old even/odd split; now hour%3==1)
cd ~/Documents/agent-analytics-research
grok-tmux-run muse-collect-HH32 -- \
  muse exec --json --trust-workspace --disable-approval --prompt-file prompt.md

# DSH (hour%3==2) — Flash for the run, then restore coding default
grok-tmux-run dsh-collect-HH32 -- \
  dsh-collect-pack prompt.md

Outer loop → inner loop

Grok bots orchestrate (prompts, routines, EM babysitting). Mac CLIs / Cursor Cloud Agents execute. Obsidian is the shared memory across both layers.

13. How to extend the team

  1. Decide the layer — Grok bot (orchestrator) vs Mac CLI (worker).
  2. Agent Manage Bot creates/organizes Grok bots; onboards Mac CLIs (binary, auth, usage card, vault card).
  3. Vault — add Agents/<slug>.md, update Maps/Roster.md + AGENTS.md, file a Maps/Decisions/ lock.
  4. Hooks — extend install-agent-hooks.sh if the CLI has an AGENTS/skills home.
  5. Routines — owning Grok bot schedules the cron/event listeners (Collection Bot for packs; Github Bot for coding EM).
  6. Usage — add a collector + card in usage-dashboard/collect_and_build.py, refresh, push.
  7. Never put keys in the vault or hub HTML. Rotate anything pasted into chat.
