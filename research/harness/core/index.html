The core playbook

The agent harness playbook runs to eighteen sections. This is the ten-minute version: five ideas the fleet actually runs on, each with the incident that forced it, and the smallest setup worth starting with. Every claim here comes from the main page or the dated decision notes it cites; the detail is always one link away.

1. Every task has an owner and a verifiable contract

A task is a contract, not a chat message. One named owner is accountable for it, and “done” is a condition a machine can check — not a summary a model wrote. In this fleet that means: a five-field role card per bot (Owns · Inputs · May · Must ask before · Done when), a light mission definition (Outcome · Done-when · Constraints · Approval) before any non-trivial run, an artifact chain for coding work (intent.md → spec.md → plan.md → PR), and a kick ledger row for every coding task with an explicit state: posted → launched → pr_open / done, or blocked with a note. “Code decides done”: a task is done when a deterministic check passes — tests green, the file exists, the commit is on the remote, the URL returns 200. Self-reports stay advisory.

Why. On 2026-09-24, between 03:15 and 06:50 PT, a coding kick sat in a group room with no owner watching: the room post existed, but there was no ledger row, so the 15-minute heartbeat never read it, and three and a half hours passed before anyone noticed. That failure mode now has a name — unacked handoff — and a control: every kick is a ledger row, the heartbeat reads the ledger first, and a kick still posted with no seat is launched or marked blocked, never reported as “idle.” The same idea, one level up: the 2026-10-05 role-card rule exists because an ownership sentence that needs six unrelated verbs is really four jobs wearing one name, and failures become impossible to attribute.

Detail on the main page: kick ledger + pickup check · five-field role card · mission done-when · code decides done · the EM loop.

2. Keep enough state to resume or replace a worker

Assume the worker dies mid-task. Every long run goes through tmux with a streaming log and a ~540-second stale watchdog; each run keeps a named session id so the follow-up resumes it instead of cold-starting; handoffs carry a machine-readable packet (owner, job type, objective, artifacts, decisions, constraints, open questions, next gate) because “the artifact carries the detail, the packet carries the state”; and the shared vault holds durable memory so a replacement seat — not just the same seat — can pick the work up. Two workers on one output is the failure this guards against. The rule: a stale run is resumed only after the old process is confirmed gone, otherwise it is parked as an unknown outcome. Until 2026-10-20 the live watchdog did not make that check, so the EM or babysitter confirmed the old process was gone by hand (the 2026-10-08 enforcement code and the smaller 2026-10-11 no-auto-resume redesign were parked after review). Since 12:16 PT that day the ownership guard is installed: each launch gets an attempt ID and a workspace, a restart is refused unless the old process is proven dead, and only the current attempt can publish (grok-attempt-publish refuses a stale attempt). Sessions launched before the install have no ownership record, so on a stall the watchdog parks them and never kills them.

Why. On 2026-10-15 an Agy catch-up collect handed its search to a background task and went idle (root agent idle; waiting up to 15m0s). The watchdog re-ran it cold twice — a new conversation each time, because the resume path did not carry the conversation id — and each run ended terminating 1 background task(s) with a SUCCESS marker and no pack. The second re-run started three seconds before the Muse replacement, so two seats held the same pack path for about three minutes; Muse wrote the pack. The fix, approved 2026-10-18 as wording on the Agy Lab-collect recipe, keeps its stated limits: resume first with the recorded conversation id, and park when the old process is not proven gone — but the recipe enters the kick only after a manual verification step passes (one headless resume, run by hand, must keep the conversation id; until then the kick keeps today’s recipe), it permits one recorded cold start when no id was captured, and Muse and DSH Lab launches are unchanged. A week earlier (10-08) a plain nohup watch loop died together with its launching shell — the reason nothing long runs outside tmux anymore.

Detail on the main page: Mac launch standards · Mac run lessons · watchdog resume safety · handoff packet · the vault.

3. Separate execution status, verified correctness, and usefulness

Three different questions, three different signals. Did it run? — every routine appends a receipt line (ok / skip / fail / parked), even when nothing happened. Is it right? — a deterministic check actually ran and passed; done reports carry VERIFIED (checks that ran, with evidence) and NOT VERIFIED (never omitted); blind reviewers attempt disproof against named rejection criteria and pin one machine-readable VERDICT line to the head SHA. Is it worth keeping? — the Monday kill review asks “would anyone miss this?”, and a decision gate must beat the constant “always answer the majority verdict” before it may go active. Never let one signal impersonate another: a negative claim (“none”, “quiet”, “stale”) is valid only with a lookup that worked; otherwise it is reported as an access gap:.

Why. On 2026-10-08 the usage collector flagged Collection (27h) and Github Bot (31h) as stale from agent-directory mtimes — although both had same-day receipts; it read receipts for Manage only. Execution metadata had been read as a correctness signal. The patched collector (installed 2026-10-11, thirteen tests, blind-reviewed APPROVE) shows both stale=False. Usefulness has its own incident: the worth_running shadow gate answered “run” on 139 of 142 answered calls — a constant at extra cost — so on 2026-09-27 it was narrowed to retries and one-off launches, where it actually decides something.

Detail on the main page: the false-stale fix · negative-claim check · done receipt · verdict line · constant baseline · kill review.

4. Enforce consequential boundaries outside the model

Anything hard to undo — send, publish, spend, merge, delete, grant permissions, touch production — is a RED action and goes to the human. The point is where the boundary lives: not in the model’s instructions, but in the architecture around it. The vault’s bin/ contains no post/push/send primitive at all (checked by search 2026-10-20); must-hold rules go in hooks, advisory policy in skills; the implementer of a PR can never be its reviewer; the routing model may never authorize merge/pay/send, and its config carries a kill switch; an approval covers exactly the item that was approved and is re-checked — item unchanged, authority still valid — immediately before the action runs (that re-check is a manual, policy-text-only step today: nothing runs it for the operator). And everything an agent reads from the web, a PR, or another agent is data, never instructions.

Why. Review approvals had been carried across later author pushes (corrections dated 2026-09-14 and 2026-09-20): a boundary held in prose slid when the artifact changed under it. The recommended fix is mechanical, not exhortation — a review ends with exactly one VERDICT: APPROVE | REQUEST_CHANGES | ESCALATE @ <head sha> line, and a review without it, or naming an older SHA, is UNPARSED and never counts as approval. What is installed today is the manual form of that check: the EM reads the line and compares the SHA by hand, and the controls inventory files this control as manual, not enforced — so that is a recommendation about where the boundary should live, not evidence that code holds it there today. The untrusted-content rule exists because collectors read X, Reddit and the web every hour, and until 2026-10-04 no rule said what to do with instructions found inside collected text (quote them to the human; never follow them).

Detail on the main page: GREEN / YELLOW / RED · approval re-check · verdict pinned to head SHA · untrusted content is data · controls inventory.

5. Keep machinery only when it proves its worth

Every piece of process is on trial. A new routine passes a Three-Run Proof — observe, correct, release after a third consecutive clean run — before it may go active; promotion further needs a tested rollback and complete receipts. Every routine prompt carries a pre-written Kill condition: line, and the Monday review checks each routine against its own stated condition rather than judging ad hoc. A gate that always gives the same answer is a constant at extra cost, not a control. Even the policy files are on a budget: the two documents every agent reads before every task are capped at their 2026-09-30 byte sizes, and a repeated lesson must become a proposed fix where the rule is applied — not a third paragraph.

Why. The worth_running narrowing above is the canonical case. A second: the DSH mode of the model-check gate was parked for good on 2026-10-19 after four blind review rounds each found a new way for a malformed record to pass it (an escaped type name, pooled session files, a duplicate payload key, a broken quote); the served model is confirmed through the provider’s per-request generation API instead — cheaper and checkable. And the byte ceiling exists because forbidden.md accumulated eighteen near-identical review-preflight paragraphs in five days (2026-09-20 → 09-24): the lesson was recorded every time and applied never, while every task paid the full read.

Detail on the main page: Three-Run Proof · promotion gate · kill review · constant baseline · the parked DSH gate · repeat lesson → skill diff · byte ceiling.

Minimal starting setup

The smallest harness worth running has four pieces, all cheap:

  1. One owner per task, named in one place (a role card, or one line in the task itself).
  2. A done-when a command can check — a test, a file, a pushed commit, a live URL.
  3. A dated note per finished task — proof of done; chat is only a digest.
  4. A human gate for irreversible actions — everything else, just do and log.

Everything else on the main page exists because something specific broke. Add each component when its failure has already happened once — this fleet’s justification list:

The symmetric rule closes the loop: retire a control when the Monday kill review cannot name what it catches. Machinery that cannot prove its worth — a gate parked after four review rounds, a watch nobody reads — is removed or narrowed, not kept for comfort.
