01 / Where traces come from

1. Where traces come from

In plain terms

A single view may not capture the whole picture.

Different tools watch an agent from different places. Each place sees part of the work. This page starts there, then asks a simpler question: once traces are captured, how are they stored, found and used?

The detail and citations follow below.

Josh Rosen’s survey Agent Traces: Patterns for Capturing Agent Execution (article text retrieved 26 October 2026; publication date UNVERIFIED) makes the framing point this comparison needs: “no single instrumentation point necessarily has the whole picture”; the survey describes a range of patterns for addressing that visibility problem (Rosen). Watching the model through API instrumentation or a gateway yields messages, responses, configuration, latency, tokens, cost and errors, but “you’re still observing the agent through its conversation with the model” (Rosen, ‘Watching the Model’). The instrumented harness records operations directly from inside the loop — Rosen places LangSmith’s capture through LangChain and LangGraph, Google’s Agent Development Kit tracing, and Microsoft agent tooling in this family, while noting that blind spots can remain inside tool calls (Rosen, ‘The Instrumented Harness’). Other records arrive as native session files, OpenTelemetry with GenAI semantic conventions, environment evidence such as diffs and test results, and evaluator scores layered on afterwards (Rosen, ‘Native Execution Records’, ‘Distributed Tracing’, ‘Environment Evidence’ and ‘Semantic Enrichment’).

SmithDB and BQAA both sit downstream of harness instrumentation, but they answer different follow-on questions. LangSmith calls traces “the agent’s core behavioral record” and built a database to serve them interactively (Intro, ‘Agents present a new data problem’). BQAA writes harness events into a BigQuery table so they can be analysed with SQL alongside everything else in the warehouse (ADK, ‘BigQuery Agent Analytics plugin for ADK’). Rosen’s closing concern — the need to “reconstruct an increasingly large and fragmented amount of execution data into something humans can actually comprehend” (Rosen, ‘Where Tracing Is Going’) — is where the two architectures diverge: in the sources reviewed SmithDB presents reconstruction as indexed point access, BQAA as SQL and SDK query over warehouse rows.

02 / Why LangChain built SmithDB

2. Why LangChain built SmithDB

In plain terms

Agent traces can be big, nested and long-running.

  • LangChain says that mix is why it built SmithDB.
  • The key idea is simple: “In SmithDB, a run is a sequence of events, not a single immutable row”.
  • The hard part is keeping many kinds of query fast at the same time.

The seven query patterns are named in the text below.

The stated problem

LangChain’s case is that agent traces outgrew general-purpose observability stores on three dimensions at once: “hundreds of nested spans, multi-modal content, and spans that stay open for hours”, with trace volume and individual payload size both exploding since LangSmith launched in 2023 (Intro, ‘Key Takeaways’ and ‘Agents present a new data problem’). “A modern agent trace can have hundreds of deeply nested spans”, and traces “arrive in pieces: a start event for an agent span can arrive minutes, maybe even hours before an end event” (Intro, ‘Agents present a new data problem’). The search post quantifies the payload side: the inputs and outputs fields are “the overwhelming majority of its total bytes”, “1 MB+ payload sizes … are common, with some of these stretching to hundreds of megabytes uncompressed”, dwarfing identity and timestamp columns “by orders of magnitude” (FTS-1, ‘Challenge 1’). Seven query patterns must all stay fast over that shape — random access, interactive filtering, full-text search, JSON filtering, tree-aware queries, thread reconstruction and aggregations — “with self-hosting and multi-cloud requirements” (Intro, ‘Agents present a new data problem’). Section 3 takes each pattern in turn.

Judgement: the load-bearing claim is not scale alone but the conjunction: huge nested payloads and long-open mutable runs and interactive content search. A store that handles any two without the third does not meet LangChain’s stated requirement. That conjunction is the right test to hold BQAA to in section 5.

Architecture in one pass

SmithDB is described as “LangSmith’s data layer purpose-built for agent observability and evaluation workloads”, “built in Rust” on “the Apache DataFusion query engine and Vortex file toolkit, with heavy customizations”, comprising object storage for durable trace data, “a small Postgres metastore for segment metadata”, and stateless ingestion, query and compaction services (Intro, ‘Introducing SmithDB’). At launch LangChain reported “100% of US Cloud ingestion” and “100% of tracing UI query traffic” on SmithDB, with run rules, bulk export and experiments “nearing completion” and self-hosted availability listed under “Soon” (Intro, ‘SmithDB is now serving production traffic’). Underneath, it is “an object-storage backed log-structured merge tree (LSM)” with five components: an ingestion service that “batches them per partition and time bucket, and writes immutable files”; a metastore recording “location, time bounds, row counts, and update/delete vectors”; a query service with “custom execution plans that understand LangSmith run semantics and object storage” plus heavy SSD and memory caching; a compaction service; and a cluster manager that “assigns live service nodes to key ranges” so repeated queries land on nodes likely to hold the right cache (Intro, ‘Key engineering challenges’). The migration docs add the one partitioning fact users now feel directly: project_id is “the SmithDB partition key” and becomes required on per-trace run listing (Mig-Traces, ‘Traces: list runs’).

Data model: a run is a sequence of events

The central modelling decision is stated plainly: “In SmithDB, a run is a sequence of events, not a single immutable row” (Intro, ‘Multiple events per run’). Agent spans stay open through “model completion, tool calls, retries, background work, or handoffs to other agents”, and waiting for span end before writing “would be less than ideal”; instead “extra care is taken to fanout filters to target specific events and merge events at query time in an efficient manner”, and the same multiplicity shapes compaction (Intro, ‘Multiple events per run’). Two supporting mechanisms matter for the comparison. First, late materialisation: “Core rows carry pointers to large-field files, and the query engine only fetches those large payloads when the query actually projects them”, so list and filter queries do not read “megabytes of JSON unless the user actually opens the run” (Intro, ‘Late materialization of large fields’). Second, mutations without rewrites: deletes and upgrades attach “deletion and upgrade vectors to segment entries” in the metastore, interpreted on the query and compaction paths, with file rewrites deferred to compaction — important because “only a small subset need to be retained for a long time based on the content of the particular trace” (Intro, ‘Deletes, TTL, and Retention changes’).

Event merge and time-tiered compaction

Ingestion optimises for write latency and therefore “produces many small immutable segments”; compaction “rewrites write-optimized segments into query-optimized segments while applying deletes, upgrades, TTL expiry and index merging” (Intro, ‘Key engineering challenges’ and ‘Time-tiered compaction’). The tiering is explicitly age-aware: “Recent data is more likely to receive end events, so compacting it into huge files too early would create unnecessary write amplification”, while older, stable data is “worth collapsing into larger files” (Intro, ‘Time-tiered compaction’). Freshness does not wait for object storage round-trips: each segment records its writer, and if that writer is online the planner can “scan those files directly from the ingestion node’s local SSD and memory cache” (Intro, ‘Reading fresh data from ingestion nodes’). For the newest-runs queries that dominate the UI, SmithDB “walks backward through time and builds a bounded time window over the newest candidate segments”, turning “sort everything, then limit” into streaming the newest slice and stopping “as soon as correctness allows” (Intro, ‘Progressive querying over object storage’). Sticky routing completes the picture: the cluster manager divides the keyspace into slices assigned to stable nodes, LangChain citing Google’s Slicer and Databricks’ Dicer as inspiration as spelled in the post, so related requests reuse cached metadata and segment bytes (Intro, ‘Cluster management and sticky routing’).

Storage, portability, deployment

“Because SmithDB is backed by object storage, there are no local disks to manage. Query and ingestion services are stateless. The system scales by adding compute, while durable data lives in object storage” — positioned against “traditional database clusters that require local disks and complex sharding” for self-hosted and multi-cloud deployment (Intro, ‘Portability’). The search post restates the trade: durable data in object storage keeps compute “relatively stateless”, at a query cost “roughly proportional to (requests issued to object storage) × (bytes read per request)”, with each request carrying “tens of milliseconds to hundreds of milliseconds of latency” (FTS-1, ‘Challenge 2’). What SmithDB replaced is never named in the launch post; the migration guide says only that deprecated methods “stop working once ClickHouse is disabled” and require self-hosted 0.16 or later “independent of the data store used” (Mig, ‘About self-hosted’). Whether SmithDB is formally the ClickHouse replacement, which object stores and clouds are supported for self-hosting, and what it costs to run are UNVERIFIED from the sources reviewed; see Not verified.

03 / How SmithDB answers the core queries

3. How SmithDB answers the core queries

In plain terms

This section asks everyday questions.

  • Can I open one trace quickly?
  • Can I filter many traces?
  • Can I search the words inside them?

SmithDB publishes times for these jobs. They are vendor-reported. The measurement environment is UNVERIFIED.

LangChain publishes a latency table without dataset size, tenant mix, or hardware in the launch post reviewed. Read it as vendor-reported latencies — not a reproducible benchmark; the measurement environment is UNVERIFIED (the launch post separately reports production deployment but does not specify where these latencies were measured): “Performance is not just a nice-to-have for observability. For both humans and agents, slow observability tools become a bottleneck in the agent development loop” (Intro, ‘Performance’). Note also an internal inconsistency: the summary claims experiences “up to 15x faster than before” (Intro, ‘Key Takeaways’) while the performance section says “up to 12x faster than before” (Intro, ‘Performance’). Random access by ID

The requirement is to “instantly load an individual run or trace” (Intro, ‘Agents present a new data problem’), answered at P50 71 ms for a single run and P50 92 ms for a full tree (Intro, ‘Performance’). The documented API surface matches the shape: fetch runs for a trace by ID, now as GET /api/v2/traces/{trace_id}/runs with project_id required as the partition key, returning runs “in start_time order” (Mig-Traces, ‘Traces: list runs’); run_ids fetches “runs with a given list of run ids” and “will ignore all other filtering arguments” (TQS, ‘Filter arguments’). Late materialisation is what keeps the common case honest: opening a run pays for its large fields, listing runs does not (Intro, ‘Late materialization of large fields’).

Interactive filtering

Filtering means slicing “by metadata, feedback, latency, errors, tags, and time” (Intro, ‘Agents present a new data problem’) at a published P50 of 82 ms (Intro, ‘Performance’). The query language is comparator functions — eq, neq, gt, gte, lt, lte, has, search, in — combined with and and or (TQS, ‘Comparators’ and ‘Logical operators’). Filterable fields are a narrow, typed list: id, name, run_type, status, start_time, end_time, latency, tags, metadata_key/metadata_value, and feedback_key/feedback_score (TQS, ‘Filterable fields’). Two details matter for implementers copying the pattern: latency accepts seconds only (“Only the s suffix is supported”; m and h are not) (TQS, ‘Filterable fields’ and ‘Value formatting’), and excluding inputs and outputs via select “can significantly improve query performance and reduce response sizes, especially for large runs” (TQS, ‘Filter arguments’) — projection discipline exposed in the API, not left as folk wisdom.

Full-text search and the inverted index on object storage

SmithDB’s search subsystem is documented in two dedicated design posts (FTS-1 and FTS-2) in the sources reviewed. The starting economics are inverted relative to logs: “Typically the source:index ratio for logs is about 1:1.25. However for agent traces in LangSmith, we observed the average to be closer to 1:1.9”, because “one document can produce more index data than many small log lines” (FTS-1, ‘Challenge 1’). Without an index, “‘Find runs whose tool output mentions a timeout’ cannot scan every payload in the candidate range otherwise it would scan many gigabytes to return three rows”; term frequencies are Zipfian, so the index “must stay compact and prunable across many orders of magnitude of term frequency, all inside one file” (FTS-1, ‘Challenge 1’). The published result is full-text search and JSON filtering “with a median (P50) latency of 400 ms” over “large, deeply nested JSON documents stored in object storage” (FTS-1, ‘Overview’).

Three predicate families share one index. Path existence (json_key) asks whether a key path exists and supports LIKE on the path itself — json_key(inputs, "author.%") or json_key(inputs, "%.user_id") with patterns at prefix, suffix or infix (FTS-1, ‘SmithDB search query shapes’). Keyed value search (json_key_search) binds path to value, including multi-token phrases where “‘latency regression’ matches only documents where those words appear consecutively” (FTS-1, ‘SmithDB search query shapes’). Full-text search (search) matches any indexed value regardless of path, or a text column directly such as search(error, "timeout") (FTS-1, ‘SmithDB search query shapes’). Positions are what make the phrase case honest: the index records token offsets per document so adjacency can be verified rather than approximated by co-occurrence (FTS-1, ‘Terms, postings, positions’). At query time, multi-token phrases first intersect postings, then “decode positions only for those candidates and verify adjacency”, so a selective phrase “pays almost no positions IO” (FTS-2, ‘Three query shapes, three lookup paths’).

Why not reuse Tantivy? LangChain’s answer is specific and worth quoting in substance: Tantivy assumes mmap with effectively free random I/O while SmithDB faces “~100 ms round trips, where layout and coalescing decide query latency, not CPU”; search had to push down through the same DataFusion-over-Vortex scan pipeline “not run as a parallel query stack”; and doc IDs had to be Vortex row positions directly, with “no translation table, no second identity to reconcile at query time” (FTS-1, ‘Why we leveraged Vortex and not Tantivy’). The v1 layout failed instructively at scale: whole-column encoding let one common token inflate every term’s bit width; fixed term-count row groups let “a single high-frequency term … push one row group past 100 MB compressed” (past 500 MB in the worst case LangChain reports); and merging had to decode and reshuffle the full positions structure, dominant because positions are “70%+ of bytes” (FTS-1, ‘Our (unsuccessful) first attempt’).

The v2 layout replaces term counts with byte budgets: “32 MB of posting bytes” bounding the worst-case GET per row group and “64 MB of raw term-string bytes” per row group, with per-row-group min/max zones so “most row groups simply don’t contain anything in the predicate’s range” for prefix path queries (FTS-1, ‘Row groups, sized in bytes’). Inside a row group, an FST maps each term to an ordinal, term_info holds doc count plus postings/positions offsets, and postings and positions are separate binary blobs split into “128-doc blocks of bitpacked deltas with a VInt tail”; path existence skips positions entirely, and “a non-phrase query fetches just term + term_info + postings and never opens the positions column” (FTS-1, ‘Inside one row group’). On a representative row group with 2.79M term occurrences, the FST collapses 546 unique JSON paths from 88.8 MiB raw to 3.8 KiB, while on 1.41M unique token values it is larger than zstd but — the deciding point — directly searchable: “exact lookup, prefix and range scans, and automaton walks (LIKE, fuzzy, regex) all run directly against the compressed bytes” (FTS-1, ‘Encoding choices’). Keyed and unkeyed search share one FST by storing values as {token}\0{flattened_path}: keyed search is exact lookup, full-text is a prefix scan on token\0 (FTS-1, ‘Encoding choices’). Per-term block bitpacking means “a frequent term like agent packs at 3–4 bits per doc, a rare term never leaves its VInt tail” (FTS-1, ‘Encoding choices’).

Construction is inline, not a batch afterthought: “Index construction happens inline during ingestion. New runs become searchable within seconds”, with fresh indexes read from the writer’s local storage (tier L0) before promotion to object storage (L1), and “no separate ‘live tail’ mode and no eventually-consistent gap” (FTS-2, ‘Inverted index construction and merging’ and ‘Handling recently ingested data’). Payloads are flattened to (path, leaf_value) pairs by a JSON tape with “no per-field allocation, no numeric conversion”, tokenised by splitting on non-alphanumeric boundaries, lowercasing, dropping stop words and capping tokens at 256 characters (FTS-2, ‘Payload parsing’ and ‘Tokenization’). String interning cut construction time by “~2.2× in our benchmark” (vendor-reported) (FTS-2, ‘Sorting and interning’). At read time the planner routes each predicate per segment — index, column scan fallback, or short-circuit — “before any object-storage request”, and the Vortex scheduler merges reads “within a 1 MB gap into one, up to a 16 MB window” so a selective phrase lookup “resolves to one GET covering term_info, postings, and positions” (FTS-2, ‘One segment, many files’ and ‘From layout to GETs’). Index merging during compaction is streaming, with memory scaling “with the number of inputs being merged, not the total index size” (FTS-2, ‘Index merge’).

Judgement: in the sources reviewed, three properties here have no documented BQAA counterpart and should anchor the gap analysis: positional phrase search (UNVERIFIED whether BQAA/BigQuery surfaces beyond those sources provide it), path-pattern (LIKE on key paths) as a first-class predicate (UNVERIFIED beyond the sources reviewed), and an index whose worst-case read is bounded in bytes by construction (UNVERIFIED whether a BQAA/BigQuery counterpart with an equivalent byte-bound exists beyond the sources reviewed). On the documented SEARCH semantics reviewed, token containment alone does not subsume any of the three.

JSON filtering and tree-aware filters

JSON filtering covers “arbitrary user-defined metadata and structured tool outputs” (Intro, ‘Agents present a new data problem’), surfaced to SDK users through metadata key/value comparators — for example and(eq(metadata_key, "user_id"), eq(metadata_value, "usr_abc123")) (TQS, ‘Filter by metadata key or value’) — and underneath through the json_key/json_key_search index predicates described above (FTS-1, ‘SmithDB search query shapes’). The launch post summarises the mechanism briefly: “Terms are sorted into row groups, and every row group records min/max term zones. Exact and prefix term queries can therefore prune index row groups before SmithDB fetches postings bytes” (Intro, ‘Full-Text Search and JSON Filtering’).

Tree awareness is a three-way split for which no equivalent BQAA descendant/root filter is documented in the sources reviewed, so on that documented path those predicates are hand-written SQL (whether a BQAA helper exists beyond those sources is UNVERIFIED). Session discovery is different: the BQAA SDK does document client.list_traces() (section 5 below), which filters sessions but is not documented in the sources reviewed as a descendant-run predicate. filter “applies to the returned run”, trace_filter “applies to the root run of the trace”, and tree_filter “applies to any run anywhere in the trace tree” (TQS, ‘Using trace_filter and tree_filter’). The docs are honest about the boundary: for “predicates over arbitrary nested child-run fields, such as returned inputs, outputs, or extra payload paths, first narrow candidates with server-side filters, then hydrate root traces with child runs and traverse them locally” (TQS, ‘Using trace_filter and tree_filter’). In the new traces API the generic any-run filter disappears entirely: “The generic filter (evaluated against any run) has no direct equivalent; use trace_filter or tree_filter instead” (Mig-Traces, ‘Traces: query — Query parameters’) — the tree semantics become the only semantics.

Threads and aggregations (cost, latency, tokens)

Thread reconstruction means to “rebuild long-running conversations across many agent traces instantly” (Intro, ‘Agents present a new data problem’), published at P50 131 ms / P95 268 ms for threads filtering (Intro, ‘Performance’), with threads explicitly included in the migrated UI traffic (Intro, ‘SmithDB is now serving production traffic’). At the filter-language level a thread is still metadata — and(in(metadata_key, ["session_id", "thread_id"]), eq(metadata_value, "<your_thread_id>")) (TQS, ‘Filter by thread ID’) — while the migration guide gives threads their own method area: “Query the threads in a project and list the traces (turns) that belong to one thread” (Mig, ‘Methods by area’).

Aggregations must “compute cost, latency, token usage, evaluator scores for different filters” (Intro, ‘Agents present a new data problem’). What the sources actually pin down is narrower than the slogan. The new traces query returns each trace’s root run plus optional trace_aggregates (total_tokens, total_cost, first_token_time) so “clients never have to merge by trace_id” (Mig-Traces, ‘Traces: query’). Only total_tokens/total_cost are described as “summed across every run in the trace instead of just the root run”; first_token_time is identified separately as new, not as summed; and the aggregates object is omitted unless selected (Mig-Traces, ‘Response fields’). Feedback scores are filterable (feedback_key/feedback_score) (TQS, ‘Filterable fields’), and SmithDB is stated to back “metadata, feedback, text search, tree filters, and trace filters” (Intro, ‘SmithDB is now serving production traffic’). No aggregation latency, scan-size, or grouping-cardinality numbers are published in the sources reviewed, and the promised deep dive on “sub-second stats on massive datasets” was still future work when FTS-2 closed (FTS-2, ‘What’s next’). Fleet-wide aggregation performance is therefore UNVERIFIED beyond per-trace token/cost rollups; section 5 covers the BQAA aggregation recipes documented in the sources reviewed without claiming a measured comparison.

04 / What the SDK migration changes

4. What the SDK migration changes

In plain terms

SmithDB is not just a quiet swap behind the scenes.

People who use the SDK need new methods. Some old methods go away on stated dates. That is real work, so the dates and version numbers below matter.

SmithDB is not a transparent backend swap: “New SDK methods are required to query your traces with SmithDB” (Mig, ‘Context’). Deprecation and removal are dated and shared between each SDK method and its endpoint: all Cloud regions deprecate at end of July 2026 with removal on 31 January 2027; self-hosted deprecates at v0.16 with removal at v0.18 (Mig, ‘Deprecation and removal’). Minimum versions are Python langsmith >=0.10.15, TypeScript langsmith >=0.8.9, Java langsmith-java 0.1.0-beta.22, Go langsmith-go v0.25.4 and CLI langsmith-cli v0.2.44, the CLI querying “the same SmithDB-backed endpoints” (Mig, ‘Minimum SDK version’). Six areas move: query runs (“the largest surface area in the migration”), retrieve runs, traces, threads, dataset experiment runs, and feedback and sharing (Mig, ‘Methods by area’). One product note deserves respect from any team planning a similar cutover: “Where possible, the SDK raises a warning or error identifying the version to upgrade to, instead of failing without explanation” (Mig, ‘About self-hosted’).

Traces: from generic run queries to scoped trace queries

client.list_runs(is_root=True) becomes client.traces.query() (async in Python: “Call it with await”), and POST /api/v1/runs/query becomes POST /api/v2/traces/query (Mig-Traces, ‘Traces: query — Method name’). The semantic tightening is the story. Scope narrows from a list of projects to exactly one: “session (a list of project UUIDs) becomes project_id, a single UUID; traces.query scopes to exactly one project per call”, and is_root is removed because the method “is always scoped to root runs implicitly” (Mig-Traces, ‘Traces: query — Query parameters’). Time becomes a scan window with defaults: min_start_time “defaults to 24 hours before the request” and max_start_time to request time, replacing an unbounded start_time and an end_time that filtered a run’s own end timestamp rather than bounding the scan (Mig-Traces, ‘Traces: query’ and ‘Query parameters’). select is renamed selects, routing fields to root_run or to trace_aggregates; trace_ids is new as “a fast-path restriction to a known set of trace UUIDs, more efficient at scale than an equivalent trace_filter” (Mig-Traces, ‘Traces: query — Query parameters’). In responses, total_tokens/total_cost move off the root run onto trace_aggregates — a breaking field move that also fixes those two fields’ semantics to whole-trace sums — while first_token_time is separately new (not described as summed) (Mig-Traces, ‘Traces: query — Response fields’). TypeScript callers additionally switch from camelCase options to “the wire-format snake_case keys directly” (Mig-Traces, ‘Traces: query — Query parameters’).

Listing a trace’s runs changes shape the same way: client.list_runs(trace_id=...) becomes client.traces.list_runs(), POST /api/v1/runs/query becomes GET /api/v2/traces/{trace_id}/runs, the trace ID moves from parameter to path, and “project_id is new and required (the SmithDB partition key)” where the old call needed none (Mig-Traces, ‘Traces: list runs’). Unlike traces query, its min_start_time/max_start_time have no defaults — “omit both and runs are not filtered by time at all” — but if either is set both must be passed; selects uses “the same 44-value enum as traces.query” (Mig-Traces, ‘Traces: list runs — Query parameters’).

Errors, removals, and what it costs users

Python and TypeScript exception handling breaks deliberately, but differently. In Python, the new methods “raise new exception classes instead of the legacy langsmith.utils exception classes” — including a casing change from LangSmithError to LangsmithError — while LangSmithUserError and LangSmithExceptionGroup have no equivalent. In TypeScript, which previously used plain Error, the new methods raise new exception classes instead of plain Error (Mig, ‘Exceptions’). Java, Go and cURL error handling is explicitly unaffected (Mig, ‘Exceptions’). Feedback formula methods are discontinued with “no SDK replacement”: the retired /feedback/formulas endpoints “return 410 Gone on composite-feedback v2 and are scheduled for removal on 2026-08-20”, composite scores moving to composite evaluators built from a code evaluator plus a run rule (Mig, ‘Discontinued’).

Judgement: read the migration as the storage design surfacing in the API. Single-project scope, required partition key, default 24-hour scan windows, field projection as a typed enum, and whole-trace aggregates are exactly the disciplines an object-storage LSM needs from its callers. The cost to users is real — async rewrites, moved fields, renamed exceptions, one feature deleted — and LangChain pays it openly with dates, minimum versions, and per-language before/after examples (Mig-Traces, ‘Examples’). On the evidence reviewed, BQAA’s Python/Java table-schema auto-upgrades are additive (Kotlin does not implement Auto Schema Upgrade) rather than a SmithDB-scale forced method migration — a narrower usability credit, because BQAA has still imposed migration work outside table schema: in Java v1.8.0 and later datasetId is required and tableName defaults to agent_events, where Java v1.7.0 and earlier defaulted those values to agent_analytics and events respectively (ADK, ‘BigQueryLoggerConfig Builder options’), and the plugin no longer exports its own OpenTelemetry spans, a path the docs say is “intentionally gone” for hosts that relied on it (ADK, ‘Tracing and observability’). Whether BQAA interactive performance matches SmithDB’s published percentiles is UNVERIFIED, because no BQAA interactive percentiles are published in the sources reviewed.

5. BQAA on the same axes

In plain terms

BQAA takes a different path.

  • You then use SQL or the SDK to read those rows.
  • That helps when you want traces beside other warehouse data.

Capture and data model: typed events in one table

The ADK plugin “captures and logs critical operational events directly into a Google BigQuery table” via the BigQuery Storage Write API in Python and Java (Kotlin uses a different write path; see below), for “debugging, real-time monitoring, and comprehensive offline performance evaluation”, supported in ADK Python v1.21.0, Java v1.5.0 and Kotlin v0.8.0 as fetched (ADK, ‘BigQuery Agent Analytics plugin for ADK’). For those Python/Java writes, the Storage Write API dependency is flagged in the docs themselves: “This feature uses BigQuery Storage Write API, which is a paid service” (ADK, ‘BigQuery Storage Write API’). The SDK’s own framing is producer/consumer: the ADK plugin and the LangChain/LangGraph BigQueryCallbackHandler “emit the same schema and can write to the same table side by side”, while the SDK is “read-only over that table: trace reconstruction, evaluation, insights, the context graph” (SDK README at e42366f, ‘How this fits together’). Event coverage is broad and explicitly lifecycle-shaped — user messages, invocation and agent start/complete/error, LLM request/response/error with usage and time-to-first-token, tool start/complete/error with provenance (LOCAL, MCP, SUB_AGENT, A2A, TRANSFER_AGENT, TRANSFER_A2A), state deltas, human-in-the-loop requests, A2A interactions, and ADK 2.0 workflow events (AGENT_TRANSFER, AGENT_STATE_CHECKPOINT, EVENT_COMPACTION, TOOL_PAUSED, NODE_OUTPUT, NODE_ERROR) (ADK, ‘Captured events summary’ and ‘Use cases’). Parity is uneven and documented as such: several workflow events are Python-only, Java emits TOOL_PAUSED without the attributes.adk envelope that lets readers “reconstruct the agent execution graph and join a paused tool to the row that resumes it”, and Kotlin logs only INVOCATION_STARTING/INVOCATION_COMPLETED via synchronous tabledata.insertAll rather than the Storage Write API, without views, schema upgrade, provenance, offloading or drop statistics (ADK, ‘Captured events summary’ and ‘Kotlin support’).

Where SmithDB models a run as a mergeable event sequence, BQAA models each lifecycle moment as its own immutable row in agent_events: timestamp (ordering and daily partitioning key), event_id (Python schema version 2; the Java schema does not include it and Kotlin leaves it null — see the delivery note below), event_type, agent, session_id (“a persistent identifier for the entire conversation thread”), invocation_id (one execution turn), user_id, trace_id/span_id/parent_span_id, polymorphic content JSON, attributes JSON, latency_ms JSON, status, error_message, is_truncated and repeated content_parts for multimodal segments (ADK, ‘Schema Reference’). Long-open work is therefore represented by paired rows (for example TOOL_STARTING then TOOL_COMPLETED, or TOOL_PAUSED joined to its resume row) rather than by updating one span record (ADK, ‘Captured events summary’ and ‘Agent workflow and pause/resume events (ADK 2.0)’).

Delivery behavior depends on the language and version. In ADK Python v2.7.0 and later, the schema is version 2. Every Python row gets a stable event_id before it is queued. The ID has 32 hexadecimal characters. It stays the same through Storage Write API retries. This works “so consumers can identify duplicate rows”.

In default delivery mode, readers remove duplicates themselves. The documented pattern is the consumer-side QUALIFY event_id IS NULL OR ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY timestamp) = 1. The event_id IS NULL OR guard matters. It “retains rows written before the column was introduced”. Rows written before schema version 2 have NULL. Historical null-ID rows are therefore kept. They are not collapsed into one row.

That key does not generalise across BQAA. “The Java schema does not include event_id”. A table created from the manual DDL remains Java-compatible. That is because the column is nullable.

Kotlin populates only timestamp, event_type, agent, session_id, invocation_id, user_id and content. It leaves event_id always null. It also leaves the remaining columns always null.

Retry guarantees need separate care. Python has an opt-in exactly_once_delivery mode. That mode “is not a lossless-delivery guarantee”. Batches can still drop after retry exhaustion. They can also drop during stream-rotation backoff (ADK, ‘Delivery and deduplication’ and ‘Schema Reference’).

The BQAA QUALIFY pattern does one job. It removes duplicate deliveries of the same row. It does not merge start/end lifecycle events into a run.

SmithDB separately documents a different operation. It merges a run’s lifecycle events at query time. It also deduplicates scanned rows (Intro, ‘Multiple events per run’). That does not establish an equivalent duplicate-delivery retry guarantee. Comparative retry guarantees are therefore UNVERIFIED.

For Python-written rows in default mode, BQAA leaves duplicate-delivery deduplication to every reader.

Storage, portability, deployment

Production DDL is a native BigQuery table partitioned by day and clustered on event_type, agent and user_id rather than on trace_id or session_id:

CREATE TABLE `project.adk_agent_logs.agent_events` ( … )
PARTITION BY DATE(timestamp)
CLUSTER BY event_type, agent, user_id;

(ADK, ‘Manual DDL for production setup’). The plugin creates the table if missing; in Python and Java it can add columns automatically (Python auto_schema_upgrade / Java autoSchemaUpgrade, additive only; Kotlin does not implement Auto Schema Upgrade); and by default in Python it creates flat per-event-type views (v_llm_request, v_tool_completed, …) that unnest JSON into typed columns to avoid “repetitive JSON_VALUE and JSON_QUERY expressions”; Java creates views only when createViews(true) is set and Kotlin creates none (ADK, ‘Automatically Created Views’ and ‘BigQueryLoggerConfig options’). Large payloads follow the opposite split from SmithDB’s late materialisation in Python and Java: inline content is capped by max_content_length/maxContentLength (default 500 * 1024) before offloading or truncating, and with gcs_bucket_name/gcsBucketName set, large text and multimodal content go to Cloud Storage while content_parts keeps an object_ref to the gs:// URI, readable back via signed URLs with OBJ.GET_ACCESS_URL; those Python/Java batching, offloading and view-creation options do not exist in Kotlin (ADK, ‘BigQueryLoggerConfig options’, ‘BigQueryLoggerConfig Builder options’, ‘BigQueryLoggerConfig properties’ and ‘Storage behavior: GCS offloading’). That aligns with BigQuery object tables generally — “read-only tables over unstructured data objects that reside in Cloud Storage” whose inference results can be joined “with the rest of your structured data in BigQuery” (BigQuery docs, ‘Introduction to object tables’) — but it also means the full payload may live outside the row any text predicate can reach. Whether such Python/Java offloaded or truncated content remains searchable through any BQAA-documented path is UNVERIFIED; the ADK page documents retrieval by signed URL, not search over offloaded bytes (ADK, ‘Querying Offloaded Content (Get Signed URLs)’).

Judgement: portability means opposite things here. SmithDB portability is operational: stateless services over object storage that LangChain can deploy self-hosted or multi-cloud (Intro, ‘Portability’). BQAA portability is data ownership: traces land in the customer’s own BigQuery dataset (the ADK page documents the IAM roles the writing principal needs), queryable as BigQuery tables with SQL, with the analysis SDK open source under Apache-2.0 (SDK README at e42366f; ADK, ‘Schema and production setup’). No BQAA deployment outside BigQuery is documented in the sources reviewed (UNVERIFIED whether any such option exists elsewhere); likewise, no way to query SmithDB as warehouse tables joined to business data is documented in the sources reviewed (UNVERIFIED beyond those sources). Teams should pick which kind of “portable” they actually need.

Random access and filtering

Random access is a SQL predicate, optionally wrapped by the SDK. The documented recipe fetches one conversation turn with WHERE trace_id = 'your-trace-id' ORDER BY timestamp ASC, projecting JSON_VALUE(content, '$.response') as a summary (ADK, ‘Trace a specific conversation turn using trace_id’), and span hierarchy comes from selecting span_id/parent_span_id with duration extracted from latency_ms JSON for completed operations (ADK, ‘Span Hierarchy & Duration Analysis’). The SDK wraps this as client.get_trace("trace-abc-123") rendering a hierarchical tree, with structured access to tool calls, final response and error spans (SDK reference at e42366f, section 2). Filtering is documented two ways. In SQL it is predicates over typed columns and, where created (Python by default, Java opt-in, Kotlin none), views — recent tool and LLM errors are twenty-row ordered selects over v_tool_error/v_llm_error (ADK, ‘Error Analysis (LLM & Tool Errors)’) — with timestamp documented as the daily partitioning key (ADK, ‘Schema Reference’). In the SDK, client.list_traces() discovers sessions “using rich filtering criteria — no SQL required”, with TraceFilter examples filtering by agent, time window, has_error, minimum latency and explicit session IDs (SDK reference at e42366f, section 2, ‘List & Filter Traces’). No latency percentile for trace load, run filtering, or any interactive workload is published in the ADK page, SDK README or SDK reference as fetched; BQAA interactive latency is therefore UNVERIFIED, and this brief invents no number to set against SmithDB’s table. Two structural observations can still be made from sourced facts alone: the default clustering (event_type, agent, user_id) does not include trace_id or session_id (ADK, ‘Manual DDL for production setup’), and BigQuery search indexes — the engine’s point-lookup accelerator — are never mentioned in the ADK page (full-text check of the fetched page: zero occurrences of SEARCH(, CREATE SEARCH or “search index”). Whether equivalent guidance exists elsewhere in the SDK repository beyond the files read for this brief is UNVERIFIED.

Full-text search and JSON filtering: engine documented, BQAA wiring not documented in the sources reviewed

BigQuery documents the following engine primitives. A search index “is a data structure designed to enable very efficient search with the SEARCH function” and can also optimise =, IN, LIKE and STARTS_WITH (BigQuery docs, ‘Manage search indexes’; BigQuery docs, ‘Search indexed data’). By default it indexes STRING, ARRAY<STRING>, string-bearing STRUCT and JSON columns, tokenised by the default LOG_ANALYZER, which “works well for machine generated logs and has special rules around tokens commonly found in observability data” (BigQuery docs, ‘Manage search indexes’). Search indexes exist precisely to “efficiently find unique data elements that are buried in unstructured text and semi-structured JSON data, without having to know the table schemas in advance”, enabling “efficient row lookups when you need to find individual rows of data” (BigQuery docs, ‘Introduction to search in BigQuery’). SEARCH itself “provides tokenized search on data” and does not require an index to run: it is “designed to be used with an index to optimize lookups”, queries return correct results “even if some of the data isn't indexed yet” while performance “can be greatly improved with an index”, and the usage example shows a SEARCH query completing with indexUsageMode UNUSED because “the table doesn't have a search index” — the index only accelerates SEARCH, it does not enable it (BigQuery docs, ‘Search indexed data’). SEARCH can target whole tables or column subsets and saves most when matches are “a relatively small fraction of the total rows” (BigQuery docs, ‘Search indexed data’). JSON filtering without an index is also native: the JSON type supports schema-on-read storage where BigQuery “can encode and process each JSON field individually” and field-access queries are “intuitive and cost efficient” — with the sharp edges that JSON columns cannot partition or cluster a table and nesting is capped at 500 (BigQuery docs, ‘Work with JSON data in GoogleSQL’). BQAA’s own recipes use exactly this unindexed path, extracting with JSON_VALUE(content, '$.usage.total') and JSON_VALUE(latency_ms, '$.total_ms') over the base table (ADK, ‘Token usage analysis’ and ‘Latency Analysis (LLM & Tools)’).

Three gaps separate that engine capability from SmithDB’s productised search, each grounded in the docs. First, activation: “Search indexes are designed for large tables. If you create a search index on a table that is smaller than 10GB, then the index is not populated” (BASE_TABLE_TOO_SMALL), and active indexes incur storage costs (BigQuery docs, ‘Manage search indexes’; BigQuery docs, ‘Pricing’) — small or new BQAA deployments get correct-but-unaccelerated SEARCH until they cross that size threshold; no corresponding SmithDB size threshold is stated in the sources reviewed, and whether SmithDB imposes any equivalent threshold is UNVERIFIED. Second, semantics: “The SEARCH function is designed for point lookups. Fuzzy searching, typo correction, wildcards, and other types of document searches are not available”, indexes cannot be created on views or external tables, and indexed queries “are not accelerated by BigQuery BI Engine” (BigQuery docs, ‘Limitations’). The worked examples define multi-term search as token containment where “the order of terms doesn't matter” (BigQuery docs, ‘Search indexed data’); no positional phrase semantics comparable to SmithDB’s adjacency-checked json_key_search (FTS-1, ‘SmithDB search query shapes’) appear in the BigQuery pages reviewed, so phrase search on agent_events is UNVERIFIED and should not be assumed. Third, wiring: where they are created (Python by default, Java opt-in, Kotlin none), BQAA views flatten JSON (ADK, ‘Automatically Created Views’) but, in the sources reviewed, no CREATE SEARCH INDEX DDL, no SEARCH(content, …) recipe, and no guidance mapping SmithDB’s three shapes (path exists / path+value / any value) onto BQAA columns. On the sources reviewed, a BQAA user who wants “find runs whose tool output mentions timeout” can run SEARCH without an index today; only to obtain index acceleration must they discover and create the index themselves and pay its storage cost when active (and cross the 10 GB population threshold above) (BigQuery docs, ‘Search indexed data’; BigQuery docs, ‘Pricing’). No BQAA-documented path-pattern (LIKE on key paths) or positional phrase predicate was found in those sources; whether either exists in BQAA or BigQuery surfaces beyond the pages reviewed is UNVERIFIED.

Judgement: on the sources reviewed this remains a product-wiring and evidence gap rather than an engine-availability gap: SEARCH runs without an index and BigQuery documents the accelerating index, but in those sources BQAA does not document turning the index on for agent_events or benchmark content search for traces (UNVERIFIED whether such guidance exists in BQAA surfaces beyond the sources reviewed). Performance parity with SmithDB’s vendor-reported P50 400 ms (Intro, ‘Performance’) is therefore UNVERIFIED — unbenchmarked in the sources reviewed, not shown to be slower.

Tree-aware queries and threads

BQAA stores parent links for the tree. Its parent_span_id is the “16-character hex Span ID of the immediate caller. Used to reconstruct the parent-child execution tree (DAG)” (ADK, ‘Schema Reference’). For one trace, the SDK reconstructs that DAG. It also renders it (SDK reference at e42366f, section 2).

But the sources reviewed do not contain a tree-aware filter. In those sources, there is no documented equivalent for either request:

  • “return root traces where any descendant is a failed RetrieveDocs run” (tree_filter)
  • “condition on the root run while returning children” (trace_filter) (TQS, ‘Using trace_filter and tree_filter’)

Whether such a helper exists in BQAA surfaces beyond the sources reviewed is UNVERIFIED.

The ADK recipes work more narrowly. They filter within one known trace_id (ADK, ‘Span Hierarchy & Duration Analysis’). On that documented path, cross-trace descendant filtering is hand-written SQL. One example is an EXISTS/semi-join over trace_id and span IDs. Its cost in the sources reviewed is UNVERIFIED. Its correctness also falls on the author. That includes duplicate rows and identity collisions.

The SDK is commendably explicit about one such trap. A session_id “is not a globally unique trace key”. Singular session reads resolve identity plus scope. When identity is ambiguous, they raise AmbiguousSessionError with candidate selectors rather than choosing the newest row implicitly (SDK reference at e42366f, section 2, ‘Resolve a Session Safely’).

Threads map to that same session_id. It means the whole conversation thread. It covers all turns and sub-agent calls (ADK, ‘Schema Reference’).

Threads are reconstructed by grouping events per session. The root-cause recipe does this with STRING_AGG. It orders the events by timestamp (ADK, ‘AI-powered root cause analysis’).

Session discovery is not DIY SQL. It is itself a documented SDK API. client.list_traces() is introduced as “Discover sessions using rich filtering criteria — no SQL required”.

In the worked examples, TraceFilter supports filtering by:

  • agent
  • start/end time
  • error
  • minimum latency
  • explicit session IDs (SDK reference at e42366f, section 2, ‘List & Filter Traces’ and ‘Filter by Session IDs’)

This sits alongside the identity-safe singular reads above.

One thing is still missing in the sources reviewed. No published latency for list_traces() appears there. SmithDB publishes vendor-reported threads-filtering figures of P50 131 ms / P95 268 ms (Intro, ‘Performance’). Performance parity with those figures is therefore UNVERIFIED. The API exists. Its speed relative to SmithDB is unbenchmarked here.

Aggregations, evaluation, and analysis beyond the trace

Token and latency aggregates are documented as queries. They run over the per-event views, where those views are created. Python creates them by default. Java is opt-in. Kotlin creates none.

The examples include:

  • average prompt, completion and total tokens from v_llm_response
  • average total latency
  • average time-to-first-token latency
  • tool latency grouped by name and origin (ADK, ‘Token usage analysis’ and ‘Latency Analysis (LLM & Tools)’)

These SQL recipes query BigQuery tables and views, grouping and filtering by fields such as agent and tool origin.

Adding further time windows is ordinary SQL over the same dataset. Joining to non-trace tables is also ordinary SQL over the same dataset. It is not a per-trace rollup field (Mig-Traces, ‘Traces: query’).

The SDK adds deterministic session metrics:

  • latency
  • turn count
  • error rate
  • token efficiency
  • context-cache hit rate
  • estimated cost per session

The caveats are unusually careful. Token totals prefer explicit provider totals. They may include thinking tokens. cost_per_session() “does not consume a separate thoughts_token_count field, so do not treat it as provider invoice reconciliation” (SDK reference at e42366f, section 3).

The SDK also adds evaluation depth:

  • LLM-based performance metrics
  • multi-trial pass rates
  • weighted/binary/majority grader composition
  • eval-suite lifecycle
  • drift detection (SDK README at e42366f, ‘Key Features’)

It also has a client.insights() pipeline. It generates seven analysis sections. It builds them from per-session facets. The sections are:

  • Task Areas
  • Interaction Patterns
  • What Works Well
  • Friction Analysis
  • Tool Usage Patterns
  • Improvement Suggestions
  • Trends & Anomalies (SDK reference at e42366f, section 10)

These evaluation and insights layers have no SmithDB counterpart documented in the sources reviewed (UNVERIFIED beyond those sources). In those sources, SmithDB is described as a store. These are analysis layers.

Two more shapes documented for BQAA in the sources reviewed deserve note. Traces can be reasoned over in SQL with models in the loop: AI.GENERATE root-cause analysis over a reconstructed failed session, and multimodal analysis passing content_parts object references to a remote model (ADK, ‘AI-powered root cause analysis’ and ‘Analyze Multimodal Content with BigQuery Remote Model (Gemini)’); natural-language querying is available through Conversational Analytics agents connected to agent_events (ADK, ‘Conversational Analytics’). And decisions can be materialised as a property graph — “the requests it handled, the options it weighed, and the outcomes it chose” — queryable in GQL to “trace why a decision happened … not just that an event was logged”, refreshed on a schedule via bqaa context-graph (ADK, ‘The context graph’).

The SDK also exports BigQuery tables to LangSmith as run trees. It reconstructs the span_id/parent_span_id hierarchy. It uses stable derived UUIDs. Replay is idempotent (SDK reference at e42366f, section 23).

The same section states material limits (SDK reference at e42366f, section 23, ‘Backfill and incremental CLI’):

  • Scheduling: the v1 connector is “one-way and scheduled/batch only”. It has no real-time streaming surface.
  • ±24-hour restriction: LangSmith Cloud “accepts a run only when its start_time lies within 24 hours of the current time, in either direction”. Bounded backfill therefore “cannot import trace history that has aged out”. Incremental export must run frequently enough to land inside that ±24-hour window.
  • Self-hosted limits: self-hosted deployments “may enforce a different limit”.
  • Missing parents: each export window reconstructs hierarchy only from rows in that window. A child’s parent may have been exported earlier. That child “is attached to the synthetic root”. Its original parent ID is kept in extra.bqaa.source_parent_run_id.

The two systems interoperate in one direction, for recent traces on a schedule. This is not a live serving path or a history migration.

Cost and deployment complete the axes. The charges explicitly stated in the sources reviewed are the paid Storage Write API used by the Python and Java plugins (Kotlin writes via tabledata.insertAll instead) (ADK, ‘BigQuery Storage Write API’ and ‘Kotlin support’) and search-index storage when active, with index builds free only below regional limits (BigQuery docs, ‘Pricing’). Section 12 now lists the fetched Storage Write API and BigQuery storage/query rates and works through list-rate scenarios. AI.GENERATE model-call costs behind the documented recipes (ADK, ‘AI-powered root cause analysis’) remain outside that model, search-index storage has no workload-specific dollar estimate, and actual comparative operating cost remains UNVERIFIED (see Not verified). Deployment is the customer’s BigQuery project plus optional dashboards (Looker Studio template, Looker Block, notebooks) and SDK surfaces including a CLI, a BigQuery Remote Function and continuous-query templates (ADK, ‘Build a dashboard’; SDK README at e42366f, ‘Deployment Surfaces’).

On table-schema change alone, the sources reviewed report no SmithDB-style breaking method migration for BQAA.

In Python and Java, table-schema change arrives as additive auto-upgrade. Kotlin does not implement Auto Schema Upgrade (ADK, ‘BigQueryLoggerConfig options’, ‘BigQueryLoggerConfig Builder options’ and ‘Kotlin support’).

Python automatically adds the schema-version-2 event_id column by default (auto_schema_upgrade=True). Manual-DDL users are told to add it before ADK Python v2.7.0. The Java schema does not include event_id (ADK, ‘Schema Reference’).

That additive claim has limits. It does not extend to plugin configuration. It does not extend to telemetry.

Java configuration changed in v1.8.0 and later. datasetId is required. tableName defaults to agent_events. In Java v1.7.0 and earlier, those values defaulted to agent_analytics and events respectively (ADK, ‘BigQueryLoggerConfig Builder options’). Java callers who relied on the old defaults must now set them explicitly. Or they must move tables.

Plugin-driven OpenTelemetry export has also been removed. The plugin “does NOT export OTel spans of its own”. It tracks spans on an internal stack instead. Hosts that used the plugin as an OTel side channel must configure OTel instrumentation in the host application (ADK, ‘Tracing and observability’).

13 / ScopeDB at Raft

13. ScopeDB at Raft: agent-written pipelines over warehouse traces

In plain terms

This section was added on 2026-10-29. It is a fourth data point, not a fourth column in the earlier tables.

  • Raft keeps service traces and product events as rows in ScopeDB, beside PostgreSQL business state.
  • Its observability agents write pipeline queries to check whether a new release broke something.
  • The pipeline idea is not unique to ScopeDB: BigQuery documents its own pipe syntax.
  • The transferable lessons for BQAA are dedicated nullable version columns (population depends on the producer), an event registry that states its question, and product events beside traces.

ScopeDB scale and example counts below are vendor-reported. No ScopeDB latency percentiles are published in the sources reviewed; ScopeDB interactive latency is therefore UNVERIFIED.

Raft is “an agent-native workspace where AI agents work alongside people as first-class teammates in shared channels, threads, and tasks” (SDB). PostgreSQL owns its business state, RisingWave maintains live views from PostgreSQL changes, Redis coordinates running services, and ScopeDB “sits alongside those workflow systems to store and analyze the high-volume stream of observations they produce” (SDB, ‘More agents, more events to investigate’). That placement will look familiar after section 5: where BQAA puts harness lifecycle events into the customer’s BigQuery dataset (ADK, ‘BigQuery Agent Analytics plugin for ADK’), Raft puts service/database spans and product events into a managed ScopeDB workspace, queried after the fact by engineers and by dedicated observability agents (SDB). The two traces are of different subjects — Raft traces its platform and product, BQAA traces agents inside an invocation (section 5) — so this section compares contracts and query ergonomics, not feature parity.

The trace contract is code, fingerprinted

The public mirror lets this brief check the blog against the writers. raft.trace_events_v2 is a code-owned projection of 67 explicitly named columns — resource identity including service_version and deployment_environment, trace/span identity, row_kind (event or span_fact), and promoted failure fields db_system, query_name, phase, outcome, reason, sqlstate and heuristically scrubbed error_message — generated into one ingest statement so “every producer uses one reviewable, type-checked statement”, with SHA-256 schema fingerprints kept for the current, previous (66-column) and legacy (59-column) projections during additive rollouts (RS, eventRows.ts). Writes are batched and fail-aside: the server sink streams through the ScopeDB SDK at a default batch of 128 rows with a one-second flush, carries out live-schema validation on the first nonempty export, enabled by default, against the code projection, and counts dropped rows rather than hiding them, under an explicitly non-authoritative “decision_support” persistence tier (RS, scopeDbTraceEventSink.ts). Product behaviour goes to a second table, product.events, pairing typed columns (uuid, event, app_version, platform, timestamps) with a semi-structured properties object, written in committed batches of up to 500 by default with bounded retries (RS, productEventScopeDbWriter.ts).

Two registries are the product-level point. Trace families are registered with a privacy tier and named consumers — the server.db.query family’s consumer is a related database-failure investigation over trace_events_v2, grouped by db_system/query_name/phase/sqlstate/timeout_bucket/retryable (RS, traceFamilyRegistry.ts) — and those span fields are produced by one wrapper that classifies failures into bounded diagnostic vocabularies (statement_timeout for SQLSTATE 57014, client_aborted, database_error, unknown) with heuristically scrubbed error text; the scrubber is fail-open and may retain unrecognized row values (RS, queryTrace.ts). Product events are stricter still: every registered event must state “The question this event answers” and who asked, properties have registered types and constraints, including high-cardinality operation IDs, and ingest rejects and counts anything unregistered (RS, productEvents.ts). Their effect on agent-query reliability has not been measured.

ScopeQL pipelines, and BigQuery’s own pipe syntax

ScopeQL is documented as pipelines: “Each clause takes the rows produced by the preceding clause, so you can filter a calculated column or aggregate a filtered result without wrapping it in a subquery”, with repeatable SELECT/WHERE, keyed DISTINCT ON, and GROUP BY … AGGREGATE stages that can repeat (ScopeQL query syntax). The blog’s release check uses exactly that shape — filter production server.db.query span facts to the last hour, DISTINCT ON service_name, trace_id, span_id, then group by service_version, db_system, query_name, outcome — and claims the flat pipeline avoids “the nested subqueries or CTEs where agent-generated SQL often loses column scope” (vendor-reported; no LLM query-error measurement is published, so any reliability advantage is UNVERIFIED) (SDB, ‘An agent can follow a failure across the system’). Typed columns plus an object payload is also ScopeDB’s documented modelling guidance — stable fields typed, flexible fields queried inside the object and promoted later without rewriting history (Model event data) — with columnar storage, index pruning and additive indexes (including over object paths) behind it (Understand storage; Add indexes), and storage/compute separation over shared object storage with separate compute groups over the same committed tables (SDB, ‘Grow the history without replacing the database’; Cloud Elasticity).

For a BigQuery reader the syntax claim needs one correction of omission. BigQuery GoogleSQL already documents pipe syntax: “Each pipe operator in pipe syntax consists of the pipe symbol, |>, an operator name, and any arguments”, a query can start with FROM, and each operator consumes the table passed through the pipe (SQL-Doc, ‘Pipe query syntax’). The same release-regression question therefore has a flat BigQuery form (illustrative translation over a same-shaped table, not executed for this brief). The BigQuery examples prefer the latest timestamp within each deduplication key; ScopeQL without BY chooses an unspecified row. Grouped results agree only when duplicate rows agree on the grouping dimensions:

FROM `proj.raft.trace_events_v2`
|> WHERE deployment_environment = 'production'
    AND span_name = 'server.db.query' AND row_kind = 'span_fact'
    AND event_time >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR)
    AND event_time < CURRENT_TIMESTAMP()
|> SELECT *, ROW_NUMBER() OVER (
      PARTITION BY service_name, trace_id, span_id
      ORDER BY event_time DESC) AS rn
|> WHERE rn = 1
|> AGGREGATE COUNT(*) AS operations
   GROUP BY service_version, db_system, query_name, outcome
|> ORDER BY operations DESC;

Honestly scored: pipe form genuinely helps where standard SQL nests — sequential roll-ups such as the blog’s dedupe-by-uuid, per-operation, then per-version/platform funnel over two consecutive GROUP BY … AGGREGATE stages (SDB, ‘The same database answers product questions’) — and BigQuery’s pipes recover most of that, since operators including WHERE, SELECT and AGGREGATE … GROUP BY can be applied in sequence to the preceding table (SQL-Doc). What BigQuery pipe syntax does not give back is keyed deduplication as a clause: its DISTINCT pipe operator dedupes on all visible columns, not on named keys, hence the ROW_NUMBER stage above (SQL-Doc, ‘DISTINCT pipe operator’). Whether BQAA’s own recipes teach pipe syntax anywhere beyond the ADK page as fetched is UNVERIFIED; on that page the documented recipes are standard-syntax SQL (ADK).

What BQAA could take from Raft, in order: first, a version-first contract — deployment version/revision/environment as documented columns plus the release-regression recipe as a supported query, since Raft’s check is a single grouped count over dedicated nullable version columns; population depends on the producer (RS, eventRows.ts). Third, product events beside agent events in the same dataset, so feature funnels join agent behaviour with ordinary SQL (SDB, ‘The same database answers product questions’). Fourth, teach BigQuery pipe syntax as the agent-query dialect and publish an error-rate comparison, instead of leaving the pipeline frame to competitors (SQL-Doc). The go-to-market lesson is organisational as much as technical: ScopeDB’s strongest artefact is a shared channel where the vendor, the customer CTO and the customer’s observability agents verify release telemetry together, quoted by Raft’s CTO as a “two-way build” (vendor-reported testimonial) (SDB); BQAA’s equivalent proof would be a named agent running scheduled regression queries over its own agent_events in production. Whether that joint-room pattern repeats beyond Raft is UNVERIFIED.

Judgement: ScopeDB at Raft confirms this page’s central BQAA thesis — traces as warehouse rows, queried later by agents — while showing concrete contract patterns; the registry and promoted columns are worth testing, and their contribution relative to query syntax remains UNVERIFIED. Raft’s agent-written pipelines group on promoted columns combining bounded diagnostic values with string-valued versions, query names, database systems, phases, and SQLSTATEs, governed by code registries (RS, eventRows.ts; queryTrace.ts; traceFamilyRegistry.ts). Their effect on agent-query reliability has not been measured. In these examples, ScopeQL offers concise keyed deduplication, while BigQuery also supports linear pipelines (SQL-Doc). BQAA keeps the deeper analysis layers (section 5) and customer-owned data; it should copy Raft’s version-first schema, event registry and product-event companion, and answer the syntax pitch with documented pipe-syntax recipes and measured agent-query error rates — until then, relative agent-query reliability and all ScopeDB interactive performance remain UNVERIFIED.
