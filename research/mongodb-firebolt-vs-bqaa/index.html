MongoDB + Firebolt and BigQuery Agent Analytics: how they differ

TL;DR

  • On 17 November 2026, MongoDB said it had acquired Firebolt, a high-performance analytical database, and plans to run Firebolt’s engine next to MongoDB so applications and agents can analyze live data; it is not available yet, and there is a waitlist (MongoDB post; waitlist).
  • BigQuery Agent Analytics (BQAA) does a different job: it records what agents do, such as requests, responses, tool calls and errors, in BigQuery, Google Cloud’s data platform, so teams can debug, monitor and evaluate them (BigQuery guide; BigQuery overview; ADK docs).
  • In our judgement, BQAA’s closest MongoDB counterpart is not Firebolt but the tracing built into Atlas Agent Engine, MongoDB’s agent platform, which is in public preview (trace docs; Atlas Agent Engine docs).
  • BQAA was announced generally available in Google’s Agent Development Kit (ADK) in April 2026, in a note that names no language, and its maturity varies by language: Python’s plugin reached version 2.0 in December 2025, while the Go and JS plugins arrived in November 2026 (release notes; Python; Go; JS).

Prepared and sources fetched on 18 November 2026, Pacific time. Written from the BQAA side, so weigh its judgements accordingly.

Main sources: MongoDB’s announcement, MongoDB Acquires Firebolt to Bring Lightning-Fast Real-Time Analytics Into Its Intelligent Data Platform (17 November 2026); Firebolt’s What is Firebolt?; the ADK BigQuery Agent Analytics plugin page; and the BigQuery guide Use BigQuery agent analytics. 01 / The news

1. What MongoDB announced

On 17 November 2026, MongoDB published “MongoDB Acquires Firebolt to Bring Lightning-Fast Real-Time Analytics Into Its Intelligent Data Platform”, written by Fred Roma, its Senior Vice President of Engineering (post).

The reasoning fits in one line. MongoDB customers’ operational data already lives in MongoDB, “so analytics should be able to run there too, at the source. That’s why MongoDB acquired Firebolt.” (post)

You cannot use it yet. The post says the teams “are already working together to bring Firebolt’s engine into MongoDB”, and that customers will be able to turn on real-time analytics in the coming months. Until then, MongoDB offers a waitlist (post; waitlist page).

If you already use Firebolt, the post says “Nothing changes” and you “can continue using the product with the same support and service” (post). Firebolt’s own site now carries a banner: “Firebolt is joining MongoDB to bring real-time analytics into their Intelligent Data Platform” (firebolt.io).

Plans can change, and the post says so: its forward-looking statements notice covers “the anticipated benefits, integration, and future development of Firebolt’s technology”, and warns that “actual results may differ materially” (post).

02 / The company MongoDB bought

2. What Firebolt is

MongoDB says data infrastructure has long been split into “two worlds: operational databases that run applications, and data warehouses that analyze what already happened” (post). Firebolt sits on the analytics side. It calls itself “a high-performance analytical database” that “runs as a single binary on a laptop and scales to hundreds of nodes and petabytes of data on object storage in your own cloud” (What is Firebolt?). MongoDB’s FAQ adds that it is “designed for low-latency queries and high-concurrency applications”: fast answers to many queries at once (post).

  • It uses standard SQL (What is Firebolt?).
  • It keeps real-time data in its own storage format and reads open formats, Parquet and Iceberg, for batch work, “so there is no lock-in” (What is Firebolt?).
  • It runs as a single binary, on Kubernetes or as a managed service; AWS and GCP are generally available (GA) and Azure is in preview, and self-managed Firebolt is in preview too (What is Firebolt?).
  • Its MCP (Model Context Protocol) server, which Firebolt calls “a bridge between your data warehouse and AI assistants”, lets clients built on large language models (LLMs) write and execute SQL against Firebolt (Firebolt MCP Server).
  • It has its own route from MongoDB: a change data capture (CDC) feature, in private preview (early access on request), that keeps a Firebolt table continuously in sync with a MongoDB collection and stores each document whole, as JSON (Firebolt MongoDB CDC).

03 / The reasoning

3. Why MongoDB wants it

MongoDB’s argument is about where analytics runs. Its post says that copying operational data into a separate system means building and maintaining pipelines, keeping systems in sync and running another platform, with a “risk of stale answers”; it calls this “the data-movement tax” (post).

MongoDB’s plan: “Firebolt’s engine will run right alongside your database, and we’ll keep it in sync automatically, so there’s no pipeline to build or manage.” The post says customers will get “one platform for operational and real-time analytical workloads” (post).

Agents are a big part of the pitch. MongoDB says they “act continuously, can drive thousands of concurrent queries, and need sub-second answers on fresh data” (post).

It is not meant to replace a warehouse. Asked whether it does, MongoDB’s FAQ answers: “No. Traditional data warehouses and data lakes remain the right fit for internal BI, reporting, and data science” (BI is business intelligence); real-time analytics is for “application-facing analytics” (post).

Real-time analytics will extend MongoDB’s platform, which the post says already brings together operational data, search and vector search, AI models, stream processing, and the ability to build and run agents in production. Over time, MongoDB says, customers will also be able to analyze data from other sources and formats alongside their MongoDB data (post). For reference, MongoDB stores data records as BSON documents, a binary representation of JSON documents (MongoDB manual).

04 / Our side

4. What BQAA is

BigQuery Agent Analytics (BQAA) is a plugin for the Agent Development Kit (ADK), which its site calls “the open-source agent development framework that lets you build, debug, and deploy reliable AI agents at enterprise scale” (ADK home). When an agent runs, the plugin “captures and logs critical operational events directly into a Google BigQuery table”, for debugging, real-time monitoring and offline evaluation (ADK docs).

BigQuery itself is a “fully managed, AI-ready data platform” for managing and analyzing data (BigQuery overview). BigQuery’s guide says its logging integrations write through the Storage Write API, which gives “high-throughput, low-latency log streaming without blocking agent execution” (the language notes below cover Kotlin, where the ADK page and the code differ). The same guide calls BQAA “an open source solution” that streams “requests, responses, tool calls, and errors” into BigQuery, and says it is supported in ADK and in LangGraph, another agent framework (BigQuery guide).

  • Where the data lands: a table in your own Google Cloud project, agent_events by default in ADK, with a predefined schema that tracks metrics such as token use and latency (BigQuery guide; ADK docs).
  • How you use it: SQL, which can use AI.GENERATE for automated root-cause analysis of errors or join agent events with your business tables; dashboards; notebooks; and a Python software development kit (SDK) that reconstructs and evaluates multi-turn agent traces (BigQuery guide). The ADK page adds a Looker Studio template and a Looker Block (ADK docs).
  • Other frameworks: a LangGraph and LangChain callback handler in Python, or direct ingestion through the Storage Write API for custom frameworks (BigQuery guide).
  • Safety and cost: BigQuery’s access controls, data masking and encryption can secure the logs (BigQuery guide), and the Storage Write API is a paid service (ADK docs).

ADK is available in Python, TypeScript, Go, Java and Kotlin (ADK home), and the plugin’s code exists in all five: Python, Go, Java, Kotlin and JS (TypeScript), each at a release tag. The ADK page lists four of them (Python from v1.21.0, Go from v0.1.0, Java from v1.5.0, Kotlin from v0.8.0) but not JS (ADK docs). The JS plugin says it writes the same table schema as the Python one, so Python and TypeScript agents can share one table and its views (JS source).

Features differ by language. The ADK page says Java records only one of the four workflow event types added for ADK 2.0 (TOOL_PAUSED), and its Kotlin notes describe rows inserted one at a time (ADK docs), while ADK Kotlin v1.6.0, released 17 November 2026, lists “write analytics rows in background batches” (Kotlin release notes). This page does not compare languages feature by feature; section 5 shows where each one stands.

08 / Overlap

8. Where they meet

Both are about agents, from opposite ends

MongoDB says real-time analytics will let “applications and agents” analyze live data and act on it (post). BQAA exists to log and analyze what agents do (ADK docs).

The real overlap is agent tracing

MongoDB defines a trace as “a record of everything that happens while your agent processes a request” (trace docs). Atlas Agent Engine’s runtime “traces every model call, tool call, and memory access” (Atlas Agent Engine), and each trace is organized as sessions, runs and steps, with each step’s duration and each model call’s token count (trace docs). BQAA covers similar ground: LLM calls and tool usage, plus user input and model responses (ADK docs).

The difference: where the records go, and what is sent

  • Atlas Agent Engine keeps traces on its own platform by default. You can export them over OTLP, but an export currently has to include full trace content, and metadata-only redaction is not yet available (trace docs).
  • BQAA sends captured event rows to a BigQuery table in your configured project (BigQuery guide). In ADK Python and Go, you can exclude selected columns at write time with an optional payload column denylist; the columns you can list are content, content_parts, attributes and latency_ms (ADK docs).
  • BQAA rows can also line up with Cloud Trace. When the plugin inherits an active OpenTelemetry trace ID, you can use it to match BigQuery rows to the corresponding trace if that trace was exported to Cloud Trace; with no active span, the plugin falls back to a per-invocation trace_id (ADK docs).

Both speak ADK

MongoDB has a guide for running ADK agents on Atlas Agent Engine: its agent-engine-sdk-adk adapter, available for Python only, translates ADK agents, workflow nodes and tool calls into operations that the platform runs and records (ADK guide). BQAA is itself an ADK plugin (ADK docs). Neither MongoDB’s ADK guide (ADK guide) nor the ADK plugin page (ADK docs) says whether the two can be used together.

Could they work together?

Judgement: they need not compete. MongoDB’s FAQ says “Traditional data warehouses and data lakes remain the right fit for internal BI, reporting, and data science” (post), and BQAA’s offline evaluation of agent logs is one example of analysis done in BigQuery (ADK docs). Once MongoDB’s real-time analytics is available, a team could use both: its agents query live business data through MongoDB, while BQAA logs the agents’ own behavior to BigQuery. That is an untested example: neither MongoDB’s ADK guide (ADK guide) nor the ADK plugin page (ADK docs) describes it.

09 / Bottom line

9. Bottom line

Judgement: these two answer different questions. MongoDB + Firebolt asks how an application or agent gets fast answers from live operational data with no pipeline to build or manage; it is announced, not yet available, with a waitlist (post; waitlist page).

Judgement: BQAA asks what an agent did, and records it in BigQuery for debugging, monitoring and evaluation (ADK docs). It was announced GA in ADK on 15 April 2026 (release notes), but maturity varies by language: Go’s plugin is pre-1.0 and the JS plugin arrived in November 2026 (Go release; JS release).

Judgement: for BQAA readers, the MongoDB product to watch is Atlas Agent Engine’s built-in tracing, in public preview, which keeps traces on its own platform by default (trace docs; Atlas Agent Engine docs). The Firebolt deal shows MongoDB wants analytics to run next to the data its customers’ applications and agents rely on, and the announcement does not mention agent telemetry (post).

Gaps

What the sources do not say

What we looked for and could not find, and where we looked:

  • Deal price, terms and closing date: not in MongoDB’s announcement (post). MongoDB’s press-release list, as of 18 November 2026, has no Firebolt release; its newest item is dated 29 September 2026 (press releases). Firebolt’s site banner links to MongoDB’s post, and its blog listing has no post of its own about the deal (firebolt.io; Firebolt blog).
  • Launch date, price and regions for real-time analytics on MongoDB: the post gives no date beyond “In the coming months” (post), and the real-time analytics page shows a sign-up form and no price (waitlist page).
  • Which MongoDB deployments it will cover, Atlas or self-managed: the post does not say (post).
  • How the automatic sync will work, and whether it reuses Firebolt’s MongoDB change data capture (private preview): not stated in the post or the CDC guide (post; Firebolt MongoDB CDC).
  • Agent telemetry in the deal: the post does not mention tracing, telemetry or agent observability (post), and the trace docs do not say whether Atlas Agent Engine traces will be queryable through the Firebolt engine (trace docs).
  • Whether the BQAA plugin runs inside an ADK agent hosted on Atlas Agent Engine: not stated in MongoDB’s ADK guide or the ADK plugin page (ADK guide; ADK docs).
  • Firebolt’s standalone roadmap: the post says “Nothing changes for existing Firebolt customers” and gives no roadmap for the standalone product (post).
  • Launch stage of the plugin in each language: the 15 April 2026 GA note names no language (release notes), and neither the ADK plugin page (ADK docs) nor the BigQuery guide (BigQuery guide) states a launch stage for the plugin in each language.
  • Performance: MongoDB’s announcement (post), Firebolt’s home page (firebolt.io), its docs overview (What is Firebolt?) and its blog listing (Firebolt blog) do not compare Firebolt’s performance with BigQuery’s, and this page makes no comparative performance claim.
